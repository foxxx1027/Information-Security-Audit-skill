# API 盲区优先级与三准则 (vf20)

## R — 原文 (Reading)

> 「传统的漏洞扫描器很难进行高覆盖率漏洞扫描，因为爬虫无法抓取到这种API接口，所以接口的SQL注入等漏洞就相对较多」「必要的情况下加入账户体系，严格控制数据调用权限……加入不可暴力破解的访问密钥」「用户资料的API就存在注册邮箱信息泄露……类似于这种没必要输出的信息应该要注意禁止输出」

> — 原作者, 原始方法论来源第11章 11.14（source.txt 行17617、行17621、行17623）

---

## I — 方法论骨架 (Interpretation)

资源有限时"先测哪里"不按资产名气排，按一条定律排：**漏洞密度与检测覆盖率成反比**。爬虫/扫描器抓不到的入口，长期缺检，漏洞存量最大。App 专用接口、无页面链接的回调、深层协议端点都属此类（乌云搜"接口"上千条是作者给的经验证据）。

配套两条执行纪律：

1. **人工枚举补盲区**: 扫描器覆盖率低的地方，先花功夫做协议级入口盘点——抓包、反编译客户端、翻接口文档，把"看不见的入口"变成清单，这一步本身不可省略也不可外包给爬虫。
2. **三准则排序测试**: 逐接口按三准则核——访问鉴权（登录态/不可爆破密钥/对象级授权）、敏感信息最小化（返回字段 vs 展示需要的差异）、常规漏洞（注入等）。经验排序"未授权访问与数据遍历居首"，因为 API 的字段全、层级深，一个接口泄露一类数据。

产出是优先级矩阵：入口 × 覆盖盲区程度 × 数据敏感度，资源从密度最高处投起。

## A1 — 书中的应用 (Past Application)

### 案例 1: 密度定律——App 接口扫描器抓不到（11.14 行17617）
- **问题**: 为什么 API 接口的注入漏洞"相对较多"。
- **方法论的使用**: 因果归位——不是接口天生更弱，而是检测覆盖率低：爬虫无法抓取 App 内调用的接口，检测少了存量就多。
- **结论**: API 区的安全投入应与"爬不到"程度成正比，而非与页面知名度成正比。
- **结果**: 作者以乌云"接口"关键字上千条结果作经验背书，该定律成为 11.14 的组织原则。

### 案例 2: 知乎 App 资料接口泄露注册邮箱（11.14 行17623，作者抓包证实）
- **问题**: 接口返回字段未按需要裁剪的实际后果。
- **方法论的使用**: 准则二检验——用户资料接口把注册邮箱一并返回，"只要知道某人的知乎账号即可知道他的个人邮箱"。
- **结论**: 没必要输出的信息应禁止输出；API 审计动作=抓包比对各端返回字段与页面展示的差异。
- **结果**: 该案例成为字段最小化准则的定型证据（cs48）。

### 案例 3: 淘宝 API 免登录换发 Cookie（11.2.2 行17259）
- **问题**: API 接口鉴权缺陷的价值上限。
- **方法论的使用**: 准则一检验——登录跳转接口仅凭 user_num_id 即返回该用户 Cookie，无一次性 Token。
- **结论**: 接口鉴权缺陷（改参数登录任意用户）属最高价值类，验证"未授权居首"的排序经验。
- **结果**: 乌云报告后阿里 5 万元奖励并设 500 万悬赏计划——接口鉴权缺陷高价值的行业级证据。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 制定渗透/安全测试计划，决定先测 Web 站点还是 App/小程序/开放 API。
2. 引入 GraphQL、内部服务 API、第三方回调后，评估扫描器覆盖盲区。
3. 排查"接口被无门槛高频调用/数据被遍历"的暴露面。
4. 给客户的测试报告解释"为什么 API 区发现的漏洞密度更高"。

### 语言信号 (用户的话里出现这些就应激活)

- "API 安全测试怎么做 / API security testing / 从哪个接口开始"
- "扫描器爬不到 / scanner can't crawl / App 接口测不全"
- "小程序/GraphQL/内部接口 怎么盘点 / API inventory"
- "接口未授权 / unauthorized API access / 数据遍历 / IDOR on APIs"
- "接口返回了多余字段 / API over-returning fields"

### 与相邻 skill 的区分

- 【组合】`caudit-logic-vuln-audit`: 两边共用"漏洞密度与检测覆盖率成反比"定律——那边盲区在语义维（机器模拟不了业务逻辑），本 skill 盲区在可达性维（爬虫抓不到入口）。正交且可叠加：测试计划可同时按两个维度排优先级；本 skill 第一步是入口枚举而非业务状态机。
- 【组合】`caudit-api-relay-architecture`: 那边是架构侧（API 层收口 + 监控），本 skill 是测试侧（测什么、先测什么），共用"接口是受控与被观测通道"这一判断；那边收口层自身又是新的接口盲区，其 B 段自注的前提正由本 skill 兜住。
- 【组合】`caudit-audit-path-selection`: 那是白盒读码路径选型，本 skill 是黑盒/灰盒测试资源分配；衔接顺序为——先按本 skill 定测试面，再按路径选型决定对入选面怎么读码。

## E — 可执行步骤 (Execution)

1. **盘点入口全集**: 用抓包（各端）、客户端反编译、接口文档、网关路由表枚举全部 API 入口，标注哪些无页面链接（爬虫盲区）。
   - 完成标准: 入口清单含来源标注（页面/抓包/反编译/文档），盲区入口单独成列。
2. **算盲区密度**: 按入口的可达性（爬虫能否发现）× 数据敏感度排序，得出测试优先级。
   - 完成标准: 每个入口有优先级分数或序号，盲区入口排前。
3. **按三准则逐接口核**: 准则一鉴权（未授权可达？对象级授权？密钥可爆破？）→ 准则二字段最小化（返回字段 vs 展示差异）→ 准则三常规漏洞（注入/上传等）。
   - 完成标准: 每个高优接口三准则各有结论。
   - 判停条件: 若接口全部经统一网关且已有完整鉴权中间件，准则一可记录"继承网关"后聚焦对象级授权与字段裁剪。
4. **优先跑未授权与数据遍历用例**: 对高优接口先做"不带凭证调用 + 改对象 ID"两类测试。
   - 完成标准: 两类用例在高优接口上全部执行并记录。
5. **输出优先级报告**: 入口清单 + 盲区标注 + 三准则结果 + 建议纳入常规扫描的部分（可爬部分回填扫描器）。
   - 完成标准: 报告能直接转化为测试计划条目。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 入口已完整枚举后的单接口深入测试——直接做该接口的漏洞分析，无需重排优先级。
- API 的功能测试/契约测试（非安全目标）。
- 纯网络层资产测绘（端口/指纹）——那是资产发现，不是应用接口盲区。

### 作者在书中警告的失败模式

- 把常规扫描覆盖率外推到 API 区，认为"接口已测过"（ce71）。
- 接口按内部结构吐字段，不按调用方需要裁剪（ce72，知乎案例）。
- 无账户体系的接口无访问密钥，被无门槛高频调用消耗资源（行17617 后文）。
- 只验"是否登录"不做对象级授权（与 ce64 越权同根）。

### 作者的盲点 / 时代局限

- 2015 语境：App 专用 HTTP 接口；现代 GraphQL（自省/内省可枚举全部 schema）、gRPC、WebSocket、消息队列消费者均是新盲区形态，枚举手段要换，定律不变。
- 未提 OpenAPI/Swagger 文档泄露这一入口发现捷径，也未提 API 版本治理与废弃接口的残留风险。
- 字段最小化的现代落地需配合 DTO 分层与序列化白名单，作者只给出"禁止输出"原则。
- "未授权居首"是经验排序而非统计结论，迁移时当缺省假设而非定律。

### 容易混淆的邻近方法论

- 与"资产清点/攻击面管理（EASM）"不同：EASM 求全；本 skill 用密度定律做取舍与排序，回答"先测哪"。
- 与逻辑漏洞审计不同：本 skill 的三准则是接口层的快速核对表，不做业务状态机推演。
