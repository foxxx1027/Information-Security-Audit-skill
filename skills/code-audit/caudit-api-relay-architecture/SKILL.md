# 站库分离的安全重构——API 中转 + 阈值监控 (vf23)

## R — 原文 (Reading)

> 「大多数的站库分离只不过是把数据库放到另外一台服务器上……对于安全性的提高并没有什么帮助」「攻击者即使拿到了Web服务器，也无法在短时间内将全部数据拖走，只要我们建立API接口监控，设置一个阈值……这也起到一种入侵检测的作用」

> — 原作者, 原始方法论来源第12章 12.6（source.txt 行17997、行18005）

---

## I — 方法论骨架 (Interpretation)

架构名词不产生安全收益，访问路径与权限收口才产生。评审任何"分离/拆分"方案时先跑一个判别式：**应用是否仍持全权数据库凭证直连数据库端口？** 是——则搬机器、开端口只优化了性能，注入/SSRF 拿到 Web 权限后照样全库拖走，还多开了网络面。

作者主张的重构是"API 式站库分离"，两个要件：

1. **访问收口**: 数据操作全部经 API 层，该层用受限凭证与逐接口权限访问数据——拖库者必须先理解并逐个调用接口，速度被结构性地压下来。
2. **阈值监控内建**: API 层天然有调用画像（频率、返回行数、查询模式），设阈值即可发现"突然被频繁调用"的刷库行为——监控不是另建的外挂系统，是收口架构的副产品，兼作入侵检测。

推论到现代语境：微服务、读写分离、上云等一切拓扑改造，都按同一判别式检验——安全收益看权限收口与可观测性，不看名词。注意作者自注的前提："这一切的前提是API服务器的安全要做好"——收口层自身成为新的高价值目标。

## A1 — 书中的应用 (Past Application)

### 案例 1: 传统站库分离的反迷思（12.6 行17997）
- **问题**: "数据库放另一台服务器"被普遍当作安全措施。
- **方法论的使用**: 判别式检验——Web 仍持数据库密码直连开放端口，攻击者拿下 Web 即直达全量数据。
- **结论**: 该方式"只能优化服务器的效率，对于安全性的提高并没有什么帮助"。
- **结果**: 迷思被显式破除，引出 API 式分离方案（ce77）。

### 案例 2: API 分离 + 阈值监控即入侵检测（12.6 行18005）
- **问题**: 即使收口，拖库仍可能发生，如何发现。
- **方法论的使用**: 副产品思路——收口层建立接口监控与阈值，"遇到监控接口突然被频繁调用的情况，则说明可能存在刷库行为"。
- **结论**: 监控内建于业务架构，无需独立外挂检测系统先行。
- **结果**: "拖不快 + 拖了会被发现"组合构成完整的防拖库设计。

### 案例 3: 接口被无门槛高频调用（11.14 行17617 后文）
- **问题**: 接口频率作为安全观测量的独立佐证。
- **方法论的使用**: 另一功能语境（API 资源滥用）下，调用频率异常同样是最直接的异常信号。
- **结论**: "接口调用频率是安全观测量"跨场景成立——既是滥用防线也是入侵信号。
- **结果**: 与 12.6 互证，支撑"收口+监控"作为通用架构模式。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 架构评审："我们做了站库分离/拆了微服务，安全性提升了吧？"
2. 防拖库专项设计：如何让拖库变慢、变可见。
3. 数据库访问权限治理：应用账号该有什么权限、直连还是走中间层。
4. 规划监控告警体系时，判断哪些观测能力应由架构自带。

### 语言信号 (用户的话里出现这些就应激活)

- "站库分离 安全吗 / DB separation security"
- "怎么防拖库 / anti-dump / prevent mass data exfiltration"
- "微服务/中台 之后安全是不是就好了"
- "数据库账号权限怎么给 / least privilege DB account"
- "API 调用阈值 / API rate threshold as detection"

### 与相邻 skill 的区分

- 【组合】`caudit-trust-tier-isolation`: 那边在数据模型层按信任级切分存储（分表/结构隔离）；本 skill 在访问路径层收口与观测。两者正交且组合——先隔离数据域，再收口访问。
- 【组合】`caudit-choke-point-first`: 那边是审计视角的收口（审一处覆盖多数路径）；本 skill 是同一"收口"概念的架构落地与防御视角（把收口建成受控可观测层）。
- 【组合】`caudit-rate-limit-dual-edge` / `caudit-api-blindspot-priority` / `caudit-horizontal-depth-pillars`: 限频阈值是本 skill 监控画像可共用的计数设施（防滥用配额与入侵检测信号同源）；接口盲区定律决定收口层自身成为高价值目标后的测试优先级；两支柱策略则决定何时、以什么配比建这层收口。
- 与运维的"数据库审计日志"不同：日志是事后取证；本 skill 要求阈值熔断的实时响应能力内建于访问层。

## E — 可执行步骤 (Execution)

1. **跑反迷思判别式**: 盘点全部数据访问路径——哪些服务/进程持有数据库凭证？凭证权限多大（库/表/DML/DDL/FILE）？端口对哪些网段开放？
   - 完成标准: 访问路径清单完成；存在"全权凭证 + 广网段直连"即判"分离零增益"。
   - 判停条件: 若已是单服务+ORM 收口且凭证最小化，直接进步骤 3 检查监控。
2. **设计收口层**: 数据访问统一经中间层/API 服务，凭证降为受限账号，逐接口（或逐数据域）授权，Web 层不再持库凭证。
   - 完成标准: 收口前后凭证与权限对比表完成，直连路径清零（运维通道单独管理）。
3. **内建调用画像与阈值**: 为收口层定义画像指标（QPS、返回行数、扫描型查询模式、调用方分布），设阈值与熔断/告警动作。
   - 完成标准: 每类指标有基线、阈值、触发动作三要素。
4. **压测验证拖库成本**: 模拟从 Web 层拖库——验证无法直连、接口限速、批量拉取触发熔断。
   - 完成标准: "拖不快"（速率被压）与"拖了可见"（告警触发）两个结论均有实测。
5. **审计收口层自身安全**: API 服务器本身的鉴权、注入面、凭证管理（作者自注的前提）。
   - 完成标准: 收口层漏洞评估完成，未把旧风险平移进新层。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯性能/可用性动机的分离决策（读写分离、负载分担）——本 skill 只评判安全属性，不要用安全判据否决性能方案，只标注其安全增益为零。
- 小型单机应用——强行走 API 层收口是过度设计，直接做数据库账号最小化与网络隔离即可。
- 已有专业数据访问治理（如数据库防火墙、行级安全策略平台）时的重复建设评估。

### 作者在书中警告的失败模式

- "搬库 + 开端口"式分离被当安全措施（ce77）——安全增益为零且扩大网络面。
- 分离后不建监控——拖库依然又快又静。
- 忽视作者自注前提："这一切的前提是API服务器的安全要做好"——收口层失守则全盘皆输（且它是新的高价值目标，参见 vf20 的接口盲区）。

### 作者的盲点 / 时代局限

- 2015 语境：单体 Web + 单库；现代等价物是数据访问服务、API 网关、服务网格、数据库代理（ProxySQL 类）、云 IAM/行级安全——"收口+受限凭证+阈值监控"骨架不变，构件全部升级。
- 未讨论阈值的基线学习与误报治理（正常营销流量 vs 刷库的区分）、多租户下的画像隔离。
- "无法在短时间内拖走"是速率防御不是绝对防御——作者未量化"短时间"；现代应以可检测窗口（MTTD）为目标值设计阈值。
- 未提及备份通道的旁路（拖备份比拖库更快），收口设计需覆盖备份/导出类接口。

### 容易混淆的邻近方法论

- 与"网络隔离/防火墙"不同：网络层控制可达性；本 skill 管凭证与访问语义（谁、以什么权限、经什么路径、被谁观测）。
- 与零信任架构不同：理念同源（不信网络位置、逐请求授权），本 skill 是其在数据访问层的 2015 年先声表述，无身份体系组件。

## 相关 skills

- **composes-with `caudit-trust-tier-isolation`**: "先分域、再收口"——数据按信任级切开存储后，访问路径经 API 层统一收口并观测，两步构成完整的结构性防御。
- **composes-with `caudit-choke-point-first`**: 同一"收口"概念的攻防两侧——那边审收口（读透一处即覆盖多数路径），本 skill 建收口（把统一访问层建成受控、可观测的架构构件）。
- **composes-with `caudit-rate-limit-dual-edge`**: 接口调用阈值监控与限频配额可共用同一计数设施——目标兼收入侵检测（异常拖库）与防滥用（资源耗尽）。
- **composes-with `caudit-api-blindspot-priority`**: 收口层是新的高价值接口目标（作者自注"前提是 API 服务器的安全要做好"），其自身的盲区评估按那边的密度定律执行。
- **composes-with `caudit-horizontal-depth-pillars`**: 本 skill 是两支柱体系中"纵深防御"在数据访问层的标准构件之一，是否建、何时建由那边的投资框架裁决。
