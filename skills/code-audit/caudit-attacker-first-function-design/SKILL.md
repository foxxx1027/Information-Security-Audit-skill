# 功能安全设计总纲——攻击者视角先行 (vf14)

## R — 原文 (Reading)

> 「要打造安全的应用程序，要从业务功能的设计开始，只有功能设计得足够安全，编写代码的时候才会少出现一些漏洞，特别是逻辑漏洞」「我们在这章从攻击者的角度详细分析常见功能会出现哪些安全问题，在分析出这些安全问题的利用方式后，再给出问题的解决方案」

> — 原作者, 原始方法论来源第11章 引言（source.txt 行13515、行17149）

---

## I — 方法论骨架 (Interpretation)

这是一个把"以攻击者视角思考"从口号变成流程门禁的框架。核心是一条强制顺序：

1. **先枚举攻击面**：这个功能暴露给谁调用？哪些参数客户端可控？哪些状态会被改变？哪些值被当作可信？
2. **再推演利用方式**：对每个攻击面问"具体怎么利用"——抓包改参数、并发重放、伪造身份、批量刷量、跨权限投递。推演不到利用方式的面，威胁评估就没完成。
3. **最后才写安全设计**：设计是对已推演利用的逐条封堵，而不是功能写完后的补丁清单。顺序不可颠倒——作者断言逻辑漏洞只能在设计阶段消灭，事后过滤无效。

它与审计侧的功能点定向（先找"经常出问题的功能"再定向）是同一框架的反向使用：审计是对既有代码跑步骤 2，设计是在代码存在前跑步骤 2。产出物是一份"攻击面 → 利用方式 → 对策"三列对齐的设计清单，每个对策都能指回它封堵的利用。

## A1 — 书中的应用 (Past Application)

### 案例 1: 第11章体例——十余个功能逐一执行该流程
- **问题**: 如何系统地为常见功能给出安全设计而非零散提醒。
- **方法论的使用**: 11.1~11.14（验证码、登录、注册、找回密码、资料操作、投票/积分/抽奖、支付、私信反馈、文件管理、数据库管理、命令执行、备份、API）每个功能都按"会出现哪些安全问题 → 利用方式 → 解决方案"组织。
- **结论**: 该顺序可复制到任何新功能，是可教学的设计流程而非灵感。
- **结果**: 全章十余节均按此模板产出设计要点，构成书的防御篇核心。

### 案例 2: 找回密码（11.4）——先摆缺陷谱再给七条设计
- **问题**: 找回密码是账号接管高发功能。
- **方法论的使用**: 先枚举利用：抓包改收件地址、4 位验证码爆破、Token=用户名+邮箱 MD5 可预测、验 key 后改 uid"验 A 改 B"；分析完这些利用后才给出七条设计（地址来源/凭证强度/绑定复验等）。
- **结论**: 设计条目与利用方式一一对应，无一条是凭空最佳实践。
- **结果**: 该节成为流程门禁的示范样本（细节展开见 vf16）。

### 案例 3: 支付（11.7）——利用方式分析前置
- **问题**: 支付漏洞层出不穷，防不胜防。
- **方法论的使用**: 先复述 6.2.1.4 的四类利用（改单价/总价/数量含负数、时间差重复购买），分析完后给出三条对策（金额服务端真值/数量>0/锁定账户）。
- **结论**: 对策全部由利用方式反推，覆盖可枚举的利用面。
- **结果**: 三条对策成为支付域的不变量（见 vf17 的实例化）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品要上线新功能（打赏、拼团、邀请返利、工单、导出），需要在写代码前产出安全设计。
2. 架构师/研发负责人做功能设计评审，需要一套系统的提问框架。
3. 安全团队给业务方写"功能安全需求"，要求每条需求可追溯到威胁。
4. 复盘某逻辑漏洞，反推"设计阶段本应如何拦住"。

### 语言信号 (用户的话里出现这些就应激活)

- "要上线 XX 功能，安全上要注意什么 / 帮我出个安全设计"
- "攻击者视角 / think like an attacker"
- "上线前安全评审 / pre-launch security review / secure design review"
- "这个功能会有什么安全问题"
- "威胁建模 / threat modeling（功能级、轻量场景）"

### 与相邻 skill 的区分

- 【对比】`caudit-logic-vuln-audit`: 同一"攻击者视角"框架的两个方向，按情境选一——代码存在之前用本 skill 推演利用、产出设计清单；已有代码用那边做应然/实然对照、产出漏洞。
- 【区分】`caudit-audit-path-selection`: 那是审计资源的路径选型；本 skill 是防御侧设计流程，不建链。
- 与正式威胁建模方法（STRIDE 等）的区别: 本 skill 无资产/信任边界画布，是"攻击面→利用→对策"三列清单式的轻量流程，适合单功能快速评审。
- 【被依赖】`caudit-password-reset-three-stages` 依赖本 skill: 它是本总纲在"凭证重发"功能域的完整实例化（三阶段缺陷谱 = 步骤 2 利用推演的成品）。

## E — 可执行步骤 (Execution)

1. **枚举攻击面**: 列出该功能的全部入口（页面/接口/回调）、客户端可控参数、被改变的状态、被当作可信的值。
   - 完成标准: 四类各至少一条，无入口遗漏（含定时任务与回调）。
2. **逐项推演利用方式**: 对每个攻击面写出具体利用动作（改什么参数/怎么重放/伪装什么身份/如何批量），不接受"可能有风险"这类无动作的描述。
   - 完成标准: 每个攻击面至少对应一条可执行利用或明确标注"无利用路径"及理由。
   - 判停条件: 若功能是纯静态展示且无状态变更，记录结论后直接跳到步骤 4 写最小对策。
3. **按利用反推设计**: 每条已确认的利用方式对应至少一条设计对策（真值换来源、凭证加绑定、迁移加原子、通道加隔离），未对应利用的对策单列标注"纵深"。
   - 完成标准: 三列对齐表（攻击面/利用方式/对策）完成，无利用无对策、无对策无利用的悬空项。
4. **跨功能检查**: 把清单对照相邻功能复用（同一利用方式是否在本功能同样成立）。
   - 完成标准: 至少核对一次同型功能的历史漏洞模式。
5. **交付设计文档**: 三列对齐表随功能需求文档进入评审。
   - 完成标准: 评审记录确认每条对策有唯一责任模块。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有代码的具体漏洞挖掘——那是审计侧技能（机理搜索、逻辑漏洞审计）的领域，设计总纲不产出代码级结论。
- 纯合规/等保对标——驱动力是外部条款而非利用方式推演，套本流程会产出牵强的"对策"。
- 基础设施与网络层设计（VPC 划分、WAF 选型）——攻击面枚举的对象应是业务功能参数与状态。

### 作者在书中警告的失败模式

- 先写功能再补安全：事后加过滤对逻辑漏洞无效（行13515 的因果论断——逻辑漏洞只能消灭在设计阶段）。
- 只列安全问题不分析利用方式就给方案——对策与威胁脱节，评审时无法验证有效性。

### 作者的盲点 / 时代局限

- 2015 语境：无正式威胁建模体系（STRIDE/攻击树未引入），作者的"攻击面清单式"流程缺乏信任边界与数据流图，复杂多系统功能下覆盖靠经验而非系统性。
- 功能清单基于单体 PHP Web 应用（前后台一体）；现代多租户 SaaS、微服务、第三方 OAuth 集成需自行扩展攻击面类别（租户边界、服务间调用、回调签名）。
- 未涉及滥用经济性之外的合规维度（隐私最小化、数据驻留）与安全需求可验证性（如何写验收用例）——对策停留在清单粒度。

### 容易混淆的邻近方法论

- 与 SDL/安全开发生命周期不同：SDL 是组织流程容器，本 skill 是其中"设计阶段"的一个可执行工作法。
- 与风险评分（DREAD 等）不同：本流程不排序打分，靠"利用方式是否被推演穷尽"控制质量。
