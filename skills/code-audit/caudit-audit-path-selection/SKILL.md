# 审计路径选型框架（vf01）

## R — 原文 (Reading)

> 「快速寻找漏洞…回溯参数非常有效，但并不适合企业安全运营」「（功能点定向先黑盒快测常见洞，读码时）略过黑盒测过的点，提高审计速度」
>
> — 原作者, 原始方法论来源第3章 3.2/3.3（source.txt 行1409-1411、行3789）

---

## I — 方法论骨架 (Interpretation)

开始审计前先做一次显式选型，而不是拿到代码就埋头读。决策变量有三个：

1. **时间预算**：几小时、几天还是长期运营，直接排除不可行的路径。
2. **目标归属**：外部目标（快速找洞、出报告即止）与自有产品（要长期为安全负责）适用不同路径——回溯法快但挖不到逻辑漏洞，自有产品恰恰逻辑漏洞存量最大。
3. **漏洞类型**：注入/上传/包含这类有明确关键字的漏洞适合回溯与功能点定向；逻辑漏洞"没有特别明显的关键字"，只能通读 + 吃透业务。

四条路径各有能力边界：敏感函数回溯效率最高、覆盖最窄；变量正向追踪适合追已知可控点；功能点定向先把登录/找回/支付/上传等高发功能黑盒快测一遍，白盒阶段跳过已测点以降本；通读最慢但唯一能覆盖逻辑漏洞。

关键产出不是"选哪条路径"这一个名词，而是一份**作业方案**：主路径 + 辅助路径 + 明确放弃什么 + 在报告中声明覆盖边界与剩余风险类型。最高效的路径在存量最大的漏洞上失效——这个反直觉事实必须写进方案，否则时间紧迫下的选型会被误当成完整结论。

## A1 — 书中的应用 (Past Application)

### 案例 1: espcms 搜索注入——回溯法的外部目标打法
- **问题**: 需要在大量 CMS 里快速定位可利用注入。
- **方法论的使用**: 用 Seay 审计系统载入 espcms 自动审计列出可疑点，从 sink 手工回溯到 accept()/daddslashes() 取参链，确认 $_GET 可达。
- **结论**: 回溯法对"快速找外部目标漏洞"效率最高，坐实了该路径的定位。
- **结果**: 3.1 节以此演示回溯法为"目前使用得最多"的思路（作者本人 2013 年即以此发现该漏洞，见 4.1.1.3）。

### 案例 2: 骑士cms——自有产品级目标改用通读
- **问题**: 要系统性理解一套程序并挖到含逻辑漏洞在内的全部类型。
- **方法论的使用**: 走通读路径：按 api/admin/manage/include 关键字挑文件 → 读过滤链与配置 → 理入口 → 标记敏感点复读。
- **结论**: 通读虽慢，但是覆盖业务逻辑漏洞的唯一路径，"并不适合企业安全运营"指的是把它当快速找洞手段，而非否定其必要性。
- **结果**: 通读中先后产出 XSS 过滤链缺陷、asyn_userkey 可预测令牌、GBK 宽字节前提等多类发现（3.2.1 系列）。

### 案例 3: BugFree 重装漏洞——功能点定向 + 黑盒先行
- **问题**: 时间有限，不可能通读。
- **方法论的使用**: 直接黑盒请求 install/index.php 这类高发功能文件，命中"跳转不终止"缺陷后用 Burp 验证。
- **结论**: 高发功能点先黑盒排雷，白盒阶段即可略过已测点。
- **结果**: 重装漏洞确认（3.3 节，WooYun 同型），验证"功能点定向"路径的性价比。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接到审计委托/内部任务，只有有限人天，要出"有无高危漏洞"结论（如 48 小时 + 30 万行老系统）。
2. 公司自有产品要做长期安全运营，规划季度审计投入。
3. 渗透测试中拿到源码，想快速定位可利用点。
4. 安全团队复盘："上次审计为什么漏掉了这个逻辑漏洞"——路径能力边界问题。

### 语言信号 (用户的话里出现这些就应激活)

- "时间只有 X 天，代码有 X 万行，从哪里下手"
- "通读一遍代码现实吗 / 要不要全部读完"
- "audit approach / how to structure a code audit"
- "full read vs. keyword search / black-box first?"
- "审计报告怎么写覆盖范围 / 剩余风险怎么声明"
- "每年有固定的安全预算 / 每季度投入多少代码审计 / 审到什么深度"（长期运营下的审计投入与深度配比）

### 反向信号 (用户的话里出现这些则不应激活)

- "审计做到一半卡在一个可疑点上 / 帮我看看这段代码 / 这个 substr 截断到底能不能绕过校验"——已进入执行期的单点漏洞分析，选型阶段已过，不激活本技能（此类单点判定也不应触发册内其他技能）。
- "预算怎么花在防御建设上 / 纵深防御 / 规则细化到什么程度"——对象是防御体系而非审计作业，属 `caudit-horizontal-depth-pillars`。

### 与相邻 skill 的区分

- 【被依赖】`caudit-structured-full-read` 依赖本 skill: 本 skill 只做路径**选型决策**（选哪条、放弃什么）；选定"通读"后才由结构化读法接管怎么读。
- 【被依赖】`caudit-mechanism-to-search-terms` 依赖本 skill: 那是回溯/定向路径选定后的**执行层**方法（怎么搜、怎么判过滤）；本 skill 在其上游。
- 【区分】`caudit-logic-vuln-audit`: 逻辑漏洞方法论是通读路径内的专项打法；本 skill 决定"何时必须走这条路"，不另建链。
- 【区分】`caudit-horizontal-depth-pillars`: 那边管防御建设的投入与体系（横向细化/纵深防御/安全预算投向建设）；"每季度在自家产品上投入多少代码审计、审到什么深度"是审计作业的路径与深度配比，对象仍是"怎么读代码"，归本技能。
- 【组合】`caudit-api-blindspot-priority`: 那边按"检测覆盖率反比定律"定黑盒/灰盒测试面，本 skill 定白盒读码路径；两步衔接成完整作业方案（先定面、再选路径）。

## E — 可执行步骤 (Execution)

1. **采集决策变量**：确认时间预算、目标归属（自有/外部/一次性）、目标规模、是否已熟悉该系统、委托方最关心哪类漏洞。
   - 完成标准: 三项变量（时间/归属/类型优先级）均有明确答案并记录。
2. **查路径能力矩阵**：将关心的漏洞类型对照四条路径的覆盖能力（回溯=关键字类漏洞、通读=逻辑类唯一覆盖、功能点定向=高发功能、正向追踪=已知可控点）。
   - 完成标准: 每个关心的漏洞类型都标注了由哪条路径负责。
3. **组合主辅路径并写"放弃声明"**：确定主路径、辅助路径与黑盒先行清单；显式写出本次不覆盖的漏洞类型（如逻辑/越权）。
   - 完成标准: 方案含"主路径 + 辅路径 + 放弃清单"三要素。
   - 判停条件: 若时间预算连单条路径的最小执行单位都不够（如无法完整跑一遍 sink 清单），则改为纯黑盒 + 声明"未做代码审计"，不要产出虚假覆盖。
4. **报告回填覆盖边界**：结论章节必须重申已覆盖/未覆盖类型与剩余风险。
   - 完成标准: 报告含独立的"覆盖范围与局限性"段落。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已经进入具体漏洞的分析/利用阶段——选型是一次性前置决策，反复纠结路径是拖延。
- 纯黑盒渗透（拿不到源码）——四条路径全部以白盒为前提。
- 单文件/单函数的代码审查请求——直接审即可，不需要路径框架。

### 作者在书中警告的失败模式

- 把回溯法当万能：它"对逻辑漏洞挖掘覆盖不到"（行1050-1058），逻辑漏洞恰恰是企业系统存量最大的一类。
- 自有产品用快速找洞的思路运营安全——作者明确"并不适合企业安全运营"（行1409-1411）。

### 作者的盲点 / 时代局限

- 书中四路径基于 2015 年单体 PHP 应用（无框架或轻框架）；现代框架下"通读"的对象应是框架约定层（路由/中间件/ORM）而非逐文件，成本结构已变，但"时间预算 × 目标归属 × 漏洞类型"的决策表仍可平移。
- 作者假设通读在工程上可行，未论证百万行级项目的时间成本——跨语言迁移时，"通读"应替换为"全局数据流图 + 关键层精读"的等价物。
- 无自动化辅助的路径假设（半自动化 SAST 未纳入选型变量），当代应把工具覆盖率作为第五个决策变量。

### 容易混淆的邻近方法论

- 与"测试策略选型"（黑盒/灰盒测试计划）不同：本框架选的是**读代码的路径**，黑盒只作为排雷辅助手段嵌入。
- 与威胁建模不同：威胁建模面向设计资产，本框架面向既有代码的阅读资源分配。
