# 黑名单失效模式与等价能力推演（vf10）

## R — 原文 (Reading)

> 「当你想用本指令禁止一些危险函数时，切记要把dl（）函数也加到禁止列表，因为攻击者可以利用dl（）函数来加载自定义的PHP扩展以突破disable_functions指令的限制」「基于黑名单的过滤总给人不靠谱的感觉，事实确实是这样，目前好像还没有看到基于黑名单过滤的规则一直没有被绕过」
>
> — 原作者, 原始方法论来源第1章 1.3 / 第9章 9.1.2（source.txt 行591、行15009）

---

## I — 方法论骨架 (Interpretation)

"黑名单会被绕过"是口号；把口号变成可执行分析的是**失效模式分类学**——黑名单从四个方向漏：

1. **枚举不全**：目标域是开放集合（WebServer 可解析后缀、MySQL 报错函数、PHP 标签形态），清单天然滞后——作者在 8.7 直接指出"多数人以为只有三种…实际上还有很多"。
2. **等价变体**：同一能力有多种表示——大小写、编码形态、标签变体、同义字段名。禁了标准形态，变体照走。
3. **破坏性改写后语义重建**：过滤先把命中内容替换为空/改写，再拿改写后的结果做检测或放行——"badbadonclick" 删掉 "bad" 拼成 onclick；单引号内容被清空后关键字检测扑空而 MySQL 照常执行。改写不是消除，是重排。
4. **检测与目标引擎解析语义错位**：检测器匹配的字面（字符串、域名、关键字）与目标引擎实际解析的语义（解析后的目标、hex 明文、字段域）不在一个层面——字面全拦住，语义照进。

配套动作是**等价能力推演**：每禁一项能力 A，强制枚举"与 A 等价的全部通道"——同族函数、变体写法、加载器（dl() 载扩展绕过整个禁用清单）、编码/间接表示。推演给不出闭环，即证明黑名单在该域不成立，应转向白名单或结构化校验——分析的产出是**设计层面的否定与替代方案**，不是再补几个关键字。

## A1 — 书中的应用 (Past Application)

### 案例 1: dl() 突破 disable_functions——加载器旁路
- **问题**: 禁函数清单看起来很全，为何等于没禁。
- **方法论的使用**: 等价能力推演——"执行任意代码"这个能力不止被禁用清单里的函数承载，dl() 可加载自定义扩展，扩展内即任意代码，整份清单被旁路。
- **结论**: 禁用清单必须封"加载/执行类入口"，否则枚举不全。
- **结果**: 作者在 1.3 以"切记"级别的警告给出（行591）。

### 案例 2: discuz 过滤类单引号清空绕过
- **问题**: 多重黑名单+替换的过滤器为何失效。
- **方法论的使用**: 失效模式3——注入语句放进单引号，preg_replace 清空引号内内容，后续关键字检测对象已是残句；@`'` 在 MySQL 为 null，语句照常执行。
- **结论**: 破坏性改写使检测与放行基于不同数据，语义在改写后重建。
- **结果**: 9.1.1 记录该历史绕过，成为"过滤类也可被绕"的实证。

### 案例 3: 上传扩展名黑名单"漏网之鱼"
- **问题**: 黑名单为何是上传漏洞的主流成因。
- **方法论的使用**: 失效模式1+2——各 WebServer 可解析后缀不同（IIS 的 cdx/asa/cer…），大小写/多后缀/解析特性未覆盖，"1.php␣" 尾空格更使比较本身落空。
- **结果**: 作者断言"目前上传漏洞的主流成因就是黑名单绕过"（5.1.3），正解为白名单+重命名+禁执行。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审"封禁关键字/危险函数/扩展名"类防御方案是否值得上。
2. 给 GraphQL/搜索过滤/富文本编辑器设计"危险内容拦截"规则。
3. 复盘一次绕过事件，向管理层解释为什么补关键字补不完。
4. 甲方要求"既能拦截又不能误杀"时的可行性评估。

### 语言信号 (用户的话里出现这些就应激活)

- "我们封了这些关键字/函数/后缀，够吗 / is this blacklist enough"
- "blacklist vs whitelist / 为什么黑名单不行"
- "过滤之后替换为空 / replace matched content with empty"
- "怎么绕过这个过滤 / how to bypass this filter"
- "再补几个词是不是就安全了"

### 与相邻 skill 的区分

- 【对比】`caudit-whitelist-spectrum`: 互为对偶——本 skill 论证黑名单为何不成立（设计否定），谱系 skill 给出三形态替代方案（设计肯定）；一次评审的标准顺序是先否定、再建设。
- 【区分】`caudit-escape-as-last-step`: 时序判据是"过滤位置"问题；本 skill 的失效模式3（破坏性改写）虽涉及改写，但焦点是改写后**检测语义**被破坏，而非转义时序，不建链。
- 【组合】`caudit-filter-coverage-map`: 评审一个统一过滤连问两句——覆盖面测绘问"过滤照没照到这类数据"，本 skill 问"照到的数据里，清单内容追不追得上变体"。
- 【组合】`caudit-patch-diff-remediation`: 修复的字面性检查（短链/编码/变体等等价表示绕过）就是等价能力推演在修复域的应用，那边步骤 4 直接复用本 skill 的推演动作。

## E — 可执行步骤 (Execution)

1. **描述黑名单的声称目标**：它想禁止的**能力**是什么（执行代码/解析为脚本/携带恶意语义），而非它列了哪些项。
   - 完成标准: 目标能力有一句话定义。
2. **等价能力推演**：枚举承载该能力的全部通道——同族 API、语法变体、编码/间接表示、加载器、解析特性，逐项标注是否在清单内。
   - 完成标准: 通道清单 ≥ 清单覆盖，未覆盖通道显式列出。
   - 判停条件: 若目标域是开放集合且无法证明枚举闭合（如任意脚本形态），直接得出"黑名单在该域不成立"，跳到第4步替代方案。
3. **逐失效模式过筛**：对现有实现分别检查枚举完整性、变体覆盖、是否有破坏性改写后再检测、检测层与目标引擎语义是否同层。
   - 完成标准: 四模式各有"存在 / 不存在该缺陷"结论。
4. **产出判定与替代**：结论三选一——成立（附闭合证明）/ 仅作纵深（降级定位）/ 不成立（给出白名单或结构化校验替代设计）。
   - 完成标准: 判定附理由与替代方案草图，替代方案落到 `caudit-whitelist-spectrum` 的三形态之一。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 白名单/类型锁定方案的选型——直接用白名单谱系，无需先证伪黑名单。
- 非安全域的"黑名单"（内容审核、垃圾词过滤）——那里误杀成本主导，分析框架不同。
- 时间只够修一个具体绕过——先修，再用本框架做同类排查（连到补丁横向收敛）。

### 作者在书中警告的失败模式

- 禁函数忘 dl()（行591）；扩展名黑名单漏后缀（行6355）；PHP 标签变体留后门绕 WAF（行12561）；报错函数认知只有三个（行12821）；总论断"还没有看到一直不被绕过的"（行15009）——五个对象、同一结论。
- 替换为空式的"清洗"——改写后拼接重组出可执行内容（与 ce20/ce52 同族）。

### 作者的盲点 / 时代局限

- 书中例子全部是 2015 PHP/WebServer 生态（IIS 解析、PHP 标签、MySQL 报错函数）；四类失效模式本身不随载体过期，但推演时必须换成当前生态的等价通道（CDN 规则、Serverless 沙箱逃逸面、ORM 方言）。
- 作者论证黑名单不可靠后，书内替代方案（自建过滤类+标签白名单）仍属清洗流派，未达到当代"结构上消除"（参数化、默认不执行目录、CSP）的力度——判定可平移，替代方案要升级。
- 未区分"黑名单作为唯一防线"与"黑名单作为纵深一层"的定位差异，实践时应显式降级定位而非全盘否定。

### 容易混淆的邻近方法论

- 与模糊测试（fuzz 黑名单）不同: fuzz 是经验性撞变体；等价能力推演是从目标能力出发的系统性枚举，fuzz 只能作为推演的验证手段。
- 与 WAF 规则绕过研究不同: 那是针对具体产品的攻防；本 skill 产出**防御设计选型**结论。

## 相关 skills

- **contrasts-with `caudit-whitelist-spectrum`**: 黑名单与白名单是防御设计的两种对立选型——本 skill 给出"黑名单为何终将被绕过"的四类失效证明，那边给出替代方案的三形态谱系；连用顺序为先否定再建设。
- **composes-with `caudit-filter-coverage-map`**: 评估既有过滤的两问——它没照到哪些数据（覆盖盲区）、照到的数据里清单追不追得上变体（内容失效）；一外一内配合出完整结论。
- **composes-with `caudit-patch-diff-remediation`**: 修复验证的"字面性检查"要枚举输入的全部等价表示（编码、短链、大小写、协议变体），这正是本 skill 等价能力推演的动作在修复域的复用。
