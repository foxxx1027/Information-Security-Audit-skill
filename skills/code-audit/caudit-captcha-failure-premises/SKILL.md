# 验证码失效四前提与硬规则 (vf15)

## R — 原文 (Reading)

> 「后端程序在接收一次请求后，并没有主动刷新验证码……所以会把验证码明文或者加密后放在Cookie或者POST数据包里面，所以每次只要同一个数据包里面的两个验证码对上了即可绕过」「因为目前网络上还有专门提供人工打码的服务平台」「不把验证码放到HTML页面或者Cookie中」

> — 原作者, 原始方法论来源第11章 11.1.1/11.2.1（source.txt 行17171、行17239、行17189）

---

## I — 方法论骨架 (Interpretation)

验证码是否"有效"不是一个演示问题（挡住一个脚本），而是四个前提是否同时成立的检验问题。前提失效，验证码整体失效：

1. **一次性前提**：验证通过后（甚至校验尝试后）服务端必须销毁旧值；不刷新即可复用。负载均衡下把验证码放 Cookie/POST 回传比对，是这一前提的典型破坏——同包两值对上即绕过。
2. **限次前提**：短数字验证码（4/6 位）若无错误次数限制与有效期，就是可穷举的弱凭证。
3. **机器识别前提**：验证码形态的可枚举性——识别算法或对抗样本能否稳定还原。
4. **经济学前提**：打码平台把"人工解码"商品化后，"防机器"的目标退化为"抬成本"——单次代答价格低于攻击收益，验证码就只挡君子。

配套硬规则是前提的工程化：错一次即失效、验证码与答案都不进 HTML/Cookie、服务端只存 Session 中的判定结果、敏感操作用独立验证码（与登录页不同源）。验收一个验证码方案 = 逐条检验四前提，而非看演示。

## A1 — 书中的应用 (Past Application)

### 案例 1: 负载均衡下 Cookie/POST 回传验证码绕过（11.1.1）
- **问题**: 大业务多机部署，验证码与 Session 绑定导致跨机失效，工程师把验证码放进请求包回传。
- **方法论的使用**: 用一次性前提检验——两值同包比对等于把答案交给请求方，复用与伪造同时成立。
- **结论**: 验证码判定必须留在服务端共享存储，请求侧只传用户输入。
- **结果**: 该案例成为"不把验证码放到 HTML/Cookie"硬规则的出处（行17189）。

### 案例 2: 找回密码 4 位验证码无限爆破（3.3 行3821、11.4 行17323）
- **问题**: App 端找回密码验证码多为 4 位且无错误次数与有效期限制。
- **方法论的使用**: 用限次前提检验——4 位仅 1 万种可能，无限次提交必然可穷举。
- **结论**: 短验证码必须配错误次数上限、短时效、用后作废、错误触发冷却。
- **结果**: 作者标注这是"目前最常见的一种找回密码漏洞利用方式"。

### 案例 3: 打码平台的经济学否证（11.2.1 行17239）
- **问题**: 登录验证码能否阻止撞库。
- **方法论的使用**: 用经济学前提检验——打码兔/Q赚类平台用廉价人力代答，单次成本极低。
- **结论**: 验证码只能提高自动化成本，防撞库必须组合多因素认证与限频。
- **结果**: 11.2.1 的对策从"换更强验证码"转向"验证码+多因素"的组合设计。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为登录/注册/找回密码/敏感操作选型验证码（图形、短信、行为滑块、无感验证）。
2. 验收第三方验证码服务或自研方案，需要可检验的合格标准。
3. 事故复盘："上了验证码还是被刷爆/撞库"，定位是哪个前提失效。
4. 评审负载均衡/多机房部署下的验证码一致性实现。

### 与相邻 skill 的区分

- 【组合】`caudit-rate-limit-dual-edge`: 限频是"允许尝试多少次"，验证码是"每次尝试的通过条件"；限次前提（前提二）由限频策略支撑，分级响应中"何时触发验证码"又反过来消费验证码——两者互为配套。
- 【组合】`caudit-password-reset-three-stages`: 那边审找回密码全流程的三阶段，本 skill 只管其中验证码这一个控件的有效性定义；审"凭证重发"流程时两边同时上场。
- 【区分】`caudit-type-context-defense` 等"过滤类" skill: 验证码不是输入过滤，不处理内容语义，只做人机区分，不建链。

## E — 可执行步骤 (Execution)

1. **画验证码生命周期**: 从生成→下发→提交→校验→销毁，标出答案值存在的每个位置（HTML、Cookie、POST、Session、缓存）。
   - 完成标准: 生命周期图上能指出答案值的销毁时刻；若答案出现在响应或请求侧，直接判缺陷。
2. **检验一次性前提**: 校验成功/失败后旧值是否销毁；同值能否二次提交。
   - 完成标准: 复用测试用例（同验证码连发两次）通过/失败有记录。
3. **检验限次前提**: 确认错误次数上限、有效期、冷却机制三者至少具备其二。
   - 完成标准: 穷举成本 = 组合数/限速 的估算值；无上限即缺陷。
   - 判停条件: 若方案为非穷举型（如行为评分型），跳过本步并在步骤 4 补充评分绕过分析。
4. **检验机器识别与代答前提**: 评估形态可枚举性；查打码平台是否已支持该类型及报价。
   - 完成标准: 给出"单次通过成本"估算，明确该验证码定位是拦截还是抬价。
5. **输出验收结论**: 四前提逐条 PASS/FAIL + 硬规则符合性（错即失效/不入页面与 Cookie/Session 判定/敏感操作独立）。
   - 完成标准: 任一前提 FAIL 即整体验收不通过，附修复指向对应硬规则。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- CSRF/请求伪造防护——Token 才是对策，验证码"只用在敏感操作的页面"是作者明确的分工边界（行5887），不要把验证码当全站请求来源验证。
- 限频策略本身的设计评审——那是 `caudit-rate-limit-dual-edge` 的对象；本 skill 只消费"限次"这个前提。
- 纯 UX 讨论验证码样式美观。

### 作者在书中警告的失败模式

- 验证码答案随响应下发或放 Cookie/POST 回传比对（行17171、行17189）。
- 校验后不刷新销毁，同值复用（ce57）。
- 短数字验证码无错误次数限制，被穷举（ce61）。
- 指望验证码单独挡住撞库——打码平台使"防机器"失效，只能抬成本（行17239）。

### 作者的盲点 / 时代局限

- 2015 语境：图形验证码 + 短信为主；现代行为验证码（滑块/无感/reCAPTCHA 类）书内没有，但四前提框架可直接迁移（复用→轨迹 token 一次性；识别→轨迹模拟与对抗样本；经济学→代答平台已支持滑块）。
- "人比机器便宜"前提在 LLM/视觉模型时代更加极端——机器识别成本趋近于零，验证码定位全面退化为"抬成本+风控信号"，作者时代"防机器"的目标表述需重写。
- 未讨论无障碍（accessibility）与隐私代价（第三方验证码的追踪），也未给验证码与风控评分联动的现代架构。

### 容易混淆的邻近方法论

- 与"多因素认证"不同：验证码是人机区分控件，不是"你拥有什么"的因子——把短信验证码同时当 MFA 与 CAPTCHA 用是常见混同，作者在 12.9 已分开处理。
- 与 Token（CSRF 防护）不同：Token 验证请求来源归属，验证码验证操作者是人，二者在 4.3.2 有明确分工。
