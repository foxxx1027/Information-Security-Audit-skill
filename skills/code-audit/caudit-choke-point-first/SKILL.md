# 收口点优先——统一层是审计与防御的战略点 (vf26)

## R — 原文 (Reading)

> 「SQL查询统一操作函数inserttable（）以及updatetable（）函数，大多数SQL语句执行都会经过这里，所以我们要关注这个地方是否还有过滤等问题」「安全过滤文件对我们做代码审计至关重要，关系到我们挖掘到的可疑点能不能利用」「除了总入口，在具体的功能点也需要进行一些过滤」

> — 原作者, 原始方法论来源第3章 3.2.1.2/3.2、第9章 9.1（source.txt 行2769、行1477、行13717）

---

## I — 方法论骨架 (Interpretation)

"收口点"是数据必须经过的统一通道：统一 SQL 执行函数、入口过滤类、统一取参函数、统一输出模板。
它是审计与防御共用的战略概念，用法有两条：

**有收口 → 审一处即覆盖大多数路径。** 先花精力读透收口层的过滤/校验实现，产出一张"收口覆盖表"（它处理什么、不处理什么、已知绕过是什么）。此后全系统审计变成两步：可疑点查表即判可利用性，再单独核对少数绕过收口的旁路。骑士cms 的 inserttable()/updatetable()（"大多数SQL语句执行都会经过这里"）即此——读一个函数等于读了大多数语句。

**无收口 → 这本身就是最高风险信号。** 收口不存在意味着：每个 sink 独立暴露、新增功能必然裸奔、过滤覆盖面在结构上无法审计。此时报告的价值排序要倒过来——把"建立收口"列为架构级修复建议，罗列单点漏洞反而是次要交付。

防御侧同构：应用安全中心（代码层白名单收口）是 WAF 不可替代的最内层——WAF 看不到业务语义（"已知某参数一定是INT类型，就可以在使用时将其转为INT"），收口内的类型锁定只有应用自己能做。收口是单点机会也是单点风险：它被绕过即全站失守，所以收口自身要配绕过历史追踪。

## A1 — 书中的应用 (Past Application)

### 案例 1: 骑士cms 统一 SQL 函数（3.2.1.2 行2769）
- **问题**: 通读一套 CMS 时哪些文件值得优先精读。
- **方法论的使用**: 识别收口——inserttable()/updatetable() 是"大多数SQL语句执行都会经过这里"的统一操作函数，审计注意力优先投向"这个地方是否还有过滤等问题"。
- **结论**: 读透两个函数的过滤行为即可给大多数 SQL 语句的可利用性定型。
- **结果**: 收口优先成为通读法"关键文件清单"（函数集/配置/过滤/入口）中权重最高的对象。

### 案例 2: discuz 入口过滤类——收口的双刃（9.1.1 行13719 起）
- **问题**: 全站级过滤类的价值与风险。
- **方法论的使用**: 收口的防御形态分析——过滤类决定全站可注入性；同时拆解其历史绕过（单引号内容置空绕过，cs37），证明收口被绕过即全站失守。
- **结论**: 收口覆盖表必须含"已知绕过清单"；80sec 类过滤被 discuz/dedecms/phpwind 复用，缺陷也被批量复制。
- **结果**: 9.1 章以拆解该类为示范，确立"读第三方过滤实现=读全站安全水位"的审计动作。

### 案例 3: 应用安全中心——收口的架构定位（12.10 行18075）
- **问题**: WAF 普及后应用层防御还有什么不可替代。
- **方法论的使用**: 收口定位论证——WAF"无法结合应用代码逻辑"，而应用安全中心能做类型锁定白名单（参数已知是 INT 即强制转型），是"其他层面的WAF无法取代的"。
- **结论**: 最内层收口必须内建于应用，不能外包给外挂设备。
- **结果**: 审计侧（收口优先读）与防御侧（安全中心建设）用同一概念贯通。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接手大型/遗留系统做安全评估，时间有限，需要性价比最高的切入点。
2. 制定审计计划：先读公共层还是逐功能扫描的决策。
3. 架构评审：系统该不该建统一数据访问/过滤层，价值如何论证。
4. 审计报告撰写：判断"缺收口"应作为发现还是仅作背景描述。

### 语言信号 (用户的话里出现这些就应激活)

- "几十万行代码从哪里开始审 / audit a huge legacy codebase"
- "有没有统一的数据库访问/取参/过滤 / common DB layer / centralized input filtering"
- "审公共函数值不值 / should I audit the shared library first"
- "到处都在拼SQL，审不过来 / SQL everywhere, can't cover"
- "WAF 能不能替代应用层过滤 / WAF vs application-layer validation"

### 与相邻 skill 的区分

- 【组合】`caudit-structured-full-read`: 通读法回答"读什么类型的文件、按什么顺序"；本 skill 回答"其中哪个点值得压倒性投入"——收口是通读优先级清单里权重最高的对象，总纲与聚焦配合使用。
- 【组合】`caudit-api-relay-architecture`: 那边是防御侧把收口建成受控可观测层（架构重构方案）；本 skill 是审计侧的切入策略 + "无收口"风险定性——同一"收口"概念的攻防两视角。
- 【被依赖】`caudit-filter-coverage-map` 依赖本 skill: 那边测绘统一过滤的覆盖面边界（盲区图）；本 skill 先判断"收口存在与否"——有收口之后才轮到画它的覆盖图。

## E — 可执行步骤 (Execution)

1. **找收口点**: 在代码库中检索统一通道——SQL 执行是否收敛到少数函数/类（inserttable/查询构造器/ORM 入口）、取参与过滤是否有入口循环、输出是否走统一模板函数。
   - 完成标准: 每类通道（DB/输入过滤/输出）标注"收口位置 + 覆盖比例估计"或"无收口"。
   - 判停条件: 若全部通道均无收口，跳到步骤 4 输出结构风险定性。
2. **精读收口实现**: 逐行读收口的过滤/校验逻辑，产出收口覆盖表：处理哪些输入类型/上下文、不处理什么、历史绕过（检索该组件的 CVE/公开绕过）。
   - 完成标准: 覆盖表三列（覆盖/不覆盖/已知绕过）完成，附行号引用。
3. **查旁路清单**: 检索绕过收口的调用点（直接执行原生查询、直接读 $_SERVER/$_FILES、不经模板的 echo），逐个核对。
   - 完成标准: 旁路调用清单逐条判定"已另行防护/暴露"。
4. **定性输出**: 有收口——给出"审一处覆盖多数"的结论与残余旁路风险；无收口——把"建立收口"列为架构级修复建议之首，单点漏洞清单降为次要交付。
   - 完成标准: 报告含收口判定结论 + 对应的审计工作量估计或架构建议。
5. **（防御向）评估收口自身**: 收口的测试责任、绕过追踪机制、版本更新（复用第三方过滤类时缺陷同样被复制）。
   - 完成标准: 收口自身风险单列一节，不停留在"有收口=安全"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 无共享层的小型脚本/单文件应用——没有收口可找，逐文件读即可，套本方法空转。
- 已定位单点漏洞的深入分析——直接分析该点，收口概念只用于判断过滤上下文，不是主工具。
- 纯黑盒测试（无源码）——收口识别需要白盒视角（黑盒下只能以 WAF/网关为类似物，语义不同）。

### 作者在书中警告的失败模式

- 跳过收口直接逐功能扫——工作量爆炸且覆盖无系统性（收口决定"可疑点能不能利用"，行1477）。
- "有收口=安全"的静止判断——收口被绕过即全站失守（discuz 过滤类多次绕过，行13723、cs37）。
- 把入口过滤当全部——"除了总入口，在具体的功能点也需要进行一些过滤"（行13717），收口是主防线不是唯一防线。
- 用 WAF 替代应用内收口——WAF 无法做业务语义的类型锁定（行18075）。

### 作者的盲点 / 时代局限

- 2015 语境：作者面对的是无框架或轻框架 PHP 应用，"建收口"是自建工程；现代框架（ORM、中间件、序列化器）已内置收口，审计对象转变为"框架约定 + 自定义旁路"（原生查询、跳过中间件的路由），方法不变但检索对象要换。
- 未讨论收口的组织成本——收口层自身需要专人维护与测试，作者只谈其收益；复用第三方过滤类的"缺陷批量复制"风险点到但未展开治理。
- "大多数语句都经过这里"的覆盖比例无度量方法；现代可用调用图/静态分析量化收敛度。

### 容易混淆的邻近方法论

- 与"看公共函数"的普通审计习惯不同: 本 skill 把收口上升为双重信号——存在性决定审计策略（审一处 vs 逐 sink），缺失性本身是架构级发现，且防御侧（安全中心）与审计侧贯通。
- 与 `caudit-filter-coverage-map` 的盲区测绘不同: 盲区图回答"这个过滤盖住了什么"；本 skill 回答"先看哪、以及没有它意味着什么"。
