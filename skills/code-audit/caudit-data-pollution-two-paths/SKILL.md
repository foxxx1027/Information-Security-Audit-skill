# 数据污染两条路径模型与过滤部署位置（vf04）

## R — 原文 (Reading)

> 「数据污染有两种方式…被动接收参数…主动获取参数…防止SQL注入就是要守住这两条路」；过滤的执行时机存在"入口统一"与"语句前"两种部署，「除了总入口，在具体的功能点也需要进行一些过滤」
>
> — 原作者, 原始方法论来源第4章 4.1.2 / 第9章 9.1（source.txt 行4599、行13717）

---

## I — 方法论骨架 (Interpretation)

多数人把"过滤输入"默认等于"过滤 HTTP 请求参数"。这个模型把污染面画成两条路径：

1. **被动接收**：应用等着收的参数（GET/POST/Cookie 等请求入口）——这是统一入口过滤覆盖的部分。
2. **主动获取**：应用自己伸手拿的数据——读文件、抓远程页面/RSS、回读数据库、消费消息队列。这些数据从不经过请求入口，入口过滤对它们是零作用。

在此基础上加两条部署规则：

- **两层时机**：入口统一过滤（拦最常见的面）+ 功能点专项过滤（进入具体解释器前，按该语境选防御）。只有一层都守不住全场景。
- **中间改写点 = 新污染源**：数据过了入口、进入业务流程后，任何对它的改写（拼接、替换、转码）都可能重新引入污染——"入口干净"不能豁免任何下游消费点。

审计/设计的产出物是一张**"两条路径 × 两层时机"的检查点矩阵**：列出系统全部数据来源，标注每个来源经过哪层过滤、在哪些消费点进入哪个解释器，逐一核对。矩阵把"要过滤输入"变成可执行的覆盖清单。

## A1 — 书中的应用 (Past Application)

### 案例 1: SQL 注入防范的两路守门
- **问题**: 防 SQL 注入应该在哪里设防。
- **方法论的使用**: 4.1.2 开篇即以"两条路径"定义问题——被动接收的参数与主动获取的数据都要守，再讨论过滤部署在入口还是语句前。
- **结论**: 防注入 = 守住两条路 + 两层时机组合，单点方案（只在入口 addslashes）被后续章节反复证伪。
- **结果**: 该模型成为第9章过滤体系（入口过滤类 + 功能点过滤）的地基。

### 案例 2: phpcms 任意文件读取——主动获取路径的实例
- **问题**: 主动获取路径的漏洞长什么样。
- **方法论的使用**: file_get_contents 的目标直接取自 GET 的 url 参数——读什么由请求决定，数据（文件内容/远程响应）绕过一切入口过滤被消费。
- **结论**: 读取类功能的"获取目标"可控即成立，入口过滤帮不上忙。
- **结果**: 5.1.2 拆解该漏洞，同类下载/读取功能被列为必查项。

### 案例 3: 回读数据库成独立污染面
- **问题**: 库里的数据算不算输入。
- **方法论的使用**: 作者以 magic_quotes_runtime 专管"从数据库、文件读取的数据"说明配置层面也承认两路之分；第1章明言"很多程序员只对外部输入的数据进行过滤，却没有想过从数据库获取的数据同样也会有特殊字符"。
- **结论**: 回读数据是主动获取路径的常态成员，取出即新输入。
- **结果**: 该判断在第7章二次漏洞章展开为完整方法论（写入/触发分离）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计新系统的输入验证架构：统一中间件过滤 vs 各 handler 自行过滤怎么分。
2. 审计爬虫/聚合系统：定时抓第三方 RSS/API 入库再渲染、推送，入口过滤是否够。
3. WAF 全覆盖后评估残余注入通道（哪些数据源根本不经过 HTTP 入口）。
4. 数据中台/ETL：多来源数据汇聚后分发，消费点各自的过滤责任。

### 语言信号 (用户的话里出现这些就应激活)

- "数据不是用户传的，是从库里/文件里/接口抓来的，还要过滤吗"
- "统一入口过滤了，功能点还要不要校验 / global filter vs per-endpoint validation"
- "external data ingestion security"
- "二次污染 / 入口之后数据被改了算谁的"
- "WAF 挡住了请求，还有什么进得来"

### 与相邻 skill 的区分

- 【组合】`caudit-filter-coverage-map`: 本 skill 正向画全图（有哪些数据、哪些路），那边对**既有统一过滤**反向找例外（哪些字段/入口漏了）——一个画地图一个找洞，画完地图才找得全洞。
- 【被依赖】`caudit-second-order-vuln` 依赖本 skill: 二次漏洞聚焦"写入→取出→触发"的链式追踪；本模型先把"取出"定义为独立污染路径，是它的上游建模。
- 【被依赖】`caudit-escape-as-last-step` 依赖本 skill: 时序判据是本模型"中间改写点 = 新污染源"规则在时序维度的深化——先理解两条路径，才理解为什么转义后不得再改写。

## E — 可执行步骤 (Execution)

1. **列数据来源清单**：穷举系统获取数据的全部途径——请求参数、头、上传文件、读文件、外呼抓取、库/缓存回读、消息队列、内部 RPC。
   - 完成标准: 每个来源标注"被动接收 / 主动获取"。
   - 判停条件: 若连来源清单都列不全（无文档），先回 `caudit-structured-full-read` 建图，不要在残缺模型上做设计。
2. **标注现有过滤的覆盖**：对每个来源标注它实际经过的过滤层与时机（入口/功能点/无）。
   - 完成标准: 形成"来源 × 过滤层"矩阵，空格即未覆盖。
3. **列出消费点与解释器**：每个来源的数据最终进入什么（SQL/HTML/shell/Excel/命令行/日志），逐消费点核对语境化过滤是否存在。
   - 完成标准: 每条"来源 → 消费点"边都有过滤标注。
4. **标记中间改写点**：入口到消费点之间的拼接/替换/转码/解码调用全部标为潜在新污染源。
   - 完成标准: 改写点清单并入矩阵，作为重点复核对象。
5. **产出部署决策**：给出每个未覆盖格子的补救层位（补入口层 / 补功能点层 / 两层都补）。
   - 完成标准: 矩阵无未处理空格，决策记录了理由。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单个漏洞点的定性（如"这个参数转义够不够"）——用专项判据，不需要全系统建模。
- 纯输出编码问题（XSS 输出语境）——属输出侧选型，不是污染路径建模。
- 尚无任何过滤体系的早期设计争论——直接引用本模型即可，不必走五步矩阵。

### 作者在书中警告的失败模式

- 只在总入口 addslashes 一把梭："仅仅addslashes…对特定场景不那么好使，除了总入口，具体的功能点也需要过滤"（9.1，行13717）。
- 只防请求侧：程序员"只对外部输入的数据进行过滤，却没有想过从数据库获取的数据同样也会有特殊字符"（第1章，行493）。

### 作者的盲点 / 时代局限

- 模型诞生于 GPC 时代，示例全是 PHP 超全局；现代栈的对应物：入口中间件、ORM 读出的实体、消息消费者、微服务间调用——两路划分仍成立，但"入口"从 index.php 变为多个协议端点。
- 书内推荐的功能点过滤以自建过滤类为主，低于当代实践（参数化查询为默认、框架级验证器）；迁移时应把"功能点过滤"优先实现为参数化/类型化，而非再写一层黑名单。
- 未覆盖现代数据源：WebSocket、gRPC streaming、Serverless 事件源等，建模时需自行扩展清单。

### 容易混淆的邻近方法论

- 与 OWASP"验证一切输入"口号不同：本 skill 的增量是把"主动获取"并列为同等入口、并把中间改写点定义为新污染源——口号没有这两条。
- 与零信任架构的"从不信任"原则方向一致，但本模型是数据流层的可操作清单，不涉及身份与网络分段。
