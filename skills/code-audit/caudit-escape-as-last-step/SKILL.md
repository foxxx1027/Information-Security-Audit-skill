# 过滤时序判据——转义必须是最后一步（vf05）

## R — 原文 (Reading)

> 「如果某处使用了urldecode或者rawurldecode函数，则会导致二次解码生成单引号而引发注入」「只要发生编码转换就有可能出现这种问题…mb_convert_encoding同样」
>
> — 原作者, 原始方法论来源第4章 4.1.1.2 / 第8章 8.1.2（source.txt 行4335、行11427）

---

## I — 方法论骨架 (Interpretation)

开发者的默认心智模型是"过滤过 = 安全"。本判据把**顺序**提为过滤生死的判定维度：

- 转义的作用是让数据在"进入解释器的那一刻"不改变语句结构。因此它必须发生在进入解释器前的**最后一步**，中间不能插进任何其他变换。
- 转义之后若发生以下任何一类变换，转义即归零：**解码**（urldecode 把 %27 还原成引号）、**转码**（iconv/mb_convert_encoding 吃掉转义反斜杠字节）、**改写**（str_replace 用用户输入覆盖已过滤值）、**检测依赖被修改的数据**（过滤器先清空再检测，检测对象已非原始输入）。
- 反向规则：所有解码/转码/规范化动作一律**前移**到转义之前，让进入转义函数的就是最终形态。

审计动作是机械的：沿输入链列出全部变换调用（解码、转码、替换、格式化），画出每个调用相对转义点与解释器入口的位置。任何位于转义之后的变换都是候选攻击面，构造相应 payload 验证（双重编码、宽字节、替换吃反斜杠）。

这条判据跨解释器成立：SQL、HTML、shell、Excel 公式、cron 表达式的转义全都只认"最后一步"。

## A1 — 书中的应用 (Past Application)

### 案例 1: espcms 二次 urldecode 绕过 GPC
- **问题**: 入口转义（GPC/addslashes）开着，注入为何仍成立。
- **方法论的使用**: 沿链找变换——程序在转义之后又对该参数 urldecode，提交 %2527 双重编码，第二次解码还原出单引号。
- **结论**: 解码发生在转义之后，转义对该参数失效。
- **结果**: 作者 2013 年发现的搜索注入坐实（4.1.1.3）；4.1.1.2 给出普适判据。

### 案例 2: Ecshop 支付宝回调 str_replace 破坏过滤
- **问题**: 业务逻辑里的改写如何复活注入。
- **方法论的使用**: $order_sn 已过滤，随后被 POST 同名参数经 str_replace 回填，反斜杠被吃掉，值再进查询。
- **结论**: "过滤后的变量"被二次加工即回退为未过滤——业务改写点就是新污染源。
- **结果**: 注入成立，6.2.1.5 将其定性为"逻辑错误型注入"（本非漏过滤，而是过滤后又被改写）。

### 案例 3: discuz 过滤类"先清空后检测"绕过
- **问题**: 过滤器自身为什么能被绕过。
- **方法论的使用**: 过滤类先用 preg_replace 清空单引号内内容再做关键字检测——注入语句放进单引号即被抹掉，后续检测扑空，而 MySQL 的 @`'` 表示 null 使语句照常执行。
- **结论**: 检测不得依赖"已被自己修改"的数据——破坏性改写后语义重建，是顺序缺陷的过滤器版。
- **结果**: 9.1.1 拆解该历史绕过，成为"黑名单 + 破坏性替换"的经典反例。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 复盘："我们明明统一转义了，怎么还被注入了"。
2. 设计数据管线：入库前统一编码 + 后续"智能纠错/规范化"管道（自动 urldecode、繁简转换、全文规范化）是否安全。
3. 审计任何"过滤 → 若干处理 → 拼接"的既有链路（模板渲染、报表导出、消息推送）。
4. 评审第三方过滤器/清洗库（WAF 规则、富文本过滤器）是否会改写后再检测。

### 语言信号 (用户的话里出现这些就应激活)

- "明明 addslashes/转义了还能注入 / escaped but still injected"
- "程序里有个 urldecode / iconv / str_replace，有影响吗"
- "double encoding / %2527 bypass"
- "转码之后过滤还有效吗 / does encoding conversion break escaping"
- "入库前统一编码，后面还要再处理"

### 与相邻 skill 的区分

- 【依赖】`caudit-data-pollution-two-paths`: 本判据是两路模型"中间改写点 = 新污染源"规则在时序维度的深化——先理解污染路径建模，再用本判据查管线位置。
- 【组合】`caudit-type-context-defense`: 类型判据回答"这个语境该用转义还是类型锁定"（选武器），本 skill 回答"选定的转义在管线里放的位置对不对"（查持枪姿势）——两问都过转义才有效。
- 【组合】`caudit-mechanism-to-search-terms`: 本判据是那边三步法第三步"过滤充分性"的专项判据之一——搜到 sink 回溯时按本判据列变换清单。
- 【区分】`caudit-second-order-vuln`: 二次漏洞是跨请求的写入→取出→触发；本判据也适用于单请求内的顺序错误，不要求存储介质——共享"过滤后变换"根因但时域不同，不建链。
- 【区分】`caudit-blacklist-failure-modes`: "破坏性改写后语义重建"这一失效模式在本 skill 里聚焦于它对**转义时序**的影响，不建链。

## E — 可执行步骤 (Execution)

1. **锁定解释器入口**：明确数据最终进入哪个解释器（SQL/HTML/shell/公式），以及该语境的转义点在哪一行。
   - 完成标准: 转义调用与解释器调用都有确切位置。
2. **列变换清单**：沿数据流枚举转义点之前的全部解码/转码/替换/格式化调用，及其相对位置。
   - 完成标准: 每个变换标注"转义前 / 转义后"。
   - 判停条件: 若数据流无法静态追全（动态调度），转入动态验证（构造标记输入跟踪变形），不得凭"看起来没有变换"下结论。
3. **攻击面判定**：对所有"转义后"的变换逐个构造 payload 验证（双重编码 / 宽字节 / 替换吃转义符）。
   - 完成标准: 每个转义后变换有"可破坏 / 不可破坏"结论及证据。
4. **给出顺序修复方案**：把解码/转码/规范化全部前移到转义之前；无法前移的（业务必需改写）在改写之后重新转义。
   - 完成标准: 修复后链路上转义重新成为最后一步，并附回归用例（%2527、%bf%27 等样本）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 语境选型问题（数值位该用类型锁定）——顺序对了武器不对照样漏，先用类型语境判据。
- 纯参数化查询的代码路径——没有手动转义就没有时序问题，别画蛇添足。
- 输出到纯文本渠道（日志文件按文本消费）且无再解析——不存在解释器闭合问题。

### 作者在书中警告的失败模式

- 二次 urldecode（行4335）、编码转换（行11427：ecshop 因此多次出洞）、过滤后 str_replace 改写（行9583）、检测依赖被修改的数据（行14879）——四类对象、同一根因：过滤之后仍有变换。
- 作者特别提醒宽字节是"非常典型的编码转换问题导致绕过GPC的方式"（8.1.2）——字符集不一致本身就是一种隐藏转码。

### 作者的盲点 / 时代局限

- 书内例子绑定 GPC/GBK 等 2015 PHP 语境（PHP 5.4 起 GPC 已移除、UTF-8 普及后宽字节权重下降）；迁移到现代栈时等价物变为：框架中间件统一编码后的自定义解码、日志管道的格式化器、CSV/Excel 导出的二次加工、模板引擎的富文本过滤器。
- 书内修复方案停留在"把解码前移"，未提"优先参数化查询使转义点消失"这一更根本的现代做法——判据可平移，方案应升级。
- 未覆盖 Unicode 规范化（NFD/NFC）这一现代同型变换，审计现代系统时应自行加入清单。

### 容易混淆的邻近方法论

- 与"输出编码"通识的区别: 通识说"输出时要编码"，本判据给出可判定的顺序条件——编码之后不得再有任何变换，包括看起来无害的"纠错"。
- 与数据污染两路模型的"中间改写点"规则同源：本 skill 是该规则在时序维度的深化。
