# 过滤覆盖面盲区测绘（vf07）

## R — 原文 (Reading)

> 「PHP5中magic_quotes_gpc并不会过滤$_SERVER变量，导致很多类似client-ip、referer一类的漏洞能够利用」；第3章直接把 HTTP_CLIENT_IP/X_FORWORDFOR「当搜索关键字」用于审计
>
> — 原作者, 原始方法论来源第1章 1.3 / 第3章 3.1（source.txt 行471、行1050）

---

## I — 方法论骨架 (Interpretation)

任何统一过滤都是一个有边界的集合：它覆盖若干入口、若干数据类别、若干时机——**边界之外的部分就是盲区，盲区是系统的属性，可以系统测绘**。

审计统一过滤的第一问不是"它过滤得严不严"，而是"它的覆盖面边界在哪"：

1. **按数据类别问**：哪些超全局/数据容器不在内？（书中的原型：GPC 只管 GET/POST/Cookie，$_SERVER 头字段、$_FILES 文件名都在外。）
2. **按入口问**：哪些进入途径不经过它？（非 HTTP 入口、内部调用、消息队列、CLI。）
3. **按时机问**：过滤发生的时刻之前/之后各有什么数据流？
4. **按武器化方向问**：盲区里的字段被用在什么安全决策上？头字段进 SQL 是注入；被当作客户端 IP 用于限频/鉴权，则是伪造。

方法产出一张**覆盖面地图**：行的维度是全部数据来源（参照数据污染两路模型），列的维度是统一过滤的实际覆盖，空格即盲区；再对每个盲区验证可利用性。这比"发现一个 XFF 注入就修一个"高一个层级——下一个攻击者会换一个盲区字段再来。

## A1 — 书中的应用 (Past Application)

### 案例 1: GPC 不管 $_SERVER——盲区的机制定义
- **问题**: 入口转义全开，头字段为何仍是通道。
- **方法论的使用**: 第1章以 magic_quotes_gpc 的覆盖范围定义盲区（$_SERVER 不在其中），client-ip、referer 类漏洞由此成立；第8章 8.1.1 以专节重申"不受GPC保护的$_SERVER变量"。
- **结论**: 盲区由过滤机制的覆盖定义决定，可枚举。
- **结果**: 第3章把这两个头字段直接列为搜索关键字——盲区知识转化为审计检索词。

### 案例 2: Burp 伪造 Client-IP 绕过登录限频
- **问题**: 盲区字段的次生危害。
- **方法论的使用**: Discuz 用 HTTP_CLIENT_IP 取 IP 做登录错误次数限制，该值可伪造——每个 IP 5 次的限制被头伪造绕过，爆破继续。
- **结论**: 盲区字段一旦进入安全决策（限频主键），盲区即升级为鉴权类缺陷。
- **结果**: 2.3.1 完成实测演示；11.2.1 防撞库设计据此排除"单按 IP 限频"。

### 案例 3: 骑士cms getip() 未校验格式
- **问题**: 通读中如何利用盲区视角。
- **方法论的使用**: 定位 getip() 优先取 $_SERVER['HTTP_X_FORWARDED_FOR']，指出"很多应用都会由于在获取IP时没有验证IP格式，而存在注入漏洞，不过这里还只是可以伪造IP"。
- **结论**: 同一盲区字段在不同消费点表现不同（伪造 vs 注入），须逐消费点判定。
- **结果**: 3.2.1.2 记录两档危害，与 cs02/11.2.1 形成跨章印证。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. "全站上了 WAF / 统一中间件校验"之后，评估残余注入与伪造通道。
2. 安全评审问"还有哪些数据不经过统一入口"（日志管道、回读数据、内部服务调用、webhook 回调）。
3. 攻防复盘：攻击者从不被检测的通道进来，要找系统性原因。
4. 设计新统一过滤时，先定义覆盖面并显式声明不覆盖项。

### 语言信号 (用户的话里出现这些就应激活)

- "WAF 都买了还有什么注入面 / WAF bypass surface"
- "XFF / X-Real-IP / referer 这些头能注入吗"
- "file name / $_FILES 文件名会过滤吗"
- "map what the global filter does and doesn't cover"
- "日志字段 / 内部调用要过 WAF 吗"

### 与相邻 skill 的区分

- 【依赖】`caudit-choke-point-first`: 测绘的前提是统一过滤（收口）存在——无收口的系统先按收口点优先定性并建议建收口，盲区图无从谈起。
- 【组合】`caudit-data-pollution-two-paths`: 两路模型从**数据来源**正向建模（含主动获取），本 skill 从**既有防御的覆盖面**反向找例外——地图的行清单由两路模型提供。
- 【组合】`caudit-blacklist-failure-modes`: 黑名单失效讲"清单内容永远追不全"（照到的部分），本 skill 讲"过滤根本没照到的数据类别"——即使清单完美盲区仍在，两问连用才闭合。
- 【区分】`caudit-rate-limit-dual-edge`: 那边关注限频策略本身被绕过/滥用两端；本 skill 只提供"IP 取自盲区头字段"这类上游事实，不建链。

## E — 可执行步骤 (Execution)

1. **描述统一过滤的声称覆盖**：读配置/文档/代码，写出它处理的数据类别、入口、时机。
   - 完成标准: 声称覆盖有明确清单（而非"全站防护"一句话）。
2. **列全量数据来源**：按两路模型（被动接收的全部容器 + 主动获取的全部途径）列系统实际数据来源。
   - 完成标准: 来源清单含头字段、文件元数据、回读、内部调用、队列、CLI 等非常规项。
3. **对照出盲区清单**：全量来源减去声称覆盖，空格即候选盲区。
   - 完成标准: 每个来源标注"覆盖 / 盲区 / 未知"，未知项按盲区处理。
4. **逐盲区验证可达性**：对每个盲区字段追消费点——进解释器的构造 payload 验证；进安全决策的（限频/鉴权/审计）验证伪造效果。
   - 完成标准: 每个盲区有"可利用 / 不可利用 / 待验证"结论。
   - 判停条件: 无法确认消费点归属时标记待验证并保留在地图上，不得从报告中删除。
5. **输出覆盖面地图与修复建议**：地图 + 两条修复方向（扩大覆盖 / 把盲区字段从安全决策中移除）。
   - 完成标准: 地图成为可复用工件，修复建议按盲区归因而非按单漏洞归因。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 系统没有任何统一过滤层——先讨论建立收口（choke point），测绘无从谈起。
- 针对单个已知注入点的利用构造——那是机理与 payload 的事。
- 过滤内容质量审查（黑名单全不全）——用黑名单失效模式分析，别混入覆盖面问题。

### 作者在书中警告的失败模式

- "开了 GPC = 所有入参都转义了"的错觉——$_SERVER/$_FILES 是结构性例外（第1、8章两处专节）。
- 把可伪造头字段当可信网络身份用于限频/白名单/审计取证（cs02、ce09）。

### 作者的盲点 / 时代局限

- 原型盲区（GPC、$_SERVER）在 PHP 5.4 后消失，但**"统一过滤必有覆盖边界"的视角不变**；现代等价盲区：WAF 不解的 JSON 体/GraphQL 字段、gRPC/HTTP2 头、mTLS 客户端证书字段、对象存储事件、CDN 注入的头。
- 书中只画了"数据类别"一维；现代系统应加"入口协议"与"序列化格式"两维，地图才完整。
- 作者语境中盲区修复靠功能点各自补过滤；当代优先"盲区字段不进安全决策"（如可信代理注入客户端 IP 并剥外部头），比逐点消毒更结构化。

### 容易混淆的邻近方法论

- 与攻击面枚举（attack surface enumeration）不同: 攻击面枚举列"能被打的点"；本 skill 以**既有防御为参照物**反向定义例外，参照物不同结论不同。
- 与"安全默认值"审查的区别: 那是配置审计；本 skill 是覆盖审计，即使配置全对，覆盖边界仍存在。
