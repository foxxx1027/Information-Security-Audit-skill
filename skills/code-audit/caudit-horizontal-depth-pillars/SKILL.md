# 两支柱体系——横向细化 + 纵深防御 (vf25)

## R — 原文 (Reading)

> 「横向细化策略的精髓在于坚持能杀掉一个是一个的原则，依靠规则量来填补空洞，规则做得越细，拦掉的攻击越多。这是在提升黑客的攻击成本，而缺点在于同样也提升了防御成本」「纵深防御策略是假设上一层防御策略失效而设计的」「不仅仅用在企业整体安全建设上，更是要细化到每个应用设计上面」

> — 原作者, 原始方法论来源第12章 引言（source.txt 行17635、行17633、行17637）

---

## I — 方法论骨架 (Interpretation)

防御体系由两个互补支柱构成，各自回答不同的问题：

**横向细化——广度支柱。** 承认单条规则必有遗漏，用规则量堆覆盖："能杀掉一个是一个"。它买到的不是安全而是**攻击成本**——攻击者要绕过越来越细的规则集合。关键自省：防御成本同步上升，因此横向细化有停止条件——当边际拦截量低于规则维护成本时停做。它适合高频攻击面（上传、注入变体），不适合低频高危逻辑漏洞（规则写不出来）。

**纵深防御——深度支柱。** 每一层都按"上一层最可能怎么失效"来设计：假设 WAF 被绕过→应用层类型白名单兜底；假设口令泄露→双因素；假设第一层验证被跳过→关键操作二次验证。推演失效模式而非平均铺层，是纵深与"多堆几层"的区别。

**资源投向用木桶原理裁决**: 整体安全状态由最薄弱业务点决定，投入应先补最薄处（对外表单、未鉴权接口、逻辑层），而非加固已很强的环节。

最后一条纪律：两支柱不能只落在"公司级安全建设"的幻灯片上，必须细化到每个应用的设计里（登录口加验证码+错误限制+多因素就是单应用两支柱的落地样本）。

## A1 — 书中的应用 (Past Application)

### 案例 1: 12.3-12.9 落地链——两支柱逐应用实例化
- **问题**: 抽象的两支柱如何变成可执行措施。
- **方法论的使用**: 纵深：后台登录叠"地址隐藏→密码策略→验证码→错误次数限制→双因素"，每一层假设前一层失效；横向：口令黑名单（禁 123456/1qaz2wsx）、IP 限制等规则逐条细化。
- **结论**: "这些手段都是为了防止暴力破解行为"——同一目标下两支柱并用，且全部落在单个登录口上。
- **结果**: 第12章以该链示范"细化到每个应用设计上面"的纪律（行17637）。

### 案例 2: 登录限制的纵深推演（12.5 行17991）
- **问题**: 已有内网 IP 限制，为什么还要双因素。
- **方法论的使用**: 纵深推演——假设 IP 层失效（"攻击者有很大的可能已经通过其他途径进入到内网"），下一层双因素仍能挡住。
- **结论**: 单因素假设失效是下一层设计的输入；IP 限制"相对安全但还不够安全"。
- **结果**: 口令策略+IP 限制+MFA 三层成为 12.5 的标准纵深（ce76）。

### 案例 3: CSRF 防御的层内配比（4.3.2）
- **问题**: Token 与验证码在 CSRF 防御中如何分工。
- **方法论的使用**: 配比应用——Token 全局铺（横向广覆盖），验证码因体验成本"只用在敏感操作的页面"（行5887），两层按成本分层配置。
- **结论**: 层内也有广度与成本的配比决策，横向细化不是无限堆。
- **结果**: 防御方案同时体现两支柱与成本自省，成为 4.3.2 的设计范式。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 初创/小团队安全投入规划：有限的人与预算先做什么后做什么。
2. 制定年度安全建设方案或应用安全基线（哪些措施必选、哪些按应用细化）。
3. 评审"再买一层防护/再加一批规则"的提案：该横向还是纵深？边际值还剩多少？
4. 事后复盘：攻击穿透了多层防御，检查各层是否按"上一层失效"设计（还是重复的功能堆叠）。

### 语言信号 (用户的话里出现这些就应激活)

- "安全预算/人力有限，先做什么 / security budget priorities"
- "纵深防御怎么设计 / defense in depth design"
- "规则越加越多值得吗 / diminishing returns of rules"
- "安全体系怎么规划 / security program roadmap"
- "最薄弱的环节在哪 / weakest link / 木桶"

### 与相邻 skill 的区分

- 【组合】`caudit-api-relay-architecture` / `caudit-trust-tier-isolation`: 那两个是具体架构决策（访问收口/数据隔离），本 skill 是其上层的投资与组合策略——决定何时、何地、以什么配比使用它们。
- 【区分】`caudit-attacker-first-function-design`: 那是单功能的设计流程；本 skill 管跨功能的资源分配与体系组合——粒度不同，不建链。
- 与合规基线（等保/PCI）的区别: 合规是外驱清单符合性；本框架按攻击成本与失效推演决定投入，产出可能高于或低于合规要求。

## E — 可执行步骤 (Execution)

1. **盘点木板**: 列出全部业务点/功能面，按暴露度（对外/可未授权访问）与价值（数据/资金/权限）标出最薄的 3-5 处。
   - 完成标准: 最薄点清单有排序依据，无"全都重要"的结论。
2. **对最薄点做横向细化**: 为高频攻击面逐条加规则/检查，记录每条的预估拦截面与维护成本。
   - 完成标准: 规则清单含成本列；边际拦截量明显低于维护成本的条目标记"停做"。
   - 判停条件: 若攻击面属逻辑漏洞类（规则写不出），跳过横向，直接进步骤 3 用纵深兜底并回补业务模型。
3. **按失效推演设计纵深**: 对每个高价值目标自上而下问"这层最可能怎么失效？"，下一层针对性设计（WAF 绕过→类型白名单；口令泄露→MFA；登录态窃取→二次验证）。
   - 完成标准: 每个高价值目标至少两层，且下层能说出针对的上一层失效模式（说不出即重复堆叠，删除）。
4. **细化到应用**: 把选定的措施映射到具体应用/登录口/接口，禁止只停留在"公司级"表述。
   - 完成标准: 每条措施有落点应用与配置位置。
5. **输出预算分配方案**: 按"补最薄优先 + 横向到边际 + 纵深按失效"输出投入排序与年度路线。
   - 完成标准: 方案每项可追溯到步骤 1-3 的依据，无凭经验拍脑袋条目。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单点漏洞修复决策——直接修，不需要体系框架；把每个洞都上升到体系讨论是拖延。
- 合规对标/等保测评应对——按条款执行即可，两支柱的投资逻辑与合规逻辑不同轨。
- 事件应急响应期间——先止血，体系复盘放事后。

### 作者在书中警告的失败模式

- 横向细化的成本双刃被忽视——"同样也提升了防御成本，需要更多的投入"（行17635），规则量失控反噬维护能力。
- 平均铺层冒充纵深——层与层之间无失效模式关联，只是重复买同类产品。
- 只做企业级建设、不落到每个应用——措施悬空（行17637 明确反对）。
- 加固强项而非补短板——木桶原理下回报最低（行17633）。

### 作者的盲点 / 时代局限

- 2015 语境：无风险量化体系（概率×损失）、无 MTTD/MTTR 指标，"边际拦截量/维护成本"未给算式，落地靠经验；现代可引入攻击面量化与 SLA 指标使步骤 2-3 更可计算。
- 书中部分"纵深"实例（后台地址隐藏 12.3）实为 security by obscurity——抬侦察成本可作一层，但把它计入结构性防御是作者立场盲点（批判章指出），使用时应归入横向且标注低价值。
- 未涉及安全左移（CI/CD 门禁、自动化测试）对"防御成本"结构的改变——现代横向细化的很多规则可代码化进流水线，成本曲线已变。
- 木桶原理假设攻击者攻击最短板，未考虑定向攻击可绕开短板直取供应链/人员（现代补充：人是最常被打的板）。

### 容易混淆的邻近方法论

- 与"纵深防御"行业通识的区别: 配对的"横向细化"命名及其成本双刃自陈、木桶资源投向规则、'细化到每个应用'的落地纪律——四者组合才是作者的框架，单说纵深防御只是通识。
- 与风险矩阵（可能性×影响排序）不同: 木桶原理按"最薄弱"而非"期望损失"排序——两者结论常一致，但在"低概率但短板"资产上分歧。
