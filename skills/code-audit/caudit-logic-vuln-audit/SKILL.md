# 逻辑漏洞方法论——应然/实然对照 (vf21)

## R — 原文 (Reading)

> 「机器代码很难模拟这块的逻辑处理，所以无法用机器批量化扫描检测，检测的少了，现存的漏洞自然就多了」「（逻辑漏洞）没有特别明显的关键字可以用来快速定位，通常这类漏洞的挖掘技巧是通读功能点源码，先熟悉这套程序的业务流程」「所有的逻辑漏洞都是因为开发者对业务逻辑或者代码逻辑理解不清楚导致」

> — 原作者, 原始方法论来源第6章 6.2（source.txt 行9049、行9053、行9737）

---

## I — 方法论骨架 (Interpretation)

逻辑漏洞挖不动的根源是"没有关键字可搜"：注入能搜 sink，逻辑漏洞的缺陷藏在"步骤顺序、条件分支、状态迁移"里。方法分四步：

1. **接受存量定律**: 机器模拟不了业务语义→批量化扫描检测不了→检测少→存量最大。这决定了资源投向：逻辑层是漏洞密度最高、单位投入回报最大的地方，也是扫描报告"零高危"最不可信的地方。
2. **先建应然模型**: 在读代码前写出业务"应该"如何——状态机（订单：待付→已付→发货→完成；分享：创建→撤销即失效）、不变量（金额>0、次数有限、操作者=属主）、流程规则（先验证后执行、验证谁改谁）。模型来自产品需求而非代码。
3. **通读功能点源码，逐项对照实然**: 通读不是为了找坏函数，是提取代码的"实际"状态机与规则，与应然逐项 diff——撤销后旧凭证是否失效？只读链接能否跳到编辑？扣费与开通是否原子？每个 diff 点即候选漏洞。
4. **双前提归因**: 一切逻辑漏洞源于开发者对业务逻辑或函数行为理解不清（如 in_array 松散比较、== 转换）——修复与评审都要回这两个前提。

产出是结构化的状态机对照表，这是扫描器给不出的东西。

## A1 — 书中的应用 (Past Application)

### 案例 1: BugFree 可重装漏洞——流程控制缺陷的定型（3.3，6.2.1.3 抽象）
- **问题**: install/index.php 检测到已安装后跳转首页，但重装逻辑照常执行。
- **方法论的使用**: 应然规则"已安装→安装流程必须不可达"，实然是 header 跳转不终止代码（无 die/exit），对照即出漏洞。
- **结论**: 抽象出通用缺陷模式"判断后未 return/exit"，可批量检索（搜 if 判断后是否紧跟终止）。
- **结果**: 作者用 Burp 绕过跳转验证重装成立（cs11/cs26），模式被列入 6.2 的关注点清单。

### 案例 2: 支付四类漏洞——不变量缺失的实然提取（6.2.1.4）
- **问题**: 商城支付逻辑缺陷如何系统发现。
- **方法论的使用**: 应然不变量（金额真值、数量>0、扣费开通原子）对照实然代码（金额客户端来、不验负数、两步非原子），三类 diff 全部成洞，外加时间差重放。
- **结论**: 逻辑漏洞可按"不变量逐条对照"批量产出，不需要灵感。
- **结果**: 四类缺陷成为 11.7 三对策的输入（vf17 的展开）。

### 案例 3: espcms 任意用户登录——身份不变量（6.3.1.2，WooYun-2015-90324）
- **问题**: 会话身份从加密 Cookie 解密直接使用。
- **方法论的使用**: 应然规则"身份由服务端裁决"，实然是解密 Cookie 取 user_id 即登录、不校验签名。
- **结论**: 伪造任意用户加密 Cookie 即任意登录；密钥还是硬编码常量。
- **结果**: 完整链路拆解成为"cookie 验证是否可绕过"关注点的示范（cs10）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计委托要求覆盖越权/支付/找回密码等业务逻辑，需要可执行方法而非"多注意"。
2. 自有产品上线前的逻辑层自查（功能：分享、审批、订单、工单、会员权益）。
3. 扫描器全绿但被薅/被越权后复盘，解释为什么扫不出来并补方法。
4. 评审产品需求文档时预埋"应然规则"（与 vf14 衔接）。

### 语言信号 (用户的话里出现这些就应激活)

- "逻辑漏洞怎么挖 / how to find business logic vulnerabilities"
- "扫不出来 / 扫描器测不到逻辑漏洞 / scanner misses logic bugs"
- "越权/支付/找回密码 的业务逻辑审计"
- "state machine audit / expected vs actual behavior"
- "这个流程有没有逻辑漏洞 / review this flow for logic flaws"

### 与相邻 skill 的区分

- 【对比】`caudit-mechanism-to-search-terms`: 技术型漏洞有 sink 关键字，走那边的三步法；逻辑漏洞"无关键字"，走本 skill 的应然/实然对照——按漏洞类型二选一，是全书审计方法的分水岭。
- 【组合】`caudit-structured-full-read`: 通读法提供"读什么、按什么顺序"；本 skill 提供通读时带着什么模型去读（应然状态机）、怎么把读到的变成漏洞——覆盖逻辑漏洞时的标准组合。
- 【对比】`caudit-attacker-first-function-design`: 同一框架的设计侧与审计侧——那边在代码存在前推演利用产出设计清单，本 skill 对既有代码做应然/实然 diff 产出漏洞，按有无代码选一。
- 【组合】`caudit-api-blindspot-priority`: 两边共用"检测覆盖率决定存量"定律；那边盲区是入口可达性，这边是语义可模拟性——正交且可叠加，测试计划按两个维度同时排序。
- 【组合】`caudit-payment-invariants`: 支付域的预编译清单——先跑那边的三条不变量快速核对，未覆盖处再回到本 skill 的通用状态机对照法。

## E — 可执行步骤 (Execution)

1. **圈功能点清单**: 列出目标系统的业务功能（登录、找回、支付、订单、审批、分享、安装/升级、导入导出），按敏感度排序。
   - 完成标准: 清单含功能名与数据/资金/权限敏感度标注。
2. **写应然模型**: 对每个高敏功能写三件套——状态机（状态与合法迁移）、不变量（金额/次数/属主/时序）、流程规则（验证与执行的关系）。
   - 完成标准: 每功能至少 3 条应然断言，来源标注（需求/常识），未读代码先写。
3. **通读功能点源码提取实然**: 按功能逐文件读代码，记录实际状态迁移、条件分支、验证位置。
   - 完成标准: 每功能的实然提取覆盖全部状态写入点与验证点。
   - 判停条件: 若功能状态全部由成熟框架基元（ORM 事务、框架中间件）保证且无自定义分支，记录"实然=框架默认"后转下一功能。
4. **对照 diff**: 应然断言逐条对照实然实现，偏差即候选漏洞，标注利用方式（改参数/跳步/重放/并发）。
   - 完成标准: 对照表三列（应然/实然/利用方式）完成，每条偏差有可执行的验证路径。
5. **验证与归因**: 构造请求验证候选，归因到两前提（业务逻辑不清 or 函数行为差异）。
   - 完成标准: 每个确认漏洞有复现记录与前提归因，候选未确认的标"待验证"及原因。
6. **报告覆盖声明**: 声明逻辑层的覆盖范围（哪些功能已建模型）与未覆盖项。
   - 完成标准: 报告含"已对照功能清单/未覆盖功能"两节。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 技术型漏洞挖掘（注入/上传/包含/命令执行）——有明确 sink，用机理搜索三步法更快，套本方法会把时间浪费在状态机上。
- 无业务状态的纯展示/静态内容。
- 已有成熟应然模型（如协议规范 RFC）的对照测试——直接用规范做模糊测试更高效。

### 作者在书中警告的失败模式

- 把"扫描器没报"当"没有漏洞"——逻辑漏洞恰恰是扫描盲区（ce42，行9049 因果链）。
- 跳过"吃透业务"直接找关键字——逻辑漏洞没有关键字，先读流程（行9053）。
- 只关注业务流程忽视函数行为差异（松散比较、类型转换）——两前提缺一不可（行9737）。
- 四类高发关注点漏检：可重复安装、改密越权、找回验证码爆破、cookie 预测/绕过（行9053 清单）。

### 作者的盲点 / 时代局限

- 2015 语境：人工通读是唯一路径；现代符号执行/污点分析可部分覆盖越权类，基于覆盖率引导的模糊测试可撞出状态异常，但语义类（如"验 A 改 B"）仍靠人建模型——"应然模型+人工对照"的骨架未过时，工具只是加速实然提取。
- "应然状态机"未发展为正式记法（作者以文字清单表达）；迁移时可引入状态图/不变量断言（属性测试 property-based testing 是其现代对偶）。
- 未给出通读的成本控制（多大系统可行）；大系统应结合收口点优先（先读统一层）降本。
- 未涉及团队知识沉淀（业务规则库），依赖审计者个人还原应然，成本高。

### 容易混淆的邻近方法论

- 与功能测试不同：功能测试验证"能用"，本方法验证"不能被滥用"（应然含攻击者视角的负向规则）。
- 与威胁建模不同：威胁建模在设计期枚举威胁；本方法在存量代码上做行为对照，产出是漏洞而非威胁清单。
