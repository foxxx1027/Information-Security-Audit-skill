# 找回密码三阶段防线 (vf16)

## R — 原文 (Reading)

> 「提交的时候可以直接抓包修改手机或者邮箱参数……原本发送给账号A的验证码会发送到被我们篡改的手机或者邮箱上」「部分网站找回密码的Token是根据当前的"用户名+邮箱"或者时间戳进行一次MD5后生成，这就存在一定的预测性」「服务器端并没有判断当前这个key是否跟uid或者email匹配」

> — 原作者, 原始方法论来源第11章 11.4（source.txt 行17313、行17327、行17359）

---

## I — 方法论骨架 (Interpretation)

找回密码的本质是"在没有密码的情况下改密码"，因此流程的每一步都是攻击面。方法是把流程切成三阶段，每阶段配一张独立缺陷谱，分别核验：

1. **发码阶段——收件地址来源**：验证码/链接发往的目标必须取自服务端已绑定的资料。若取自请求参数，抓包改收件人即把凭证送进攻击者渠道，后续校验再严密也是替攻击者校验。
2. **校验阶段——凭证四性**：凭证必须不可预测（随机源，不是用户名+邮箱/时间戳的确定性哈希——那等于可重算签名）、一次性（用后即焚）、短时效、并绑定当前会话/账号。
3. **执行阶段——复验绑定**：提交新密码时必须原子地复核"凭证 ↔ 目标账号"的绑定。校验步与执行步分离而不复验，就会出现"用 A 的合法凭证改 B 的密码"。

三阶段防线可平移到一切"凭证重发"类流程：换绑邮箱、换绑手机、OAuth 换绑、免登录跳转——它们与找回密码同构，缺陷谱同源。任何一个阶段失守都是完整的账号接管，不存在"部分安全"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 11.4 找回密码缺陷谱——三阶段各失守一例
- **问题**: 找回密码漏洞利用场景众多，需系统化组织。
- **方法论的使用**: 按三阶段归档：抓包改手机/邮箱参数（阶段一）、验证码无错误次数可爆破（阶段二）、Token=用户名+邮箱/时间戳 MD5 可预测（阶段二）、改密时不校验 key 与 uid 绑定（阶段三），随后给出七条设计。
- **结论**: 三阶段缺陷谱覆盖了绝大多数已知利用场景，设计按阶段逐条对应。
- **结果**: 该节成为功能安全设计总纲（vf14）的示范样本。

### 案例 2: 骑士cms asyn_userkey 令牌可预测（3.2.1.2 行3001）
- **问题**: 注册/找回密码链接里的 key 如何生成才可信。
- **方法论的使用**: 阶段二判别式——asyn_userkey() 拼接用户名+密码salt+密码做一次 MD5，材料全部已知或可推，属确定性推导而非随机凭证。
- **结论**: 单次 MD5 不产生不可预测性；知道部分资料即可离线构造任意用户的 key。
- **结果**: 作为"凭证材料可推=凭证失效"的定型反例（ce12），直接对应阶段二设计要求。

### 案例 3: 淘宝 API 免登录换发 Cookie（11.2.2 行17259）
- **问题**: 2014 年淘宝登录跳转链接仅凭 user_num_id 即返回该用户 Cookie，改参数登录任意用户（乌云报告后阿里设 500 万悬赏）。
- **方法论的使用**: 阶段三复验缺失的 API 形态——身份切换接口把"目标用户 ID"交给服务端时没有带上唯一一次性 Token，即无绑定复验。
- **结论**: 身份切换/凭证换发接口需要双要素：目标标识 + 绑定该标识的一次性凭证。
- **结果**: 该事件成为"接口鉴权缺陷高价值"的行业级证据（与 vf20 交叉引用）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计找回密码、换绑邮箱/手机、注销找回等账号恢复流程。
2. 接入 OAuth 第三方登录后的绑定/换绑流程评审。
3. 审计已有找回密码功能，产出缺陷清单。
4. 响应"重置链接被猜出来/验证码发给了攻击者"类账号接管事件。

### 语言信号 (用户的话里出现这些就应激活)

- "找回密码怎么设计才安全 / password reset security"
- "换绑邮箱流程 / email change flow / rebind flow"
- "账号被接管了 / account takeover"
- "重置 Token 可以预测 / predictable reset token / md5(username+email)"
- "验证码发到别人手机上了 / OTP hijacking"
- "注册激活链接和找回密码是一个性质吗 / 激活邮件凭证"

### 反向信号 (用户的话里出现这些则不应激活)

- "登录页想加'记住我' / cookie 里存什么比较合适"——登录会话票据设计，不是"凭证重发"流程，也不属限制状态真值裁决，本册技能均不激活。

### 与相邻 skill 的区分

- 【依赖】`caudit-attacker-first-function-design`: 那是通用设计总纲；本 skill 是它在"凭证重发"功能域的完整实例化——先懂"攻击面→利用→对策"的强制顺序，再看三阶段缺陷谱如何由利用方式反推。
- 【组合】`caudit-captcha-failure-premises`: 那边定义验证码控件自身的四前提；本 skill 把验证码当凭证的一种审其在三阶段中的位置与绑定——审找回/换绑流程时两边同时上场。
- 【组合】`caudit-server-side-state-truth`: "凭证↔账号绑定"是真值原则在认证域的化身；本 skill 提供流程级的阶段拆解与缺陷谱，粒度在流程步骤而非状态项。"记住我 cookie 存什么"这类会话票据存放设计两边都不接。

## E — 可执行步骤 (Execution)

1. **画流程三阶段图**: 把实际流程拆为发码→校验→执行，标出每阶段的输入参数、服务端存储、跨阶段传递的凭证。
   - 完成标准: 每阶段单独成块，跨阶段传递值（key/token/uid）全部显式。
2. **核阶段一（地址来源）**: 追"发送目标"的数据来源——服务端绑定资料还是请求参数。
   - 完成标准: 抓包改手机/邮箱字段的测试有结论；参数来源即缺陷。
   - 判停条件: 流程无发送环节（如安全问题自助改密），跳到步骤 4 核执行绑定。
3. **核阶段二（凭证四性）**: 对凭证逐项检查：随机源（CSPRNG 而非资料推导）、一次性、时效、会话绑定。
   - 完成标准: 四性各有 PASS/FAIL；发现确定性材料生成 Token 即标"可重算签名"缺陷。
4. **核阶段三（执行复验）**: 检查提交新密码/新绑定落库时是否原子复核凭证与目标账号的匹配。
   - 完成标准: "合法凭证 + 改目标参数"的验 A 改 B 用例有结论；不复验即缺陷。
5. **输出三阶段缺陷表与修复映射**: 每条缺陷对应到阶段设计要求（地址服务端取值/凭证四性/执行原子复验）。
   - 完成标准: 缺陷表与修复条目一一对应，无阶段遗漏。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 登录流程本身（口令校验、会话建立）的审计——用状态真值/限频相关 skill；本 skill 只覆盖"凭证重发"型流程。
- 纯密码存储强度问题（哈希算法、加盐）——属密码存储议题，与流程三阶段正交。
- 验证码控件形态选型（图形/滑块）——用验证码四前提 skill。

### 作者在书中警告的失败模式

- 收件地址取请求参数，验证码发给攻击者（ce60）。
- 4/6 位验证码无错误次数限制被穷举（ce61）——书称"目前最常见的利用方式"。
- Token 由用户名+邮箱/时间戳 MD5 生成，可本地碰撞（ce62；骑士cms asyn_userkey 同型 ce12）。
- 校验与执行分离，执行步不复验 key 与 uid 绑定（ce63，TOCTOU 的业务版）。
- 免登录跳转只传目标 ID 不带一次性 Token（ce59 淘宝案例）。

### 作者的盲点 / 时代局限

- 2015 语境：短信/邮箱双通道；现代等价物需补 OAuth state/nonce/PKCE、TOTP、Passkey 恢复码——三阶段框架直接适用但凭证形态清单要换。
- 未深入短信下发接口自身的滥用面（轰炸/刷费）——那是限频 skill 的对象，书中一笔带过。
- "短时效"未给量化建议；现代实践（5-15 分钟 + 单次有效 + 重发作废旧码）应补齐。
- 安全问题找回（母亲姓氏类）在书内已被弱化，但现代仍存，属阶段二"凭证可枚举"的同型。

### 容易混淆的邻近方法论

- 与"密码策略"（复杂度/黑名单）不同：本 skill 不管密码本身，管"没有密码时如何安全地换密码"。
- 与 CSRF Token 不同：找回密码的 key 是认证凭证（证明身份），CSRF Token 是来源凭证（证明请求归属），混用会导致把防 CSRF 的 Token 当恢复凭证。
