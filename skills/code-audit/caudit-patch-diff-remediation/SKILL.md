# 补丁 diff 入口与成因类修复 (vf22)

## R — 原文 (Reading)

> 「非专业安全的人修复漏洞都有一个通病，不会做漏洞联想，别人指出哪有漏洞就修哪，跟这个漏洞同样利用方式的漏洞，在另外一个文件至今几年过去了还存在」「大部分厂商修复的时候应该不会考虑到短地址的问题，所以在修复之后仍然可以通过生成短链接来利用」「（用文件对比功能来快速找到修改了哪段代码……或者未公开的漏洞）」

> — 原作者, 原始方法论来源第7章 7.3、第11章 11.9、第2章 2.1.2（source.txt 行10511、行17521、行663）

---

## I — 方法论骨架 (Interpretation)

把"修复"本身当作审计对象，框架有两条支柱：

**支柱一：补丁 diff 作为审计入口。** 官方补丁是免费的漏洞情报——diff 一下就知道根因语句在哪、利用方式是什么，甚至能发现未公开的漏洞（补丁修的比公告说的多）。diff 的价值不止于"看它修了什么"，更在于反推"漏洞模式"。

**支柱二：修复质量管理。** 两类通病要主动检查：
1. **不做漏洞联想**：报告指哪修哪，同利用方式的洞在别的文件原样留存（dedecms 实证：残留数年）。正确动作是把漏洞提炼成模式（sink 特征 + 污染路径），按利用方式全库检索，一次收敛一类。
2. **字面性修复**：限制落在"用户填的字符串"而非"系统实际连接/解析的目标"——SSRF 修复禁了域名清单，短链接一跳就绕过。检查方法：枚举输入的等价表示（编码、短链、大小写、协议变体、间接引用），验证限制是否对每种表示都成立。

对企业侧推论：修复流程必须含"同类检索"与"字面性验证"两个环节，否则补丁只是把洞挪了个位置。

## A1 — 书中的应用 (Past Application)

### 案例 1: dedecms 修复不做漏洞联想（7.3 行10511）
- **问题**: 官方对 WooYun-2013-18562（评论引用二次注入）的修复质量。
- **方法论的使用**: 支柱二检查——官方只修被举报的 feedback.php，"跟这个漏洞同样利用方式的漏洞，在另外一个文件至今几年过去了还存在"。
- **结论**: 修复必须以利用方式为键横向检索全库，而非按报告点位打补丁。
- **结果**: 该观察成为"修复质量"议题的定型反例（ce43），并支撑第10章补丁复查动作。

### 案例 2: UltraEdit 文件对比分析官方补丁（2.1.2 行663）
- **问题**: 拿到开源程序补丁后如何快速定位漏洞。
- **方法论的使用**: 支柱一执行——下载 Phpcms 代码执行漏洞补丁，用 UltraEdit 文件对比快速找到修改点，判断"是不是成功修补了这个漏洞，或者未公开的漏洞"。
- **结论**: diff 是成本最低的漏洞情报通道，比公告信息量更大。
- **结果**: 该方法作为工具章节的推荐审计入口（cs22 thinkphp 补丁对比同用）。

### 案例 3: SSRF 修复字面性——短地址绕过（11.9 行17521）
- **问题**: 厂商限制了回调地址填写，为何仍可利用。
- **方法论的使用**: 等价表示检查——修复只限制"填写的字符串"，短链接把目标藏到跳转后，字面限制失效。
- **结论**: 限制必须落在实际发起连接的目标（解析+跟随重定向后），而非原始输入串。
- **结果**: "大部分厂商修复的时候应该不会考虑到短地址的问题"——字面性检查成为修复验证的标准动作（ce68）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 使用的开源组件/依赖爆出漏洞且有补丁，需要评估自身影响与修复方案。
2. 内部 fork 并魔改过开源库，官方补丁不一定覆盖魔改点。
3. 安全团队复盘修复质量：修过的洞为什么换个文件还在/换种写法还成立。
4. 响应 SRC/白帽报告后的修复验证（修复是否真闭环）。

### 语言信号 (用户的话里出现这些就应激活)

- "官方出了补丁，我们怎么分析 / patch diff / what did the patch change"
- "修复不彻底 / incomplete fix / bypass after patch"
- "同样的漏洞还有哪里有 / find all instances of this bug pattern"
- "我们 fork 过这个库 / we maintain a fork"
- "短链接/编码/大小写 绕过了限制 / equivalent representation bypass"

### 与相邻 skill 的区分

- 【组合】`caudit-mechanism-to-search-terms`: 那是"从漏洞机理现场推导搜索词"；本 skill 是"从补丁 diff 反推机理后全库检索"——检索动作复用那边的三步法，入口与目的（修复收敛）不同。
- 【组合】`caudit-blacklist-failure-modes`: 字面性修复失效是黑名单失效模式在修复域的化身——步骤 4 的等价表示枚举直接套用那边的等价能力推演。
- 【区分】`caudit-logic-vuln-audit`: 那边从业务模型出发找洞；本 skill 从补丁/修复出发——入口不同，不建链。

## E — 可执行步骤 (Execution)

1. **diff 补丁定位根因**: 获取修复前后版本，文件对比找出全部修改点，标出根因语句（被改的 sink 或验证逻辑）。
   - 完成标准: 根因语句以代码位置+一行说明记录；多处修改时逐处标注"根因修复/连带改动"。
   - 判停条件: 若拿不到补丁只有公告，从公告描述反推漏洞模式后直接进步骤 3，并标注"无 diff 验证"。
2. **提炼漏洞模式**: 把根因抽象为可检索的模式——sink 特征（函数/结构）+ 污染路径（输入到 sink 的形态），与利用方式绑定。
   - 完成标准: 模式可用一句话+一条检索式表达。
3. **全库同成因检索（漏洞联想）**: 用模式检索自有代码库/fork 的全部同型点，包括官方可能未覆盖的魔改处。
   - 完成标准: 检索结果清单逐条判定"同成因/不同成因"，同成因项列为待修。
4. **修复字面性检查**: 对每处修复枚举等价表示——编码变体、短链/跳转、大小写与空白、协议变体（http/file/gopher）、间接引用——验证限制对每种表示是否仍成立。
   - 完成标准: 等价表示清单逐项有测试结论；限制应落在实际语义目标（解析/重定向后）。
5. **回归验证与闭环**: 对全部修复点构造原利用与等价表示利用重测。
   - 完成标准: 原始 PoC + 至少 2 种等价表示 PoC 全部阻断；输出修复闭环报告。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 无补丁可参照的 0day/自研代码漏洞分析——直接走机理搜索或逻辑审计。
- 例行依赖版本升级（无 fork、无魔改）——升级+回归即可，diff 分析是额外成本；仅当升级成本高或有兼容约束时启用。
- 闭源二进制补丁的逆向（方法同源但工具链不同，书内不涉及）。

### 作者在书中警告的失败模式

- 修复不做漏洞联想，同利用方式漏洞他处留存数年（ce43，dedecms 实证）。
- 字面性修复被短链接绕过（ce68）——"只要限制填写就可以"是幻觉。
- 修复 commit 只改单点、无同类检索记录（ce43 预警信号）。
- 只看公告不 diff 补丁——错过未公开修复与真实根因。

### 作者的盲点 / 时代局限

- 2015 语境：手工 UltraEdit 对比、单仓检索；现代等价物是 SCA 工具、CI 中的补丁门禁、依赖漏洞告警（ Dependabot 类）——但"fork 与魔改点官方补丁不覆盖"的判断仍然必须人工做，工具只覆盖已知依赖路径。
- 未讨论修复的回归测试工程（用例库、模糊测试回归），"看起来修了"与"修了"的差距留给读者。
- 供应链时代的新面（恶意补丁/投毒、签名校验）超出书中语境，迁移时 diff 前应先验来源可信。

### 容易混淆的邻近方法论

- 与"跟进 CVE 情报"不同：情报消费知道"有洞"；本 skill 要求 diff 到根因并做自身收敛，多两层动作（模式提炼+全库检索+字面性验证）。
- 与代码评审不同：评审面向变更质量整体；本 skill 只针对"漏洞修复"这一类变更做专项收敛检查。
