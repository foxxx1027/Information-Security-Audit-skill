# 支付三不变量 (vf17)

## R — 原文 (Reading)

> 「第一、二、三种比较简单，分别是客户端可修改单价、总价和购买数量，服务器端未校验严格导致」「并没有验证这两个数字是否小于0……把数字改成负数然后提交上去」「1）保证数据可信，商品单价及总价不可从客户端获取。2）购买数量不能小于等于0。」「当一个支付操作开始就应该立马锁定当前账户」

> — 原作者, 原始方法论来源第6章 6.2.1.4、第11章 11.7（source.txt 行9361、行9365、行17449-17455）

---

## I — 方法论骨架 (Interpretation)

支付安全的检查不必逐漏洞记忆，收敛为三条不变量——任何资金流程跑一遍，违反任一条即是洞：

1. **金额服务端真值**: 单价、总价、退款金额参与计价的部分一律取服务端数据（商品库价格、订单持久态）。客户端上报的金额字段最多做一致性校验，绝不能作为入账依据。部分退款比例、优惠计算同理须服务端重算。
2. **数值下限**: 数量、金额必须校验 > 0。负数数量在"单价×数量"型结算里等于反向充值；0 元单是边界绕过入口；无上限的退款次数等于重复提现。
3. **原子与幂等**: 扣费与权益发放（开通、发货、积分）必须同事务或等价原子地完成；同一订单/请求重复提交必须幂等。"开通-扣费"两步之间的时间差允许重复发包——低价多购，这是独立的攻击面而非理论并发问题。

三条之外补一条链路检查：支付回调里"已过滤参数被业务再次改写"（如 str_replace 回填）会使过滤归零——金额链上过滤之后的任何再加工都要逐行核对来源。

## A1 — 书中的应用 (Past Application)

### 案例 1: 购物车三类改值 + 时间差（6.2.1.4）
- **问题**: 商城支付漏洞反复出现，需要一个系统检查框架。
- **方法论的使用**: 归纳四类利用：改单价、改总价、改数量（含负数，"部分商城只做单价×数量=总价、不验小于0"）、重复发包利用开通与扣费时间差。
- **结论**: 前三类对应不变量一、二，第四类对应不变量三；"找到支付功能代码，看看代码过滤情况即可"定位。
- **结果**: 四类成为 11.7 对策的输入，QQ钻/VPS 开通是同类实例。

### 案例 2: 11.7 三对策——不变量化表达
- **问题**: 把四类漏洞的修复整理为设计规范。
- **方法论的使用**: 逐条映射：金额不可从客户端获取（不变量一）、数量不能≤0（不变量二）、支付开始即锁定账户防并发（不变量三的雏形）。
- **结论**: 对策与漏洞一一对应且可逐条验证，优于"加强校验"式表述。
- **结果**: 三对策成为书内支付设计的定型输出，12 章账户/操作层锁定是其体系延伸。

### 案例 3: Ecshop 支付宝回调 str_replace 注入（6.2.1.5）
- **问题**: 支付插件回调参数已过滤，为何仍出注入。
- **方法论的使用**: 链路检查——$order_sn 过滤后被 POST 同名参数 str_replace 回填，反斜杠被吃掉，过滤失效后进查询。
- **结论**: 支付回调是"过滤后再加工"的高发带；对过滤→使用之间的每次再赋值/替换核对数据来源。
- **结果**: 作者把支付模块列为高危专项，回调/验签/金额/订单号定为必查项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计电商/知识付费/SaaS 订阅的支付、充值、退款、提现流程。
2. 设计"先享后付、随时退款、部分退款"类非标准资金流程。
3. 压测或红队前的支付域自查清单。
4. 复盘资损事件（0 元购、负数对冲、重复提现）定位违反了哪条不变量。

### 语言信号 (用户的话里出现这些就应激活)

- "支付逻辑漏洞 / payment logic vulnerabilities / 支付越权"
- "改价格 / price tampering / 0元购 / 负数购买"
- "重复退款 / duplicate refund / 提现重放"
- "支付回调怎么校验 / payment callback validation"
- "下单和扣款不是原子的 / non-atomic payment"

### 与相邻 skill 的区分

- 【依赖】`caudit-server-side-state-truth`: 那是通用三问；本 skill 是资金域的实例化——三条不变量（金额真值=真值存哪、原子幂等=迁移原子、数值下限=裁决输入校验）可直接对照执行，并加入回调再加工检查这一支付特有链路。
- 【组合】`caudit-security-metadata-pollution`: "金额真值不得来自请求"同时是元数据污染的形态；本 skill 给资金流程的完整核对顺序，那边给"参与构造结构的参数"判别式的推广。
- 【组合】`caudit-logic-vuln-audit`: 那是逻辑漏洞的通用方法（状态机对照）；本 skill 是其支付域的预编译清单，直接逐条跑，清单之外回到通用法。

## E — 可执行步骤 (Execution)

1. **画资金流图**: 标出金额、数量、订单号在客户端→下单→回调→入账/退款全链路的每个来源与写入点。
   - 完成标准: 每个金额类字段标注"来源=客户端/服务端"，每个状态变更标注事务边界。
2. **跑不变量一（金额真值）**: 对每个入账金额反查其最终来源。
   - 完成标准: 所有计价输入均为服务端值；发现客户端金额参与计价即缺陷。
3. **跑不变量二（数值下限）**: 对数量/金额检查 >0 校验与上限（次数/频率）。
   - 完成标准: 负数、0、超大值、小数精度四类边界用例各有结论。
4. **跑不变量三（原子幂等）**: 检查扣费与权益发放的事务边界；同一订单重复回调/重复点击/并发请求的行为。
   - 完成标准: 重复请求双扣/双退测试有结论；时间差窗口（开通未扣费期间重放）有结论。
   - 判停条件: 若流程无余额扣减（全额第三方支付、无退款），记录后跳过并发复测，保留幂等检查。
5. **查回调再加工**: 对回调处理代码列出过滤之后的每次替换/拼接/解码，核对数据来源。
   - 完成标准: 再加工清单为空或每项确认来源可信。
6. **输出违反项报告**: 每条违反对应不变量编号与修复方向。
   - 完成标准: 三不变量 + 回调链四节各有明确 PASS/FAIL。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 支付渠道协议层问题（签名算法、证书、通信安全）——属对接安全，不是业务不变量问题。
- 对账/清结算系统设计（渠道差异、汇损）——业务正确性议题，超出三不变量。
- 风控反欺诈（盗卡、洗钱识别）——三不变量只保证"流程自身不被改值与重放"，不判断交易合理性。

### 作者在书中警告的失败模式

- 单价/总价/数量客户端可改（ce38）——书内四类漏洞的前三类。
- 负数数量未拦截："并没有验证这两个数字是否小于0"（行9365）。
- 开通-扣费时间差，重复发包低价多购（行9367，QQ钻/VPS 同型）。
- 回调参数过滤后被 str_replace 再改写（cs27 Ecshop）。

### 作者的盲点 / 时代局限

- "锁定当前账户"粒度过粗：锁整账户会阻塞同用户其他正常支付，现代按订单/幂等键加锁（数据库唯一约束、幂等令牌）；作者未达幂等键概念，"不能同时两个请求"是其雏形表述。
- 2015 语境：单一 MySQL 事务可覆盖大多数场景；现代分布式支付（跨服务、消息队列、最终一致）需引入 saga/补偿与至少一次投递下的幂等设计。
- 未讨论优惠/组合支付/积分抵扣等复合计价的真值边界——迁移时"金额真值"须扩展为"全部计价输入服务端化"。

### 容易混淆的邻近方法论

- 与"金额签名防篡改"不同：签名只保证传输完整性，不改"客户端决定金额"这一事实；不变量一要求金额根本不来自客户端。
- 与 WAF/风控规则不同：三不变量是业务层断言，扫描器与 WAF 均无法代验（作者在 12.10 明言 WAF 无法结合应用逻辑）。
