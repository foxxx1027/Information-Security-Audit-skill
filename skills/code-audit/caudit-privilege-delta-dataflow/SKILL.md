# 权限差数据流——低权写高权必读的通道 (vf27)

## R — 原文 (Reading)

> 「XSS盲打是指在不确定能否利用的情况下输入XSS代码进行不可预知的攻击，而这正是利用了私信和反馈这些功能……利用其中存在的XSS漏洞拿到管理员cookie数据」「当管理员在Web后台查看反馈后，即可获得管理员的cookie」「程序会在页面中输出文件名，而通常会疏忽对文件名进行过滤」

> — 原作者, 原始方法论来源第11章 11.8、第3章 3.3（source.txt 行17463、行17477、行3801）

---

## I — 方法论骨架 (Interpretation)

存储型攻击的价值不由 payload 决定，由**数据流两端的权限差**决定。方法论是把系统里的数据流按"谁写入 × 谁读取"过滤一遍：

**低权可写 + 高权必读 = 必达通道。** 私信、反馈、工单、评论审核、报错日志——这些字段是攻击者与高权限会话之间唯一"保证被看见"的管道：管理员的工作职责就是打开它。一次注入的成功率接近 100%，远高于钓鱼。因此找目标不是撒网，是列通道：

1. 枚举全部"客户/低权写、客服/管理员读"的字段——不止正文：附件文件名、User-Agent（工单系统常把用户 UA 回显给客服排障）、邮箱客户端标识、订单备注、截图名、搜索关键词日志；
2. 每个字段在高权端按其上下文（HTML/属性/JS）输出编码；
3. 高权会话与普通会话隔离，后台 Cookie 加固 + 重要操作二次验证（即便 Cookie 被窃也挡住关键操作）。

配套"盲打"定性：不确定内容会在哪渲染、能否执行时，照样投递——必达通道的投递成本极低，回显未知不应阻止测试。这条纪律与"必须有回显才算洞"的保守习惯相反。

## A1 — 书中的应用 (Past Application)

### 案例 1: 爱鲜蜂反馈 XSS 盲打入后台（11.8，WooYun-2015-118779）
- **问题**: 反馈功能注入的完整提权链。
- **方法论的使用**: 通道分析——粉丝反馈是"直接跟管理员沟通"的必达通道；图11-15~11-17 完整演示：反馈处插 XSS → 管理员后台查看 → Cookie 被送出 → 用 Cookie 登录后台。
- **结论**: 私信、反馈、留言、报错页这类"直接与管理员沟通"的功能是盲打高发带。
- **结果**: 定性成立并配真实案例（cs45），防线落点为后台 Cookie 加固 + 重要操作二次验证。

### 案例 2: 文件名输出 XSS——非正文字段的通道（3.3 行3801）
- **问题**: 文件管理/上传功能还有什么字段会被忽视。
- **方法论的使用**: 通道枚举扩展——"程序会在页面中输出文件名，而通常会疏忽对文件名进行过滤"，低权提交的文件名（含尖括号等特殊符号）在高权/公共页面渲染时执行。
- **结论**: 正文之外的元字段（文件名/路径）同样是低权写高权读通道。
- **结果**: 通道清单从正文扩展到元数据，审计覆盖面修正。

### 案例 3: dedecms 二次注入——写入/触发分离的权限与时间差（7.3 行10491）
- **问题**: 存储型注入与权限差通道的关系。
- **方法论的使用**: 机制层佐证——payload 先写入保存（低权），后续被调用触发（高权/后续流程读取），"写入-触发分离"即权限差与时序差的数据流表达。
- **结论**: 二次漏洞的审计锚点（按表名/字段名追消费点）与权限差通道枚举是同一数据流的两种视角。
- **结果**: 与 vf09 的锚点追踪法衔接，通道枚举提供"追哪些字段"的候选集。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 排查"存储型 XSS 会不会打到后台/管理员"的风险评估。
2. 审计工单、客服、私信、反馈、内容审核、举报类系统。
3. 设计这类系统的防线：字段级输出编码 + 会话隔离 + 后台加固的取舍。
4. 红队评估中决定 XSS 漏洞的利用优先级（哪些注入点值得先打）。

### 语言信号 (用户的话里出现这些就应激活)

- "存储型 XSS 怎么利用/危害多大 / stored XSS impact"
- "XSS 打后台 / XSS to admin panel / 盲打 / blind XSS"
- "工单/客服/反馈系统 安全审计 / ticket system security"
- "附件名/UA/备注 这些字段要过滤吗 / metadata fields XSS"
- "管理员会看到用户提交的内容 / admin views user content"

### 与相邻 skill 的区分

- 【组合】`caudit-second-order-vuln`: 二次漏洞讲"写入与触发分离"的机制（取出即新输入、锚点追踪）；本 skill 讲"按权限差给这些数据流排序选目标"——机制回答怎么追，通道枚举回答先追哪、值不值得追，审工单/私信/反馈类系统时连用。
- 【区分】`caudit-logic-vuln-audit`: 那是业务状态机的应然/实然对照；本 skill 是数据流视角的定向透镜（谁写谁读）——同为审计透镜但维度不同，不建链。
- 与输出编码类 skill 的区别: 编码是对策层（每个消费点怎么转义）；本 skill 在其上游决定"哪些字段必须进编码清单"。

## E — 可执行步骤 (Execution)

1. **枚举通道字段**: 对目标功能列出全部"低权可写"字段，再标注每个字段的读取端及读者权限（客服/管理员/公共页面）。
   - 完成标准: 字段表三列（字段/写入者/读取者与权限），"低权写+高权必读"项单独标出——含附件名、UA 回显、备注、日志等非正文字段。
   - 判停条件: 若功能无任何高权读取端（用户写、只有同权用户读），记录"无权限差通道"后转普通输出编码审计。
2. **追每个通道字段的渲染上下文**: 找到高权端展示该字段的模板/代码，确定上下文类型（HTML 体/属性/JS/URL）。
   - 完成标准: 每个通道字段标注渲染位置与上下文类型。
3. **盲打投递验证**: 对通道字段投递上下文对应的测试 payload（回显位置未知也投递），在高权会话中观察执行。
   - 完成标准: 每个通道字段有投递记录与执行/未执行结论。
4. **评估提权链纵深**: 假设 Cookie/凭据已窃，核对后台防线——HttpOnly/SameSite、会话隔离（前后台域分离）、重要操作二次验证。
   - 完成标准: "XSS 成立后还能走多远"有明确结论（窃取即沦陷 / 沦陷但关键操作有二次验证拦截）。
5. **输出字段级整改清单**: 每个通道字段对应高权端输出编码修复 + 管理建议（后台展示纯文本化/元字段服务端重写）。
   - 完成标准: 清单可直接指到模板行号，附提权链纵深结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 反射型 XSS 的单会话场景——无存储、无权限差，用输出编码审计即可。
- XSS payload 与绕过技巧的构造（编码变形、WAF 绕过）——那是机理搜索的载荷域；本 skill 不关心 payload 怎么写，只关心往哪投、值不值得投。
- 纯内容安全策略讨论（CSP 设计）——那是纵深层，本 skill 输出的是通道清单与编码落点。

### 作者在书中警告的失败模式

- 只审正文字段，忽视文件名、UA、备注等元数据通道（行3801）。
- "不确定能否利用就不测"——盲打定性恰恰要求先投递再说（行17463）。
- 拿到 Cookie 即视为终点——关键操作无二次验证时提权链才完整闭合（cs45 后的防线要求）。
- 把反馈/私信当普通用户内容给低优先级——"直接跟管理员沟通"的通道价值最高（行17463）。

### 作者的盲点 / 时代局限

- 2015 语境：以窃取 Cookie 为主链；现代 HttpOnly/SameSite/CSP 削弱了经典链，但 token 存于 JS 的 SPA、DOM 型 XSS、水坑式二次注入仍在——通道枚举方法不变，第 4 步的纵深评估须按当代浏览器防线重写。
- 未提出前后台域名/会话隔离（scope 切分）这一现代标准措施；也未考虑后台把用户内容导出（CSV/Excel）后的离线触发面。
- "必达"判断依赖管理员职责（一定会打开反馈），未覆盖延迟读取（周报导出、批量审核）的时间维度——通道仍在，时点更晚。
- 书中防御落点偏输出编码，未提输入侧元字段重写（文件名服务端重生成即结构性消除该通道）。

### 容易混淆的邻近方法论

- 与"存储型 XSS"漏洞类型知识不同: 类型知识说"入库的会执行"；本 skill 是目标选择方法——按权限差×必达性排序，输出字段级清单，正文之外的通道（文件名/UA）正是类型知识不提示的盲区。
- 与最小权限原则不同: 那管"账号能做什么"；本 skill 管的是"哪些数据流天然跨越权限边界"。
