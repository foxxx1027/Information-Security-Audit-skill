# 限频多维组合与策略滥用面 (vf18)

## R — 原文 (Reading)

> 「之前有个"锁QQ"的茬儿，说的是QQ登录密码连续错误次数30次，就会被锁定QQ，就有人利用这个问题不断地去锁定别人的QQ」「这种防御撞库的手段存在一个误杀的问题，如果出口IP里面还有一个大内网，比如企业网、学校网，这时候就会误杀其他用户」

> — 原作者, 原始方法论来源第11章 11.2.1（source.txt 行17233、行17237；另见行17211 短信双层限频、行845 Client-IP 伪造、行17991 内网IP不够）

---

## I — 方法论骨架 (Interpretation)

常见做法是问"这个接口要不要限频"；本框架换一个问题：**这个限频策略本身会被怎么攻击**。任何单维限频都同时暴露两个面：

- **绕过端**：按 IP 限——IP 头（Client-IP/XFF）可伪造，Discuz 式取 HTTP_CLIENT_IP 直接作废整条策略；按账号限——攻击者换账号列表继续撞。
- **滥用端**：按账号限错误次数——攻击者可以故意输错 30 次把你锁在门外（锁号式 DoS，受害者替攻击者买单）；按 IP 限——企业网/学校网共享出口，误杀无辜用户。

因此设计输出必然是组合而非选型：**多维组合**（账号+IP+设备，缺一不可，短信下发即"单手机号+单IP"双层）+ **分级响应**（告警→验证码→锁定，而非一步封死）+ **失败计数与成功配额分离**（失败计数不应消耗受害者的可用性）+ **申诉通道**（误杀可解）。

审视任何现存限频时，逐维问两端：能不能绕？能不能被武器化？

## A1 — 书中的应用 (Past Application)

### 案例 1: 锁QQ——按账号限频的滥用端（11.2.1 行17233）
- **问题**: QQ 密码错 30 次锁号本为防爆破，却被用来恶意锁他人 QQ。
- **方法论的使用**: 滥用端推演——策略的触发条件由任何人满足，攻击者替受害者触发。
- **结论**: 基于账号的错误次数限制本身成为拒绝服务攻击面；只能组合（验证码/多因素/代价型验证）而不能单独依赖。
- **结果**: 作者以"茬儿"（真实事件）定性，支撑 11.2.1 的组合式防撞库设计。

### 案例 2: Discuz 按 IP 限登录失败——绕过端（2.3.1 行845）
- **问题**: 每个 IP 5 次失败机会的限制如何被破。
- **方法论的使用**: 绕过端推演——Discuz 取 HTTP_CLIENT_IP，该头由请求方任意填写。
- **结论**: 以可伪造头为限频主键，策略整体失效；Burp 伪造该头即可继续爆破。
- **结果**: 与 11.2.1 互相印证："discuz获取的是Client-IP存在绕过的问题"。

### 案例 3: 短信双层限频（11.1.2 行17211）
- **问题**: 短信验证码接口被刷，消耗短信资源（轰炸/刷费）。
- **方法论的使用**: 多维组合落地——单手机号上限防轰一个人，单 IP 上限防批量手机号刷资源，双层缺一不可。
- **结论**: 每个维度各自封堵一类滥用，组合才闭合。
- **结果**: 双层限制成为短信接口的标准设计，12.5 进一步叠加双因素。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计登录/短信/评论/抽奖等接口的限频与锁定策略。
2. 评审已有策略："连续错 5 次锁账号半小时"这类提案的风险。
3. 事故响应："我们的登录口被脚本撞库/我们的用户被恶意锁号"。
4. 投诉处理："整个公司出口 IP 被封了"——误杀分析。

### 语言信号 (用户的话里出现这些就应激活)

- "登录错误次数限制怎么设计 / account lockout policy"
- "锁号 / 恶意锁定别人账号 / lockout DoS"
- "按 IP 限还是按账号限 / rate limit by IP or account"
- "短信接口被刷 / SMS flooding /轰炸"
- "误杀 / false positive / NAT 用户被限"

### 与相邻 skill 的区分

- 【组合】`caudit-captcha-failure-premises`: 验证码解决"每次尝试的通过条件"，限频解决"允许尝试多少次"；限次前提由限频支撑，分级响应中"何时触发验证码"又消费验证码——互为配套。
- 【组合】`caudit-server-side-state-truth`: 限频计数也是一种必须服务端持有的状态（cookie 计数可被删），真值原则是本 skill 的底层依赖之一；本 skill 聚焦策略的双端推演与组合设计。
- 【组合】`caudit-api-relay-architecture`: 那边的接口调用阈值是入侵检测信号（异常拖库），本 skill 是防滥用的配额策略——目标相反（拦滥用 vs 发现入侵）但可共用同一计数设施。

## E — 可执行步骤 (Execution)

1. **列出现有/拟定的限频维度**: 每条策略写清主键（账号/IP/设备/手机号）、计数事件（失败/请求/成功）、阈值、响应动作（锁定/验证码/拒绝）。
   - 完成标准: 策略表四要素齐全，无"加强限制"式模糊条目。
2. **逐维推演绕过端**: 主键能否伪造（IP 头/改号/换设备指纹）或轮换（账号列表/代理池）。
   - 完成标准: 每维标注可绕过方式或"不可绕过"的理由。
3. **逐维推演滥用端**: 攻击者能否用他人主键触发惩罚（锁号）、惩罚是否误伤共享主键的无辜者（NAT 出口）。
   - 完成标准: 每维标注滥用方式与受害群体。
   - 判停条件: 若策略主键与服务端强身份（如按订单幂等键）绑定且无对外惩罚，两端推演可记录"不适用"后跳过。
4. **设计组合与分级**: 输出多维组合 + 分级响应（告警/验证码/锁定）+ 失败计数与成功配额分离 + 申诉/解锁通道。
   - 完成标准: 每个绕过端与滥用端各被至少一条组合措施覆盖。
5. **验证 IP 取值链路**: 确认限频用的 IP 来自可信来源（网关注入并剥离外部头），而非客户端可控头。
   - 完成标准: IP 来源链路图完成，可控头不参与主键。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 网络/传输层 DDoS 防护（SYN flood、带宽耗尽）——那是基础设施层，本 skill 的对象是应用层业务配额。
- 验证码强度与形态选型——用验证码四前提 skill；本 skill 只决定"何时触发验证码"这一分级动作。
- 内部系统的可信调用方配额（SLA 管理）——无对抗方时不需要滥用端推演。

### 作者在书中警告的失败模式

- 完全不限——撞库敞开（ce58）。
- 只按账号限——被"锁QQ"式滥用，且换用户名列表即可继续撞（行17233）。
- 只按 IP 限——Client-IP 伪造绕过（cs02/ce09）+ 大出口 IP 误杀（行17237）。
- 内网 IP 限制当完整防护——"攻击者有很大的可能已经…进入到内网"（行17991，需叠双因素）。

### 作者的盲点 / 时代局限

- 2015 语境：无设备指纹、无风控评分/渐进式挑战（step-up）术语，作者的"验证码+多因素+代价型验证"是分级响应的雏形；现代实现应补设备维度与风险评分。
- 未讨论限频算法与窗口（固定窗口临界突刺、滑动窗口、令牌桶）——书内只谈策略不谈实现，迁移时需自选算法。
- 未给"锁定时长/自动解锁"与人工申诉的运营设计；锁号 DoS 的根治（如仅对失败计数触发验证码而非锁定）未展开。
- IPv6 海量地址轮换、住宅代理池使"按 IP"维度的现代权重进一步下降。

### 容易混淆的邻近方法论

- 与"防暴力破解"通识不同：通识只覆盖绕过端；"安全机制自身成为攻击面"（滥用端）是本框架的差异化视角。
- 与风控系统不同：本 skill 是策略评审框架，不建模型、不打分，输出的是组合规则与分级动作。
