# 二次漏洞——取出即新输入（vf09）

## R — 原文 (Reading)

> 「二次漏洞的出现归根结底是开发者在可信数据的逻辑上考虑不全面，开发者认为这个数据来源或者这个配置是不会存在问题的，而没有想到另外一个漏洞能够修改这些"可信"数据」
>
> — 原作者, 原始方法论来源第7章 7.1（source.txt 行10493）

---

## I — 方法论骨架 (Interpretation)

二次漏洞 = 攻击载荷分两个请求阶段生效：第一次请求把 payload 写进存储（库、配置、文件、日志），后续请求取出使用时触发。判定规则有三个转向：

1. **信任判定看解释器，不看来源**。"这是从库里来的""这是系统配置"——来源标签不提供任何豁免；唯一问题是：这个值**本次**要进哪个解释器（SQL/HTML/shell/Excel 公式）？进哪个，就按哪个的规则过滤。
2. **两个独立控制点**。写入点的过滤（如入库时 addslashes）只对写路径负责；消费点的过滤必须独立存在且按消费语境选择。写入点过滤"已做"不能推出消费点安全——dedecms 的 addslashes 之败正在于此。
3. **锚点追踪法**。输出点与输入点可能完全不在同一业务流（低权用户写入的昵称，在高权后台被渲染）。按**数据**而非按**页面**组织审计：以表名/字段名为锚点，grep 全部读该字段的位置，逐个核对输出语境。

附带判据：**格式限制不是安全边界**。字段长度、字符集白名单只影响单次写入的形态；分次提交、引用拼接、后续加工都能凑齐 payload——60 字符限制挡不住两次提交。

## A1 — 书中的应用 (Past Application)

### 案例 1: dedecms 评论二次注入（WooYun-2013-18562）
- **问题**: 第一次写入明明转义了，为何注入仍发生。
- **方法论的使用**: 按两阶段拆解——第一次写入 addslashes 生效；引用评论重新写入时**不再过滤**，转义只覆盖了第一跳。
- **结论**: 写入点过滤与消费点过滤是独立控制点，缺后者即成洞。
- **结果**: 漏洞成立并公开于乌云（7.3 完整分析）。

### 案例 2: 60 字符限制分次提交拼接
- **问题**: 字段长度限制能否当防线。
- **方法论的使用**: 标题限 60 字符放不下完整 payload → 两次提交前后半段，利用二次注入在库中拼接成型。
- **结论**: 业务格式限制（长度/字符集/关键字）不是安全边界。
- **结果**: 绕过成功，漏洞"并不鸡肋"（7.3，safekey 团队讨论结论）。

### 案例 3: 骑士cms 友情链接存储型 XSS——输出语境错位
- **问题**: 过滤链存在，为何还能执行。
- **方法论的使用**: logo 的 img 标签被放进 span 的 title 属性，鼠标悬停解析时执行——写入侧过滤未按"属性语境"编码。
- **结论**: 消费点的解释器（属性上下文）决定过滤形态，与写入侧做了什么无关。
- **结果**: 4.2.1.3 拆解完整链路（前台提交→过滤链→入库→列表页渲染触发）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计带"用户内容入库、他处展示/导出"的功能：评论、昵称、备注、附件名、工单回复。
2. 评估"入库前统一转义了"这类安全声明的有效性。
3. 设计导出功能（CSV/Excel）——低权用户写的字段被高权用户打开。
4. 排查配置/缓存被另一漏洞改写后的连锁触发（"可信"数据被污染）。

### 语言信号 (用户的话里出现这些就应激活)

- "数据已经过滤过入库了，展示还要处理吗 / do I still need to escape on output"
- "存储型 / stored XSS / 二次注入 / second-order injection"
- "Excel 打开导出文件会执行 =cmd 吗 / CSV formula injection"
- "字段就 20 个字符，放不下 payload 吧"
- "评论被引用/搜索高亮/邮件转发时会不会出问题"

### 与相邻 skill 的区分

- 【依赖】`caudit-data-pollution-two-paths`: 两路模型把"回读"定义为独立的主动获取污染路径（建模）；本 skill 给出回读数据的具体审计流程与判定规则（执行）——先接受建模，再跑流程。
- 【组合】`caudit-privilege-delta-dataflow`: 那边按"低权写→高权必读"给数据流排序（找哪个字段值得审）；本 skill 给出字段选定后的链路判定方法（锚点追踪 + 双控制点）——先排序再追踪。
- 【区分】`caudit-escape-as-last-step`: 时序判据管单链路上转义的位置；本 skill 管**跨请求**的写入/触发分离——共享"过滤后变换"根因但时域不同，不建链。

## E — 可执行步骤 (Execution)

1. **选定锚点字段**：确定要审计的持久化数据（表.字段 / 配置键 / 文件）及其全部写入点。
   - 完成标准: 锚点字段与写入点清单明确。
2. **枚举全部消费点**：按字段名/配置键全库检索读取处，包括非显性消费（搜索高亮、日志回显、邮件模板、导出、统计）。
   - 完成标准: 消费点清单覆盖"进解释器"与"进安全决策"两类。
   - 判停条件: 消费点枚举不全（动态拼字段名）时，标注覆盖率并降级结论置信度——不得声称"已全部核对"。
3. **逐消费点定解释器**：为每个消费点标注其解释器与语境（SQL/HTML/属性/JS/shell/公式）。
   - 完成标准: 每个消费点有语境标签。
4. **核对消费点过滤**：该语境的过滤/编码是否存在、是否对口（属性语境用属性编码而非实体转码）。
   - 完成标准: 每个消费点标注"有对口过滤 / 无过滤 / 过滤错语境"。
5. **验证格式限制非边界**：对有长度/字符集限制的锚点字段，评估分次提交、引用拼接、加工链等凑齐 payload 的路径。
   - 完成标准: 限制字段有"可绕 / 不可绕"结论。
6. **输出锚点追踪表**：写入点×消费点×语境×过滤状态的完整表格，作为报告附件。
   - 完成标准: 表格可复用于回归审计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单请求内即时反射的漏洞（反射 XSS、直接注入）——无第二跳，用注入语境判据即可。
- 数据只写不读（归档日志无任何消费路径）——无消费点即无二次漏洞，但需先确认真的没人读。
- 纯机读字段（自增 ID 由 DB 生成且不可影响）——锚点不可污染时链条第一环不成立。

### 作者在书中警告的失败模式

- "可信数据"标签永久豁免检查——作者点名的总根因（行10493）。
- 把长度/格式限制当防护——60 字符被分次提交击穿（行11263）。
- 只在原功能页面找输出——"输出点可能跟输入点完全不在一个业务流上"（4.2.1.2，行5017），必须按数据锚点全局搜。

### 作者的盲点 / 时代局限

- 书内锚点搜索基于 PHP+MySQL 直拼（grep 表名字段名即可）；现代 ORM/序列化（JSON 列、对象图）中锚点形态变化，需按实体字段与 DTO 展开，方法不变。
- 未覆盖现代二次攻击面：反序列化链、缓存投毒、搜索引擎索引触发、浏览器自动预取——都符合"写入/触发分离"定义，迁移时应扩展进锚点追踪表。
- 书内消费点修复以功能点各自过滤为主；当代对 HTML 语境优先 CSP + 模板自动转义等系统性方案，审计结论可平移、修复建议应升级。

### 容易混淆的邻近方法论

- 与"存储型 XSS"这个漏洞名词不同: 名词是知识，本 skill 是**判定规则与检索流程**（取出即新输入 + 双控制点 + 锚点追踪），适用于 SQL/shell/公式等一切解释器。
- 与 TOCTOU（检查-使用时间差）同属状态假设失效家族，但二次漏洞强调跨请求的持久化写入，TOCTOU 强调同请求内的竞态。
