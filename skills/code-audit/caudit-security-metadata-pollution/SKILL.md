# 安全策略参数污染（vf12）

## R — 原文 (Reading)

> 「检查上传格式，不过$alowexts是从表单提交的，可绕过」「不把验证码放到HTML页面或者Cookie中」
>
> — 原作者, 原始方法论来源第5章 5.1.3 / 第11章 11.1.1（source.txt 行6721-6725、行17189）

---

## I — 方法论骨架 (Interpretation)

"不要信任用户输入"的通识版本只覆盖**数据**参数（内容要转义、校验）。本判据点出元层失效：**安全机制自身的参数被污染**——过滤、白名单、开关、凭证这些"安全元数据"本身交给了请求方决定。

判别式：问这个参数在下游扮演什么角色——

- 进入解释器被当作**数据**处理（值参与计算/展示）→ 属于普通数据参数，走过滤/校验路线。
- 参与**构造结构或裁决**（决定白名单内容、开关状态、验证答案、金额真值、列名/排序键、凭证要素）→ 属于安全元数据，**出现在请求链上即构成缺陷本身**，不存在"过滤好了就行"的补救空间——因为过滤它的依据同样需要另一个不可信输入。

四类高频形态：(a) 白名单集合随表单提交（phpcms $alowexts）；(b) 验证答案/凭证随响应下发或由请求自证；(c) 金额/数量真值由客户端上报；(d) 结构参数（列名、排序键、返回字段）直接来自请求。

修复方向唯一且同构：请求只传**选择意图/索引**，服务端映射到自己持有的常量、真值或枚举——把"元数据"从请求词汇表中彻底移走。

## A1 — 书中的应用 (Past Application)

### 案例 1: phpcms 上传白名单 $alowexts 来自表单
- **问题**: 白名单机制在，为何形同虚设。
- **方法论的使用**: 作者读 file.php 时在代码注释中直接点破——检查扩展名的白名单数组是从表单提交的，攻击者改为 php 即通过校验。
- **结论**: 白名单的**内容**被参数化 = 机制不存在。
- **结果**: "可绕过"成为该上传链缺陷群的第一环（行6721-6725，WooYun-2014-062881 同链）。

### 案例 2: 支付金额/数量由客户端上报
- **问题**: 元数据污染在资金域的形态。
- **方法论的使用**: 6.2.1.4 拆解四类支付漏洞——改单价/改总价/改数量（含负数）全部源于真值参数走请求通道。
- **结论**: 金额真值是安全元数据，必须服务端定价。
- **结果**: 11.7 落地为"金额需要以服务器的数据为准"等三对策（并入支付不变量）。

### 案例 3: 验证码答案下发与免登录缺 Token
- **问题**: 凭证类元数据的污染形态。
- **方法论的使用**: 11.1.1 要求答案不进 HTML/Cookie（答案即元数据，不得交请求方）；11.2.2 淘宝案例中 user_num_id 直接换发 Cookie、缺一次性 Token——凭证要素由请求自证。
- **结论**: 验证答案、身份凭证均属元数据，出现在请求/响应可及处即缺陷。
- **结果**: 前者成为验证码硬规则之一，后者是被阿里 5 万元悬赏确认的高危逻辑漏洞。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计导出/列表功能：用户可勾选"导出字段"或传排序字段，服务端要拼 SQL。
2. 评审表单时发现隐藏域携带"原价/折扣/角色/白名单"等值。
3. 审查 API：哪些参数在服务端被用于 if 分支/权限裁决而非数据展示。
4. 配置化系统：策略（限流阈值、开关）可否经普通用户请求链修改。

### 语言信号 (用户的话里出现这些就应激活)

- "导出字段名/排序列直接用用户传的，有风险吗 / column name from request"
- "白名单放表单里方便扩展 / hidden field carries price or role"
- "金额前端算好传上来 / client computes total"
- "验证码答案要不要下发 / send captcha answer to client"
- "feature flag 由请求控制"

### 与相邻 skill 的区分

- 【组合】`caudit-server-side-state-truth`: 状态真值原则管"资格/次数/额度/身份/结果"这类**业务状态**的存放与裁决；本 skill 管"安全机制自身的参数"来源——金额真值在两者交叠处，一边给来源判别式，一边给状态机与原子性。
- 【组合】`caudit-var-overwrite-chain`: 变量覆盖判定"外部数据能否改写程序变量"的链条；本 skill 直接按参数角色定性——元数据字段（白名单/开关/角色）是那边三点连线中价值最高的连线目标。
- 【组合】`caudit-type-context-defense`: 类型判据给"标识符语境用枚举映射"的防御选型；本 skill 是选型背后的归属原则——为什么只能枚举映射（因为列名是元数据）。
- 【组合】`caudit-whitelist-spectrum`: 那边管白名单的**形态与处置**怎么设计（枚举/类型锁定/形态约束）；本 skill 管白名单的**内容**必须由谁决定（服务端）——来源与结构两个维度合起来白名单才成立。
- 【组合】`caudit-payment-invariants`: "金额/数量真值不得由客户端上报"是本判据在资金域的形态；那边给出资金流程的完整核对顺序。

## E — 可执行步骤 (Execution)

1. **列请求参数角色表**：对目标接口的全部入参（含隐藏域、header、cookie）逐个标注角色——数据 / 安全元数据 / 混合。
   - 完成标准: 每个参数有角色标注，依据是其服务端用途。
2. **元数据定性**：对每个元数据参数确认其裁决对象（白名单内容？开关？真值？结构？凭证？）。
   - 完成标准: 裁决对象明确，缺陷定性成立。
   - 判停条件: 角色无法静态判定时按元数据从严处理并标记待验证——本判据不存在"过滤后放行"的中间态。
3. **设计替代通道**：请求改为传索引/意图（字段编号、排序键枚举名），服务端持映射表；真值改服务端计算；凭证改服务端生成与会话绑定。
   - 完成标准: 每个元数据参数都有"离开请求词汇表"的替代实现。
4. **回归验证**：构造直接提交元数据值的请求，确认服务端不再采信。
   - 完成标准: 原 payload（改 alowexts/改金额/传列名）全部失效。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯数据参数（正文、备注、搜索词）——走过滤/校验/转义路线，硬套本判据会把所有输入都报成缺陷。
- 用户对**自己的资源**做合法选择（选择自己的收货地址 ID）——那属对象级授权问题，不是元数据污染。
- 管理员后台对策略的显式管理（高权限通道修改白名单）——权限模型问题，需配合授权审查。

### 作者在书中警告的失败模式

- 白名单随表单提交（行6721-6725）——机制存在但内容被请求决定。
- 验证答案下发到 HTML/Cookie（行17189）——答案即元数据。
- 凭证要素请求自证（淘宝 user_num_id 缺 Token，行17259）。
- 金额真值客户端上报（行9361）。

### 作者的盲点 / 时代局限

- 书内四类形态来自 2015 表单/Cookie 语境；现代等价形态更多：GraphQL 指令参数、JWT claim 中的角色字段、feature flag SDK、前端 computed 价格签名——判别式（数据 vs 结构/裁决）不变，形态清单要扩。
- 作者未系统命名"元数据"概念，判据散在四个章节的案例里；本 skill 把它收敛为统一判别式，这是蒸馏后的结构而非书的原文结构。
- 未涉及签名方案（HMAC 请求签名能否救客户端金额）——当代实践中签名只是防篡改的辅助，真值仍须服务端，不应误读为可签名后信任。

### 容易混淆的邻近方法论

- 与"服务端校验"通识不同: 通识说"重要值服务端要再验一次"；本判据更严——元数据连"被请求携带"都不允许，验证与否不改变缺陷定性。
- 与 mass assignment 的区别: 变量覆盖绑定是"多绑了字段"；本判据即使单字段显式传值（就一个 alowexts）也构成缺陷——按角色而非按绑定机制判定。

## 相关 skills

- **composes-with `caudit-server-side-state-truth`**: 元数据污染（参数归属）与状态真值（状态存放/原子/裁决）常在同一场缺陷中同现——客户端上报的金额既是污染的元数据，又是缺失的服务端真值。
- **composes-with `caudit-var-overwrite-chain`**: 白名单集合、功能开关这类元数据字段是变量覆盖三点连线里最高价值的连线目标——覆盖点审出后按本 skill 定性其角色。
- **composes-with `caudit-type-context-defense`**: 排序键/列名在这边定性为"不得由请求携带的元数据"，在那边给出口（服务端枚举映射）——归属原则与防御选型配套。
- **composes-with `caudit-whitelist-spectrum`**: 白名单要同时过两关——内容由服务端决定（本 skill）、形态与处置按谱系选（那边）；缺任一关白名单形同虚设。
- **composes-with `caudit-payment-invariants`**: 支付三不变量中"金额服务端真值"的缺陷定性由本判据给出（真值是被污染的元数据），资金链核对顺序由那边给出。
