# 业务状态真值原则 (vf13)

## R — 原文 (Reading)

> 「抽完奖之后删除cookieshared_t42014和logind_t42014，刷新页面后即可再次做任务并抽奖」「当一个支付操作开始就应该立马锁定当前账户，不能同时两个后端请求对余额进行操作」「当前用户信息存储到session，不放到request中，避免攻击者修改当前用户ID」

> — 原作者, 原始方法论来源第11章 11.6/11.7/11.5（source.txt 行17423、行17455、行17397）

---

## I — 方法论骨架 (Interpretation)

一切"用户还能不能再做一次"的判断，都必须有一个无法被客户端单方面改写的真值来源。方法是把"状态"展开成一张清单——资格、次数、额度、身份、结果——然后对每一项问三个问题：

1. **真值存哪？** 存 Cookie、隐藏域、请求参数里的状态都是声明，不是真值；客户端删掉重发，服务端就重发资格。真值只能存服务端持久态（数据库/会话存储）并绑定不可伪造的主体标识。
2. **迁移是否原子？** "开通与扣费"分两步执行就有时间差窗口，重复发包可低价多购。状态迁移（签到+发奖、扣费+开通）要么同事务，要么加并发锁，且锁定粒度要落在被争夺的资源上（账户/订单）。
3. **裁决来源可伪造吗？** 身份从 session 取而非请求；IP、设备号是可伪造的辅助信号，只能用于风控降权，不能作最终裁决。

三类典型绕过形态（cookie 删改 / IP 伪造 / uid 可改）可直接当验收用例集，逐条对照设计。

## A1 — 书中的应用 (Past Application)

### 案例 1: 抽奖删 Cookie 重置次数（WooYun-2014-65631）
- **问题**: 促销抽奖的单用户次数限制被黄牛批量绕过，奖品直接损失。
- **方法论的使用**: 按真值三问定位：抽奖次数真值存在客户端 Cookie（shared_t/logind_t），删掉即重置——第一问即失败。
- **结论**: 次数与资格必须服务端持久化、按账户维度计数、原子扣减。
- **结果**: 作者以此案例（11.6）作为"状态在客户端即被重置"的定型例证，并推广到投票/积分同类功能。

### 案例 2: 支付"开通-扣费"时间差（6.2.1.4）
- **问题**: IDC 开通 VPS、手机刷 QQ 钻类业务可重复发包，以少量钱多次开通。
- **方法论的使用**: 第二问（原子性）：检测到开通与扣费非原子，重复请求在窗口内多次生效。
- **结论**: 支付操作开始即锁定当前账户，不允许两个后端请求并发操作余额（11.7 对策三）。
- **结果**: 作者把它与"金额真值/数量下限"并列为支付三条对策（见 vf17 的实例化）。

### 案例 3: 身份也是状态——espcms 任意用户登录（WooYun-2015-90324）
- **问题**: 会话身份（user_id）从加密 Cookie 解密而来，服务端不再校验。
- **方法论的使用**: 第三问（裁决来源）：身份真值放在客户端可构造数据里，伪造任意用户的加密 Cookie 即可登录。
- **结论**: 当前用户信息存 session、不放到 request（11.5 行17397 的对策原文）。
- **结果**: 作者在 6.3.1.2 完整拆解该链路，落点为服务端会话方案。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计"每日签到/抽奖/投票/限领优惠券"类带次数或资格限制的功能。
2. 评审支付、开通、提现等涉及余额与权益发放的流程（并发重复请求是否双扣/双发）。
3. 审计中发现某限制条件的判断数据来自 Cookie/请求体，需要定性是否可绕过。
4. 事后复盘"活动被刷/被薅羊毛"事件，定位真值层失效点。

### 语言信号 (用户的话里出现这些就应激活)

- "删了 Cookie 还能再抽一次 / 限制形同虚设"
- "防刷 / 防薅羊毛 怎么设计"
- "开通会员和扣费是两步操作不是原子的 / 中间被打时间差 / 重复请求多次生效"
- "state 存哪里 / server-side vs client-side state"
- "签到接口怎么做幂等"

### 反向信号 (用户的话里出现这些则不应激活)

- "评论'是否已读'放 localStorage，用户改了也只是自己骗自己"——已读/浏览历史/界面偏好类只影响用户自身的低价值展示状态，客户端存放不构成可利用绕过，不激活。
- "登录页加'记住我'，cookie 里存什么比较合适"——会话凭证存放设计，不是限制状态的真值裁决，不激活。
- "退款接口被重复请求造成双倍退款，资金类问题怎么系统排查"——要资金域预编译清单逐条跑，属 `caudit-payment-invariants`。

### 与相邻 skill 的区分

- 【被依赖】`caudit-payment-invariants` 依赖本 skill: 那是本原则在支付域的三条不变量实例化。"两步操作不原子/开通扣费被打时间差"的原子性裁决直接走本 skill 第二问；要资金域预编译清单（改价/负数数量/重复退款）逐条排查时才用那边。本 skill 是通用三问，覆盖抽奖/投票/签到/身份等全部状态类。
- 【组合】`caudit-security-metadata-pollution`: 那边针对"策略参数"（白名单集合/开关/金额真值）被请求污染；本 skill 针对"业务状态"的存储位置与原子性——两者常同场出现，判定维度互补。
- 【组合】`caudit-rate-limit-dual-edge`: 限频计数本身也是一种状态真值；那边聚焦限频策略的双端滥用，本 skill 提供其底层判定原则。
- 【组合】`caudit-password-reset-three-stages`: "凭证↔账号绑定"的执行复验是真值裁决原则在认证域的化身；那边提供流程级的阶段拆解与缺陷谱。

## E — 可执行步骤 (Execution)

1. **列状态清单**: 把功能涉及的资格、次数、额度、身份、结果五类状态全部列出。
   - 完成标准: 每个状态项有一个名字（如"今日剩余抽奖次数"）。
2. **对每项问真值位置**: 追该状态判断时读取的数据源——session/DB 为真值；Cookie/隐藏域/请求参数为声明。
   - 完成标准: 每项标注"真值 / 客户端声明"，客户端声明项即缺陷。
3. **检查迁移原子性**: 对每个状态变更找出"检查→变更→副作用"链路，判断两请求并发或重复发包时是否双生效。
   - 完成标准: 每个变更点标注"原子（同事务/锁/幂等键）"或"存在窗口"。
   - 判停条件: 若功能只读不写状态（纯查询），跳过步骤 3-4。
4. **核对裁决来源**: 身份类判断是否全部取服务端会话；IP/设备号是否被用作最终裁决。
   - 完成标准: 列出所有裁决输入及其来源，可伪造项降级为辅助信号。
5. **跑三类验收用例**: 删改客户端状态重放 / 伪造 IP 或设备号 / 改 uid 或对象 ID，逐条验证。
   - 完成标准: 三类用例各有通过/失败记录，失败项即漏洞。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯技术型漏洞（注入/XSS/上传）的过滤与编码审计——状态真值不管字符层安全。
- 性能型缓存数据（页面片段缓存、CDN 状态）——不是裁决依据，不适用真值判定；判错对象会把人引向过度设计。
- 已明确由基础设施保证的原语（如数据库事务内的单行更新）——不必重复推演。

### 作者在书中警告的失败模式

- 次数/资格存 Cookie，删除即重置（ce65，行17423）。
- "开通与扣费"时间差被重复发包利用（行9367-9369，QQ钻/VPS 开通同类）。
- 身份从 Cookie/请求正向读取，伪造即任意用户登录（ce40/ce41，espcms、骑士cms 同型）。

### 作者的盲点 / 时代局限

- 2015 语境：单机 PHP session/MySQL，"锁定当前账户"的粒度是整账户——会阻塞同一用户的其他正常支付；现代等价物是按订单/幂等键加锁，作者未及此层。
- 未提出"幂等键"术语，但其"锁定+不能同时两个请求"的表述是幂等设计的雏形；迁移到现代栈时应补上幂等键与分布式锁（Redis/数据库唯一约束）。
- 分布式与最终一致场景（跨服务状态迁移、消息队列重投递）超出书中语境，需引入 saga/事务外补偿。

### 容易混淆的邻近方法论

- 与"客户端不可信"口号不同：本 skill 不是重复"别信客户端"，而是给出可执行的三问清单（存哪/原子否/谁裁决）与三类验收用例。
- 与会话管理（cookie 属性加固、HttpOnly）不同：那是票据传输层；本 skill 管的是"业务裁决读什么"。
