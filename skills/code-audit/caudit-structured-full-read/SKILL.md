# 通读法的结构化读法（vf02）

## R — 原文 (Reading)

> 「首先需要看看有哪些文件和文件夹，寻找名称里有没有带有api、admin、manage、include一类关键字的文件和文件夹，通常这些文件比较重要」「安全过滤文件…关系到可疑点能不能利用」
>
> — 原作者, 原始方法论来源第3章 3.2.1.1/3.2（source.txt 行1639、行1477）

---

## I — 方法论骨架 (Interpretation)

通读不是从第一个文件顺序读到最后一个，而是**按文件角色分派注意力**：

1. **目录结构先行**：文件与文件夹名（api/admin/manage/include 等）暴露程序的功能分区，先据此圈出核心区域。
2. **四类关键文件**决定阅读优先级——公共函数集、配置文件、安全过滤文件、入口 index 文件。
3. **过滤文件优先于业务文件**：它是全站误报与真洞的分水岭。不懂过滤层的实现与覆盖范围，后面看到任何可疑拼接都无法判断"能不能利用"。
4. **入口文件读一遍即得全局地图**：参数怎么进来、路由怎么分发、哪些超全局被消费，一遍下来应能画出全局数据流图。
5. 配置文件里埋着语言陷阱与前置条件（编码、引号形态、可写点），它们决定漏洞成立的边界。

产出物是两张图/表：**全局数据流图**（输入从哪进、被谁改、到哪去）与**过滤覆盖表**（哪些入口/参数/时机被哪层过滤覆盖）。零散漏洞只是这个过程的副产品。

判定标准：读完 I 段的地图与覆盖表，任何人接手都能回答"这个参数进 SQL 前经过了什么"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 骑士cms 四步通读
- **问题**: 如何系统性理解一套陌生 CMS 并形成复读锚点。
- **方法论的使用**: 按目录关键字选文件 → 读关键文件（顺带读出三层 XSS 过滤链）→ 理出前后台与自定义入口 → 标记敏感操作供复读。
- **结论**: 通读的价值在于先建立过滤层与入口的认知，再谈找洞。
- **结果**: 后续多个漏洞（过滤链缺陷、令牌可预测）都直接来自第一遍通读的产出（3.2.1 系列，作者建议每套程序读三遍）。

### 案例 2: 74cms 配置文件读出两条利用线索
- **问题**: 配置文件在通读中读什么。
- **方法论的使用**: 读出配置值用双引号包裹（可变变量执行前提）+ QISHI_DBCHARSET=GBK（宽字节注入前提），并跟进连接函数确认实际 SET NAMES。
- **结论**: 配置文件审计的标准产出 = 可写点、编码/宽字节前提、备份泄露风险。
- **结果**: 从"配置里可能有问题"推进到"连接代码确认后成立"的完整证据链（3.2.1.3）。

### 案例 3: 骑士cms 三层 XSS 过滤链——读防御本身
- **问题**: 通读阶段要不要读安全函数。
- **方法论的使用**: 顺 common.php 读出 new_html_special_chars → remove_xss → check_str 各层职责与缺陷（位置分散、关键字替换破坏正常词）。
- **结论**: "读安全函数本身"是通读的重要产出：先看防御实现，再找绕过。
- **结果**: 过滤链的形态与缺口成为后续 XSS 判定的基准（3.2.1.2，4.2.1.3 复用）。

4. 评审前想快速判断"这个系统的过滤体系长什么样、管多大范围"。

### 与相邻 skill 的区分

- 【依赖】`caudit-audit-path-selection`: 那里决定"要不要通读"；本 skill 只解决"通读时怎么读、按什么顺序、为什么"——选型定下通读后本 skill 才上场。

## E — 可执行步骤 (Execution)

1. **画目录结构**：列出文件树，按名称关键字（api/admin/manage/include 及现代等价物 routes/middleware/handlers）圈出核心区。
   - 完成标准: 产出一张"目录 → 功能角色"对照清单。
2. **读入口，建全局数据流图**：确认所有入口文件（web 入口、CLI、cron、消息消费者——2015 年语境之外现代系统必加）。
   - 完成标准: 能回答"一个 HTTP 参数从进入到落库/输出经过哪些节点"。
   - 判停条件: 若入口无法穷举（动态路由/多协议），先记录未覆盖入口清单，不得假装完整。
3. **读过滤/中间件层，产出过滤覆盖表**：逐层记录每层过滤的对象、时机、覆盖的超全局/入口。
   - 完成标准: 覆盖表能回答"任意给定参数，它被哪层处理、哪层不处理"。
4. **读函数集与配置**：公共函数按引用频次排优先级；配置文件核对编码、引号形态、密钥、可写点。
   - 完成标准: 高频公共函数与危险配置项各有清单。
5. **标记复读锚点**：敏感操作、未覆盖入口、可疑拼接处打标，供第二遍定向复读。
   - 完成标准: 锚点清单可直接转为定向挖掘任务（交给机理定向 skill）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 时间预算只够定向结论——先走路径选型，不要半途开始"假装通读"。
- 单功能专项排查（只审一个支付回调）——直接定向，通读是浪费。
- 代码量远超人力（百万行级）——退化为"框架约定层精读 + 数据流图"，全量逐文件通读不可行。

### 作者在书中警告的失败模式

- 初学阶段直接读大型开源框架——控制流被打散在多层封装里，没有经验时"分析不出个所以然"（3.2 节，行1623）；作者建议先读小应用攒经验。
- 不读过滤层就开始找洞——看到的每个可疑点都无法判真伪，产出全是误报。

### 作者的盲点 / 时代局限

- 四类关键文件清单是 2015 年 PHP 单体应用的形态；现代栈映射要换载体（入口=路由/控制器注册、过滤=中间件/序列化器、函数集=utils/lib、配置=settings/env），但"按角色分派注意力、过滤层优先"的规则不变。
- 作者建议"每套程序读三遍"，隐含人力充足假设；当代应以工具生成的调用图替代部分遍数。
- 书中通读面向服务端渲染应用，对前后端分离架构还需补"前端入口 + API 契约"两个阅读对象，书中未覆盖。

### 容易混淆的邻近方法论

- 与"代码熟悉/onboarding 教程"不同：本方法以**安全过滤层与数据流**为组织线索，不是业务功能导览。
- 与 `caudit-filter-coverage-map` 的区别: 盲区测绘针对"统一过滤"这种既有机制找例外；本 skill 是建设期对全系统建立过滤认知的读法。
