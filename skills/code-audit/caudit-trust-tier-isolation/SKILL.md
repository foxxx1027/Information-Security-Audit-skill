# 按信任级别做数据隔离——结构型优先 (vf24)

## R — 原文 (Reading)

> 「两个不在同一操作层面的账户等级，完全不用将账户放到同一个数据库表里面，因为当同表的情况下可能存在越权修改管理员信息的情况，比如密码、找回密码的邮箱等」「Metinfo系统的会员和管理员都在met_admin_table表」「（文件管理）限制只能操作这两个目录，目录不能从客户端提交，直接在代码中设置好即可」

> — 原作者, 原始方法论来源第12章 12.2、第11章 11.10（source.txt 行17665、行17667、行17539）

---

## I — 方法论骨架 (Interpretation)

防御有两种建法：**校验型**——数据和低信任数据放在一起，靠每处读写代码记得加校验；**结构型**——让不同信任级别的数据在存储结构上就不相干，危险组合在数据模型上不存在。本框架给出从校验型升级到结构型的判别式：

**一次编码疏忽能否越界？** 如果某个开发者在某个查询里漏写 `WHERE tenant_id=?` 或漏一次属主校验，就完成了跨信任边界访问——那么这条边界只存在于编码纪律里，迟早被漏。升级方向：

- 不同信任级的账号/凭证分表甚至分库（前后台分表），两条代码路径互不共享写接口；
- 可操作域（目录、表、URL 前缀）在代码/配置中写死，不从客户端提交——边界不再依赖参数正确；
- 存储层强制默认条件（现代等价物：行级安全策略、租户上下文自动注入、视图收窄），让"忘记加条件"查询不出数据。

价值定位是防御投资选型：逐点校验修一个洞，结构隔离灭一类洞（"很大程度上防止账户体系上的越权"）。代价是查询与迁移成本，故判别式只对高价值边界执行。

## A1 — 书中的应用 (Past Application)

### 案例 1: Metinfo 前后台同表越权改管理员密码（12.2，作者 2012 年发现、官方 Demo 实测成功）
- **问题**: 会员与管理员共用 met_admin_table 单表，修改资料接口的 $useid 直接取自请求。
- **方法论的使用**: 判别式检验——会员接口按自己 id 改资料，id 撞上管理员行（提交 user_id=1）即改管理员密码；同表结构使一次参数疏忽直达垂直越权。
- **结论**: 两个信任等级不该同表；分表让前台代码路径在结构上够不到管理员行。
- **结果**: 作者在官方 Demo 上实测成功并提交官方（已修复）——结构型缺陷的真实代价证明（cs49）。

### 案例 2: 文件管理目录代码写死（11.10 行17539）
- **问题**: 文件管理功能允许目录跳转时的越权操作。
- **方法论的使用**: 结构型思维的域限定版——"限制只能操作这两个目录，目录不能从客户端提交，直接在代码中设置好"，确需跳转则禁止 ../。
- **结论**: 可操作域写死在代码里，边界不再依赖校验参数正确。
- **结果**: 目录参数从攻击面中移除，剩余风险压缩到目录内部。

### 案例 3: 站库分离的同构原则（12.6）
- **问题**: 数据访问层的信任边界如何落地。
- **方法论的使用**: 按信任边界划分访问域——Web 层与数据层经 API 收口，是同一"结构性隔离优于逐点校验"原则在访问层的应用。
- **结论**: 隔离原则可跨层复用（存储分表、目录写死、访问收口三处同构）。
- **结果**: 与 12.2 互证，构成第12章的架构主张之一。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计账号体系：管理员/内部员工/普通会员是否同表？靠权限字段区分够不够？
2. 多租户 SaaS 的数据隔离选型（共享表+tenant_id / 独立 schema / 独立库）。
3. 审计发现"漏加一个条件就越权"的接口，评估是修接口还是改结构。
4. 内外部数据域划分（用户可见数据 vs 运营敏感数据 vs 密钥配置）。

### 语言信号 (用户的话里出现这些就应激活)

- "前后台账号放一张表，加个 type 字段区分 / admin and users in one table"
- "多租户怎么隔离 / multi-tenant data isolation / tenant_id everywhere"
- "漏加一个 where 条件就跨租户了 / missing tenant filter"
- "分表还是权限字段 / separate table vs permission column"
- "结构上防止越权 / structurally prevent cross-tenant access"

### 与相邻 skill 的区分

- 【组合】`caudit-api-relay-architecture`: 那边收口的是**访问路径**（谁能连、被谁观测）；本 skill 切分的是**数据模型**（什么和什么根本不存放在一起）。组合顺序：先分域，再收口。
- 【组合】`caudit-admin-webshell-parity`: 后台 webshell 等价功能的管控清单里"独立高权限账号 + 凭证域隔离"正是本 skill 的功能层落点——功能定级与结构隔离配合。
- 【组合】`caudit-horizontal-depth-pillars`: 那边决定何时、以什么配比投资结构性防御；本 skill 是"灭一类洞"的典型纵深构件——投资裁决与构件落地配套。
- 【区分】`caudit-security-metadata-pollution`: 那边管"策略参数不得由请求携带"（角色字段被 mass assignment 覆盖即是其形态）；本 skill 更进一步把角色差异提升到"表/库"结构——判别维度不同，不建链。
- 与逐点权限校验（ce37/ce64 的行级属主校验）的区别: 校验是必要但属于"记得型"防御；本 skill 决定何时值得把它升级为"结构型"。

## E — 可执行步骤 (Execution)

1. **枚举信任级别**: 列出系统内全部数据主体与访问者等级（游客/会员/管理员/租户/平台运营），两两标注是否存在信任差。
   - 完成标准: 信任级别矩阵完成，有信任差的组合全部标出。
2. **对每个信任差跑判别式**: 追问"一次编码疏忽（漏加条件/漏一次校验/漏一个 if）能否跨越该边界？"——能，则边界是校验型。
   - 完成标准: 每个信任差标注"校验型/结构型"，校验型即升级候选。
   - 判停条件: 若系统只有单一信任级（无外部用户、无租户），记录"无信任差"后结束，不做结构改造。
3. **选结构隔离形态**: 按边界价值选——分表/分库（账号凭证域）、存储层默认条件（租户行级安全/自动注入过滤器）、可操作域代码写死（目录/表/路由白名单）、独立代码路径（前后台不共享写接口）。
   - 完成标准: 每个校验型边界有目标形态与迁移方案。
4. **验证"忘记"不可达**: 模拟漏加条件的查询/请求，验证结构层兜底（查不出数据/路径不存在/表不可见）。
   - 完成标准: 每个已升级边界有"漏加条件"的负向测试记录。
5. **输出投资决策**: 结构改造项按边界价值排序，逐点校验保留项标注为纵深而非主防线。
   - 完成标准: 决策表含"升级/保留+理由/成本"，评审可拍板。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 同信任级的数据分片（按地域/哈希拆库）——那是性能问题，无信任差即无本框架的适用对象。
- 单角色小系统/原型——无跨信任边界可越，结构改造是纯成本。
- 热数据频繁跨级联查的场景（运营后台确需 join 全量）——结构隔离代价极高，应改为导出/数仓副本方案而非硬拆。

### 作者在书中警告的失败模式

- 前后台同表 + 接口按请求 id 改资料（ce74）——单点疏忽直达管理员密码重置。
- 操作域（目录/表）从客户端提交——边界本身被参数化，../ 跳转越权（行17539 前文）。
- 把"加了权限校验"当永久安全——校验型边界随代码量增长必然出现漏网点。

### 作者的盲点 / 时代局限

- 2015 语境：单库分表即可表达隔离；现代等价物是 RLS（PostgreSQL 行级安全）、ORM 默认作用域（自动注入租户条件）、独立 schema/库、服务化数据所有权——判别式不变，落地构件升级。
- 未讨论结构隔离的代价面：跨域统计查询、数据迁移、外键约束丧失——投资决策需计入。
- "结构性消灭"的绝对化表述应弱化为"把漏洞类从默认路径上移除"——结构隔离仍需配套校验作纵深（作者在 12.8 权限控制中亦有逐点校验要求）。
- 多租户现代场景中"独立库"与"共享表+强制过滤"的权衡（成本 vs 隔离强度）书中无涉及。

### 容易混淆的邻近方法论

- 与最小权限（账号权限收敛）不同：最小权限管"凭证能做什么"；本 skill 管"数据怎么摆才能让疏忽不越界"。
- 与 RBAC/权限模型不同：RBAC 描述授权关系（仍是校验型）；本 skill 决定授权错误的爆炸半径。
