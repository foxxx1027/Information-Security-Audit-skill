# 类型即边界——按注入语境选防御（vf06）

## R — 原文 (Reading)

> 「（转义）在int类型注入时效果并不好…intval等函数就起作用了」「双等于在判断等于之前会先做变量类型转换…可能存在安全风险」「已知某参数一定是INT类型，就可以在使用时将其转为INT」
>
> — 原作者, 原始方法论来源第4章 4.1.2.2 / 第6章 6.2.1.1 / 第12章 12.10（source.txt 行4701、行9217、行18075）

---

## I — 方法论骨架 (Interpretation)

防御手段和注入语境必须配套，错配等于没防：

1. **语境选型表**：引号包裹的字符串语境 → 转义有效；无数值的裸拼语境（`where id=$id`）→ 引号根本不存在，转义无处发力，只能**类型锁定**（强制转 INT/float，参数本身失去携带语法的可能）；标识符/结构语境（列名、排序键）→ 唯一安全解是枚举映射，任何"过滤"都不可靠。
2. **校验器语义 = 下游解析器语义**：校验函数认为的"数字"必须和数据库/解释器认为的一致。is_numeric 认 0x 十六进制，而 MySQL 恰好能用 hex 代替字符串明文——校验器的宽容恰好构成通道。同理：比较器的类型转换规则（in_array 不带 strict、== 先转换）会在白名单比对时放行整串注入。
3. **比较前三件事**：规范化（trim/大小写/进制统一）→ 严格比较 → 命中即拒绝。文件名 "1.php␣" 尾空格使黑名单比对落空，就是缺规范化的实例。
4. **失败语义**：类型锁定的完整规则是"强制转型 + 失败即拒绝"——解析失败回退默认值（置 0 继续）等于把攻击降级为"0 值攻击"（0 元下单、默认角色），是类型白名单最常被漏掉的一环。

## A1 — 书中的应用 (Past Application)

### 案例 1: in_array 松散比较放行整串注入
- **问题**: 白名单已经存在，为何还注入。
- **方法论的使用**: 6.2.1.1 分析 typeid 白名单校验：in_array 比较前自动类型转换，"1'union select…" 与整数 1 判等通过，字符串整体进 SQL。
- **结论**: 比较器语义与防御意图错位——校验器认为相等 ≠ 下游安全。
- **结果**: 同节连出三例（in_array、is_numeric 认 hex、== 先转换），构成"比较器语义缝隙"证据链。

### 案例 2: 文件名尾空格绕过扩展名黑名单
- **问题**: 黑名单比对为何落空。
- **方法论的使用**: 上传 "1.php␣"，提取的扩展名带尾空格，in_array 严格比较不命中黑名单，Windows 落盘时剥空格还原可执行。
- **结论**: 比较前未规范化，规范化是比较的一部分。
- **结果**: 上传成功（5.1.3，行6525）；修复 = trim + 小写 + 白名单严格比较。

### 案例 3: 数字位注入的正解——类型锁定
- **问题**: 转义在数字语境失效后该用什么。
- **方法论的使用**: 作者在 4.1.2.2 给出选型结论（intval 等起作用），并在 12.10 升华为"已知参数一定是INT类型就转为INT"——把类型知识变成最强白名单。
- **结论**: "转义解决引号闭合、类型锁定解决无引号语境"的语境选型表成立。
- **结果**: 成为第12章代码层白名单体系的支柱判据（行18075）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计 API 的数值参数（金额、数量、页码、ID）——发现只做了字符串转义。
2. 评审排序/过滤参数（order by、返回字段）的处理方案是否可靠。
3. 复盘"校验明明写了还是被打穿"的比较逻辑（白名单 in、角色判断、token 比对）。
4. 设计新参数校验：决定某字段用转义、类型转换还是枚举映射。

### 语言信号 (用户的话里出现这些就应激活)

- "id 是数字还用转义吗 / do I need to escape an integer"
- "用了 in_array 白名单还能注入 / whitelist bypass"
- "strconv.Atoi 失败置 0 继续跑有问题吗 / fallback to default on parse failure"
- "is_numeric 够吗 / is is_numeric enough"
- "order by 字段怎么防 / sanitize sort column"

## E — 可执行步骤 (Execution)

1. **语境分类**：对目标参数判定注入语境——引号字符串 / 裸数值 / 标识符结构（列名、表名、排序键、键名）。
   - 完成标准: 每个参数标注语境类型。
2. **选型对照**：引号语境 → 转义（查时序）；裸数值 → 类型锁定；标识符 → 服务端枚举映射。
   - 完成标准: 每个语境有对应防御，无"用转义对付数值位"的错配。
3. **校验器语义核对**：列出现用校验/比较函数，逐一核对其类型定义与下游解析器是否一致（hex、科学计数法、前导零、尾空白、大小写）。
   - 完成标准: 每个函数有"语义一致 / 存在缝隙"结论。
   - 判停条件: 若校验函数的接受集无法确定（自定义解析器），直接视为有缝隙，转第4步构造用例。
4. **构造边界用例**：对每个缝隙构造样本（"1 union…"、0x…、"1.php␣"、魔法哈希"0e…"）验证是否穿透。
   - 完成标准: 用例全部执行并记录结果。
5. **核对失败分支**：检查所有解析/校验失败路径是否拒绝而非回退默认值继续。
   - 完成标准: 失败分支清单全部标注"拒绝/回退"，回退项列为缺陷。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 输出到 HTML/JS 的编码选型——那是输出语境（HTML 实体、JS 转义）问题，不是注入语境问题。
- 已全程参数化 + ORM 类型绑定的字段——语境错配已被框架消除，把注意力移向其他面。
- 纯业务枚举（状态机状态值）与安全无关的比较——不要把所有 == 都当漏洞报。

### 作者在书中警告的失败模式

- 数字位靠转义："int类型注入时效果并不好，比如可以通过报错或者盲注等方式来绕过"（行4701）。
- 松散比较三连：in_array 类型转换放行整串 SQL、is_numeric 认 hex 而 MySQL 可用 hex 代明文、== 先转换（6.2.1.1，作者以面试题形式强调 == 与 === 之别）。
- 比较前不规范化：尾空格/大小写/多后缀使名单比对落空。

### 作者的盲点 / 时代局限

- 例子全部是 PHP 弱类型语义（==、in_array 第三参）；跨语言迁移时具体缝隙不同（JS 的 == 与 NaN、Go 的多返回值忽略 err、Python 的 True==1），但"校验器语义必须与下游解析器一致 + 失败即拒绝"两条判据不变。
- 书内正解止于 intval 一类强制转型，未提参数化查询对数值位同样有效且更根本（现代默认）。
- 未覆盖 JSON 类型混淆（数组变字符串、对象键注入）等现代语境，需按判据自行扩展。

### 容易混淆的邻近方法论

- 与"使用严格比较"的通识建议不同: 通识给结论，本 skill 给判据链——语境选型 → 语义一致性 → 规范化 → 失败分支，四环缺一即漏。
- 与正则校验严谨性（锚点/元字符转义）同属"校验器实现质量"家族，正则问题是本判据在"形态约束"形态下的具体化。
