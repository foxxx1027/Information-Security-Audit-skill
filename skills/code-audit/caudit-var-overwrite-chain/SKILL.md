# 变量覆盖的可利用性判定——三点连线法（vf08）

## R — 原文 (Reading)

> 「一定要看漏洞代码行之前存在哪些变量可以覆盖并且后面有被使用到」；Metinfo $$ 覆盖「在这段代码之前的变量，我们都可以覆盖掉，包括数据库配置」
>
> — 原作者, 原始方法论来源第6章 6.1.1 / 6.1.1.3（source.txt 行8445、行8993）

---

## I — 方法论骨架 (Interpretation)

变量覆盖是一类"半成品漏洞/放大器"：它本身常常什么都不直接造成，价值取决于它能否接到别的环节上。因此审计纪律是把**发现覆盖点**与**确认漏洞**严格分开，用三点连线判定：

1. **覆盖点**：外部数据能改写哪个程序变量/对象字段？（机制：请求注册变量、批量绑定、配置注入。）
2. **前文关键变量**：这个覆盖机制的作用域内，有哪些**在覆盖点之前定义**的变量会被波及？（覆盖只影响先定义的量——这是搜索方向。）
3. **后文消费**：被波及的变量在覆盖点**之后**被谁使用？（进 SQL、进 include、进权限判断、成为配置。）

三点连上（覆盖点 → 恰好覆盖关键变量 → 关键变量恰好被危险消费）漏洞才成立；连不上任何一条边，就只能算风险信号。报告里写"存在变量覆盖"而不写链条，等于没写。

修复与判定同构：绑定白名单（只允许预期字段）+ 敏感字段/配置只由服务端赋值 + 变量先初始化——都是斩断某一条边。

现代形态同理：框架把 JSON 请求体自动绑定到领域对象（mass assignment），判定方法一字不改——覆盖点=自动绑定机制，前文=对象字段默认值，后文=isVip/role 等字段的授权消费。

## A1 — 书中的应用 (Past Application)

### 案例 1: Metinfo $$ 覆盖连到数据库配置
- **问题**: $$ 变量覆盖到底能干什么。
- **方法论的使用**: 按三点连线——覆盖点 = 请求参数经 $$ 注册成变量；前文 = 包括数据库配置在内的全部先定义变量；后文 = 数据库连接使用被覆盖的配置。
- **结论**: 覆盖配置可把连接指向攻击者外部库，实现任意登录。
- **结果**: 6.1.1.3 挖出完整链（"包括数据库配置"），覆盖从理论风险变成认证绕过。

### 案例 2: register_globals——同一根因的配置形态
- **问题**: 没写 $$ 的程序为何也有覆盖面。
- **方法论的使用**: 第1章分析 register_globals=On 时"GET、POST等方式提交上来的参数注册成全局变量"——环境本身成为覆盖点，放大一切未初始化变量。
- **结论**: 覆盖面既可来自代码（$$/extract）也可来自环境配置，判定法不变。
- **结果**: 该配置被列为全书反复引用的高危配置（行417）。

### 案例 3: 6.1.2 防御对偶
- **问题**: 修复怎么设计才和判定法对得上。
- **方法论的使用**: 原始数组（不拆散注册）、注册前验证变量存在、extract 用 EXTR_SKIP、变量必须初始化——每条都对应斩断三点连线的一条边。
- **结论**: 防御不必理解攻击细节，斩断任一边即可。
- **结果**: 形成第6章变量覆盖防范清单（行9035/9043）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 代码里搜到 extract($_POST)/parse_str/$$，要判断是真漏洞还是噪音。
2. 审计现代框架的请求绑定（Rails/Strong Parameters、Spring 表单绑定、Node ORM 批量赋值）是否可越权。
3. 评审配置加载（env 注入、YAML 反序列化）被外部影响的场景。
4. 报告定级：覆盖点该报高危还是低危——取决于链条。

### 语言信号 (用户的话里出现这些就应激活)

- "发现 extract / $$ / parse_str，能利用吗 / is it exploitable"
- "mass assignment / 批量绑定 / 用户可以多传字段吗"
- "覆盖了变量之后呢 / so what after overwrite"
- "JSON body 直接绑定到 model 安全吗"
- "半成品漏洞 / 放大器是什么意思"

### 与相邻 skill 的区分

- 【组合】`caudit-mechanism-to-search-terms`: 机理定向法负责**发现**覆盖点（搜索阶段）；本 skill 负责发现之后的**可利用性判定**（连线阶段）——两阶段首尾相接。
- 【组合】`caudit-security-metadata-pollution`: 元数据污染断言"安全参数不得来自请求"；本 skill 是更一般的判定框架，元数据字段（白名单/开关/角色）是它最高价值的连线目标之一——连线后按那边定性。
- 【区分】`caudit-second-order-vuln`: 二次漏洞追踪"写入→取出→触发"的跨请求数据流；本 skill 追踪"覆盖→消费"的变量流，不要求存储介质——不建链。

## E — 可执行步骤 (Execution)

1. **描述覆盖机制**：确认覆盖点的工作方式（注册哪些名字、作用域、优先级）与触发条件。
   - 完成标准: 能回答"攻击者能设置哪些名字、不能设置哪些"。
2. **枚举前文关键变量**：列出覆盖点之前定义、且在其作用域内的全部变量，标出安全敏感项（配置、路径、权限标志、SQL 片段、跳转地址）。
   - 完成标准: 敏感变量清单完成。
   - 判停条件: 若作用域内无任何敏感变量且后文无危险消费，判定为"不可利用，记录关闭"——到此为止。
3. **追踪后文消费**：对每个敏感变量查覆盖点之后的全部使用位置，归类消费类型（进解释器/进路径/进决策）。
   - 完成标准: 每个敏感变量有消费点清单。
4. **连线验证**：构造请求实际改写变量并观察消费点行为，证明三点连通。
   - 完成标准: 有 PoC 或等价证据链；无法连通的写明断在哪条边。
5. **按边修复**：任选一条边斩断（绑定白名单 / 敏感字段服务端赋值 / 初始化默认值），并说明选择理由。
   - 完成标准: 修复后重跑第4步连线失败。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已直接成形的注入/XSS（污染直接进 sink）——按对应漏洞判定，不需要覆盖框架。
- 语言层面已消灭该机制的现代默认（PHP 5.4 移除 register_globals，主流框架默认白名单绑定）——先确认机制真的存在再启动判定。
- 纯功能 bug 的变量遮蔽问题（不涉及外部可控数据）。

### 作者在书中警告的失败模式

- 见 $$ 就报高危：作者明确覆盖"通常需结合其他功能成完整利用"，单独不成洞（BOOK_OVERVIEW 术语表）。
- 只看覆盖点不看作用域方向：覆盖只影响**先于覆盖点定义**的变量，搜错方向会得出虚假的覆盖面。

### 作者的盲点 / 时代局限

- 书内机制（register_globals/extract/parse_str）在现代 PHP 基本绝迹；迁移对象是框架绑定器、依赖注入容器、配置合并（config merge）、YAML/JSON 反序列化、模板上下文注入——机制名字全变，"覆盖点×前文×后文"判定不变。
- 作者时代无对象语义（protected/final）参与判定；现代实现里访问修饰符、getter/setter 白名单会影响"能覆盖谁"，第2步枚举时必须纳入。
- 未讨论覆盖发生频率与稳定性（竞态、请求生命周期），现代长生命周期对象（单例）的覆盖后果更持久。

### 容易混淆的邻近方法论

- 与污点分析的"source→sink"不同: 污点分析追数据值；本框架追**变量名/绑定槽位**——被覆盖的不是数据而是程序自身状态。
- 与默认值缺失类 bug（CWE-456）同根，但本框架强调外部可控性那一维，纯初始化建议是它的防御子集。
