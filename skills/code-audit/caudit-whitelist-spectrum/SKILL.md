# 白名单形态谱系（vf11）

## R — 原文 (Reading)

> 「如果匹配到的事件不在白名单列表，就直接拦截掉，而不是替换为空」「白名单并不是说完全固定为参数…可以结合正则表达式来进行白名单限制」
>
> — 原作者, 原始方法论来源第4章 4.2.2.2 / 第5章 5.2.2（source.txt 行5395、行7933）

---

## I — 方法论骨架 (Interpretation)

"白名单优于黑名单"人人会说，但一到设计就卡壳——很多参数根本列不全。本谱系把白名单展开为三种可选形态：

1. **固定枚举**：合法值可穷举（上传扩展名 ∈ {jpg,png,gif}、排序键 ∈ 预定义列）。配套严格比较与规范化。
2. **类型锁定**：参数语义已知为某类型（一定是 INT、一定是布尔），直接强制转型——类型即最强白名单，参数从此携带不了任何语法。
3. **正则形态约束**：值域开放（表达式、路径模板、自定义标识符）时，不放弃白名单，改为约束**形态**：全串锚定（^…$）的结构正则 + 字段域白名单 + 长度上限——约束"长什么样"而非"是什么"。

这是"参数不可预测"与"必须放行用户输入"之间的第三条路：谱系直接回答无法枚举怎么办。

**处置规则与形态同样重要**：不匹配即拦截整个输入，**不得替换为空/部分清洗**——替换会拼接重组（删除 "script" 后 "scrscriptipt" 复原），清洗后的数据再进入系统，等于校验与放行的对象不一致。

## A1 — 书中的应用 (Past Application)

### 案例 1: 标签事件属性白名单——"拦截而非替换为空"
- **问题**: XSS 防护里事件属性怎么处理。
- **方法论的使用**: 4.2.2.2 对标签事件属性用白名单：匹配不在名单即拦截整条输入，作者显式排除"替换为空"这种处置。
- **结论**: 白名单的处置规则是设计的一部分，替换为空会使名单失效。
- **结果**: 该规则成为书内 XSS 过滤设计的基础约定（行5395）。

### 案例 2: eval/preg_replace 参数的形态约束
- **问题**: 解释器参数无法枚举，白名单是否只能放弃。
- **方法论的使用**: 5.2.2 提出"白名单并不是说完全固定为参数"，可用正则约束参数形态——开放值域下的白名单第三形态。
- **结论**: 形态约束填补"枚举不动"与"裸放行"之间的空档。
- **结果**: 该形态与固定枚举、类型锁定并列为书内白名单用法（行7933）。

### 案例 3: 上传扩展名白名单三件套
- **问题**: 枚举形态的完整配套是什么。
- **方法论的使用**: 5.1.5.2 给扩展名白名单 + in_array/=== 严格比较 + MD5 重命名——枚举 + 严格比较 + 去predictability 三件套。
- **结论**: 只给名单不给严格比较与规范化，枚举形态照样被 "php␣" 类边界击穿。
- **结果**: 上传防范成为书内白名单设计的样板间（行7115）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计开放性参数的校验：cron 表达式、自定义 slug、报表筛选条件、模板变量名。
2. 团队争论"这个参数没法白名单，只能黑名单关键字"时给出第三条路。
3. 评审已有白名单实现：查处置规则是否"替换为空"、比较是否严格。
4. 富文本/UBB 这类必须放行部分标签的场景设计允许集。

### 语言信号 (用户的话里出现这些就应激活)

- "这个参数值没法穷举，怎么白名单 / open-ended validation"
- "whitelist with regex / structure validation"
- "不匹配的时候清掉非法部分行不行 / strip invalid parts"
- "cron / 表达式 / 模板参数怎么校验"
- "白名单太小会误杀，太大没意义"

### 与相邻 skill 的区分

- 【对比】`caudit-blacklist-failure-modes`: 那是论证黑名单不成立（否定）；本 skill 给出替代设计（肯定）；连用顺序 = 先否定再建设。
- 【组合】`caudit-security-metadata-pollution`: 元数据污染断言白名单的**内容**必须由服务端决定；本 skill 断言白名单的**形态与处置**如何设计——来源与结构两关都过，白名单才成立。
- 【区分】`caudit-type-context-defense`: 类型语境判据覆盖谱系中的"类型锁定"形态并深入其语义细节（校验器 vs 解析器）；本 skill 管三形态之间的**选型**与统一处置规则——谱系与专项深化的关系，不另建链。

## E — 可执行步骤 (Execution)

1. **判定值域性质**：目标参数的合法值是可穷举、语义类型固定、还是形态开放。
   - 完成标准: 三选一标注完成。
2. **选形态并落地**：可穷举 → 枚举清单 + 严格比较 + 输入规范化（trim/大小写）；类型固定 → 强制转型 + 失败即拒绝；形态开放 → 全串锚定结构正则 + 字段域白名单 + 总长度上限。
   - 完成标准: 所选形态的配套件全部到位（无"只有名单没有严格比较"的残缺实现）。
   - 判停条件: 若三形态均不可行（如必须放行任意 HTML），说明该参数本质上不该用白名单解决，转输出编码/沙箱方向，不要硬造低质量正则。
3. **处置规则检查**：确认不匹配路径是整体拒绝，没有任何替换为空/部分清洗。
   - 完成标准: 拒绝路径有代码级证据；替换路径为零。
4. **对抗性用例回归**：构造拼接复原样本（scrscriptipt）、大小写/编码变体、超长输入、空串，验证全部被拒。
   - 完成标准: 用例清单全部执行，拦截率 100%。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 必须放行富语义内容的场景（任意 HTML、自由文本）——白名单谱系不适用，转输出编码/上下文转义/CSP。
- 数据本来就来自可信配置且无外部输入参与——不需要这层校验。
- 黑名单还在被论证阶段——先用失效模式分析把否定做完，再进入本 skill。

### 作者在书中警告的失败模式

- "替换为空"处置——拼接重组复原 payload（4.2.2.2 与 ce20/ce52 同族警告）。
- 白名单配松散比较——in_array 不带 strict、比较前不规范化，名单形同虚设（上传尾空格案例）。
- 把"参数不可预测"当作放弃白名单的理由——作者以形态约束正面回击（行7933）。

### 作者的盲点 / 时代局限

- 书内形态约束以 PHP preg 正则为载体；现代实现应优先解析器/AST 校验（真正的结构验证）而非正则——正则是形态约束的近似，复杂语法（cron、表达式、路径）正则既难写对又难维护。
- 未讨论 ReDoS（形态正则自身成为 DoS 面）——迁移时必须给正则加长度上限与超时。
- 书内示例未覆盖 Unicode/多字节形态，跨语言使用时规范化（NFC）应前置于校验。

### 容易混淆的邻近方法论

- 与"校验 schema"（JSON Schema、OpenAPI 参数校验）的关系: schema 校验是本谱系三形态的工程化封装，选型逻辑同源；本 skill 补充的是"拦截而非改写"的处置纪律。
- 与数据净化（sanitization）理念对立: 净化派修改输入后放行，本谱系派拒绝不符输入——混用两者是常见设计错误。
