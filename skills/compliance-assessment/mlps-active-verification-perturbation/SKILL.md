# 主动验证法（可控扰动与否定式验证）

## R — 原文 (Reading)

> "可采用验证的方法对该测评指标进行验证，以非授权用户身份（没有审计权限的普通用户）登录数据库系统，修改审计配置选项，查看是否可以修改成功，如不能修改，则认为该测评指标符合。"
> "b.在对系统进行备份的前提下，尝试修改或删除重要程序配置文件。验证是否对程序
> 完整性进行了保护；"
>
> — 原作者 等，原始方法论来源第8章 8.3.3 SQLServer 安全审计 + 8.3.1 Windows 入侵防范（source.txt L6157–6159、L4650–4651）

## I — 方法论骨架 (Interpretation)

一类测评指标问的不是"配置写了什么"，而是"能力真的存在吗"——程序完整性检测、审计进程保护、通信完整性识别、登录失败锁定。静态看配置永远答不死，主动验证法的做法是把指标翻译成一个**可复现的小实验**：

1. **设计扰动**：让一个低权限/非授权主体去做指标所禁止的事——改审计配置、删重要文件、篡改报文、输错口令。
2. **观察响应**：被拒绝/被检测/被恢复 = 保护生效；操作成功 = 保护不存在。
3. **否定式判定**：与直觉相反，"改不动"才是符合的证据——攻击尝试失败本身就是防护存在的证明，且属于测试类强证据（在证据强度排序中压过一切配置截图）。

实验有三条纪律：权限设定准确（用真的低权限身份，不是管理员模拟）；扰动最小且可控（改一个文件、发一个报文，不搞破坏性动作）；**备份前提**——先备份可回退，事后恢复并留证。作者在 OS、数据库、应用三层复用同一套实验设计，说明它是"能力类指标"的通用取证法。

## A1 — 书中的应用 (Past Application)

### 案例 1: SQLServer 审计进程保护的反向尝试（第8章 8.3.3，cs024）
- **问题**: "保护审计进程避免未预期中断"默认符合，怎么加强证据？
- **方法论的使用**: 以无审计权限的普通用户登录，尝试修改审计配置选项；改不动才判符合；若改成功，再执行查询退出，看日志能否记录这些操作。
- **结论**: 否定式验证——越权尝试失败即防护有效的证据；改成功且无日志则不符合。
- **结果**: 该项虽标"默认符合"，主动验证提供了一级更强的测试类证据。

### 案例 2: Windows 程序完整性的备份下破坏实验（第8章 8.3.1，cs014）
- **问题**: "对重要程序完整性进行检测并在破坏后恢复"如何取证？
- **方法论的使用**: 先访谈确认工具 → **在备份前提下**尝试修改/删除重要配置文件 → 观察是否被检测、能否恢复 → 查备份记录。
- **结论**: 构造扰动→观察响应，比"装了完整性工具"的配置证据强一级。
- **结果**: 备份前提控制了实验风险，与测试前风险分析的总要求一致。

### 案例 3: 通信完整性的篡改报文实验（第9章 9.3.1，cs029/pr043）
- **问题**: "通信过程中能检测到完整性破坏"如何证明？
- **方法论的使用**: 抓包看有无校验码 → 主动篡改一方报文发给对端 → 验证对端能否识别；保密性则用扫描器查"已解密的登录请求"类漏洞。
- **结论**: "配置存在"与"策略生效"分开验证，以实测行为为证据。
- **结果**: 文档+访谈+实测三类证据互相印证，实测一票定音。

### 案例 4: 登录失败处理的实测（第9章 9.3.1，pr041/cs028）
- **问题**: 口令锁定策略"配置了"是否等于"生效"？
- **方法论的使用**: 正确账号+错误口令连续实测，观察自动退出与锁定。
- **结论**: 配置存在≠策略生效，须以实测行为佐证。
- **结果**: 登录失败处理判定落到实测记录上。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保测评中核查"保护 X 不被未预期干扰"类指标（审计进程、审计配置、程序完整性、通信完整性）。
2. 零信任/终端准入方案验证："设备不合规即拒访""低权限不能停审计"是否真生效。
3. 整改复核：修补后须证明防护行为级生效，而非仅配置回显正确。
4. 云环境核查：低权限角色能否关闭 CloudTrail 类审计/修改防护策略（否定式验证的云上形态）。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么证明这个防护真的生效？光看配置截图行吗？"
- "拿普通用户试一下改审计配置/删文件，可以吗？negative test 怎么设计？"
- "篡改报文看对端能不能识别——这种实验怎么做？"
- "配置了但没实测，能判符合吗？"

### 与相邻 skill 的区分

- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 后者规定证据强度的排序与裁决（测试>检查>访谈）；本 skill 是**生产**测试类强证据的手段——两者是"证据怎么裁"与"证据怎么造"的关系。
- 与 `mlps-control-effectiveness-four-checks`（控制有效性四查）的区别: 四查中"生效""技术强制"两查的取证手段正是本 skill 的扰动实验；四查给判据框架，本 skill 给实验设计。
- 与 `mlps-tool-test-typology`（工具测试类型学）中的渗透测试的区别: 渗透以攻破为目标、范围大；本 skill 是单点、最小、可回退的合规验证实验，两者风险纪律不同。

## E — 可执行步骤 (Execution)

1. **把指标翻译成扰动命题**：写出"若保护生效，则 [低权限主体] 尝试 [被禁止动作] 应 [失败/被检测/被记录]"。
   - 完成标准: 命题一句话可执行，主体、动作、期望结果三要素齐。
   - 判停条件: 若扰动不可控或不可逆（可能损坏生产数据且无回退方案）→ 停止实验，降级为检查类取证并注明"未做主动验证的原因"。
2. **备份与授权准备**：快照/配置备份、明确实验窗口、获得被测方书面授权。
   - 完成标准: 回退方案就位且有书面授权记录（与作业红线衔接）。
3. **执行最小扰动并记录**：用真实低权限身份执行一次动作，全程留证（命令、返回、时间、截图/日志）。
   - 完成标准: 原始返回证据在手，扰动范围与计划一致。
4. **按否定式判定**：失败/被拒/被检测 = 符合证据；成功 = 保护缺失，判不符合并记录成功路径。
   - 完成标准: 判定落档，注明"测试类证据"。
5. **恢复与复核**：恢复现场，确认系统回到初态，把实验记录归档。
   - 完成标准: 恢复后状态核对记录 + 实验证据归档完成。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 不可逆/高破坏动作（删除生产库、DoS 压力）——作业红线明令禁止类策略不因验证目的豁免。
- 生产高峰或无备份窗口——备份前提不成立则实验不成立。
- 静态存在性指标（"是否配置了口令长度"）——看配置即可，实验是浪费与风险。

### 作者在书中警告的失败模式

- 只看产品部署（"装了完整性工具"）不实验——配置存在≠策略生效（cs014 之前提）。
- 用管理员身份"模拟"低权限——权限设定失真，实验无效。
- 扰动后不复原——验证行为本身成为变更，违反测试纪律。

### 作者的盲点 / 时代局限

- **版本提示**：书中实验模板依附等保 1.0 测评项（SQLServer 2008 审计选项、RHEL6 配置文件）；2.0 与云原生下实验对象换成云审计服务、准入控制器、服务网格策略，但"扰动设计+否定式判定+备份前提"结构不变。
- 未讨论实验的检测盲区：防护可能对测评者 IP/时段放行（"表演模式"），书未提供防伪装的对照实验设计。

### 容易混淆的邻近方法论

- penetration testing：目标导向的链条化攻击；本 skill 是单点合规验证，范围、授权、回退要求更严。
- chaos engineering：注入故障验韧性（可用性视角）；本 skill 注入违规验防护（安全性视角），失败即成功语义相反。
