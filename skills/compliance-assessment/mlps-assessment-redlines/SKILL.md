# 测评作业红线与现场纪律

## R — 原文 (Reading)

> 「（5）使用扫描工具进行扫描检测时应根据扫描计划在指定的网段地址内进行扫描，严禁全网扫描；」
>
> — 方法论出处，第4章 4.2.2（工具使用的十条风险控制要求之五；第2章 2.4 配套现场纪律）

---

## I — 方法论骨架 (Interpretation)

红线不是"小心点"的口号，而是可核查的动作清单，设计逻辑只有一条：**验证手段自身的风险不得超过被测系统的承受力**。

1. **测试前的三件套**：书面授权 + 测试方案（含风险说明）、规则库更新、备份与应急准备——接入前"风险分析 + 备份 + 应急预案"三项缺一不可。
2. **执行中的限域限速**：只在授权网段清单内扫描（严禁全网扫描）、避开业务高峰、控制并发与线程、生产系统禁用 DoS/溢出/数据修改类策略。
3. **人的边界**：渗透测试与口令强度审核必须被测方陪同；测评人员不直接操作系统，口述步骤由配合人员执行，测评人员只见证并取证；借用账号/设备逐项授权、最小权限、用完回收。
4. **数据的边界**：验证数据不得留存、须安全删除；禁止 U 盘传递数据文档。
5. **发现的边界**：测试中新发现的弱点只报告不自行深入验证——保全证据与权限边界。
6. 每条红线都有可核查的对应物：授权书字段、备份确认记录、扫描日志与网段清单比对、陪同记录、删除证明。可据此推导任何新测试技术（混沌工程插桩、Fuzzing）的准入条件。

## A1 — 书中的应用 (Past Application)

### 案例 1: 十条风险控制要求
- **问题**: 扫描渗透工具是双刃剑，如何避免"测评变事故"。
- **方法论的使用**: 第4章 4.2.2 列出十条要求——①未经授权不得测试；②先编写测试方案并经被测单位授权；③接入前规则库更新；④生产系统禁 DoS/溢出/数据修改类策略；⑤限定网段严禁全网扫描；⑥尽量非高峰；⑦扫描前通知数据备份等应急准备；⑧渗透须陪同；⑨口令审核须陪同且验证数据安全删除；⑩禁 U 盘传数据。
- **结论**: 红线把风险控制拆成逐条可核查的动作，覆盖授权、范围、时机、人员、数据五个面。
- **结果**: 十条要求成为测评机构作业规范，可提炼为"授权—方案—限域—限速—陪同—清零"六要素检查表。

### 案例 2: 测评人员只见证不操作
- **问题**: 测评工程师为图方便直接敲命令、改配置，责任如何界定。
- **方法论的使用**: 第2章 2.4 规定测评人员不直接接触信息系统，由配合人员操作，测评人员见证并获取证据；第1章 1.5 质量控制要求借用账号/设备必须出于测评需求、逐项授权、最小权限、用完回收。
- **结论**: 操作主体分离（配合人员操作、测评人员见证）是现场法律与操作风险的分界线。
- **结果**: 证据材料能对应"谁操作、谁见证、何时何地"，纠纷时责任清晰。

### 案例 3: 弱点只报不验
- **问题**: 测试中发现计划外弱点，顺手深入验证一下？
- **方法论的使用**: 第12章 12.4.12 把"应报告所发现的安全弱点和可疑事件，但任何情况下用户均不应尝试验证弱点"写成硬性要求，措辞"任何情况下"无例外。
- **结论**: 一线人员自行验证弱点可能扩大损害、破坏现场证据；验证与取证由事件处置职责方按程序进行。
- **结果**: 该边界既约束被测方一线员工，也约束测评人员的现场行为，与"搜集证据、记录处理过程"并列。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 计划对客户生产环境（K8s 集群、核心业务系统、工控网）执行渗透测试前，落实控制措施。
2. 起草/评审测试授权书与测试方案，需要完整的字段清单。
3. 测试中突发发现高危弱点，纠结要不要顺手验证利用。
4. 测试后收尾：凭据回收、数据删除证明、遗留物清理。
5. 引入新测试技术（混沌工程、Fuzzing、AI 自动化测试）时推导其准入条件。

### 语言信号 (用户的话里出现这些就应激活)

- "渗透测试前要准备什么/注意什么？"
- "授权书里应该写哪些内容？"
- "扫描把客户系统搞挂了怎么办？"
- "发现了新漏洞能不能顺手验证一下？"
- 英文: "rules of engagement"、"pentest authorization"、"before running the scan"、"safe testing checklist"、"verify the finding ourselves?"

### 与相邻 skill 的区分

- 与 `mlps-intrusive-test-downgrade`（降级权衡与豁免）的区别: 本 skill 划定"测试必须满足什么才能做"；后者解决"满足不了时的降级与豁免"。
- 与 `mlps-test-vantage-point-placement`（接入点布点法）的区别: 后者是空间设计（从哪里测）；本 skill 是行为边界（怎么测才合规），两者正交。
- 与 `mlps-tool-test-typology`（工具测试类型学）的区别: 后者是工具类型与证据形态匹配；本 skill 对所有类型工具统一施加纪律约束。

## E — 可执行步骤 (Execution)

1. **核对授权与方案**
   - 完成标准: 书面授权书在手（载明范围、时段、联系人）；测试方案已获批准，含测试风险说明；无授权即停，不得"先测后补"。
2. **落实接入前三件套**
   - 完成标准: 风险分析记录、系统/配置备份确认、应急预案（回退手段+应急联系人）三项书面材料齐备，缺一即不得接入。
3. **比对扫描范围与授权清单**
   - 完成标准: 扫描目标地址清单与授权网段逐一比对一致；排除项已设置；DoS/溢出/数据修改类策略确认禁用；时段避开业务高峰。
4. **执行中的人员与操作纪律**
   - 完成标准: 全程陪同人在场；测评人员不直接敲命令（由配合人员操作、测评人员见证取证）；借用凭据最小权限并有回收计划。
   - 判停条件: 客户方陪同人员中途离场或系统出现异常告警，立即暂停测试，按应急预案处置并留痕，恢复需双方确认。
5. **发现计划外弱点时的处置**
   - 完成标准: 只记录并报告（含位置与初步影响），未做任何利用/深入验证；报告移交事件处置职责方。
6. **收尾清零**
   - 完成标准: 验证数据已安全删除并留删除证明；借用账号/设备已回收；扫描日志目标地址与授权清单比对归档；无 U 盘等介质外带数据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯文档审阅/访谈类检查——零接入零状态变更，红线约束的接入类风险不存在（但"不直接操作"纪律仍适用）。
- 攻防演习/红队场景——有专门的 ROE 体系且目标导向不同；本 skill 的部分红线（如只报不验）在演习中按演习规则豁免，不可混用。
- 自有测试环境——授权、陪同等要素简化，但限域/备份/删除纪律仍是好实践。

### 作者在书中警告的失败模式

- 未授权即测、不写方案、规则库过期就上场（4.2.2 十条的前三条）。
- 生产系统使用 DoS/溢出/数据修改类策略——"把测评变成事故"。
- 全网扫描、高峰扫描、不限并发（ce04 列举的典型违反形态）。
- 以"改了会坏"为由绕过纪律或以测试之名浏览无关业务数据（pr008）。

### 作者的盲点 / 时代局限

- 红线成书于等保 1.0 时代，工具以 Nessus/Paros/SqlMap/Metasploit 一代为主；新测试形态（云上 agent、CI 内扫描、AI 自动化渗透）会产生书中未见的责任面（跨租户影响、供应链侧残留），须按"手段风险 ≤ 系统承受力"的设计逻辑自行推导准入条件。
- "自愿放弃验证测试"与红线并置时的张力（阶段 0 批判）：豁免转移责任但不降低系统真实风险，报告须如实披露证据基础削弱。

### 容易混淆的邻近方法论

- 作业红线 vs 最小影响原则（一般测试方法论）：前者是可核查清单化的中国等保实务版本，包含"不直接操作、只报不验"等本地化责任边界。
- 红线 vs 混沌工程守则：都讲爆炸半径控制，但混沌工程主动注入故障，准入论证更重（需显式 SLO 与回滚），不能因本 skill 存在就直接套用到故障注入。
