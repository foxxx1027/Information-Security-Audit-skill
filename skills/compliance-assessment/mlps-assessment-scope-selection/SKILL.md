# 测评对象确定法

## R — 原文 (Reading)

> 「在现场测评中，需要调研应用系统架构，明确包含哪些业务模块。」（第9章 9.3.1）「依据GB/T28449—2012信息系统安全等级保护测评过程指南的测评对象确定原则和方法，结合资产重要程度赋值结果，描述本报告中测评对象的选择规则和方法。」（附录A 3.1）
>
> — 方法论出处，第9章 9.3.1（"某软件服务网"案例）；附录A 3.1（测评对象章节）

---

## I — 方法论骨架 (Interpretation)

范围选择错了，后面所有工作不是失真就是浪费。作者的方法分四步：

1. **架构调研先行**：先画出系统的等级、整体结构、边界、网络区域、重要节点与业务应用，再谈测什么——"先划范围再定要求"是顺序约束，跳过它选对象必然拍脑袋。
2. **资产赋值驱动选择**：按资产重要程度赋值结果从九类对象（机房、网络设备、安全设备、服务器/存储、终端、数据库、业务应用软件、访谈人员、管理文档）中挑选，而不是"能测的都测"。
3. **剔除规则**：测评范围 = 需要鉴别/授权的业务面——前台展示这类无鉴权面不纳入身份鉴别测评（但其他适用指标仍可能覆盖它）。
4. **可复核性要求**：设备名在报告中唯一（如"xx 业务主数据库服务器"）；选择规则（哪层为何入选/落选）写进报告；范围须经委托方书面确认，防事后争议。
5. **两种错误形态等价地致命**：漏测高价值层（存储/鉴权层没进范围→结论系统性失真）与测无鉴权面（浪费测评配额）——架构调研先行同时防两者。

## A1 — 书中的应用 (Past Application)

### 案例 1: "某软件服务网"的前后台裁剪
- **问题**: 一个既有公开前台又有运营后台的网站，身份鉴别测评测哪部分。
- **方法论的使用**: 第9章 9.3.1 先架构调研把系统分为前台展示（无需登录）与后台运营管理系统，仅将后台纳入身份鉴别测评对象；该贯穿案例随后演示九方面 32 项逐项取证。
- **结论**: 测评范围 = 需要鉴别/授权的业务面；前台不测鉴别但其他适用指标（如通信、容错）仍按需覆盖。
- **结果**: 范围裁剪有据可写进报告，避免对无鉴权面做无效测评；该案例成为全书最大单一测评演示。

### 案例 2: 九类对象与报告呈现规则
- **问题**: 报告里"测了哪些东西"如何让第三方复核。
- **方法论的使用**: 附录A 3.1 规定按"国标确定原则 × 本系统资产重要程度赋值"描述选择规则；对象分九类列举；设备名称唯一化；测评方法四类（访谈、检查、测试、风险分析）对应到对象。
- **结论**: 对象选择是可复算的决策产物——读者能从报告重建"为什么测这些、不测那些"。
- **结果**: 对象清单 + 选择规则成为报告固定栏目，范围争议以书面确认为准。

### 案例 3: 数据湖式的分层选择推演
- **问题**: 接入/存储/分析/BI 四层数据平台，对象怎么选才不失真。
- **方法论的使用**（第3章 3.1.2 顺序约束 + 资产赋值规则的运用）: 先架构调研分层，再按资产重要程度赋值——存储层与鉴权层必进（数据与访问控制核心），BI 公开报表层若无鉴权面则不纳入身份鉴别对象。
- **结论**: 漏测高价值层与测无鉴权面是对象选择的两种对称错误，分层+赋值同时防两者。
- **结果**: 对象清单按层生成，每层入选/落选理由可写进报告。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 多层架构系统（微服务、数据湖、中台）首次测评，需要划范围、选对象。
2. 测评预算/工期有限，要决定"哪些对象必须测、哪些可以不测"并有依据。
3. 复审测评报告，检查对象选择是否有规则、是否漏了高价值层。
4. 委托方质疑范围（"为什么不测那个系统"），需要书面解释框架。
5. 系统含公开面（官网、开放 API）与内部面，纠结鉴别类指标测哪里。

### 语言信号 (用户的话里出现这些就应激活)

- "测评对象怎么选？""范围怎么划？"
- "这个模块要不要纳入测评？"
- "为什么没测存储层/数据库？"
- "测评对象清单怎么写进报告？"
- 英文: "assessment scope"、"scoping"、"which systems to test"、"test target selection"、"in-scope / out-of-scope"

### 与相邻 skill 的区分

- 与 `mlps-indicator-selection-rules`（指标确定规则集）的区别: 本 skill 决定"测哪些对象"（横向覆盖面）；后者决定"对象上用哪级指标、哪些不适用"（纵向要求集）。先对象后指标，构成方案编制的两步。
- 与 `mlps-deliverable-stage-gates`（产物阶段门）的区别: 本 skill 是方案编制阶段的核心技术之一；后者管四阶段的产物与质量门——本 skill 的输出是方案阶段的产物内容。
- 与 `mlps-grading-decision`（等保定级决策）的区别: 后者定等级（对象作为整体的保护等级）；本 skill 在等级确定后选具体测评对象集合。

## E — 可执行步骤 (Execution)

1. **架构调研**
   - 完成标准: 产出结构图与清单——等级、系统边界、网络区域、重要节点、业务应用分层；能指出哪层承载最高价值资产、哪层有鉴权面。
2. **资产赋值并排序**
   - 完成标准: 按重要程度对候选对象赋值排序（可衔接 `mlps-risk-assessment-six-steps` 的 CIA 赋值法），数据/鉴权/核心服务层置顶。
3. **生成对象清单（九类映射）**
   - 完成标准: 每个入选对象归入九类之一、名称唯一；每类都有"入选/不适用"结论，无悬空对象。
4. **应用剔除规则并记录理由**
   - 完成标准: 无鉴权面的业务面被剔出鉴别类指标范围（但记录其他适用指标的覆盖方式）；每个落选对象有一句落选理由。
   - 判停条件: 若发现高价值层（数据存储、鉴权、核心业务逻辑）因"在云上/是托管服务"被排除在范围外，暂停定稿——这属于漏测高价值层，先与委托方确认责任边界与替代证据，再决定纳入或书面声明限制。
5. **写选择规则入报告并取得书面确认**
   - 完成标准: 报告含"选择规则和方法"段落（规则+赋值结果+入选落选清单）；委托方书面确认范围。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 等级确定（`mlps-grading-decision`）之前——对象集合以等级与系统边界为输入。
- 渗透测试的目标选择——渗透目标按攻击面价值选，与本 skill 的合规覆盖逻辑不同（可参考但不重合）。
- 资产台账建设本身——九类映射可借用，但台账管理是 CMDB/资产管理方法。

### 作者在书中警告的失败模式

- 跳过架构调研直接点对象——"先划范围再定要求"的顺序被破坏，指标与对象错配（fw15 顺序约束）。
- 把无鉴权面前台纳入身份鉴别测评——无效取证、浪费配额（fw60）。
- 对象名称含混（多台设备同名）——报告无法复核到具体设备（fw101 唯一性要求）。
- 范围无委托方书面确认——事后争议无据（fw15 配套约束）。

### 作者的盲点 / 时代局限

- 九类对象与选择方法出自 GB/T 28449—2012 / 2015 版报告模板（等保 1.0）；等保 2.0 报告模板对对象类别有扩展（如虚拟化组件、云管理平台），云上测评还须处理"共享责任下的对象归属"（CSP 侧对象不可选时的替代证据），套用时按现行模板与云扩展要求补全。
- 阶段 0 批判：作者较少站在建设方视角算覆盖成本，选择规则偏合规完备——实际使用时应把"漏测高价值层"的风险权重显式高于"多测"的成本权重。

### 容易混淆的邻近方法论

- 测评对象 vs 定级对象：定级对象是整体系统（`mlps-grading-decision`），测评对象是其中的具体资产集合——一个定级对象对应一批测评对象。
- 范围裁剪 vs 缩小结论：剔除对象后，报告结论必须限定适用范围（衔接 `mlps-report-validity-retest` 的效力边界），裁剪不声明就是夸大结论。
