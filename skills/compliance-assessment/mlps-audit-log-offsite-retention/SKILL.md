# 审计记录留存的异地化判据（本地可灭失→无异地即不符合）

## R — 原文 (Reading)

> "Windows审计日志通常保存在本地，若采用覆盖方式，则当日志超过规定大小后，会自动覆盖之前的日志。同时，
> Administrator用户可对日志进行删除操作，对于该要求项如未部署日志服务器并对日志进
> 行备份保存，该项即默认不符合。"
>
> — 原作者 等，原始方法论来源第8章 8.3.1 Windows 安全审计（source.txt L4472–4476）

## I — 方法论骨架 (Interpretation)

审计留存指标的靶子不是"日志功能开了没有"，而是**证据的可灭失性**。作者把主流产品的默认失效形态逐个枚举：

- 网络设备：本地日志断电/重启即丢、存储空间有限；
- Windows：本地保存 + 超过上限自动覆盖 + Administrator 可删；
- SQLServer/Oracle：固定存储空间写满后自动覆盖最早日志——产品固有缺陷。

三重形态（断电丢/覆盖删/权限删）共享同一本质：**本机最高权限者或运行机制本身可以消灭证据**。因此判定规则收敛为基线型：只要缺"日志服务器 + 确认接收 + 备份"这条异地基础设施链，该项默认不符合——不逐案辩论日志有没有价值。取证顺序固定：查被测端是否配置外发（logging/日志服务器地址）→ 登录日志服务器确认真的收到 → 查服务器空间、保存与备份方式。三条齐才闭环。

云原生形态同构代入：Pod 销毁日志即丢、stdout 轮转覆盖，等于"本地可灭失"的现代版；集中日志 + 对象存储归档 + 防篡改（WORM）是其异地化对等物。

## A1 — 书中的应用 (Past Application)

### 案例 1: 交换路由设备日志断电即失（第7章 7.3.2，ce15）
- **问题**: 交换机/路由器审计留存怎么查？
- **方法论的使用**: 枚举失效形态（断电丢+空间有限）→ show run 查 logging 配置 → 登录日志服务器确认接收 → 查服务器空间与备份。
- **结论**: 需部署日志服务器；设备本身一般还无日志分析能力，服务器须定期出报表。
- **结果**: 检查步骤成套写入 7.3.2，成为网络设备审计项的标准取证路径。

### 案例 2: Windows 无日志服务器默认不符合（第8章 8.3.1，ce20）
- **问题**: Windows 审计已开启，留存项怎么判？
- **方法论的使用**: 三重风险叠加（本地+按大小覆盖+Administrator 可删）直接触发基线规则。
- **结论**: 未部署日志服务器并备份保存，该项即默认不符合——这是"缺关键基础设施即不符合"的基线型判定，不是程度扣分。
- **结果**: 与 SQLServer 空间满自动覆盖（ce27）、Oracle msdb 同构（cs026）、Linux rsyslog @loghost（pr037）四处复现，证明为系统性规则。

### 案例 3: 数据库审计实时备份异地保存（第8章 8.3.3/8.3.4，cs026）
- **问题**: SQLServer/Oracle 固定空间写满覆盖是产品固有缺陷，怎么补偿？
- **方法论的使用**: 补偿固定为"实时备份、异地保存"；核查看备份策略与备份记录双证据。
- **结论**: 缺实时异地备份，留存完整性不成立。
- **结果**: 三级测评中该缺口在多平台重复出现，被认定为系统性风险而非单点问题。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保测评/内审核查"审计记录保护（避免未预期的删除、修改、覆盖）"类指标。
2. 容器平台/K8s 审计日志随 Pod 销毁丢失，评估是否达标及如何整改。
3. 日志架构评审：设计集中日志方案时验证是否满足留存防灭失要求（采集→传输→归档全链演示）。
4. 事件复盘：怀疑日志被删/被覆盖时，用三重可灭失形态反推证据缺失原因。

### 语言信号 (用户的话里出现这些就应激活)

- "日志都在本机，留存够不够？要不要日志服务器？"
- "审计日志能被管理员删掉，判什么？"
- "日志写满会自动覆盖，怎么办？log overwrite/retention policy"
- "容器日志 Pod 一删就没了，合规吗？centralized logging 怎么设计？"

### 与相邻 skill 的区分

- 与 `mlps-audit-six-dimension-assessment`（审计六维框架）的区别: 六维是审计能力的完备拆解（范围/内容/报表/防篡改/进程/防覆盖）；本 skill 是其中"防覆盖+防删除（留存）"一维的深度判定规则与取证程序。
- 与 `mlps-backup-recoverability-verification`（备份可恢复性验证）的区别: 后者验证业务数据"有备份≠可恢复"，重心在恢复演练；本 skill 是审计日志这一特殊数据类型的留存判据，重心在防灭失而非可恢复。
- 与 `mlps-native-capability-gap-chain`（原生能力缺口判定链）的区别: 本地日志能力缺陷可视为原生缺口的一种，但本 skill 给出的是该族的专属基线判定（缺异地即不符合）与三步取证，比通用判定链更具体。

## E — 可执行步骤 (Execution)

1. **枚举被测对象的日志可灭失形态**：按产品/平台列"断电丢？自动覆盖？最高权限可删？"三问，写出失效因果链。
   - 完成标准: 三问各有结论与依据（配置项/默认行为出处）。
2. **查外发配置**：登录被测端查日志外发目标（logging 服务器地址、rsyslog @loghost、审计服务对接配置）。
   - 完成标准: 外发配置证据在手；无任何外发配置 → 记"缺异地基础设施"。
   - 判停条件: 若无外发配置且本地存在可灭失形态 → 直接判不符合，跳到步骤 4 出整改项。
3. **在日志服务器侧闭环验证**：登录服务器确认被测端日志真实接收、可检索；查服务器可用空间、保存期限与备份方式。
   - 完成标准: 接收证据（检索到被测端近期日志）+ 空间/保存/备份三要素记录。
4. **裁决并出整改基线**：链路齐 = 符合；有外发无备份 = 部分符合并写明缺口；无外发 = 不符合。整改建议落到"集中日志 + 归档 + 防篡改（如 WORM）"三件套。
   - 完成标准: 判定 + 缺口描述 + 三件套整改清单。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 日志字段不全、范围不覆盖（缺主体标识/未覆盖某类用户）——那是六维中"内容/范围"维的问题。
- 日志没有分析和报表——"分析报表"维问题，留存合规不必然意味着有分析能力。
- 普通业务数据的备份核查——用备份恢复验证法，判据是"可恢复"，不是"防灭失"。

### 作者在书中警告的失败模式

- 证据只有设备内 show logging / 本地查询截图，无异地副本（ce15 信号）。
- "审计已开启"充当留存证据——开关是内容维证据，与留存完整性是两回事。
- 数据库端只访谈备份方式、不看备份记录——补偿必须"策略+记录"双证据（cs026）。

### 作者的盲点 / 时代局限

- **版本提示**：判定所对照的"保护审计记录避免未预期删除修改覆盖"条款属等保 1.0（GB/T 22239—2008）；2.0 沿用该要求但测试准则与云环境日志（多租户、控制面日志）须按现行 GB/T 28448 及行业细则重建，本书的平台级命令细节（RHEL6 rsyslog、SQLServer 2008）已过时。
- 未讨论日志服务器自身的防护（日志服务器被拿下则全部证据失守）与留存期限的量化依据——书中只要求"确认保存和备份方式"。

### 容易混淆的邻近方法论

- SIEM 建设方法论：关注采集、关联分析、告警；本 skill 只裁"证据会不会被消灭"，分析能力是另一维。
- "日志备份最佳实践"：运维建议；本 skill 是判定规则——缺基础设施的后果被收敛为"默认不符合"这一档位动作。
