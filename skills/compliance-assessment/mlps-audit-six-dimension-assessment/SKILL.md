# 安全审计六维测评框架

## R — 原文 (Reading)

> "安全审计的测评项主要包括以下六点：
> ①审计范围应覆盖到服务器……上每个操作系统用户和数据库用户；
> ②审计内容应包括重要用户行为、系统资源的异常使用和重要系统命令的使用等……
> ③审计记录应包括日期和时间、类型、主体标识、客体标识、事件的结果等项目；
> ④应能够根据记录数据进行分析，并生成审计报表；……"
>
> — 原作者 等，原始方法论来源第8章 8.3.1 Windows 安全审计（source.txt L4310–4316，第⑤⑥维为"保护审计进程/保护审计记录"，见同段）

## I — 方法论骨架 (Interpretation)

"要看日志"不成其为一个检查方案。把安全审计拆成六维，每维一个独立问题、一种证据形态：

1. **范围**——审计覆盖谁？每个 OS 用户**和数据库用户**都要在网内；漏一类用户即有盲区。
2. **内容**——记什么事？重要用户行为、资源异常使用、重要命令；记录字段五件套（日期时间/类型/主体/客体/结果）缺一则记录不可用。
3. **分析报表**——日志被用起来了吗？原始日志≠审计，须有分析产物（报表/事件追踪）。
4. **防篡改与留存**——记录会不会被消灭？（连接日志异地化判据）
5. **进程保护**——审计本身会不会被停？用否定式验证：低权限尝试停审计/改配置，改不动才合格。
6. **防覆盖**——存储写满/轮转策略会不会吃掉早期记录？

六维是**完备清单**：任何平台的审计方案缺哪一维，弱点就在哪一维，可预判其测评结果。同时作者给了"默认符合"的适用边界——如主流网络设备开启审计后字段齐全，内容维可凭型号+配置截图简化判定，但留存与防覆盖两维**不随之默认**，仍须另查：默认符合只豁免"记什么"，不豁免"保不保得住"。

## A1 — 书中的应用 (Past Application)

### 案例 1: SQLServer 审计六项逐维配证据（第8章 8.3.3，fw56）
- **问题**: 数据库审计测评项怎么逐条落地？
- **方法论的使用**: 六项指标各配证据形态——登录审核选"失败和成功的登录"+C2 审计跟踪（范围/内容）；日志查看器筛选导出+访谈查报表实物（分析）；实时异地备份（留存）；普通用户改审计配置的验证实验（进程保护）；空间与覆盖策略核查（防覆盖）。
- **结论**: 六维每维有独立取证路径，混在一起查必漏。
- **结果**: 成为数据库审计项的标准测评实施模板。

### 案例 2: 网络设备"默认符合"的边界（第7章 7.3.2，pr025）
- **问题**: 路由交换设备审计项是否可简化判定？
- **方法论的使用**: 主流设备开启审计后记录字段齐全，内容维以型号+配置截图判"默认符合"；但设备本地日志断电即失——留存与防覆盖两维不豁免，仍须日志服务器核查。
- **结论**: 默认符合只解决"记录内容"维，不自动覆盖其余维。
- **结果**: 判定被简化但未失真，工时省在可省处。

### 案例 3: "有日志无审计"的跨层共同失败模式（第8/9章，tm039）
- **问题**: 各层审计测评的高频失分形态是什么？
- **方法论的使用**: 用六维扫描 OS 与应用层：未开启、留存不足、业务账号可删日志——分别对应范围/留存/进程保护维缺失。
- **结论**: "有日志无审计"（日志在但无人分析、留不住、可被删）是各层共同失败模式。
- **结果**: 六维成为审计能力成熟度的完备诊断表。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保测评/内审前自查：按六维预检审计配置，定位最弱维。
2. 评估云审计服务（CloudTrail/操作审计类）：查六维是否齐备。
3. 审计方案设计评审：新系统的审计需求用六维写成检查表。
4. 事件溯源失败复盘：查不清操作人时，用六维反推当初缺了哪维。

### 语言信号 (用户的话里出现这些就应激活)

- "审计这块要查哪些方面？光有日志够吗？"
- "audit coverage 怎么评？日志字段要哪些？"
- "云上审计服务开了，还缺什么？"
- "日志能被业务账号删/写满覆盖，算什么问题？"

### 与相邻 skill 的区分

- 与 `mlps-audit-log-offsite-retention`（日志异地化判据）的区别: 后者是六维中"留存/防覆盖"维的深度判定规则（异地化基线）；本 skill 是六维全景框架——先六维定位弱点，再按维调深度技能。
- 与 `mlps-active-verification-perturbation`（主动验证法）的区别: 六维的"进程保护"维用后者的否定式实验取证；本 skill 规定在哪一维用它。
- 与 `mlps-artifact-verification-record-quality`（产物核验与记录质检）的区别: 后者质检"分析报表"维的产物实质；本 skill 决定该产物是六维之一。

## E — 可执行步骤 (Execution)

1. **列六维检查表**：范围/内容/分析/防篡改留存/进程保护/防覆盖，每维写出该平台的对应配置点。
   - 完成标准: 六行检查表，每维有具体检查对象（不含" TBD "项）。
2. **逐维取证**：范围查覆盖对象清单；内容查字段五件套；分析查报表实物；留存查异地链路；进程保护做否定式验证；防覆盖查空间上限与轮转策略。
   - 完成标准: 每维有"通过/缺失/部分"结论 + 证据指向。
   - 判停条件: 若范围维即不通过（审计整体未开启）→ 其余维全部记"无法评估"，直接汇总。
3. **适用"默认符合"时标注边界**：凡引用平台默认能力豁免的（如网络设备内容维），显式写明豁免只覆盖该维。
   - 完成标准: 每处默认符合都有维度限定注记。
4. **输出弱点定位**：缺失维清单 + 各维对应的整改方向（覆盖配置/字段补全/上分析/建异地/加保护/调轮转）。
   - 完成标准: 弱点-整改对照表，可直交整改方。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单点日志排障（查某次故障日志）——运维诊断，不做能力完备性评估。
- SIEM 告警规则/关联分析调优——那是分析维之上的工程深化，六维只问"有没有分析产物"。
- 业务日志（订单流水）审计——对象不是安全相关事件。

### 作者在书中警告的失败模式

- "开启审计"一票判全部符合——默认符合只覆盖内容维，留存/防覆盖常缺（pr025 边界）。
- 有采集无分析：报警记录在、分析报告无，判部分符合（ce56）。
- 审计可被业务账号删除/停用——进程保护维缺失的典型形态（tm039）。

### 作者的盲点 / 时代局限

- **版本提示**：六维源自等保 1.0（GB/T 22239—2008）"安全审计"控制点原文列举；2.0 保留该控制点但测评准则细化，云环境还须补"管理面操作审计/多租户隔离"维——六维结构可平移，条款映射须按现行标准重建。
- 六维未含"时钟同步"（无统一时间轴则跨系统溯源失效）与"日志量监控"——现代审计完备性需补两维，属书外增量。

### 容易混淆的邻近方法论

- 日志管理平台选型清单（采集/存储/检索/展示）：工程视角；六维是**判定视角**——每维直接映射符合/不符合结论。
- 日志审计 maturity model（如 CMMI 式分级）：评等级；六维评完备性缺口，粒度更适合一次性测评。
