# 等级测评与风险评估的分工边界

## R — 原文 (Reading)

> 「等级测评评估的是系统的安全防护能力，风险评估评估的是系统面临的风险。具体说来就是风险评估评估的是系统面临的威胁、系统自身的脆弱性。等级测评评估的是系统的脆弱性和安全措施。二者可以结合使用。」
>
> — 方法论出处，第5章 5.4（测评与风险评估的对等互补）

---

## I — 方法论骨架 (Interpretation)

"合规"和"安全"是两个问题，作者把它操作化成三组可执行规则：

1. **对象分工**：等级测评 = 脆弱性 + 安全措施（对照基线评"措施达没达标"）；风险评估 = 威胁 + 脆弱性（结合资产评"会被打成什么样"）。脆弱性是两者交集，威胁与措施各归一侧。
2. **结论措辞限定**：《基本要求》是最低保护要求（基线）——测评达标只证明满足该等级下限。结论必须写"符合该等级基线要求"，不得写"系统安全"；且基线符合不豁免风险评估——全绿报告回答不了威胁暴露问题。
3. **术语的合同边界**：风险分析 = 总体战略与完整过程（评估 + 管理/处置）；风险评估只是其中的量化环节。合同与对外承诺用窄词（风险评估），避免把风险处置责任隐含进交付。
4. **生命周期耦合**：定级阶段用风险评估辅助定级、测评阶段用它判断是否达到必需等级、运维阶段定期复评确认等级是否变化——两者对等互补，不是替代关系。
5. **可检验的推论**：一个"全绿"测评报告 + 从未做过威胁分析的组织，其对高级持续性威胁的暴露无法从报告中读出。

## A1 — 书中的应用 (Past Application)

### 案例 1: 两套结论分别呈现
- **问题**: 测评与风险评估的结果能否互相折算。
- **方法论的使用**: 第5章 5.4 定义分工——测评发现"不符合项"，风险评估回答"这些安全问题的严重程度与处置优先级"；报告流程中风险等级只由"问题+关联资产+威胁"定性给出，与得分体系是两套并行呈现。
- **结论**: 等级测评结论不能直接当风险等级用，风险结论也不能替代合规结论，报告中分别呈现。
- **结果**: 测评报告同时有符合性结论（分数/档位）与风险分析章（高/中/低），互不换算。

### 案例 2: 基线达标 ≠ 系统安全
- **问题**: 测评全过后宣称"我们安全了"。
- **方法论的使用**: 第1章 1.4 强调《基本要求》是最低保护要求——达标只证明满足基线下限；结论应表述"符合该等级基线"而非"系统安全"，且基线符合不豁免风险评估。
- **结论**: 措辞限定是硬规则——把合规结论说成安全结论，既夸大效力也掩盖剩余风险。
- **结果**: 该原则成为报告结论章与对外宣传的措辞纪律，也是"测评/风险分工"的前提（pr004）。

### 案例 3: 术语混用把处置责任隐含进合同
- **问题**: 服务合同里写"提供风险分析"，交付时只做了量化评估，算不算违约。
- **方法论的使用**: 第5章 5.1 区分——风险分析=评估+管理（消减与控制）的完整过程，风险评估只是其中一项量化工作；"很多人认为风险分析就等同于风险评估"正是作者点名的常见混淆。
- **结论**: 写"风险分析"意味着覆盖处置闭环，写"风险评估"只承诺量化打分；对外承诺用窄词避免隐含处置责任。
- **结果**: 合同与报告用词得以对齐交付范围，术语边界成为合同谈判的实务判据（ce07）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 客户拿到"符合"的测评报告后问"我们安全了吗"，需要专业而不夸大的回答。
2. 撰写测评/评估报告的结论章，纠结措辞（符合基线 vs 系统 安全）。
3. 起草或审查安全服务合同，决定用"风险分析"还是"风险评估"。
4. 管理层拿全绿报告削减安全预算，需要论证剩余风险的存在。
5. 把等保测评、渗透测试、风险评估几份报告整合给董事会看，需要说明各自回答什么问题。

### 语言信号 (用户的话里出现这些就应激活)

- "测评过了是不是就安全了？""全绿是不是没问题了？"
- "报告结论怎么写才不担责？"
- "风险分析和风险评估有什么区别？"
- "合规和安全的区别是什么？"
- 英文: "compliance vs security"、"does passing the assessment mean we're safe"、"baseline requirements vs risk"、"residual risk after compliance"

### 与相邻 skill 的区分

- 与 `mlps-risk-assessment-six-steps`（风险评估六步法）的区别: 后者是风险侧的操作流水线；本 skill 是两侧的边界与措辞规则——先有边界，再决定要不要补风险结论。
- 与 `mlps-score-aggregation-chain`（得分聚合链）的区别: 后者复算合规分数；本 skill 声明该分数的语义边界（合规记分≠风险度量）——分数的结论解释必须挂本 skill 的声明。
- 与 `mlps-report-validity-retest`（报告效力与重测）的区别: 后者限定结论的时间/对象射程；本 skill 限定结论的意义范围（证明什么、不证明什么）——一个管"覆盖多久"，一个管"证明什么"。

## E — 可执行步骤 (Execution)

1. **识别当前问题的类型**
   - 完成标准: 明确用户问的是"措施达没达标"（合规）还是"会被打成什么样"（风险），或两者衔接。
2. **核对结论措辞**
   - 完成标准: 所有合规结论都表述为"符合/基本符合该等级基线要求"，无"系统安全""风险已消除"类表述；有风险结论处注明其来自独立的风险评估。
   - 判停条件: 若用户场景是纯风险决策（上不上新控件、买不买保险），停止引用合规结论——直接转 `mlps-risk-assessment-six-steps` 风险流程，合规数据只作输入。
3. **检查两套结论的覆盖**
   - 完成标准: 已确认威胁分析是否存在——"全绿报告+无威胁分析"组合被标注为"对 APT 类暴露不可知"；缺失侧的建议已给出（补做风险评估）。
4. **术语对齐（合同/报告场景）**
   - 完成标准: 交付物用词与承诺范围一致——只做量化用"风险评估"，覆盖处置闭环才用"风险分析"；关键术语在合同中定义。
5. **输出边界声明**
   - 完成标准: 生成一段标准声明（基线性质、结论射程、剩余风险提示），可嵌入报告结论章或合同附件。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 实际开展风险评估——那是 `mlps-risk-assessment-six-steps` 的流水线；本 skill 只划边界、定措辞。
- 非中国等保语境的合规框架（SOC 2、ISO）——"基线/等级"结构不同，但"合规≠安全"的推理可类比迁移，须重新锚定术语。
- 对抗性营销话术（用"不安全"吓唬客户买服务）——本 skill 的措辞纪律恰恰反对两个方向的夸大。

### 作者在书中警告的失败模式

- 把合规结论当安全结论——"符合基线"≠"系统安全"（pr004）。
- 两套结论互相折算或混排——测评结论与风险等级不可互替（fw40）。
- 合同混用"风险分析/风险评估"，把处置责任隐含进量化交付（ce07）。
- 用全绿报告豁免威胁分析（本 skill 的 V2 推论：APT 暴露读不出来）。

### 作者的盲点 / 时代局限

- 分工框架基于等保 1.0 体系；等保 2.0 与《网络安全法》时代，"合规"外延扩大（关基条例、数据安全、个保法），"测评过了"的法律含义更重，但"基线达标≠安全"的命题更加成立而非减弱。
- 阶段 0 批判：报告流程中风险等级只做定性给出，与得分体系是"松散耦合的两张皮"——作者指出分工却未给出统一模型；使用时应明确说明两套结论的集成方式，防止读者以为分数里已含风险。
- 作者对标准本身不作批判（"案例不符合"永远归因执行不力），未讨论"基线本身在特定场景不合理"的可能——边界声明不应止于措辞，还应提示基线适用性。

### 容易混淆的邻近方法论

- 合规 vs 风险 vs 安全成熟度（如 CMM/C2M2）：三条轴各自独立——合规对基线、风险对损失期望、成熟度对能力持续性；本 skill 只处理前两条。
- 风险评估（量化工作）vs 风险分析（全过程）vs 风险管理（处置）——三层术语嵌套，混用即合同事故。
