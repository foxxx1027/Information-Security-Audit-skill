# 控制有效性四查（粒度/覆盖/生效/技术强制）

## R — 原文 (Reading)

> "针对未部署应用层访问控制设备的情况，查看网络防火墙设备是否对上述应用层协
> 议进行了网络层面的控制，如禁用端口、限制访问源地址等。在网络层端口和源地址的控
> 制无法实现应用层命令级别的控制，仅能降低安全风险。"
>
> — 原作者 等，原始方法论来源第7章 7.3.1 访问控制（source.txt L3331–3335）

## I — 方法论骨架 (Interpretation)

"装了"和"防住了"之间隔着四道独立的坎，每道坎都可能让一个看似到位的控制失效：

1. **粒度**：控制的粗细是否达到指标要求的目标层级。防火墙端口/源地址过滤再严，也到不了 HTTP 命令级——层级不够时"做了控制"不能折算成达标，最多算降险。
2. **覆盖**：控制是否罩住全部入口与被保护对象本身。值守记录若只登记"进大楼的人"而不登记"进机房的人"，控制边界停在外层，核心资产未被覆盖——措施存在但覆盖不全，判部分符合而非符合。
3. **生效**：规则集与默认策略是否真的在拦。iptables 服务 running 但 INPUT 链 policy 为 ACCEPT，等于全放行——存在性证据（服务状态）与有效性证据（规则+默认策略输出）必须分开取。
4. **强制等级**：靠技术强制还是靠管理制度。无认证平台时口令复杂度只能靠策略文档约定，作者明确这只算"管理符合"、技术上未实现——两者是不同证据等级，不可混判。

四查是验收次序：先问层级够不够，再问覆盖全不全，再问是否真生效，最后问靠什么强制。任意一查不过，结论最多"部分符合"，并写明缺口在哪一查。

## A1 — 书中的应用 (Past Application)

### 案例 1: 边界防火墙的网络层控制判据（第7章 7.3.1，ce12）
- **问题**: 指标要求对 HTTP/FTP/TELNET 等做命令级过滤，被测单位只有传统防火墙，怎么判？
- **方法论的使用**: 分档——部署 WAF/下一代防火墙的查命令级控制；未部署的只能看到端口/源地址级，作者判定"仅能降低安全风险"。
- **结论**: 控制粒度低于指标要求的目标层级，不能以"已部署防火墙"判符合。
- **结果**: 该测评项未达标或部分符合，判定记录写明"网络层控制达不到应用层命令级"。

### 案例 2: iptables 默认 ACCEPT——组件在、防护空转（第8章 8.3.2，ce25）
- **问题**: Linux 主机防火墙服务状态 running，是否证明入侵防范到位？
- **方法论的使用**: 查生效维度——不看病历看处方：`#service iptables status` 显示 filter 表 INPUT 链 policy 为 ACCEPT、规则全 ACCEPT。
- **结论**: "如图8-31所示，Linux系统防火墙允许所有用户从任何地方登录系统"——有组件无防护。
- **结果**: 判定依据落在规则集与默认策略输出，而非服务运行状态。

### 案例 3: 无认证平台的口令复杂度只算管理符合（第7章 7.3.2，ce14）
- **问题**: 交换路由设备无 AAA/Radius 平台，口令复杂度只有策略文档要求，算不算符合？
- **方法论的使用**: 查强制等级——技术强制（平台拒绝弱口令）与管理约定（文档要求+人工遵守）分开评价。
- **结论**: "仅能算作满足安全策略管理要求，无法从技术上实现鉴别信息的复杂度"。
- **结果**: 判定输出区分"管理符合/技术符合"两栏，防止管理约定冒充技术控制而降格通过。

### 案例 4: 机房值守记录对象泛化（第6章 6.3.2，ce09）
- **问题**: 建筑物出入口有专人值守并登记，物理访问控制算符合吗？
- **方法论的使用**: 查覆盖——记录对象是"访问建筑物人员"还是"访问机房人员"。
- **结论**: 泛化到建筑物层即控制未覆盖被保护对象本身，判不符合。
- **结果**: 形式上有值守有登记，仍因覆盖缺口不通过，防"假符合"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审测评中核对防火墙、安全组、WAF、EDR 等"控制台显示已配置"的项目是否真正生效。
2. 云安全组界面显示"已配置访问限制"，需判断粒度（端口级 vs 命令级）与覆盖（是否含东西向路径）。
3. 被测单位出示安全策略文档证明口令/访问管控，需区分管理约定与技术强制。
4. 红队/紫队评估后的整改验证：确认修复措施不是"装了组件但策略空转"。
5. 供应商宣称产品能力（"支持命令级过滤/微隔离"），需实测验证粒度声明。

### 语言信号 (用户的话里出现这些就应激活)

- "防火墙已经部署了，为什么还判不符合？"
- "这个控制算不算到位/生效？effectiveness 怎么验？"
- "策略文档里写了要求，算符合吗？管理手段算不算数？"
- "default policy 是 ACCEPT / 规则全是允许，这有问题吗？"
- "控制台显示已启用，实测却没拦住"（false compliance / 策略空转）

### 与相邻 skill 的区分

- 与 `mlps-active-verification-perturbation`（主动验证法）的区别: 后者是取证手段（构造扰动实测能力）；本 skill 是验收判据框架（四查），其中"生效""技术强制"两查的取证手段正是扰动实验。
- 与 `mlps-native-capability-gap-chain`（原生能力缺口判定链）的区别: 后者处理"产品原生做不到→需第三方补偿→缺即不符合"的能力缺口裁决；本 skill 处理"能力存在但层级/覆盖/生效/强制不够"的有效性裁决——一个问有没有，一个问灵不灵。
- 与 `mlps-verdict-tiers`（判定档位体系）的区别: 四查的任一缺口落到哪一档（部分符合/不符合）由后者的档位纪律承接。

## E — 可执行步骤 (Execution)

1. **确认指标要求的目标层级**：写出指标原文，标注它要求的控制粒度（端口级/命令级/单用户级）、覆盖对象（哪些入口、哪些用户/区域）。
   - 完成标准: 一句话写清"指标要的是 ___ 级控制、覆盖 ___"。
2. **查粒度**：取实际控制的配置证据，比对层级。低一层即记录"层级差"。
   - 完成标准: 有配置截图/输出佐证层级结论；层级差的写明"仅能降低风险"。
   - 判停条件: 若控制根本不存在 → 直接进不符合裁决，四查不必继续。
3. **查覆盖**：列出全部入口/路径/被保护对象，逐项核对控制是否罩住；找最薄弱路径（东西向、非边界入口、外层泛化记录）。
   - 完成标准: 覆盖清单 + 缺口位置（缺口决定"部分符合"并写入整改项）。
4. **查生效**：不看服务状态看规则与默认策略（firewall policy、安全组默认规则、WAF 模式检测/阻断），必要时发一条测试流量验证拦截行为。
   - 完成标准: 默认策略输出 + 至少一条规则生效证据；ACCEPT 式空转记不符合。
5. **查强制等级**：判断控制靠技术强制还是文档约定，输出"管理符合/技术符合"分级结论。
   - 完成标准: 每个控制有明确的强制等级标注；管理符合的不得记为技术达标。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 控制完全缺失的情形——不存在有效性问题，直接按档位判不符合。
- 纯管理类条款（制度、培训、审批流）——没有"粒度/策略生效"的技术语义，用管理域核查法（三重一致性）。
- 攻击路径分析（ATT&CK 类）——那是威胁视角的推演，本 skill 是控制视角的验收。

### 作者在书中警告的失败模式

- "已部署防火墙"截图直接判符合——ce12 点名的假符合模板。
- iptables 服务 running 即认定防护到位（ce25）；审计功能"开启"与"规则生效"混为一谈。
- 管理约定冒充技术控制（ce14）：策略文档截图充当口令复杂度技术证据。
- 双层防护同构：两层恶意代码防护用同一病毒库，会被同一变种同时击穿（第8章 8.3.1，fw54）——"做了两层"不等于"有效性翻倍"。

### 作者的盲点 / 时代局限

- **版本提示**：书中案例平台（天清汉马、iptables、Windows 2008）为等保 1.0 时代（GB/T 22239—2008），2.0（GB/T 22239—2019）下指标层级与安全计算环境/安全区域边界口径已变，四查框架可迁移但条款对应须重建。
- 四查本身未覆盖"时效"维度（规则是否过时、例外规则残留），现代云环境还须补 IaC 漂移检查——这是书外增量。

### 容易混淆的邻近方法论

- "深度防御（defense in depth）"：主张多层数量；本 skill 追问每层的层级/覆盖/生效/强制是否达标——层数多不等于有效。
- CIS 基线核对：静态配置与基线比对；本 skill 的第三、四查要求行为级与等级级证据，超出配置 diff。
