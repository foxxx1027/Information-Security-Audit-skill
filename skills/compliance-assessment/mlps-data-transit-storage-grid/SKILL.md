# 数据安全传输/存储两分检查格

## R — 原文 (Reading)

> "①应能够检测到系统管理数据、鉴别信息和重要业务数据在传输过程中完整性受到破
> 坏，并在检测到完整性错误时采取必要的恢复措施；
> ②应能够检测到系统管理数据、鉴别信息和重要业务数据在存储过程中完整性受到破
> 坏，并在检测到完整性错误时采取必要的恢复措施。"
>
> — 原作者 等，原始方法论来源第9章 9.3.3 数据完整性测评指标（source.txt L7461–7467；数据保密性同构两问见同节）

## I — 方法论骨架 (Interpretation)

数据保护讨论极易滑向"我们上了 TLS"一句话了事。两分检查格强制把问题摊成四格：

|  | 完整性 | 保密性 |
|---|---|---|
| **传输中** | 校验码/签名能否检测+重传机制能否恢复 | 通道加密或端到端加密是否覆盖全链路 |
| **存储中** | 数据库能否检测损坏+恢复措施 | 落盘加密/加密存储是否到位 |

两条生成规则：**同一属性必须问两遍**（传输中一遍、存储中一遍——传输加密管不了落盘，落盘备份管不了链路）；**完整性格必须"检测+恢复"成对验收**——只报错不能恢复、只能恢复不检测，都只算半格。

备份恢复**独立成第三块**：它既不是传输也不是存储防护，而是可用性的最后底牌（策略文档→备份记录与恢复测试→介质场外→冗余），单独立项防止被前四格"顺带通过"。经验规律：多数方案的自查缺口集中在"存储中"一列和第三块——传输加密最显眼所以做得最全，落盘加密与恢复演练最隐性所以最常缺。

## A1 — 书中的应用 (Past Application)

### 案例 1: 数据完整性固定两问（第9章 9.3.3，fw64）
- **问题**: "保证数据完整性"指标怎么拆？
- **方法论的使用**: 压缩为固定两问——传输中能否检测+恢复（抓包看校验码→篡改报文→验证对端识别）；存储中能否检测+恢复（查数据库完整性检测能力与恢复措施，可用第三方审计系统佐证）。
- **结论**: 每格取证动作固定化，判定不依赖理解差异。
- **结果**: 完整性测评实施成为可照抄的步骤序列。

### 案例 2: 保密性同构两问防"只查通道"（第9章 9.3.3）
- **问题**: 保密性检查为什么总漏存储？
- **方法论的使用**: 同构拆分——传输问抓包密文/会话初始化验证（扫"已解密的登录请求"漏洞）；存储问数据库加密存储与否。
- **结论**: 两问并列后，"只查通道不查落盘"的结构性遗漏被格网暴露。
- **结果**: 传输/存储两列成为数据保密测评的标准骨架。

### 案例 3: 备份恢复独立成块（第9章 + 第12章）
- **问题**: 备份为什么不算"存储保护"的一种？
- **方法论的使用**: 独立第三块：本地完全备份每天至少一次+介质场外、异地定时传送、拓扑与硬件冗余；管理侧再接四层核查与恢复测试。
- **结论**: 备份恢复是可用性底牌，混入前四格会顺带通过。
- **结果**: 技术块（9.3.3）与管理块（12.4.11）两条线分列，各查各的证据。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审的数据安全及备份恢复类测评，需要防漏项的检查结构。
2. 数据出境/跨境调用场景评审：境外链路+境外落盘的双列核查。
3. 方案评审：设计文档声称"数据已加密"，用四格验证覆盖面。
4. 事后检查复盘：数据被篡改/泄露事件后，反推当初哪一格是空的。

### 与相邻 skill 的区分

- 与 `mlps-auth-transport-plaintext-veto`（明文一票否决）的区别: 后者是"传输×保密（鉴别信息）"格的深度判据（明文否决+开关验证）；本 skill 是四格全景——后者管一格的裁决，本 skill 管格网完备性。
- 与 `mlps-backup-recoverability-verification`（备份可恢复性验证）的区别: 后者是第三块的深度核查法（四层+恢复测试）；本 skill 负责把第三块从四格中分离出来并指向它。
- 与数据分类分级方法论的区别: 先分数据级别再定保护强度；本 skill 不分级，假定对象已定为"重要数据"，查保护维度覆盖。

## E — 可执行步骤 (Execution)

1. **圈定数据对象**：列出系统管理数据、鉴别信息、重要业务数据三类及其传输路径与存储位置。
   - 完成标准: 对象×路径×位置三列清单。
2. **逐格取证**：四格各配证据——传输×完整（校验码+篡改实验+重传机制）、传输×保密（抓包密文/加密协议）、存储×完整（检测能力+恢复措施）、存储×保密（加密存储配置）。
   - 完成标准: 每格"通过/缺失/部分"结论+证据；完整性格拆"检测/恢复"两半分别记。
   - 判停条件: 若数据对象只在本地单机存取、无任何传输路径 → 传输列两格记"不适用"（注明依据），继续存储列。
3. **单独走第三块**：备份恢复按独立块核查（策略/记录/恢复测试/介质场外——细节接 `mlps-backup-recoverability-verification`）。
   - 完成标准: 第三块结论独立于四格呈现。
4. **汇总缺口定位**：输出四格+一块的矩阵，标出空格；空格即整改项。
   - 完成标准: 矩阵无未评估项，缺口附整改方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 加密算法/协议选型评审——格网只管覆盖面，不管选型质量。
- 网络/通道层安全（VPN、专线）——对象是通道不是数据；数据格网与通道核查互补但不替代。
- 数据删除/销毁合规（注销后抹除）——超出 CIA 与备份三块的范围。

### 作者在书中警告的失败模式

- "有 HTTPS"即判数据安全通过——最常见假象，存储列与备份块被跳过（结构性防漏的靶子）。
- 完整性只验"检测"不验"恢复"——半格通过。
- 传输加密只覆盖登录页/部分流量——抓包实测暴露（连接保密性②c）。

### 作者的盲点 / 时代局限

- **版本提示**：格网结构源自等保 1.0（GB/T 22239—2008）"数据完整性和保密性/备份恢复"三控制点；2.0 沿用并扩展（新增个人信息保护、数据脱敏等），格网应扩列而非照抄；跨境场景的"密钥属地"维度是书外增量。
- 未覆盖数据在使用中的状态（内存/缓存中的明文）——两分格在"传输/存储"之外漏了"使用中"第三态，现代数据安全框架（如 D3F 类）已补。

### 容易混淆的邻近方法论

- CIA 三性：属性轴（完整性/可用性/保密性）；本 skill 把状态轴（传输/存储）与属性轴交叉成格——是 CIA 在数据域的操作化细分。
- "encryption everywhere"最佳实践：只对应保密性一列；本 skill 强制完整性列与备份块的同等地位。
