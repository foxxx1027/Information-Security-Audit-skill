# 产物驱动的阶段管理与关键节点评审冻结

## R — 原文 (Reading)

> 「等级测评由测评机构开展，分为测评准备、方案编制、现场测评、分析与报告编制四个阶段，最终向被测单位出具等级测评报告。」
>
> — 方法论出处，第2章 2.1.4（图2-3 四阶段活动与产物对照）；第3章 3.1 展开为表3-1至3-4

## I — 方法论骨架 (Interpretation)

判断一个测评项目"做没做完某阶段"，不看汇报看产物：

1. **四阶段 = 四组固定产物**：准备（项目计划书、系统调查表/基本情况分析报告、工具清单）；方案编制（测评方案书、作业指导书）；现场测评（六类证据记录——访谈结果、文档审查、配置检查、工具测试、实地察看、结果确认文件）；报告编制（等级测评报告）。
2. **缺产物即阶段未完成**——阶段间的交接靠文档产物保证可追溯，这是"阶段完成"的可审计定义，与日历时间无关。
3. **方案内的顺序约束**：结构识别（边界/区域/重要节点）先于指标选择——先划范围再定要求。
4. **质量门三步**：评审（关键节点四项评审：测评方法、测评方案、测评记录、测评报告）→ 确认（方案须委托单位**书面**确认）→ 冻结（方案批准后不得随意调整）。
5. **冻结的意义**：方案不可被现场随意改写，是结论可复现的制度基础——若现场可以随手改范围改指标，报告的任何数字都无法复核。

## A1 — 书中的应用 (Past Application)

### 案例 1: 四阶段产物对照表
- **问题**: 测评项目的进度与质量如何客观衡量。
- **方法论的使用**: 第2章 2.1.4 图2-3 给出四阶段的活动与产物对照；第3章 3.1.1/3.1.3 用表3-1/3-3 把每阶段任务绑定固定产物（如准备阶段三任务各出一件产物，现场阶段输出六类证据记录）。
- **结论**: 产物链使"阶段完成"可审计——缺产物即未完成，不以"我们去过了"为准。
- **结果**: 全书项目组织按此产物链交接，后续质量控制（3.3.2）以产物为审查对象。

### 案例 2: 方案编制的顺序约束
- **问题**: 方案编制六任务有无先后依赖。
- **方法论的使用**: 第3章 3.1.2（表3-2）规定六任务链条：测评对象确定（识别等级、整体结构、边界、网络区域、重要节点与业务应用）→ 测评指标确定 → 测试工具接入点确定 → 测评内容确定 → 测评指导书开发 → 测评方案编制（引文含 OCR 噪声"接人点"）。
- **结论**: 结构识别先于指标选择——没划清边界就选指标，方案必然返工。
- **结果**: 方案书的标准结构（基本情况、结构边界、指标对象、内容方法）固定下来，且须经委托单位书面确认后方可实施。

### 案例 3: 评审—确认—冻结质量门
- **问题**: 现场发现情况与方案不符，能不能现场改方案。
- **方法论的使用**: 第3章 3.3.2 规定关键节点四项评审——测评方法（适当性、成本风险平衡）、测评方案（委托单位书面确认，批准后不得随意调整）、测评记录（同步记录、更改规范）、测评报告（真实准确、结论验证）。
- **结论**: 方案冻结不是官僚主义，而是结论可复现的前提；确需调整要走正式变更，留痕。
- **结果**: 质量体系（依据 GB/T 28449 与 ISO/IEC 17020）以节点评审代替事后追责，"审计一个项目是否真完成方案编制"变成查五件产物 + 查书面确认单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计一个测评/评估项目（含云原生测评）是否真的完成了某阶段，不信任口头进度汇报。
2. 外包测评/咨询验收，需要客观的"完成"判据。
3. 项目经理搭建测评项目管理框架，需要任务-产物对照表。
4. 现场情况变化引发"要不要改方案"的决策。
5. 复盘一个失败项目，定位是从哪个产物缺口开始失控的。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么判断项目做到哪一步了？"
- "测评方案定稿后还能改吗？"
- "验收测评服务要看什么材料？"
- "现场和方案对不上怎么办？"
- 英文: "stage gate"、"deliverables checklist"、"assessment plan sign-off"、"project audit"、"can we change the scope mid-engagement"

### 与相邻 skill 的区分

- 与 `mlps-assessment-scope-selection`（测评对象确定法）的区别: 后者是方案编制阶段内部"对象怎么选"的技术；本 skill 是跨阶段的产物链与质量门管理，其输出（对象清单）恰是本 skill 方案阶段的核心产物之一。
- 与 `mlps-readiness-self-inspection`（就绪度迎检自查）的区别: 后者是被测方迎检自查；本 skill 是测评项目自身的管理审计——一个是客户侧就绪，一个是项目侧交付。
- 与 `mlps-verdict-chain-revision`（判定链与回改）的区别: 后者管报告编制阶段内部的判定链与回改纪律；本 skill 管四阶段之间的门，报告阶段只是四门之一。

## E — 可执行步骤 (Execution)

1. **列出该阶段的应产物清单**
   - 完成标准: 按四阶段对照表写出当前阶段的固定产物（准备 3 件 / 方案 2 件 / 现场 6 类记录 / 报告 1 件），无一遗漏。
2. **逐件核对存在性与完整性**
   - 完成标准: 每件产物存在、内容完整（不是空模板）、版本与日期可追溯；任一缺失即判定"阶段未完成"并记录。
3. **核对书面确认与冻结状态**
   - 完成标准: 测评方案有委托单位书面确认单；确认后无未经变更程序的改动（比对版本差异）。
   - 判停条件: 若发现方案被现场随意改写且无变更记录，停止产物核对，直接判质量门失效，项目结论的可复现性存疑——输出该结构性风险而非继续数产物。
4. **核对阶段顺序合规**
   - 完成标准: 方案编制内"结构识别→指标选择"顺序成立（对象/边界文件日期早于指标文件）；跳序即返工风险标记。
5. **输出审计结论**
   - 完成标准: 每阶段给出"完成/未完成（缺 X 产物）/形式完成（产物存在但无确认无冻结）"三态结论，并附产物清单索引。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单次技术核查（一次配置检查、一次访谈）——没有多阶段产物链可管。
- 通用软件项目管理——产物清单完全不同，只有"缺产物即未完成"的思想可类比。
- 抢时间的应急测评——可压缩产物但本 skill 会如实判定其为"形式不全"，别用它给缩水流程背书。

### 作者在书中警告的失败模式

- 以"人去过现场了"代替阶段完成——无证据记录即现场阶段未完成（fw14 六类证据记录的推论）。
- 方案无书面确认即实施——委托方确认缺位，范围争议无解（fw15）。
- 方案批准后被现场随意改写——结论不可复现（fw21）。
- 产物是空模板/事后补做——结合 `mlps-triple-consistency-check` 时间戳检查识别。

### 作者的盲点 / 时代局限

- 四阶段框架出自 GB/T 28449—2012（等保 1.0 过程指南），等保 2.0 时代过程指南已更新（2020 版 GB/T 28449），阶段划分基本延续但产物模板有调整——审计口径以现行指南为准，本 skill 的"产物链+冻结门"方法不受版本影响。
- 阶段 0 批判：产物齐备证明的是程序合规，不等于证据为真——产物审计要和 `mlps-triple-consistency-check` 一致性穿透配合，否则会产出"文件齐全的空转项目"。

### 容易混淆的邻近方法论

- 产物门 vs 里程碑（时间节点）：前者以可核验交付物定义完成，后者以日历定义——混用会出现"里程碑到了产物没有"的假进度。
- 方案冻结 vs 敏捷迭代：测评是取证型一次性项目，范围冻结是结论有效性的前提；与产品开发的迭代语义相反，不要把"拥抱变化"套进测评管理。
