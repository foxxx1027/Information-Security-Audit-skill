# 交付完整性核查（物+纸+人+责）

## R — 原文 (Reading)

> "（1）应制定详细的系统交付清单，并根据交付清单对所交接的设备、软件和文档进行
> 清点；
> （2）应对负责系统运行维护的技术人员进行相应的技能培训；
> （3）应确保提供系统建设过程中的文档和指导用户进行系统运行维护的文档；"
>
> — 原作者 等，原始方法论来源第11章 11.4.8 系统交付测评指标（source.txt L10252–10258）

## I — 方法论骨架 (Interpretation)

交付不是"东西搬过去了"，是四个要素同时到位：

- **物**：设备、软件按交付清单清点交接——清单是动作的前提，先有清单才谈得上清点。
- **纸（双清单）**：这是本方法的核心增量——文档分两类，缺一类痛感不同：
  - *终态文档*：用户手册、管理员手册、配置信息——支撑**运行**，缺了马上疼；
  - *过程性文档*：设计方案、阶段性工程报告、变更与决策记录——支撑**演进**，缺了当时不疼、升级/二次开发时致命。
- **人**：运维人员技能培训（培训记录含人员、日期、内容）——物纸到位而人不会用，交付仍失败。
- **责**：专门部门负责交付管理与过程监控，按制度与清单执行。

隐性债务的规律：外包项目最常缺的是过程性文档——验收时只清点可见交付物（手册、安装包），设计与演进记录没人要；直到系统升级调阅全部文档，才发现链条断裂。云原生形态同构：终态可用（镜像能跑），过程性资产（ADR、流水线配置、环境定义）未移交，两年后无人敢动。清点动作因此必须**按双清单分别核对**，而不是按"对方给了什么"签收。

## A1 — 书中的应用 (Past Application)

### 案例 1: 外包交付缺过程性文档（第11章 11.4.8 案例情形二，ce49）
- **问题**: 外包开发交付了操作手册、配置信息、后台管理手册，做过培训、有签收，为何还判不符合？
- **方法论的使用**: 双清单核查——终态文档齐，过程性文档（软件设计开发过程文档）缺失；业务发展需要升级时调阅全部文档，发现链条断裂。
- **结论**: 终态文档支撑运行、过程性文档支撑演进；只签收可见交付物是外包项目最常见的隐性债务。
- **结果**: 交付清单与培训项判不符合；升级工作受阻成为实际后果。

### 案例 2: 大组织自主开发的完整交付（第11章 11.4.8 案例情形一）
- **问题**: 交付做得好的样板长什么样？
- **方法论的使用**: 四要素齐备——源代码、安全设计方案、用户手册等文档与软硬件移交运维部门；制定交付管理制度、清单与记录；管理部门负责记录、清点、监督、审批；并对技术运维人员培训。
- **结论**: 物纸人责四要素各自有制度与记录支撑。
- **结果**: 判符合，成为对照样板。

### 案例 3: 工程过程文档可追溯（第11章 11.4.6 工程实施，关联）
- **问题**: 过程性文档从哪来？
- **方法论的使用**: 工程实施阶段要求实施计划、会议、变更、验收等阶段性文档可追溯——与交付双清单同源，建设期不留档，交付期就无纸可交。
- **结论**: 交付完整性是建设期过程管理的下游结果。
- **结果**: 交付核查与工程实施核查衔接成链。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审的系统交付控制点核查。
2. 项目验收前的交付清单设计：把双清单写进合同与验收单。
3. 外包/低代码平台项目收尾：识别并追讨过程性资产。
4. 云原生项目（IaC+CI/CD）交付：镜像、代码、流水线、环境定义的移交核对。

### 语言信号 (用户的话里出现这些就应激活)

- "交付验收要交接哪些东西？handover checklist 怎么列？"
- "外包只给了手册和安装包，够吗？"
- "系统要升级了才发现没有设计文档，问题出在哪？"
- "IaC/流水线算不算交付物？as-built documentation 要哪些？"

### 与相邻 skill 的区分

- 与 `mlps-go-live-quality-gate`（上线质量门）的区别: 后者是放行前的**测试证据门**（独立性与四件套）；本 skill 是放行后的**移交完整性门**（物纸人责）——测试过了但交付缺文档，仍是半成品。
- 与 `mlps-backup-recoverability-verification`（备份可恢复性验证）的区别: 后者查运行期"能不能恢复"；本 skill 查移交时"该给的都给了吗"——过程性文档缺失会让恢复演练更难，但两者对象不同。
- 与资产管理/CMDB 建库的区别: 建运行态台账；本 skill 查一次性移交事件的完整性，产出可入台账。

## E — 可执行步骤 (Execution)

1. **建四要素清单**：物（设备/软件/镜像/IaC/密钥托管）、纸（终态+过程性双清单）、人（应培训角色）、责（接收部门与制度），逐项列出应有项。
   - 完成标准: 四张应有清单；纸类明确标注终态/过程性两列。
2. **实物清点**：按清单核对交接记录与签收记录，对照"对方实际给了什么"。
   - 完成标准: 每项有"已交/未交"状态；未交项单独列表。
   - 判停条件: 若连交付清单本身都不存在 → 直接判不符合方向，先要求制定清单再继续核查。
3. **双清单分离核验**：终态文档核对（手册/配置可支撑日常运维）；过程性文档核对（设计决策、工程报告、变更历史可支撑升级演进）。
   - 完成标准: 两列分别给出齐/缺结论；过程性缺失项标注"演进风险"。
4. **人与责核验**：查培训记录（人员/日期/内容）与负责部门的制度、监控记录。
   - 完成标准: 培训记录实物 + 责任部门授权文件。
5. **裁决与追讨清单**：按档位判定（清单+培训项可单独落不符合）；输出待追讨资产清单（含过程性文档与云原生等价物：ADR、流水线配置、环境定义）。
   - 完成标准: 判定 + 追讨清单（每项注明用途与缺失后果）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 运行期运维交接（岗位轮换）——那是人员与知识管理，用人员全周期框架。
- 合同商务条款审查（付款节点、违约责任）——法务域；本 skill 只管移交完整性。
- 数据迁移验证——数据正确性有专门验证方法，非交付清点范畴。

### 作者在书中警告的失败模式

- 只签收可见交付物（手册、安装包），过程性文档无人追讨（ce49）。
- 无交付清单即开展交接——清点失去基准。
- 有培训之名无记录之实（缺人员/日期/内容三要素）。

### 作者的盲点 / 时代局限

- **版本提示**：控制点条文属等保 1.0（GB/T 22239—2008 系统交付）；2.0 沿用；云原生与 SaaS 交付形态下"物"的外延（镜像、IaC、密钥、流水线）书未覆盖，须按 V2 推论扩展映射。
- 未涉知识产权与源代码许可的交割（拿到源代码但无使用许可的场景）——工程与法务的缝隙。

### 容易混淆的邻近方法论

- as-built documentation（竣工文档）惯例：只覆盖"纸"要素的一部分；本 skill 强调双清单区分与物纸人责四要素完整性。
- project closure checklist（项目管理收尾）：商务与行政收尾为主；本 skill 聚焦安全建设管理语境下的可核查证据链。
