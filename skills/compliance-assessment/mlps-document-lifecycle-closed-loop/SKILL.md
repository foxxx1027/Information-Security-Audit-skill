# 文档闭环管理（制定—发布—评审—修订—版本）

## R — 原文 (Reading)

> "安全管理制度制定时应按照统一的格式或要求，
> 安全管理制度发布时应注明适用和发布范围，发布的制度文件应格式统一、规范，有版本控
> 制。"
> "领导小组定期审定→检查→修订→再宣导"及"每年对安全管理制度进行评审和修订"（第10章制定和发布/评审和修订指标分析）
>
> — 原作者 等，原始方法论来源第10章 10.4.1（source.txt L7862–7866、L7822 摘述）

## I — 方法论骨架 (Interpretation)

制度文档不是交付物，是**活文档**——写完那天才是衰变的开始。闭环管理把"还活着吗"拆成三个可核查的证据：

1. **评审记录**：有没有按周期（如每年）组织评审。没有评审动作，文档与环境变化脱节只是时间问题。
2. **修订记录**：版本时间线连续吗？三年无修订痕迹 = 断链——要么业务没变（罕见），要么制度已死。物流公司式的"各自定制度不通知全员"就死在这一环。
3. **掌握度访谈**：抽访相关人员知不知道制度存在、要遵守什么。这是三证据中最锋利的——评审和修订都可以突击补（时间戳会说话），但一群人"不知道有这制度"补不出来。

再加**版本控制两追问**："当前有效版本是哪一版？旧版是否回收？"新旧版本并存时，执行者拿哪版都"有据可依"，制度等于失效——无版本号/新旧并存判部分符合。

闭环还有一条回流边：**测评/评估结果必须回流修订**（安全方案按测评结论定期调整，指标⑤回路）——文档不仅随业务更新，还随符合性结论更新，形成双向活回路。

## A1 — 书中的应用 (Past Application)

### 案例 1: 良好实践的闭环样板（第10章 10.4.1 案例，fw70）
- **问题**: 制度做得到位的组织长什么样？
- **方法论的使用**: 领导小组定期审定→检查→修订→再宣导；取证=评审记录+修订记录+重要岗位人员掌握度访谈三件齐。
- **结论**: 制度在被运营，判符合。
- **结果**: 三证据法从该案例中固化下来，成为管理制度的测评实施要点。

### 案例 2: 无归口部门的制度断链（第10章 10.4.1 案例，ce32/物流公司）
- **问题**: 为什么业务部门各自定制度、技术加固仍"作用不大"？
- **方法论的使用**: 查闭环主体——没有授权专门部门负责制度的制定与维护，各自定制度且不通知全员。
- **结论**: 无归口→制度分散不透明→操作无章可循→技术投入失效；评审修订环节自然空白。
- **结果**: 判不符合；该案例同时是 `mlps-management-root-cause-traceback` 管理根因回溯的载体。

### 案例 3: 安全方案随测评结论滚动更新（第11章 11.4.2，fw82）
- **问题**: 设计方案类文档要不要闭环？
- **方法论的使用**: 方案须按测评/评估结果定期调整修订（指标⑤）——方案不是立项时的一锤子文件。
- **结论**: 方案是随测评结论滚动更新的活文档。
- **结果**: 闭环思想从制度推广到方案类文档，覆盖管理域多文档类型。

### 案例 4: 版本控制两追问（第10章，pr056）
- **问题**: "统一格式并进行版本控制"怎么落地核查？
- **方法论的使用**: 问两个问题——当前有效版本是哪版？旧版是否回收？无版本号或新旧并存判部分符合。
- **结论**: 版本控制的可核查形态就是这两问。
- **结果**: 版本核查进入表 10-9 测评实施要点（查格式要求、版本控制及修订记录）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/ISMS 管理测评核查"制定和发布/评审和修订"控制点。
2. 组织自查：怀疑制度文档多年未动、已成纸面摆设。
3. 制度整合/换版项目：理清旧版回收与版本切换的检查点。
4. 事件复盘：违规操作引用了过期版本的制度。

### 语言信号 (用户的话里出现这些就应激活)

- "制度三年没更新了，怎么判？stale policy 有问题吗？"
- "版本控制要查什么？新旧版本并存算什么？"
- "评审记录和修订记录要看什么？review cycle 怎么核？"
- "怎么发现'写了没人知道'的纸面制度？"

### 与相邻 skill 的区分

- 与 `mlps-policy-four-layer-pyramid`（制度四层金字塔）的区别: 金字塔判**结构**（四层齐不齐）；本 skill 判**时间**（文档还活着吗）——结构完整但停止更新的体系，金字塔管不了，本 skill 才能判。
- 与 `mlps-artifact-verification-record-quality`（产物核验与记录质检）的区别: 后者质检执行类记录的实质要素；本 skill 核查制度文本自身的生命周期证据（评审/修订/版本），对象不同。
- 与 `mlps-management-root-cause-traceback`（管理根因回溯）的区别: 后者把"技术整改无效"回溯到管理根因时，归口部门缺失是高频根因——本 skill 的案例 2 正是其证据形态。

## E — 可执行步骤 (Execution)

1. **索三证据**：定期评审记录、修订记录（版本时间线）、版本控制文件（格式要求/收发文登记）。
   - 完成标准: 三类材料到手或确认缺失（缺失即记录）。
   - 判停条件: 若连归口部门/责任人都不存在 → 判不符合方向，直接跳步骤 4 出"先建归口"的整改前置项。
2. **查时间线**：把修订事件画在时间轴上，找断裂区间（>1 个评审周期无动作=断链）；对照业务变更事件（系统上线、组织调整）看制度是否随之更新。
   - 完成标准: 时间轴图 + 断链区间标注。
3. **做掌握度访谈**：抽 2–3 名应知人员，问制度存在性、关键要求、执行方式。
   - 完成标准: 访谈记录；"不知道有这制度"的比例如实记载。
4. **版本两追问**：确认当前有效版本与旧版回收情况。
   - 完成标准: 两问有明确答案；并存/无版本记录为缺陷。
5. **判档与整改**：三证据齐+版本清晰=符合；断链或掌握度差=部分符合并写明缺口；无归口无评审=不符合。整改按"归口→评审周期→修订触发（含测评结果回流）→版本管理"排序。
   - 完成标准: 判定 + 缺口描述 + 四步整改清单。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 制度内容质量评审（条款合理否）——闭环只证"活着"，不证"写得好"。
- 一次性产物（测评报告、某次演练总结）——无持续运营语义，不是活文档。
- 技术配置文件版本管理（代码/配置库）——用工程版本控制实践，语义不同。

### 作者在书中警告的失败模式

- 各自定制度、不通知全员、无归口部门（ce32 断链的根）。
- 突击补评审/修订记录——时间戳与业务周期不吻合即露馅（与 `mlps-artifact-verification-record-quality` 实质质检同源）。
- 新旧版本并存执行——"有据可依"的假象，判部分符合。

### 作者的盲点 / 时代局限

- **版本提示**：闭环要求源自等保 1.0 管理指标（GB/T 22239—2008 第 10/11 章）；2.0 延续该控制点，云与敏捷环境下"年度评审周期"可能太慢，须按变更节奏定义触发式评审（事件驱动+周期兜底）——属书外增量。
- 未给出"评审有效性"判据（评审是走过会还是真审议）——掌握度访谈是间接代理，缺直接证据形态。

### 容易混淆的邻近方法论

- document control（ISO 文控）：管理文件收发、编号、受控状态的行政流程；本 skill 聚焦"制度还活着"的三证据与回流回路，比文控更针对时效性。
- knowledge management 的文档保鲜：内容视角；本 skill 是合规判定视角。
