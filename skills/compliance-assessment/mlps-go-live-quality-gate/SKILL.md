# 建设期质量门（第三方独立性 + 四件套 + 外包后门审查）

## R — 原文 (Reading)

> "组织应委托公正的第三方测试单位（如第三方软件测试机构）对信息系统进行安全性测试，不
> 可由组织内部或开发方进行安全性测试。"
> "（4）应要求开发单位提供软件源代码，并审查软件中可能存在的后门。"
>
> — 原作者 等，原始方法论来源第11章 11.4.7 测试验收指标分析 + 11.4.5 外包软件开发测评指标（source.txt L10085–10086、L9857）

## I — 方法论骨架 (Interpretation)

上线质量门有两根独立的轴，**独立性 × 覆盖度**，各自失守都会开门放行：

**独立性轴**：安全性测试必须由公正第三方做，内部自测与开发方自测被明文排除——利益冲突使结论失去效力。最常见的规避形态是"UAT/试运行顶替验收"：UAT 验证的是业务适配性，既不覆盖安全性也不满足独立性。第三方但只测功能（案例三）与内部但测得全（案例二）是两种对称的不合格。

**覆盖度轴**：安全测试四件套——配置检查、漏洞扫描、渗透测试、**源代码扫描**。前三件是黑盒/灰盒，第四件是白盒：源代码后门只能靠代码级手段发现，功能测试永远发现不了。无源码场景（低代码平台）不豁免，须替换为等价的"应用逻辑与连接器配置审查+平台导出的自动检查"——缺代码级审查即部分符合。

**外包防线**：安装前恶意代码检测、设计文档、源代码交付并审查后门。诊断经验有一条金子般的启发：**无规律的间歇性异常且"重启即好"，本身就是疑似木马信号**，应触发安全检查而非继续当可用性问题修。

## A1 — 书中的应用 (Past Application)

### 案例 1: UAT 顶替验收（第11章 11.4.7 案例情形二，ce47）
- **问题**: 为降成本，企业内部人员做接入测试（UAT），以试运行结果当验收依据直接投产，行吗？
- **方法论的使用**: 双轴核查——独立性轴失守（内部测试），覆盖度轴也未做安全四件套。
- **结论**: 第三方安全性测试项不符合；"试运行通过"不能替代书面验收方案、过程记录与验收报告。
- **结果**: 使用一段时间后暴露重大功能缺陷与性能瓶颈，验证了门的必要。

### 案例 2: 第三方但漏安全测试（第11章 11.4.7 案例情形三，ce48）
- **问题**: 委托了有资质第三方测功能与性能、评审验收也走了流程，为何上线即被 SQL 注入？
- **方法论的使用**: 覆盖度轴核查——验收未纳入恶意代码检测、源代码扫描、渗透测试；黑客利用源代码中的后门与恶意代码发起 SQL 注入，用户账号、银行卡号泄露。
- **结论**: 功能性能验收与安全性验收是两扇独立的门，前者通过不代表后者可豁免。
- **结果**: 安全性测试项判不符合；案例确立"四件套"为最低覆盖清单。

### 案例 3: ERP 木马（第11章 11.4.5 案例情形三，ce46）
- **问题**: 外包开发的 ERP 上线后经常异常、重启服务即恢复正常，问题出在哪？
- **方法论的使用**: 外包防线回查——未做安装前恶意代码检测、未审查源代码后门；间歇性异常+重启即好被当作一般可用性故障处理。
- **结论**: 建设期缺陷（木马植入+源代码漏洞）在运行期以业务数据被窃的形式暴露；该信号本身即疑似恶意代码。
- **结果**: 委托第三方安全检查才发现植入木马与多个源代码漏洞，名誉资产双损失。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新系统/新版本上线前的验收把关：设计验收方案的安全测试部分。
2. 采购评审：低代码平台/SaaS 定制交付的系统，验收怎么要求证据。
3. 外包开发合同安全条款设计：源代码交付、恶意代码检测、后门审查写进合同。
4. 运行期排查：系统反复"莫名异常重启即好"，怀疑建设期埋雷。

### 语言信号 (用户的话里出现这些就应激活)

- "UAT 通过了能不能上线？还需要什么测试？"
- "开发方自己做了安全测试，行不行？independent testing 为什么必须？"
- "源代码拿不到，源码扫描怎么办？"
- "系统时不时抽风、重启就好，可能是什么问题？"（木马信号）
- 英文: UAT is not acceptance / code review before go-live

### 排除信号 (出现这些不应激活本 skill)

- "已经验收放行了，接下来做运维移交，交接清单里该列哪些东西？"——验收放行后的移交门（物纸人责），转 `mlps-delivery-completeness-check`；移交接收方是运维部门也属项目交付移交，勿因"运维"二字误判为运行期运维交接（岗位轮换）。
- "上线后定期跑漏洞扫描/打补丁，频率够不够？"——运行期漏洞管理，转运维域。

### 与相邻 skill 的区分

- 与 `mlps-tool-test-typology`（工具测试类型学）的区别: 后者讲三类工具怎么用（扫描/监测/渗透的方法学）；本 skill 讲**谁来做、是否可缺项、什么门放行**——组织与裁决层面。
- 与 `mlps-assessment-redlines`（作业红线）的区别: 红线约束测试执行中的行为（授权/限域/陪同）；本 skill 约束验收结论的效力条件（独立性/覆盖度）。
- 与 `mlps-delivery-completeness-check`（交付完整性核查）的区别: 后者查验收放行后的交付物清单完整性（物纸人责）——凡问"移交/交接清单里该列哪些东西"（含移交给运维部门）都属后者；本 skill 只查放行前的测试证据——测试门过了才轮到交付清点。

## E — 可执行步骤 (Execution)

1. **验独立性**：确认安全性测试的执行方——公正第三方（查资质证明）？内部/开发方自测即独立性失守；追问"验收依据文件是什么"，只有试运行记录=UAT 顶替。
   - 完成标准: 测试主体独立性结论 + 验收依据文件清单。
   - 判停条件: 若安全性测试根本未做（无论谁做）→ 直接判不符合，跳步骤 3。
2. **验覆盖度**：对照四件套逐项核对测试报告——配置检查、扫描、渗透、源代码扫描（或无源码场景的等价审查）；漏项即部分符合。
   - 完成标准: 四件套有/无对照表；等价审查的替代物明确记录。
3. **外包专项**：查安装前恶意代码检测记录、源代码交付与后门审查记录；无源码则查合同为何放弃及补偿措施。
   - 完成标准: 外包三防线各有证据或缺口标注。
4. **裁决与整改**：双轴结论合成——独立+全覆盖=门通过；任一轴失守按档位判（第三方缺安全/内部全测均不合格）；整改指向"补第三方安全测试/补四件套缺项/补代码级审查"。
   - 完成标准: 双轴判定矩阵 + 整改项与放行条件。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 运行期漏洞管理与补丁流程——那是运维域（系统安全管理），质量门只管上线时点。
- 采购商务谈判（价格、交付周期）——质量门结论是技术放行条件，不替代商务决策。
- 已上线多年系统的存量安全评估——用测评/风险评估框架，质量门的"上线前"语境已过。

### 作者在书中警告的失败模式

- UAT/试运行顶替验收（ce47）；第三方只测功能性能漏四件套（ce48）。
- 间歇性异常当可用性问题处理，错过恶意代码信号（ce46）。
- "平台支持安全功能"的宣称替代实测（与 `mlps-auth-transport-plaintext-veto` 能力≠启用同族）。

### 作者的盲点 / 时代局限

- **版本提示**：指标条文属等保 1.0（GB/T 22239—2008 系统建设管理）；2.0 沿续测试验收控制点；DevOps 持续交付下"上线时点门"应演化为流水线中的持续安全门（每发布版本过四件套的自动化子集）——书的时代没有这条流水线。
- 未讨论第三方的利益冲突残余（甲方付钱能否买来不利结论）与"公正"的验证手段——资质之外的行为独立性无程序。

### 容易混淆的邻近方法论

- 一般 SDLC 测试阶段（单元/集成/系统测试）：开发质量视角；本 skill 是安全验收视角——独立性与安全四件套是其特有增量。
- bug bounty/众测：运行期持续发现机制；质量门是时点门，两者时段与责任主体不同。
