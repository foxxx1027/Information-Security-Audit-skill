# 等保定级决策程序（双要素 × S/A 取高 × 三方校验）

## R — 原文 (Reading)

> 「信息系统的安全定级主要由两方面的要素来确定：一是信息系统受到破坏时所侵害的客体；二是信息系统受到破坏时对客体造成的侵害程度。」「若信息系统定级不准确，后续工作将没有保证。」
>
> — 方法论出处，第2章 2.1.1（表2-1，定级双要素矩阵）

---

## I — 方法论骨架 (Interpretation)

定级不是"感觉重要就定高"，而是一张二维记分卡加一套合成规则：

1. **两个正交维度打分**：受侵害客体分三类（公民/法人/其他组织合法权益 → 社会秩序与公共利益 → 国家安全），侵害程度分三档（一般损害/严重损害/特别严重损害）。客体的类别决定可用的最高级。
2. **两条平行评分线**：S 线只看"业务信息被破坏"伤到谁、多重；A 线只看"系统服务中断"伤到谁、多重。两条线必须独立评定，不能把可用性损失混进信息线重复计分。
3. **取高合成**：G = max(S, A)。不许折中、不许平均——谁高按谁。
4. **等级是下游一切的开关**：指标集、测评频次、备案材料全部由 G 推导，定级错则全链失据，链上没有独立纠错点。
5. **三方外部校验兜底**：专家评审 + 主管部门审批 + 公安机关备案审核，用制度程序对冲单点定级错误。
6. **抽象要素可翻译**：行业可把"客体×程度"换成业务可自评的维度（如烟草行业用信息类型/服务范围/运行环境/RTO 四因素），骨架不变。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 烟草行业把双要素翻译成四因素自评
- **问题**: 国标"客体×程度"太抽象，业务部门无法自行判定定级。
- **方法论的使用**: 把两个抽象要素操作化为四个可判定业务维度——信息类型（公开/专有/重要）、服务范围（局域/区域/全局）、运行环境（互联网/内联网）、恢复时间目标 RTO（8h 以上/4~8h/4h 以内三档）。
- **结论**: 抽象定级要素可以无损翻译为业务可自评选项，且可用性（RTO）可量化进定级。
- **结果**: 形成行业定级准则（YC/T389）与实施规范（YC/T495），按新建/已建系统分述落地流程。

### 案例 2: 定级结论向测评指标集传导
- **问题**: 定级结论出来后如何决定"测什么"。
- **方法论的使用**: 第3章方案编制中，测评指标按 S/A 对应等级从《基本要求》对应级别选取（附录A 表3-1）。
- **结论**: 定级错则指标集错——G 是指标选择的唯一上游变量。
- **结果**: 报告侧以 S/A 等级选基本指标成为固定栏目，定级理由可追溯。

### 案例 3: 定级不准的全链传导与公安兜底
- **问题**: 定级偏差会带来什么后果。
- **方法论的使用**: 作者画出失效链——定级错→备案信息错→建设整改目标错→测评指标选错→测评结论无意义。
- **结论**: 定级是"首要环节、关键环节"，单点错误无下游纠错，只能靠三方校验前置拦截。
- **结果**: 公安机关对定级不准的系统发整改通知并要求重新定级，构成制度兜底；发现定级偏差应作为最高优先级问题上报，而非逐项修补下游。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新建信息系统或既有系统首次进入等保流程，需要确定安全保护等级、撰写定级报告。
2. 被问"我们这个系统该定几级"，用户只有业务描述（数据类型、用户群、停机影响），需要翻译成定级语言。
3. 复核一份已有定级报告，怀疑等级定高了（成本压力）或定低了（风险暴露）。
4. S 与 A 冲突的场景：信息很敏感但服务中断只影响单一客户，或反之——需要说服力强的裁决逻辑。
5. 云上部署、数据出境、多租户等新形态系统，直接套用"Web 系统定二级"的老经验产生争议。

### 语言信号 (用户的话里出现这些就应激活)

- "这个系统定几级？""定级报告怎么写？"
- "S 级和 A 级怎么定？""两个不一样取哪个？"
- "定级定低了/定高了会有什么后果？"
- "公安/专家评审要过定级，我们要准备什么？"
- 英文: "determine the protection level / grading"、"security classification"、"how to classify this system"

### 与相邻 skill 的区分

- 与 `mlps-indicator-selection-rules`（指标确定规则集）的区别: 本 skill 产出等级 G；后者拿 G 去选指标集。先定级后选指标，顺序不可倒置。
- 与 `mlps-risk-assessment-six-steps`（风险评估六步法）的区别: 定级回答"应达到什么保障水平"（看 CIA 损失最大值），风险评估回答"现状离目标多大险"；CIA 价值高不等于风险高，两套结论不可互替。
- 与 `mlps-readiness-self-inspection`（就绪度迎检自查）的区别: 本 skill 是定级环节本身的决策程序；后者是备案、监督检查环节的组织就绪度自查。

## E — 可执行步骤 (Execution)

1. **界定定级对象**
   - 完成标准: 能一句话说清系统边界（独立业务使命、独立软硬资产），多个系统共用资源的情况已标注。
2. **独立评定 S 线**
   - 做法: 假设业务信息被破坏（泄露/篡改/不可用），沿"侵害客体类型×侵害程度"矩阵判 S1–S5，写出具体侵害场景（波及谁、多大规模、什么后果）。
   - 完成标准: S 等级 + 一段可复核的侵害场景描述。
3. **独立评定 A 线**
   - 做法: 假设系统服务完全中断，重复上述判定得 A1–A5。不得引用 S 线的损失做依据。
   - 完成标准: A 等级 + 独立的可用性损失场景描述。
4. **取高合成 G = max(S, A)**
   - 完成标准: 写出 S_G 与 A_G 的组合记法（如 S3A2G3）及取高理由。
   - 判停条件: 若任一线证据不足以区分"严重/特别严重"，先补业务影响分析再回来，不得凭感觉取档。
5. **组织三方校验**
   - 完成标准: 专家评审意见、主管部门审批、公安机关备案审核三环节已安排或已完成；定级后 30 日内备案衔接已列入计划。
6. **输出定级报告**
   - 完成标准: 报告含定级对象描述、S/A 两线评定过程、G 结论、侵害场景依据；发现既有定级与评定不符时，已作为最高优先级问题提出重新定级。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 做威胁建模或风险排序——那是风险评估（`mlps-risk-assessment-six-steps`）的领地；定级只定"应然保障水平"，不度量"实然风险"。
- 产品安全检测、密码应用安全性评估等非等级保护定级场景。
- 已有明确行业定级细则且与国标冲突时的最终裁决——本 skill 只提供"翻译"思路，法律适用以现行行业主管部门规定为准。

### 作者在书中警告的失败模式

- 定级不准确→备案、整改、测评、结论全链失据，且无独立纠错点（第2章 2.1.1）。
- 把可用性损失混入信息线重复计分，导致 S 线虚高（作者强调两线独立评定）。
- 只因"是个 Web 系统"就定二级，忽略规模化个人信息泄露对社会秩序/公共利益的侵害。

### 作者的盲点 / 时代局限

- 全书基于等保 1.0（GB/T 22239—2008 + 公通字[2007]43 号）。等保 2.0（GB/T 22239—2018，2019-12 实施）下：定级对象规则更明确（云计算平台、大数据、物联网系统等可整体定级）、定级备案流程电子化，具体条款与程序须对照现行标准复核，本 skill 的"双要素×取高×三方校验"骨架仍然成立。
- 五级定义的具体文本属标准原文（阶段 1.5 未录取为方法论），引用时须查现行标准而非本书转述。

### 容易混淆的邻近方法论

- "定级" vs "风险等级"：前者是保护义务等级，后者是威胁×脆弱性×资产的量化结果。
- 等保定级 vs 商用密码应用安全等级、行业主管部门的自定分级体系——判定要素不同，不可混用。
