# 管理根因回溯法（技术整改无效→回查管理）

## R — 原文 (Reading)

> "该公司的核心业务系统经常发生网络攻击，技术部门已向总裁申请
> 安全设备对核心系统进行加固，但作用不大。经技术总监对各个业务部门和操作流程的
> 调查，发现人员操作无章可循，其根本原因是业务部门自行制定各自的管理制度，并没有
> 通知到全员。公司没有授权专门的部门负责制定和维护安全管理制度。"
>
> — 原作者 等，原始方法论来源第10章 10.4.1 制定和发布案例情形三（source.txt L7977–7982）

## I — 方法论骨架 (Interpretation)

安全圈有个反复出现的怪圈：设备越买越多，事故照发不误。本书给出的诊断假设是——**"技术整改无效"本身是管理根因的信号**。回溯沿三条路径：

1. **制度归口**：有没有一个被授权统一负责安全制度的部门？还是各业务团队自定义规则、互相不知会？没有归口，制度就分散且不透明，操作者无章可循，技术控制落在混乱的制度地基上。
2. **职责闭合**：拿高风险流程（变更、审批、离岗收权）当试金石——复盘时两个岗位互相推诿"不归我管"，就是职责边界不闭合的行为证据。
3. **人员链**：培训考核记录与实际操作是否两张皮；人员隐患不除，技术防护形同虚设。

理论上有个干净的分工：**技术回答"能不能"，管理回答"允不允许、谁批准、留没留痕"**——管理是对技术的社会工程学补偿层，不是附属品。由此推出行动准则：**诊断顺序与采购顺序相反**。技术失效时先测管理三路径定位根因，再决定技术预算；继续堆产品只会重复物流公司的"作用不大"。

## A1 — 书中的应用 (Past Application)

### 案例 1: 物流公司技术加固失效（第10章 10.4.1 案例情形三，ce32）
- **问题**: 核心业务系统频遭攻击，买了安全设备加固"作用不大"，根因在哪？
- **方法论的使用**: 技术总监调查各业务部门与操作流程，回溯制度归口——业务部门各自定制度不通知全员，无授权专门部门负责制度的制定与维护。
- **结论**: 因果链=无归口→制度分散→操作无章可循→技术投入失效。
- **结果**: 该案例成为"技术整改无效先查管理"的立论证据，判定落到制定和发布的归口指标上。

### 案例 2: 管理是技术的社会工程学补充（第12章 12.4.6 网络安全管理，fw89）
- **问题**: 为什么"重技术轻管理"必然留缺口？
- **方法论的使用**: 立论定位——网络安全管理是对网络技术层面的补充，从社会工程学角度避免系统因偶然或恶意原因遭破坏、更改、泄露。
- **结论**: 技术与管理的问题域不同：能不能 vs 允不允许、谁批准、留没留痕。
- **结果**: 全书管理篇的测评重心由此定位在配置、日志、策略、记录、监控等"人与流程"证据上。

### 案例 3: 人员隐患抵消技术投入（第10章 10.4.3 概述，fw76/ce43）
- **问题**: 何时应把调查重心从技术转到人员链？
- **方法论的使用**: 信号识别——技术投入持续增加但事故/违规仍在发生；立论"如果人员的安全问题与潜在隐患没有得到很好的解决，技术防护措施都将会形同虚设"。
- **结论**: 该信号下应转查人员管理链（录用审查、培训考核、离岗收权）。
- **结果**: 人员五环节进入必测清单，与管理根因回溯互相支撑。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 组织"年年买安全产品仍频繁出事"，要找持续失效的根因。
2. 测评/咨询项目切入策略：先测管理五域定位根因，再定技术整改范围。
3. 事件复盘：技术整改项都关闭了，同类事件为何复发。
4. 安全预算答辩：论证"再堆产品无用，需先补管理"的决策依据。

### 语言信号 (用户的话里出现这些就应激活)

- "安全设备买了不少，为什么还是出事？"
- "技术整改都做了，同类问题为什么还在发生？"（整改无效信号）
- "root cause 是技术还是管理？从哪里查起？"
- "要不要再采购一套 XX 产品？"（应先问管理三路径查过没有）

### 与相邻 skill 的区分

- 与通用复盘法（5why/鱼骨图）的区别: 通用因果分析工具不限定路径；本 skill 给定安全域的**回溯路径集**（归口/职责/人员）与**触发信号**（技术整改无效），是领域特化。
- 与 `mlps-document-lifecycle-closed-loop`（文档闭环管理）的区别: 无归口是文档闭环断链的最深根因；后者核查单份/单域文档的时间证据，本 skill 定位"为什么整个闭环都建不起来"的组织原因。
- 与 `mlps-triple-consistency-check`（三重一致性核查）的区别: 三重一致性是取证技术（文档↔实地↔记录对不上即暴露）；本 skill 是诊断策略（从失效信号出发选哪里下钩）——先用本法定方向，再用取证技术落证据。

## E — 可执行步骤 (Execution)

1. **确认触发信号**：列出"技术整改无效"的证据（投入曲线 vs 事件曲线、已关闭整改项与复发事件的对照）。
   - 完成标准: 信号成立（技术到位而失效/复发），否则走常规技术排查。
   - 判停条件: 若技术整改本身未真正落地（配置空转、策略未生效）→ 先回 `mlps-control-effectiveness-four-checks` 四查验技术有效性，管理回溯暂缓。
2. **查制度归口**：有无授权部门统一负责安全制度？访谈多岗位对同一制度的说法是否一致；制度文本有无发布范围与收发文登记。
   - 完成标准: 归口结论（有/无/名存实亡）+ 依据。
3. **查职责闭合**：抽 1–2 个高风险流程（变更/应急/密钥操作）走责任链，记录推诿或真空点。
   - 完成标准: 流程责任链图，断点标注。
4. **查人员链**：培训考核记录与实际操作的对照（抽访一线人员），离岗收权样本核查。
   - 完成标准: 三路径各自的"根因嫌疑度"评级（高/中/低）。
5. **出诊断与预算重定向**：按嫌疑度排序管理根因；结论输出"管理补偿项优先于新增技术采购"的整改顺序。
   - 完成标准: 根因清单 + 管理整改项 + 技术预算建议（含"暂缓采购"项及理由）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单点技术缺陷（某防火墙规则错误、某漏洞未修）——直接技术定位，抬升到管理根因是过度归因。
- 尚未做过任何技术整改的组织——没有"技术无效"信号，管理归因缺乏对照。
- 纯技术选型问题（买 WAF 还是 IPS）——本 skill 只回答"该不该先补管理"，不选型。

### 作者在书中警告的失败模式

- 继续堆产品重复"作用不大"（ce32 的惯性路径）。
- 把管理根因当成万能解释——书中对标准本身不批判的盲点（阶段 0）提醒：有时"整改无效"的根因是控制项与业务现实不匹配，不是执行不力。
- 口头确认、无记录的管理动作不构成补偿证据（与 `mlps-personnel-lifecycle-controls`/v27 同源纪律）。

### 作者的盲点 / 时代局限

- **版本提示**：案例与立论基于等保 1.0 管理域（GB/T 22239—2008 第 10–12 章）；2.0 管理域扩展（如供应链、数据安全治理）后回溯路径应相应增列；DevOps/云环境下"归口部门"可能演化为平台团队+策略即代码，须重新定义归口的形态。
- 批判段盲点：全书立场是"管理补技术"，反向情形（过度管理拖垮技术响应，如变更审批迟滞致补丁拖延）书中未讨论——回溯时应对两个方向都保持开放。

### 容易混淆的邻近方法论

- governance framework（ISO 38500 类）：治理结构设计框架；本 skill 是失效诊断程序，从症状回溯，不设计治理。
- security culture 评估：度量组织安全文化成熟度；本 skill 不做文化度量，只沿三路径找结构性根因。
