# 访谈/检查/测试三法角色组合策略

## R — 原文 (Reading)

> 「现场测评以配置检查为基本方法，工具测试作为验证手段，访谈作为辅助手段，具体测评过程中测评工程师需根据项目实际情况灵活运用三种测评方法。」
>
> — 方法论出处，第8章 8.2（第6章 6.2、第9章 9.1、第10章 10.3 按对象层给出同构分工）

---

## I — 方法论骨架 (Interpretation)

三种取证方法不是"都用一点"的大杂烩，而是按对象层固定分派角色：

1. **三法的属性差异**：访谈最快但证据最弱（人的陈述）；检查零接入、不改系统状态、风险小（配置/文档/实地）；测试能拿到行为证据但要接入、可能改状态（受约束最多）。
2. **角色分派规则**：检查当"基本"（每个测评项的主证据来自它）、测试当"验证"（对关键声明做主动验证）、访谈当"辅助"（补背景、确认意图）。
3. **顺序也有讲究**：物理域"文档→现场→人"（先看文档带着问题进机房，再访谈补缺）；主机/应用域"配置检查→工具测试→访谈"。
4. **管理域的禁区**：制度、人员、机构类对象只用访谈+检查（文档审查/实地查看），不引入工具测试——管理对象没有可测试的技术状态。
5. **分配的底层逻辑**：对象层可见性（能不能直接查配置）× 测试副作用风险（改状态的成本）决定组合。这使方法选型可以外推到任何新对象类型：先问"这层看得见什么、动了会怎样"，再定角色。

## A1 — 书中的应用 (Past Application)

### 案例 1: 物理安全的"文档→现场→人"顺序
- **问题**: 机房测评对象杂（区域划分、消防、供电、监控），方法怎么排。
- **方法论的使用**: 第6章 6.2 规定实地查看为基本方法，文档审阅验证实地结果（设计验收文档、防雷检测报告、来访审批），访谈补无法现场获得的证据，推荐顺序"先审文档→实地查看→有疑问访谈机房管理员"。
- **结论**: 顺序设计让每种方法带着前一步的问题进场，证据互相咬合。
- **结果**: 该"文档→现场→人"三角顺序被作者明示可迁移到其他对象测评。

### 案例 2: 主机与应用的"检查基本、测试验证、访谈辅助"
- **问题**: OS/数据库/应用层技术状态可查可测，三法比例如何定。
- **方法论的使用**: 第8章 8.2 以配置检查为基本（Windows 图形界面、Linux 命令行与关键文件），工具测试验证身份鉴别、访问控制等关键项，访谈补剩余信息保护等难查项；第9章 9.1 应用层以文档审阅、配置检查、测试为主（应用逻辑不可直接观察，比主机更依赖文档）。
- **结论**: 对象层技术可见性越高，检查与测试占比越大。
- **结果**: 全书技术篇各章测评实施表都按此角色分派写取证步骤，方案评审有章可循。

### 案例 3: 管理域禁用工具测试
- **问题**: 管理类对象（制度、人员）能不能也用工具"测"。
- **方法论的使用**: 第10章 10.3 明确管理现场测评只用访谈+检查（检查再分文档审查与实地查看），依据 GB/T 28449《测评过程指南》。
- **结论**: 方法集合的差异是技术测评与管理测评的根本分工点——管理对象无技术状态可测。
- **结果**: 管理五域所有测评项的方法栏只出现访谈/文档审查/实地查看三种，工具测试不进入管理域。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为新型对象（Serverless、Service Mesh、数据湖、SaaS 租户面）设计测评/审计方案，不知道访谈/检查/测试怎么配。
2. 测评方案评审时被问"为什么这项只用访谈"或"为什么必须上工具测试"。
3. 管理域检查被建议用自动化工具"扫"出结论，需要判断合理性。
4. 团队新手把访谈当主要证据来源，需要纠正方法组合。
5. 面对不可中断的生产系统，需要论证"以检查为主、测试最小化"的方案。

### 语言信号 (用户的话里出现这些就应激活)

- "测评方法怎么选？""这三项（访谈/检查/测试）怎么搭配？"
- "这项能不能不用工具测？""光查配置够吗？"
- "管理制度怎么测？也要上工具吗？"
- "帮我设计取证方案/测评实施方案"
- 英文: "assessment methodology"、"evidence collection plan"、"interview vs inspection vs testing"、"can we skip tool testing"

### 与相邻 skill 的区分

- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 本 skill 决定"收集什么类型的证据"（方案设计）；后者决定"收集到的证据谁说了算"（结果裁决）。
- 与 `mlps-intrusive-test-downgrade`（降级权衡与豁免）的区别: 本 skill 是常态下的角色分派；后者处理例外——测试做不了时如何降级替代与豁免。
- 与 `mlps-tool-test-typology`（工具测试类型学）的区别: 后者在"决定要用测试"之后选哪类工具、匹配哪种证据形态；本 skill 在更上游决定要不要、占什么角色。

## E — 可执行步骤 (Execution)

1. **给被测对象分层**
   - 完成标准: 已把测评范围按对象类型分层（物理/网络/主机/应用/数据/管理域），每层标注"技术状态可见性"（可直接查配置？）与"测试副作用风险"（动了会怎样？）。
2. **逐层分派三法角色**
   - 完成标准: 每层明确谁是基本证据、谁是验证、谁是辅助；管理域只出现访谈+检查；技术层每项至少有一个非访谈证据来源。
3. **排方法顺序**
   - 完成标准: 每层写了执行顺序（如文档→现场→人；配置→测试→访谈），顺序让后一步带着前一步的问题进场。
4. **标注测试的约束条件**
   - 完成标准: 凡安排工具测试的项，已标注授权、备份、时段等前置约束（衔接 `mlps-assessment-redlines` 红线），无约束安排即方案缺陷。
   - 判停条件: 若对象层完全不可见（如纯 SaaS 黑盒），测试降级为"供应商声明+可执行的黑盒验证"，方案中显式写出替代路径。
5. **输出方法矩阵并评审**
   - 完成标准: 测评项 × 方法的矩阵成表，每格有角色标注；被评审方确认"仅靠访谈判符合"的项为零（除纯主观项）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 证据已收齐只待裁决——那是 `mlps-preponderant-evidence` 的场景，方法组合帮不上忙。
- 攻击性安全测试（红队）目标设定——红队以测试为主、绕开检查，与本 skill 的合规取证语境不同。
- 一次性快速尽调（时间只够访谈）——本 skill 会告诉你这属于证据不足，要挂"进一步跟踪"，而不是教你压缩方法。

### 作者在书中警告的失败模式

- 全靠问卷/访谈取证：证据最弱、回收最慢，方案过度依赖单一弱取证方式即为质量缺陷（ce02）。
- 仅靠访谈描述功能存在就判符合（第9章 9.1）。
- 给管理对象硬上工具测试——方法与对象错配，产生伪客观证据。

### 作者的盲点 / 时代局限

- 三法角色框架出自等保 1.0 测评实务（GB/T 28448/28449—2012），对云原生/无服务器等新架构需要重新映射"检查"的落点（函数环境变量、IAM 策略、日志配置成为新的"配置检查面"），但分配逻辑（可见性×副作用）不过时。
- 阶段 0 批判：全书对测试的约束偏保守（可被豁免、被检查替代），动态验证最弱——外推到高对抗场景应适当提高测试/主动验证占比（衔接 `mlps-active-verification-perturbation`）。

### 容易混淆的邻近方法论

- 三法组合 vs "工具越多越好"：测试占比由对象层决定，不是证据强度的单调函数——管理域加工具不会更好。
- 检查 vs 测试的证据地位：本 skill 让检查当基本、测试当验证，但证据裁决时（`mlps-preponderant-evidence`）测试结果强于检查——"方案角色"与"证据强度"是两个维度，勿混。
