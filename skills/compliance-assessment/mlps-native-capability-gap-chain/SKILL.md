# 原生能力缺口判定链（缺口→补偿→否则不符合）

## R — 原文 (Reading)

> "天清汉马防火墙设备不支持两种或两种以上组合鉴别技术来进行身份鉴别，在现场
> 测评中，大部分安全设备本身均不支持，一般通过认证平台的方式实现；"
> "测评中常见的Windows、Linux等系统均未达到安全标记级别，所以需采用第三方工具进行安全加固。……如未采用，本要求项为不符合。"
>
> — 原作者 等，原始方法论来源第7章 7.3.3 + 第8章 8.3.1（source.txt L3757–3759、L4287–4295，OCR"CB17859"噪声保留）

## I — 方法论骨架 (Interpretation)

高等级安全指标常超出产品的出厂能力：Windows 做不了组合鉴别，Linux 默认没有强制访问控制，WebLogic 不出审计报表。测评者面对的不是"有没有做"，而是一条固定裁决链：

1. **判原生边界**：该产品/平台的默认能力到哪一层？够不够指标？这一步要依据实测配置，不听"支持 XX"的宣传。
2. **查补偿链**：原生不够时，补偿组件（堡垒机、认证平台、MAC 工具、第三方审计系统）是否真实部署、配置生效？取证对象从被测系统转向补偿设施。
3. **缺即不符合**：连补偿都没有，判不符合。行业普遍空白不减免——"大家都没有"只是说明该项是高概率失分项，不是豁免理由。

这条链的实用价值是**可预判**：能力缺口是产品 defaults 的函数，可在进场前列出"三级系统高概率不符合清单"（组合鉴别、敏感标记、入侵检测、审计报表、单用户资源限额、剩余信息清理一族），把有限测评时间优先花在这些项上。

## A1 — 书中的应用 (Past Application)

### 案例 1: 安全设备组合鉴别（第7章 7.3.3，cs008/ce16）
- **问题**: 三级要求网络设备双因素鉴别，实测天清汉马防火墙不支持，怎么办？
- **方法论的使用**: 走链——原生不支持（访谈+配置确认）→ 查 Radius/堡垒机认证平台是否部署并在其上实现组合鉴别 → 都没有则不符合。
- **结论**: 大部分安全设备本身均不支持，认证平台是通行补偿；无平台即不符合。
- **结果**: 形成判定模板"设备能力缺口→通用补偿控制→连平台也没有则不符合"，并在 SQLServer、WebLogic 段复用。

### 案例 2: Windows 五处同构原生缺口（第8章 8.3.1，ce17–ce22）
- **问题**: Windows 主机面对三级指标有哪些系统性缺口？
- **方法论的使用**: 同一判定链扫过组合鉴别、敏感标记、入侵检测、审计报表、单用户资源限额五项，逐项给出补偿路径（堡垒机、第三方加固工具、HIDS、日志平台、资源限制工具）。
- **结论**: 五处均为"原生不足→第三方→缺即不符合"的同构形态。
- **结果**: Windows 测评项的取证重心整体转向第三方组件的部署与生效证据。

### 案例 3: 剩余信息不清理不因"行业普遍"放行（第9章 9.3.1，pr042/ce29）
- **问题**: "通常情况下，应用系统在用户退出后不会对内存残留数据清理"——普遍现状能否从宽？
- **方法论的使用**: 判定链不看普及率：未提供清除功能即不符合，第三方工具补偿须访谈+检查双证据。
- **结论**: "行业普遍不清理"不构成放低标准的理由。
- **结果**: 该项成为应用层预置的高概率不符合项，测评前即可列入清单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 三级等保测评进场前预判高概率不符合项，规划取证优先级。
2. 容器平台/云 PaaS 面对强制访问控制、审计报表类指标，需判断默认 seccomp/AppArmor/内置日志够不够、缺什么补偿。
3. 采购评审：厂商宣称"平台支持 XX 能力"，需区分宣传能力、默认状态与实际生效配置。
4. 整改方案设计：按判定链确定"补什么第三方组件"才能把不符合项翻盘。

### 语言信号 (用户的话里出现这些就应激活)

- "Windows/这个产品本身做不到 XXX，怎么判？"
- "全行业都没部署这个，也判不符合吗？"
- "厂商说支持强制访问控制/双因素，可信吗？capability vs default？"
- "三级系统哪些项基本都不符合？"（预判清单诉求）

### 与相邻 skill 的区分

- 与 `mlps-control-effectiveness-four-checks`（控制有效性四查）的区别: 后者裁决"能力存在但层级/覆盖/生效不够"；本 skill 裁决"原生能力根本达不到→须第三方补偿→缺即不符合"——一个问灵不灵，本链问有没有。
- 与 `mlps-audit-six-dimension-assessment`（审计六维框架）的区别: 后者是审计能力的六维拆解；本链是其中"原生报表缺失→第三方日志平台补偿"这类缺口的通用裁决程序。
- 与 `mlps-auth-transport-plaintext-veto`（明文一票否决）的区别: 后者处理"能力存在但默认关"（启用开关即可达标）；本链处理"原生就没有"（必须外购补偿）——判定动作不同。

## E — 可执行步骤 (Execution)

1. **列出指标并判原生边界**：写出指标要求，检索被测产品/平台的默认能力（配置实测为准），标注"原生可达 / 原生不可达"。
   - 完成标准: 每个指标有原生能力结论 + 依据（配置输出/官方默认文档），不以宣传页为据。
2. **对原生不可达项查补偿链**：确认补偿组件名称、部署位置、生效配置三要素。
   - 完成标准: 补偿组件的配置证据到手（不是"已购买"而是"已启用"）。
   - 判停条件: 若无法获得任何补偿证据 → 直接判不符合，记录"无补偿"，进入下一指标。
3. **验证补偿是否覆盖指标语义**：补偿组件提供的能力层级须等于指标要求（如平台组合鉴别须覆盖该设备的登录路径），低于要求的仍为缺口。
   - 完成标准: 逐项标注"补偿等效 / 补偿不足"。
4. **汇总裁决与预判清单**：输出不符合项清单及缺失的补偿组件；把"该平台+该等级"的系统性缺口整理为可复用的高概率不符合预判表。
   - 完成标准: 清单含指标号、缺口原因、建议补偿组件三列，可作为整改方案输入。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 原生能力可达标（产品支持且配置可启用）——走普通取证+四查即可，不需要补偿链。
- 低等级系统（一级/二级）指标本就低于产品默认——多数项默认即符合，硬套判定链浪费工时。
- 管理类指标（制度、培训）——无产品能力语义。

### 作者在书中警告的失败模式

- 被"产品支持 XX"宣传说服，未验证默认状态与生效配置（cs008 信号）。
- "大家都没有"从宽判定——pr042/ce29 明确行业普遍不清理仍判不符合。
- 补偿链只查"已部署"不查"已生效"——平台存在但该设备未接入，补偿不成立。

### 作者的盲点 / 时代局限

- **版本提示**：判定链所依附的条款（组合鉴别、敏感标记等）属等保 1.0 三级（GB/T 22239—2008）；2.0（2019）改为"安全计算环境"框架且新增云/移动/物联/工控扩展要求，指标清单须按现行标准重建，但"原生缺口→补偿→否则不符合"的裁决结构不变。
- 书中对"标准要求 vs 产品现实"的系统性落差（如安全标记级"常见系统均未达"）处理方式仍是"第三方加固否则不符合"，未追问该要求在小规模场景的现实性——阶段 0 批判指出的"对标准不作批判"盲点。

### 容易混淆的邻近方法论

- hardening guide（加固指南）：给出把默认配置改到位的步骤；本链裁决的是改不到位的部分该买什么、买不到怎么判。
- compensating control（NIST 概念）：任何替代性控制都算补偿；本链要求补偿能力层级与指标等效，且把"缺补偿"直接收敛为不符合档。
