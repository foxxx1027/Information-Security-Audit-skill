# 制度体系四层金字塔自查

## R — 原文 (Reading)

> "信息安全管理体系（ISMS）通常由总体安全方针和策略、信息安全相关的规章制度、日
> 常行为的操作规程以及记录类文档（运行记录、表单、工单等）构成的四层金字塔体系。信
> 息安全方针和安全策略是组织信息安全工作的纲领性文件，是组织进行有效安全管理的基
> 础和依据。"
>
> — 原作者 等，原始方法论来源第10章 10.4.1 安全管理制度（source.txt L7689–7693）

## I — 方法论骨架 (Interpretation)

一个组织"有没有管理制度"不是一个是/否问题——制度是由四层文件叠成的金字塔，每层回答不同的问题：

- **方针层**（一级）：纲领——为什么管、管到什么程度。一页纸即可，但缺了就没有授权源头。
- **制度层**（二级）：各安全域的规章制度——管什么、谁负责。
- **规程层**（三级）：操作手册、流程图、表单——具体怎么做。制度不落规程，执行者只能自由发挥。
- **记录层**（四级）：运行记录、表单、工单——做过的证据。没有记录，前三层全部不可验证。

两个用法：**判定**用自上而下——四层齐全判强；有方针无规程、有制度无记录各判弱档（"缺任何一层都能在测评中暴露"）。**自查**用自下而上——先翻记录（有没有在做），再对规程（做得对不对），最后看制度与方针（是否成文授权）。自下而上是经验结论：小组织最常缺的不是高冷的方针，而是最底下的记录层——"制度有而记录无"是运维域高发形态。

对小规模组织的口径：可以因规模小简化各层的繁简（方针一页纸、规程只覆盖关键操作），**不可以缺失任何一层的闭环**——"规模小"不是豁免理由。

## A1 — 书中的应用 (Past Application)

### 案例 1: 案例判定按四层完整性分档（第10章 10.4.1，fw66）
- **问题**: 管理制度大类案例的符合/不符合怎么给？
- **方法论的使用**: 每个组织情形按四层齐全度判：四层齐=符合；有方针缺规程或制度=弱档；全无=不符合。
- **结论**: 判定锚点是结构完整性而非文字质量。
- **结果**: 第10章各案例表按此分档，金字塔成为判定的坐标系。

### 案例 2: 小分公司逐层定位三层缺口（第10章 评审和修订案例，ce33）
- **问题**: 规模较小的分公司体系不全，缺口在哪、怎么描述？
- **方法论的使用**: 按金字塔逐层定位——缺纲领性文件（一层）、部分制度规程不完善（二三层）、记录类文档不够完善（四层），且评审修订未规范化（闭环断裂）。
- **结论**: 小组织把"规模小"当豁免，实际只可简化流程、不可缺失闭环。
- **结果**: 缺口被精确定位到层，整改可逐层下单。

### 案例 3: 运维域"制度有而记录无"（第12章，tm048）
- **问题**: 哪一层是运维管理的高发缺口？
- **方法论的使用**: 运维各控制点（环境/介质/恶意代码/变更/备份）普遍有制度文本、缺执行记录。
- **结论**: 第四层记录是稽查重点，金字塔顶层齐不能代表底层实。
- **结果**: 运维测评的取证重心落到过程类记录上。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 组织安全制度自查/迎检准备：快速定位体系缺口在哪一层。
2. 等保/ISMS 管理类测评：按层组织取证与判定。
3. 创业公司/小团队建制度：决定每层做多薄、哪些不能省。
4. 接手安全职能：用金字塔盘点前任留下的体系家底。

### 语言信号 (用户的话里出现这些就应激活)

- "安全制度体系要建哪些文档？从哪儿建起？"
- "我们公司小，制度可以简化到什么程度？"
- "policy / procedure / record 怎么分？有制度没记录算什么问题？"
- "管理测评都查什么文档？"（按层列取证清单）

### 与相邻 skill 的区分

- 与 `mlps-document-lifecycle-closed-loop`（文档闭环管理）的区别: 后者查单份/单域制度文档的**时间维**（制定→评审→修订是否还在运营）；本 skill 查体系的**结构维**（四层是否齐全）。结构完整但停止更新的体系用后者判，缺层的体系用本 skill 定位。
- 与 `mlps-triple-consistency-check`（三重一致性核查）的区别: 金字塔描述"该有哪些层"；三重一致性验证"层与层之间对不对得上"（文档↔实地↔记录）。结构是三重一致性的载体。
- 与 ISO 27001 文件层次（四层级文件惯例）的区别: 分层定义属 ISO 惯例；本 skill 的录取点是**判定用法与自下而上自查路径**，不是分层定义本身。

## E — 可执行步骤 (Execution)

1. **盘点四层现存文件**：列出组织的方针、制度、规程、记录四类文件清单（真实的，不是目录里该有的）。
   - 完成标准: 四层各有实际文件清单；某层为空即显性缺口。
2. **自下而上质检**：从记录层往上——抽查记录是否覆盖关键操作、规程是否指导了这些操作、制度是否授权了规程、方针是否统领制度。
   - 完成标准: 每层给出"覆盖/部分/缺失"结论 + 断层位置（记录无对应规程、规程无制度依据都记断层）。
   - 判停条件: 若记录层完全为空 → 直接判"体系未运行"，上面三层只需速查授权链，不必逐项精查。
3. **按层判档**：四层齐且互相对应=符合；缺规程或记录=部分符合（写明缺口层）；缺方针或制度=不符合方向。
   - 完成标准: 判定注明缺失层与断层描述。
4. **出分层整改清单**：按"记录→规程→制度→方针"顺序补（自下而上建立可运行性），每层给出该组织规模下的最小厚度建议。
   - 完成标准: 整改清单含层、动作、最小可用形态三列。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 制度内容质量评审（条款是否科学、控制点是否够）——金字塔只判结构完整，不评内容好坏。
- 单个技术控制点核查（防火墙策略、口令）——那是技术域取证。
- 非安全类管理体系（质量、环境）——结构同构但域内容不同，套用时须换域。

### 作者在书中警告的失败模式

- 小微组织以"规模小"豁免闭环——ce33 明确只可简化不可缺失。
- "制度有而记录无"的运维高发形态——顶层文件齐全制造的虚假安全感（tm048）。
- 缺纲领性文件直接判不符合档——无授权源头，下层文件合法性存疑。

### 作者的盲点 / 时代局限

- **版本提示**：四层结构表述基于等保 1.0 管理要求（GB/T 22239—2008 第 10–12 章）与 ISO/IEC 27001:2005 语境；2.0 与 27001:2013/2022 下层级惯例未变，但各层应覆盖的域（如云供应链、数据安全域）须按现行要求扩充。
- 层间"数量配比"无指引：多少条制度配多少规程算合理，书中无口径——自查者需自行防过度文件化（阶段 0 批判的"臃肿体系"风险）。

### 容易混淆的邻近方法论

- 文档分级（秘密级/公开级）：按**保密属性**分级；金字塔按**职能层次**分层——同一份文件两个坐标。
- policy hierarchy in cloud（组织 SCP→OU→账号策略）：权限继承链；本 skill 是管理制度文件链，对象不同。
