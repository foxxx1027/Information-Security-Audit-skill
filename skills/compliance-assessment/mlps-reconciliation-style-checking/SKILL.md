# 对账式核查法（外部基准 × 不可变主键 × 差集）

## R — 原文 (Reading)

> "要依据系统管理员提供的用户列表对系统中的用户进行核对，确认是否存在共享账户，用
> 户列表中需包含账户实际使用人。"
> "用户的UID不相同且唯一，是Linux中用户的身份标识。因
> 此，可以通过查看用户UID的方法来检验用户的唯一性和是否重复。"
>
> — 原作者 等，原始方法论来源第8章 8.3.1 Windows 访问控制 + 8.3.2 Linux 身份鉴别（source.txt L4078–4081、L5156–5159）

## I — 方法论骨架 (Interpretation)

"查一下有没有多余账号"是句空话——对什么查？拿什么判多余？对账式核查把这件事程序化为三个要素：

1. **基准来自系统之外**。身份域的基准是管理员提供的用户列表（且必须标注"实际使用人"——没有使用人的账号无法问责，共享账号=责任不可追溯）；服务域的基准是安全策略配置文档定义的"应有服务/端口清单"。基准若取自系统本身，管理员可以先改系统再"对上"，对账失效。
2. **用不可变主键核对**。用户名可重复、可改名，UID/唯一 ID 才是身份锚点——Linux 用 UID 查重，云 IAM 用唯一 ID 而非 display name。重名账户靠主键暴露。
3. **做差集，超集即不符合**。系统实测减去基准应有：多出来的是多余/幽灵/共享账号、多余服务与监听端口（netstat -an 对照策略文档）；基准里有而系统没有的，则提示过期未清理或清单失真。

默认账户是差集里的特殊族：安装即建 + 高权限 + 名称公开可枚举（sa、weblogic/system、Administrator/Guest、Oracle 默认账户），处置固定为改名/禁用/EXPIRED&LOCKED——它们是暴力破解的首要目标。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三平台身份域对账（第8章，fw58/cs010/cs017/cs023）
- **问题**: Windows/Linux/SQLServer 的账号唯一性与共享账户怎么查？
- **方法论的使用**: 以管理员提供的用户列表（含实际使用人）核对系统账户；Linux 用 UID 而非用户名查重复与共享；SQLServer 用 `select name from syslogins` 导出全量再对。
- **结论**: 共享/重名/过期账户在对账差集中显形。
- **结果**: 三平台复用同一程序，成为跨平台标准核查法。

### 案例 2: 服务域应有面比对（第8章 8.3.1，fw51）
- **问题**: "仅安装需要的组件和服务"怎么落地成检查？
- **方法论的使用**: `netstat -an` 列监听端口，逐一对照安全策略配置文档的应有面；超出应有面的端口即多余服务线索，再追到服务清单与补丁状态。
- **结论**: 最小化判定的锚点是策略文档，不是"看着顺眼"。
- **结果**: 最小服务检查从主观印象变成差集运算。

### 案例 3: 默认账户收敛（第8/9章，cs012/ce26/pr053）
- **问题**: sa、weblogic、Administrator 等默认账户为什么必查、怎么处置？
- **方法论的使用**: 风险三要素（默认存在+高权限+名称可枚举）识别为暴力破解首要目标；处置=改名/禁用/EXPIRED&LOCKED。
- **结论**: 默认凭据消除攻击成本，属"默认身份收敛"类控制的反面。
- **结果**: 各平台检查表均内置默认账户项（sa 状态、WebLogic 四账号、Guest 禁用）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审的身份鉴别与访问控制核查：共享账号、过期账号、默认账户逐项查。
2. 云上 IAM 治理：以人事清单核对 IAM 用户/角色/服务账号/长期令牌，查幽灵账号与供应商内置角色。
3. 最小化审查：服务器/K8s 节点的监听端口、运行服务、镜像内进程对照应有清单做差集。
4. 接管遗留系统：无文档时先建外部基准（人事+业务清单）再做首轮对账。

- "多余服务/端口怎么判定多余？least service/最小化怎么核查？"

### 与相邻 skill 的区分

- 与 `mlps-separation-of-duties-dual-axis`（职责分离双轴）的区别: 后者查"一人是否兼任互斥角色"（人→角色的求交集）；本 skill 查"账号是否与真实使用人对应、服务是否超应有面"（账→人/策略的求差集）。
- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 对账结果是检查类强证据；后者规定它与访谈矛盾时如何裁决。
- 与 `mlps-risk-assessment-six-steps`（风险评估六步法）的资产清查步的区别: 资产清查面向 CIA 赋值；本 skill 面向账号/服务的合规差集，两者输入可互用但目标不同。

## E — 可执行步骤 (Execution)

1. **建外部基准**：向管理员索取用户列表（强制含"实际使用人"列）与安全策略文档（应有服务/端口清单）；拒给或给不出 → 记"基准缺失"，按进一步跟踪处理。
   - 完成标准: 两份基准文件到手且字段齐全；实际使用人列无空值（空值本身即缺陷）。
2. **导出系统实测**：身份域（账户列表+UID/唯一ID+状态）、服务域（监听端口/服务清单），保留命令输出作为证据。
   - 完成标准: 实测导出与基准同格式，可直接比对。
3. **做双向差集**：系统−基准 = 多余项（共享/幽灵/默认账户、多余服务端口）；基准−系统 = 清单失真项（该有没有/已离职仍在单）。默认账户单列。
   - 完成标准: 差集逐条列出；默认账户族有专门处置标注（改名/禁用/锁定）。
   - 判停条件: 若基准本身不可信（如用户列表明显落后于人事变动）→ 停止判定，先要求重建基准，输出"基准失效"结论。
4. **裁决与整改**：多余项按档位判（默认/共享高权账号通常不符合），整改指向"每账号一实际使用人、最小服务面、默认账户收敛"。
   - 完成标准: 差集每条有判定与整改责任人方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 无任何外部基准可用且无法重建（无人事、无策略文档）——对账无从做起，应先走制度整改而非硬判。
- 权限体系设计评审（角色粒度是否合理、RBAC 模型好坏）——对账只查"账实相符"，不评设计优劣。
- 一次性渗透前的攻击面枚举——目标不同，差集判据（策略文档）在攻击视角不存在。

### 作者在书中警告的失败模式

- 以系统自身导出充当基准（管理员自查自证）——防作弊要点即基准外置（V2 推论）。
- sa 仍启用、口令未按策略强制、用户列表未对应实际使用人（ce26 信号三联）。
- Linux 默认账户（UID<500）一刀切改名——书中承认指标与工程惯例有张力：系统默认账户改名可能导致功能失效，可行折中是限制其文件访问权限+禁用闲置账户（ce24）。

### 作者的盲点 / 时代局限

- **版本提示**：检查命令与平台（RHEL6 passwd/shadow、SQLServer 2008、WebLogic 10）属等保 1.0 时代产物，2.0 场景下应对云 IAM、服务账号、机器身份重做映射；"外部基准×不可变主键×差集"的程序结构不变。
- 未覆盖非人类身份爆炸（API key、CI 机器人、工作负载身份）的治理——现代云环境对账面须从"人"扩到"人与非人"。

### 容易混淆的邻近方法论

- IAM 审计工具的"未使用密钥检测"：只覆盖时间维度闲置；本 skill 强调基准外置与主键不可变，覆盖账实对应关系。
- 配置管理（desired state）：以模板收敛状态；本 skill 以外部事实（人事/策略）裁决现状合法性，基准性质不同。
