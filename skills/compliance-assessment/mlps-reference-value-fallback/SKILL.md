# 标准留白参考值兜底法

## R — 原文 (Reading)

> "测评
> 标准中未对测评指标进行具体要求，在测评实施过程中，建议各个配置项的参考值如表8-
> 3所示。"
> （表8-2 密码策略配置参考值：密码长度最小值≥8位；密码最长使用期限≥90天；强制密码历史≥5次）
>
> — 原作者 等，原始方法论来源第8章 8.3.1 Windows 身份鉴别（source.txt L3986–3988、表8-2 L3964–3984 摘录）

## I — 方法论骨架 (Interpretation)

标准常写"应对口令复杂度提出要求"却不说多长多久——测评者对着定性条款无法落笔。兜底法分三步处理这个"最后一公里"：

1. **确认留白**：查标准原文，确认该指标确实无参数。标准有的，直接用标准，不走兜底。
2. **建参考值表**：为每个无参指标给出建议基线（口令≥8 位/90 天/历史 5 次；锁定 30 分钟内 5 次失败锁 30 分钟；会话超时≤10min；CPU 5min 利用率<60%——后者还须高峰采样）。参考值是**建议**不是红线，作用是让"逐项比对记录实际值"成为可能。
3. **结合策略文档判定**：被测方自己的策略文档若给了合理参数（且现场配置符合其策略），按其策略判——参考值只作风险提示；完全无策略文档、无配置，则不符合。

最重要的纪律是**同表声明性质**：参考值无标准出处、是编写组经验值。不声明就会发生性质漂移——建议值被下游当成强制红线，测评变成"拿我们的习惯罚人"。判定记录里要写清"依据=被测方策略 or 参考值提示"，让结论可复核。

## A1 — 书中的应用 (Past Application)

### 案例 1: 主机口令/锁定/审核九项参考值表（第8章，表8-2/8-3/8-4 等，fw49）
- **问题**: Windows/Linux 口令与锁定策略标准无参数，怎么逐项判？
- **方法论的使用**: 表8-2/8-3 给密码策略与账户锁定参考值，逐项比对实际配置值记录差异。
- **结论**: 留白→参考值基线→逐项比对，测评从"凭感觉"变成"对表打分"。
- **结果**: 第8章十余张参考值表覆盖主机主要配置项，形成体系化落地。

### 案例 2: 物理环境量化判据（第6章，pr018/pr019）
- **问题**: "机房应位于建筑物内高层""温湿度适宜"如何判？
- **方法论的使用**: 建量化判据——高层=总楼层 2/3 以上、温湿度 20~22℃/40%~70%。
- **结论**: 物理项同样可用参考值摆脱主观判定。
- **结果**: 机房测评记录可写出具体数值依据。

### 案例 3: 会话超时的平台语境区分（第7/9章，pr021/pr048/cs020）
- **问题**: 超时≤10min 的参考值在不同平台怎么用？
- **方法论的使用**: 网络设备会话超时≤10min；WebLogic 闲置超时默认 1 小时须按策略收紧；Linux 取 TIMEOUT=180s——引用参考值须区分平台语境，不能一个数打天下。
- **结论**: 参考值表要带"平台/语境"列。
- **结果**: CPU 5min<60% 还标注"须高峰采样"，避免低谷期采样得出假符合。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审测评遇到无参数指标（口令、超时、阈值、频次），要写出可复核的判定依据。
2. 组织自建安全基线（configuration baseline）：为定性要求定量化锚点。
3. 新技术场景（容器镜像漏洞修复时限、密钥轮换周期）标准尚未规定，需建表兜底。
4. 评审他人报告：发现"依据不足"的判定，检查是否缺参考值声明。

### 语言信号 (用户的话里出现这些就应激活)

- "标准只说要有要求，没说多少，怎么判？"
- "口令长度/超时时间你们按什么标准判？baseline 参考值哪来的？"
- "这个阈值有没有依据？能不能这么定？"
- "被测方自己定的策略和参考值不一样，听谁的？"

### 与相邻 skill 的区分

- 与 `mlps-indicator-selection-rules`（指标确定规则集）的区别: 后者决定"用哪套指标"；本 skill 解决"选定的指标没有参数怎么判"——发生在指标确定之后。
- 与 CIS benchmark 直接套用的区别: CIS 是别人做好的参考值表；本 skill 是**建表的方法与纪律**（含性质声明与策略优先），可用于任何无现成 benchmark 的场景。
- 与 `mlps-verdict-tiers`（判定档位体系）的区别: 本 skill 产出比对结果，落"符合/部分符合/不符合"哪一档由后者的档位纪律承接。

## E — 可执行步骤 (Execution)

1. **确认留白**：逐条查指标原文，标注"有参数（引用之）/无参数（入兜底流程）"。
   - 完成标准: 指标清单带参数状态列；有参数的不进下一步。
2. **建参考值表**：每个无参指标给出建议值 + 适用语境（平台/采样条件），表头声明"参考值=建议基线，无标准出处，编写组/本方经验值"。
   - 完成标准: 表含指标、参考值、语境、性质声明四要素；无法给出建议的标"待商定"而非硬造。
3. **取被测方策略文档**：索取其安全策略中对应参数；无策略文档本身就是缺陷（记录之）。
   - 完成标准: 每项有"策略值/无策略"标注。
   - 判停条件: 若被测方策略值明显低于常识安全下限（如口令 4 位永久有效）→ 不宜直接按其策略判符合，记风险提示并上升人工裁量。
4. **逐项比对并判定**：现场配置 ≥ 策略值=符合；符合参考值但无策略=符合+风险提示（或部分符合，视档位纪律）；两者皆无=不符合。
   - 完成标准: 每项判定含依据来源标注（标准/策略/参考值），可复核。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 标准已给明确参数的指标——直接引用标准，建参考值反而降级依据。
- 合同/行业细则已有量化要求——依据优先级：法规>合同/行业>被测方策略>参考值，参考值永远垫底。
- 攻击面评估中的阈值推演（如何时算暴力破解）——分析参数，不是合规判据。

### 作者在书中警告的失败模式

- 把参考值当强制红线用——性质漂移是本方法的最大风险，须同表声明（V2 推论的核心）。
- 低谷期采样 CPU 利用率得出假符合——参考值自带采样条件（高峰 5 分钟），条件不可省。
- 平台语境混淆：Windows 10min 与 Linux TIMEOUT=180s 混用一套数。

### 作者的盲点 / 时代局限

- **版本提示**：书中具体参考值（≥8 位/90 天/5 次锁定 30min、CPU<60%、20~22℃）成书于 2016、基于等保 1.0 语境，且**均无标准出处标注**——阶段 0 批判点名"建议参考值缺乏出处，实为编写组经验值"。2.0 时代部分值已被行业指南超越（口令长度走向 12+、轮换策略有争议），引用须复核现行依据。
- 参考值的适用规模未分级：同一锁定阈值对 10 人公司与万人机构的外部攻击面完全不同，书中未讨论分级。

### 容易混淆的邻近方法论

- CIS/DISA STIG 基线：权威预制参考值；本 skill 是自制参考值时的程序与纪律，权威基线可用时应优先引用并注明版本。
- risk-based threshold setting（按风险算阈值）：从威胁建模推参数；本 skill 不做风险推演，只做"经验值+策略优先"的合规兜底。
