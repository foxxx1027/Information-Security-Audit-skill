# 测评结论时效边界与变更重测触发

## R — 原文 (Reading)

> 「本报告中给出的测评结论仅对被测信息系统当时的安全状态有效。当测评工作完成后，由于信息系统发生变更而涉及的系统构成组件（或子系统）都应重新进行等级测评，本报告不再适用。」
>
> — 原作者 等，附录A（测评报告声明）；第12章收尾落款语境

---

## I — 方法论骨架 (Interpretation)

一份测评报告的效力不是无限期的，它被四条边界精确限定：

1. **时点有效**：结论只描述测评当时的状态——系统是活的，报告是照片。
2. **变更即失效（组件级）**：测评后系统发生变更且涉及构成组件（或子系统）的，该部分必须重新测评，原报告对它不再适用；判定标准是"是否动了系统构成组件"，不是"变更大不大"的感觉。
3. **系统过测 ≠ 产品过测**：结论是对系统的，不构成对系统内部署产品的认证——别拿系统报告当产品合格证。
4. **引用约束**：引用报告不得增、改、伪造或掩盖事实——断章取义的引用本身违规。
5. **双触发重测**：周期轨（三级年测、四级半年测等法定频次）+ 事件轨（变更、级别变化强制重测）——等保合规是持续验证，不是一次性拿证。
6. **对高频发布的推论**：每两周一次 CI/CD 发布的环境里，"一次测评一张证"模式失效——常规业务发布不必然整体失效，但架构、安全组件、等级要素变更必须触发重测；可持续安排是"基线测评 + 变更触发增量测评"，且报告须披露发布频率与适用边界。

## A1 — 书中的应用 (Past Application)

### 案例 1: 报告声明的四条边界
- **问题**: 报告出具后，机构与被测单位各自的责任边界在哪里。
- **方法论的使用**: 附录A 报告声明固定四条——结论建立在被测评单位提供证据真实的基础上；仅对当时状态有效、变更组件须重测；不构成对产品的测评结论；引用须保持原意；落款盖章。
- **结论**: 四条边界 + 盖章是报告效力的完整定义——超出边界的任何使用（拿旧报告覆盖新系统、当产品认证）都无效。
- **结果**: 该声明成为报告模板固定件，出报告机构的免责与使用者的义务两边说清。

### 案例 2: 变更重测落进建设管理指标
- **问题**: "变更要重测"如何被核查而不是靠自觉。
- **方法论的使用**: 第11章 11.4.10 等级测评控制点四指标——至少每年一次等级测评并及时整改；系统变更或级别变化是强制重测触发器；选有资质测评单位；专人负责测评管理。
- **结论**: 重测义务是指标化的，"重大变更未重测"可直接判不符合；查证方法是看前一次测评报告 + 整改记录 + 变更记录的交叉。
- **结果**: 周期轨与事件轨在指标侧合流，形成"该测未测"的判定依据。

### 案例 3: 高频发布场景的失效判定
- **问题**: 业务系统每两周经 CI/CD 发布一次，报告多久失效。
- **方法论的使用**（本 skill 的 V2 推演，锚定"系统构成组件"判定标准）: 架构、安全组件（网关/认证/数据存储）、等级要素变更→触发重测，报告对该部分失效；常规业务发布不必然整体失效，但报告须披露发布频率与适用边界。
- **结论**: 一次测评一张证的模式在高频发布下失效，应改为基线测评+变更触发增量测评。
- **结果**: 报告有效期问题从"日期游戏"转化为"变更分类 + 覆盖范围声明"的可操作判定。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿一份一年多前的测评报告去投标/续证/应对检查，不确定还有没有效。
2. 系统刚完成大改造（换网关、迁移上云、升级核心中间件），问报告是否作废。
3. 并购/供应商审查中评估对方报告的时效与覆盖面。
4. CI/CD 高频发布的团队被要求"持续合规"，需要设计重测策略。
5. 有人把系统级报告当产品认证引用，需要纠正。

### 语言信号 (用户的话里出现这些就应激活)

- "测评报告有有效期吗？过期了吗？"
- "系统改了之后上次测评还算数吗？"
- "变更多大才需要重新测评？"
- "我们的发布频率这么高，每年测一次有什么意义？"
- 英文: "report validity"、"has the assessment expired"、"retest after changes"、"assessment expiration"、"does the report still apply"

### 与相邻 skill 的区分

- 与 `mlps-readiness-self-inspection`（就绪度迎检自查）的区别: 后者是被测单位的全套义务自查（备案/检查/频次）；本 skill 聚焦单份报告的效力边界与重测触发——一个是组织就绪，一个是文件效力。
- 与 `mlps-deliverable-stage-gates`（产物阶段门）的区别: 后者管测评项目的过程质量；本 skill 管测评产物的有效期与适用范围。
- 与 `mlps-compliance-vs-risk-boundary`（合规与风险分工边界）的区别: 后者讲"符合基线≠安全"的概念边界；本 skill 讲"结论只覆盖测评时点与组件"的时间/对象边界——一个问结论的意义，一个问结论的射程。

## E — 可执行步骤 (Execution)

1. **确认报告的基本效力前提**
   - 完成标准: 报告有签章、声明在册、证据真实性前提未被推翻；缺签章或被证实提供虚假证据的，直接判无效。
2. **对照变更清单核查组件**
   - 完成标准: 收集测评日期以来的变更记录，逐条标注是否涉及系统构成组件/子系统（架构、安全组件、等级要素）；标注为"是"的变更清单成表。
3. **裁定失效范围**
   - 完成标准: 输出三类范围——报告仍有效部分 / 已失效须重测部分 / 常规发布不触发但须披露的部分；结论明确"整份有效/部分失效/整体失效"。
   - 判停条件: 若变更记录本身缺失或不可信，无法完成组件级核对，判"效力无法确认"，按整体失效处理并要求补充变更史。
4. **核对周期轨**
   - 完成标准: 法定频次（三级年测等）距今未超期；超期的标注"该测未测"合规缺口。
5. **输出处置建议**
   - 完成标准: 给出重测范围建议（全量/增量）、披露义务（发布频率与适用边界写进报告或使用说明）、引用规范提示（不得增改）；高频发布团队给出"基线+增量"的持续安排方案。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 判断报告分数对错——那是 `mlps-score-aggregation-chain` 的复算场景；本 skill 只问"结论覆盖什么、还作不作数"。
- 定级是否需要调整（等级要素变化引发的是重新定级，走 `mlps-grading-decision`）——本 skill 管重测触发，定级变化是其输入之一。
- 通用代码审计报告/SAST 扫描报告的时效——无组件级"系统构成"概念，按各自工具的覆盖声明判断。

### 作者在书中警告的失败模式

- 用旧报告覆盖已变更系统——判不符合（pr091）。
- 把系统报告当产品认证引用——违反边界三。
- 断章引用、增改数据——违反边界四。
- "一次拿证终身有效"心态——双触发机制明确否定（fw87）。

### 作者的盲点 / 时代局限

- 四条边界与频次（三级年测/四级半年测）为等保 1.0（公通字[2007]43 号 + 2015 模板）口径；《网络安全法》与等保 2.0 时代测评频次与备案联动有调整，法定频次须按现行规定复核；"时点有效+组件变更失效+双触发"的框架本身稳定。
- 作者未预见持续交付场景——"基线+增量"安排是本 skill 的外推推论而非书中原文，使用时应标注为方法论延伸。
- "系统构成组件"的粒度在云原生下更细（一个 sidecar 升级算不算？），需要组织自行定义变更分类表并写入报告披露。

### 容易混淆的邻近方法论

- 报告时效 vs 证书有效期（如商用密码证书、ISO 证书的三年周期+监督审核）：前者由系统变更驱动（事件优先），后者由认证制度周期驱动——判定逻辑不同。
- 变更重测 vs 回归测试（工程概念）：回归测试验证功能不坏，变更重测验证合规状态仍成立——前者是后者的一部分而非全部。
