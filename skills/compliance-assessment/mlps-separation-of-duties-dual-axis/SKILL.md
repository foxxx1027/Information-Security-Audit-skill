# 职责分离双轴核查（跨层互斥 × 角色互斥）

## R — 原文 (Reading)

> "③检查操作系统和数据库系统特权用户是否分离。Linux操作系统除管理员用户外，
> 还需分配审计员用户，两者之间的权限应互斥。检查方法如下：……c.检查管理员、审计员用户所在组和相关文件的访问权限，检查管理员和审计员用户
> 权限是否分离。"
>
> — 原作者 等，原始方法论来源第8章 8.3.2 Linux 访问控制（source.txt L5216–5224）

## I — 方法论骨架 (Interpretation)

"要分权"人人会说，落成检查动作要拆成两条独立的轴：

**纵向——跨层互斥**：同一身份不得兼任相邻系统层的管理员。典型是 OS 层与 DB 层：导出操作系统管理员组与数据库管理员（OSDBA 组）两组名单，**求交集**，交集非空即不符合——一个能同时动操作系统和数据库的人是单点全能。反向的适用性裁决：主机未装数据库，该指标判"不适用"。

**横向——角色互斥**：同一层内的管理权与审计权必须双向制约：审计员只有审计权无管理权，管理员无审计权（管账的和查账的不能是一个人）。延伸到机构层：安全管理员专职专岗不兼任，关键岗位须多人共管、有备岗——一人多职+权限过大+无记录是典型不符合形态。

第三件工具是**显影剂**：静态名单查不出的职责真空，用高风险流程（变更、应急、密钥操作）来显影——变更时两个岗位互相推诿"不归我管"，即是职责边界不闭合的行为证据，比任何文档都硬。

## A1 — 书中的应用 (Past Application)

### 案例 1: OS 与 DB 管理员求交集（第8章 8.3.1，pr029）
- **问题**: "操作系统和数据库系统特权用户分离"怎么核查？
- **方法论的使用**: 分别导出 Windows/Linux 管理员名单与数据库管理员名单（Oracle OSDBA 组），求交集。
- **结论**: 交集非空即不符合；主机未装数据库则判不适用。
- **结果**: 纵向互斥被翻译成一个可执行的集合运算。

### 案例 2: 应用系统三角色双向制约（第9章 9.3.1，fw63/cs011）
- **问题**: 业务系统的角色最小集是什么？
- **方法论的使用**: 系统管理员/安全管理员/审计员三角色最小集，落到 Windows 内置组名单（Administrators、Event Log Readers 等）逐一核对；审计员无管理权、管理员无审计权双向检查。
- **结论**: 三角色齐备且互斥才是横向闭合。
- **结果**: 角色核查点直接落到内置组名单，可照抄执行；WebLogic 侧 Auditor 独立配置、审计员与管理员不得同一账号（pr047）同构复现。

### 案例 3: 变更推诿显影职责真空（第10章 10.4.2，ce34）
- **问题**: 创业公司岗位职责文件齐全，怎么发现职责真空？
- **方法论的使用**: 用变更场景当显影剂——系统管理员说"变更不归我管"，应用管理员说"他不更新我没法动"，互相推诿、变更失控。
- **结论**: 关键流程无人负责是职责边界不闭合的行为证据，绩效考核形同虚设。
- **结果**: 判不符合；方法论固化"以高风险流程反推职责闭合"。

### 案例 4: 一人多职的典型不符合（第10章 10.4.1，ce31）
- **问题**: 管理测评最高频的不符合模板长什么样？
- **方法论的使用**: 特征叠加——无清晰制度、无责任部门、系统管理员身兼机房/设备/安全管理员数职、权限过大、操作记录不完善无法追溯。
- **结论**: 兼任安全与审计角色后失去相互制约。
- **结果**: 该情形作为"典型不符合情形"入表 10-7，成为管理类测评的反例清单条目。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 等保/内审核查特权用户分离、访问控制策略中的职责分离项。
2. DevOps/SRE 团队评审：同一人同时负责发布平台与审计日志平台怎么判？
3. 云环境 IAM 治理：平台管理员与业务系统管理员、审计角色与管理角色的交集分析。
4. 事件复盘：越权/误操作事故后核查职责矩阵是否先天不闭合。

### 语言信号 (用户的话里出现这些就应激活)

- "管理员和审计员可以是同一个人吗？separation of duties 怎么查？"
- "OS 管理员兼 DBA 合规吗？特权账户怎么核？"
- "变更时两个岗位互相甩锅，说明什么？"
- "关键岗位只有一个人会做，有问题吗？"（备岗/多人共管）

### 与相邻 skill 的区分

- 与 `mlps-reconciliation-style-checking`（对账式核查）的区别: 后者对账"账号↔实际使用人/应有服务"（账实差集）；本 skill 对账"人↔互斥角色"（角色交集）——一个查多余，一个查冲突。
- 与 `mlps-personnel-lifecycle-controls`（人员全周期管控）的区别: 后者管人员进出组织的全周期（录用/离岗/外部人员）；本 skill 管在岗人员的角色组合约束。岗位设置指标是两者交界——前者查"有没有人、怎么进出"，本 skill 查"这些人角色是否互斥"。
- 与 RBAC 设计方法论的区别: 设计权限模型；本 skill 验证已运行系统的角色分配是否违规，不重新设计。

## E — 可执行步骤 (Execution)

1. **画角色-身份清单**：枚举各层管理员（OS、DB、网络、应用、审计员、安全管理员），导出成员名单（组导出/IAM 列表）。
   - 完成标准: 每层每角色一份成员名单，含唯一身份标识。
2. **纵向求交集**：相邻层管理员名单两两求交（OS∩DB、平台∩业务系统）。
   - 完成标准: 每对交集有结果；非空交集列出具体身份。
   - 判停条件: 若某层对象不存在（未装数据库）→ 该对记"不适用"并注明依据，继续其他对。
3. **横向查双向制约**：核对审计角色的权限不含管理操作、管理角色不含审计配置权；机构层查安全管理员专职专岗、关键岗位备岗与多人共管。
   - 完成标准: 双向制约逐向有"成立/不成立"结论；专岗与备岗有访谈+文件证据。
4. **跑显影剂**：抽 1–2 个近期高风险流程（变更/应急处置），追溯各环节责任人，查是否存在推诿、无人认领的步骤。
   - 完成标准: 流程责任链完整或记录断点（断点即职责缺口证据）。
5. **汇总裁决**：交集非空/制约缺失/显影断点分别落档（通常不符合），整改指向"角色移交、独立审计角色、备岗设置"。
   - 完成标准: 问题-证据-整改三列汇总表。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 岗位编制与组织架构设计（定岗定编）——人事管理咨询，非合规核查。
- 小型组织"一人多岗"的合理简化——书口径是规模小可简化流程、不可缺失制约闭环；但若系统与人员规模确实极小，先按"进一步跟踪"给整改路径而非机械判不符合（需结合 `mlps-verdict-tiers` 档位纪律裁量）。
- 应用内业务角色的授权粒度（谁能审批报销）——业务授权，非安全职责分离。

### 作者在书中警告的失败模式

- 系统管理员身兼数职、权限过大、操作记录无法追溯（ce31 典型模板）。
- 变更互相推诿的职责真空（ce34）——静态文件查不出，必须跑显影剂。
- WebLogic 审计员与管理员同账号兼任（pr047 语境）——审计独立性失守。

### 作者的盲点 / 时代局限

- **版本提示**：核查所依条款（特权用户分离、岗位设置指标）属等保 1.0（GB/T 22239—2008）；2.0 延续职责分离要求但云环境须映射到 IAM 角色/服务账号，"求交集"运算对象从系统组变成 IAM 策略绑定，方法结构不变。
- 书中双轴以"管理员/审计员"为中心，未覆盖现代场景的第三方托管（MSP 代维与被测方职责切分）、以及"机器身份"（CI/CD 服务账号）的角色互斥。

### 容易混淆的邻近方法论

- least privilege（最小权限）：约束单个主体权限面；SoD 约束主体间角色组合——两者正交，最小权限满足的系统仍可能 SoD 违规。
- RACI 矩阵：任务分工管理工具；本 skill 的显影剂借用其"责任归属"思想，但产出是合规判定而非分工表。
