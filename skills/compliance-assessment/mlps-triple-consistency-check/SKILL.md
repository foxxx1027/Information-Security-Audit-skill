# 三重一致性核查与形式合规穿透

## R — 原文 (Reading)

> 「不仅要核实所有文档之间的一致性，还需判断实地察看的情况与制度和文档中规定的要求是否一致，所有执行过程记录文档应与相应的管理制度要求保持一致。」
>
> — 方法论出处，第10章 10.3 末段（第12章 12.3 管理测评判定框架同构复述）

---

## I — 方法论骨架 (Interpretation)

"管理是否落实"无法直接观察，作者把它操作化成三角互证：

1. **三条互证链**：文档链（制度文本之间互相一致，总纲与细则不打架）、实地链（现场看到的行为/设施与制度规定一致）、记录链（执行留痕与制度要求的频度、格式、内容一致）。
2. **任一环断裂即降档**：三条链全部闭合才能判符合；纸面齐全但执行记录对不上，就是"纸面合规"，按证据暴露程度降为部分符合或不符合。
3. **技术侧同一骨架**：技术测评用"策略文档（如访问控制矩阵）→ 系统配置 → 实测行为"三级比对——与管理侧同构，全书通用。这使该骨架可迁移到任何"声明体系 vs 实际体系"的核查。
4. **穿透技术补位**：三链互证会被"突击补记录"骗过，因此加两招——记录时间戳分布检查（日期是否与业务周期匹配、是否集中在检查前夕）与访谈交叉验证（执行人是否真知道流程）。
5. 该方法的输出是"断裂点定位"：缺制度（文档链断）、有制度不执行（实地链断）、执行不留痕（记录链断），三种缺口的整改动作完全不同。

## A1 — 书中的应用 (Past Application)

### 案例 1: 管理测评的判定框架
- **问题**: 管理类控制（制度、培训、审批）看不见摸不着，怎么判定符合与否。
- **方法论的使用**: 第10章 10.3 与第12章 12.3 把判定标准定为三重一致性——纸面合规但执行不符即暴露。
- **结论**: 管理测评的取证结构 = 文档审查 + 实地查看 + 记录核对，三角闭合才判符合。
- **结果**: 全书管理五域（制度/机构/人员/建设/运维）所有测评项沿用该框架，判"进一步跟踪/不符合"时通常靠某一环断裂取得证据。

### 案例 2: 应用访问控制的"矩阵→配置→实测"三级比对
- **问题**: 技术侧的访问控制策略是否真实生效。
- **方法论的使用**: 第9章 9.3.1 先访谈获取访问控制矩阵文档（主体×客体×操作），再核对系统内角色分组与权限设置是否依据矩阵配置，最后用无审计权限用户实测越权访问。
- **结论**: 技术侧与管理侧共用同一取证骨架——策略文档→系统配置→实测。
- **结果**: 该三级比对成为访问控制类测评项的标准路径，"配置存在"与"策略生效"被分开验证。

### 案例 3: 识破突击补做的培训记录
- **问题**: 被测单位出示齐全的培训记录，如何判断真伪。
- **方法论的使用**: 第10章 10.4.3 案例情形三——培训"基本不开展，在外部审核前才去完善相关记录"；用时间戳分布（记录日期高度集中于审核前夕）+ 访谈交叉验证（人员答不出培训内容）穿透。
- **结论**: 记录不反映真实过程即失去证据效力，判不符合。
- **结果**: "应付式合规"被识别出来，时间戳分布检查进入取证常规动作。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 制度类测评/内审：判断"写了制度"是否等于"在运行"。
2. 供应商/外包方合规审查：对方材料齐全，怀疑纸面合规。
3. 新架构（零信任、DevOps 流程）落地验证：策略声明与实际配置、执行记录是否一致。
4. 组织自查发现"制度都有但总出事"，需要定位断裂点在哪一环。
5. 审阅第三方报告时，检查其取证是否做到了三链互证还是只翻了文档。

### 语言信号 (用户的话里出现这些就应激活)

- "制度是有的，就是不知道落没落地"
- "记录会不会是补的？""怎么识别应付检查的材料？"
- "文档和实际对不上怎么办？"
- "怎么验证策略真的生效了？"
- 英文: "paper compliance"、"policy vs practice"、"verify implementation"、"check if records are fabricated"、"consistency check"

### 与相邻 skill 的区分

- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 本 skill 生成互相印证/矛盾的证据网；后者在证据矛盾后裁决采信谁。本 skill 是取证设计，后者是裁决规则。
- 与 `mlps-verdict-tiers`（判定档位体系）的区别: 本 skill 定位断裂点（哪一环断了）；后者把断裂翻译成档位结论。
- 与 `mlps-control-effectiveness-four-checks`（控制有效性四查：粒度/覆盖/生效/技术强制）的区别: 后者问"措施本身够不够格"；本 skill 问"声明的措施与实际之间是否一致"——一个评质量，一个评落地。

## E — 可执行步骤 (Execution)

1. **取得制度/策略基准**
   - 完成标准: 已收集总纲、细则、操作规程等全套文本，绘出要求清单（谁、做什么、多久一次、留什么痕）。
2. **文档链互证**
   - 完成标准: 逐条核对文档之间不打架（母子公司层级、新旧版本、制度与规程的对应）；发现的矛盾已记录。
3. **实地链核对**
   - 完成标准: 抽取制度中可现场观察的要求（门禁、值守、区域划分、系统配置），实地/实配核对，标注"规定有、实际无"或"实际有、规定无"。
4. **记录链核对**
   - 完成标准: 按制度要求的频度抽查执行记录，核对内容要素与时间分布；记录缺失或与要求不符的条目已列出。
5. **形式合规穿透**
   - 完成标准: 对可疑记录完成时间戳分布检查（对照业务周期）+ 执行人访谈交叉验证；判定记录是否构成有效证据。
   - 判停条件: 若三链中有两链已断裂且无法在本次核查内补证，停止逐条核对，直接按最弱环下结论并进入整改建议。
6. **输出断裂点定位与档位**
   - 完成标准: 明确写出断裂的是哪一环（缺制度/有制度不执行/执行不留痕/记录存疑），并按 `mlps-verdict-tiers` 档位给出结论与整改方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一技术配置核查（无制度声明面）——直接用配置检查/测试即可，三角无从搭起。
- 尚无任何制度文本的组织——文档链不存在，先做制度建设而非一致性核查。
- 证据冲突裁决场景——那是 `mlps-preponderant-evidence` 的职责。

### 作者在书中警告的失败模式

- 只翻文档不进现场：纸面合规但执行不符暴露不了（第10章 10.3 的直接警告）。
- 记录齐全即放行：突击补记录的时间戳与业务周期不匹配（ce40）。
- 形式合规的实质失效：UPS/柴发双失效损失 580 万的案例（ce50）——签字式检查记录全是"正常"，恰恰说明留痕不等于落实。

### 作者的盲点 / 时代局限

- 阶段 0 批判指出：全书隐含"留痕≈落实"假设，且证据金字塔中文档/访谈类占比最大、可伪造——三重一致性是缓解而非根治；作者未在判定规则里为"文档齐全但实效存疑"设置系统性穿透测试（仅个别项做了）。使用时应对高后果控制额外补动态验证（衔接 `mlps-active-verification-perturbation` 主动验证法）。
- 该骨架本身与标准版本无关，可直接用于等保 2.0、ISO 27001、SOC 2 等任何"声明 vs 实际"核查；但具体制度条款引用须按现行标准复核。

### 容易混淆的邻近方法论

- 三重一致性 vs 一般"抽样检查"：前者要求跨链（文档/实地/记录）交叉，后者只在单一链内抽样——只做后者会被整链伪造骗过。
- 三重一致性 vs 控制测试（audit 的 test of controls）：思想同源，本 skill 的增量是把"突击补记录的时间戳识别"标准化为取证动作。
