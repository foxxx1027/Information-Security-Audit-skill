# 判定链与整体测评回改机制

## R — 原文 (Reading)

> 「分析报告编制活动，包括单项测评结果判定、单元测评结果判定、整体测评、风险分析、等级测评结论形成及测评报告编制六项主要任务。」
>
> — 方法论出处，第3章 3.1.4（表3-4，报告编制六任务链）

---

## I — 方法论骨架 (Interpretation)

"先分块、再关联、后定论"——判定是一条有回路的固定链：

1. **六任务顺序不可跳**：单项判定（用优势证据法）→ 单元判定（按对象×单元汇总）→ 整体测评 → 风险分析 → 结论 → 报告。跳过整体测评直接汇总出结论，是流程作弊。
2. **整体测评的四个视角**：安全控制间（一项控制弥补另一项）、层面间（技术层弥补管理层）、区域间、验证测试（扫描渗透结果回填）——寻找的是"局部不符合是否被整体结构补偿"。
3. **回改是唯一合法修正通道**：整体测评发现弥补关系可以回改单元结论，但必须书面写明关联测评项与弥补程度（对应 `mlps-score-aggregation-chain` 的修正因子 0.5–0.9），不能凭印象调分。
4. **结论由残留计数驱动**：最终结论依据的是回改后"再次汇总仍为部分符合/不符合的项数"——不是初次判定的原始计数。
5. **审计价值**：任何"最终分比单元分好看"的报告，必须能出示回改记录（关联项+弥补程度）；出示不了，就是美化。

## A1 — 书中的应用 (Past Application)

### 案例 1: 表3-4 把回改固化为流程
- **问题**: 单元判定做完，能否直接算分出结论。
- **方法论的使用**: 第3章 3.1.4（表3-4）规定整体测评位于单元判定与风险分析之间，且"整体测评可能改变单元结果，需修订后再做风险分析"。
- **结论**: 整体测评不是可选的润色步骤，而是判定链的强制环节；顺序不可跳。
- **结果**: 测评机构的过程文件按六任务留痕，报告审查可核对回改发生在风险分析之前。

### 案例 2: 弥补关系的认定与量化
- **问题**: 应用层审计不符合，但全部管理操作都经堡垒机且审计完整——这种"别的控制补上了"怎么处理才合规。
- **方法论的使用**: 走整体测评四视角——堡垒机审计对应用审计缺陷构成弥补（控制间视角）→ 认定弥补程度 → 修正因子下调严重程度值 → 回改单元结论并在报告列明关联项与弥补程度 → 再做风险分析与结论。
- **结论**: 弥补是真实的分析对象，但必须走回改通道并留书面理由；直接在总分上"看着给分"不合法。
- **结果**: 该案例路径成为"最终分与单元分不一致"报告的合法性检验模板（本 skill 的 V2 推演，锚定附录A 5.4 四视角与修正机制）。

### 案例 3: 结论由残留问题计数驱动
- **问题**: 回改之后，最终"基本符合/不符合"看什么。
- **方法论的使用**: 第3章 3.4 规定最终结论依据再次汇总后仍为部分符合/不符合的项数，风险分析对每个残留问题关联资产+威胁定高/中/低。
- **结论**: 结论 = 残留问题计数 × 风险等级的函数，不是对第一轮数字的重新解释。
- **结果**: 报告的结论章可追溯到"哪些问题在回改后仍残留"，整改清单与之闭环。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 编制测评报告，从一堆单项结果走到最终结论，不确定中间流程。
2. 发现某控制不符合但有等价补偿（堡垒机审计、异地日志、冗余部署），想合规地体现弥补。
3. 审查第三方报告：最终得分明显好于单元判定，怀疑被美化。
4. 客户质疑"为什么第一次说不符合、报告里又变基本符合"，需要解释回改机制。
5. 设计审计底稿模板，让回改留痕可核查。

### 语言信号 (用户的话里出现这些就应激活)

- "单项判定之后怎么出结论？"
- "这个不符合项能不能用别的控制抵消？"
- "整体测评是什么？必须做吗？"
- "最终分为什么比单元分高？"
- 英文: "overall assessment"、"compensating controls"、"conclusion formation"、"can this control offset that finding"、"unit verdict aggregation"

### 与相邻 skill 的区分

- 与 `mlps-score-aggregation-chain`（得分聚合链）的区别: 本 skill 管回改的**程序**（何时改、怎么留痕）；后者管回改后的**算术**（修正因子如何进公式）。先程序后算术。
- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 后者是链的第一环（单项判定内部的证据裁决）；本 skill 是第一环之后的全链纪律。
- 与 `mlps-verdict-tiers`（判定档位体系）的区别: 后者定义档位语义；本 skill 定义档位如何逐级聚合与合法修订。

## E — 可执行步骤 (Execution)

1. **完成单项与单元判定**
   - 完成标准: 每个测评项已按 `mlps-preponderant-evidence`/v04 出档位与 0–5 分；单元（对象×控制点）汇总完成并留存底稿。
2. **执行整体测评四视角扫描**
   - 完成标准: 对每个部分符合/不符合项，从控制间、层面间、区域间、验证测试四个视角排查是否存在弥补控制；候选弥补关系列表成表（问题项 ↔ 弥补项）。
   - 判停条件: 若某"弥补"依赖的控制自身也是不符合项，该弥补不成立，剔除出候选表。
3. **认定弥补程度并回改**
   - 完成标准: 每条认定的弥补写明关联测评项、弥补程度（对应修正因子取值理由）；回改后的单元结论更新并在报告中单列（编号与单元问题表一一对应）。
4. **重新汇总残留问题**
   - 完成标准: 以回改后的结论再次汇总，得到仍为部分符合/不符合的残留清单——结论将以此驱动。
5. **风险分析与结论**
   - 完成标准: 每个残留问题关联资产与威胁定风险（高/中/低）；按 `mlps-score-aggregation-chain` 二维判据形成结论三档；报告含回改记录附录。
6. **自审流程完整性**
   - 完成标准: 核对"整体测评发生在风险分析之前、每处单元结论变动都有书面理由"——任一不满足即流程缺陷，修正后再出报告。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单项证据的采信争议——回到 `mlps-preponderant-evidence`，链的第一环都没定论谈不上聚合。
- 想用"整体不错"掩盖关键控制失效——弥补只适用于真实的功能等价补偿，不适用于核心控制缺失（如无任何审计 vs 有部分审计不是弥补关系）。
- 非结构化评估（无单元划分的自由评审）——没有"单元"就没有回改机制的前提。

### 作者在书中警告的失败模式

- 直接汇总单元结果出结论——跳过整体测评的流程作弊（fw17 顺序约束）。
- 回改无书面理由、无关联项与弥补程度——修正因子沦为调分手柄（pr009）。
- 用不符合的控制"弥补"不符合的控制——弥补链断裂（判停条件）。

### 作者的盲点 / 时代局限

- 判定链出自 GB/T 28449—2012 与 2015 版模板（等保 1.0）；2.0 时代报告模板对整体测评视角与结论表述有调整，正式作业以现行标准复核——"先分块再关联后定论 + 回改留痕"的链式纪律本身稳定可迁移。
- 阶段 0 批判：修正因子 0.5–0.9 的取值无量化依据（"弥补程度"的认定高度依赖测评员判断），跨机构一致性存疑——使用时应把弥补程度认定的证据写得更实（等效性论证），而非仅给一个因子数。

### 容易混淆的邻近方法论

- 整体测评回改 vs "风险接受"（risk acceptance）：回改承认控制等效补偿、结论仍指向整改；风险接受是明示不整改、留 residual risk——混用会把应整改项合法化。
- 弥补控制 vs defense in depth：纵深防御是建设策略（多层都保留），弥补是判定概念（一层替另一层得分）——不可把"我们还有别的层"直接当弥补证据。
