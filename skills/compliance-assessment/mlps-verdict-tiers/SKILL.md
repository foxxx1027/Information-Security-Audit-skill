# 测评项判定档位体系与判定纪律

## R — 原文 (Reading)

> 「对发现情况一时不能得出判断的，应扩大访谈或检查范围，查找证据材料，并进一步跟踪。」（第11章 11.3）「符合程度根据被测信息系统实际保护状况进行赋值，完全符合项赋值为5，其他情况根据被测系统在该测评指标的符合程度赋值为0~4（取整数值）。」（附录A 附件A）
>
> — 方法论出处，第11章 11.3；附录A（第12章 12.3 原样复述同一规则）

---

## I — 方法论骨架 (Interpretation)

把"判符合还是不符合"这个二值冲动，替换成一套有触发条件的五档体系：

1. **五档及其触发条件**：符合（措施存在且完整覆盖）/ 部分符合（措施存在但覆盖不完整或粒度不足）/ 不符合（缺失或失效）/ 不适用（环境不触发该要求）/ 进一步跟踪（证据不足，待扩证）。
2. **中间档的价值是"强制写明缺口"**：判部分符合必须指出缺口在哪（覆盖面缺哪段、粒度差在哪级），进整改清单——它是分析工具，不是给人情分的缓冲带。
3. **"进一步跟踪"是挂起状态不是通过**：它的正确后续是扩大取证范围继续查，绝不能当合格处理。
4. **"不适用"须给原因**：环境不具备（如未安装数据库）时该项单列并写明原因，不适用 ≠ 不符合，也不得默默跳过。
5. **档位与 0–5 分衔接**：完全符合 5 分，其余按程度 0–4 取整，中间档的信息进入打分链（供 `mlps-score-aggregation-chain` 聚合）。
6. **判定校准靠案例矩阵**：用"典型良好实践 / 部分符合的残缺形态 / 完全不符合"三情形对照，把尺度锚定在案例上而非评估者心情。

## A1 — 书中的应用 (Past Application)

### 案例 1: 防盗报警只装机房入口——部分符合的显式触发条件
- **问题**: 机房四周 vs 仅入口设红外探测器，判定如何区分。
- **方法论的使用**: 第6章 6.3.3 给出三档对照——四周设红外/振动报警=符合；仅入口处=部分符合；无=不符合（引文"人口处"为 OCR 噪声）。
- **结论**: "措施存在但覆盖不完整"就是部分符合的典型触发条件。
- **结果**: 部分符合必须写明缺口位置（覆盖了哪几面、缺哪几面），进整改清单而非直接通过；同族判定（访问控制类覆盖不全）沿用此规则。

### 案例 2: Linux 默认账户——指标要求与工程惯例的张力
- **问题**: 指标要求"重命名默认账户"，但 Linux 系统默认账户（UID<500）改名可能导致系统功能失效，照抄指标会判出无法整改的"不符合"。
- **方法论的使用**: 第8章 8.3.2 以等效控制折中——检查是否限制默认账户文件访问权限、禁用闲置默认账户，判定时说明理由。
- **结论**: 不机械判不符合也不放弃判定，用等效控制 + 显式说明守住判定纪律。
- **结果**: 该项落"部分符合/符合（等效）"并附说明，成为书中少见的判定校准示范。

### 案例 3: 管理制度三情形判定矩阵
- **问题**: 管理类测评项如何给出一致的档位输出。
- **方法论的使用**: 第10章 10.4.1 用"情形一 ISMS 完备 / 情形二 子公司体系待完善（进一步跟踪）/ 情形三 无制度无责任人一人多职（不符合）"三情形 × 四条标准要求，在表10-7 给出判定矩阵。
- **结论**: 判定尺度用案例矩阵锚定，跨测评员可复现。
- **结果**: 该三情形结构成为全书管理篇案例的标准输出格式（表11-2、表12-13 等沿用）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 测评/审计报告中要给每个控制项写结论，纠结"这项算符合还是不符合"。
2. 措施"做了但没做全"（如审计只覆盖部分组件、值守记录只覆盖楼宇不覆盖机房），需要正确的分档。
3. 证据不够下结论，用户想知道该硬判还是挂起。
4. 环境不具备某要求的前提（未装某组件、无该业务），需要判断是"不适用"还是"不符合"。
5. 评审他人报告时检查判定纪律（部分符合有没有写缺口、不适用有没有给原因）。

### 语言信号 (用户的话里出现这些就应激活)

- "这项判部分符合还是不符合？"
- "做了但没做全怎么算？"
- "不适用和不符合有什么区别？"
- "证据不够，先给个初步结论行吗？"
- 英文: "verdict"、"partially compliant"、"not applicable vs non-compliant"、"insufficient evidence"、"scoring rubric"

### 与相邻 skill 的区分

- 与 `mlps-preponderant-evidence`（优势证据法）的区别: 后者裁决采信哪份证据；本 skill 在证据采信后决定结论档位与缺口描述。先后衔接，不互相替代。
- 与 `mlps-score-aggregation-chain`（得分聚合链）的区别: 本 skill 产出单测评项的档位与 0–5 原始分；后者把原始分聚合成控制点/层面/系统得分。
- 与 `mlps-indicator-selection-rules`（指标确定规则集）的区别: 后者在指标集层面裁决"这一类指标不适用"（如无拨号网络）；本 skill 在单个测评项判定层面使用不适用档——层级不同。

## E — 可执行步骤 (Execution)

1. **确认适用性**
   - 完成标准: 已核对被测环境是否触发该要求的前提；不触发的项单列并写明原因，进入"不适用"档。
2. **核对措施存在性**
   - 完成标准: 依据已采信证据（`mlps-preponderant-evidence` 之后）回答"有没有这个控制"，缺失或失效即判不符合并记录证据。
3. **核对完整性与粒度**
   - 完成标准: 对照要求的目标覆盖面/粒度（覆盖哪些对象、什么级别），逐点核对；存在但覆盖不全的判部分符合，并逐条写明缺口位置。
   - 判停条件: 若证据不足以区分"全/不全"，不硬判——转步骤 4。
4. **证据不足时挂"进一步跟踪"**
   - 完成标准: 写明待补的证据与扩证范围（扩大访谈/检查），设定跟踪期限；该项不得计入通过项。
5. **赋 0–5 分并写判定理由**
   - 完成标准: 完全符合=5；部分符合按程度 1–4 取整；不符合=0；判定理由引用具体证据与缺口描述。
6. **对照案例矩阵校准**
   - 完成标准: 抽查 2–3 项与同类案例（三情形）对照，确认档位尺度与全项目一致。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 证据矛盾尚未裁决时——先用 `mlps-preponderant-evidence` 优势证据法定采信，再谈档位。
- 需要跨项聚合总分时——档位/原始分只是输入，聚合规则见 `mlps-score-aggregation-chain`。
- 非符合性语境（如漏洞严重度分级 CVSS）——那是风险量化体系，档位语义不同。

### 作者在书中警告的失败模式

- 把"进一步跟踪"当通过：待定是程序状态，最终必须落到四档之一（第11章 11.3、第12章 12.3 反复强调）。
- 部分符合不写缺口：中间档失去"强制写明缺口"的功能就沦为面子分（ce10 防盗报警案例的推论）。
- 不适用不说明原因直接跳过——报告口径要求不适用项单列表并给原因（附录A 表3-2）。
- 机械照条款判出无法整改的结论（Linux 默认账户，ce24）：判定要在指标与工程可行性之间显式说明折中。

### 作者的盲点 / 时代局限

- 档位体系与 0–5 分制源自 2015 版报告模板（公信安〔2014〕2866 号）；等保 2.0 时代的报告模板对档位与分值口径有调整，出正式报告前须对照现行模板复核。
- 三情形案例矩阵是编写组构造的典型情形，非跨机构判定一致性统计数据，校准效果未经信度检验（阶段 0 批判）。

### 容易混淆的邻近方法论

- "部分符合" vs "低风险不符合"：前者是覆盖/粒度维度的描述，后者是风险维度（`mlps-compliance-vs-risk-boundary`/v14 结论档用）——两个维度不要混。
- "进一步跟踪" vs "不适用"：前者是证据不足（挂起待查），后者是环境不触发（终局裁决）。
