# 防重放机制选型与窗口工程

## R — 原文 (Reading)

> "如果要求反重放（默认设置），则发送方不允许循环计数（到达232-1后返回0），否则，同一个序列号可以有多个合法的包。如果该序列号达到232-1，则SA必须终止，用新的密钥协商生成新的SA。"
>
> — 方法论出处，第20章 20.3.4 反重放机制

---

## I — 方法论骨架 (Interpretation)

防重放的第一步不是"加时间戳"（本能反应），而是**分型**：重放分四型（简单重放/接收方窗口内可检测/窗口内不可检测/反向重放），类型决定防护可行性。第二步按**信道形态**选机制，因为三种机制各有"否定自身优点"的场景：

- **质询-应答握手**：最可靠，但要求双方同时在线——它否定了无连接/异步信道的优点（邮件做不了握手）。
- **时间戳**：不需往返，但困于时钟同步假设与窗口两难——窗口太大挡不住重放，太小误杀正常延迟（抑制重放攻击正是打这个缝隙）。
- **序号**：适合无连接包流，但需要跟踪状态；且计数器是**一次性资源**——到 2^32-1 不许回绕，用尽必须换钥重建会话。

无连接流的工程解是"单调计数器不回绕+滑动窗口"：窗口大小 W=允许的在途乱序度（IPsec 默认 64 位图），窗口右移规则三分支判定。异步信道（邮件、事件）只能做内容级新鲜性（每消息唯一标识+接收端去重登记）。另记一条判据："只有 A 知道 Ka"不构成身份证明——密文可被截获重放。

## A1 — 书中的应用 (Past Application)

### 案例 1: IPsec 序列号窗口（第20章）
- **问题**: 无连接 IP 包流可能乱序、重放，如何防？
- **方法论的使用**: 按形态选序号+窗口——32 位单调计数器不许回绕；接收端 W=64 位图滑动窗口，标记已见序号，三分支判定（窗口左侧丢弃、窗口内查重、右侧右移）。
- **结论**: 计数器是一次性资源，到 2^32-1 必须终止 SA、用新密钥协商新 SA。
- **结果**: 成为防重放的参考实现；SAD 中的序列号溢出标志即为此设计。

### 案例 2: 加密邮件的时间戳两难（第15章）
- **问题**: 把实时认证协议（KDC 三步）裁剪到加密电子邮件，防御策略含时间戳，行吗？
- **方法论的使用**: 信道形态检查——邮件是存储转发，天然存在潜在延误：时间戳窗口太小误杀正常邮件、太大挡不住重放。
- **结论**: 时间戳机制在异步信道的适用域被否定；应改用与时间无关的新鲜性（每消息唯一 nonce/序列登记）或显式接受上层去重。
- **结果**: 单向/异步场景的选型判据成型——机制必须匹配信道形态。

### 案例 3: Kerberos 票据绑定来源地址（第15章）
- **问题**: 票据被截获后拿到另一台工作站重放冒充怎么办？
- **方法论的使用**: 内容级绑定——AS 把生成票据的工作站网络地址写入票据（Ticket=E(Kv,[IDc‖ADc‖IDv])），换机重放即失效。
- **结论**: 逐字段解释"防什么"（加密防篡改、ID 验来源、地址绑位置），并显式列出残余问题（同网段伪造地址）作为下一层输入。
- **结果**: v4 以此挡住跨机重放；v5 把地址类型改为可选以适配多协议环境。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计 API/webhook/事件消息的防重放与幂等（serverless、消息队列、重试语义）。
2. 无连接/异步信道（UDP、MQ、邮件类）的新鲜性设计。
3. 评审时间戳窗口参数（"窗口多大合适"）。
4. 序列号/计数器耗尽与换钥策略制定。

- "滑动窗口 / sliding window, W=64"
- "重试与重放怎么区分 / retry vs replay"
- "序号回绕了 / sequence number wrap-around"

### 与相邻 skill 的区分

- 与 `stallings-protocol-belief-analysis` 的区别: 那个用重放作为武器证伪协议信念（发现漏洞），本 skill 为确认的重放面选机制、定参数（修复漏洞）——先后关系。

- 与 `stallings-challenge-response-design-criteria` 的区别: 那个谈质询-应答机制本身的设计判据，本 skill 谈三法比较、信道适配与窗口参数工程——机制内部 vs 选型框架。

## E — 可执行步骤 (Execution)

1. **判信道形态**：面向连接可交互？无连接？异步存储转发？
   - 完成标准: 形态判定成文。
2. **重放分型**：按四型（简单/窗口内可检测/窗口内不可检测/反向）判定攻击者可用的类型。
   - 完成标准: 分型结论+依据（攻击者能力假设）。
   - 判停条件: 若消息天然幂等且无状态副作用（纯查询），记录"重放无害"豁免并结束。
3. **按形态选机制**：可交互→质询握手；有可靠同步时钟→时间戳；无连接→单调序号+滑动窗口；异步→内容级唯一标识+接收端去重登记。
   - 完成标准: 机制-信道匹配表成文。
4. **定窗口参数**：W=最大乱序/重试容忍度，写出依据（网络实测或协议规范）；时间戳方案同时定窗口与失步策略。
   - 完成标准: W 值与依据成文。
5. **定用尽策略**：对计数器/序号定"到顶换钥/重建会话"的触发与监控（剩余量告警）。
   - 完成标准: 换钥触发器与监控项成文。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯业务幂等/去重问题（无安全语义时由业务层处理）。
- 时钟不可信环境强行上时间戳——先解决时钟信任或改机制。

### 作者在书中警告的失败模式

- 抑制重放攻击：发送者时钟快于接收者时，截获消息的时间戳恰好落入接收者窗口（ce059）——时间戳的修补假设自身可被攻击。
- 计数器回绕=同一序号多个合法包，防重放整体失效（ce093）。
- "只有 A 知道 Ka"不构成身份证明：E(Ka,R) 可被截获重放冒充（ce056）。

### 作者的盲点 / 时代局限

- 窗口工程书内只有 IPsec W=64 一个样本（成书 2017 前），无自适应窗口讨论；分布式/云环境的时钟服务（NTP 治理）不在书内——外推时需补。

### 容易混淆的邻近方法论

- v36 信念分析（发现 vs 修复）。
- v34 撤销传播（凭证 vs 消息）。
