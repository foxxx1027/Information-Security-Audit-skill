# 攻击—服务—机制三层对齐矩阵

## R — 原文 (Reading)

> "安全服务加强数据处理系统和信息传输的安全性的一种处理过程或通信服务，目的在于利用一种或多种安全机制进行反攻击。……根据X.800中的定义，表1.4给出了安全服务和安全机制的关系。"
>
> — 方法论出处，第1章 1.2/1.5 OSI 安全架构（source.txt 行1300区、表1.4）

---

## I — 方法论骨架 (Interpretation)

大多数"安全需求"写成了机制清单（"要加密、要上 TLS"），既没说防什么攻击，也没说提供什么服务。三层对齐把这件事变成三栏互相咬合的表：

1. **攻击**：对手能做什么（被动窃听、伪装、重放、篡改、抵赖……），是"对象"。
2. **服务**：系统要达成什么安全性质（认证、完整性、保密性、不可否认、可用性），是"目标"，粒度（整条连接/单块/选择域）直接决定成本。
3. **机制**：用什么实现（加密、签名、MAC、访问控制……），是"手段"。

闭环规则：每种要防的攻击都有一行；每行都能指到一个服务；每个服务都有机制实现并且有验证证据。交叉矩阵（服务×机制、机制×攻击）里的空白格只有两种合法状态——已论证的不需要，或漏项。需求清单会重复"上 TLS"，矩阵会暴露"QoS0 场景下重放行没有任何机制覆盖"这类真缺口。

## A1 — 书中的应用 (Past Application)

### 案例 1: X.800 服务×机制矩阵与两张补全矩阵
- **问题**: 安全服务有 14 种、机制有 8 类，需求与手段之间容易脱节（上了加密但需求是不可否认）。
- **方法论的使用**: 表1.4 以服务为行、机制为列标出可实现关系；书中习题进一步要求读者补全"服务×攻击""机制×攻击"两张矩阵，构成三层闭环。
- **结论**: 需求→手段要走查表路径，且攻击维度必须显式交叉核对，不能只查服务。
- **结果**: 该模板在第17章表17.1（Web 威胁—后果—对策）、第19章表19.5（邮件四类威胁→对策）被原样复用，成为全书部署章的统一写法。

### 案例 2: 资产×目标定级得出不同优先序
- **问题**: 同一套 CIA 三元组被当成所有场景的统一优先序。
- **方法论的使用**: 第1章用三组资产分别定级：医院过敏信息→完整性优先（错一条可能致命）；学生成绩（FERPA）→保密性优先；认证服务本身→可用性优先（不可用则所有依赖它的服务全不可用）。
- **结论**: 先按资产给 C/I/A 排序，再选控制，而不是人人"先加密"。
- **结果**: 定级结论直接改变机制投入方向（校验与冗余 vs 加密 vs 高可用），避免机制错配。

### 案例 3: 第12章八类攻击→三手段映射
- **问题**: "消息认证"要防什么，边界模糊。
- **方法论的使用**: 12.1 把攻击细化为八类（透露、传输分析、伪装、内容修改、顺序修改、计时修改、发送方否认、接收方否认），逐类指派机制：加密防(1)(2)，认证符防(3)–(6)，数字签名防(7)(8)。
- **结论**: 机制指派必须落到攻击行上——加密防泄露但防不了抵赖。
- **结果**: "上了加密就以为都安全"的缺项被逐行暴露。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为新系统/新协议（如 MQTT 物联网平台）写安全需求规格，要避免"要加密"式的机制罗列。
2. 评审一份安全设计，检查威胁清单与需求清单是否互相覆盖、每个承诺的服务有没有实现证据。
3. 事故后复盘"为什么上了 TLS/WAF 还被打穿"，需要定位覆盖缺口。
4. 给资产做 C/I/A 定级，决定不同数据类的控制投入方向。

### 语言信号 (用户的话里出现这些就应激活)

- "帮我写/评审 security requirements / 安全需求规格"
- "威胁清单和需求对不上 / 这个威胁谁来挡"
- "上了 TLS 还会漏什么"
- "这些数据哪些要先加密、哪些要先保完整性"
- "threat model 怎么起步 / coverage check"

### 与相邻 skill 的区分

- 与 `stallings-security-solution-four-elements` 的区别: 那个管方案内部四栏（算法/产生/分发/协议）是否齐全；本 skill 管方案与**威胁/需求**的外部对齐——方案可以四栏齐全但防错了攻击。
- 与 `stallings-attack-tree-and-or-modeling` 的区别: 攻击树把单一攻击目的展开成路径并排优先级；本 skill 做全谱覆盖核对，不排序、不收敛路径。
- 与 `stallings-passive-active-response-asymmetry` 的区别: 那个是预算分配判据（预防 vs 检测）；本 skill 是覆盖完整性判据，两者可组合。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **资产×目标定级**: 盘点资产，对每类资产分别给 C/I/A 排优先序（参照医院/成绩/认证服务三例的思路）。
   - 完成标准: 每类资产有一行"最不能容忍的后果"结论。
2. **列攻击行**: 按被动（泄露、流量分析）与主动（伪装、重放、内容/顺序/计时修改、抵赖）枚举，结合业务补充特有攻击。
   - 完成标准: 攻击行覆盖通用八类 + 至少 1 条业务特有攻击。
3. **填服务列并查机制**: 每行攻击指派对冲的安全服务（注意粒度：连接级/单块/选择域），再查实现机制。
   - 完成标准: 每行有"攻击→服务→机制"三联，机制名具体到可验收。
4. **交叉核对空白格**: 对矩阵每个空格判定——漏项（补机制）还是已论证不需要（记录理由）。
   - 完成标准: 无未解释的空白格；每个有机制的格附验证方式。
   - 判停条件: 若发现整行无任何机制覆盖且该行威胁真实存在，直接标记为高危缺口并停止细化其他行，先处理该行。
5. **输出**: 对齐矩阵 + 缺口清单 + 定级结论。
   - 完成标准: 缺口清单每条含威胁、缺失服务、建议机制方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一机制/算法的强度评估（这个 MAC 够不够强）——矩阵只表达"可实现"，不表达成本与强度。
- 攻击路径排序与防御优先级决策——用攻击树类方法。
- 方案内部结构完备性（密钥怎么分发、协议时序）——用四要素类框架。

### 作者在书中警告的失败模式

- 服务清单当威胁清单用：14 种服务逐项勾选≠威胁被覆盖，必须与攻击矩阵交叉核对（fw005/fw006 明示边界）。
- 粒度错配：选了"整条连接完整性"但业务只需"选择域"，成本翻倍；反之选粗了留下缺口。
- 机制与目标脱节："上了加密但需求是不可否认"是书中点名的常见病。

### 作者的盲点 / 时代局限

- X.800 词汇表成形于 1990s 电信网时代：对 API 滥用、供应链攻击、业务逻辑漏洞没有现成词条，使用时需自行扩行（书自己也在第17/19章为 Web/邮件扩了行）。
- 第7版（2017 前后）未覆盖零信任、云原生边界的"资产"定义——资产定级需补上云上共享组件与托管服务。
- 矩阵是静态快照，书中未给持续复核机制。

### 容易混淆的邻近方法论

- 与 STRIDE 类威胁枚举的区别: 本 skill 的差异在"三层闭环对齐"——枚举只是第一步，每格还要有实现与验证证据。
- 与风险矩阵（可能性×影响）不同: 这里不量化风险值，只判覆盖有无。
