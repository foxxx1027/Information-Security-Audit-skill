# 认证机制目标分层四轴

## R — 原文 (Reading)

> "DKIM的产生源于如下因素：（1）S/MIME要求接收方和发送方都使用S/MIME。但是，对几乎所有的用户而言，天量的软件并不适用S/MIME，并且大量给接收方发送的邮件也并不使用S/MIME。"
>
> — 方法论出处，第19章 19.9.2 DKIM 策略

---

## I — 方法论骨架 (Interpretation)

认证机制不是强度单一维度，而是按**目标分层**的两族：域级透明基础设施认证（DKIM 型）与个人级强追责认证（S/MIME/PGP 型）。比较用四把尺子：

1. **覆盖率**：需要对方也部署吗？域级不需要（接收方查 DNS 即可），个人级要求双方都有软件与密钥。
2. **保护范围**：证明的是"这个域"还是"这个人"；覆盖内容、头域还是全部。
3. **用户摩擦**：域级对用户零操作；个人级有密钥管理负担。
4. **可追责**：只有个人级绑定到人并支持不可否认。

典型误判是拿一族去干另一族的活：用个人级方案做全员防钓鱼（覆盖率轴不及格，DKIM 产生的五因素正源于此），或用域级签名冒充个人合同效力（追责轴不及格）。正确输出是四轴打分表+两类叠加：域级打底全覆盖、个人级护高价值操作。配套还有"认证到哪一层"的粒度分档（联合身份的账户/角色/机器链三档）——粒度按对方需要知道多少收敛。

## A1 — 书中的应用 (Past Application)

### 案例 1: DKIM 产生五因素（第19章）
- **问题**: 已有 S/MIME，为什么还需要 DKIM？
- **方法论的使用**: 覆盖率轴分析——S/MIME 要求收发双方都部署，现实中"天量的软件并不适用"；DKIM 改由邮件提供者用域私钥签名、接收侧查 DNS 验证，对用户透明零操作。
- **结论**: 域级机制以覆盖率与低摩擦取胜，可应用于所有从协作域发出的邮件。
- **结果**: 部署形态落地（gmail 等公共邮件工具签名），反仿冒规模化可行。

### 案例 2: DKIM 与 S/MIME 的五轴对照（第19章）
- **问题**: 两套机制怎么分工？NIST 站哪边？
- **方法论的使用**: 四轴逐项对照——DKIM 高覆盖率/域范围/零摩擦/域级追责；S/MIME 双方部署/内容级/有摩擦/个人不可否认；NIST SP800-177 推荐需要个人追责的场景用 S/MIME。
- **结论**: 两类机制目标不同，叠加互补而非互相替代。
- **结果**: "按目标分层选型"成为邮件安全的部署共识。

### 案例 3: 联合身份粒度三档与云 IAM（第15、16章）
- **问题**: 跨域认证"验到哪一层"合适？
- **方法论的使用**: 粒度分档——账户/角色/机器链三档，按对方需要知道多少收敛；云 IAM 的域级身份转换是基础设施认证形态的旁证。
- **结论**: 认证粒度本身是一个选型轴，不是越细越好。
- **结果**: 粒度三档用于联合身份与身份映射设计。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 企业邮件/消息防伪与高管合同签署要不要用同一套方案的决策。
2. 认证机制选型——覆盖率与追责的取舍（批量通知、平台签名、API 调用方识别）。
3. 联合身份/SSO 的粒度设计（验到账户还是角色还是设备链）。
4. "一套方案解决所有认证"的提案评审。

### 语言信号 (用户的话里出现这些就应激活)

- "覆盖率还是追责 / coverage vs accountability"
- "域级签名 / domain-level signing, DKIM"
- "个人签名/不可否认 / personal non-repudiation"
- "零用户摩擦 / zero user friction, transparent deployment"
- "认证到什么粒度 / granularity of authenticated identity"

### 与相邻 skill 的区分

- 与 `stallings-auth-assurance-tiering` 的区别: 那个在对象层分解（验物/验人）与风险档位，本 skill 在机制层比选（域级/个人级四轴）——对象分档在前、机制选型在后。
- 与 `stallings-evidence-alignment-binding` 的区别: 那个要求所选机制的判定最终对齐核心身份（From 域），本 skill 先按四轴选出机制层——选型与对齐配套。
- 与 `stallings-evidence-asymmetry-non-repudiation` 的区别: 那个管不可否认的判定法（MAC 不能给、谁应当给），本 skill 管机制选型的四轴比较——追责轴的展开在那个 skill。

## E — 可执行步骤 (Execution)

1. **需求四轴打分**：写出业务需求在覆盖率/范围/摩擦/追责四轴上的要求（哪轴一票否决）。
   - 完成标准: 需求得分表成文，标注否决轴。
2. **候选机制逐个打分**：对每个候选机制（域级/个人级/两层混合）按四轴评分，标出不及格轴。
   - 完成标准: 打分表成文，无全轴及格时显式说明。
3. **设计叠加**：无单机制满足时设计两类叠加（域级全覆盖+个人级高价值操作），写明各自覆盖与责任边界。
   - 完成标准: 叠加职责表成文。
   - 判停条件: 封闭域内全员同构部署可行时，单机制即可。
4. **定粒度档**：跨域/联合场景按"对方需要知道多少"选粒度（账户/角色/机器链），不过度披露。
   - 完成标准: 粒度选择与理由成文。
5. **归档决策记录**：把四轴分+叠加方案写进选型决策记录，供后续审计。
   - 完成标准: 决策记录评审通过。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 把四轴当加权求和公式——追责轴在合同/法律场景是一票否决，加权平均会得出危险结论。
- 拿域级认证冒充个人追责（范围错配）或反之——四轴的意义正是阻止这类越界。

### 作者在书中警告的失败模式

- S/MIME 只签消息内容、头部发送源不受保护（ce090）——范围轴的具体代价要在打分时计入。

### 作者的盲点 / 时代局限

- 四轴谱系来自邮件域（成书 2017 前）；Passkey/平台认证器、企业数字员工签名等新机制书内无内容——新机制需按四轴自行打分，勿引用书内不存在的结论。

### 容易混淆的邻近方法论

- v42 对象分档（人/物维度）。
- v41 证据对齐（聚合结构）、v27 不可否认判定（追责轴展开）。
