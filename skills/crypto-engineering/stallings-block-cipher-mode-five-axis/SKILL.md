## I — 方法论骨架 (Interpretation)

分组密码只定义"一块怎么变"，模式决定"一串数据怎么处理"——模式是**适配应用**的技术，不提升算法强度。选型不靠习惯默认（"无脑 GCM"），靠五轴打分：

1. **开销轴**：填充、链接状态、每块额外运算（相对 ECB 的成本）。
2. **错误恢复轴**：第 i 块密文错误只影响恢复后少数明文块——噪声信道（无线、卫星）要它。
3. **错误传播轴**：第 i 块错误波及后续所有块——方向与上一轴**相反**：它帮助发现篡改（错误来自攻击而非信道），完整性敏感场景要它、还要另配 MAC。
4. **并行/随机访问轴**：能否并行加解密、能否直接跳到第 i 块（磁盘扇区、数据库、高速链路）。
5. **认证轴**：模式本身给不给完整性——多数不给，需 MAC/AEAD 另配。

关键辨析就是第 2、3 轴的反向关系：把"错误不传播"（OFB 优点）当全面优点，就漏了它抗篡改弱（密文翻转一位=明文翻转一位）。CTR 是五轴明星（并行、预处理、随机访问、只需加密实现），但有一条硬前提：**同一密钥下计数器全局唯一**——复用即密钥流复用，全盘皆输。选型输出应是"应用约束→五轴权重→模式+配套（IV/计数器管理、MAC）"的推导链。

## A1 — 书中的应用 (Past Application)

### 案例 1: CFB 与 OFB 的错误传播差异量化
- **问题**: 噪声信道上流式加密选哪个模式。
- **方法论的使用**: 按错误轴比较：CFB 的密文进移位寄存器，一块错误污染后续全部消息；OFB 的输出序列只依赖密钥与 IV，一位错误只影响对应明文位。
- **结论**: OFB 容忍信道误码但抗篡改弱（密文位取反=明文位取反，攻击者可同步改校验和）；IV 必须时变。
- **结果**: "错误容忍≠抗攻击"成为模式选型的显式权衡，完整性另配 MAC。

### 案例 2: CTR 六优点与唯一性硬前提
- **问题**: 高吞吐+随机访问场景（磁盘、高速链路）的模式。
- **方法论的使用**: [LIPM00] 六优点逐项核对：并行、软件效率、预处理、随机访问、可证明安全、简单（只需加密方向）。
- **结论**: CTR 成为部署默认的前提是计数器管理——"一个计数器的值使用了多次，对应明文分组的保密性就会泄露"。
- **结果**: 计数器状态被当作持久化状态管理（崩溃恢复不回退），并另配 MAC 补认证轴。

### 案例 3: WEP→TKIP→CCMP 的模式更换动因
- **问题**: 无线协议为何反复换模式。
- **方法论的使用**: 按五轴复盘：WEP 的 RC4+外部 CRC 在认证轴与错误传播轴全溃（线性校验可定向翻转）；TKIP 过渡修补；CCMP 直接换 AES-CCM（CTR+CBC-MAC 认证加密）。
- **结论**: 模式与校验的组合方式是协议成败变量，不只是算法变量。
- **结果**: 802.11i 以认证加密模式收口，五轴中"认证轴"的缺位被正面补上。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为特殊信道（卫星遥测高误码、工业总线、音频流）选模式，不能默认 GCM。
2. 存储加密/数据库字段加密需要随机访问，评估 CTR/XTS 的适用与计数器管理成本。
3. 评审"为什么这里用 CBC 不用 GCM / 为什么不用 ECB"的设计文档。
4. 嵌入式只有加密硬件（无解密引擎）或需要预处理降低在线时延的实现约束选型。

### 语言信号 (用户的话里出现这些就应激活)

- "block cipher mode 怎么选 / mode selection"
- "高误码信道加密 / 错误传播"
- "随机访问加密 / 磁盘加密模式"
- "CTR 的 counter/nonce 怎么管理"
- "为什么不能用 ECB"

### 与相邻 skill 的区分

- 与 `stallings-nonce-iv-one-time-constraints` 的区别: 那个是选定模式后的一次性参数硬约束清单（IV/nonce/计数器/k）；本 skill 是选定模式之前的五轴比较——先选后管，接口在"CTR 唯一性"处衔接。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **写应用约束**: 列出数据形态（块/流/随机访问需求）、信道质量（误码率）、性能约束（并行/预处理）、是否广播、完整性需求。
   - 完成标准: 五轴权重表（高/中/低）成形。
   - 判停条件: 若数据含多块结构化内容且方案候选含 ECB，直接否决 ECB，再继续比较其余模式。
2. **逐模式打分**: 对候选模式（CBC/CFB/OFB/CTR/GCM/CCM/XTS）逐轴打分，重点核对错误恢复与错误传播两轴的**方向**是否符合需求。
   - 完成标准: 打分表无空格；两轴结论附"容忍误码 or 发现篡改"的方向说明。
3. **定配套**: 为入选模式定 IV/计数器生成与管理方案、MAC/AEAD 配置、失败响应。
   - 完成标准: 配套项完整（IV 来源、唯一性保证、认证范围含 IV/计数器）。
4. **登记硬前提**: 把该模式的硬前提（如 CTR 全局唯一、CBC IV 不可预测）写成可测试的运维断言。
   - 完成标准: 每条前提有监控/告警手段。
5. **输出选型理由**: 一段可追溯的推导（约束→权重→模式→配套→前提），入设计文档。
   - 完成标准: 评审者可复现推导，无"经验默认"步骤。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 算法本身选型（AES 还是 ChaCha）——五轴评模式不评算法。
- 公钥加密的填充方案（OAEP 等）——那是随机化填充议题。
- 密钥分发与管理——模式选型假设密钥已正确到位。

### 作者在书中警告的失败模式

- ECB 加密结构化/长数据——确定性泄漏是结构性缺陷，"每块都加密了"不构成安全。
- 把错误容忍当完整性（OFB 教训）；或反过来在高误码信道用强传播模式导致可用性崩塌。
- CTR/OFB 的计数器/IV 复用——不是概率问题，是必破。
- 加密模式顺带做完整性（PCBC 交换块攻击）——认证必须独立构造。

### 作者的盲点 / 时代局限

- 五标准成形于 2000 年前后：认证加密（AEAD）当时刚起步，书中五轴的"认证轴"以"另配 MAC"为主答案，现代默认应先考虑 AEAD 一体模式。
- 第7版未覆盖 XTS 之外的存储新形态（对象存储、可搜索加密）与长度隐藏（填充/分块策略）轴。
- 广播/多播场景（一对多密钥流复用风险）书中仅点题未成轴。

### 容易混淆的邻近方法论

- 与"算法强度评估"：模式不提升强度——弱算法配好模式仍是弱系统，强算法配 ECB 也会漏。
- 与 nonce 管理规范（RFC/标准建议）：那些是选定模式后的执行细则；本 skill 决定"选哪个"并指出配套需求。
