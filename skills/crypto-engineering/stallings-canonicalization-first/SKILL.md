# 规范化先行与松紧权衡

## R — 原文 (Reading)

> "DKIM定义了两个头部标准化算法（simple和relaxed）和两个正文标准化算法（与前者相同。)其中simple算法几乎不容忍修改，而relaxed算法能容忍普通的修改。"
>
> — 方法论出处，第19章 19.9.3 DKIM 功能流程

---

## I — 方法论骨架 (Interpretation)

签名绑定的是字节，不是语义。消息只要经过中继（网关、邮件服务器、序列化库），空白、折叠、编码、键序都可能被无害地改写——验签随之失败。

所以凡对可改写对象做签名/哈希/比较，第一步不是选算法，而是定**规范化算法**，且规范化规则本身是安全协议的一部分，要与签名算法一起评审。

松紧是可量化的权衡：规范化决定了"哪些变形被视为相同"（等价类）。

- 过严（simple）：等价类最小、最安全，但中间环节任何改动都导致验签失败。
- 过宽（relaxed）：通过率高，但等价类内可被"合法"替换的空间变大——攻击者在等价类内换字段仍能验签通过。

选档要按信道实际改写情况定，并把等价类代价写成显式决策，而不是让序列化库的默认行为替你决定。

## A1 — 书中的应用 (Past Application)

### 案例 1: DKIM 的 simple/relaxed 两档（第19章）
- **问题**: 邮件经中继会出现行内空格、头域折叠等微小变化，严格签名必然验证失败。
- **方法论的使用**: 头域与正文各设两档标准化，两端在签名/验证前重复同一规范化，使规范值尽可能一致。
- **结论**: simple 几乎不容忍修改（默认严格），relaxed 容忍普通改写；实际部署（如 gmail）用 relaxed/relaxed——通过率优先，等价类代价显式接受。
- **结果**: DKIM 在真实邮件改写环境下可运转，成为域级签名的基础。

### 案例 2: S/MIME 规范格式（第19章 19.2.2）
- **问题**: 各系统本地格式（行终止符、字长、字节序）不同，同一消息在不同平台产生不同字节，跨平台签名校验必然失败。
- **方法论的使用**: 定义与内容类型对应的规范格式，作为所有端系统签名/验证/比较前的统一锚点。
- **结论**: 规范格式是 MIME 和 S/MIME 的重要概念——跨系统一致性的前提。
- **结果**: 跨平台签名验证可行。

### 案例 3: MD 结构的长度填充（第11章）
- **问题**: 任意长消息如何规范成压缩函数可接受的定长输入？
- **方法论的使用**: Merkle–Damgård 用长度域填充把消息规范化为定长块序列——规范化进入结构内部。
- **结论**: 规范化不只是协议附属品，密码结构本身就内嵌规范化步骤。
- **结果**: 同族思想统一了邮件标准化与 Hash 内部构造两类场景。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 跨微服务/跨语言的消息签名（JWS 类）频繁出现"签名对但验证失败"。
2. 文档/合同电子签章，中间经过格式转换（PDF 规范化、富文本清洗）。
3. 设计跨系统一致性校验（哈希去重、对账），同一数据两端哈希不一致。
4. 审计签名方案被绕过——怀疑规范化过宽，等价类内替换仍验签通过。

### 语言信号 (用户的话里出现这些就应激活)

- "签名对但验签失败 / signature valid but verification fails"
- "规范化 / canonicalization, canonical form"
- "中继/网关改写了消息体 / intermediary rewrites the payload"
- "同一份数据两端哈希不一样 / same content different hash"
- "strict 还是 lenient / simple or relaxed normalization"

### 与相邻 skill 的区分

- 与 `stallings-crypto-operation-ordering` 的区别: 那个决定操作谁在外层，本 skill 决定签名对象本身的字节形态；规范化永远排在签名前，是那条流水线的第一站，两者组合使用。
- 与 `stallings-evidence-alignment-binding` 的区别: 那个要求多个证据对齐到同一核心身份，本 skill 只关心单一对象内部的等价类；"两个签名都对但结论冲突"归那个 skill。
- 与"编码≠加密"误区（ce089）：Base64 传输编码是为过 7 位通道，不参与安全论证——不要把编码问题包装成规范化决策。

## E — 可执行步骤 (Execution)

1. **盘点改写点**：列出对象从签名到验证之间经过的全部中间环节（中继、序列化库、编码转换、存储引擎）。
   - 完成标准: 改写点清单成文，每处标注可能改变的字节形态。
2. **定规范化规则**：对每类改写写明规范化处理（键序、空白、Unicode 归一化、数值表示、行终止符），形成规格。
   - 完成标准: 规则规格成文，两端可各自独立实现并复算同一规范值。
   - 判停条件: 若对象不经任何中间改写（端到端原始字节），跳到步骤 4 只做锁定测试。
3. **选松紧档并列等价类**：写出"哪些变形被视为相同"的等价类清单，评估等价类内可被替换内容的业务风险，记录选档决策。
   - 完成标准: 等价类清单+风险判定+选档理由成文。
4. **锁定实现与测试向量**：两端固定序列化库版本或共享规范化实现；建双向测试向量。
   - 完成标准: 等价类内变形必须通过、类外修改必须失败的测试全部绿。
5. **把规范化写进接口契约**：与签名算法同级评审，版本化治理。
   - 完成标准: 契约文档含规范化规范引用与版本号。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 封闭系统内端到端原始字节传递（无改写点）——强行规范化只增加复杂度无收益。
- 传输编码类问题（Base64 让二进制过文本通道）——那是兼容性服务，不是安全决策。

### 作者在书中警告的失败模式

- 过宽规范化扩大等价类：可被合法替换的空间变大，签名验证通过不代表内容未被换。
- S/MIME 只签消息内容、RFC5322 头部发送源不受保护（ce090）——覆盖域缺口常被误认为规范化问题，需分开定位。

### 作者的盲点 / 时代局限

- 书中规范化讨论集中在邮件域（DKIM/S/MIME 规范格式），没有 JSON/JWS 签名实践；推导到 JSON 需自行补键序、数值、Unicode 归一化规则（成书 2017 前）。

### 容易混淆的邻近方法论

- 覆盖域审计（v29 的 MAC 覆盖）：字段在不在签名内 vs 字节形态是否一致，两个不同层面。
- 证据对齐（v41）：多证据对同一身份，不是单对象等价类。
