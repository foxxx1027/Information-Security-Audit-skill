# 挑战-应答设计判据

## R — 原文 (Reading)

> "由于消息是被会话密钥加密的，C可以确信此消息只可能由服务器V生成。消息中的内容确保该应答不是一个对以前消息的应答。"
>
> — 方法论出处，第15章 15.3.2（source.txt 行19950–19953，Kerberos 消息(6) TS+1）

---

## I — 方法论骨架 (Interpretation)

挑战-应答形态（"发随机数、回个值"）人人会画，安全性取决于四条判据：

1. **变换型应答，不是回显**：应答=对（挑战‖会话上下文）做带密钥的变换——Kerberos 的 TS+1（把认证码里的时间戳加 1 再用会话钥加密回传）是模板：能解出 TS+1 ⇒ 对方持钥（来源），且值来自我刚发的时间戳（新鲜，不是旧应答重放）。原样回显挑战值则可被反射/重放。
2. **权威应答三件套**：权威方（服务器/管理员）的签名应答应含——目标数据（你要的东西）+**请求回显**（防错配：确实是回答"这个"请求）+**新鲜性标记**（原始时间戳/nonce，防拿旧应答冒充新）。缺一件各对应一类攻击。
3. **明文与密文不得同现**：WEP 反例——AP 明文发挑战、STA 用流密码加密回送，攻击者异或二者即得该钥下密钥流，可伪造后续应答；且该协议只单向认证。挑战值绝不能与其流密码密文同时可见；配对码类秘密须经 KDF 折叠+CMAC 类带密钥变换，不当流密钥直接加密明文。
4. **证明共享≠共享**：双方算出同一密钥≠互相知道对方知道——需要显式密钥确认握手（四次握手模板：确认双方持有同一 PMK、确认协商套件未被篡改、派生新鲜会话钥），握手消息必须被派生出的密钥保护。

## A1 — 书中的应用 (Past Application)

### 案例 1: 公钥授权应答的三件套与代价
- **问题**: 向公钥管理员查询"B 的公钥"怎么防错配与重放。
- **方法论的使用**: 应答含 B 的公钥+A 原始请求回显+原时间戳，管理员私钥签名；代价是 7 条消息，靠缓存与周期刷新摊销。
- **结论**: "数据+回显+新鲜性"三件套是权威查询的标准构成，缺件各有对应攻击。
- **结果**: 该构成成为后续目录/证书协议（X.509 族）应答设计的参照。

### 案例 2: Kerberos TS+1 与 v5 的条件性省略
- **问题**: 服务器如何向客户端证明自己（双向认证）。
- **方法论的使用**: 消息(6) 把认证码时间戳加 1 用会话钥加密——变换证明持钥+新鲜；v5 省去"+1"因为攻击者无会话钥根本造不出消息(6)。
- **结论**: 应答变换的必要性随协议中对手伪造能力变化——按实际能力定价，不为仪式性步骤买单。
- **结果**: "变换型应答 vs 回显"成为认证协议审查的第一问。

### 案例 3: WEP 挑战认证反例
- **问题**: 教科书式的"明文挑战+加密回送"错在哪。
- **方法论的使用**: 三重解剖：明文挑战与其流密文同现⇒异或即得密钥流（可事后重放应答冒充）；只单向认证 STA，AP 未自证；无与会话绑定的新鲜性。
- **结论**: 形似挑战-应答不等于安全——判据逐条不满足。
- **结果**: 802.11i 以 802.1X/EAP 双向认证+四次握手（密钥确认）取代，反例成为判据的教学载体。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计设备配对/登录二次验证的挑战-应答（蓝牙数字比较、扫码确认、动态口令）。
2. 评审回调/唤醒类协议的应答构造（能否反射、能否重放旧应答）。
3. 握手协议审查：协商结果是否被派生密钥保护（防降级改套件）。
4. 事故分析：疑似重放/冒充的认证流，按判据定位缺陷。

### 语言信号 (用户的话里出现这些就应激活)

- "challenge-response 怎么设计 / 应答回什么"
- "nonce 挑战会不会被重放 / 反射攻击"
- "key confirmation / 密钥确认要不要"
- "配对码/OTP 直接加密挑战行不行"
- "握手消息要不要加密"

### 与相邻 skill 的区分

- 与 `stallings-anti-replay-window-engineering` 的区别: 那个管消息层的防重放机制选型（nonce/时间戳/序号窗口工程）；本 skill 管挑战-应答**应答本身的构造**——新鲜性判据与窗口工程衔接但不同层。
- 与 `stallings-protocol-belief-analysis` 的区别: 那个是全协议的设计者断言/攻击反例三步法；本 skill 是其中应答构件的局部判据——先用本 skill 造对构件，再拿三步法整审。
- 与 `stallings-nonce-iv-one-time-constraints` 的区别: 那个管一次性参数不复用；本 skill 管挑战如何被变换着回应——一个管"料"，一个管"用法"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **写消息流**: 画出挑战的生成、发送、应答计算、验证四步，标明每步谁持什么密钥。
   - 完成标准: 消息流图+密钥持有表成文。
2. **核应答构造**: 检查应答是否为"对（挑战‖上下文）的带密钥变换"，上下文含会话标识与双方身份（防错配/反射）。
   - 完成标准: 应答公式成文；无"原样回显挑战"分支。
   - 判停条件: 若挑战明文与其（流密码）密文可能同时被观测，直接判泄露密钥流，先改构造（KDF+CMAC/签名），其余审查暂停。
3. **核三件套**: 权威应答含目标数据、请求回显、新鲜性标记吗？新鲜性来源（nonce/时间戳）依赖什么（时钟同步？）？
   - 完成标准: 三件套核对表；时钟依赖显式登记。
4. **核密钥确认**: 双方"互相证明持有"是否由显式握手完成、握手消息是否被派生密钥保护、失败是否断开。
   - 完成标准: 密钥确认路径成文；无"算了同一密钥即算认证"的假设。
5. **攻击推演**: 对成品跑三类推演——重放旧应答、反射（把挑战转给真正持钥者）、明密文对抽取。
   - 完成标准: 三类推演各被一个具体设计元素挡住；推演记录入测试用例。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 整协议的信念/时序分析（Needham-Schroeder 类审查）——用协议三步法，本 skill 只供构件。
- 防重放窗口/序号管理的工程参数——防重放机制选型的事。
- 纯令牌传递（Bearer token）体系——那是bearer 语义，无挑战-应答结构。

### 作者在书中警告的失败模式

- 应答=回显（可反射/重放）；挑战明文与流密文同现（WEP）。
- 单向认证：只验客户端，服务器不自证（中间人空间）。
- 省略密钥确认：算出相同密钥就开聊——"共享秘密"未获证明。
- 仪式性堆叠：v5 省略 TS+1 的理由说明判据按对手能力定价——反向教训是别为已不存在的对手保留死代码。

### 作者的盲点 / 时代局限

- 跨设备配对（蓝牙数字比较、PAKE 类协议）在书中无对应词条——判据可迁移，协议形态需自行引入现代 PAKE 知识。
- 手机推送/异步回调场景的"挑战生存期与重试语义"未覆盖（挑战重用窗口是新型事故面）。
- 隐私保护认证（匿名凭证、环签名应答）不在此框架内。

### 容易混淆的邻近方法论

- 与 OAuth 类授权码流程: 那是授权语义（谁允许谁访问什么）；本 skill 是认证语义（证明持钥）——常组合，勿混审。
- 与"加盐比较"（把口令 hash 后比对）: 那是一次性静态比较，无新鲜性结构——对在线冒充无抵抗力，不是挑战-应答。
