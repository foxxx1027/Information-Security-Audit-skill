## I — 方法论骨架 (Interpretation)

传输加密的威胁模型（流式、攻击者短暂接触密文、无写权限）不能照搬到存储场景。正确顺序是**先列约束、再反推构造**：

1. **列攻击面**：谁能读密文（数据库部分授权、介质被盗、云运营商）？**谁能写介质**（可写对手是存储特有威胁——CTR 下改密文对应位即改明文）？数据版面能否改变？
2. **列功能代数**：系统要用哪些操作——等值查询？范围比较？随机访问第 i 块？密文必须等长（原地重写）？必须保格式（16 位卡号仍是 16 位数字）？
3. **反推约束并显式取舍**：P1619 是范本——密文与明文等长（排除填充）、分组独立随机访问（排除链接）、同位置重写同密文（防块搬移检测的**刻意取舍**，代价是泄漏"块未变"）。XTS 的 i/j 双参数、密文窃取的末块处理都是这些约束的解。
4. **可逆性是底线**：格式约束不能靠取模/截断实现（128 位 AES 输出 mod 10 不可逆）；任何"格式化输出"方案先验双射性。
5. **查询代数逐项判活**：把密文当数据库引擎用之前，列出全部查询类型逐项检查"加密后是否存活"——范围查询死于"密文不保序"，这是结构事实不是实现 bug。

输出应是"约束清单 → 被排除的方案 → 选定构造 + 显式记录的取舍"，而非"先加密再说"。

## A1 — 书中的应用 (Past Application)

### 案例 1: P1619 七条要求——威胁模型反推的范例
- **问题**: 磁盘加密为什么不能直接用 CBC/CTR。
- **方法论的使用**: 从攻击面（密文可被随意获取、介质可被盗、**对手可写**）与版面约束反推出七条：密文明文等长、以 16 字节分组独立加密、除位置外不用元数据、同位置重写同密文、互操作。
- **结论**: 传输模式在此失效——CTR 可被改位、CBC 可由位置副本推 IV；需求清单本身由威胁模型生成。
- **结果**: XTS-AES（双密钥、i/j 双 tweak、密文窃取）成为标准解，七条逐项落地。

### 案例 2: FPE 的可逆性反例
- **问题**: 怎么让密文仍是 16 位十进制数。
- **方法论的使用**: 检查朴素方案：AES 加密 128 位再逐元素 mod 10——格式对了，但 12 mod 10=2 mod 10，不可逆，解密无从谈起。
- **结论**: 格式约束必须以整体可逆的构造实现（Feistel 模加/模减结构），并满足五条设计要求（同格式、多字母表、变长、近 AES 强度、短明文不降级）。
- **结果**: FPE 成为"不改 schema 的遗留系统加密"专门技术，但其安全裕度需单独评估（等价类问题另议）。

### 案例 3: 云加密数据库——功能代数先于加密
- **问题**: 整表加密上云后"照常用"行吗。
- **方法论的使用**: 列查询代数逐项判活：关键词搜单条须整表下载解密；等值检索可靠加密主键勉强支撑；范围查询（工资<X）直接失效——密文集合不保留大小顺序。
- **结论**: 加密抹掉数据的顺序与代数性质；功能需求必须在加密设计阶段推演，"灵活性换泄露面"的取舍要显式写进方案。
- **结果**: 图16.10 四实体方案（加密主键+未加密索引表划分）作为带取舍记录的折衷输出。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计磁盘/对象存储/备份加密（原地重写、随机访问、等长约束）。
2. 数据库字段加密但业务要求等值查询/范围查询仍可用。
3. 遗留系统（COBOL、定长字段）要加密但不能改 schema——FPE 评估。
4. 合规驱动的"加密上链/上云"方案评审（先加密再谈功能 vs 先列功能再选构造）。

### 语言信号 (用户的话里出现这些就应激活)

- "磁盘/存储加密用什么方案 / XTS"
- "encrypted database / 加密后还能范围查询吗"
- "format-preserving / FPE / 保持格式加密"
- "密文必须和明文一样长 / 原地重写"
- "先加密上云再说"

### 与相邻 skill 的区分

- 与 `stallings-deterministic-leak-tweak-binding` 的区别: 那个深入"相等关系泄漏与 tweak"这一具体判据；本 skill 是完整的反推流程（攻击面+功能代数→构造），tweak 是流程中的一种输出。
- 与 `stallings-block-cipher-mode-five-axis` 的区别: 五轴评传输侧模式选型；本 skill 处理传输假设失效的存储/功能受限场景——"可写对手"与"版面约束"是五轴之外的输入。
- 与 `stallings-security-solution-four-elements` 的区别: 四要素管方案完备性（算法/密钥/协议）；本 skill 管算法之前的**需求约束推导**。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列攻击面**: 写明谁能读密文（含十年后的读）、能否写介质、数据版面可否改变、密文生命周期。
   - 完成标准: 三项各有明确答案；"可写对手"一栏不可缺省。
2. **列功能代数**: 枚举业务对数据的全部操作（等值/范围/排序/聚合/随机访问/等长/保格式），逐项标"必须/可选/可放弃"。
   - 完成标准: 功能清单获业务方确认；每项标注放弃的代价。
3. **反推约束**: 由攻击面+功能清单推导硬约束集（等长？随机访问？确定性？可逆域？），排除不满足的构造。
   - 完成标准: 每个"被排除方案"附违反的具体约束编号。
   - 判停条件: 若约束集自相矛盾（如"完全隐藏相等关系"+"必须等值查询"且不可分层），停止选型，先回业务重谈约束——没有诚实的构造能满足矛盾约束。
4. **选定构造并记录取舍**: 选 tweakable/窃取/FPE/分层列等构造，把每条刻意保留的泄漏（同位置确定性等）写进设计文档。
   - 完成标准: 取舍表（保留性质/泄漏性质/理由）成文；可逆性经小域枚举验证。
5. **攻击推演回归**: 按"可写对手定向篡改、等价类撞库、范围/顺序泄漏"三条路各推演一次。
   - 完成标准: 三条路均有对策或显式风险接受；推演用例入回归测试。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 传输/会话加密（TLS 类）——无版面与随机访问约束，走模式五轴。
- 通用协议设计与密钥管理——本 skill 假设密钥已就位，只管数据面构造。
- 纯访问控制问题（谁能读）——加密不是权限模型的替代品（加密数据库案例中 DoS/损坏威胁依然有效）。

### 作者在书中警告的失败模式

- 传输模式不加改造用于存储（CTR 改位、CBC 推 IV 的双反例）。
- 取模/截断实现格式约束（不可逆即不可部署）。
- "先加密上云再谈功能"——范围查询失效在部署后才被发现。
- 忽略可写对手：只想着"读不了"，没想过"改得了"。

### 作者的盲点 / 时代局限

- 第7版（2017 前后）的可搜索加密/保序加密研究刚起步：书中对范围查询只给"未加密索引+表划分"的老办法，未覆盖 OPE/ORE 及其泄漏谱系——现代设计需把泄漏抽象纳入取舍表。
- 存储完整性（防回滚/块搬移检测）在 P1619 语境下被取舍掉，配套方案（如默克尔树、dm-verity 类）书中未展开。
- 云原生形态（托管 KMS、信封加密、按列策略）缺位。

### 容易混淆的邻近方法论

- 与"分层加密/信封加密": 那是密钥组织方式（数据密钥+密钥加密钥）；本 skill 是数据面构造的约束推导——两者正交，常组合。
- 与数据库透明加密（TDE）: TDE 解决"介质被盗"，不解决"数据库管理员/查询功能"——攻击面对不上时 TDE 不适用，正是本 skill 第 1 步要判的。
