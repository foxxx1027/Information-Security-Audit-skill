# 凭据拆分与协商摊销

## R — 原文 (Reading)

> "如果生命期太短（如几分钟），则用户将被要求重复输人口令；而如果生命期太长（如几小时）则为攻击者提供了大量攻击机会。"
>
> — 方法论出处，第15章 15.3.2 Kerberos 版本4

---

## I — 方法论骨架 (Interpretation)

单一寿命参数同时承担两类相反的损失函数（打扰用户 vs 资助攻击），**没有可行中间值**——这是参数两难，不是调参问题。正确解法是给系统加一维：把凭据拆成两类，各管一件事、各配各的寿命：

1. **可重用载体凭据**管分发摊销（票据/refresh 类：长生命、可撤销、走安全存储）；
2. **一次性使用证明**管身份绑定（认证码/access 类：短生命、scope 受限、一次一用）。

拆分之后"有效期调多长"的争论消失，变成"两层各配各的寿命"。配套三条设计律：策略差异（可续期/可转发/可代理）用可协商标志位编码进凭据内部，而不是另起协议分栈；昂贵的一次性协商产出可复用句柄（会话），廉价操作随用随取，故障以最小单元隔离（断连接不断会话）；工作密钥必须新鲜——会话内再派生子密钥，票据密钥只做认证不做数据加密。

## A1 — 书中的应用 (Past Application)

### 案例 1: Kerberos 票据与认证码职责分离（第15章）
- **问题**: 票据生命期两难无解（太短重复输口令、太长攻击窗口大）。
- **方法论的使用**: 拆分——票据（可重用，管分发）配认证码（一次性，会话钥加密的 ID+地址+时间戳，管"此刻是本人"）；v5 再加 RENEWABLE 双重有效期、FORWARDABLE/PROXYABLE 标志族与子会话密钥。
- **结论**: 两类凭据各配寿命后，单一参数的矛盾被结构消除。
- **结果**: 成为可运营的认证体系；v5 标志位机制把策略差异装进凭据本身。

### 案例 2: TLS 会话/连接两层（第17章）
- **问题**: 完整握手昂贵，每连接重做不可承受。
- **方法论的使用**: 摊销结构——昂贵握手产出会话（可复用句柄），恢复时用会话标识廉价再造连接；致命警报只断当前连接、不断会话。
- **结论**: 故障以最小单元隔离；协商成本按会话摊销到多条连接。
- **结果**: 会话恢复成为 TLS 标准能力，"断连接不断会话"成为容错语义。

### 案例 3: 换钥频率按形态定档（第14章）
- **问题**: 密钥多久换一次？
- **方法论的使用**: 同族分档思路——面向连接与无连接协议各配各的换钥频率（连接型按会话、无连接型按数据量/时间），不一刀切。
- **结论**: 频率参数与信道/凭据形态绑定，而非全局常数。
- **结果**: 密钥层次的时间维度与 v32 的数量维度合成完整的密钥治理。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计 API 凭证体系（raw API key 泄露频发，要重构）。
2. SSO/会话 token 结构设计（access/refresh 分层、续期策略）。
3. 长生命周期凭证的续期与撤销策略（设备注册、服务账户）。
4. 故障隔离设计——凭据失效要不要连坐整个会话。

### 语言信号 (用户的话里出现这些就应激活)

- "token 有效期多长合适 / token lifetime trade-off"
- "refresh token 和 access token / two-tier credentials"
- "API key 又泄露了 / raw API key leaked"
- "会话恢复 / session resumption"
- "凭证可以续期吗 / renewable credential"

### 与相邻 skill 的区分

- 与 `stallings-revocation-as-propagation` 的区别: 那个分析"失效何时生效"的时间语义（撤销是传播问题），本 skill 生成凭据结构消除两难——本 skill 产出的长寿命层仍需那个的撤销语义，组合使用。
- 与 `stallings-key-counting-hierarchy` 的区别: 那个拆密钥的数量与频次层次，本 skill 拆凭据的职责与寿命——数量维度 vs 职责维度。
- 与 `stallings-auth-assurance-tiering` 的区别: 那个拆"验什么对象、要多确信"（对象/档位），本 skill 拆"凭据怎么活得久又安全"（结构/寿命）。

## E — 可执行步骤 (Execution)

1. **识别两难参数**：列出陷入"太短损失 vs 太长损失"的单一参数（寿命、权限范围、作用域）。
   - 完成标准: 两难表成文（两端损失各自量化）。
   - 判停条件: 若单一短命一次性凭据已满足（低价值、低频操作），无需拆分。
2. **拆职责**：把参数背后的职责分开——分发摊销（可重用载体）与使用绑定（一次性证明），各配独立凭据与寿命。
   - 完成标准: 两类凭据的定义、寿命、存储要求成文。
3. **策略进凭据**：把可续期/可转发/可代理等差异写成凭据内标志位/claims，并为每个标志位定默认值。
   - 完成标准: 标志位清单+默认策略成文。
4. **设计摊销与隔离**：昂贵协商→可复用句柄→廉价操作随用随取；定义失效单元（哪层失效连坐什么）。
   - 完成标准: 摊销路径图+失效连坐表成文。
5. **强制工作密钥新鲜**：会话内每次或定期派生子密钥，载体凭据密钥不直接加密业务数据。
   - 完成标准: 派生规则成文，历史会话不因载体凭据长期存活而连坐。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 低价值场景可用一次性短命凭据解决时——拆分只增加复杂度。
- 把长寿命层当保险箱：refresh/载体凭据失陷等于全部短命凭据的源头，必须配安全存储与撤销通道（v34）。

### 作者在书中警告的失败模式

- 会话密钥随票据反复重用：同一密钥保护的密文量随访问次数累积，票据密钥泄露则生命周期内所有历史会话连坐（ce063）——所以工作密钥必须新鲜。
- 票据生命期两难的原文警告（本 skill 的 R 段）。

### 作者的盲点 / 时代局限

- 书中拆分形态以 Kerberos/TLS 为原型（成书 2017 前），OAuth 的 refresh/access 词汇书内没有——推导到 API token 体系时需自行映射概念，勿直接引用 OAuth 细节为书内内容。

### 容易混淆的邻近方法论

- v34 撤销语义、v32 密钥层次、v42 对象分档。
