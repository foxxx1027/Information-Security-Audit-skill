# 密码操作次序纪律与可仲裁性

## R — 原文 (Reading)

> "注意这里是先进行签名，然后才执行外层的加密，这样在发生争执时，第三方可以查看消息及其签名。若先对消息加密，然后才对消息的密文签名，那么第三方必须知道解密密钥才能读取原始消息。"
>
> — 方法论出处，第13章 13.1.4 数字签名（签名与加密的次序）

---

## I — 方法论骨架 (Interpretation)

签名、加密、压缩、MAC 的先后次序不是实现细节，而是"谁在什么时刻能看见什么、能为争议作证"的分配决策。

判断次序的三个抓手：
1. **可仲裁性**：争议发生时第三方能否不持解密密钥就核验签名？能，则签名必须在加密边界之内（先签名后外层加密）。
2. **改写敏感性**：压缩等可变变换必须在签名之前；加密之后通常不可再压。签名绑的是字节，任何签名后的改写都会破坏验证。
3. **覆盖域语义**：MAC/ICV 覆盖哪些字段，就只防那些攻击——漏版本域=降级攻击面，漏序号=重放面，漏接收者=签名可被搬运。

组合方案按"认证覆盖面 × 开销 × 信息可保留"三角打分比选，而不是默认某个顺序。次序选择要写成契约条款（协议规范/接口文档），不能是实现巧合。

## A1 — 书中的应用 (Past Application)

### 案例 1: 仲裁需求决定"先签名后加密"（第13章）
- **问题**: 直接签名的效力完全押在私钥保密上，且双方争议时如何让中立第三方裁决？
- **方法论的使用**: 按可仲裁性判据排次序——签名留在加密边界之内，第三方查看明文与签名即可裁决；若对密文签名，第三方必须先拿到解密密钥，中立性丧失。
- **结论**: 先签名后外层加密；接收方还应存储明文形式的签名以备将来争执。
- **结果**: 成为 S/MIME 等协议的次序惯例，仲裁路径与保密性同时成立。

### 案例 2: ESP 的 ICV 对密文计算（第20章）
- **问题**: 认证与解密谁先做？解密昂贵，伪造包不应消耗解密资源。
- **方法论的使用**: 覆盖域与次序三角权衡——ICV 覆盖密文而非明文，验证在解密之前完成。
- **结论**: 先验 ICV 再解密，伪造/重放包在昂贵操作前被丢弃（抗 DoS），代价是认证对象是密文。
- **结果**: 与 SA 组合三案一起按"认证覆盖面×开销×信息可保留"三角定型为 IPsec 标准。

### 案例 3: TLS MAC 覆盖域补版本字段（第17章）
- **问题**: SSLv3 的 MAC 不含协议版本域，中间人可以把连接降级到弱版本。
- **方法论的使用**: 逐字段问"这个字段不进 MAC 会导致什么攻击"——版本域缺失=降级面。
- **结论**: TLS 把 seq‖type‖version 全部纳入 MAC 覆盖。
- **结果**: 降级类篡改被 MAC 拦截，覆盖域逐字段语义成为 TLS 记录层规范的一部分。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计 API 网关/微服务消息管线："签名+加密+WAF 留日志"的流水线怎么排。
2. 设计需要第三方仲裁或归档离线验证的业务消息（电子合同、审计存证）。
3. 评审协议时发现降级或重放漏洞，怀疑 MAC/签名覆盖域缺字段。
4. 设计存储加密+完整性组合（先加密后 MAC 还是反之）。

### 语言信号 (用户的话里出现这些就应激活)

- "先签名还是先加密 / sign-then-encrypt vs encrypt-then-sign"
- "签名放加密边界里面还是外面 / signature inside or outside encryption"
- "MAC 要覆盖哪些字段 / what fields should the MAC cover"
- "第三方要能不拿密钥验签 / third party must verify offline"
- "压缩和签名的先后 / compression before or after signing"

### 与相邻 skill 的区分

- 与 `stallings-cheap-check-first` 的区别: 那个是成本/DoS 视角的排序（便宜检查先做），本 skill 是可见性/责任视角的次序学；ESP 的 ICV 前置是交叉点，但那个解释"为什么前置"，本 skill 解释"覆盖域防什么"。
- 与 `stallings-canonicalization-first` 的区别: 那个决定签名对象本身的字节形态（签什么），本 skill 决定各操作谁在外层（怎么排）；规范化永远排在签名之前，是本流水线的第一站。
- 与 `stallings-anti-replay-window-engineering` 的区别: MAC 覆盖序号防重放的机制选型归那个 skill，本 skill 只负责覆盖域的逐字段语义登记。

## E — 可执行步骤 (Execution)

1. **列出流水线全部候选操作**：规范化、压缩、签名、加密、MAC、日志/归档。
   - 完成标准: 操作清单成文，标注每个操作的存在理由。
2. **对每对相邻操作问三问**：改写敏感性（可变变换是否都在签名前）、可见性需求（签名是否必须留在加密内）、仲裁需求（第三方无密钥可验吗）。
   - 完成标准: 每对相邻操作的三问有书面回答。
   - 判停条件: 若消息不经任何不可信中继改写、且无仲裁/归档需求，直接跳到步骤 5 并采用标准 AEAD 组合。
3. **逐字段列 MAC/签名覆盖域清单**：每个被覆盖字段标注"防什么攻击"，空白格逐个解释（是漏项还是已论证不需要）。
   - 完成标准: 覆盖域表无未解释空白。
4. **按三角打分比选**：对 2–3 个候选次序按"认证覆盖面×开销×信息可保留"评分，记录胜出理由。
   - 完成标准: 评分表与决策理由成文。
5. **写成契约条款**：把选定次序与覆盖域写进协议规范/接口 schema，标注每步理由。
   - 完成标准: 实现者无需猜测次序；第三方仲裁路径（如有）已实际演练。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已采用标准 AEAD（GCM/CCM）且无外层归档/仲裁需求的场合——不要自创组合次序。
- 单机存储加密（无中继改写、无第三方仲裁）——次序自由度不构成安全差异。

### 作者在书中警告的失败模式

- 先加密后签名使仲裁第三方必须持解密密钥，中立性丧失（第13章 13.1.4）。
- WEP 的 H→E 组合存在根本缺陷导致整个协议被取代——组合次序本身是安全决策（第12章）。
- SSLv3 MAC 漏版本域的降级面（第17章）。

### 作者的盲点 / 时代局限

- 成书于 2017 前：认证加密讨论止于 CCM/GCM，未覆盖 Signal 双棘轮等现代分层结构；"Encrypt-then-MAC vs MAC-then-Encrypt"的学术争论只在 WEP 案例中侧面提及，未给出一般性判据。

### 容易混淆的邻近方法论

- "fail fast"性能排序（v31）——目标不同，勿混用论据。
- 规范化（v30）——解决签名对象一致性，不是次序问题。
