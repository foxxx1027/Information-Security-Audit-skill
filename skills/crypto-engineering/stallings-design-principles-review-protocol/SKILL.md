# 安全设计准则的清单化治理：张力登记与独立性检验

## R — 原文 (Reading)

> "虽然已经有了多年的研究和开发，但目前仍然没有一种安全设计或实现技术能够系统地摒除安全漏洞、阻止所有的非授权行为。"
>
> — 方法论出处，第1章 1.6 基本安全设计准则（source.txt 行1571区）

---

## I — 方法论骨架 (Interpretation)

设计准则的价值不在"知道这 13 条"，而在三条使用纪律：

1. **准则是不保证的启发式**：没有哪条能确保安全。所以评审的输出不是"已满足"的勾选表，而是**"违反项 + 补偿控制"登记表**——发现违反经济性（设计太复杂），就登记"复杂度风险"并配测试补偿；发现违反完整监察（访问决策吃了缓存），就登记"撤销延迟"并配传播机制。
2. **准则之间有张力，要管理而不是假装消解**：机制经济性（越简单越好）与完整监察（每次访问都裁决）互相顶牛；心理接受度（不能把用户逼到绕过）会限制强制点的强度。承认张力、写下取舍理由，比硬凑"全部满足"诚实。
3. **多层防御要做独立性检验**：分层只有当各层不同因失效才是纵深；三层防护若共享同一口令、同一库、同一管理员，只是同一控制重复计数三遍（伪纵深）。作者自己也示范了登记落差：经济性"最难遵循"、完整监察"现实中很少使用"——教材作者把落差写成已知风险，这正是评审该有的输出格式。

## A1 — 书中的应用 (Past Application)

### 案例 1: 作者对 13 条准则的自我落差登记
- **问题**: 准则若被当成"照做即安全"，读者无法定位真实工程差距。
- **方法论的使用**: 作者逐条评注：机制经济性"实践中最难遵循"（新特性需求不断复杂化设计）；完整监察"这种资源密集监察型方法很少使用"（典型实现是打开文件后不再检查）。
- **结论**: 准则与工程现实之间存在已知落差，落差本身应显式登记。
- **结果**: 读者拿到的是带自评的准则清单——违反不是意外，而是可预期的登记项。

### 案例 2: VM 隔离与 MAC 过滤的"必要非充分"判级
- **问题**: 多租户 IaaS 的隔离、无线网络的 MAC 过滤，都被 vendor 当作充分方案宣传。
- **方法论的使用**: 用准则检验单一机制的定位：第16章明确独立虚拟机"只能是这个安全策略的一部分"（虚拟化隔离必要非充分，需叠配置监测、强认证、SLA、审计）；第18章对 MAC 过滤同样判"仅是策略元素之一"。
- **结论**: 单一机制在准则框架下的正确定位是"策略的一部分"，不是策略本身。
- **结果**: 两处均给出配套控制清单，构成纵深而非单点依赖。

### 案例 3: 密码工程中的权限分离实现
- **问题**: 最小权限/权限分离如何落到密码系统设计。
- **方法论的使用**: 第13/14章把 DSA 的用途单一化、控制向量机制作为最小权限与权限分离在密钥管理层的实现形态。
- **结论**: 准则可以下推到密钥用途与控制粒度，不止于操作系统权限。
- **结果**: 准则从架构词汇变成密码工程可核查项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 架构评审/设计文档安全章节审查，需要产出结构化结论（而不是"总体没问题"）。
2. 检查"我们已经有三层防御/多因子/隔离"的方案是否是伪纵深（层间同因失效）。
3. 评估安全机制的可用性风险：控制是否把用户逼成绕过者（心理接受度）。
4. 给智能门锁、IoT 固件等带人机交互的系统做安全评审出结论。

### 语言信号 (用户的话里出现这些就应激活)

- "过一遍 security design principles / 安全设计准则"
- "符合 least privilege / 最小权限吗"
- "我们有 defense in depth / 三层防御，够了吗"
- "这个控制用户会不会绕过 / 用户嫌麻烦怎么办"
- "评审结论怎么写 / 帮我出评审发现"

### 与相邻 skill 的区分

- 与 `stallings-attack-surface-shrink-then-layer` 的区别: 那个管攻击面的测绘收缩与分层的**部署决策**；本 skill 管已部署设计的**准则符合性评审**与登记输出。分层在两边都出现：那边定在哪加层，这边检验层间是否独立。
- 与 `stallings-attack-service-mechanism-alignment` 的区别: 对齐矩阵查威胁覆盖；本 skill 查设计质量（简不简、默认拒不拒、可不可接受），两者是评审的两个轴。
- 与通用 checklist 审计的区别: 本 skill 的差异是张力管理与"违反项+补偿控制"的输出格式，不是打勾。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **取准则清单**（经济性/故障安全默认/完整监察/开放设计/权限分离/最小权限/最小共同机制/心理接受度/隔离/密封/模块化/分层/最小意外），逐条对照被评审设计。
   - 完成标准: 每条准则有"符合/违反/不适用"三态标注。
2. **违反项取证**: 对每个"违反"写明具体表现（哪个机制、哪种用法）与触发条件。
   - 完成标准: 无泛泛的"可能不满足"，每条违反能指到设计的具体部位。
3. **配补偿控制**: 为每个违反项指派补偿（如心理接受度违反 → 降低摩擦的上限设计；完整监察违反 → 撤销传播与缓存键绑定）。
   - 完成标准: 每个违反项有补偿控制或显式的风险接受声明。
   - 判停条件: 若某违反项既无法补偿、又落在关键资产上，直接判"设计退回"，不再继续其余条目。
4. **独立性检验**: 对设计中所有"多层"结构，逐组问"这些层是否共享同一失效因（同口令/同库/同管理员/同厂商）"。
   - 完成标准: 每组多层结构有"独立/同因"判定；同因者重标为单层。
5. **输出登记表**: 准则条目 / 状态 / 违反表现 / 补偿控制 / 残余风险。
   - 完成标准: 登记表可直接进设计文档的风险章节，结论非"安全/不安全"二元。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 具体漏洞/渗透验证：准则评审不替代渗透测试与代码审计（书中明示准则"不替代具体威胁分析与渗透验证"）。
- 威胁枚举与覆盖：准则不告诉你对手会打哪，用对齐矩阵/攻击树。
- 合规映射（等保/SOC2 条款对照）：那是条款映射工作，不是启发式评审。

### 作者在书中警告的失败模式

- 把准则勾选当结论：违反项必须登记为已知风险，"已满足"式的全勾评审是自欺。
- 伪纵深：多层同因失效只是重复计数（pr010 失效边界明示）。
- 权限分离的同源假分离：多条件共享同一失效因（同源泄露、同一台主机）不构成真正分离（pr006）。
- 心理接受度被忽视：机制被用户绕过即失效，UX 是安全属性。

### 作者的盲点 / 时代局限

- 13 条前 8 条出自 1975 年 Saltzer-Schroeder：书中未覆盖供应链完整性、CI/CD 管道、零信任、密钥托管与可审计性等现代议题（第21–24章系统安全在本书为在线部分，正文缺失）。
- 准则间张力的处理书中只点名（经济性 vs 完整监察），未给权衡流程。
- 开放设计准则在 AI/ML 组件与专有固件时代的适用边界书中未讨论。

### 容易混淆的邻近方法论

- 与 NIST SSDF/安全开发生命周期: 那些管流程节点；本 skill 管设计时刻的质量判据。
- 与"纵深防御"口号: 本 skill 把纵深降为一条准则并加上独立性检验——"有几层"不是结论，"层间是否同因失效"才是。
