# 证据绑定与对齐聚合

## R — 原文 (Reading)

> "找到Bob的邮件、去掉其签名并换成自已的，后将邮件传送给Alice，最终Max会得到该想法的所有权。"
>
> — 方法论出处，第15章 15.4.2 单向认证（签名剥离替换攻击）

---

## I — 方法论骨架 (Interpretation)

多因子/多层验证的强度不由因子数量决定，而由**对齐结构**决定：每个证据各自锚定不同的标识（IP、密钥、域名、设备），攻击者只需攻破最松的一条链进入——证据各自为政等于没有证据。

聚合有效的条件是：所有认证链最终**对齐到同一个核心身份**，且这个身份必须是用户可见、不可绕过的（DMARC 选 RFC5322 From 域，因为它展示给用户且是被冒用的首要目标）。

签名类证据有第二条定律——**三方绑定**：签名必须绑定内容+发送者+接收者。明文可见的签名是可搬运的数据，可被整体剥离重签（Max 抢创意）。

第三条是**范围对齐**：保护范围必须与声称的保证对齐——只签消息内容不等于发送源头域可信（S/MIME 头部缺口）。

签名与对象解耦也有正面用法：作为独立证据文件存档（代码签名、审计日志），按需选择绑定形态。

## A1 — 书中的应用 (Past Application)

### 案例 1: DMARC 标识符对齐（第19章）
- **问题**: SPF（认证 IP 与信封域）和 DKIM（认证签名域）都通过时，用户看到的 From 域就可信了吗？
- **方法论的使用**: 对齐检查——要求 From 域与 DKIM 签名域或 SPF 已认证域对齐；两个弱判定只有聚合到用户可见的 From 域上才产生强判定。
- **结论**: 不对齐时，攻击者可通过的 SPF/DKIM 与展示的 From 无关，防伪失效。
- **结果**: DMARC 以 From 对齐为核心机制，补上了 SPF/DKIM 的判定缺口。

### 案例 2: 签名剥离替换（第15章）
- **问题**: 单向认证邮件发 M‖E(PR_a,H(M))，签名在密码学上不可伪造，为何创意仍被窃取？
- **方法论的使用**: 三方绑定检查——签名与消息明文穿越开放系统，Max 剥掉 Bob 的签名换上自己的，Alice 验签照旧通过。
- **结论**: 缺接收者绑定时签名可被整体搬运；修正配方=消息与签名整体用接收者公钥加密，内容、发送者、接收者绑定为一体。
- **结果**: 修正方案进入认证协议设计；公钥新鲜性另配证书保证。

### 案例 3: S/MIME 范围错配（第19章）
- **问题**: 部署端到端 S/MIME 签名后，"邮件有了数字签名，发件人字段可信"成立吗？
- **方法论的使用**: 范围对齐检查——签名仅覆盖消息内容，RFC5322 头部发送源字段不在签名范围，头部可被中途改写而签名依旧有效。
- **结论**: 只签内容≠头部可信；保护范围与声称保证错配是体系性缺口。
- **结果**: 推动把关键头域纳入签名覆盖（DKIM 签正文+选定头域）并与 From 对齐联动。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 多层验证体系被绕过的排查（webhook 三层验证：IP 白名单+HMAC+来源域）。
2. 设计聚合风控/认证判定——多个弱信号如何合成一个身份结论。
3. webhook/API 回调的签名验证设计（防签名搬运重放）。
4. 签名覆盖范围评审——"签了名就可信吗"。

### 语言信号 (用户的话里出现这些就应激活)

- "多层验证还是被打穿 / multiple checks still bypassed"
- "标识符对齐 / identifier alignment"
- "签名覆盖哪些字段 / what does the signature cover"
- "多个证据怎么聚合 / combining weak authentication signals"
- "签名被剥离重放 / signature stripping"

### 与相邻 skill 的区分

- 与 `stallings-auth-assurance-tiering` 的区别: 那个先拆对象（验物还是验人）并定档位，本 skill 再管多个证据如何对齐聚合——"验什么、多确信"与"证据怎么合成"两阶段。
- 与 `stallings-canonicalization-first` 的区别: 那个定单一对象的字节形态（等价类），本 skill 定证据之间的结构关系（对齐到谁）——单对象 vs 多证据。
- 与 `stallings-auth-mechanism-axes` 的区别: 那个按四轴选出机制类型（域级/个人级），本 skill 要求选出的机制最终对齐同一核心标识——选型与对齐配套。

## E — 可执行步骤 (Execution)

1. **列证据-标识映射**：写出系统全部认证/验证证据及其各自锚定的标识（IP、密钥、域、设备、账户）。
   - 完成标准: 映射表成文，无身份归属不明的证据。
2. **选定核心身份**：选用户可见且不可绕过的标识（如 From 域、账户 ID），说明为何可见、为何绕不过。
   - 完成标准: 核心身份有书面理由。
3. **逐条查对齐**：对每条证据问"是否强制对齐到核心身份"——不对齐者即旁路入口。
   - 完成标准: 每条证据有对齐/旁路结论；旁路处有修复或豁免。
4. **核对三方绑定**：对签名/证明类证据核对内容+发送者+接收者是否都在覆盖内，做剥离搬运测试。
   - 完成标准: 搬运测试失败（签名挪到其他服务/接收者无效）。
5. **声明保证范围**：逐条证据声明"证明什么、不证明什么"，与产品话术对齐。
   - 完成标准: 范围声明成文，无"签了=全都可信"式越界主张。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 把对齐当充分的聚合条件——证据各自的强度仍需独立评估（对齐不产生新强度，只防止强度错配）。
- 选择用户不可见的锚——锚点用户看不到就无法帮助用户判定真伪，对齐就失去意义。

### 作者在书中警告的失败模式

- 明文签名可剥离重签（Max 案例）。
- S/MIME 只签内容的头部缺口——范围与声称保证错配。

### 作者的盲点 / 时代局限

- 书中对齐概念来自邮件域（DKIM/DMARC，成书 2017 前）；跨域身份的语义对齐（联合身份三档粒度）书内只在第15章简述，推广到 webhook/风控聚合需自行映射。

### 容易混淆的邻近方法论

- v42 对象分档（验什么）、v30 规范化（签什么形态）、v50 机制四轴（选哪类机制）。
