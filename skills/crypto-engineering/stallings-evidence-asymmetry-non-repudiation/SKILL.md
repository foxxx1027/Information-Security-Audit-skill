# 证据不对称性与不可否认判定

## R — 原文 (Reading)

> "最后，要注意的是，由于收发双方共享密钥，因此MAC不能提供数字签名。……（1）Mary可以伪造一条消息并称该消息发自John。Mary只需产生一条消息，用John和Mary共享的密钥产生认证码，并将认证码附于消息之后。"
>
> — 方法论出处，第12章 12.2.2 / 第13章 13.1.2（source.txt 行16883、17809–17852）

---

## I — 方法论骨架 (Interpretation)

选"用 MAC 还是签名"不看算法强度，看**证据的方向**：

1. **两问定机制**：这份认证码，谁能生成？谁能验证？MAC（共享密钥）双方都能生成也能验证——能力对等意味着：接收方可自造"对方发来的"消息（Mary 伪造），发送方可否认"那是你自己算的"（John 抵赖），任何第三方都无法裁决。签名（私钥生成、公钥验证）天然不对称——只有签名人产得出、任何人验得了，可仲裁。
2. **从互恶场景推需求**：电子转账（接收方篡改金额声称来自发送方）、经纪人对不利邮件抵赖——凡有法律/商务后果的承诺流，把"双向不可否认"列为独立需求，配签名+可信时间戳+归档（签名三特征：验身份与时间、验内容、可第三方仲裁）。
3. **认证与保密是独立旋钮**：六种用 MAC 而非加密的情形——广播给多接收者（一人验证余人报警）、重负荷抽检、明文认证程序、纯认证协议（SNMP 类）、分层（应用认证+传输加密）、延长保护期（解密后仍受 MAC 保护）。需求矩阵：保密/认证/签名三列+运算代价列，逐格打勾。
4. **部分补偿**：KDC 见证、可信时间戳、审计日志能补一部分仲裁能力，但不等价签名——Kerberos 票据同样受"双方能力对等"限制。

## A1 — 书中的应用 (Past Application)

### 案例 1: Mary 伪造与 John 抵赖——对称认证的两类争议
- **问题**: 已有对称认证（第12章方案）为何还需要数字签名。
- **方法论的使用**: 场景推演：共享密钥下 Mary 可自造合法认证码声称来自 John；John 事后可否认一切（"码是你造的"）。两争议均有法律后果（转账金额、经纪人邮件）。
- **结论**: 推出签名三特征（验证者与时间、内容、第三方仲裁）——签名是被"互相作恶"场景逼出来的需求，不是密码学装饰。
- **结果**: 第13章以这两场景立章，需求由争议场景而非算法目录驱动。

### 案例 2: 六种必须用 MAC 的情形
- **问题**: 有了加密和签名，MAC 的定位是什么。
- **方法论的使用**: 按负荷/广播/保护期枚举：广播多接收者只需一人验证；重负荷抽检；明文认证省解密；纯认证不要保密；应用认证+传输加密分层；解密后仍需保护——六情形里签名过重或不对口。
- **结论**: 认证与保密独立取用；MAC 在"无需仲裁"场景更经济。
- **结果**: 选型从"谁更强用谁"改为按需求矩阵（保密/认证/签名/代价）逐格决策。

### 案例 3: 公钥加密四组合的代价意识
- **问题**: 保密+认证+签名全要时怎么组合。
- **方法论的使用**: E(PUb,E(PRa,M)) 内签外加密三者兼得，代价是每条消息四次公钥运算——方案成立但代价列必须填。
- **结论**: 组合可行性与运算/密钥分发代价同时入矩阵。
- **结果**: "按需求选组合并标注代价"成为文档格式，避免只写机制不算账。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. SaaS 计费 webhook、开放 API 回调通知：HMAC 还是平台签名？
2. 电子合同/审批流/交易回执设计：怎么让"发送方事后无法抵赖、接收方无法自造"。
3. 内部对账流与对外承诺流的机制分道（同一系统两套证据要求）。
4. 审计"我们全程 HMAC 校验"的系统的争议处置能力。

### 语言信号 (用户的话里出现这些就应激活)

- "non-repudiation / 不可否认怎么实现"
- "webhook 用 HMAC 还是签名 / 平台能不能否认"

- "电子合同什么机制才有效力"

### 与相邻 skill 的区分

- 与 `stallings-hash-property-application-mapping` 的区别: 那个管 Hash 性质档位（用哪条抗性）；本 skill 管认证构件的**主体不对称性**（谁能产证据）——两轴正交：HMAC 内核用哪个 Hash 是那边的事。
- 与 `stallings-attack-capability-success-levels` 的区别: 那个给攻击声明定档（能力×危害）；本 skill 给**业务争议**定机制——一个是攻击者视角的强度，一个是法庭视角的可仲裁性。
- 与 `stallings-trust-topology-blast-radius` 的区别: 那个管可信第三方的引入与集中度；本 skill 只在"KDC 见证可部分补偿签名"处与它相交。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列消息流与争议面**: 枚举系统内每类需认证的消息流，各问两个假设争议——"接收方自造一条怎么办""发送方否认怎么办"。
   - 完成标准: 每类消息流有两问的后果说明（有无法律/商务后果）。
2. **问证据方向**: 对每类流标注现有机制的"生成方/验证方"矩阵。
   - 完成标准: 矩阵成文；对称机制（双方均可生成）在高争议流上标红。
   - 判停条件: 若高争议流（涉及承诺/计费/合同）当前仅有 MAC，直接判机制错配，进入第 3 步换签名，其余流后置。
3. **配机制**: 高争议流上私钥签名（必要时 KMS 见证+可信时间戳+归档）；低争议内部流保留 HMAC（经济性）；按六情形核对是否有更合适的 MAC 场景。
   - 完成标准: 每类流的机制+理由+代价（运算/密钥管理）三联。
4. **补仲裁要件**: 对签名流核对签名三特征（身份/时间/内容）与长期存证（副本可保存备日后仲裁）。
   - 完成标准: 时间戳来源与归档策略成文。
5. **输出机制矩阵**: 消息流×（保密/认证/签名/代价）的最终选型表。
   - 完成标准: 无"一刀切 HMAC"或"一刀切签名"；每格可追溯到第 1 步的争议分析。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 算法强度与攻击模型问题——先走双轴声明与原语判据。
- 匿名/隐私场景（显式不要可追溯）——本 skill 的要件（身份+时间+归档）与匿名目标冲突，需另行权衡。
- 纯内部、无争议面的数据流——HMAC 足矣，引入签名是过度工程。

### 作者在书中警告的失败模式

- 用 MAC 追求不可否认（ce043）：双方共享密钥，争议时机制自身无法排解。
- 公钥加密当认证（ce039）：任何人可用公钥冒充发送方——E(PUb,M) 只保密不认证。
- 只写机制不算代价：四次公钥运算的方案在高吞吐流上不可行。

### 作者的盲点 / 时代局限

- "私钥保管不当可主张密钥被窃"——书中点到即止；现代远程签名/门限签名/监管沙箱把"谁实际控制私钥"变成复杂举证问题，第7版未展开。
- 区块链存证、可信时间戳服务的现代形态缺位；证据链的法律效力因司法辖区而异，需本地化补充。
- 六情形清单成形于 1990s（TSUD92），实时 API 时代的回调/事件流形态需自行映射。

### 容易混淆的邻近方法论

- 与"传输层 TLS 签名"：TLS 证书签名解决"服务器身份"，不给你的业务消息提供不可否认——通道认证≠消息证据。
- 与审计日志：日志是事后记录（可信度依赖系统未被攻破）；签名是密码学证据（不依赖系统状态）——合规场景常要两者叠加而非二选一。
