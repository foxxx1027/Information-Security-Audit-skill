# 密钥用途单一化与上下文绑定

## R — 原文 (Reading)

> "另外还需要考虑一个主密钥被作为数据加密密钥的风险。";"则非授权的应用可能会获得以后通信中用该主密钥加密的会话密钥。"
>
> — 方法论出处，第14章 14.1.6 控制向量方式（主密钥误用警告）

---

## I — 方法论骨架 (Interpretation)

密钥复用是最小权限原则在密码学上的违例：同一把钥既加密又认证、既管 A 租户又管 B 租户，任何一处暴露都连坐全部用途。治理分两问：

1. **分离**：一钥一用——加密、MAC、签名、密钥包装各用独立派生的钥匙；算法也可以在定义层裁剪用途（DSA 只提供签名功能，同一密钥拿去加密根本无定义）。
2. **绑定**：光有外部标签不够。8 位标签反例说明：策略若只是与密钥分存的元数据，攻击者可调包标签与用途。约束必须经**单向函数与秘密耦合**——控制向量做法是解密钥=H(CV)⊕主密钥，剥离控制向量就解不出任何东西；同时策略以明文随密文流转、各层可校验（明文有效的优点）。

第二问的现代形态是派生上下文：KDF 把用途、算法、租户/环境、期限、双方地址、nonce、协商套件、transcript 全部当原料——改任何一个字段，输出全变，密钥"焊"在这一次会话/这一个用途上，搬到别处自动失效。

## A1 — 书中的应用 (Past Application)

### 案例 1: 控制向量耦合（第14章）
- **问题**: 密钥托管/分发时，如何保证"这把钥只能用于声明的用途"？
- **方法论的使用**: 控制向量 CV 经 Hash 与主密钥异或耦合产生解密钥（H(CV)⊕K），剥离或篡改 CV 即无法正确解密；书内列两大优点——长度可无限扩展、CV 各层明文有效可校验。
- **结论**: 策略与秘密耦合后，外挂篡改不可行；对照 8 位标签方案（标签与钥分离可被调包）凸显绑定方式的差异。
- **结果**: 成为密钥托管通信安全的控制机制。

### 案例 2: DSA 只签名的设计逻辑（第13章）
- **问题**: 签名密钥能否顺手用于加密等其他用途？
- **方法论的使用**: 算法定义层裁剪——DSA 刻意只提供数字签名功能，不定义加密用途。
- **结论**: 用途单一化可以做到算法级，而不是靠运维纪律。
- **结果**: 一钥一用获得标准级示范。

### 案例 3: 802.11i PTK 派生与 TLS 握手签名（第18、17章）
- **问题**: 派生出的会话密钥如何防搬运/劫持到别的会话？
- **方法论的使用**: PTK 派生绑定双方 MAC 地址+双方 nonce；TLS 的握手签名覆盖 ClientHello.random‖ServerHello.random‖参数——会话上下文全部进派生/签名原料。
- **结论**: 密钥与签名都"焊"在本次会话上，重放到别的连接即失效。
- **结果**: 会话级上下文绑定成为现代协议标配。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 多租户 KMS 的派生密钥设计（单钥失陷不越界）。
2. 审计"一把密钥多处使用"的系统（同一钥跨环境、跨用途、跨算法）。
3. 设计协议的密钥派生——会话绑定该纳入哪些上下文。
4. 密钥策略/标签机制设计（为什么外挂标签不够）。

### 语言信号 (用户的话里出现这些就应激活)

- "同一把密钥加密和签名 / same key for encryption and MAC"
- "密钥派生上下文 / key derivation context"
- "用途分离 / key separation"
- "派生密钥加 tenant id 吗 / domain-separated keys"
- "这把密钥还能用在别处吗 / key reuse across systems"

### 与相邻 skill 的区分

- 与 `stallings-key-counting-hierarchy` 的区别: 那个拆数量与频次层次（多少把、多久换），本 skill 拆用途与上下文（每把能干什么、绑在哪）——正交两轴，合起来才是完整密钥治理。
- 与 `stallings-credential-splitting` 的区别: 那个拆凭据职责与寿命（票据 vs 认证码），本 skill 拆密钥用途与绑定——凭据与密钥两个层面的最小化。
- 与 `stallings-nonce-iv-one-time-constraints` 的区别: 那个管 nonce/IV/随机数的一次性（易变参数），本 skill 管密钥本身的用途绑定（长命材料）。

## E — 可执行步骤 (Execution)

1. **盘点密钥-用途矩阵**：列出系统全部密钥及其使用点，标出任何"一钥多用"（跨用途/跨环境/跨租户/跨算法）。
   - 完成标准: 矩阵成文，复用处全部标红。
   - 判停条件: 单一用途单一密钥且无增长预期的封闭系统，登记豁免。
2. **拆分派生**：对每处复用按用途独立派生（enc/dec/mac/sign/wrap/tenant 各一支）。
   - 完成标准: 复用处清零或有书面风险接受。
3. **把约束绑进派生**：KDF 输入固定为（用途‖算法‖租户/环境‖期限），写明"改任一字段输出全变"并测试。
   - 完成标准: 派生公式与字段清单成文，篡改字段导致解密失败的测试通过。
4. **核对绑定方式**：检查策略与秘密是否经单向函数耦合（对照 8 位标签反例），策略是否明文随密文流转可校验。
   - 完成标准: 绑定强度判定成文；外挂标签类设计被识别并升级。
5. **会话上下文入料**：对协议会话密钥，把双方标识/地址/nonce/协商套件/transcript 纳入派生原料。
   - 完成标准: 搬运/重放测试（把钥或签名挪到另一会话）失败。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 把用途分离当无成本的性能话题——分离增加管理与派生开销，粒度按风险定，不是越细越好。
- 策略与密钥分存的弱标签方案——那正是本 skill 要替换的反模式，不是折中选项。

### 作者在书中警告的失败模式

- 主密钥当数据加密密钥：非授权应用可能借机获得主密钥保护的会话密钥（ce051）——根材料暴露在最大攻击面。
- 8 位标签反例：标签与钥分离，剥离/调包即可绕过用途约束。

### 作者的盲点 / 时代局限

- 控制向量是书中承自 IBM传统的机制（成书 2017 前），现代等价物是 KDF context、AEAD 的 associated data、key commitment——映射关系需自行建立，勿混称书内已有后者。

### 容易混淆的邻近方法论

- v32 密钥层次（数量维度）、v38 凭据拆分（寿命维度）、v18 一次性参数（易变维度）。
