# 灰度策略与遥测回路

## R — 原文 (Reading)

> "允许渐进加强的策略，从发送方域对DMARC检查失败的邮件建议不采取措施（p-none），到将未通过邮件视为怀疑对象（p=quarantine），再到拒绝所有未通过邮件（preject）"
>
> — 方法论出处，第19章 19.10 DMARC（引文含 OCR 噪声，按原样保留）

---

## I — 方法论骨架 (Interpretation)

一条会拒流量、锁账号、退邮件的安全策略，直接全量上线等于用生产环境做实验。可运营的上线路径是**观测-收紧回路**：

1. **档位序列**：策略设计成递进档（仅记录→软处理/隔离→硬拒绝），档位之间的差异是可回滚的旋钮而非版本切换。
2. **百分比灰度**：配 pct 类参数从小流量开始——双参数（档位×百分比）把任何一步的爆炸半径都压到最小。
3. **度量驱动升级**：先开仅记录模式收报告（谁会被误杀、失败率多少），定量评估达标才升档——决策挂阈值，不挂日历日期。
4. **元数据反制**：安全功能新增的公开元数据（DNS 中的报告邮箱）本身会扩大攻击面——公开即被爬，需预设过滤/别名等骚扰反制。

单点认证机制装上只是开始，"采用率遥测+效果回路"才是运营态——没有回路，部署者在盲区调策略，等于 v47 的静默失效在策略层的翻版。

## A1 — 书中的应用 (Past Application)

### 案例 1: DMARC 三档+pct 灰度（第19章）
- **问题**: 直接 p=reject 会误杀大量正常邮件（转发、未对齐的合法服务），怎么上线？
- **方法论的使用**: 档位序列 p=none→quarantine→reject + pct 百分比灰度（默认 100，"防止在收到对现有策略的反馈之前执行太过严苛的策略"）；SP800-177 部署路径：先设 p=none 收汇总报告，凭对外部接收方认证程度的定量评估再切 reject。
- **结论**: 影响可达性的策略必须先观测后收紧；升级由报告数据触发。
- **结果**: DMARC 成为策略灰度的标准范式。

### 案例 2: SSH 强制最低算法集+客户端偏好（第17章）
- **问题**: 服务端怎么逐步淘汰弱算法而不切断存量客户端？
- **方法论的使用**: 策略档位化的另一形态——声明强制最低算法集与客户端偏好列表，按度量（客户端能力分布）逐步收紧；802.11i 时代的 TKIP 过渡同构（兼容档位+淘汰表归 v39）。
- **结论**: 档位不只用于处置动作，也用于能力基线。
- **结果**: SSH 算法策略成为可分步收紧的配置面。

### 案例 3: 报告地址被垃圾邮件盯上（第19章）
- **问题**: DMARC 要求在 DNS TXT 记录公开报告接收邮箱，有什么代价？
- **方法论的使用**: 元数据攻击面评估——DNS 记录对所有人可读"易于被发现，发布者容易收到大量垃圾邮件"。
- **结论**: 安全机制的公开元数据自身扩大攻击面，须配套骚扰反制措施。
- **结果**: 公开命名信息（DNS/WHOIS/security.txt）进部署清单的固定检查项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 全公司强制 MFA/强策略的 rollout 计划编写。
2. 强制安全策略上线（HSTS、mTLS、签名校验、邮件策略）。
3. 灰度期间的监控与回滚设计。
4. 公开元数据（security.txt、报告邮箱、well-known 端点）暴露评估。

### 语言信号 (用户的话里出现这些就应激活)

- "rollout 计划 / gradual enforcement, canary policy"
- "先观测后强制 / monitor mode before enforce"
- "百分比灰度 / percentage rollout, pct"
- "误杀率监控 / false positive rate during enforcement"
- "报告邮箱被爬/轰炸 / public reporting address abused"

## E — 可执行步骤 (Execution)

1. **设计档位序列**：写出策略的递进档（仅记录→提示/软拒绝→硬拒绝），每档的判定逻辑与回滚成本。
   - 完成标准: 档位表成文，相邻档位可一键切换。
2. **加百分比参数**：从小流量开始灰度，定初始 pct 与递增步长。
   - 完成标准: 灰度参数与调整规则成文。
   - 判停条件: 不影响可达性的纯观测类策略可跳过灰度直接上线（仍保留报告）。
3. **开观测期**：部署仅记录模式，产出覆盖率/误杀/失败率报告。
   - 完成标准: 报告管道跑通并有首批数据。
4. **定阈值升档**：把升档条件写成度量阈值（如误杀<0.1% 连续两周），记录每次升档的决策依据。
   - 完成标准: 阈值与决策记录成文。
5. **预设元数据反制**：对策略新增的公开元数据（邮箱、端点）配过滤/别名/中转，评估被爬后果。
   - 完成标准: 反制措施上线并验证。
6. **演练回滚**：从最高档回退到观测档做一次演练。
   - 完成标准: 回滚在约定时限内完成。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 正被主动利用的漏洞紧急阻断——快速止血优先于灰度，先封再评估。
- 观测无终点：停在"仅记录"模式永不收紧等于没有防护——观测期必须有明确升档条件。

### 作者在书中警告的失败模式

- 过严策略在收到反馈前执行会大面积误杀（pct 存在的理由）。
- 公开报告地址"易于被发现"，垃圾邮件轰炸随即而来（ce091）。

### 作者的盲点 / 时代局限

- 书中灰度形态是 DMARC/SSH 算法策略（成书 2017 前），特性开关平台/A-B 基础设施书内无内容；"度量驱动升级"的书内证据集中在邮件域，推广到 MFA 类 rollout 是同构迁移。

### 容易混淆的邻近方法论

- SRE 的 canary 部署（无安全语义的通用发布）——本 skill 的差异在"安全策略专属的观测-收紧回路+安全元数据反成攻击面"。
- v39 演进治理、v47 fail 方向、v49 协商基线。
