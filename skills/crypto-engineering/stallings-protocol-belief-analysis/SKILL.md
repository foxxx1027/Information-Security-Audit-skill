# 协议信念分析三步法与演进审查

## R — 原文 (Reading)

> "展示C如何利用映像重新运行协议，使得A认为已经和B就新的会话密钥达成一致（尽管事实上是和C进行了通信）。从而，（a）中是错误的。"
>
> — 方法论出处，第14章 习题14.6（镜像重跑制造错误共识）

---

## I — 方法论骨架 (Interpretation)

时序协议的审查可以变成可穷举的清单作业，而不是靠直觉或"跑一遍没问题"：

1. **列信念断言**：把设计者的每条隐含主张写成显式句子——"A 相信密钥新鲜，因为看到了自己的 nonce 回来"。每条断言都是一个攻击面，消息里的每个字段都要能指到某条断言，否则它多余。
2. **逐条证伪**：在攻击者模型下为每条断言找反例——镜像重跑（把双方消息互相转交制造错误共识）、反射（把挑战原样弹回）、旧钥复活（泄露的历史会话钥重放）、时钟回拨。
3. **修补后再审**：对被证伪断言做最小修补，然后把修补**引入的新假设**（时钟同步、地址可信、nonce 全局唯一）写进假设清单再审——每代修补的新假设就是下一代攻击面。

"看起来安全"恰是需要再审的信号，不是放行理由。配套动作：按阶段拆解，每个阶段问"开始前信任什么、结束新增什么信任"，信任增量对不上就是漏洞。

## A1 — 书中的应用 (Past Application)

### 案例 1: 镜像重跑推翻"密钥来自彼此"（第14章 习题14.6）
- **问题**: "A、B 共享长期密钥、三步换新会话钥"的协议，设计者相信双方能确信密钥来自彼此且新鲜。
- **方法论的使用**: 把信念写成断言，再构造镜像反例——C 把 A、B 的消息互相转交，A 相信已与 B 达成一致，实际对端是 C。
- **结论**: 每条消息经长期密钥加密不等于每条信念成立；断言清单暴露了"密钥确认"这一隐含主张。
- **结果**: 习题成为三步法的教学原型；正式攻击者模型下逐条证伪成为后续章节的审查范式。

### 案例 2: Needham–Schroeder→Denning→Neuman 三代演进（第15章）
- **问题**: N/S 协议有握手确认步（第4、5步 nonce 往返），为何仍可被重放？
- **方法论的使用**: 反例=攻击者已知旧会话钥时截获第 4 步伪造第 5 步（旧钥复活）；修补=Denning 加时间戳；再审发现新假设"全网时钟同步"被抑制重放攻击击穿（发送者时钟快于接收者时重放恰落窗口）；Neuman 再改为单方校验时间戳。
- **结论**: 每代修补引入的新假设成为新攻击面——时钟同步、窗口大小都是可攻击的信任前提。
- **结果**: 三代演进史成为"修补-再审"循环的完整实证；作者脚注自评"构造正确的协议的确很困难"。

### 案例 3: Woo-Lam 自我修正与 X.509 反射（第15章）
- **问题**: 看似面面俱到的协议还有哪些隐形漏洞？
- **方法论的使用**: 作者自查 Woo-Lam 发现 nonce 不绑身份即可被冒用（N_a 只在 A 的 nonce 中唯一，不保证全局唯一），修正=把 ID_a 加入 KDC 加密集；X.509 习题演示时间戳校验"可选"时，C 用截获消息+反射完成双向冒充。
- **结论**: 随机数必须与属主标识成对绑定；"可选校验"等于把防重放闸门交给部署者自觉。
- **结果**: "看起来安全的协议也需要不断的分析修正"成为章末结论。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计自研认证/会话协议（登录、票据、单点登录、设备配对）。
2. 评审协议的演进版本——补丁是否引入新假设。
3. 对"协议看起来没问题"但直觉不安的设计做系统排查。
4. 接手第三方协议做安全评审，需要可交付的审查报告。

### 语言信号 (用户的话里出现这些就应激活)

- "这个协议安全吗 / is this protocol secure"
- "重放/反射攻击测试 / replay attack, reflection attack"
- "第 N 步的 nonce 防什么 / what does this nonce protect"
- "修补之后还安全吗 / does the patch introduce new assumptions"
- "协议消息交换审查 / protocol walkthrough, message flow review"

排除信号 (用户的话里出现这些就不应激活)：

- "关旧版 TLS / 改 nginx 配置 / 变更单怎么写 / 怎么灰度上线"——主诉求是配置变更的工单与上线节奏（运维变更管理），不是消息时序逻辑审计；出现 "TLS/协议"字样不等于协议审计诉求。

### 与相邻 skill 的区分

- 与 `stallings-unauthenticated-key-exchange` 的区别: 那个是单一问句族（公钥谁背书），本 skill 是全协议三步法；那个的问句常作为本 skill 步骤 2 的一类反例。
- 与 `stallings-policy-gradual-rollout` 的区别: 那个管安全策略上线的观测-收紧回路（档位×灰度），本 skill 管协议消息时序的信念成立性。"把 tls1.0/1.1 关掉的变更单怎么写、怎么灰度"主诉求是变更单与上线窗口等运维流程，不是信念断言审计，也不该由本书密码技能受理。
- 与 `stallings-anti-replay-window-engineering` 的区别: 那个为已确认的重放面选机制定参数，本 skill 把重放当证伪信念断言的武器——先证伪（本 skill）再修复选型。
- 与 `stallings-fail-direction-audit` 的区别: 那个审配置错误时的行为方向，本 skill 审协议时序的信念成立性——配置面与时序面分开。

## E — 可执行步骤 (Execution)

1. **列断言清单**：写出协议全部消息与状态，逐条列设计者信念断言（"A 相信 K 新鲜因为…"），每个字段指到至少一条断言。
   - 完成标准: 断言清单覆盖全部消息，无字段无主。
   - 判停条件: 单消息无状态协议（无时序依赖）停在此步，记录"无信念链"。
2. **逐条构造反例**：对每条断言尝试镜像重跑、反射、旧钥复活、时钟回拨四类攻击，标注成功条件（攻击者需要什么能力）。
   - 完成标准: 每条断言有"被证伪/未证伪+所需攻击能力"标注。
3. **最小修补**：对被证伪断言做最小改动修补，不引入多余机制。
   - 完成标准: 每处修补对应一条被证伪断言。
4. **再审新假设**：把修补依赖的新假设写入假设清单，逐条问"该假设可满足吗、自身可被攻击吗"，必要时循环回步骤 2。
   - 完成标准: 假设清单经一轮再审，无未检验的新假设。
5. **输出阶段拆解表**：每阶段"开始前信任什么/结束新增什么信任"+ 断言-反例-修补对照表。
   - 完成标准: 交付物为对照表而非"基本安全"结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 非时序的配置/部署审计（用 v47 一类的方向审计）。
- 需要形式化安全证明的高保障场景——本方法是工程师可执行的清单作业，能系统性找漏洞，不构成证明。

### 作者在书中警告的失败模式

- X.509 把时间戳校验设为可选，反射冒充三消息得手（ce060）——"可选校验"是断言清单里的隐形漏洞。
- Kerberos v4 用 PCBC 加密扩散顺带做完整性，被交换密码块攻击攻破（ce061）——加密模式的扩散特性不是完整性机制，断言"扩散=防篡改"必被证伪。

### 作者的盲点 / 时代局限

- 书中方法脱胎于习题与三代协议演进史（成书 2017 前），未引入 BAN 逻辑等正式信念逻辑工具的名称与机器可查形式；自动化（模型检测）不在书内——大协议需自行补充工具。

### 容易混淆的邻近方法论

- v35 MITM 反例族（单一问句 vs 三步法）。
- v37 防重放选型（修复阶段）、v36 前后的挑战-应答判据（v28，另一段单元）。
