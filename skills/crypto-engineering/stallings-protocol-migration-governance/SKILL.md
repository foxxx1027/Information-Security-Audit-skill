# 兼容过渡与协议演进治理

## R — 原文 (Reading)

> "在隐私性方面，802.11定义了WEP（WiredEquivalentPrivacy）算法。802.11标准中隐私性部分有致命的缺陷。"
>
> — 方法论出处，第18章 18.4 IEEE 802.11 无线局域网安全

---

## I — 方法论骨架 (Interpretation)

协议/算法演进不是"平滑升级"的工程问题，而是有纪律的治理问题，五条规则：

1. **双清单分账**：升级障碍先分成两堆——环境缺陷（接口、编码、性能改一改就能通）与技术不足（机制本身必须换）。两类问题分开决策，混在一起会把"不想改"伪装成"改不了"。
2. **兼容层是过渡品**：EDE 型"看似多余"的步骤（3DES 中间那次解密）是为向后兼容付的代价，且必须封堵退化配置（K1=K2）；兼容驱动的方案（TKIP）生来就是过渡品，要带退役表。
3. **致命缺陷按替换处理**：核心机制被判致命（WEP）时整个替换（802.11i），不是无限打补丁。
4. **封死降级面**：可协商的升级通道（STARTTLS）天然自带降级攻击面，必须配带签名的强制策略（DNSSEC 保护的 TLSA）拒绝静默回退。
5. **减法窗口**：大版本升级是砍 legacy 的正当时机——删代码比加固代码更减攻击面；存量审计要查三列：协议版本+实现库版本+已攻破套件，不能只看协议版本。

## A1 — 书中的应用 (Past Application)

### 案例 1: WEP→WPA(TKIP)→WPA2(CCMP) 全链（第18章）
- **问题**: 802.11 的 WEP 隐私机制被判"致命的缺陷"，但海量存量设备怎么办？
- **方法论的使用**: 分层治理——核心机制按替换处理（802.11i 重写）；为存量先发过渡标准 WPA（TKIP 兼容驱动 WEP 硬件），TKIP 定位为过渡品；WEP 仅保留 40/104 位向后兼容。
- **结论**: 过渡品必须有终点——最终 WPA2 认证完整 802.11i（CCMP），TKIP 进入淘汰。
- **结果**: "标准先上线、缺陷后暴露、过渡方案补锅、最终替换"成为演进范式。

### 案例 2: 3DES EDE 的兼容设计与退化封堵（第7章）
- **问题**: 双重 DES 被中间相遇攻破，如何兼容既有 DES 投资升级到 112 位强度？
- **方法论的使用**: EDE 结构（加密-解密-加密）使 K1=K2 时退化为单 DES——看似多余的中间解密正是兼容开关；但退化配置必须显式封堵，不允许默认落入弱档。
- **结论**: 兼容层可留，退化配置必须封死。
- **结果**: 3DES 成为过渡期标准，为 AES 全面替换争取了时间。

### 案例 3: STARTTLS 剥离与 TLSA 封堵（第19章）+ TLS 1.3 减法（第17章）
- **问题**: 邮件 STARTTLS 是机会性升级，中间人破坏升级宣传即可让两端回退明文。
- **方法论的使用**: 带签名的强制策略封死回退——域在 DNSSEC 保护的 DNS 中发布 TLSA 记录，声明"该域要求 TLS 及应持证书"，客户端查记录即拒绝明文回退；TLS 演进则以 1.3 大版本做减法（移除弱套件/压缩/RSA 密钥交换）。
- **结论**: 可协商升级必须配可验证的强制声明；版本升级是砍 legacy 的正当窗口。
- **结果**: 降级剥离面被封堵；TLS 1.3 用减法收敛攻击面。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 规划算法/协议升级路线（PQC 混合签名、TLS 版本、SHA-1 退役）。
2. 评估存量系统安全状态（"我们还在用旧协议吗、实现库呢"）。
3. 设计兼容模式与回退机制（双栈、降级开关）。
4. 决定某个被判缺陷的机制是修补还是替换。

### 语言信号 (用户的话里出现这些就应激活)

- "迁移计划 / migration plan, crypto agility"

- "什么时候砍掉旧算法 / deprecate legacy ciphers"
- "混合双栈过渡 / hybrid classical + post-quantum"

### 与相邻 skill 的区分

- 与 `stallings-algorithm-retirement-crypto-agility` 的区别: 那个管单个算法的退役判据与时间表（何时换、换什么），本 skill 管系统级过渡治理（分账、兼容层身份、降级封堵、减法窗口）——单算法 vs 系统演进两层。
- 与 `stallings-capability-negotiation-baseline` 的区别: 那个定协商的选择规则与最低集（机制层），本 skill 管过渡期策略与砍 legacy 的时机（治理层）。
- 与 `stallings-policy-gradual-rollout` 的区别: 那个管单条策略上线的节奏与回路，本 skill 管协议/算法族的演进治理——一次发布 vs 一场迁移。

## E — 可执行步骤 (Execution)

1. **存量三列审计**：逐系统列协议版本、实现库版本、已攻破套件/配置，对照已知缺陷清单。
   - 完成标准: 三列审计表成文，缺一列即漏。
2. **双清单分账**：把升级障碍分为环境缺陷与技术不足两张单，分别定处置。
   - 完成标准: 两张清单各自有负责人与处置结论。
3. **给兼容层写退役表**：每个过渡方案/兼容模式登记"生效条件+预定拆除时点+触发升级的事件"。
   - 完成标准: 退役表成文且被纳入路线图评审。
   - 判停条件: 绿地系统无存量依赖时跳过兼容层设计，直接采用目标强机制。
4. **封堵降级面**：对所有可协商升级通道配带签名的强制策略，验证静默回退不可行。
   - 完成标准: 降级尝试必然失败或有告警。
5. **立项减法窗口**：把大版本升级定义为砍 legacy 的窗口——删代码优先于加固代码，砍除项写进发布说明。
   - 完成标准: 每个升级版本有明确的移除清单。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 功能升级的通用项目管理（本 skill 只管安全语义的过渡）。
- 以"平滑"为名保留无退役表的永久双栈——兼容层没有终点就是攻击面常态化。

### 作者在书中警告的失败模式

- 向后兼容把弱算法长期留在标准里（WEP 40/104 位保留于 802.11i 时代设备）。
- EDE 退化配置 K1=K2 若不封堵等于自愿降级。
- BEAST 类协议缺陷"往往只能靠打补丁升级应对"——没有升级通道的协议只能被动挨打。

### 作者的盲点 / 时代局限

- 书中演进史是回顾性叙述（成书 2017 前），PQC/混合签名在书内无内容——治理框架是归纳产物，外推到抗量子迁移时参数需自定；"删代码减攻击面"的原则书内有 SSDP/IPsec 语料支撑，量化收益书内未给。

### 容易混淆的邻近方法论

- v15 算法退役判据（单算法层）。
- v49 协商基线（机制层）、v48 灰度回路（发布层）。
