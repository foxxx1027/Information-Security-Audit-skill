# 随机数工程与验收治理

## R — 原文 (Reading)

> "这些应用对随机数序列产生提出了两个不同且未必兼容的要求：随机性和不可预测性。……因为PRNG是一个确定性算法，如果对手能推导出种子，那么就可以决定输出。因此，种子必须不可预测。"
>
> — 方法论出处，第8章 8.1（source.txt 行11874–11893、11981–12008）

---

## I — 方法论骨架 (Interpretation)

随机数出事几乎从不在"算法"，而在**治理**。五条纪律：

1. **双轴分判**：统计随机（均匀、子序列独立、过测试）与密码学不可预测（前向不能猜下一位、后向不能由输出推种子）是两条独立验收——过统计测试不证明不可预测（LCG 统计漂亮但少量输出即反推参数）。
2. **验收矩阵**：随机性测试要对**多种子×多测试×多子序列**跑矩阵，单种子一次抽样不充分——这是三特征中"一致性"的工程化。
3. **种子即密钥**：PRNG 确定性，种子决定全部输出——种子按密钥同级保护；开机熵池空、虚拟机快照回滚、同批设备同源是最常见的事故形态。
4. **三级架构+健康测试**：TRNG 产熵→调节器去偏（Hash_df/AES-CBC-MAC，**调节不创熵**）→DRBG 扩流（CTR_DRBG，reseed_interval 限制单种子输出量）。噪声源做灾难性故障测试（重复计数、适应比例），**熵不足时拒绝发钥并告警，而非静默降级**。
5. **状态≠输出**：输出位不参与状态反馈（输出分半、X9.17 的状态更新再过一次加密），公开输出才不泄露内部状态；上游随机库的内部机制也要审计（Sage random_prime 自注"不是最密码学安全"）。

## A1 — 书中的应用 (Past Application)

### 案例 1: LCG 参数反推——统计合格≠密码安全
- **问题**: 通过统计测试的 LCG 能否用于密钥。
- **方法论的使用**: 双轴分判：LCG 满足统计随机（全周期、分布均匀），但线性结构下已知少量连续输出即可解出 a、c、m 预测全序列。
- **结论**: 统计随机只是必要条件；密码用途必须独立论证不可预测性。
- **结果**: LCG 被限定于仿真/抽样；混时钟重置种子"只是提高门槛，不是密码安全"。

### 案例 2: CTR_DRBG 的 reseed_interval 与初始化设计
- **问题**: 标准 DRBG 如何补偿"伪随机与真随机的差距"。
- **方法论的使用**: 读参数设计：seedlen=outlen+keylen（熵保证）、reseed_interval 限制单种子最大输出分组数、初始化把熵源异或进状态、达上限必须重播种。
- **结论**: 限制可分析样本量是 DRBG 的显式安全机制；reseed 失败必须报错而非继续。
- **结果**: SP800-90A 成为实现基准；fork/快照导致的状态重复列为已知失效边界。

### 案例 3: Intel DRNG 三级架构与 RDRAND/RDSEED 语义区分
- **问题**: 硬件随机怎么组织才可靠。
- **方法论的使用**: 分层验证：硬件熵源（热噪声）→AES-CBC-MAC 调节（256 位）→AES-CTR DRBG（>3Gbps）；RDRAND 是 DRBG 输出、RDSEED 是种子级熵——语义不同不可混用。
- **结论**: "熵源-调节-扩流"分层使各层可独立验证；接口分级对应用途分级。
- **结果**: 密钥生成走 RDSEED 级路径、流式用途走 RDRAND 级成为部署纪律。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 50 万台 IoT 设备首次开机生成设备密钥，防"同批同钥"事故。
2. 审计系统随机源（含第三方库/硬件 RNG 的上游链）。
3. DRBG/熵池实现评审：reseed 策略、健康测试、fork/快照处理。
4. 验收一台设备/一个库的随机质量，设计测试方案（而不是跑一次 NIST 测试套件了事）。

### 语言信号 (用户的话里出现这些就应激活)

- "随机数够随机吗 / NIST 测试过了"
- "entropy / 熵池 / 启动熵不足怎么办"
- "量产设备会不会同批同钥"
- "CSPRNG / DRBG / reseed 怎么配"
- "RDRAND / RDSEED 用哪个"

### 与相邻 skill 的区分

- 与 `stallings-nonce-iv-one-time-constraints` 的区别: 那个管随机数的**消费纪律**（nonce/k 一次性）；本 skill 管**生产与验收**（熵源、调节、DRBG、测试矩阵）——供给和消费两端各审各的。
- 与 `stallings-hardness-dependency-audit` 的区别: 那个审公钥方案的难题归约（BBS 的续位测试可归约是其一例）；本 skill 审整个随机供应链的工程治理，不要求可归约、要求可验证。
- 与通用 fuzz/统计测试: 那是功能测试；本 skill 的矩阵（多种子×多测试×多子序列）+健康测试+熵估计是密码学验收协议。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画随机供应链**: 从物理熵源→调节器→DRBG→各消费点（密钥/nonce/IV/挑战值）画出全链，标注每级的算法与参数。
   - 完成标准: 链路图覆盖全部消费点；种子来源与保护方式成文。
2. **双轴分别验收**: 统计轴按矩阵跑（≥3 个种子×一组测试×多个子序列）；不可预测轴审种子熵与算法结构（是否 CSPRNG/DRBG）。
   - 完成标准: 两轴各有独立结论；无"过了统计测试所以安全"的合并结论。
   - 判停条件: 若发现 LCG/时间戳种子/固定默认种子等非密码源在供密钥类消费点，直接判不合格，优先换源，其余步骤后置。
3. **健康测试与拒绝语义**: 检查噪声源的重复计数/适应比例测试是否运行时生效；熵不足时的行为是拒绝发钥还是静默继续。
   - 完成标准: 两类测试有阈值依据；拒绝路径验证过。
4. **状态与输出核查**: 检查输出是否参与状态反馈、fork/快照/重启后状态是否可能重复、reseed_interval 是否被当作强制上限。
   - 完成标准: 三项各有实现证据或整改项。
5. **量产/部署策略**: 设备侧强制开机混入唯一物理量（芯片 ID+出厂随机数）后才许生成密钥；抽批按矩阵验收。
   - 完成标准: 量产流程含熵保障步骤；抽检方案入出厂规范。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 消费侧纪律问题（nonce 复用、k 重复）——用一次性参数约束清单。
- 非安全用途的随机（仿真、抽样、负载打散）——LCG 足矣，别过度工程。
- 随机数协议测试（挑战值比对逻辑）——那是协议层议题。

### 作者在书中警告的失败模式

- 单种子一次测试就宣布合格（"一致性"被违反）。
- 种子低熵/可推（时间戳、PID、MAC 拼接；开机空熵池）——穷举种子比破算法便宜。
- 把调节当创熵：输入熵不足时输出熵仍不足，调节器只会把缺陷搅拌得更隐蔽。
- 健康测试只查灾难性故障，不能替代熵估计——两者都要。

### 作者的盲点 / 时代局限

- 云原生/容器环境（fork、快照回滚、热迁移导致状态重复）在书中仅作失效边界点名，无治理方案。
- 熵估计方法（min-entropy 评估、SP800-90B 的完整体系）在书中未展开，第7版时代 90B 刚成形。
- 双椭圆曲线 PRNG（DECPRNG）书中按正面材料转述（后曝出 NSA 后门嫌疑）——提示"标准化≠可信"，供应链维度需读者自行加强；此为成书时代的历史局限。

### 容易混淆的邻近方法论

- 与"跑 NIST SP800-22 测试套件": 套件只覆盖统计轴且对单序列——本 skill 要求矩阵化+独立论证不可预测轴。
- 与密码审计中的"密钥管理": 种子保护是其中的特殊一章（种子=未来全部密钥），但随机治理还包括健康测试与拒绝语义，超出保管范畴。
