# 公钥信任谱系与撤销传播滞后

## R — 原文 (Reading)

> "时间戳可以在攻击者已知A的私钥的情况下抗攻击，假设A产生新的公私钥对并向公钥管理员申请新的证书，同时，攻击者重放A的旧的证书给B，若B用旧公钥加密数据的话，则攻击者就可以读取信息。"
>
> — 方法论出处，第14章 14.3.4 公钥证书

---

## I — 方法论骨架 (Interpretation)

撤销难，不是"作废"这个动作难，而是**通知传播**难：怎么让所有依赖方都知道？

把问题这样重述后，解法自然浮现——用有效期/时间戳把"通知所有人"重构为"各自检查"：验证方查有效期即可，无需联系任何中心。

代价同样是时间性的：泄露到全部过期之间存在**不设防窗口**，旧证书可以被重放（书内类比：信用卡挂失后，在所有通信方都知道旧卡过时之前，持卡人并不安全）。

由此得到三条工程律：

1. 每类凭证的撤销语义必须显式声明"多久内生效"；
2. 窗口期=有效期+时钟偏差+查询滞后，要定价登记而不是假装为零；
3. 成员变更事件（设备离网、人员离职、成员退出）必须触发组密钥轮换——凭证与成员资格绑定的失效传播同构。

另外，公钥分发方法是一个封闭四分类（公开发布→目录→公钥授权→证书），安全性递增，分析任何分发体系时逐类攻最弱环节即可定位。

## A1 — 书中的应用 (Past Application)

### 案例 1: 证书时间戳对抗旧证书重放（第14章）
- **问题**: A 私钥泄露、换新钥申新证后，攻击者仍可把 A 的旧证书重放给 B，B 用旧公钥加密的会话密钥恰被持旧私钥的攻击者解出。
- **方法论的使用**: 把撤销重构为自查——证书带时效（截止日期），验证方各自检查；超时即失效，无需等吊销通知到达。
- **结论**: 时间戳使旧证书重放窗口收敛到有效期内；吊销问题简化为"各自检查有效期"。
- **结果**: 成为 X.509 证书与后续 CRL 体系的基础语义。

### 案例 2: 被解雇雇员的延迟注销（第1章）
- **问题**: 人员侧的撤销怎么失效？雇员截获并延时发送人事经理的注销通知，换取继续访问服务器的窗口。
- **方法论的使用**: 同一"传播滞后"透镜看人员流程——注销类控制的安全语义依赖"通知何时到达"。
- **结论**: 凡异步通知都应设确认与超时兜底，加密不阻止延迟。
- **结果**: 该案例成为全书画"吊销≠即时生效"的原型示例。

### 案例 3: 无线组密钥的成员绑定轮换（第18章）
- **问题**: 设备离开网络后仍持旧 GTK 怎么办？
- **方法论的使用**: 把成员变更事件登记为轮换触发器——设备离开即轮换 GTK，新成员加入亦然。
- **结论**: 组密钥的生命周期必须与成员资格绑定，撤销传播由轮换实现。
- **结果**: 802.11i 四次握手+GTK 更新成为标准流程；DNSSEC 侧连否定应答也要可验证（第19章），同族思想。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计证书/凭证撤销体系（代码签名、内部 PKI、设备证书）。
2. 离线验证场景的凭证时效设计（构建机、边缘设备不能联网查状态）。
3. 评估吊销机制实效（CRL/OCSP 的窗口期、软失败配置）。
4. 组密钥/共享秘密的成员变更流程设计。

### 语言信号 (用户的话里出现这些就应激活)

- "撤销多久生效 / revocation propagation delay"
- "CRL/OCSP 窗口期 / stale revocation check"
- "离线怎么验证证书有效 / offline certificate validation"
- "旧证书/旧 token 重放 / replaying old certificates"
- "成员离开后要换密钥吗 / rekey on member departure"

### 与相邻 skill 的区分

- 与 `stallings-trust-topology-blast-radius` 的区别: 那个管"谁有权签"（签发权集中度与爆炸半径），本 skill 管"签出去的怎么收回"（失效传播的时间语义）——签发线与撤销线分开审计。
- 与 `stallings-credential-splitting` 的区别: 那个用拆分结构消除寿命两难，本 skill 用短有效期做撤销的近似重构——有效期是传播问题的解，凭据拆分是结构解，取材角度不同。
- 与 `stallings-fail-direction-audit` 的区别: 那个问"配置错误/组件崩溃时返回什么"，本 skill 问"失效通知何时到达"——方向与时间是两个独立缺陷维度。

## E — 可执行步骤 (Execution)

1. **盘点凭证类别与传播机制**：对每类凭证写出撤销后依赖方通过什么途径知道（在线查询/推送列表/不查）。
   - 完成标准: 凭证×传播机制表成文。
2. **算不设防窗口**：若"通知所有人"不可行，用有效期重构——窗口=有效期+时钟偏差+查询滞后，逐类算出数值。
   - 完成标准: 每类凭证有显式窗口值。
   - 判停条件: 一次性短命凭据（生命周期内无撤销需求）停在此步按一次性处理。
3. **登记窗口风险与应急通道**：把窗口写进风险登记；泄露应急走双通道（吊销+钉扎名单/带外通知）。
   - 完成标准: 风险登记含窗口值与应急流程。
4. **列成员变更触发器**：对组密钥/共享秘密场景，把成员加入/离开/角色变更事件列为轮换触发器清单。
   - 完成标准: 触发器清单成文并与流程挂钩。
5. **声明撤销语义**：为每类凭证写出"N 分钟/天内生效"的显式声明，进接口文档与 SLA。
   - 完成标准: 语义声明成文，验证方实现与声明一致。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 会话密钥类一次性材料——本无撤销问题，交给 v38 的寿命拆分。
- 把"能吊销"当"已吊销"——没有时间语义的吊销声明不构成安全保证。

### 作者在书中警告的失败模式

- 公开广播公钥的伪造窗口正是"发现+通知"的滞后时间，广播型分发没有吊销与时效概念（ce053）。
- 公钥目录的记录可被篡改、管理员私钥单点（ce054）——传播机制本身也需保护。

### 作者的盲点 / 时代局限

- 书内撤销工具以时间戳+CRL+DANE 为主（成书 2017 前），OCSP 软失败、证书透明度等现代实践着墨很少；"短有效期简化撤销"是书内逻辑的外推应用（如 7 天代码签名证书），书内未给此类工程参数。

### 容易混淆的邻近方法论

- v33 签发集中度、v47 fail 方向、v38 凭据拆分。
