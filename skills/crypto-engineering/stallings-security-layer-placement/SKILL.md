# 协议栈层次与覆盖段选型

## R — 原文 (Reading)

> "使用IPsec的优点在于，它对终端用户和应用均是透明的，并且提供通用的解决方案。另外，IPsec"
>
> — 方法论出处，第17章 17.1 Web 安全威胁与对策（引文按 OCR 原样保留截断）

---

## I — 方法论骨架 (Interpretation)

同一个密码机制，放在协议栈不同层，得到的是不同的系统：网络层（IPsec）覆盖杠杆大、对应用透明，但不懂数据语义；传输层（TLS）折中；应用层（S/MIME）语义精准（能区分哪笔操作、能签名追责）但要逐应用实现。三条选型规则：

1. **透明性是可枚举的部署收益**，不是形容词：不改应用、不培训用户、无法被应用绕过——逐项列出并计价。
2. **先画覆盖段图**：保护覆盖路径的哪一段？分段保护≠端到端——每跳安全不等于全程安全，802.11i 只护 STA-AP 段、网关终止 TLS 后的内网明文段，这些"被遗忘的明文段"要显式登记信任理由。
3. **模式判据**：传输/隧道模式按"保护对象是载荷还是整包+SA 端点在哪"选；实现介质也参与选型（软件素曲线/硬件二元曲线的权衡）。

选型输出是"覆盖段图+透明性收益清单+语义粒度成本"三联，典型结论是两层叠加（传输层全覆盖+应用层高价值操作签名）而非二选一。

## A1 — 书中的应用 (Past Application)

### 案例 1: Web 安全三位置比较（第17章）
- **问题**: Web 通信安全应落在网络层、传输层还是应用层？
- **方法论的使用**: 同机理不同落点的三轴比较——IPsec 对终端用户和应用透明、提供通用解决方案、可过滤选定流量；SSL/TLS 在传输层折中；S/MIME/SET 在应用层语义精准但逐应用实现。
- **结论**: 无全局最优，按"保护边界+部署成本+粒度"选落点。
- **结果**: 三位置谱系成为全书部署章的组织框架。

### 案例 2: IP 层的一次实现全应用受益（第20章）
- **问题**: 为什么把安全下沉到 IP 层？
- **方法论的使用**: 覆盖杠杆+五项可枚举优点（对应用透明、免逐应用改造等）+传输/隧道模式判据（保护载荷 vs 整包、SA 端点）。
- **结论**: 同一机制 IPv4/IPv6 共用，防护落地不必等新协议普及。
- **结果**: IPsec 成为跨应用保护的基准方案。

### 案例 3: 802.11i 的显式边界与邮件双形态（第18、19章）
- **问题**: 无线加密保护到哪一段？邮件该用传输加密还是端到端？
- **方法论的使用**: 画覆盖段——802.11i 显式声明只保护 STA-AP 段，AP 之后属信任域内明文；邮件侧 STARTTLS 是跳到跳传输加密，S/MIME 是端到端内容保护，两者覆盖段不同。
- **结论**: 每跳安全≠全程安全；覆盖段必须在架构文档中显式声明。
- **结果**: "明文段登记信任理由"成为部署评审的固定检查项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 微服务间通信选型：服务网格 mTLS 还是应用层业务签名。
2. 全链路加密评估——找出哪里还有明文段（网关终止后、内网东西向）。
3. VPN/网关/端到端方案比较（远程访问、跨域互联）。
4. "上了 TLS 就够了吗"类评审。

### 语言信号 (用户的话里出现这些就应激活)

- "IPsec 还是 TLS / which layer, IPsec vs TLS"
- "端到端还是逐跳 / end-to-end vs hop-by-hop"
- "服务网格 mTLS / service mesh"
- "网关解密/终止 / TLS termination at gateway"
- "内网还要加密吗 / encrypt internal traffic"

### 与相邻 skill 的区分

- 与 `stallings-control-anchor-forgeability` 的区别: 本 skill 选层与覆盖段（放哪里），那个在网络/准入语境下核对每个检查点依赖的标识是否可伪造（落定后怎么验）——先选层再验锚。
- 与 `stallings-two-phase-gated-access` 的区别: 那个是选定层内的开门状态机设计，本 skill 决定开门机制长在哪一层。
- 与 `stallings-metadata-length-side-channel` 的区别: 那个管覆盖段之外的可观测面——覆盖图画完后，段外观测（长度/存在性）另按其审计。

## E — 可执行步骤 (Execution)

1. **画路径图**：画出通信路径全部跳数与信任域边界，标注每段当前保护状态。
   - 完成标准: 路径图成文，每段有保护机制名或"明文"标记。
2. **登记明文段**：标出全部明文段（网关终止后、AP 后、服务内），逐段问"该段在信任域内吗"并写明理由。
   - 完成标准: 明文段清单+信任理由成文。
3. **三轴比选落点**：覆盖杠杆（一次保护多少流量）、透明性收益（逐项枚举）、语义粒度（能区分哪笔操作/能否追责），对候选层打分。
   - 完成标准: 三轴打分表成文。
4. **设计叠加**：单层不足时设计两层叠加（如传输层全覆盖+应用层高价值操作签名），写明各层职责与不重叠的理由。
   - 完成标准: 叠加方案职责表成文。
   - 判停条件: 单跳封闭链路（点对点专线）按跳保护即可，无需叠加。
5. **归档**：把覆盖段图与选型理由写进架构文档，作为后续审计基准。
   - 完成标准: 文档评审通过。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 落点已定后的协议配置加固——那是 v44/v47 的对象。
- 以"透明"为唯一标准——透明方案不懂数语义，业务级追责仍需应用层补充；透明性只是三轴之一。

### 作者在书中警告的失败模式

- 每跳安全≠全程安全；AP 后明文段被遗忘（覆盖段未显式声明）。
- 应用层方案逐应用实现的成本——覆盖率不足是 DKIM 产生五因素的动因之一（同书第19章）。

### 作者的盲点 / 时代局限

- 书中三层谱系以 2017 前协议为样本（成书时间），无 service mesh/SASE/QUIC 词汇；映射到微服务架构时"mTLS=传输层形态、业务签名=应用层形态"的类比需自行完成并注明。

### 容易混淆的邻近方法论

- v44 锚点可伪造性（层内检查点）。
- v46 段外观测面、v52 环境迁移重推（覆盖段是其中一维）。
