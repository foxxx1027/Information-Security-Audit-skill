# 安全方案四要素核对

## R — 原文 (Reading)

> "1.设计一个算法，它执行与安全相关的变换。该算法应是攻击者无法攻破的。2.产生算法所使用的秘密信息。3.设计分配和共享秘密信息的方法。4.指明通信双方使用的协议，该协议利用安全算法和秘密信息实现安全服务。"
>
> — 方法论出处，第1章 1.8 网络安全模型（source.txt 行1792–1796）

---

## I — 方法论骨架 (Interpretation)

一个安全方案不是"选了个算法"就成立的，它由四件互相独立的事情共同构成：

1. **算法**：执行安全变换的函数，要有"攻击者无法攻破"的证据。
2. **秘密产生**：密钥从哪来、随机性够不够。
3. **分发与共享**：秘密怎么到对方手里而不落在攻击者手中——这栏最容易被完全遗忘。
4. **协议**：双方按什么时序、什么格式使用算法与秘密。

评审时把这四栏当验收栏：每栏都要拿出可验证的证据（算法分析报告、随机源说明、KMS/分发通道设计、协议时序图）。任何一栏空白，方案整体不可用——攻击者永远攻击最弱的一栏，不会陪你比拼最强的一栏。这也是快速戳破"算法栏满分"式方案的问句：密钥怎么生成？怎么到对端？双方按什么顺序说话？

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 对称密码模型把"密钥怎么到对方手里"单列成要求
- **问题**: 初学者设计对称加密时只关心算法本身，密钥问题被当作实现细节略过。
- **方法论的使用**: 第3章 3.1 给出对称加密五成分模型后，明确把安全要求拆成两条——算法足够强、收发双方以安全方式获得并保管密钥，"密钥怎么到对方手里"成为与算法同权的独立验收项。
- **结论**: 算法强度只是四要素之一；密钥获得与保管是并列的第二条要求。
- **结果**: 全书第14–15章（KDC、Kerberos、X.509、PKI）两章篇幅整体在补"分发"栏，第20章 IKE 是"协议"栏的完整实例——教材自己的结构就是四要素的组织原则。

### 案例 2: WEP 事故的四栏归因
- **问题**: 802.11 无线保密协议 WEP 被攻破后，业界一度归罪于 RC4 算法。
- **方法论的使用**: 按四栏归因：算法栏（RC4）没有先被攻破，出问题的是秘密产生/分发栏——IV 与共享密钥的拼接方式有漏洞，以及协议栏的封装方式。
- **结论**: "这个问题并不在于 RC4 本身，而是作为 RC4 输入的密钥的产生途径有漏洞"。
- **结果**: 修改 WEP 的密钥产生方式即可修复该攻击，RC4 在其他正确封装下仍可使用——四栏定位避免了"错误退役算法、留下真正病根"的误修。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审一份安全方案/投标书/设计文档，其中密码部分只写了"采用 AES-256 / 国密 SM4"，需要找出还缺什么。
2. 自研系统已选定算法，进入密钥管理与协议设计阶段，需要检查完备性清单。
3. 事故复盘时需要归因：问题出在算法、密钥产生、分发还是协议（如 WEP 型"冤枉算法"场景）。
4. 车联网/V2X、IoT 平台等新场景的密码方案立项评审，算法已定标准算法，成败在其余三栏。

### 语言信号 (用户的话里出现这些就应激活)

- "我们已经用 AES-256/SM2/SM4 加密了，安全性应该没问题了吧"
- "密钥怎么分发还没定，先评审算法部分"
- "key distribution / key management 怎么做"
- "协议时序谁负责设计"
- "这个方案还缺什么 / 方案完备性怎么查"

### 与相邻 skill 的区分

- 与 `stallings-attack-service-mechanism-alignment` 的区别: 那个管"威胁—服务—机制"三层的**外部对齐**（防的攻击与提供的服务是否互相覆盖）；本 skill 管方案**内部结构完备性**的四栏（方案自身缺不缺件）。
- 与 `stallings-algorithm-retirement-crypto-agility` 的区别: 那个管算法生命周期与替换治理；本 skill 在算法栏只问"有没有不可攻破的证据"，不涉退役时间表。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **建四栏表**（算法 / 秘密产生 / 分发与共享 / 使用协议），把被评审方案已有内容逐条归栏。
   - 完成标准: 方案中每一条密码相关陈述都能放进某一栏（或被标注"方案未提及"）。
2. **逐栏取证**：算法栏查分析证据（标准算法+参数，或自研算法的评估）；产生栏查随机源与熵；分发栏查通道与信任假设；协议栏查消息时序图。
   - 完成标准: 每栏填入"证据"或显式写"空白"。
   - 判停条件: 若算法栏即空白（自研无评估、参数不明），直接退回方案，不必评其余三栏。
3. **对空白栏提问**: 对每个空白栏生成针对性问句（如分发栏空白 → "密钥怎么到对方手里？中间人怎么防？"）。
   - 完成标准: 每个空白栏至少一个具体问句，附书内或标准对应解法方向（KDC/证书/IKE 等）。
4. **出结论**: 输出四栏状态表 + 总判定（可用/退回/需补充），并指出攻击者最可能攻击的栏。
   - 完成标准: 结论明确到"哪一栏是当前最弱项、补齐它需要什么"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一算法的数学强度/参数分析（该算法够不够强）——用理想原语判据与难题依赖审计类的技能。
- 已上线系统的运维审计（密钥轮换执行、日志）——四要素是设计完备性框架，不管运行期治理。
- 纯威胁建模（枚举攻击路径）——四栏不管外部威胁，只管方案自身结构。

### 作者在书中警告的失败模式

- 只设计算法即宣称完成方案——第3章把"密钥安全获得与保管"列为与算法并列的第二条安全要求，正是针对此病。
- WEP 型误归因：把分发/协议栏的病算到算法栏头上，导致"退役算法、留下病根"的错误修复。

### 作者的盲点 / 时代局限

- 第7版成书于 2017 前后：云原生 KMS 托管、密钥自动轮换、 Secrets 管理服务等现代分发形态书中基本缺位，"分发栏"取证需自行补充云时代清单。
- 模型默认端点可信（端点被控时密钥从内存/日志泄露，数学强度失效）——书中一笔带过，评审时需另行扩展。
- "算法应是攻击者无法攻破的"在书中未给验收路径，需配合"分析代价≥穷举"类判据使用。

### 容易混淆的邻近方法论

- 与"深度防御"（多层叠加）不同：四要素是并列必需件，不是可互相补偿的层——分发栏不能靠算法栏加倍来补偿。
- 与"安全设计准则 13 条"不同：准则是逐条启发式，四要素是方案文档的章节骨架。
