# 两阶段开门与控制面先行

## R — 原文 (Reading)

> "虽然验证成功，端口保持阻塞直到临时密钥安装到STA和AP上，密钥安装发生于4次（4-Way）握手期间。"
>
> — 方法论出处，第18章 18.4.4 认证阶段（802.11i）

---

## I — 方法论骨架 (Interpretation)

"先认证后放行"只是半句话——认证通过只说明身份核实了，不代表加密通路就绪。把开门拆成**两道独立的门**：第一道门是身份/设备认证（改状态位），第二道门是密钥安装+对端确认（装钥后才开数据面）。两道门之间不留"已认证但明文"的窗口期——这是防降级与防中间人的**结构性**保障，靠状态机而非运维纪律实现。

配套四条结构规则：
1. **最小专用通道**：为管控/认证流程预留非受控端口（只放认证流），其余默认拒绝。
2. **策略声明意图、按需兑现**：策略表只声明"该流量须保护"，命中而无 SA 时唤醒密钥协商（IKE），协商完成前流量排队或丢弃。
3. **入站白名单化**：仅显式 BYPASS 才上送，且注明理由（已有 TLS 的 443 端口标"避免双重加密"）——安全叠加不是越多越好。
4. **控制面先行**：路由/邻居/重定向等控制协议的认证是网络生存性前提——控制面被伪造则数据面保护形同虚设。

## A1 — 书中的应用 (Past Application)

### 案例 1: 802.11i 认证后端口仍阻塞（第18章+第16章）
- **问题**: EAP 认证成功、AS 已发 Access-Accept，用户流量可以通了吗？
- **方法论的使用**: 两阶段开门——受控端口在 PTK 安装完成前保持阻塞，4 次握手把密钥装入 STA 与 AP 后才放行；非受控端口只承载认证消息。
- **结论**: 消除"已认证但明文/无密钥"窗口期。
- **结果**: 802.1X 受控/非受控端口模型成为链路层准入的标准实现。

### 案例 2: IPsec 的逐包处理与按需唤醒（第20章）
- **问题**: 出站流量怎么从"策略声明"走到"受保护发送"？
- **方法论的使用**: 五步处理——查 SPD 无匹配即丢（fail-close）；命中 PROTECT 而 SA 缺失则触发 IKE 协商；IKEv2 先建 IKE SA（控制面）再派生业务 SA；入站三步白名单（仅显式 BYPASS 上送）。
- **结论**: 策略声明意图、协商兑现意图；默认拒绝+显式例外。
- **结果**: SPD/SAD/IKE 三件套成为"意图-兑现"结构的标准范本。

### 案例 3: 路由更新的生存性论证（第20章）
- **问题**: 保护数据面就够了吗？
- **方法论的使用**: 控制面先行——IPsec 确保路由广播、邻居广播、重定向报文来自授权路由器且不可伪造；"没有以上安全措施，攻击者可以中断通信或转发某些流量"。
- **结论**: 控制面协议的认证是生存性前提，先于数据面保护。
- **结果**: OSPF 等路由协议运行在启用 IPsec 的路由器上成为部署要求。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. gRPC sidecar/网关零信任握手状态机设计（没有"已认证明文"窗口）。
2. 评审现有流程中"认证后仍有明文窗口"的缺陷。
3. 策略引擎与密钥协商的联动设计（命中策略但密钥未建时怎么办）。
4. 控制面（路由/编排/配置下发/集群 gossip）保护评审。

### 语言信号 (用户的话里出现这些就应激活)

- "认证过了就能发数据吗 / authenticated but no key installed yet"
- "受控端口 / controlled port, 802.1X uncontrolled port"
- "先建 SA/隧道再跑业务 / establish SA before traffic"
- "认证后的明文窗口 / plaintext window after authentication"
- "策略未命中默认怎么办 / default action on policy miss"

### 与相邻 skill 的区分

- 与 `stallings-cheap-check-first` 的区别: 那个是单条流水线内的检查成本排序（哪步先做），本 skill 是"认证与开门"的全局状态机结构（哪扇门何时开）——先定状态机再排管线。
- 与 `stallings-fail-direction-audit` 的区别: 那个定每道门在异常输入下的放行/拒绝方向，本 skill 定门的结构与数量——结构与方向正交，组合使用。
- 与 `stallings-security-layer-placement` 的区别: 那个决定这套状态机长在哪一层，本 skill 是层内的开门协议设计。

## E — 可执行步骤 (Execution)

1. **画当前状态机**：标注认证事件后哪些通路立即打开，圈出"已认证但无密钥"的窗口状态。
   - 完成标准: 状态机图成文，窗口状态被显式标出。
2. **拆两道门**：把开门定义为两个事件——身份通过（改状态位）与密钥就绪（装钥+对端 Finished 类确认）；数据面只绑定第二事件。
   - 完成标准: 状态机无"已认证明文"状态。
3. **预留最小通道**：为认证/管控流定义专用通道（非受控端口等价物），其余默认拒绝。
   - 完成标准: 默认拒绝+通道白名单成文。
4. **定义意图-兑现联动**：命中 PROTECT 而 SA 缺失→触发协商，协商期间流量排队或丢弃（不得明文放行）。
   - 完成标准: 联动规则与超时行为成文。
   - 判停条件: 会话恢复/快速重连路径可合并两门，但必须保留对端活性确认。
5. **审计控制面与例外**：控制面协议逐一确认有认证；已受上层保护的流量标 BYPASS+理由。
   - 完成标准: 控制面清单与 BYPASS 登记表成文。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性无状态请求（无密钥可装时退化为 v31 的排序问题）。
- 以两阶段为名把密钥安装拖到首包之后——书内次序是先装钥后通流量，首包明文不是档位而是缺陷。

### 作者在书中警告的失败模式

- Kerberos v4 用 PCBC 加密扩散顺带做完整性，被交换密码块攻击攻破（ce061）——省掉独立完整性机制的"合并门"最终失败。
- WEP 单向挑战认证三重缺陷（明文挑战+流加密泄钥流、单向、无会话绑定，ce081）——门没拆对，认证形同虚设。

### 作者的盲点 / 时代局限

- 书中状态机以 802.11i/IPsec 为原型（成书 2017 前）；QUIC/0-RTT 类把握手与应用数据合并的延迟优化取舍书内无内容——引用时按两道门原则自行评估其窗口。

### 容易混淆的邻近方法论

- v31 成本排序（管线内）、v47 fail 方向（异常行为）、v43 层次选型（位置）。
