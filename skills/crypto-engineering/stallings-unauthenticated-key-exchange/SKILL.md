# 无认证密钥交换=中间人（反例族）

## R — 原文 (Reading)

> "此时，Bob和Alice想，他们已共享了密钥，但实际上，Bob和Darth共享密钥K，而Alice和Darth共享密钥K2。"
>
> — 方法论出处，第10章 10.1.3 中间人攻击（Darth 双钥替换）

---

## I — 方法论骨架 (Interpretation)

密钥协商解决"我们算出同一个秘密"，不解决"对方是谁"。离散对数再难，也回答不了"我在和谁加密"。

所以评审任何密钥建立流程，第一步只问一个问句：**协议里出现的每个公钥由谁背书？**——证书？预置信任？带外指纹？凡是答不出来的公钥，攻击者都可以替换成自己的。

替换的后果有一门"攻击经济学"：攻击者做一次主动的双钥替换（与双方各建一把密钥），此后**只需被动窃听**——主动攻击的成本只付一次，被动收益永久延续。这个不对称使无认证密钥交换在实践中等于明文。

反例族覆盖四种协议形态，同一问句全部命中：

1. 裸 DH（Darth 双钥替换）；
2. Merkle 简单方案（零留存优点不救认证缺失）；
3. TLS 匿名 DH 套件；
4. 无背书公钥分发。

修复方向是数字签名+公钥证书、预共享密钥、或显式化的带外认证（二维码指纹配对、TOFU+密钥变更告警）。

## A1 — 书中的应用 (Past Application)

### 案例 1: Darth 攻破裸 Diffie-Hellman（第10章）
- **问题**: DH 的数学无懈可击，窃听者算不出密钥——部署它就安全了吗？
- **方法论的使用**: 问"YA、YB 这两个公钥由谁背书"——无背书，则 Darth 截获替换双方公钥，与双方各共享一把密钥。
- **结论**: Bob 与 Darth 共享 K1、Alice 与 Darth 共享 K2，双方全程无察觉；Darth 可纯转发（窃听）或换消息（篡改）。
- **结果**: 书中判定根因是"协议没有对通信的参与方进行认证"，修复指向数字签名与公钥证书（第13、14章）。

### 案例 2: Merkle 简单方案的被动接管（第14章）
- **问题**: Merkle 方案"A 现场生成密钥对、B 用其公钥加密会话钥回传、用完即弃"，通信前后系统不存任何密钥——暴露面最小的精巧设计，够吗？
- **方法论的使用**: 同一问句——A 的公钥经明文信道传输且无任何背书，Darth 替换之，解出 B 的会话钥再用 A 真公钥转发。
- **结论**: "通信前后不存在密钥"的优点救不了认证缺失；A、B 都以为建立了私密信道，实际 Darth 全程持钥，此后只需窃听。
- **结果**: 证明零留存优点与认证是两个正交属性，反例被固定为公钥分发章节的标准教训。

### 案例 3: IKE 对裸 DH 三缺陷的逐条修补（第20章）
- **问题**: IPsec 场景直接用教科书 DH 做密钥确定行吗？
- **方法论的使用**: [HUIT98] 列三缺陷——不提供身份标识、易受中间人攻击、计算昂贵引阻塞攻击；IKE 五特性逐条补（Cookie 治阻塞、认证治中间人、nonce 防重放）。
- **结论**: 密钥协商原语必须包装认证与防滥用才可部署。
- **结果**: IKE"保持了 Diffie-Hellman 优点而去掉了其缺点"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 无 PKI 环境（IoT 设备首次配对、内网工具、BLE/App 连接）建立加密信道。
2. 评审协议或 TLS 套件清单，看到 anonymous/DH_anon 类配置。
3. 客户端弹出"直接接受密钥/自签名证书"告警，评估风险。
4. 设计首次信任流程（TOFU、二维码指纹、预置根）。

### 语言信号 (用户的话里出现这些就应激活)

- "反正有 ECDH / DH is secure anyway"
- "anonymous DH / DH_anon / 匿名套件"
- "首次连接直接信任 / trust on first use, TOFU"
- "无 PKI 怎么交换密钥 / key exchange without PKI"
- "自签名证书可以用吗 / is a self-signed certificate OK"

### 与相邻 skill 的区分

- 与 `stallings-protocol-belief-analysis` 的区别: 本 skill 是单一问句族（每个公钥谁背书），可在五分钟内过完；那个是全协议的信念清单+反例证伪+修补再审的完整审计法——本 skill 常作为其反例构造阶段的快速入口。
- 与 `stallings-trust-topology-blast-radius` 的区别: 那个量化背书者过多（CA 集中度）的风险，本 skill 先确认"有没有背书"——从 0 到 1 是本 skill，从 1 到 N 的治理是那个。
- 与 `stallings-control-anchor-forgeability` 的区别: 那个锚定的是管控流程依赖的标识（MAC/IP/域名），本 skill 锚定密钥协商参数（公钥）——同一"锚点"思想，不同对象。

## E — 可执行步骤 (Execution)

1. **画交换图**：写出密钥建立的全部消息，列出其中出现的每个公钥/静态协商参数。
   - 完成标准: 公钥清单成文，无遗漏。
2. **逐个问背书**：对每个公钥回答"由谁背书"——证书链、出厂预置、带外指纹、PSK；答不出者标记为 MITM 面。
   - 完成标准: 每个公钥都有背书来源或 MITM 标记。
   - 判停条件: 若信道本身已受物理/带外保护（本地回环、物理接触配对），记录豁免并结束。
3. **选修复方式**：对标记处选签名+证书、预共享密钥、带外指纹配对、或 TOFU+密钥变更告警（显式化而非默默跳过）。
   - 完成标准: 修复方案与告警路径成文。
4. **重演 Darth 场景验证**：攻击者替换公钥后各消息流向如何？验证方在哪一步发现异常？
   - 完成标准: 替换攻击在验证方必然失败，或有可见告警。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已认证会话内的算法性能比较——那不是认证缺失问题。
- 把"加了证书"当终点——证书路径自身的校验缺陷（主流库集体中招，ce076）与信任锚治理（v33/v34）是下一层审计，勿在此混谈。

### 作者在书中警告的失败模式

- SSH 允许未验证接受密钥："短期内有实际意义"但对主动攻击脆弱（ce079）——跳过验证不是中性的便利，是可利用面。
- 裸 DH 还有阻塞攻击面（昂贵计算前先证可达）——那是 v31 的对象，勿在 MITM 论证里混用。

### 作者的盲点 / 时代局限

- 反例族样本止于 2017 前的协议形态（成书时间），Noise 协议、双向静态密钥混合等现代范式书内无内容；IoT 配对外推场景（二维码指纹）是书内 TLSA/PSK 思想的迁移而非原文。

### 容易混淆的邻近方法论

- v36 三步审计法（本 skill 是其子问题）。
- v44 锚点可伪造性（标识 vs 公钥）。
