# 密钥建立的认证绑定——裸 DH 必遭 MITM，签名覆盖一切瞬时值

## R — 原文 (Reading)

> 遗憾的是，这种方案很容易遭受主动敌手发起的中间入侵攻击。
>
> 很遗憾的是，因为W并不知道V的签名算法sigv，所以他无法计算出关于字符串ID(U)IlαIα的V的签名。
>
> — 原作者,原始方法论来源第11章 11.2、11.2.2（中译本 OCR，逐字保留，ID(U)IlαIα 为 ID(U)‖α_U‖α_V 之 OCR）

---

## I — 方法论骨架 (Interpretation)

密钥交换解决"双方算出同一个数"，完全不解决"对方是谁"。裸 DH 上主动攻击者与双方各建一条会话居中转发，双方毫无察觉——这不是 DH 弱，是它从未承诺认证。把认证织进密钥建立要过四层检查。第一层，认证交织：认证必须与密钥交换同场完成，"先裸 DH 再用结果认证"会被降级/替换绕过。第二层，签名覆盖域：STS 式签名必须盖住双方身份+双方 DH 指数+会话上下文，漏绑任何一个瞬时值，攻击者就替换那个值重开 MITM——无需伪造签名本身。第三层，持有证明：证书只认证公钥不证明持有（证书可被任何人复制出示），验证链过后仍需挑战-应答确认对端掌握私钥；TA 签发证书前同样要 PoP，否则为伪造公钥背书。第四层，密钥确认：双方"算出同一 K"不等于"确认对方已算出且只有对方知道"——隐式认证/隐式确认/显式确认三层语义要按需求声明。四层缺任何一层，"协商出的密钥"就可能是与攻击者共享的密钥。

## A1 — 书中的应用 (Past Application)

### 案例 1: 裸 DH 的双向劫持
- **问题**: 双方交换 α^a、α^b 得到共享密钥，被动敌手也算不出，够吗？
- **方法论的使用**: 第 11 章 11.2：W 与 Alice 协商 g^{aw}、与 Bob 协商 g^{bw}，居中逐条解密再加密转发。
- **结论**: DH 只提供密钥一致性，不提供对端身份；主动攻击者可长期潜伏且不破坏任何数学假设。
- **结果**: 密钥协商必须叠加签名/证书/预共享密钥（STS、签名 DH），并绑定身份到指数。

### 案例 2: STS 签名覆盖域——漏一个值就重开 MITM
- **问题**: 加了签名，签什么才够？
- **方法论的使用**: 第 11 章 11.2.2：STS 让 V 对 ID(U)‖α_U‖α_V 签名——W 不知道 V 的签名算法，无法为替换后的指数伪造签名。
- **结论**: 签名覆盖双方身份+两个指数才能阻断替换；漏绑任一瞬时值，该值即成替换点。
- **结果**: "签名覆盖域逐项清点"成为协议审计算术（缺身份/缺对端指数/缺方向=可利用缺口）。

### 案例 3: Girault 的 PoP 前提
- **问题**: TA 给用户的公开值背书，需要什么前提？
- **方法论的使用**: 第 11 章 11.4：书中明示"TA 应被确信在为 U 计算 p_U 之前，U 知道 a_U 的值"。
- **结论**: 签发前不验证私钥持有，攻击者可让 TA 为自己不掌握私钥的公开值背书，随后以该身份参与协商。
- **结果**: PoP 成为 CA/TA 注册流程的硬检查项；"用户已知私钥"从隐含假设升格为可检验前提。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. IoT 配网/设备接入协议：设备广播公钥、App 回公钥、双方 ECDH 出密钥，缺什么。
2. 审计自研安全信道：哪里做的 DH、签名盖了哪些字段、有无密钥确认回合。
3. 证书流程评审：CA 签发有无 PoP、服务端验完证书后有无持有证明。
4. 事故调查：unknown key-share / 中间人劫持嫌疑，定位哪一层绑定缺失。

### 语言信号 (用户的话里出现这些就应激活)

- "MITM / man-in-the-middle / 中间人能劫持 DH 吗"
- "ECDH 之后要不要签名 / 签名应该盖哪些字段"
- "STS / signed Diffie-Hellman / 密钥协商认证"
- "proof of possession / PoP / 证书验证通过就等于对方持有私钥吗"
- "key confirmation / 密钥确认 / 对端真的算出同一个密钥了吗"

### 与相邻 skill 的区分

- 与 `stinson-certificate-validation-checklist` 的区别: 那个管证书链的验证四步与信任模型；本 skill 在证书验证通过之后接管——持有证明与密钥确认层。衔接句：证书验证是本 skill 第三层的输入。
- 与 `stinson-cross-session-reflection-defense` 的区别: 那个管协议消息的跨会话搬运（域分离）；本 skill 管密钥建立本身的认证绑定（MITM/覆盖域/PoP）——一个已认证的协议仍可能被搬运，反之已域分离的协议仍可能被 MITM。
- 与 `stinson-freshness-replay-decision-tree` 的区别: 那个管旧消息重放；本 skill 管攻击者实时插入——Denning-Sacco 型"旧密钥+重放"组合需两 skill 配合定位。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画出密钥建立消息流**: 谁发什么值、有无签名/MAC、每个认证值覆盖的字段逐项列出。
   - 完成标准: 消息流图 + 认证覆盖字段表。
   - 判停条件: 若发现无任何认证的公钥交换（裸 DH 型），直接输出"MITM 双向劫持成立"结论跳到步骤 4。
2. **核对认证交织**: 认证与密钥交换是否同场（认证值盖住 DH 瞬时值）；"事后认证"方案标红（可被降级）。
   - 完成标准: 交织判定一行；覆盖域逐项打勾（双方身份、双方指数、会话上下文、方向）。
3. **核对持有证明与签发前提**: 验证链通过后的挑战-应答；TA/CA 签发前的 PoP。
   - 完成标准: 两处 PoP（协议侧与签发侧）各自判定存在/缺失。
4. **核对密钥确认语义**: 隐式认证/隐式确认/显式确认三层，按声明与需求对照；缺失显式确认时标注"不知对端是否已算出同一密钥"。
   - 完成标准: 三层语义判定表 + 与业务需求的匹配结论。
5. **输出修复方案**: 设备出厂证书/双向签名覆盖（身份×指数×上下文）+确认回合；每层缺口对应一条修复。
   - 完成标准: 四层检查结论 + 修复后的消息流草图。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 对称密钥预分发体系（Blom/KPS 类）——其风险结构是合谋阈值，另归门限审计。
- 证书链与信任模型本身的问题（路径构造、吊销）——归证书清单；本 skill 只在"证书可信"之后继续。
- 纯加密算法选型（不涉及密钥如何建立）。

### 作者在书中警告的失败模式

- "交换公钥就能加密"的直觉——裸 DH 的居中转发（第 11 章 11.2）。
- 签名漏绑瞬时值——替换未签名值重开 MITM，无需伪造签名（11.2.2）。
- 证书≠持有：证书仅含公共信息、可被重新分配给任何用户（第 9 章 9.3.1）。
- TA 未做 PoP 即签发——为伪造公钥背书（Girault 前提，11.4）。

### 作者的盲点 / 时代局限

- 成书 2006 年：TLS 1.3 的握手设计（含 0-RTT 的重放问题）、HMQV 等后续协议不在书内；本书四层检查仍适用但应补现代语义（如 ECDH 群参数校验、downgrade 保护）。
- 前向安全性（PFS）在书中 MTI/STS 讨论中点到但未形成独立判据——现代审计应把"长期密钥泄露是否危及历史会话"补为第五问。

### 容易混淆的邻近方法论

- "认证的密钥协商"≠"加密+认证的通道"：前者发生在密钥诞生前（谁在跟谁协商），后者用已诞生的密钥保护数据——时序不同，检查表不同。
- PoP ≠ 身份验证：PoP 证明持有私钥这一事实，不证明该身份合法（身份合法性归证书链与信任模型）。
