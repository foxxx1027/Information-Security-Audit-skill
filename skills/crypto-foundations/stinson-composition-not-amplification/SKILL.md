# 组合 ≠ 增强——幂等性、可交换性与组件独立性的边界检验

## R — 原文 (Reading)

> 一个密码体制是幂等的，如果S2=S。我们在第1章研究的许多密码体制都是幂等的。
>
> 因此，如果S和S，都是幂等的，我们要想使S×S不是暴等的，则S和S，一定是不可交换的。
>
> — 原作者,原始方法论来源第2章 2.7（中译本 OCR，逐字保留：S2=S 为 S²=S、暴等为幂等之 OCR 噪声）

---

## I — 方法论骨架 (Interpretation)

"多套一层总更安全"是直觉，代数给出的答案是：默认增益为零，宣称增益需三重论证。判据一，幂等性：若组件 S 自己叠自己没变化（S²=S，古典密码里移位、代换、仿射、希尔、维吉尼亚全是），对它迭代只是白费轮密钥；DES 16 轮有意义的前提是轮函数非幂等。判据二，可交换性：两个幂等组件若还可交换，乘积照样幂等——组合这个动作本身不产生任何安全性；想让幂等组件的乘积非幂等，二者必须不可交换。判据三，独立性：计数上密钥独立则穷举界相乘，但密钥同源派生（无域分离的 HKDF 复用）时增益塌缩回单钥；结构上两个并行组件用相同参数相同种子（收缩生成器双 LFSR 同配置），输出完全相关，"双路"结构被抵消，熵清零。对照样本：HMAC 内外两层各司其职（密钥绑定首尾）是正确组合——组合的价值来自角色分工与独立密钥，不来自"多"本身。审计动作：对任何组合提议先默认增益=0，要求设计者按幂等/独立/密钥三条逐一举证，再按攻击类别分别验证。

## A1 — 书中的应用 (Past Application)

### 案例 1: 古典体制皆幂等——迭代白做
- **问题**: 用代换密码加密两次会不会更安全？
- **方法论的使用**: 第 2 章 2.7：移位、代换、仿射、希尔、维吉尼亚、置换密码都满足 S²=S——两次加密等价于用合成密钥加密一次，密钥管理开销翻倍、强度不变。
- **结论**: 迭代增密的前提是组件非幂等；多轮设计（DES/AES）的结构合法性由此建立。
- **结果**: "轮数要有意义"从口号变成可判定的代数性质（先证非幂等再谈多轮）。

### 案例 2: 幂等+可交换 ⇒ 乘积仍幂等
- **问题**: 那用两个不同的幂等体制做乘积呢？
- **方法论的使用**: 第 2 章 2.7 注记：结合律证明 (S1×S2)²=S1×S2 当两组件幂等且可交换；习题 2.20 进一步给反例方向（维吉尼亚乘积猜想取 lcm 时因密钥数减少而不成立）。
- **结论**: 组合产生安全性有代数边界条件——"组合即增强"被定理级证伪。
- **结果**: 审计组合提议的两把尺子定型：计数（密钥空间）与代数（交换性）。

### 案例 3: 收缩生成器双 LFSR 同种子——相关性抵消双路
- **问题**: 两条 LFSR 并行再收缩取舍，结构够乱了吗？
- **方法论的使用**: 第 8 章习题 8.3：两个 LFSR 取相同抽头相同种子，取舍位与被取舍位完全相关，输出退化为单个 LFSR 的子序列，线性分析可恢复。
- **结论**: 组件独立性是可验证的设计约束——配置复制（同参数同种子）使冗余退化为相关，熵清零。
- **结果**: 并行/多路组件必须独立密钥、不同参数；独立性写进实现检查表。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 团队提议"双重加密"：先 AES 再 Serpent/ChaCha，密钥同源派生，评估增益。
2. 设计评审出现"两套随机源/两个算法混着取""多重哈希叠加"等增强提议。
3. 自研混淆器用多轮相同变换叠加，需要判断轮数是否有意义。
4. 评估密钥派生方案：多把密钥从同一主密钥无域分离派生的实际强度。

### 语言信号 (用户的话里出现这些就应激活)

- "double encryption / 双重加密/两连加密安全提升多少"
- "idempotent / 幂等是什么 / 同一个算法跑两遍"
- "composition security / 组合起来更安全吗"
- "两个随机源/两把锁总比一把强吧"
- "密钥都从主密钥派生，算不算双重保护"

### 与相邻 skill 的区分

- 与 `stinson-encrypt-authenticate-composition` 的区别: 那个管加密与认证两种不同功能的拼接（顺序/模式/构造标准化）；本 skill 管"同类组件叠加是否增强"（幂等/独立/密钥同源）——加密+MAC 是分工，AES+AES 是叠加，问题不同。
- 与 `stinson-structural-security-bound` 的区别: 那个讲好设计如何用结构获得可证安全界；本 skill 讲坏组合为何零增益——组合的正确性论证（如 HMAC 的两层）恰是那个 skill 的正面案例。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **写出组合形态**: 组件列表、各组件运算、轮数/层数、密钥来源（独立生成/同源派生+派生方式）。
   - 完成标准: 形态表完整；同源派生显式标注域分离有无。
2. **幂等性检验**: 单组件自叠加是否产生新变换（S²=S 即命中）；多轮迭代的前提逐项核对。
   - 完成标准: 每组件"幂等/非幂等"判定；命中幂等的迭代标"零增益"。
   - 判停条件: 若命中幂等或同源密钥无域分离，直接输出"默认增益=0"结论跳到步骤 5。
3. **独立性与可交换性检验**: 并行组件参数/种子是否独立；可交换且幂等的组合标注乘积仍幂等；相关性推演（同配置退化为单路）。
   - 完成标准: 每对组件的独立性判定 + 相关路径说明。
4. **密钥计数核算**: 独立密钥则穷举界相乘；同源派生折算实际熵；对比宣称增益。
   - 完成标准: "宣称增益 vs 核算增益"对照一行。
5. **输出结论**: 默认增益=0 的判定维持或推翻；推翻需三重论证（非幂等+组件独立+密钥独立）+ 按攻击类别的分别验证；正面参照 HMAC 式分工组合。
   - 完成标准: 结论含三重论证逐项状态与修复建议（域分离派生、独立参数）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有组合证明的标准构造（3DES、HMAC、CCM）——它们是本 skill 的正面参照，不是审查对象。
- 加密与认证的拼接顺序问题——归组合检查表（分工型组合）。
- 协议组合（两条协议共存的干扰）——那是协议形式化验证的领域，本书代数判据不覆盖。

### 作者在书中警告的失败模式

- 古典体制全幂等——迭代只增密钥管理不增安全（第 2 章 2.7）。
- 幂等+可交换的乘积仍幂等——"组合即增强"被定理证伪（2.7 注记）。
- 双 LFSR 同参数同种子——熵清零（第 8 章习题 8.3）；同源密钥派生使穷举界塌缩。

### 作者的盲点 / 时代局限

- 成书 2006 年：多重加密的形式化（2DES 与中间人相遇攻击使双重加密只增 1 位安全、3DES 的 Mitsuru 分析）在书中未展开——评审双重加密时应补查相遇攻击（meet-in-the-middle），它使"双倍密钥≠双倍安全"有更精确的定量。
- 密钥派生的域分离（HKDF info 参数）实践未在书中出现。

### 容易混淆的邻近方法论

- "组合零增益"≠"组合有害"：正确组合（分工+独立密钥）有真实价值；本 skill 反对的是"叠同类"的增益幻觉。
- 与 ε 放大（多次重复降低错误概率）的区别：概率放大是同构重复在概率空间的合法组合（Miller-Rabin 多轮），密码组合的失效是因为敌手可以整体攻击——两者"重复"的对象不同，勿混用结论。
