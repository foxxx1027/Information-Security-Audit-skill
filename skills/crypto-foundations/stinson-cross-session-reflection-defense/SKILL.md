# 跨会话搬运攻击——每条消息流的认证值必须以不同方式计算

## R — 原文 (Reading)

> 不难看出协议9.1是不安全的，即便使用的消息认证码是安全的。它不能抵抗一种典型的攻击一一并行会话攻击。
>
> 显然，这种攻击是把一个会话中的消息重用到另一个会话的不同消息流中。……最基本的设计思想是要保证每个消息流中的消息以不同的方式来计算。
>
> — 原作者,原始方法论来源第9章 9.2、9.3.3（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

协议攻击有一类完全绕过密码学：攻击者不伪造任何 MAC，而是开两条并行会话，把 A 会话里合法方的应答搬运到 B 会话里充当自己的应答——让被冒充者"亲手"替攻击者完成认证。机理是认证值在两条消息流中计算方式相同：MAC_K(r) 不含身份，Bob 在会话 2 发出的挑战 r 原样转给 Alice，她算出的合法 MAC 正好满足会话 1 的验证。判据因此可操作：画出协议全部消息流，检查每条流的认证输入是否有唯一区分符——两个流的认证输入相同即高危。修复只有一种方向：域分离——把会话标识、双方身份、方向位/角色、全部瞬时值塞进每条流的 MAC/签名输入，使任何值跨流搬运后验证必败。两个附属纪律：其一，"多加一个随机数"不是修复——新自由度可能反被并行会话利用（书中协议 9.7 反例），改动后必须重跑攻击分析；其二，交互轮数本身是安全约束——两消息流的随机挑战识别方案被证明结构性不可能，少于承诺-挑战-应答三流的"极简协议"直接判死。

## A1 — 书中的应用 (Past Application)

### 案例 1: 协议 9.1——MAC 安全但协议不安全
- **问题**: 挑战-应答互认用安全的 MAC，协议就安全吗？
- **方法论的使用**: 第 9 章 9.2：Oscar 冒充 Alice 向 Bob 发起会话取挑战 r_B，再冒充 Bob 向 Alice 发 r_B；Alice 回的 MAC_K(r_B) 被转给 Bob，Bob 接受 Oscar 为 Alice。
- **结论**: 原语安全（MAC 不可伪造）与协议安全是两个命题；认证输入不含身份即可跨会话搬运。
- **结果**: 协议 9.2 的修复仅是把 ID 加入 MAC 输入——一行域分离改动。

### 案例 2: 协议 9.7——"多加一个随机数"反被攻破
- **问题**: 已安全的协议再加一个随机数 r3 会更安全吗？
- **方法论的使用**: 第 9 章 9.3.2：新增 r3 引入新自由度，攻击者在两个并行会话间交换被签字符串，使某一方接受本会话未发生的认证。
- **结论**: 协议改动必须重新证明——新增参数可能破坏原有绑定关系；"多了随机数"不等于更强。
- **结果**: 确立"改动后重跑跨会话攻击分析"的纪律，取代直觉增强。

### 案例 3: MTI/A0——对称结构的会话密钥连锁泄露
- **问题**: 有长期密钥与签名的密钥协商，还会被并行会话破吗？
- **方法论的使用**: 第 11 章 11.3：W 同时参与两个会话，利用会话密钥对输入的对称性，把一个已知密钥的会话与公开量组合，推出另一会话的密钥。
- **结论**: 缺会话标识/角色绑定时，已知会话密钥攻击可跨会话传导——密钥独立性需要显式论证。
- **结果**: 修复把会话标签、角色、双方身份纳入密钥推导（KDF 的 context 参数）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计或评审双向认证/挑战-应答协议：扫码登录回调、设备配网、API 互认、IM 消息握手。
2. 渗透测试报告出现"并行会话/反射攻击"字样，需要定位协议缺陷并修复。
3. 协议演进评审：有人在已验证协议上加字段/加随机数，需判断是否引入新自由度。
4. 会议密钥/群密钥方案评审，检查已知一把会话密钥是否会连锁泄露另一把。

### 语言信号 (用户的话里出现这些就应激活)

- "parallel session attack / 并行会话攻击 / reflection attack 反射攻击"
- "MAC 输入只有 challenge，安全吗"
- "domain separation / 域分离怎么加"
- "多加一个随机数/一层签名更安全吧"
- "两个用户同时扫码会发生什么"

### 与相邻 skill 的区分

- 与 `stinson-freshness-replay-decision-tree` 的区别: 那个管"旧消息重放"（时间维：这条消息是不是旧的）；本 skill 管"跨会话搬运"（空间维：这条消息是不是本会话的）——重放防护不覆盖跨会话拼接，反之亦然。
- 与 `stinson-authenticated-key-establishment` 的区别: 那个管密钥建立的整体认证绑定（MITM/签名覆盖）；本 skill 是其协议层攻击语法之一，识别协议（而非原语）上的搬运缺陷。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画出协议全部消息流**: 每条流的发送方、接收方、载荷、认证计算式（MAC/签名输入逐字段列出）。
   - 完成标准: 消息流图完整；每条流的认证输入字段表化。
2. **找相同输入的流对**: 任两条流的认证计算输入完全相同（或可被攻击者凑成相同）即标记。
   - 完成标准: 输出流对清单；每对标注可搬运的字段。
   - 判停条件: 若发现零区分符的流对且场景允许并行会话，直接输出"搬运攻击成立"结论跳到步骤 4。
3. **推演并行会话攻击**: 攻击者开两条会话，分别扮演什么角色、搬运哪个值、哪一步验证被满足；另检查"已知会话密钥→推另一会话"的对称结构。
   - 完成标准: 每条攻击路径逐步写出（会话 S1 谁↔谁、S2 谁↔谁、搬运值、通过验证的等式）。
4. **实施域分离修复**: 每条流的认证输入加入（会话 ID、双方身份、方向/角色位、全部瞬时值）；确认任何跨流搬运后验证必败。
   - 完成标准: 修复后字段表与修复前对照，每条流输入唯一。
5. **重跑攻击分析（改动纪律）**: 修复本身作为新改动重推步骤 3；协议少于三流时给出"结构性不可能"警告。
   - 完成标准: 新版本无搬运路径结论 + 交互轮数检查一行。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单会话内旧消息重放问题——时间维攻击归新鲜性决策树；本 skill 只管跨会话/跨流拼接。
- 底层原语（MAC/签名算法）本身的强度审计——本 skill 假定原语安全，专查协议层。
- 无并行能力的环境（物理上单会话串行的隔离系统）——攻击前提不成立，但需先证明并行确实不可能。

### 作者在书中警告的失败模式

- "MAC 安全 = 协议安全"的直觉——协议 9.1 反例（第 9 章 9.2）。
- 为改进而加随机数/加签名层却不重做分析——协议 9.7 被新自由度反噬（9.3.2）。
- 追求极简交互（两消息流识别方案）——结构性不可能，习题证明。

### 作者的盲点 / 时代局限

- 成书 2006 年：形式化验证工具（Tamarin/ProVerif 类）未在书中出现，本 skill 的手工推演在现代实践中可用工具复核；TLS Finished 消息式的 transcript hash 是域分离的现代样板，书中未覆盖。
- 群聊/多方会话的搬运变体（跨群转发）超出书中三案例形态。

### 容易混淆的邻近方法论

- 域分离 ≠ 加随机数：域分离是把"流身份"纳入认证输入的计算性区分；随机数若无区分符作用，只是新增自由度。
- 与 MITM 的区别：MITM 是攻击者插入双方之间转发（认证缺失）；搬运是攻击者利用合法方自身的计算（认证计算不区分流）——前者修认证绑定，后者修域分离。
