# 确定性公钥加密必败——必须随机化，且先审计明文空间

## R — 原文 (Reading)

> 因此，如果要使密文识别是计算上不可行的，必须要求加密过程是随机的。
>
> 为了确保"安全"通信，仅使用一个"安全"密码体制是不够的。
>
> — 原作者,原始方法论来源第5章 5.9.2、习题5.15（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

公钥加密有个不对称性毁掉一切确定性方案：加密密钥是公开的。这意味着敌手不需要私钥就能做"加密候选→比对密文"的枚举——身份证号 18 位数字约 10^17 且结构可枚举，逐候选加密比对即可全库恢复，RSA 模数多大都与此无关。判定流程是两问。第一问：加密是确定性的吗（同一明文总得同一密文）？是，则密文识别攻击成立——两条候选明文加密后比对就能判定哪条被加密，语义安全直接失败；ECB 是对称世界的同款病灶（相同明文块→相同密文块，模式全泄）。第二问：明文空间有多大？低熵/结构化明文（枚举类字段、短编码、逐字母加密的 26 值空间）让枚举比对从理论变实际。修复必须引入新鲜随机性（ElGamal 的随机 k、OAEP 的随机种子），使同一明文的多次密文不可区分——但要诚实计价：随机化破坏等值查询/确定性检索，数据库场景要么接受这个代价，要么换专用加密检索方案并重新声明泄漏面。核心纪律："体制安全"与"体制被安全地调用"是两道独立的闸门。

## A1 — 书中的应用 (Past Application)

### 案例 1: 密文识别问题（问题 5.3）
- **问题**: 确定性公钥加密在什么目标下失败？
- **方法论的使用**: 第 5 章 5.9.2 形式化"密文识别"：给定 y 与两条候选明文，敌手用公钥算 f(x1)、f(x2) 与 y 比对。
- **结论**: 无需私钥即答对——确定性加密在不可区分目标下结构性失败，必须随机化。
- **结果**: 确立"加密过程必须随机"为公钥加密的设计公理；ElGamal 的随机 k 是正面样本（同一明文 p−1 个可能密文）。

### 案例 2: 逐字母 RSA——体制未破、通信全破
- **问题**: Alice 把字母编码 0–25 逐字母 RSA 加密（n=18721），RSA 本身安全吗？
- **方法论的使用**: 习题 5.15：明文空间只有 26 值，Oscar 对每个密文字母穷举 26 个候选重新加密比对。
- **结论**: 密文串逐字母还原，而大模数 RSA 完全未被攻破——"协议失败"的经典形态：安全体制+危险编码=不安全系统。
- **结果**: 审计必须覆盖"体制如何被调用"（编码、分块、填充），而非只看体制本身。

### 案例 3: ECB——对称世界的确定性泄漏
- **问题**: 底层分组密码很强，直接逐块加密（ECB）行吗？
- **方法论的使用**: 第 3 章 3.7：相同明文分组产生相同密文分组，低熵明文空间下"本质上是没用的"（全 0/全 1 块的极端例）。
- **结论**: 组件安全≠系统安全；确定性在消息层泄漏结构模式。
- **结果**: 模式层必须随机化/链接（CBC 随机 IV、CTR 唯一计数器），并叠加认证。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 数据库网关对身份证号、手机号、邮箱列做 RSA/AES-ECB 加密，评估安全性。
2. 审计 API 返回的确定性加密字段（同一用户永远同一密文）能否被链接追踪或枚举。
3. 设计带检索需求的加密（等值查询）方案，纠结随机化与查询的矛盾。
4. 看到方案书声称"RSA-2048/AES-256 未被攻破，所以列加密安全"，需要反驳框架。

### 语言信号 (用户的话里出现这些就应激活)

- "RSA 直接加密手机号/身份证号，密钥 2048 位，安全吗"
- "deterministic encryption / 确定性加密能用于公钥吗"
- "ciphertext distinguish / 密文识别 / 同一明文同一密文"
- "ECB 存数据 / 逐块加密有什么问题 / ECB penguin"
- "加密后还要等值查询，怎么办"

### 与相邻 skill 的区分

- 与 `stinson-partial-leakage-amplification` 的区别: 那个讲密文上可计算谓词（Jacobi 符号类）如何被同态放大；本 skill 讲公钥可枚举比对的确定性失败——两者都属于"部分攻破"，机理不同（外延枚举 vs 内蕴谓词），两条泄漏路都要查。
- 与 `stinson-low-entropy-password-offline-audit` 的区别: 那个管低熵口令遇到可离线验证面（验证在哪）；本 skill 管确定性公钥加密的枚举比对——同一"低熵+可验证"语法在公钥加密上的实例。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确认加密形态**: 公钥还是对称、确定性还是随机化（同一明文加密两次，密文是否相同）、有无填充/nonce。
   - 完成标准: 形态三元组（公钥/对称，确定/随机，填充类型）写明。
   - 判停条件: 若已随机化且明文空间大，本 skill 不适用，转其他审计线。
2. **审计明文空间**: 字段结构（格式、校验位、取值域）、可枚举性、规模数量级。
   - 完成标准: 给出明文空间大小的数量级估计与"可枚举/不可枚举"判定及理由。
3. **推演枚举比对攻击**: 攻击者持公钥/可观察密文，逐候选加密比对的成本估算。
   - 完成标准: 一条具体攻击路径（候选集来源→加密→比对→命中），成本与空间规模挂钩。
4. **检查泄漏外延**: 相同明文相同密文带来的链接追踪、模式泄漏（ECB 的块级模式）、密文相等性可作等值查询被滥用。
   - 完成标准: 每条泄漏附现实利用场景一行。
5. **输出修复与代价**: 随机化填充（OAEP 类/随机 IV+认证模式）；诚实声明等值查询失效，检索需求转专用方案并重新评估泄漏面。
   - 完成标准: 修复建议附带功能代价清单；结论明确"RSA 未被分解与此无关"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 对称加密且带唯一 nonce/IV 的流模式（CTR 等）——确定性病灶不在其上（其风险另归 nonce 复用清单）。
- 已使用标准随机化填充（OAEP/RSA-KEM）的方案内部细节审计。
- 确定性加密被有意用于搜索且已接受泄漏声明的场景——那是风险接受决策，不是未知风险。

### 作者在书中警告的失败模式

- "为了确保'安全'通信，仅使用一个'安全'密码体制是不够的"（习题 5.15）——体制安全与调用安全分离。
- ECB 在低熵明文空间下"本质上是没用的"（第 3 章 3.7）。
- 逐字母/小块编码使明文空间坍缩到可穷举（习题 5.15 的 26 值空间）。

### 作者的盲点 / 时代局限

- 成书 2006 年：确定性公钥加密的可检索用途（后续的 deterministic authenticated encryption、ORE/OPQ 研究线）未出现；书中结论"必须随机化"针对保密语义，工程界后来发展的"确定性加密+泄漏声明"路线需另行评估，不能直接套书中否定。
- 未讨论填充方案的时序/错误通道（现代 padding oracle 事故形态）。

### 容易混淆的邻近方法论

- "确定性必败"≠"确定性对称加密必败"：对称场景敌手没有加密钥示，枚举比对需要明文可猜+密文可观察的前提组合，判定结构不同。
- 与哈希存储口令的区别：口令哈希是"故意可验证"的设计（配慢哈希），公钥确定性加密是"以为不可验证"的误设计——问题在意图与实际的落差。
