# 加密与认证的组合审计——模式、顺序、构造标准化检查表

## R — 原文 (Reading)

> ECB模式的一个明显缺点是在同一密钥下，加密相同的明文分组将会产生相同的密文分组。如果消息分组选自一个"低熵"的明文空间，那么这就是一个严重的弱点。
>
> 因为hk(x)和x都是已知的，对攻击者来说，即使K是保密的，计算hk(xllx）也是一件简单的事情。这显然是一个安全问题。
>
> — 原作者,原始方法论来源第3章 3.7、第4章 4.4（中译本 OCR，逐字保留，xllx 为 x‖x 之 OCR）

---

## I — 方法论骨架 (Interpretation)

加密管机密性、认证管完整性，两者都不能互相替代，而"怎么拼"本身就是攻击面。审计一条组合方案沿三个闸门过。闸门一：模式选型——ECB 把明文的重复模式原样搬进密文（低熵明文下等于没加密），CBC 需随机 IV 且加密本身不给完整性，CTR 需要全局唯一计数器，重复即密钥流复用；"CBC 的错误传播可借用作 MAC"只是历史便道，不等于加密提供了认证。闸门二：拼接顺序——先加密后签名使外层签名可被替换"认领"密文（归因错误），默认先签名后加密。闸门三：构造标准化——密钥只放前缀/IV 的 MAC 被长度扩展伪造（已知 (x, h_K(x))，把摘要当中间状态续算即得扩展消息的合法标签）；CBC-MAC 只对定长消息有清晰安全界（变长下 2^{t/2} 生日伪造）；HMAC 靠内外两层垫把密钥绑定首尾。总纲：加密+无密钥校验（CRC/校验和）不构成认证——CRC 线性且无密钥，攻击者篡改密文后重算即可；自定义拼接默认按可伪造处理，除非有专门证明；有证明的标准组合（CCM=GCM 前身、HMAC）优先。

## A1 — 书中的应用 (Past Application)

### 案例 1: 把密钥当 IV 的 MAC——长度扩展伪造
- **问题**: 手头有迭代 Hash，令 IV=密钥就有"带密钥的 MAC"了，行吗？
- **方法论的使用**: 第 4 章 4.4：攻击者已知 (x, h_K(x))，无需 K，以 h_K(x) 为链值继续迭代 compress(h_K(x)‖w)，即得 h_K(x‖x)。
- **结论**: 迭代结构内部状态一旦暴露，任意扩展可外推——(1,1) 假冒者，一次查询确定性伪造。
- **结果**: 修复是 HMAC 式内外垫（密钥同时绑定首尾）或域分离编码。

### 案例 2: CBC-MAC 变长消息的生日伪造
- **问题**: CBC-MAC 用分组密码构造，够不够强？
- **方法论的使用**: 第 4 章 4.4.2：请求约 1.17×2^{t/2} 个随机消息的 MAC 找前缀碰撞，再对任意尾块询一次即得新消息的有效 MAC。
- **结论**: (1/2, O(2^{t/2})) 假冒者——输出 t 位只给 t/2 位生日安全，且仅限定长消息。
- **结果**: 变长输入需长度域分离（CMAC 的动因）；MAC 位长按可接受伪造率反推。

### 案例 3: 先加密后签名的认领攻击
- **问题**: 为隐藏签名者身份，先加密再签外层，行吗？
- **方法论的使用**: 第 7 章 7.1：攻击者保留密文 z、丢弃原签名，换成自己的签名 y'=sig_Oscar(z)；Bob 解密验证通过后认为明文来自攻击者。
- **结论**: 顺序错误使签名语义被协议破坏——外层签名者可"认领"任意截获密文。
- **结果**: 默认先签名后加密；确需隐藏身份用指定验证者签名等专门原语。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. IoT/遥测方案评审："AES-CBC 加密 + 末尾附 CRC32 防篡改"类设计定结论。
2. 代码审查发现自定义 MAC：Hash(密钥‖消息)、Hash(消息‖密钥)、逐块异或后加密。
3. 设计消息保护协议：要不要同时签名和加密？顺序怎么排？各覆盖哪些字段？
4. 选型争论：CBC-MAC、HMAC、CCM/GCM 用哪个，密钥要不要分开。

### 语言信号 (用户的话里出现这些就应激活)

- "CRC/校验和能防篡改吗 / 加密了再加个 CRC 够不够"
- "length extension attack / 长度扩展 / Hash(key||msg) 当 MAC"
- "先签名还是先加密 / sign-then-encrypt vs encrypt-then-sign"
- "CBC-MAC 变长消息 / HMAC 为什么要两层 / CCM GCM 怎么选"
- "ECB 能用吗 / CTR 计数器重复"

### 与相邻 skill 的区分

- 与 `stinson-composition-not-amplification` 的区别: 加密+MAC 是分工（本 skill：两种功能的拼接与三闸门），AES+AES 是叠加（那个 skill：同类组件的增益核算）——问题不同。
- 与 `stinson-hash-property-usage-matching` 的区别: 那个管 Hash 三问题与用途匹配；本 skill 管加密与认证的组合结构——HMAC 的内外垫属于本 skill 的构造标准化闸门。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画出消息保护结构**: 加密层（算法+模式+IV/计数器来源）、认证层（构造+密钥位置）、签名层（如有）、各层覆盖的字段。
   - 完成标准: 一张"层×字段"覆盖表；无认证层的方案显式标"仅机密性"。
2. **过模式闸门**: ECB 出现即判缺陷；CBC 查 IV 随机性与覆盖范围；CTR/OFB 查计数器/IV 唯一性保障。
   - 完成标准: 每模式一条判定（通过/缺陷+理由）。
   - 判停条件: 若发现无密钥完整性机制（CRC/校验和单独承担防篡改），直接输出"不构成认证，可伪造"结论跳到步骤 5。
3. **过顺序闸门**: 签名与加密并存时核对顺序（先签后加密）与签名覆盖内容（明文还是密文）。
   - 完成标准: 顺序判定+认领攻击可能性分析一行。
4. **过构造标准化闸门**: MAC 是否标准构造（HMAC/CMAC）；自定义构造检查长度扩展面、变长输入、密钥绑定位置。
   - 完成标准: 每个认证构造标注"标准/自定义（附伪造推演）"。
5. **输出结论与修复**: 标准组合（AEAD 类）或 HMAC+加密的分工方案；认证覆盖 IV、序号、身份、上下文的字段清单。
   - 完成标准: 结论含三闸门逐项判定 + 修复后字段覆盖表（IV/上下文必须进入认证输入）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一功能的纯机密性或纯完整性需求（只加密不传认证、只校验下载完整性）——组合检查表无对象。
- 密钥管理问题（密钥怎么生成、存储、轮换）——本 skill 假定密钥安全，只审组合结构。
- 传输层标准协议（TLS 1.3）内部实现——它们已通过组合证明与全球分析，本表用于自研方案。

### 作者在书中警告的失败模式

- "加密相同的明文分组将会产生相同的密文分组"——ECB 在低熵明文空间"本质上是没用的"（第 3 章 3.7）。
- 密钥只作 IV/前缀的 MAC：即使 K 保密，h_K(x‖x) 照算——长度扩展是迭代结构固有（第 4 章 4.4）。
- CBC 错误传播可借作 MAC，但"加密本身不提供完整性"；Kerberos 评论明确职责分离：加密管机密性、MAC 管认证（第 10 章 10.5.3）。
- 填充/编码层的单射约束被破坏直接制造碰撞（第 4 章 4.3）。

### 作者的盲点 / 时代局限

- 成书 2006 年：AEAD（GCM 2007 标准化、ChaCha20-Poly1305）未成主线，书中"标准组合"止于 CCM 与 HMAC——现代评审应把 GCM/Poly1305 补入闸门三的推荐清单，但"自定义拼接默认可伪造"的总纲不变。
- padding oracle 类组合攻击（Vaudenay 攻击，2002）未在书中展开，本表使用时应补查"解密失败反馈通道"。

### 容易混淆的邻近方法论

- "完整性"≠"认证性"：无密钥 Hash/CRC 只能发现意外损坏，不能对抗篡改者——分野在第 4 章 4.1 的选型判断。
- 与跨会话域分离的区别：本 skill 管单条消息内部层与层的组合；跨会话搬运管不同会话间的值复用——攻击者可以同时利用两者。
