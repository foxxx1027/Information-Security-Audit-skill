# 可行性核算——先证信息论上界，再构造顶到上界

## R — 原文 (Reading)

> 因为p=1是最优的情况，我们把这样的一个方案称为理想的秘密共享方案。Shamir门限方案是一个理想方案。
>
> ……如果我们用定理13.13中l=2的情况组合它们，则可以得到一个信息率是P=2/3的方案，这是一个最优方案。
>
> — 原作者,原始方法论来源第13章 13.1、13.3.3（中译本 OCR，逐字保留：p=1 为 ρ=1、P=2/3 为 ρ=2/3 之 OCR）

---

## I — 方法论骨架 (Interpretation)

工程直觉遇到需求先找方案，数学纪律遇到需求先证天花板。流程是两步闭环：第一步，证上界——用信息论或计数论证证明"任何方案都不可能好于 X"（无论多少聪明才智）；第二步，构造达到 X 的方案——上界与构造吻合即最优，差多少就差多少、没得谈。秘密共享的教科书演示：信息率 ρ（秘密长度/份额长度）上界为 1，Shamir 方案恰好 ρ=1，所以"份额比秘密短"的需求不是难做，是数学禁止——出路只有改需求或接受降级（Ramp 型部分泄漏，且剩余熵必须显式声明）。更细的普查显示上界可逐结构变化：18 种访问结构中 10 个有理想方案，#5 等结构被推论证明 ρ≤2/3，分解构造恰好做到 2/3——"上界证明+构造"逐对象闭合。这个思维的价值在否定性结论：它能把"团队做不出来"与"宇宙不允许"区分开，让需求谈判发生在正确的层面——先算天花板，再设计；不可能性判定先于方案选型。

## A1 — 书中的应用 (Past Application)

### 案例 1: 信息率 ρ≤1 与 Shamir 的理想性
- **问题**: 能不能设计份额比秘密短的完美秘密共享？
- **方法论的使用**: 第 13 章 13.1-13.2：信息论论证 ρ≤1（完美性要求份额熵不低于秘密熵）；Shamir 门限 ρ=1 达界。
- **结论**: "份额减半"类需求不可满足——上界判定优先于一切设计努力。
- **结果**: 需求可行性问题转化为上界核对问题；理想方案（ρ=1）概念随之确立。

### 案例 2: 表 13.1 普查——18 种结构的逐格上界
- **问题**: 一般访问结构都能做到理想吗？
- **方法论的使用**: 第 13 章 13.3 对 2-4 参与者的 18 种单调访问结构逐一套用构造与推论：10 个理想；#5/#8/#12/#13 被推论 13.10 证明 ρ≤2/3，无理想方案。
- **结论**: 上界依结构而异；"通用构造一刀切"不存在——可行性逐对象核算。
- **结果**: 分解构造把 #5 做到 2/3 与上界吻合，"上界证明+构造"闭环完成（例 13.11/13.12 显式分发）。

### 案例 3: Ramp 方案——牺牲完美性换信息率的量化
- **问题**: 天花板挡住了需求，有没有合法的绕行？
- **方法论的使用**: 第 14 章 14.2：Ramp 方案把多个密钥打包进多项式，份额短于密钥（ρ 可升），代价是低于门限时部分泄漏——例 14.4 中一份共享把候选从 17² 压到 17。
- **结论**: 突破上界的唯一路径是放松前提（完美→部分泄漏），且剩余熵必须显式声明；非完美方案的泄漏量是设计参数不是缺陷遮蔽。
- **结果**: "改需求或接受量化降级"成为天花板下的两条规范出路；同时它是基线比较思维的实例（平凡 KPS 的 n² 存储被 Blom 的 k+1 元素打破）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 需求评审提出"份额/密文/标签比原数据短""既要完美保密又要短密钥"类组合，先判可满足性。
2. 自研方案前的尽职调查：这个性能目标在信息论上允许吗，还是注定撞墙。
3. 供应商宣称"突破信息论限制"（如超短份额秘密共享），需要快速证伪框架。
4. 权衡设计：决定放松哪个前提（完美性/确定性/无交互）来换取想要的资源指标。

### 语言信号 (用户的话里出现这些就应激活)

- "份额能不能比秘密短 / 信息率 information rate"
- "impossibility / 不可能性 / 这需求数学上可行吗"
- "理论上限 / 天花板 / 上界在哪儿"
- "既要……又要……，能不能同时满足"

### 与相邻 skill 的区分

- 与 `stinson-security-notion-calibration` 的区别: 那个选"用哪把尺子"；本 skill 用选定的尺子（尤其信息论档）算资源天花板——选尺在前，算界在后。
- 与 `stinson-collusion-threshold-verification` 的区别: 那个验收已有门限方案的双验证；本 skill 在方案不存在之前判定"该方案类是否存在"——设计前的可行性门与设计后的验收门先后接力。
- 与 `stinson-provable-security-usability-cost` 的区别: 那个算"达到安全要付多少可用性代价"；本 skill 算"任何方案最多能做到多少"——一个是代价核算，一个是不可能界。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把需求写成不等式**: 资源指标（份额长/密文长/存储/通信）× 安全指标（零信息/不可区分/完美性）的形式化表述。
   - 完成标准: 需求的数学表述一句；隐含前提（完美性、无泄漏、确定性）显式列出。
2. **查/证信息论上界**: 对照书内或标准结果（|K|≥|C|≥|P|、ρ≤1、签名排除无条件档等）判定需求是否与上界冲突。
   - 完成标准: 上界陈述+出处；冲突/不冲突判定。
   - 判停条件: 若需求违反上界，直接输出"不可满足"结论跳到步骤 4 出路分析。
3. **核对已知构造的最优性**: 现有最好方案离上界多远（达界=最优；差距=公开问题或结构限制）。
   - 完成标准: "最好构造 vs 上界"对照一行；未达界时标注是已知差距还是可改进。
4. **给出两条出路**: 改需求（资源指标对齐上界）或放松前提（明确声明放松了什么、量化剩余泄漏/残余风险）。
   - 完成标准: 出路各附一句量价（如 Ramp 型：份额减多少、泄漏多少比特）。
5. **输出可行性判定书**: 可满足（附上界+达界构造）/不可满足（附上界证明要点）/部分满足（附差距）。
   - 完成标准: 判定三态之一 + 上界依据，可直接并入需求文档。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 产品功能取舍（要不要做这个 feature）——无数学约束的决策不属于可行性核算。
- 性能优化空间（还能快多少）——无信息论下界的工程问题， benchmark 驱动而非定理驱动。
- 计算安全档的"实际不可行"评估（2^80 够不够）——那是参数预算问题，不是不可能性问题。

### 作者在书中警告的失败模式

- 直接找方案不查上界——工程努力浪费在数学禁止的目标上（ρ≤1 之下追求短份额）。
- 非完美方案的泄漏遮蔽——放松完美性必须显式声明剩余熵（Ramp 的 17²→17 是规范示范）。
- 通用构造当万能药——18 结构中 8 个无理想方案，可行性逐对象核算。

### 作者的盲点 / 时代局限

- 成书 2006 年：书中的上界-构造闭环集中在秘密共享；现代方案的可行性核算（如函数加密、FHE 的开销下界）需另引文献，但"先证上界"的方法论通用。
- 计复杂度下界（oracle 下界之外的）在密码学中普遍稀缺，本 skill 的上界多来自信息论——对计算性目标（"不可伪造"类）常无类似硬上界可用，需如实告知。

### 容易混淆的邻近方法论

- 不可能性上界 ≠ "目前做不到"：上界是数学禁止（改需求），现状是工程差距（可投入攻坚）——混谈会导致错误的项目决策。
- 与基线比较的区别：打破平凡基线（n²→k+1）是构造进步；顶到信息论上界是终点——前者可继续优化，后者不能。
