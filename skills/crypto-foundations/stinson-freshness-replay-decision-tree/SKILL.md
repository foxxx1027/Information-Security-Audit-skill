# 新鲜性与重放防护决策树——时间戳 / 随机挑战 / 一次性上下文

## R — 原文 (Reading)

> 因此，签名文件本身应该包含诸如日期在内的信息以防止该签名被重复使用。
>
> 需要说明的是每次Alice向Bob证实自己的身份时，Bob都应该选择一个新的随机挑战r。如果Bob总是使用同样的挑战r，那么Olga就可以用上述方法来假冒Alice。
>
> — 原作者,原始方法论来源第7章 7.1、第9章 9.4.1（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

数字签名与 MAC 有个共同盲区：它们认证"内容"，不认证"这是第一次"。副本与原件在数学上完全相同，截获一条合法的扣款指令就能无限重放。防护只有三条路线，各有隐性成本，构成决策树。路线一：时间戳——把日期/有效期纳入被签内容，验证方检查窗口；它依赖全网时钟同步，窗口大小在"误拒合法消息"与"窗口内重放"之间取衡，Kerberos 的时间戳+有效期 L 是样板。路线二：随机挑战——验证方每次发新鲜 nonce，应答必须覆盖它；无同步依赖但多一轮交互，且挑战必须不可预测（固定挑战=冒充者预选应答反推承诺）。路线三：一次性上下文——应用层幂等键/序号，状态由服务端维护。两条覆盖性纪律贯穿所有路线：其一，新鲜性字段必须进入被 MAC/签名 覆盖的输入——放在旁边不签等于没放；其二，"挑战响应验证通过"不等于"密钥新鲜"——Denning-Sacco 教训：旧票据+已知旧密钥的组合能让验证全过而密钥早已泄露，接受密钥前要确认它未被旧会话泄露过。

## A1 — 书中的应用 (Past Application)

### 案例 1: 签名副本即原件
- **问题**: 数字签名在法律文书上与传统签名有何关键差异？
- **方法论的使用**: 第 7 章 7.1：签名可无限复制，不含日期/序号的被签指令（如"取 100 美元"）每次验签都通过。
- **结论**: 签名本身无新鲜性；新鲜性信息必须写入被签消息体。
- **结果**: 签名文件自带日期/序号成为设计规范；重放防护成为签名应用层的必配。

### 案例 2: 固定挑战的冒充——Schnorr 的教训
- **问题**: 挑战由验证方出，出得省一点（固定值）行吗？
- **方法论的使用**: 第 9 章 9.4.1：Olga 先选定应答 s 与目标挑战 r，反算承诺值 t 使验证等式成立；会话开始直接呈交 (t,s)。
- **结论**: 挑战必须每次新生成、不可预测、足够长；固定挑战使冒充 100% 成功。
- **结果**: "挑战新鲜性"成为挑战-应答协议的独立检查项（与挑战绑定并列）。

### 案例 3: Denning-Sacco——两条不变量同破
- **问题**: 时间戳票据为什么挡不住旧密钥重放？
- **方法论的使用**: 第 10 章 10.5.2：Oscar 曾获知会话 S 的密钥 K，重放旧票据使 Bob 在新会话 S' 使用 K——"对端知道 K"与"只有对端知道 K"两条不变量同时被违反。
- **结论**: 验证挑战响应正确≠验证密钥新鲜；接受密钥前必须确认其从未泄露。
- **结果**: Kerberos 用时间戳+有效期 L 压缩窗口但引入时钟同步依赖——决策树的三路线取舍被显式呈现。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 支付回调/开放 API 的 HMAC 不含时间戳，评估重放风险并选修复路线。
2. 设计认证协议：用时间戳还是 nonce 挑战？窗口设多大？时钟不同步怎么办？
3. 令牌/票据体系设计：有效期、刷新、吊销与重放窗口的联动。
4. 事故复盘：重放攻击发生了，定位是新鲜性字段缺失还是未进签名输入。

### 语言信号 (用户的话里出现这些就应激活)

- "replay attack / 重放攻击 / 请求被原样重发"
- "timestamp vs nonce / 时间戳窗口多大合适"
- "freshness / 新鲜性 / 这个消息是不是旧的"
- "幂等键 idempotency key / 一次性令牌"
- "票据过期了还能用吗 / Denning-Sacco"

### 与相邻 skill 的区分

- 与 `stinson-cross-session-reflection-defense` 的区别: 本 skill 管时间维（消息是否新鲜）；那个管空间维（消息是否属于本会话/本流）——时间戳挡不住跨会话搬运，域分离挡不住旧消息重放，两棵树都要走。
- 与 `stinson-authenticated-key-establishment` 的区别: 那个管密钥建立中的实时插入与密钥绑定；本 skill 管旧消息重放——Denning-Sacco 型"旧密钥+重放"组合需两 skill 配合定位。
- 与 `stinson-nonce-reuse-failure-checklist` 的区别: 那个管 nonce 作为一次性值的生成端事故（复用即代数崩溃）；本 skill 管 nonce 作为挑战的消费端语义（新鲜性来源与覆盖范围）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **清点全部可重放对象**: 指令、票据、令牌、认证响应、会话密钥分发消息，逐个列出其新鲜性来源。
   - 完成标准: 对象清单 + 每项标注"有/无新鲜性字段"。
2. **验证覆盖纪律**: 新鲜性字段是否进入 MAC/签名输入（而非明文附带）；验证方是否真的校验它。
   - 完成标准: 每对象一行"字段×是否被签×是否被验"。
   - 判停条件: 若存在无新鲜性字段的资金/授权类对象，直接输出"无限重放"结论跳到步骤 4。
3. **推演重放路径**: 截获→原样重发→哪一步验证通过；配合已知旧密钥场景推 Denning-Sacco 型组合。
   - 完成标准: 至少一条完整重放链路 + 密钥新鲜性盲区标注。
4. **走决策树选路线**: 时间戳（时钟同步依赖、窗口大小权衡）/ 服务器 nonce 挑战（多一轮、无同步依赖）/ 幂等键（应用层状态）；按场景约束（能否改协议交互、时钟可信度、状态存储成本）选定。
   - 完成标准: 选型结论附两条被否路线的否决理由。
5. **补密钥新鲜性检查**: 接受会话密钥前的"未泄露确认"机制（挑战前置、密钥确认回合），与消息新鲜性分开标注。
   - 完成标准: 输出含两条独立结论：消息重放防护方案 + 密钥新鲜性方案。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 跨会话消息搬运（并行会话拼接）——空间维问题归域分离；时间戳救不了它。
- 证书/信任基础设施的过期与吊销——对象是证书链不是协议消息。
- 离线验证场景（本地验签无服务端状态）——重放只能在应用层由业务幂等吸收，协议层无解，应如实告知局限。

### 作者在书中警告的失败模式

- 签名副本=原件：不含时效信息的被签指令可无限重放（第 7 章 7.1）。
- 挑战固定/可预测：冒充者预选应答反推承诺（第 9 章 9.4.1）。
- "验证通过=密钥新鲜"的混淆：Denning-Sacco 旧票据+已知密钥两条不变量同破（第 10 章 10.5.2）。
- 时间戳的隐性依赖：Kerberos 有效期 L 依赖全网时钟同步（10.5.3）。

### 作者的盲点 / 时代局限

- 成书 2006 年：消息层重放防护在现代协议中已并入 AEAD 序号（TLS 1.3 的 record number）等机制，书中三路线之外可补充"底层序列号"路线；幂等键的分布式实现（去重表规模与 TTL）未展开。
- 时间戳信任源（可信时间戳服务 RFC 3161）只在签名寿命处点到。

### 容易混淆的邻近方法论

- 新鲜性 ≠ 域分离：前者回答"何时"，后者回答"何流"；两者都是"认证输入覆盖"纪律的实例，但检查对象不同。
- 时间戳 ≠ 因果序：时间戳只证明"在窗口内"，不证明消息先后因果；把分布式系统的因果一致性需求误交给密码时间戳会得出错误方案。
