# Hash 安全三问题与性质—用途匹配检查表

## R — 原文 (Reading)

> 如果一个Hash函数被认为是安全的，就应该出现对这三个问题都是难解的情况。
>
> 这是一种利用选择消息攻击的存在性伪造；如果h是碰撞稳固的，这种攻击就可以避免。
>
> — 原作者,原始方法论来源第4章 4.2、第7章 7.2（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

"这个哈希安全吗"是错误的问题；正确的问题是"这个用途需要挡住哪条攻击路径"。哈希安全拆成三个难度不同的问题：原像（给摘要求输入）、第二原像（给一条输入找另一条同摘要）、碰撞（任找一对）。三者的强度有严格排序——碰撞最难守（攻击者两头自由选择，生日界只需 2^{n/2} 次尝试，比原像的 2^n 少一个平方根量级），且碰撞稳固蕴含第二原像稳固（归约成立），反之不然。用途匹配才是关键动作：文件去重——对手可以构造两个文件，需要抗碰撞；口令存储——主敌是离线字典，需要抗原像外加慢哈希/盐（快哈希的抗原像挡不住批量猜测）；签名前处理——"先造碰撞再请签其一"的路径需要抗碰撞，且三类伪造（唯密钥/已知消息/选择消息）与三条性质一一对应，错配则"用了 Hash"也无效。复用同一哈希跨用途时还要查构造差异（长度扩展对口令型 MAC 的影响）。历史教训：最强性质最先倒（SHA-0/MD5/SHA-1 碰撞），依赖它的复合构造连锁失效。

## A1 — 书中的应用 (Past Application)

### 案例 1: 三问题定义与排序的确立
- **问题**: "抗碰撞"作为笼统说法够不够用？
- **方法论的使用**: 第 4 章 4.2 定义问题 4.1-4.3，4.2.3 用归约确立：碰撞稳固⇒第二原像稳固（无条件），反向需强条件。
- **结论**: 三问题强度有序，声明必须指名哪一条；"三者皆难才安全"是总检查表。
- **结果**: 后续一切哈希评审（MAC 构造、Merkle-Damgård、签名）都按三问题分别核对。

### 案例 2: 签名伪造路径与 Hash 性质一一对应
- **问题**: "先 Hash 再签"里的 Hash 要什么性质？
- **方法论的使用**: 第 7 章 7.2 把三类攻击对应三条性质：唯密钥伪造者先对随机摘要签名再求原像（需原像稳固）；已知消息攻击找第二原像（需第二原像稳固）；选择消息攻击先造碰撞再请签其一（需碰撞稳固）。
- **结论**: 性质与攻击路径一一对应——不声明威胁档位就无法选性质，笼统"抗碰撞"错配即失效。
- **结果**: Hash 选型进入签名方案的证明链，随 Hash 进展联动（SHA-1 碰撞逼近即触发签名方案迁移）。

### 案例 3: MD5/SHA-0/SHA-1 碰撞史与连锁失效
- **问题**: 理论位数没到，实际为什么倒？
- **方法论的使用**: 第 4 章 4.6 记录：2004 SHA-0/MD5 碰撞公开（Joux 给出 SHA-0 真实碰撞对，表 4.1），2005 SHA-1 估计低于 2^69 次操作。
- **结论**: 最强性质最先倒；依赖抗碰撞的复合构造（签名、证书、MAC）连锁失效。
- **结果**: "跟踪实际攻击进展而非仅理论位数"成为运维纪律；迁移到 SHA-2/SHA-3。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审系统里同一哈希（如 SHA-256）用于文件去重、口令存储、证书签名三处的要求差异。
2. 选型或迁移讨论：MD5/SHA-1 还能用在哪些非安全场景，哪里必须换。
3. 设计数据完整性校验（下载校验、去重键、内容寻址存储）时确定需要哪条性质。
4. 审计发现口令用快哈希裸存（SHA-256(password)），需要论证风险与修复。

### 语言信号 (用户的话里出现这些就应激活)

- "collision resistance / 抗碰撞是什么，去重需要吗"
- "password hashing / 口令存储用 SHA-256 够吗 / 要不要加盐加慢"
- "second preimage / 第二原像什么时候是威胁"
- "MD5 还能用吗 / SHA-1 什么时候必须迁"

### 与相邻 skill 的区分

- 与 `stinson-encrypt-authenticate-composition` 的区别: 那个审加密+认证的组合结构与 HMAC 构造；本 skill 审哈希性质与用途的匹配——HMAC 之外的所有裸哈希用途归本表。
- 与 `stinson-birthday-bound-parameter-sizing` 的区别: 那个算"n 位摘要只给 n/2 位碰撞安全"的参数账；本 skill 决定"该用途是否需要碰撞安全、需要哪条性质"——先定性（本 skill）后定量（那个 skill）。
- 与 `stinson-low-entropy-password-offline-audit` 的区别: 那个管低熵口令的离线验证面总框架；本 skill 只覆盖其中"哈希用途匹配"一角（快哈希裸存的判定）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **清点哈希的全部用途**（去重键、口令存储、签名前处理、完整性校验、密钥派生……），逐个列出。
   - 完成标准: 用途清单完整，每处标注哈希算法与构造方式（裸哈希/带盐/HMAC）。
2. **对每个用途推演攻击路径**: 对手能选两个输入吗（→碰撞）？能给定输入找替身吗（→第二原像）？能从摘要倒推吗（→原像）？
   - 完成标准: 每用途标注"所需性质=…"并附一行攻击者模型。
   - 判停条件: 若发现口令类用途使用快哈希裸存，立即输出"离线字典全速运行"结论并跳到步骤 4 修复。
3. **核对性质与构造是否到位**: 所需性质 vs 算法现状（SHA-1 碰撞已破类）；口令用途核对盐与慢哈希；跨用途复用核对构造差异（长度扩展面）。
   - 完成标准: 逐用途输出"匹配/错配/待迁移"三态判定。
4. **输出匹配表与迁移建议**: 用途×所需性质×当前状态×动作；复合构造（签名、证书）标注对哈希进展的联动依赖。
   - 完成标准: 表中每行有明确动作；结论包含"'用了 SHA-256'不构成任何一处的充分条件"式判定句。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 非安全用途的哈希（负载均衡分桶、哈希表）——无对抗者，三问题无关。
- HMAC 等带密钥构造的安全性论证——归组合审计；本表只管裸哈希用途匹配。
- 哈希算法内部设计（压缩函数结构、 Sponge 构造）分析。

### 作者在书中警告的失败模式

- 笼统"要抗碰撞"而不与伪造目标对应——第 7 章 7.2 的三对三映射显示错配即无效。
- 以"摘要足够长/业界广泛使用"认定抗碰撞——MD4→MD5→SHA-0→SHA-1 全线倒下（第 4 章 4.6）。
- 口令场景误用快哈希：抗原像的强度挡不住字典枚举（结合第 11 章口令攻击的量化）。

### 作者的盲点 / 时代局限

- 成书 2006 年：SHA-3/Keccak 竞赛结果未出；长度扩展攻击在书中作为 MAC 构造缺陷出现，未覆盖对裸哈希用途（如早期 Bitcoin 交易延展性类）的现代影响。
- 慢哈希（bcrypt/scrypt/Argon2 系）在书中只有"密钥拉伸"概念级提及，口令存储的现代实践需外部补充。

### 容易混淆的邻近方法论

- "哈希安全三问题"≠"加密强度"：哈希无密钥，安全是"难找到碰撞/原像"的组合性质，与密钥长度无关。
- 与归约排序的区别：三问题间"碰撞⇒第二原像"的蕴含是归约比较法的一个实例；本 skill 消费该排序做用途匹配，不重复证明。
