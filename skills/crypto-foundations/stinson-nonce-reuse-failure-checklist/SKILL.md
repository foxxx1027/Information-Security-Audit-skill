# 一次性值复用即失陷——复用禁忌清单

## R — 原文 (Reading)

> 例如，"一次一密"对已知明文攻击是很脆弱的，因为K可以通过异或比特串x和e(x)得到。因此，新生成的密钥需要为将要发送的明文在安全的通道上传输。这就带来了一个严峻的密钥管理问题
>
> 系统的另外一个误用是对两个不同的消息签名时使用相同的k值。这将使Oscar计算α变得容易，因而攻破系统。
>
> — 原作者,原始方法论来源第2章 2.3、第7章 7.3（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

密码系统里有一类值，名字各异（密钥流、IV、计数器、nonce、随机数 k、种子、一次性签名密钥），共同点是：复用不是"降低安全性"，而是触发一个代数等式让系统当场归零。机理只有三种，记住它们就能对任何"这个值重复了要紧吗"作出判断。机理一：异或抵消——同一密钥流加密两条消息，密文异或=明文异或，语言统计可直接分离两条明文；已知一段明文则直接还原另一段。机理二：联立方程消元——ElGamal/DSA 类签名用同一 k 签两条消息，两个签名方程相减消去未知私钥外的一切，私钥被解出（k 可预测同罪）。机理三：承诺集合并集——一次性签名每签一条消息揭示一半私钥，签两条即可逐位拼出第三条的签名。审计的真正入口不在"值"层而在"生成源"层：熵源回退、重启、VM 快照、并发竞争是最常见的复用入口，而跨用途共享生成器（TLS 与固件签名共用播种）会把两类崩溃串成供应链级事故。

## A1 — 书中的应用 (Past Application)

### 案例 1: 一次一密密钥复用
- **问题**: 理论完美的体制，工程上第一个要防什么？
- **方法论的使用**: 第 2 章 2.3 演示 K=x⊕e(x)：已知明文一对即得该位置密钥流；同一密钥两条消息时 y1⊕y2=x1⊕x2。
- **结论**: 复用使完美保密瞬间归零，所有共用该密钥流的消息一并泄露。
- **结果**: "每钥一次"从使用建议升格为硬前提；OFB/CTR 的 IV 重复=同一事故（密钥流重复）。

### 案例 2: ElGamal 签名重用 k
- **问题**: 签名里的随机数被当"内部实现细节"，复用会怎样？
- **方法论的使用**: 第 7 章 7.3：同 k 签 x1、x2 则 γ 相同，两式相减得 k=(x1−x2)(δ1−δ2)^{-1}，回代解出私钥 a。
- **结论**: 随机数 k 的一次性是 ElGamal/DSA/ECDSA 安全的命门，与算法强度无关。
- **结果**: 工程对策为 RFC 6979 式确定性 nonce 或强随机源；泄露即按私钥泄露处置。

### 案例 3: Lamport 一次性签名被用两次
- **问题**: "单向函数保证不可伪造"是否覆盖多次使用？
- **方法论的使用**: 第 7 章 7.5.1：签两条消息后，攻击者从两串揭示值中逐位挑选拼出第三条消息的完整签名，无需求逆。
- **结论**: 安全证明的前提（一钥一签）不可省略；复用使"单向性"论证整体失效。
- **结果**: 一次性签名靠 Merkle 树复用公钥而非私钥——前提条件成为设计约束。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审计嵌入式设备/物联网的随机数方案：每次启动用时间+设备 ID 播种 CSPRNG，TLS 与固件签名共用。
2. 事故响应：日志或密文中发现两条消息 IV 相同/nonce 碰撞/签名 γ 值相同，需要判定泄露范围。
3. 设计评审：nonce 应该随机还是计数器？重启后状态怎么持久化？多用途要不要域分离？
4. 代码审计：检查随机数生成调用点、fork/快照/并发场景下状态是否可能回退重复。

### 语言信号 (用户的话里出现这些就应激活)

- "nonce 重复/IV reuse/计数器回退了会怎样"
- "two-time pad / 密钥流重复 / keystream reuse"
- "签名的随机数 k / nonce 复用泄露私钥 / PlayStation ECDSA 事故"
- "设备重启后随机数会不会一样 / VM 快照恢复后熵怎么样"
- "RFC 6979 / deterministic nonce 该不该用"

### 与相邻 skill 的区分

- 与 `stinson-perfect-secrecy-formalization` 的区别: 那个从"完美保密的代价"审计一次性条件（分布论证）；本 skill 是跨对象的复用事故清单（含签名 k、一次性签名、种子），判据是代数攻击机理。
- 与 `stinson-pseudorandomness-criterion` 的区别: 那个管"输出是否可预测"的判据；本 skill 管"同一个值被用了两次"的结构性灾难——即使生成器完美，复用照样失陷。
- 与 `stinson-freshness-replay-decision-tree` 的区别: 本 skill 管 nonce 作为一次性值的生成端事故（复用即代数崩溃）；那个 skill 管 nonce 作为挑战的消费端语义（新鲜性来源与覆盖范围）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **清点所有"一次性值"使用点**: IV、计数器、nonce、签名随机数、会话密钥流、PRNG 种子、一次性密钥，逐个列表。
   - 完成标准: 每个使用点标注（值的类型、生成源、消费者、名义一次性约束）。
2. **对每个值归类崩溃机理**: 异或抵消型（密钥流/IV）、方程消元型（签名 k）、集合并集型（一次性签名）、状态相关型（种子）。
   - 完成标准: 每行标注机理类别与复用后果（明文异或暴露/私钥解出/新签名可拼出/全流可预测）。
3. **审计生成源的复用入口**: 重启、fork、VM 快照、时钟回拨、并发竞争、跨用途共享生成器。
   - 完成标准: 每个入口标注存在/排除；跨用途共享单独标红（串联两类崩溃）。
4. **核对防护措施**: 计数器持久化（NVRAM）、域分离派生、确定性 nonce（RFC 6979 思路）、复用检测告警。
   - 完成标准: 每条防护标注已部署/缺失；缺失项给出引入的崩溃机理。
   - 判停条件: 若发现签名类 k 已确定复用（如相同 γ），跳到步骤 5 直接输出"私钥按已泄露处置"。
5. **输出结论与修复优先级**: 按崩溃机理的爆炸半径排序（私钥泄露 > 明文暴露 > 单条会话失陷）。
   - 完成标准: 每个发现附机理一行解释（为什么不是概率性削弱而是代数崩溃）+ 修复动作。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 长期密钥的轮换周期、密钥保管制度——那是生命周期管理问题，复用清单管不着。
- 一次性值生成质量（熵够不够、可不可预测）本身——那归伪随机性判据管；本 skill 只管"同一个值用两次"。
- 非密码学场景的"重复"问题（缓存重复请求、幂等键）——幂等键恰恰是故意复用的业务机制，别套本清单。

### 作者在书中警告的失败模式

- 一次一密密钥复用：K=x⊕e(x) 与 y1⊕y2=x1⊕x2（第 2 章 2.3）。
- ElGamal 同 k 签两条消息联立解私钥；k 泄露/可预测同罪（第 7 章 7.3）。
- 收缩生成器两个 LFSR 同参数同种子——"双路"结构被相关性完全抵消，熵清零（第 8 章习题 8.3）。

### 作者的盲点 / 时代局限

- 成书 2006 年：书中的复用事故都是数学机理，未覆盖现代工程入口（VM 快照、容器 fork、移动端低功耗熵饥饿、云并发竞态）；清单使用时应把这些入口补进步骤 3。
- RFC 6979（2009 年定稿）在书中只能是"思路"级提及，确定性 nonce 的实现细节需另查现代文献。

### 容易混淆的邻近方法论

- "复用即崩溃"≠"重复率高的统计风险"：前者一条代数等式即失陷，与概率无关；不要用生日界思维淡化 IV 撞撞碰碰的严重性——two-time pad 是确定性利用。
- 与生日界参数选型的区分：生日碰撞是"随机撞上"、按 √N 标度做参数预算；nonce 复用是"生成源缺陷导致的确定性重复"，两者修复手段不同（加长 vs 去重复根源）。
