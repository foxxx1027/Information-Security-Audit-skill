# 可证明安全方案的可用性代价——扩张、歧义、吞吐

## R — 原文 (Reading)

> Bob并不能区别这四个可能的明文中哪一个是"正确"的，除非明文中包含足够的穴余信息来排除四个可能值中的三个。
>
> 为了避免分解n，应该取n为1024比特长的整数。此时，密文长度是明文长度的1000倍。
>
> 然而，该方案由于加密过程中数据膨胀太大而不是一个实用的系统。
>
> — 原作者,原始方法论来源第5章 5.8、第8章 8.4、第12章 12.5.3（中译本 OCR，逐字保留）

---

## I — 方法论骨架 (Interpretation)

"有证明"的方案经常用不起，因为安全性证明的代价落在三个可计价的科目上。科目一，消息扩张：逐比特概率加密（GM）每比特明文要一个千比特级密文——约 1000 倍扩张；Cocks IBE 的数据膨胀被作者直接判为"不是一个实用的系统"。科目二，解密歧义：Rabin 的归约"完美"（攻破⇔分解），但 x² 非单射使接收者面对四个候选明文无法区分——可用性的成本从密码层转嫁给编码冗余层，证明没有消失这笔账，只是换了科目。科目三，吞吐：BBS 每输出一比特做一次模 n 平方——证明式安全的速度税。审计动作是算三科目的账并对照载荷画像：高价值小载荷（根密钥分发）可容忍扩张与低吞吐，买可证安全划算；大流量（视频流）一点都不可容忍。由此得出结构性结论：混合架构（可证明的 KEM 封装一把对称密钥+对称方案承载数据）不是风格偏好，是代价结构决定的必然形态——书中 GM→BG→混合加密的演化与 ECIES 把扩张从 4 压到 2 是同一条优化轨迹。评审任何"理论安全"方案，先算扩张与吞吐账。

## A1 — 书中的应用 (Past Application)

### 案例 1: Rabin 四义解密——归约完美的方案不可直接用
- **问题**: Rabin 是全书唯一完整可证明安全的体制，为何没有普及？
- **方法论的使用**: 第 5 章 5.8：例 5.18（n=77、y=23）解密得 ±10、±32 四个根；Bob 无法区分，除非明文自带足够冗余排除三个。
- **结论**: 可证明安全不替代端到端可用性设计——歧义成本转嫁给编码层，上层自行猜测/重试还会引入新攻击面。
- **结果**: 评审规则：看方案输出是否唯一可解释；歧义方案的编码冗余要求写入部署前提。

### 案例 2: GM 的 1000 倍扩张与 BG 的改良
- **问题**: 第一个语义安全的概率加密方案代价多大？
- **方法论的使用**: 第 8 章 8.4：GM 逐比特加密，1024-bit 模数下 1 比特明文约 1024 比特密文；Blum-Goldwasser 用 BBS 伪随机串改良，扩张大幅下降但每比特仍需模平方。
- **结论**: 安全性证明与可用性冲突时，改良方向是"批量摊薄"（伪随机串一次生成多次使用）而非放弃证明。
- **结果**: 演化轨迹 GM→BG→混合加密确立"可证封装+高效承载"的分层形态。

### 案例 3: ECIES——把扩张从 4 压到 2 的工程折中
- **问题**: 直接用 ElGamal 加密数据扩张大、还要把消息编码进群，怎么办？
- **方法论的使用**: 第 6 章 6.5.4：ECIES 用 DH 型共享点派生对称密钥，再对称加密消息——消息扩张约 2（一个点+密文），例 6.9 在 Z_11 上完整演算。
- **结论**: 混合构造把公钥运算摊到"一次封装"上，数据走对称通道——KEM+DEM 思想的正面样本。
- **结果**: "扩张率"成为方案对比的硬指标；Cocks IBE 的膨胀在对照下直接出局（仅教学价值）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为根密钥分发（小载荷高价值）与业务数据流（大流量）选型加密方案，判断可证明方案用在哪一层。
2. 评审宣称"可证明安全"的新方案/论文原型，估算部署可行性。
3. 预算答辩：为什么用混合加密而不是纯公钥方案全程加密。
4. 事故复盘：方案"理论安全"却没人用，问题出在扩张/歧义/吞吐哪一科。

### 语言信号 (用户的话里出现这些就应激活)

- "ciphertext expansion / 密文比明文大多少倍"
- "有安全证明的方案为什么没被部署 / 理论方案能用吗"
- "hybrid encryption / KEM DEM / 为什么要混合加密"
- "Rabin 为什么没人用 / 四个明文选哪个"
- "吞吐/延迟预算，公钥方案扛得住吗"

### 与相邻 skill 的区分

- 与 `stinson-evidence-tier-labeling` 的区别: 那个评证据成色（该不该信）；本 skill 算信了之后的代价（用不用得起）——先信后买，两步分开。
- 与 `stinson-proof-coverage-audit` 的区别: 那个拆证明覆盖域；本 skill 完全接受证明，只审输出形态（扩张/歧义/吞吐）——证明再完美也过不了本 skill 的账。
- 与 `stinson-feasibility-ceiling-first` 的区别: 那个算"任何方案最多能做到多少"（不可能界）；本 skill 算"达到安全要付多少可用性代价"（代价核算）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **算扩张账**: 密文长度/明文长度的比率（逐比特类方案按安全参数放大）；对照场景带宽预算。
   - 完成标准: 扩张率数字 + 带宽影响一行；超预算即标注。
2. **算歧义账**: 解密/验证输出是否唯一可解释；歧义方案的编码冗余要求（哪些位校验、谁负责消除）是否落实。
   - 完成标准: 唯一性判定；歧义时附冗余编码方案与失败语义（拒绝/重试）。
   - 判停条件: 若方案输出歧义且上层无冗余机制，直接输出"不可部署（除非补编码层）"结论跳到步骤 4。
3. **算吞吐/延迟账**: 每比特/每消息的公钥运算次数；对照业务速率与硬件预算。
   - 完成标准: 吞吐数字 + 瓶颈运算标注。
4. **按载荷画像分配方案**: 高价值小载荷→可证明封装（扩张可容忍、买保证）；大流量→对称承载；混合架构（KEM 封装一次+DEM 承载数据）作为默认形态核对。
   - 完成标准: 分配表（载荷类型×方案层×理由）；混合形态有无缺失环节标注。
5. **输出代价结论**: 三科目数字 + 部署判定；"理论安全但不可用"类结论需指明卡在哪个科目。
   - 完成标准: 结论含三科目各自的数字与判定句。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 对称算法的性能调优（AES-NI、实现优化）——无公钥级扩张结构，普通性能工程。
- 协议安全属性讨论（要不要 CCA）——先定属性再看代价；本 skill 假定属性已定。
- 存储成本的企业核算（磁盘/对象存储计费）——扩张账只算协议层增量，基础设施计费另算。

### 作者在书中警告的失败模式

- 归约完美≠端到端可用：Rabin 四义解密的成本转嫁（第 5 章 5.8）。
- 只看安全性选型：GM 1000 倍扩张、Cocks"不是一个实用的系统"（第 8 章 8.4、12.5.3）。
- 上层自行"猜测重试"消化歧义——引入新的可区分性与拒绝服务面。

### 作者的盲点 / 时代局限

- 成书 2006 年：KEM/DEM 的正式化（ISO/IEC 18033-2）、DH 封装标准化（HPKE）未出现，书中混合形态停留在 ECIES 示例；现代评审可把 HPKE 类直接列入步骤 4 的默认形态。
- 延迟敏感场景（TLS 握手 RTT 预算）的代价科目（轮数）在书中未独立成科，可自行补充。

### 容易混淆的邻近方法论

- 可用性代价 ≠ 实现质量：扩张/歧义/吞吐是方案数学形态自带的；实现 bug、侧信道是工程层另附——修实现修不掉形态代价。
- 与"安全性能权衡"泛论的区分：本 skill 是三科目记账法（可量化、逐科目判定），不是"安全和性能要平衡"的空话。
