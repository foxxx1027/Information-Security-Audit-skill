# 控制措施测试的准入约束与类型选档（盲测避免、灰盒有限）

## R — 原文 (Reading)

> "测试的执行需要很小心，需要由有能力的专家来进行，并且测试对组织运行的影响必须考虑到，并且在测试之前应得到批谁，同时也要考虑测试的运行应设置在运行窗口之外，测试应选择较低投人或容易再现的环境下进行。"
>
> — 原作者、原作者，原始方法论来源第6章 6.3 测试前提（source.txt L4879–4882，OCR"批谁"="批准"、"投人"="投入"原样保留）

## I — 方法论骨架 (Interpretation)

测试是审核中唯一"主动制造事件"的高风险动作——测试本身也可能制造新风险。因此每项测试前要过**五条准入约束**：

1. 由有能力的专家执行；2. 事先评估对组织运行的影响；3. 测试前获得批准（授权留痕）；4. 设在运行窗口之外；5. 优先选低投入或容易再现的环境。

选档上，按**测试双方掌握信息的对称程度**定盲/灰/明：
- **盲测**（对方不知情、审核员信息最少）：覆盖度系于审核员个人技能与状态，结论不可重现——**应尽量避免**；
- **灰盒**（有限信息）：效率高但依赖所供信息质量，**有限使用**（常见于自评）；
- **串联测试**（双方共享细节）：可复现、保一致性，适合首次验证；
- **反向测试**（对象不知情）：模拟真实攻击者视角。

与直觉相反的排序是：越像真实攻击（盲测）越不被推荐，因为审核要的是**可重现的证据**，不是逼真度。

## A1 — 书中的应用 (Past Application)

### 案例 1: 五条准入约束（6.3）
- **问题**: "我们要对生产环境做一次测试验证防护"——立项清单是什么？
- **方法论的使用**: 逐项过五条：专家、影响评估、批准、窗口外、环境选择。
- **结论**: 任一条不满足即不具备测试前提；"做测试本身也可能制造新风险"是立项逻辑。
- **结果**: 五条作为 6.3 开篇的测试前提定型，并被 6.4.2 的测试事件复用。

### 案例 2: 盲测避免的排序（6.3 测试类型）
- **问题**: 测试类型怎么选？
- **方法论的使用**: 按信息对称度四分（串联/反向/盲/灰盒），并给出使用排序——"由于盲测的广度和深度与审核员的知识面和效率有关，因此这种测试应尽量避免使用"（L4908–4909）；灰盒依赖所供信息质量、应有限使用。
- **结论**: 结论可重现性优先于攻击逼真度。
- **结果**: 四类测试与使用约束成为测试选档底表（案例 3 见测试事件约束复用）。

### 案例 3: 约束跨子域复用（6.4.2）
- **问题**: 产生测试事件验证日志记录能力，也要走全套准入吗？
- **方法论的使用**: 测试事件作为积极手段时同样受 6.3 约束（批准、窗口外）。
- **结论**: 准入约束是所有主动测试的通用闸门，不因测试变小而豁免。
- **结果**: 支撑 verified.md V1 跨语境判定。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 计划对生产环境做渗透测试/红队紫队演练，需要立项清单与授权文书要素。
2. 审核方要求"做一次验证性测试"，双方谈 rules of engagement。
3. 选择测试档位：首次验证、自评、模拟真实攻击者各选什么类型。
4. 事件响应验证（钓鱼演练、MFA 拒绝测试）前的合规检查。
5. 复盘一次"测试把业务打挂了"的事故，查准入程序缺了哪条。

### 语言信号 (用户的话里出现这些就应激活)

- "渗透测试前要准备什么/需要什么授权？" / "pen test authorization checklist"
- "盲测/灰盒/白盒怎么选？" / "blind vs grey-box vs tandem testing"
- "测试窗口能安排在业务低峰吗？" / "change window, rules of engagement"
- "演练把系统搞挂了谁负责？"（影响评估与协议缺位）
- "我们想做一次不打招呼的测试"（警惕：盲测应尽量避免）

### 与相邻 skill 的区分

- 与 `isms-test-event-method`：本 skill 是**要不要测、怎么测的闸门与选档**；测试事件法是**具体制造受控事件验证记录/响应**的执行手法，执行时受本 skill 约束。
- 与 `isms-three-layer-evidence-chain`：被动三层取证（查文档/配置/日志）不需要本 skill；一旦要主动触发，先过准入。
- 与一般渗透测试方法论（PTES/OSSTMM）：那些覆盖测试技术执行，本 skill 只覆盖**审核语境下的准入与选档纪律**。

## E — 可执行步骤 (Execution)

1. **明确测试对象与目的**：写清测什么控制、验证什么判据（"会拦截""会记录""会响应"）。
   - 完成标准: 一句话测试目的 + 判据（可观察的预期结果）。
2. **过五条准入**：逐条核对——执行者资质证据、运行影响评估、书面批准（谁签）、时间窗口（运行窗口之外）、环境选择（staging/低投入优先，生产仅获准后）。
   - 完成标准: 五条各有责任人、证据（批准文书、窗口时段、环境说明）；缺任一条 → 测试不启动。
   - 判停条件: 若目的可用被动取证或测试事件在测试环境完成 → 取消生产环境测试计划。
3. **选档**：按信息对称度选类型——首次验证选串联；模拟真实攻击者用反向（对象不知情但已获组织批准）；不做无预告盲测；灰盒限于自评或信息质量可控时。
   - 完成标准: 选型理由一句话写明，且与测试目的匹配。
4. **定协议**：约定测试范围外的系统、回退/中止条件（发现高危即停）、误报处理（结果在结论前认真研究）、双方联系人。
   - 完成标准: 书面 RoE 双方签署。
5. **执行与收口**：按窗口执行、全程留痕；结果与预期差异逐条分析后再下结论。
   - 完成标准: 测试记录（时间、动作、结果）+ 差异分析完成，证据交审核链条。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 被动审核取证（查文档、配置、历史日志）——无需测试准入，直接走三层取证。
- 漏洞扫描只读模式/基线核查——无侵入性，按普通证据收集处理（但生产高峰期的重负载扫描仍宜评估影响）。
- 把准入清单当作拖延或拒绝验证的借口——约束是让测试可控，不是取消验证义务。

### 作者在书中警告的失败模式

- ce18：测试未获批准、在运行窗口内进行、挑高投入难复现环境——"做测试本身也可能制造新风险"。
- ce17：把盲测当常规手段——"由于盲测的广度和深度与审核员的知识面和效率有关，因此这种测试应尽量避免使用"；灰盒"依赖所供信息质量"须有限使用。

### 作者的盲点 / 时代局限

- **版本与时代提示**：6.3 成文于 2012（27002:2005 语境），未覆盖今日紫队/CTF 化演练、Bug Bounty（众测的授权模型不同——范围外报告制）、云上测试的租户边界与合同限制（云厂商渗透测试须报备）。沿用骨架时须补充这些场景的授权形态。
- "有能力的专家"未给能力判据（认证？经历？），实操中需落到具体资质要求。
- 误报研究只一句带过，未给方法。

### 容易混淆的邻近方法论

- PTES/OSSTMM/OWASP WSTG：测试的**技术执行**框架；本 skill 是**准入与选档**纪律，两者互补不互替。
- 变更管理流程：窗口与批准与变更管理同构，但测试准入多"影响评估+对象知情范围"两个测试特有维度。
