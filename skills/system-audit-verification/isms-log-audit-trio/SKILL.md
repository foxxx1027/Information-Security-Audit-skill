# 审计日志审核三件套（字段完备性 / 架构适配 / 跨系统联合）

## R — 原文 (Reading)

> "为了分析是否有未授权的活动或是否发生信息安全事态，审计日志应包含如下信息：·用户ID;·日期和时间；·诸如登录和退出这样的关键事件；·终端标识；·网络地址和协议。"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.2 审计日志·补充技术信息（source.txt L5094 起）

## I — 方法论骨架 (Interpretation)

审日志的判据不是"有没有日志、日志多不多"，而是**"出了事能不能查"**——可调查性。三件套把它变成三个可勾选动作：

1. **字段完备性**：最小字段集——用户ID、日期时间、登录/退出等关键事件、终端标识、网络地址与协议；扩展项——失败登录、配置变更、报警、保护系统自身开关。缺字段 = 出事后无法定位"谁、从哪、何时、做了什么"。
2. **架构适配**："记录日志的方法取决于系统的结构、基础架构和执行的应用"——C/S、瘦客户端、虚拟机、ASP/SaaS/云各不相同。先给环境分类，再定取证路径；拿主机 syslog 模板套云原生环境会一无所获。
3. **跨系统联合**：事件致因往往横跨多系统，日志必须能拼成一条时间线；前提是掌握每份日志的位置与类型，且各系统时钟同步。

附带一条硬警句：采集配置正常 ≠ 记录完整——容量不足、未执行等原因照样丢记录，完整性要抽查实际条目（配置态 vs 运行态落差）。三件套全部通过，才可下"事件可追溯"结论。

## A1 — 书中的应用 (Past Application)

### 案例 1: 字段集核对（6.4.2）
- **问题**: 受审方说"我们日志都开着"，如何判定够不够用？
- **方法论的使用**: 拿最小字段集逐项核对日志实际字段，做差集。
- **结论**: 缺关键字段（如无终端标识）则取证能力不足——即使日志量很大。
- **结果**: 书中把该字段集列为"补充技术信息"作为 6.4.2 的核对底稿。

### 案例 2: 架构分类定路径（6.4.2 注）
- **问题**: 一套日志审法能否通吃所有系统？
- **方法论的使用**: "记录日志的方法取决于系统的结构、基础架构和执行的应用"，注中枚举服务器/台式机差异及 C/S、瘦客户端、虚拟机、ASP/SaaS/云形态。
- **结论**: 审 A.10.10 前先画部署形态图，明确各类系统日志归属与可取证位置。
- **结果**: 形成"先分类、再取证"的前置动作；书中成书时云日志取证尚无实例（局限，见 B）。

### 案例 3: 跨系统联合前提（6.4.2 实践指南）
- **问题**: 单系统日志都正常，为什么事件还是查不清？
- **方法论的使用**: "日志应进行联合……要了解包含系统结构/基础架构/配置信息的审计日志文件的位置和类型是很重要的"（L5141–5147）。
- **结论**: 无日志资产台账、无时钟同步，事件可追溯性不成立。
- **结果**: 审核落点为"受审方是否具备日志集中化能力与台账"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 审核/评估组织的日志与监控控制（等保日志留存、ISO 27001 日志控制、SOC 运营 readiness）。
2. 事件复盘后发现"日志在但拼不出时间线"，要诊断日志体系缺陷。
3. 设计新系统/云环境的日志方案，需要"可审计性"验收字段清单。
4. 远程办公/零信任环境发生数据外发事件，评估其调查能力。
5. 采购 SIEM/日志平台前，盘点现有日志源字段与格式是否够用。

### 语言信号 (用户的话里出现这些就应激活)

- "帮我审一下日志这块" / "日志控制怎么审？"
- "日志字段要记哪些才够事后查？" / "what to log for investigation"
- "多套系统的日志怎么关联/对时间线？" / "correlate logs across systems"
- "日志配置没问题但出事还是查不到原因"（典型三件套未过）
- "audit trail review / logging completeness checklist"

### 与相邻 skill 的区分

- 与 `isms-three-layer-evidence-chain`：那是取证的通用骨架（日志只是运行层证据之一）；本 skill 审的对象就是日志体系本身。
- 与 `isms-test-event-method`：本 skill 静态核对"该记的字段和路径"；测试事件法动态验证"特定情况真的会记"。静态通过≠会记。
- 与 `isms-privilege-audit-chain`：特权审读取日志但焦点在提权盲区与分权判据；本 skill 焦在日志自身的完备性。

## E — 可执行步骤 (Execution)

1. **盘点日志源**：列出环境内全部日志产生点（主机、网络设备、应用、云服务、SaaS、IDP），并给架构形态分类（传统 C/S、虚拟化、云托管、SaaS）。
   - 完成标准: 一张日志源清单，每条标注架构形态与日志存放位置。
2. **字段完备性核对**：对每类日志源抽样实际条目，对照最小字段集 + 扩展项做差集。
   - 完成标准: 每类日志源列出"有/缺"字段；缺字段项标为发现线索。
   - 判停点: 若某日志源连采集都未开启 → 不必做字段核对，直接按 isms-nonconformity-grading-loop 走分级。
3. **架构适配检查**：按形态逐一确认取证路径可达（云侧日志有无导出权、SaaS 有无审计 API、终端日志存本机还是外传）。
   - 完成标准: 每种形态一条"日志在哪、怎么取"的可执行描述；取不到的标注为盲区。
4. **联合分析演练**：给一个模拟事件（如"某账号异常登录后外发文件"），要求现场指出需要哪几份日志、在哪、什么格式，并核对系统时钟同步。
   - 完成标准: 能列出日志组合清单；时钟偏差有数值；拼不出的环节被记录。
   - 判停点: 时钟不同步或关键日志缺失 → "事件可追溯"结论直接判不成立，进入第 5 步。
5. **完整性抽查与结论**：抽最近时段实际条目，验证应记信息未因容量/未执行丢失（ce20）；汇总三件套结果。
   - 完成标准: 输出三件套各自通过/不通过 + 缺口清单，交分级与整改。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 验证某控制"会不会记录特定情况"——那是动态功能验证，用 isms-test-event-method。
- 对单一控制（口令、备份）做三层取证，日志只是其中一层——用 isms-three-layer-evidence-chain。
- 已发生事件的技术取证（镜像、恢复删除文件）——那是数字取证专业工作，超出审核范畴。

### 作者在书中警告的失败模式

- ce20："一些审计日志中应该被记录的信息因为缺少执行、系统容量或其他原因丢失，甚至在日志设置正常的情况下"——配置态≠运行态。
- 仅静态翻历史日志就断言记录能力（ce19 的反面）：历史记录只证明"过去记了"。

### 作者的盲点 / 时代局限

- **版本提示**：字段集出自 27002:2005 A.10.10 实施指南；27001/27002 的 2013/2022 版已将日志控制重组（2022 版 8.15 监控、8.16 日志记录等），字段清单应结合现行标准与法规（中国网安法要求网络日志留存不少于 6 个月）更新。
- 书成于 2012，云/SaaS 场景仅一句枚举，无云日志（CloudTrail/审计日志 API）实操细节；零信任、EDR 遥测等新日志源需自行扩展（verified.md V2 已外推验证）。
- 作者未讨论日志本身的安全保护（防篡改、访问控制）细节，仅提示完整性检查一步。

### 容易混淆的邻近方法论

- SIEM 用例调优/告警规则设计：那是"发现实时威胁"，本 skill 是"事后调查能力"，判据不同（告警价值 vs 字段完备）。
- 日志留存合规检查（只查期限）：期限只是三件套之外的一条线，不等于可调查性。
