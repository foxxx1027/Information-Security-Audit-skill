# 网络服务安全三线审核（外部查合同/SLA、内部查设计配置、再查日志 + 五特性核对集）

## R — 原文 (Reading)

> "检查合同文档，包括服务提供商提供的SLA，以确定是否满足组织的业务、法律法规和安全需求"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.5 网络服务（source.txt L5471 起）

## I — 方法论骨架 (Interpretation)

网络服务控制的取证路径按**服务提供方**分叉：

- **外部服务**：第一证据在合同文档——SLA 与需求说明书是否把组织的业务、法律法规、安全需求写成可核对条款。
- **内部服务**：查网络服务设计文档中的系统设置，再查系统日志（身份认证、加密、连接控制、链路速度、应答、故障时间）。

需求侧有一张**五类安全特性最小核对集**，逐项确认并核落地：
1. 防窃听（加密）；2. 防未授权访问（访问控制）；3. 防恶意行为（IDS/IPS）；4. 防未授权 WEB 访问（URL 过滤）；5. 防不期望事态（事件响应）。

三条线任何一条断线（合同没写、配置与合同不符、日志拿不出）即取证不足。核心手法是把采购条款接到现场技术证据上——纸面安全需求必须能在配置与运行记录中被找到。外包场景另有专项风险：机密信息可能经外包网络服务外泄，须单独评估第三方加密与身份认证。

## A1 — 书中的应用 (Past Application)

### 案例 1: 外包 vs 内部的取证分叉（6.4.5）
- **问题**: 同是网络服务，自建与外包的审核证据从哪头取？
- **方法论的使用**: 外部服务查合同文档含 SLA 与需求说明书；内部服务查设计文档系统设置，再查系统日志。
- **结论**: 提供方决定第一证据位置——外包不进机房查配置，先审合同。
- **结果**: 形成三线分支结构，作为 6.4.5 的骨架。

### 案例 2: 五特性需求分析（6.4.5 技术说明）
- **问题**: "安全需求"笼统，怎么变成可核对项？
- **方法论的使用**: 枚举五类安全特性（防窃听/防未授权访问/防恶意行为/防未授权 WEB 访问/防不期望事态），逐项确认并核落地。
- **结论**: 五特性构成合同线与配置线的共同映射底表，缺项即"需求分析不完整"。
- **结果**: 每类特性有对应技术载体（加密、访问控制、IDS/IPS、URL 过滤、事件响应）。

### 案例 3: SLA 核对法在结合审核复用（第7章 7.4）
- **问题**: 该方法只适用于单一网络服务审核吗？
- **方法论的使用**: 27001×20000-1 结合审核中，服务级别管理、服务报告与安全测量对齐——SLA 核对法跨场景复用。
- **结论**: "实测运行指标对照承诺指标"是可迁移骨架。
- **结果**: 支撑 verified.md V1 跨语境判定。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 组织把 CDN、云备份、邮件网关、MSSP 全部外包，设计供应链安全审核方案。
2. 供应商合同续约评审：核对现有 SLA 是否还覆盖法规与业务变化。
3. 审核中发现供应商"声明加密、实际 HTTP 回源"类言行不一，需要定位断线层。
4. 制定安全服务采购需求书，需要把五特性写成可验收条款。
5. 内审自建网络服务（VPN、网关、代理）时决定从哪条线开始取证。

### 与相邻 skill 的区分

- 与 `isms-three-layer-evidence-chain`：本 skill 按提供方（外部/内部）分支并带五特性底表，是供应链场景的定制版；通用骨架不分支。
- 与 `isms-recovery-time-verification`：那是时效类承诺的专项实测；本 skill 的日志线会用到它（故障时间、恢复时限核对）。
- 与 `isms-document-consistency-matrix`：那是体系文件内部互证；本 skill 是合同↔配置↔运行三线互证，对象与证据形态不同。

## E — 可执行步骤 (Execution)

1. **判定提供方与范围**：列出待审服务清单，标注外部/内部，以及各自承载的信息类型（是否涉机密/PII）。
   - 完成标准: 服务×提供方×信息敏感度矩阵。
2. **合同线核对（外部服务）**：逐家核对合同/SLA/需求说明书是否载明五特性映射与量化指标（TLS 强制、URL 过滤、事件通报时限、恢复时限、检测率等）。
   - 完成标准: 五特性×服务的对照表；缺项标为"需求分析不完整"发现。
   - 判停条件: 连合同/SLA 都不存在 → 不必进配置线，直接按合同缺失分级开单。
3. **配置线核对**：核实际 TLS 版本、URL 分类策略、租户隔离、访问控制与合同承诺一致；内部服务查设计文档系统设置。
   - 完成标准: 每条承诺对应一条配置实测值；不一致项（如声明加密实为 HTTP 回源）标为断线发现。
4. **日志线核对**：查运行记录——拦截量、身份认证事件、加密协商、故障时间、事件通报执行。
   - 完成标准: 运行指标与承诺指标逐条对照结果。
   - 判停点: 日志由供应商持有且不可导出 → 按 isms-degraded-evidence-fallback 降级并披露，或要求第三方鉴证报告。
5. **专项与结论**：对机密信息外泄风险单独评估第三方加密与身份认证；汇总三线断点交分级。
   - 完成标准: 三线各自通过/断线清单 + 供应商级结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 组织自建的非网络类控制（口令、特权、备份）——各有专属链（三层取证骨架统一）。
- 供应商财务/资质尽职调查——采购尽调流程，证据形态不同。
- 一次渗透测试外包的测试方案评审——那是测试准入问题（isms-control-test-admission）。

### 作者在书中警告的失败模式

- ce48："当一个组织使用网络服务，组织的机密信息可能通过外包网络服务外泄。因此，评估人员应考虑需要的安全功能，例如外包网络服务提供者提供的加密和/或身份认证"——只看内部文档不查安全功能与 SLA。
- 合同缺安全指标、配置与合同不一致均未作为可查线索被处理——两处断线被放过。

### 作者的盲点 / 时代局限

- **版本与时代提示**：6.4.5 基于 27002:2005 A.10 网络域；云/供应链标准（ISO 27017/27018/27036 系）成书时未出版或未收录，书中云计算仅一句带过。今用须补充：数据出境合规（个保法/数据安全法）、次级处理者（第四方）传递、供应链攻击面（verified.md V2 已外推至 CDN+云备份+邮件网关全外包场景）。
- 五特性是 2012 年网络边界视角，未含零信任身份平面、API 安全、SaaS 租户隔离——作为底表应扩充而非照抄。
- 作者假设合同可得且可读；实际 SaaS 点击式协议常无安全条款，需以补充协议/DPA 承载。

### 容易混淆的邻近方法论

- 供应商安全问卷（SIG/CAIQ 分发）：信息收集动作，不是取证——本 skill 要求落到配置与日志证据。
- SOC 2 报告核对：第三方鉴证替代部分取证，但替代不了合同线与关键配置抽查。
