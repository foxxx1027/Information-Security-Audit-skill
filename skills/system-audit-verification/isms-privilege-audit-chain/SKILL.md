# 特权管理审核链（定义文档 → 按平台分支核查 → 使用日志 + 提权盲区与分权判据）

## R — 原文 (Reading)

> "在UNIX或Linux中，仅通过检查跟用户登录来交叉跟用户使用是否恰当是危险的。因为普通用户登录后使用"su'就可以变成根用户"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.3 特殊权限·注（source.txt L5287–5288，OCR"跟用户"="根用户"原样保留）

## I — 方法论骨架 (Interpretation)

特权审核最容易犯的错是"查 root 登录记录 = 审了特权"。本书的审核链是三段加两个判据：

**三段取证**：
1. **定义文档**：先要求"特殊权限定义文档"入档——哪些算特殊权限、分配给谁；文档须按系统/数据库/应用分别描述（各系统特权不同）。文档不覆盖的特权 = 无定义特权，本身就是发现。
2. **按平台分支核查**：大型机查 RACF 报告，UNIX/Linux/Windows 查特权使用日志与权限控制列表——环境不同证据形态不同，不能一套方法通吃。
3. **使用日志**：核对特权活动记录能否回溯到具体自然人。

**两个判据**：
- **提权盲区**：特权活动不表现为 root 登录——普通用户 su 一下就变根用户；只查 root 登录"是危险的"。现代等价物：sudo 提权、IAM role 假扮（AssumeRole）、服务账户令牌。
- **分权与日常化**：特权应分配给不同用户 ID、日常操作用普通 ID、系统应可拒绝 root 直接登录；"定期使用特殊权限会滋长未授权的行为"——把分权问题转成特权使用**频率与集中度**的可观察判据。日志里只看到一个特权 ID 在活动时，必须访谈确认背后是否真为一人。

## A1 — 书中的应用 (Past Application)

### 案例 1: su 盲区（6.4.3 注）
- **问题**: 审核员翻完 root 登录记录无异常，能否下"特权使用恰当"的结论？
- **方法论的使用**: 作者直接点破：普通用户登录后 su 即变根用户，root 登录视角根本看不到这类特权活动。
- **结论**: 必须查 su/切换记录、特权使用日志、权限控制列表并交叉，而非只看 root 登录次数。
- **结果**: 该盲区被列为 6.4.3 的注，成为特权审核的标准警示。

### 案例 2: 定义文档先行（6.4.3 证据与方法）
- **问题**: "特殊权限"在各系统含义不同，从哪开始审？
- **方法论的使用**: 先检查定义特殊权限的文档中是否描述了系统配置的设置，再按平台分支取证（RACF 报告 / 特权使用日志）。
- **结论**: 无定义文档 → 特权分配无基准可核，属设计层缺失。
- **结果**: 形成"定义→配置→日志"顺序的特权专属审核链。

### 案例 3: 分权三规则（6.4.3 实践指南）
- **问题**: 怎样判断特权管理是否健康，而不只是"有没有"？
- **方法论的使用**: 三判据——特殊权限分给不同用户ID；不需特权的操作用普通ID；系统应可拒绝 root 直接登录；辅以"定期使用特权会滋长未授权行为"。
- **结论**: 特权使用频率与集中度成为可观察指标（日志单 ID 长期高频活动 → 访谈核实是否一人）。
- **结果**: 书中以实践指南形式给出设计层检查点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 内审/外审中的特权账号管理检查（root、域管、云 root、数据库 sysdba、Break-glass 账号）。
2. 云环境特权审计：统计了云厂商 root 账号登录记录，怀疑不够（IAM role 假扮不留下 root 登录）。
3. 事件调查中发现"日志里只有一个服务账户在活动"，无法归因到人。
4. 设计/评审特权管理方案（PAM、JIT 提权、双人复核）时的验收要点。
5. 等保/ISO 审核前自查"最小权限与职责分离"落没落地。

### 语言信号 (用户的话里出现这些就应激活)

- "特权账号/管理员权限怎么审？" / "privileged access audit"
- "只看 root 登录日志够不够？"
- "su / sudo / AssumeRole 切换记录要不要查？"
- "特权账号共用一个 ID，怎么核到人？"
- "root account review, service account audit, elevation logs"

### 与相邻 skill 的区分

- 与 `isms-log-audit-trio`：本 skill 消费特权日志但焦点是提权路径盲区与分权判据；log-audit-trio 焦点在日志体系完备性。
- 与 `isms-three-layer-evidence-chain`：本 skill 是该骨架在特权域的实例化，附加值在"提权盲区"这一反直觉取证口径。
- 与 `isms-test-event-method`：验证"特权拦截会不会记"可用测试事件，但盲区诊断用本 skill 静态链即可。

## E — 可执行步骤 (Execution)

1. **取特权定义文档**：索取"特殊权限定义文档"，核对是否按系统/数据库/应用分别描述特权与持有人。
   - 完成标准: 定义清单到手；与各平台实际特权组/角色做差集（文档外的特权 = 发现）。
   - 判停点: 无定义文档 → 设计层缺失，直接记录发现并继续用平台侧证据补全局。
2. **按平台取证**：逐平台拉证据——大型机/遗留系统取 RACF 类报告；UNIX/Linux 取 su/sudo 记录与 /etc 配置；Windows 取特权组隶属与事件日志；云取 IAM 策略、角色可假扮关系、CloudTrail 类审计迹。
   - 完成标准: 每平台一份"谁持有特权、谁可提权"的实测清单。
3. **专查提权盲区**：确认取证覆盖 su/sudo、角色切换、服务账户令牌等非 root 登录路径；列出每条路径对应的日志源。
   - 完成标准: 提权路径×日志源矩阵，无日志覆盖的路径标为盲区发现。
4. **分权与集中度判读**：核对特权分 ID、日常操作用普通 ID、拒绝 root 直接登录三规则；统计特权使用频率与集中度。
   - 完成标准: 高频/单 ID 集中活动项附带访谈核实结果（是否真为一人、是否日常化）。
5. **结论输出**：按定义完整性、取证覆盖、分权健康度三线分别下结论，缺口交分级。
   - 完成标准: 每个发现绑定证据（文档条目/配置截图/日志条目），无"印象分"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 审日志体系本身（字段、留存、联合分析）——用 isms-log-audit-trio。
- 做账号体系治理咨询（角色设计、RBAC 建模）——那是建设不是审核；本 skill 审"已有特权管理是否真实运行"。
- 非特权控制（口令、备份等）——用 isms-three-layer-evidence-chain 相应链。

### 作者在书中警告的失败模式

- ce14/ce16：仅检查 root 登录记录判断特权使用（"是危险的"）；用特权账号做日常操作导致日志无法归因到人（"如果可以通过根特殊权限登录，就不会通过日志进行登录"）。
- ce15：特权定期化使用"会滋长未授权的行为"——把特权当常规资源分配。

### 作者的盲点 / 时代局限

- **版本与时代提示**：出处基于 27002:2005 A.11.2 特权域与 RACF/UNIX 时代平台；27002:2013/2022 已重组为"特权访问管理"主题（2022 版 8.2/8.18），且 PAM、JIT、云 IAM（角色假扮、权限边界、策略即代码）为 2012 后形态，书中无对应——按"定义→平台取证→提权路径盲区"骨架自行映射（verified.md V2 已外推至云 IAM）。
- 作者的取证对象假设是单机/域环境集中日志，未考虑多云多账号工厂（landing zone）下的特权平面。
- "特权频率与集中度"给了判据方向，未给阈值——阈值须由组织风险准则定。

### 容易混淆的邻近方法论

- 账号权限复核（access review，逐账号比对归属）：是本 skill 第 2 步的子集，缺提权盲区视角。
- 渗透测试中的权限提升尝试：验证"能不能提权"，本 skill 验证"特权管理是否可见、可控"。
