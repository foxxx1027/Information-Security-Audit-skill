# 备份恢复的时效实测（"有没有备份" → "实测耗时是否落在承诺时限内"）

## R — 原文 (Reading)

> "应当对恢复程序进行定期的检查和测试，以确保其有效，确保实际执行的时间在恢复操作程序要求的时间之内"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.4 备份（source.txt L5454–5456）

## I — 方法论骨架 (Interpretation)

备份类控制的通病是"文档齐全、从未恢复过"。本方法把验收标准从**存在性**换成**时效实测**：

1. **约定层**：恢复程序/SLA 中写明的时限（现代对应 RTO/RPO）是硬指标，不是参考值；策略文档声称的时限必须与备份模式（全备/差异/增量）的复杂度匹配。
2. **实测层**：定期执行恢复测试，用**实际执行时间**对照程序承诺时间——超时即控制无效，哪怕数据确实可恢复。
3. **判据**："缺测试记录 = 未验证"，而不是"暂视为符合"。没有演练记录，结论只能是"未验证"，留痕（演练日期、耗时、参与人）本身就是证据。

同一"实测运行指标对照承诺指标"的逻辑在书中跨控制复用：网络服务 SLA 的应答/故障时间字段（6.4.5）、杀毒病毒库版本与更新日志（6.4.1）——所有时效类承诺都可如此审计。策略文本 + 系统配置 + 运行实测三层一个都不能少。

## A1 — 书中的应用 (Past Application)

### 案例 1: 恢复时限实测（6.4.4）
- **问题**: 受审方备份策略、备份任务截图齐全，怎么判备份控制有效？
- **方法论的使用**: 查定期检查与测试记录，核对"实际执行的时间在恢复操作程序要求的时间之内"；并按恢复模式（全备份/差异备份）评估复杂度与耗时合理性。
- **结论**: 无恢复测试记录 → 未验证；有记录但超时 → 控制无效。
- **结果**: 该硬指标被写入实践指南，作为备份审核收口动作。

### 案例 2: SLA 时效字段核查（6.4.5）
- **问题**: 网络服务的可用性承诺怎么落地成证据？
- **方法论的使用**: 日志线核查应答（在线系统）、故障时间等时效字段，实测运行指标对照承诺指标。
- **结论**: "实测对照承诺"的同一逻辑落到另一控制对象，证明范式通用。
- **结果**: 与合同/SLA 线（三线审核）配合，形成服务时效审计。

### 案例 3: 病毒库更新时效（6.4.1）
- **问题**: "定期更新"如何验证真发生？
- **方法论的使用**: 以病毒库产品名/版本/更新日志核对更新是否按期发生。
- **结论**: 时效类指标三查（恢复时限、SLA 时效、更新频率）同构——设计承诺→运行记录对照。
- **结果**: 书中三处独立语境复用（verified.md V1 证据）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 内审/外审中的备份与业务连续性控制检查（BCP/DR 审计、等保灾备项）。
2. 采购 SaaS 备份/云 DR 服务，供应商声称 RPO 1 小时 / RTO 4 小时，验收审核怎么做。
3. 写或审 SLA 时，需要把"及时恢复"之类软承诺改写成可实测条款。
4. 备份策略评审会：策略声称的恢复时限与备份模式复杂度明显不匹配。
5. 安全事件后向管理层证明"我们恢复能力有实证"，而非只有拓扑图。

## E — 可执行步骤 (Execution)

1. **锁定承诺值**：从恢复程序/策略/合同 SLA 摘出时限承诺（恢复时间、备份保留、更新频率），注明出处。
   - 完成标准: 承诺值清单（含 RPO/RTO 或等价表述）逐条有文件出处。
   - 判停点: 承诺未成文（"尽快恢复"）→ 时限无基准可对照，按 isms-counterfactual-document-review 判目标不可测，先要求成文。
2. **索取演练记录**：要求出示最近一次（或周期性）恢复测试记录——日期、范围、全程耗时、参与人、结果。
   - 完成标准: 记录到手并核对要素齐全。
   - 判停条件: 无任何演练记录 → 结论直接定为"未验证"，跳到第 5 步（无需继续实测核对）。
3. **耗时对照**：把实测耗时与承诺时限逐条比对；同时评估备份模式复杂度与承诺的匹配度（增量/差异/全备）。
   - 完成标准: 每条承诺一行对照结果（达标/超时/无法判定）。
4. **现场验证（可行时）**：受审方配合时，在验收窗口做一次真实恢复（导出+重导入），全程计时。
   - 完成标准: 现场计时记录 + 恢复数据可用性检查（抽查文件可打开、校验一致）。
5. **结论与发现**：超时/未验证项交分级；要求把演练纳入周期性安排并留痕。
   - 完成标准: 结论区分"可恢复但超时""未验证""达标"三态，不留"大概没问题"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 编写备份策略/设计备份架构——建设咨询，非审核。
- 纸面方案评审（系统未上线、无生产数据）——方案本身无实测对象，等上线后验证。
- 数据可恢复性技术鉴定（介质损坏恢复）——专业数据恢复服务，超出审核范畴。

### 作者在书中警告的失败模式

- ce45：只查备份策略，不验证恢复程序的测试与耗时——"策略类控制的证据链 = 策略文本 + 系统配置 + 运行实测"。
- 备份介质过期/备份未过期才能恢复——时间因素是备份有效性的决定因素之一（6.4.4 同节）。

### 作者的盲点 / 时代局限

- **版本与时代提示**：出处基于 27002:2005 A.10.5 备份域；27001:2013/2022 已并入"业务连续性 ICT 就绪"（2022 版 5.29/5.30 等），且云原生备份（快照、跨区复制、IaC 重建）改变了"恢复"的含义——RTO 实测须区分数据恢复与服务重建两种形态。
- 作者默认受审方自己做恢复；SaaS 场景下演练由供应商执行，证据形态变为供应商演练报告 + 客户侧验收测试，核对方法需扩展（verified.md V2 已外推至 SaaS RPO/RTO 验收）。
- 书中无恢复耗时实测数据示例，指标完全依赖受审方记录的真实性。

### 容易混淆的邻近方法论

- 备份成功率监控（任务是否成功跑完）：只证明"备份发生"，不证明"能在时限内恢复"。
- BIA（业务影响分析）：确定 RTO/RPO 应该是多少——那是设定承诺，本 skill 验证承诺兑现。
