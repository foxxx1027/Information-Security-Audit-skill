# 风险接受准则先行 + 处置四选全覆盖（先有标尺再处置，防默认"全部加控制"）

## R — 原文 (Reading)

> "在考虑风险处置前，组织宜确定风险是否能被接受的准则。如果经评估显示，风险较低或处理成本对于组织来说不划算，则风险可被接受。……给出了四个常见的风险处置选项：处理、转移、规避和接受。"
>
> — 原作者、原作者，原始方法论来源第2章 处置（Treating）安全风险（source.txt L1461–1466）

## I — 方法论骨架 (Interpretation)

很多组织的风险流程是"评估→买控制"，中间缺了一样东西：**标尺**。没有"什么程度的风险可以接受"的事前准则，每个处置决定都只能事后自圆其说。

本方法给处置决策装三个治理装置：

1. **准则先行**：接受准则与可接受级别必须**先于**处置决定存在并文件化——顺序本身可审（时间戳/版本核对）。常见缺口形态：评估方法论齐全，可接受级别判据缺失。
2. **四选全覆盖**：每条风险的处置决定须出自对四种选项（处理/转移/规避/接受）的识别与评价，而不是"风险大就上控制"的单一反射。审核查的是"有没有考虑过其他选项"的痕迹。
3. **批准权限上收**：最终选择"接受"的残余风险是管理决策——须管理者正式批准（签字/管理评审决议），技术团队无权自决接受。

三者合起来把风险处置从安全建议升格为可核查的治理动作。

## A1 — 书中的应用 (Past Application)

### 案例 1: 处置原则的转述与定性（第2章，L1461–1466）
- **问题**: 风险处置的先后逻辑是什么？
- **方法论的使用**: 作者转述标准并点评"比较清晰地说明了风险接受的原则"：先定接受准则，评估显示风险较低或处理成本不划算时可接受；随后给出四选项。
- **结论**: 准则→评估→四选的顺序是处置流程的骨架。
- **结果**: 该顺序成为第5章处置条款审核的参照系。

### 案例 2: 三道检查题把治理装置落成可勾选项（第5章 5.3.2）
- **问题**: 治理原则怎么变成审核动作？
- **方法论的使用**: 4.2.1 c) 检查"制定接受风险的准则并确定可接受级别"；4.2.1 f) 确认"识别和评价风险处理选择措施"的过程考虑了全部 4 种选择（source.txt L3206–3210）；4.2.1 h) 核对"所有残余风险是否获得管理者正式批准"（L3256–3259）。
- **结论**: 准则存在性、四选覆盖、批准链各成一道检查题。
- **结果**: 三问进入逐条款检查表，处置审核从"看处置计划厚不厚"变为逐装置核对。

### 案例 3: 结合审核六问复用（第7章 7.4.1，cs53）
- **问题**: 该要求在多标准场景下还成立吗？
- **方法论的使用**: 27001×20000-1 结合审核风险管理六问之②即"是否有明确的风险接受准则"——同一要求跨场景复用，且 27001 侧更严，以 27001 为主轴拉齐。
- **结论**: 准则先行是跨标准稳定的审核点。
- **结果**: 六问成为结合审核风险管理议题的成品清单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 内审自家风险管理制度，发现"评完就买设备/上控制"，没有接受标准。
2. 数据出境/PII 风险处置方案评审：本地化、标准合同、加密收窄还是停止采集。
3. 供应商/外包风险决策审查：接受还是转移，谁批的。
4. 管理评审输入中残余风险清单的批准链核查。

### 语言信号 (用户的话里出现这些就应激活)

- "风险接受标准是什么？谁批的？" / "who approved the residual risk"
- "除了加控制还有别的选项吗？" / "risk treatment options beyond controls"
- "这个风险我们接受，行不行？"（先问准则，再谈接受）
- "风险处置方案怎么审？" / "how to audit risk treatment"
- "残余风险清单没人签字"（正是 ce33 症状）

### 与相邻 skill 的区分

- 与 `isms-soa-justification-traceback`：它在控制清单层（选了什么控制、为何选）；本 skill 在处置决策层（为何处理/转移/规避/接受）——处置决定为"处理"后才落到选控说理，上下游关系。
- 与 `isms-nonconformity-grading-loop`：准则缺失/批准链断裂如何开单分级用 `isms-nonconformity-grading-loop`；本 skill 负责把三个装置查出来。
- 与风险矩阵/评分方法：那些是评估工具；本 skill 管的是"接受阈值是否先于处置存在"这一治理结构，不评单条风险打分对不对。

## E — 可执行步骤 (Execution)

1. **查准则文件**：接受准则+可接受级别是否文件化，且形成时间先于处置决定（版本/时间戳核对）。
   - 完成标准: 准则文件出处 + 级别定义 + 时间顺序证据。
   - 判停条件: 若无准则 → 记"未制定接受准则"方向发现（4.2.1 c 类），后续步骤仅收集事实，不再做"接受是否合理"的实质评价。
2. **抽风险核四选**：从处置记录抽 N 条风险，核对每条有无对四种选项的识别与评价痕迹。
   - 完成标准: 抽样表——风险 | 最终选项 | 其他选项考虑痕迹；"直接跳控制"条目标出。
3. **核批准链**：所有标记为"接受"的残余风险，核管理者批准证据（签字/管评决议）。
   - 完成标准: 批准证据清单或缺失标注。
4. **判定汇总**：缺失项按 isms-nonconformity-grading-loop 分级（准则整体缺失=体系要素方向；个别批准缺=一般方向）。
   - 完成标准: 每个缺失项有分级判定与整改方向。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 一次性项目/临时决策的风险处理——无体系要求时不硬套四选留痕。
- 危机事件中的紧急处置——可事后补评审，但常态化"先做后补"即失控，需转入体系整改。
- 单条风险的评估技术质量（威胁识别全不全、打分对不对）——那是评估方法审核，不是处置治理审核。

### 作者在书中警告的失败模式

- ce32：风险处置选择单一化——没有"识别和评价风险处理选择措施"的过程，未考虑全部 4 种选择（典型：全部加控制或全部接受）。
- ce33：残余风险未经管理者正式批准就挂账运行——批准权限失守。

### 作者的盲点 / 时代局限

- **版本提示**：准则先行与四选表述转述自 27000 族（2005 版标准语境，书内条款挂接基于 27001:2005 4.2.1 c/f/h）；ISO 31000/27005:2022 与 27001:2013/2022 沿用"处置选项+成文信息"框架，方法兼容可继续用，但条款已移位（现行 6.1.3/6.1.2），检查题须重挂。
- 书中只要求"有准则"，未给准则的定量化方法（风险偏好度量、成本收益边界），实质合理性无法从书内获得判据。
- 默认管理者批准可行，未处理"管理者本人即风险源"（内部欺诈）情境下的批准独立性。

### 容易混淆的邻近方法论

- 风险偏好（risk appetite）框架（COSO ERM/ISO 31000）：更系统的标尺建设方法；本 skill 是其审核侧最小检查，方向一致。
- 风险规避 vs 风险接受的概念辨析（术语层）：本 skill 不做术语辨析，查的是四选过程痕迹与批准链。
