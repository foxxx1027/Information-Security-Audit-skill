# 测试事件法（主动产生受控事件，验证"会记录/会响应"而非"曾记录"）

## R — 原文 (Reading)

> "为了检查系统是否对特定的情况进行记录。审核员需要使用多种措施，包括产生测试事件，检查系统设计文档等"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.2 审计日志·实践指南 1.3 注（source.txt L5168–5169，OCR 断句原样保留）

## I — 方法论骨架 (Interpretation)

静态翻日志有一个逻辑漏洞：日志里有日常记录，只能证明"这类情况发生过且被记了"，**不能证明"你关心的那种特定情况会被记/会触发响应"**。报警、备份联动、权限拦截、钓鱼响应，一切依赖运行期证据的控制都一样。

测试事件法把验证方式从"静态观察"反转为"主动动态触发"：

1. **定义待验证的特定情况**（如"MFA 失败""含恶意链接的邮件""越权访问尝试"）。
2. **经批准制造一次无害的受控事件**（业务低峰、可回溯、可中止）。
3. **沿事件传播路径逐层核对**：网关拦没拦、SIEM 生没生成事件、工单开没开、时限内没有——每一层都要有与该事件**可对应**的记录。
4. **判据**：任一环节无对应记录 = "会记录/会响应"不成立——功能存在性验证失败，与历史台账是否漂亮无关。

前提约束：受 isms-control-test-admission 五条准入管辖（专家、影响评估、批准、窗口外、环境选择），测试事件不因"小"而豁免。

## A1 — 书中的应用 (Past Application)

### 案例 1: 验证日志记录能力（6.4.2 实践指南 1.3）
- **问题**: 日志系统日常记录正常，能否断定"异常情况都会被记"？
- **方法论的使用**: 作者注：为检查系统是否对特定情况进行记录，审核员需要使用多种措施，**包括产生测试事件**、检查系统设计文档等。
- **结论**: 历史记录证明力不足，须主动触发一次特定情况并核对日志条目。
- **结果**: "产生测试事件"被列为日志审核的积极手段，与设计文档检查并列为多种措施之一。

### 案例 2: 测试的定义承接（6.3）
- **问题**: 测试事件算不算"测试"？受什么约束？
- **方法论的使用**: 6.3 定义测试=特定条件下演练、比较实际情况与期望效果的差异；测试事件是其落地形态。
- **结论**: 测试事件受五条准入约束（专家/影响评估/批准/窗口外/环境）。
- **结果**: 准入约束跨子域复用（verified.md V1 证据），小事件不豁免。

### 案例 3: 适用面声明（第6章）
- **问题**: 该法只适用于日志控制吗？
- **方法论的使用**: 报警、备份、联动响应、权限拦截等一切依赖运行期证据的控制同法。
- **结论**: 验证对象是"功能会在特定情况发生"，不限于日志。
- **结果**: verified.md V2 将其外推至"钓鱼邮件告警联动"验证（网关拦截→SIEM 事件→SOC 工单三层核对）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 验证"钓鱼邮件告警联动"真的会触发，而不是只有历史告警台账。
2. 审计日志控制时，历史日志正常但想知道"该记的都会记吗"。
3. MFA/条件访问/DLP 等控制验收：控制台显示开启，要验证异常路径真的会拒、会记。
4. SOC/MDR 服务验收：承诺的检测与响应时限，用一次受控注入实测。
5. 认证审核现场需要证明控制"有效性"而非"存在性"。

### 语言信号 (用户的话里出现这些就应激活)

- "怎么验证它真的会告警/会记录？" / "will it actually trigger?"
- "历史日志都有，但没人测试过异常情况" 
- "做个 simulated phishing / synthetic transaction 测试怎么设计？"
- "检测规则写了但从来没真触发过，怎么验？"
- "验证 detection & response 是否真实联动"

### 与相邻 skill 的区分

- 与 `isms-control-test-admission`：先过准入再触发；本 skill 是触发后的取证手法。顺序不可倒。
- 与 `isms-log-audit-trio`：三件套静态核对字段/架构/联合；本 skill 动态验证"特定情况会记"。静态通过后动态仍未必要通过。
- 与渗透测试：渗透找"能不能绕过"，本 skill 验证"既定路径会不会被记录与响应"——一个是攻击面，一个是观测面。

## E — 可执行步骤 (Execution)

1. **定义特定情况与预期链路**：写出待验证事件 + 每一层的预期记录/响应（谁拦、谁记、谁响应、时限多少）。
   - 完成标准: 事件定义 + 预期链路图（层×预期记录×承诺时限）。
2. **过准入**：按 isms-control-test-admission 五条核对（批准文书、窗口、影响评估、执行人、回退方案）。
   - 判停条件: 批准未取得或影响不可控 → 不得触发，转 isms-degraded-evidence-fallback 披露验证缺口。
   - 完成标准: 批准与窗口留痕。
3. **触发受控事件**：在约定窗口执行一次无害事件（测试信箱收模拟钓鱼、一次 MFA 错误令牌、一次失败登录），标记唯一标识（时间戳/邮件主题标记）便于事后检索。
   - 完成标准: 事件执行记录（时间、操作人、标识）。
4. **逐层核对**：沿链路逐层检索对应记录——拦截记录、SIEM 事件、工单、通知；核对响应时限。
   - 完成标准: 层×实际记录对照表；每层"有对应记录（含唯一标识）/无"二值判定。
   - 判停点: 任一层无对应记录 → 功能验证失败，直接进入第 5 步，不再补触发（除非经重新批准）。
5. **结论输出**："会记录/会响应"成立与否 + 失败层定位；证据（记录条目、时间差）交 isms-nonconformity-grading-loop。
   - 完成标准: 结论绑定唯一标识的记录证据，无推定。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 未获批准、未过准入的任何"顺手一试"——包括对第三方/SaaS 系统擅自注入测试流量（可能违反合同与法律）。
- 静态可验证的对象（配置值、文档一致性）——不必制造事件。
- 高危不可逆路径（触发真实数据外发、真实停机）——受控事件必须无害可回退。

### 作者在书中警告的失败模式

- ce19：只翻静态日志，不构造测试事件验证记录能力——"静态日志只能证明'过去记了'"。
- ce18 的通用警告：测试未获批准、在运行窗口内进行——测试事件同样适用。

### 作者的盲点 / 时代局限

- **版本与时代提示**：出处基于 27002:2005 A.10.10；现行 27001:2013/2022 下"控制有效性验证"导向更强（2022 版 5.x 有效性评估），测试事件法是天然载体，但书中无云/SaaS 场景细节（租户内触发事件的合规边界、供应商协调）。
- 书中未讨论测试事件与真实事件的区分标记（防误报升级为真实事件响应），今用应补充事件标记与知会范围。
- 误报处理仅原则性提及。

### 容易混淆的邻近方法论

- 混沌工程（Chaos Engineering）：主动注入**故障**验证**韧性**；本 skill 注入**安全事件**验证**记录与响应**。判据与时限对象不同。
- 红队演练：模拟真实攻击链追求绕过；本 skill 验证既定链路的观测完整性。
- 合成监控（synthetic monitoring）：持续性自动探测，本 skill 是审核时点的一次性受控验证，但可借用其探针设计。
