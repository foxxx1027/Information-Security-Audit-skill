# 三层取证链（设计/文档 → 配置/设置 → 运行记录/实效）

## R — 原文 (Reading)

> "实践指南 检查杀毒软件是否设计了自动更新 2.1 证据 检测系统的设计文档或说明书 方法 检测、评审 实践指南 检查杀毒软件是否设置了自动更新 2.2 证据 检测系统的设置 方法 检测、观察 实践指南 通过病毒库的产品名称、版本和更新日志来检查病毒库是否已经更新"
>
> — 原作者、原作者，原始方法论来源第6章 6.4.1 恶意代码防范（source.txt L5032–5050，OCR 表格拼接噪声原样保留）

## I — 方法论骨架 (Interpretation)

任何控制都可以从三个层面取证，三层各自独立、必须互证：

1. **应然层（设计/文档）**：策略、系统说明书、网络图、设计文档——组织"声称"控制应该是什么样。
2. **配置层（系统设置）**：现场观察/登录系统核对实际设置——控制"当前被配置成"什么样。
3. **实然层（运行记录）**：日志、版本记录、时间戳、处置痕迹——控制"事实上发生过什么"。

核心纪律有两条。其一，**不能停在单层**：只有文档不能下运行结论，只有配置不能下有效结论；越靠近运行记录，证实度越高，总依据是"只有能够证实的信息方可作为审核证据"（第4章 4.2.2）。其二，**双向背离警句**：文档没写 ≠ 控制没部署（集成部署常不在说明书里）；文档写了 ≠ 控制在运行（策略可能从未落到配置）。三层两两比对，断链处就是发现。该范式在书中跨杀毒、日志、特权、备份、口令六类控制反复出现，并可外推到 2012 年后出现的任何新控制（云控制台、ZTNA、SIEM）。

## A1 — 书中的应用 (Past Application)

### 案例 1: 杀毒更新三查（6.4.1）
- **问题**: "杀毒软件应定期更新"如何审？只问负责人会得到"自动更新啊"的空口回答。
- **方法论的使用**: 2.1 查设计文档/说明书是否设计了自动更新 → 2.2 查检测系统的设置是否启用了自动更新 → 2.3 用病毒库的产品名称、版本和更新日志验证确实已更新。
- **结论**: 三段任一缺失（如只有策略没有版本日志）即证据链不完整，应进一步取证或判不符合。
- **结果**: 书中给出三步各自的证据类型与方法（检测、评审、观察），作为实践指南定型；未附实测数据。

### 案例 2: 集成部署盲区（6.4.1 注）
- **问题**: 审核员按系统说明书核对杀毒部署，发现某服务器"说明书里没有杀毒"。
- **方法论的使用**: 作者提醒：杀毒集成部署在承担其他功能的服务器上时，说明书往往不包含它；台式机更可能完全不在说明书中。
- **结论**: 文档层缺失不能推出控制缺失——必须转观察层（现场看设置）与日志层（收集杀毒日志）补证。
- **结果**: 形成"文档缺失→换层取证"的处置路径；反向盲区同样成立（浏览器检测功能可能根本不产生日志，"无日志"也不等于失效，需查策略配置或触发测试）。

### 案例 3: 口令策略闭环（6.4.6）
- **问题**: 口令这类纯管理控制（策略文本）能否用同一范式审？
- **方法论的使用**: 1.1 查组织密码策略是否描述密码选择规则 → 1.2 查系统配置是否落实系统密码策略 → 1.3 查日志文件是否显示用户确实修改过密码（source.txt L5569–5590）。
- **结论**: 同一"应然→设置→实然"结构跨到非技术控制，证明范式通用。
- **结果**: 三步各有独立证据（策略文本 / 系统配置 / 日志文档），断链即不能判有效。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 内审/验收时需要验证某个具体控制（MFA、加密、备份、杀毒、日志、DLP）"是否有效运行"，而不满足于负责人口头确认或策略文档存在。
2. 审核/评估云服务、SaaS 控制台时，发现界面显示"已开启"，需要判断配置开启是否等于实际生效。
3. 编写检查表或审核方案时，需要为某类控制设计"查什么、要什么证据"。
4. 供应商/安全自评报告与现场观察矛盾（声明加密实际回源 HTTP），需要一套定位断链的比对方法。
5. 复盘一起事件时倒查"当时为什么没发现控制没在跑"。

### 语言信号 (用户的话里出现这些就应激活)

- "这个控制怎么审才算审到了？" / "光看文档肯定不行，要看什么？"
- "策略里有、系统里没有配置，这算符合吗？"
- "控制台显示开启了，就等于生效了吗？" / "configuration enabled ≠ effective?"
- "帮我设计 XXX 控制的取证/验证要点（what evidence to collect）"
- "怎么证明控制真的在运行，而不是纸面上有？"

### 与相邻 skill 的区分

- 与 `isms-log-audit-trio`：本 skill 是所有控制的通用三层骨架；log-audit-trio 是日志这一种证据形态的专门审法（字段/架构/联合）。
- 与 `isms-degraded-evidence-fallback`：本 skill 追求走到运行层；降级 skill 处理"运行层数据客观上拿不到"时如何以配置层证据替代并披露。
- 与 `isms-test-event-method`：运行记录不足时，测试事件法是主动制造运行记录的手段，受 `isms-control-test-admission` 约束。

## E — 可执行步骤 (Execution)

1. **界定控制与判据**：写清要验证的控制名与"有效"的可观察定义（对什么对象、防什么、留什么痕）。
   - 完成标准: 一句话判据 + 至少列出该控制的应然载体（策略/设计文档名）。
2. **取应然层证据**：调策略、系统说明书、网络图、设计文档，记录"声称的覆盖范围与规则"。
   - 完成标准: 记下文档声称值（如"MFA 覆盖全体管理员""日志保存 6 个月"）及文档出处。
   - 判停点: 若文档根本不存在且该控制属策略要求类 → 按 isms-two-step-conformity-audit 判"过程缺失"，直接进入第 5 步开单流程。
3. **取配置层证据**：现场观察或登录系统，核对实际设置与声称值逐项比对。
   - 完成标准: 每项声称值都有"配置实测值"与之成对；标出不一致项。
4. **取运行层证据并收口**：抽取日志、版本记录、时间戳、处置记录，验证配置"真的发生过作用"；三层两两比对。
   - 完成标准: 每个断链（有文档无配置 / 有配置无记录 / 记录与配置矛盾）被明确记录为发现线索。
   - 判停点: 若运行层数据客观不可得（新系统未到期、日志不产生）→ 转 isms-degraded-evidence-fallback，不得硬判。
5. **输出结论**：按证据层级下结论（"文档级符合/配置级符合/实效级有效"），断链项交 isms-nonconformity-grading-loop 分级。
   - 完成标准: 结论句注明证据到达的层级；口头/传闻信息一律未进入证据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯管理体系条款审核（有没有做内审、有没有管评）——那是过程存在性判断，用 isms-two-step-conformity-audit。
- 取证对象是"人"的意识与行为（安全意识、职责理解）——用 isms-interview-tiering 分层访谈。
- 用户只是要一份控制清单/合规对照，不要求验证运行实效——直接对照即可，强行三层是浪费。

### 作者在书中警告的失败模式

- 仅凭文档评审判断已集成部署的杀毒系统（文档盲区，ce13）："往往该系统说明书中不包含杀毒系统的说明"。
- 浏览器检测功能可能不产生日志——"无日志"既不能证明失效也不能证明在运行，必须换层取证（cs29）。
- 策略只写在纸上、不落到系统配置与改密日志（ce47）："策略有而系统无 = 控制未实施"。

### 作者的盲点 / 时代局限

- **版本提示（必读）**：本书 2012 年成书，取证示例全部基于 ISO/IEC 27001:2005 附录 A 控制项（如 A.10.4.1、A.11.3）；现行 27001:2013（附录 A 114 项）/27001:2022（93 项、属性化）条款号已整体错位，引用控制条款前必须映射现行版本。三层取证范式本身与版本无关，可直接迁移。
- 书中六类控制（杀毒/日志/特权/备份/网络/口令）未覆盖云原生、零信任、供应链等 2012 后形态，需按"三层骨架 + 新控制对象"自行扩展（verified.md V2 已验证可外推至云 MFA）。
- 作者承认技术检查部分"抛砖引玉"，无企业实测数据支撑各层证据的有效性差异。

### 容易混淆的邻近方法论

- 渗透测试/漏洞扫描：测的是"能不能被打穿"，不是"控制是否按设计运行"；两者证据不可互相替代。
- 配置基线核查（CIS benchmark 扫描）：只是本 skill 的第 2 层，单独使用会漏掉运行层。

## 相关 skills

- 依赖 `isms-evidence-admissibility-threshold`：三层链取的每一层证据都要先过"相关/可证实/已记录"三道门——门槛在前，路径在后。
- `isms-degraded-evidence-fallback` 与 `isms-privilege-audit-chain` 依赖本 skill（depends-on 方向：它们以本 skill 为前置）：前者是运行层客观不可得时的降级分支，后者是本骨架在特权域的实例化（定义文档→平台核查→使用日志）。
- 组合 `isms-two-step-conformity-audit`：条款审核第二步（过程是否符合逐条 shall）的取证深度由本 skill 承担——宏观顺序配微观证据层。
- 组合 `isms-interview-tiering`：技术控制走本 skill 三层，管理/非技术控制走它的分层访谈——拼起来才是完整的证据面。
- 组合 `isms-test-event-method`：运行层证据不足时，由它在准入约束下主动制造一次受控运行记录。
- 组合 `isms-recovery-time-verification`：时效类承诺（恢复时限、更新频率）的专项实测在本骨架的运行层收口。
