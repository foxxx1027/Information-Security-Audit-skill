# 符合性审核两步法（先查"过程是否到位"，再查"是否满足逐条 shall"）

## R — 原文 (Reading)

> "对过程的审核可从两方面人手：
> （1）过程是否到位。对于IS()/IEC27001的相关条款的关键点上所要求的过程，组织实际建立的ISMS必须要有相应的过程。
> （2）过程是否符合要求。IS)/IEC27001标准对每个ISMS过程，都有具体的和明确的要求（"shall"要求）。组织的ISMS必须满足这些要求。"
>
> — 原作者、原作者，原始方法论来源第5章 5.2.1 审核的总方法（source.txt L2992–2998，OCR"人手/IS()/IS)/"原样保留）

## I — 方法论骨架 (Interpretation)

"符合"这个词里藏着两个完全不同的问题：**该有的东西有没有**（存在性），和**有的东西够不够好**（符合性）。混在一起查，第一个问题会被第二个吞掉——对着细则逐条勾选时，一个压根没建过程的组织反而可能在"文件"上拿分。

两步法把顺序固定下来：

1. **第一步存在性**：把准则拆成"过程要求"清单（每个关键点要求什么过程），逐项问"组织有没有建这个过程/角色/阶段/机制"。没有 → 直接是体系要素缺失，重大的方向，根本走不到第二步。
2. **第二步符合性**：过程存在的前提下，逐条对照 shall（覆盖范围、执行方式、例外处理……），用四栏检查表配题取证。
3. **同构佐证**：第6章访谈分层"存在→正确→有效"是同一逻辑在证据侧的形态；反过来，ISO9000 惯性审法（直接查文件/做没做到）正是被本法矫正的病灶。

## A1 — 书中的应用 (Past Application)

### 案例 1: 全书检查表的展开格式（第5章 5.3–5.7）
- **问题**: 逐条款检查表按什么骨架展开？
- **方法论的使用**: 全部条款检查表按"是否有该过程→过程是否合规"两栏展开：先判过程到位，再逐 shall 配题。第5章 26 页的逐条款审核均由此展开。
- **结论**: 两步法不是原则口号，而是第5章全部检查表的物理结构。
- **结果**: 审核员照表执行即自然遵守两步顺序，防漏判。

### 案例 2: ISO9000 惯性审法的对位矫正（前言，cs02/ce01）
- **问题**: 为什么按质量管理惯性审 ISMS 会出问题？
- **方法论的使用**: 前言指出按 ISO9000 惯性思路去审，不但不能客观评定，反而催生"庞大臃肿且与业务并不切合的高风险体系"——惯性审法跳存在性、直接做文件符合性，漏掉"没建过程"的组织，又逼出过度文件化。
- **结论**: 两步法是全书对"惯性审法"的结构性回答。
- **结果**: 与"过程不一定要用程序文件控制，凡标准要求要有的过程，组织要有相应的过程"（5.2.1 前文）共同防两种极端。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 内审按条款排计划：每条要求先查过程存在性再查合规细节。
2. 审 DevSecOps 流水线的密钥管理：第一步查有没有 secret scanning 这个过程本身。
3. 供应商对照 ISO/等保做差距分析（gap analysis）。
4. 标准换版自查：新增条款的过程先建起来没有（存在性优先于细节打磨）。

### 语言信号 (用户的话里出现这些就应激活)

- "这条要求怎么审？先查什么？"
- "过程到位是什么意思？" / "process in place"
- "gap analysis 怎么做才不漏？"
- "他们有文件但没流程，算符合吗？"（正是两步法的靶点）
- "先查存在性还是先查合规性？"

### 与相邻 skill 的区分

- 与 `isms-three-layer-evidence-chain`：三层取证是单个控制项的证据深度（文档→配置→运行）；本 skill 是条款符合性判定的总顺序——第二步取证时才用得上三层。
- 与 `isms-interview-tiering`：访谈分层"存在→正确→有效"是同一逻辑在访谈侧的形态；本 skill 在审核流程层，两者互为印证不互相替代。
- 与 `isms-four-column-checklist-design`：四栏表承载第二步的逐 shall 配题；第一步存在性判断发生在检查表执行之前/之中，不由表结构自动保证。

## E — 可执行步骤 (Execution)

1. **把准则拆成过程要求清单**：逐条款标注"要求什么过程"（如 8.2 纠正措施→纠正过程；6.1.3→处置过程）。
   - 完成标准: 条款-过程映射表，每条注明对应 shall/要求出处。
2. **逐项查存在性**：问"这个过程/角色/阶段/机制存在吗"，证据指向组织架构、流程定义、系统功能位。
   - 完成标准: 每项"存在/不存在"判定 + 证据指向。
   - 判停条件: 若不存在 → 按 isms-nonconformity-grading-loop 记体系要素缺失方向（重大候选），该条款不再走第二步逐条勾选，跳到下一条款。
3. **存在者进入符合性检查**：逐 shall 配检查题取证（用 isms-four-column-checklist-design 结构）。
   - 完成标准: 每条 shall 至少一题、答案二值化、答否附理由。
4. **汇总两步结论**：存在性缺失项与符合性缺陷项分开列示，分级开单。
   - 完成标准: 两栏汇总表，缺失项与缺陷项各有分级判定。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 纯技术控制验证（一次测试即证"会记录/会响应"）——测试证据直达结论，不必铺条款两步。
- 非管理体系对照（产品功能验收、配置基线核对）——对象不是"过程"。
- 一次性活动的检查（某次演练办没办）——那是事件取证，无过程存在性问题。

### 作者在书中警告的失败模式

- ce01/cs02：按 ISO9000 惯性思路审——直接跳文件符合性，漏存在性、催生臃肿体系。
- 用"有文件"冒充"有过程"：书中明示"有些过程不一定要用程序文件进行控制"——文件是载体不是过程本身，反之有文件无过程同样是假存在。

### 作者的盲点 / 时代局限

- **版本提示**：两步法本身与版本无关、永久可用；但书中条款框架基于 27001:2005 第 4–8 章，2013/2022 版已改为第 4–10 章结构（新增 6.1.3、6.2 目标、8 运行、10 改进等），条款-过程映射表必须按现行版本重建，照抄第5章检查表会审错依据。
- 存在性判定的灰色地带（过程"半建成"：有角色无职责、有机制无触发）书中无细分判据。
- 作者批判文件符合性，但主交付物仍是逐条检查表——检查表保证下限不保证上限（阶段 0 批判的最强反对意见）。

### 容易混淆的邻近方法论

- 通用 gap analysis 工具/模板：通常只做"现状 vs 要求"单层差集；本 skill 强制把"过程存在性"独立为第一步的顺序纪律。
- 成熟度评估（CMMI 式）：评的是过程能力等级；本 skill 只做存在+符合两级判定，不做分级度量。
