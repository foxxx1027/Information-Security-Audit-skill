# 攻击链裁剪：按升级路径的下一跳配置权限

## R — 原文 (Reading)

> "写入文件的技巧，经常被用于导出一个Web-shell，为攻击者的进一步攻击做铺垫。因此在设计数据库安全方案时，可以禁止普通数据库用户具备操作文件的权限。"（第7章 7.2.1）
> "使用高权限身份运行Apache的结果可能是灾难性的，它会带来两个可怕的后果：（1）当黑客入侵Web成功时，将直接获得一个高权限（比如root或admin）的shell"（第15章 15.2）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

"最小权限"作为口号没有可执行性——最小到什么程度？从哪开始砍？本方法给出操作顺序，把口号变成流程：

1. **先画链**：假设攻击者已拿到最低限度立足点（一个注入点、一个 webshell、一个被攻陷的容器），画出从立足点到最终目标（系统命令执行、域控、核心数据）的升级路径——每一跳靠什么能力成立？文件读写？UDF？挂载的令牌？root 身份？
2. **按跳裁剪**：对链条上每一跳，砍掉让它成立的那项能力/权限。砍的是"下一跳的原语"，不是泛泛地收缩全部权限——数据库账号砍文件读写与建 UDF 权限，Web 进程用专用低权身份，上传目录禁执行。
3. **验证链断**：裁剪后重放攻击链，确认在某一跳断掉——一个注入被降级为"只能读有限数据"，单点失陷不再放大为整机沦陷。

要点：链式配权天然给出砍多砍少的答案——砍到"业务必需能力之外、攻击链必经能力之内"的最小交集。砍多了业务断，砍少了链还通，画链让这个判断有依据。

## A1 — 书中的应用 (Past Application)

### 案例 1: SQL 注入→RCE 的升级链裁剪（第7章 7.2.1/7.3.4）
- **问题**: 注入已经发生，如何阻止它变成服务器沦陷？
- **方法论的使用**: 画链：注入 → LOAD_FILE/INTO OUTFILE 读写文件落 webshell，或 CREATE FUNCTION...SONAME 建 UDF 直接执行系统命令。在权限层砍掉这两跳：应用账户禁止文件操作与建 UDF，且不用 root/dbowner 连库、多应用共库各配独立账户。
- **结论**: 注入的危害上限由数据库账户权限决定；按下一跳配权，"一个注入"被降级为"只能读有限数据"。
- **结果**: 形成数据库侧最小权限基线（低权账户+独立账户+禁 UDF/文件），sqlmap 的 UDF 利用路径在正确配权下失效。

### 案例 2: Web 进程专用低权身份（第15章 15.2）
- **问题**: Apache/Tomcat 用什么身份运行？
- **方法论的使用**: 画链：Web 漏洞被利用 → 进程身份即所得权限。以 root 运行时立足点直接等于最高权限 shell；用专用低权账户（无登录 shell）运行，立足点被锁在低权层。
- **结论**: 高权限运行的两大灾难——入侵即提权、自身故障爆炸半径大——都源于身份与必要能力不匹配。
- **结果**: 建 user/group 专门跑 Web 的规则确立；Tomcat 配 root 导致 webshell 即 root 的反例佐证。

### 案例 3: 上传目录禁执行——砍掉"可执行"这一环（第8章）
- **问题**: 文件已能上传（前三条件中"可解析"如何破坏）？
- **方法论的使用**: webshell 成立三条件（可解析/可访问/内容未改写）中，砍"可解析"这一跳：Web 容器去掉上传目录执行权限，存储与执行分离（放 Web 根外/独立域名）。
- **结论**: 只要容器无法解析该目录，即使脚本被上传服务器也不受影响——作者点名"至关重要"的一条。
- **结果**: 与数据库权限裁剪、进程身份降权构成同一方法在三个层的实例：都按攻击链下一跳砍能力。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 数据库账户权限设计：应用连库账号、报表账号、运维账号该给什么。
2. 服务器/中间件加固：进程运行身份、目录权限、sudo 策略。
3. 容器与 K8s 权限配置：ServiceAccount、挂载、capability、NetworkPolicy。
4. 入侵演练/红队复盘后设计"失陷降损"措施。
5. 评审权限申请：这个服务"需要 root/管理员"的诉求是否成立。

### 语言信号 (用户的话里出现这些就应激活)

- "数据库账号要给哪些权限 / db account privileges"
- "程序被入侵后攻击者能干什么 / blast radius"
- "最小权限怎么落地 / least privilege in practice"
- "容器提权路径 / container escape path"
- "这个服务必须要 root 吗 / does it need root"

### 与相邻 skill 的区分

- 与 `whitehat-attack-surface-reduction` 的区别：那边减少**入口数量**（能被打的机会，横向减面）；本 skill 假设入口已被突破，纵向砍**链上每一跳的能力**。先减面、再对保留入口做链式配权，两者先后衔接。
- 与 `whitehat-defense-in-depth` 的区别：纵深防御讲多层层配合的整体结构；本 skill 给出其中"权限层"的具体操作法——画链、按跳砍、验证链断，是纵深思想在权限维度的落地工具。
- 与 `whitehat-trust-boundary` 的区别：那边定检查点位置；本 skill 定"边界内主体被攻陷后还能走多远"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **确立立足点假设与目标**
   - 完成标准: 明确起始 compromise 场景（如应用存在注入/容器内 RCE/员工账户被盗）与攻击者最终目标（系统命令、横向到其他服务、核心数据），写下攻击者画像。

2. **画出升级路径**
   - 完成标准: 从立足点到目标逐跳列出"当前能力 → 下一跳所需能力 → 获得的新能力"（如：SQL 注入 → 文件读写权限 → 落 webshell → 进程身份权限 → 系统 shell），每跳标注所依赖的具体权限/配置/挂载。多条路径并列时全部画出。
   - 判停条件: 若立足点即目标（单层系统、无任何中间能力可依赖），则无链可裁，转常规修复与减面。

3. **逐跳评估裁剪项**
   - 完成标准: 对每一跳回答：砍掉该能力的业务代价（谁还在用它？）、保留它的攻击收益（这一跳是否必经）；产出"可砍/可限/必须保留"三级清单，砍到业务必需能力之外、攻击链必经能力之内的交集。

4. **实施并验证链断**
   - 完成标准: 裁剪生效后重放原升级路径，确认至少一跳被阻断（复测注入只能读有限数据/容器内拿不到宿主凭证）；业务功能回归通过，无误伤。

5. **记录残余路径并定义重盘触发器**
   - 完成标准: 未裁剪的路径（因业务必须保留的能力）与补偿控制明确记录；新增能力类型（新挂载、新插件、新集成）触发重新画链。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 入口还没收敛就深挖权限——先用攻击面收敛减入口，否则链画不完（入口无穷多）；本 skill处理"保留入口被突破后"的问题。
- 无攻击者模型的一次性脚本/个人环境——画链成本大于收益，直接套常规加固基线即可。
- 权限修复不能替代漏洞修复：链式配权是降损（把 RCE 降为数据读取），被砍断的那跳之前的漏洞仍然存在，仍须修。

### 作者在书中警告的失败模式

- 用 root/dbowner 连库、root 跑 Web——入侵即最高权限，单点失陷放大为整机沦陷。
- 多应用共用一个数据库高权账户——爆炸半径无隔离，一家被注入全体遭殃。
- 上传目录可执行——"传上去了"直接变"执行了"，缺的只是权限层的这一刀。

### 作者的盲点 / 时代局限

- 书中链条以 LAMP 时代为主（UDF、INTO OUTFILE、Apache 身份）；今日链条换载体：容器挂载的 ServiceAccount token→K8s API 提权→横向、CI 凭证→供应链、云 IAM 角色链（角色假设链）——"画链→按跳砍→验证链断"流程直接迁移（verified V2 已按 K8s 场景外推验证）。
- 未给出自动化画链工具（攻击图）概念；今日可结合 CIS 基准与攻击路径工具半自动化。
- 对"业务必需能力"与"攻击必经能力"冲突时的取舍（如业务确实需要文件导出）只给了原则，需结合纵深防御设计补偿控制。

### 容易混淆的邻近方法论

- 攻击面收敛（入口数量 vs 链内权限——先减面后裁链）。
- 纵深防御（整体分层结构 vs 权限层的具体操作法）。
- 根因修复纪律（消除漏洞 vs 限制漏洞后果——一个治存在性，一个治爆炸半径，组合使用）。
