# 攻击面收敛：删除 > 禁用 > 加固

## R — 原文 (Reading)

> "减小攻击面包括关闭或限制对系统服务的访问，应用'最小权限原则'，以及尽可能地进行分层防御。"（第17章）
> "如果不是特别需要，建议删除FCKEditor的文件上传代码，一般情况下也用不到它。"（第8章）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

这套方法与威胁建模互补但问题不同：威胁建模问"**会被怎么打**"，攻击面管理问"**能被打的机会有多少**"——通过直接减少可利用机会降低风险。

核心是一条处置优先级，**次序不可颠倒**：

1. **删除**：业务用不到的功能直接删掉/物理移除（第三方组件自带的上传、管理台、示例页、多余插件）。功能不存在，对应漏洞类别整体消失，比任何修补都省力。
2. **禁用/限制**：删不掉的关掉或限制（默认不监听、只绑内网、白名单放行）。
3. **加固**：必须保留的才进入加固环节（改默认口令、最小权限账户、升级）。

三条配套规则：

- 管理面默认不可达：默认配置的管理后台（jBoss JMX-Console、Tomcat Manager）即便配了口令仍建议删除——暴力破解可绕过，后台存在本身就是攻击面，"没人知道地址"不是保护。
- 组件按最小权限裁剪：装得越多攻击面越大（Apache 高危集中在非默认 Module），只保留业务必需。
- **新增能力类型即重盘**：每引入一种新的可执行/可发请求的资源类型（富脚本、wasm、模板宏）或新存储介质，都要重做攻击面评估——新能力=新攻击面。

## A1 — 书中的应用 (Past Application)

### 案例 1: FCKEditor 文件上传（第8章 8.1.1）
- **问题**: 富文本编辑器自带的文件上传功能用黑名单限制后缀，仍被 php2、inc、asa、cer 等未列后缀绕过，上传目录又被容器解析成漏洞。
- **方法论的使用**: 集成第三方组件时先做功能清点——上传功能业务上根本用不到，与其修补黑名单不如删除上传代码。
- **结论**: 黑名单天然不完备；删除用不到的功能让这一漏洞类别整体消失。
- **结果**: 确立"用不到的模块物理删除而非停用"的规则，成为攻击面收敛的样板。

### 案例 2: jBoss/Tomcat 管理台（第15章 15.4）
- **问题**: jBoss 默认 8080 开放 JMX-Console 且无任何认证（addURL() 部署恶意 war 即得命令执行）；Tomcat 低权用户配 manager 角色沿用默认口令，上传 war 即拿 shell。
- **方法论的使用**: 防护顺序排优先级——删除 jmx-console.war/web-console.war 等用不到的管理面 > 强密码+不公网开放 > 仅做加固。
- **结论**: 即便配了口令，管理台存在本身仍是攻击面（可暴力破解），留着"得不偿失"；管理接口应默认不可达、显式开启、最小授权。
- **结果**: 形成管理面处置次序；Google hacking（inurl:jmx-console）批量命中这类暴露后台的事实佐证了风险规模。

### 案例 3: Apache Module 最小权限裁剪（第15章 15.2）
- **问题**: Web Server 装了一大堆组件，哪些该留？
- **方法论的使用**: 统计发现高危漏洞集中于默认未安装或未启用的 Module——装得越多攻击面越大；按最小权限只保留业务必需。
- **结论**: 安装时做减法：用不到的不装、装了的不启用。
- **结果**: 与"删除 FCKEditor 上传""删除管理台"构成同一条先减面再防护的实践线。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 服务器/中间件/NAS/容器镜像加固：面对一排默认开启的服务、端口、管理界面不知从哪下手。
2. 集成第三方组件后，发现它自带一堆自己用不到的功能（上传、调试端点、示例页）。
3. 新功能/API 上线前的暴露面评审。
4. 处置"上传类/可执行资源类"能力的策略制定（禁止自定义可执行文件）。

### 语言信号 (用户的话里出现这些就应激活)

- "这个服务用不到，要不要关掉 / disable unnecessary services"
- "默认开了好多端口/服务，怎么清理 / default services cleanup"
- "管理后台暴露在公网安全吗 / admin panel exposed"
- "怎么做系统加固/最小化 / hardening baseline / server minimization"
- "怎么减少攻击面 / reduce attack surface"

### 与相邻 skill 的区分

- 与 `whitehat-attack-chain-pruning` 的区别：本 skill 减少**入口数量**（面，横向减）；那边画升级路径后砍**链上关键跳的权限**（链，纵深砍）。先减面、再对保留入口做链式配权。
- 与 `whitehat-whitelist-first` 的区别：白名单是输入筛选策略（对进来的数据选白名单）；本 skill 是功能存废决策（让入口根本不存在）。
- 与 `whitehat-trust-boundary`的区别：那边划信任域定检查位置；本 skill 直接收缩暴露边界。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点功能面**
   - 完成标准: 服务、端口、接口、组件、管理台、示例页、上传点全量清单，逐项标注"业务是否用到"——由业务方确认，不是安全方猜测。

2. **按删除>禁用>加固排序处置**
   - 完成标准: 用不到的已删除或物理不可达；无法删除的禁用/限内网/默认关闭；保留的进入加固（改默认口令、专用低权账户、升级版本）。
   - 判停条件: 业务方声称"未来可能要用" → 按"现在不用=先关"处理，同时记录重开流程与审批人，不因"未来"保留现役攻击面。

3. **管理面专项**
   - 完成标准: 所有管理接口默认不可达、需显式开启，且配强认证+来源限制；逐一核对默认口令与角色分配。

4. **第三方组件清点**
   - 完成标准: 引入的每个第三方组件列出其自带功能，非业务必需的上传/调试/示例功能已删除；组件有版本台账。

5. **定义重盘触发器**
   - 完成标准: 新增服务、新增可执行/可发请求的资源类型（脚本、wasm、模板宏）、新存储介质接入时触发重新盘点，写入变更管理流程。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 删除不可逆且业务确实依赖的功能——那是"找等价安全实现"的问题（安全是产品特性框架），不是减面问题。
- 必须保留的入口怎么纵深设防——减面之后的事，交给攻击链裁剪与纵深防御。
- 不要用它替代补丁管理：减面降低概率，不修复已保留组件的已知漏洞。

### 作者在书中警告的失败模式

- "没人知道地址"式的隐藏管理面不是保护——默认配置的管理后台必须先删除或加固再上线。
- 给黑名单打补丁追着新后缀跑——不如删除上传功能本身（FCKEditor 教训）。
- 装全组件求全——高危恰恰集中在非必需 Module。

### 作者的盲点 / 时代局限

- 案例深度绑定 2014 年技术：FCKEditor、jBoss/Tomcat 默认配置、Apache Module、Flash（禁止上传自定义 swf 的建议随 Flash EOL 失效，但"禁止用户上传可执行资源"原则迁移到 wasm/脚本宏依然成立）。
- 未覆盖云原生攻击面：容器镜像层、K8s CRD/RBAC、Serverless 事件源、sidecar 接口、对象存储暴露——"删除>禁用>加固"次序与"新增能力类型即重盘"可直接迁移到这些新面。
- 书中无暴露面持续管理（EM/ASM 类工具与外部攻击面发现）概念，今日减面需要内部盘点+外部视角双轨。

### 容易混淆的邻近方法论

- 攻击链裁剪（面 vs 链）。
- 白名单优先（数据筛选 vs 功能存废）。
- 纵深防御（多层配合 vs 入口收缩）。
