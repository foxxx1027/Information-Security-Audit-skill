# 业务逻辑漏洞的通用审查问法（四问）

## R — 原文 (Reading)

> "当他发现有人出价更高时，就去恶意登录这个用户的账户：当登录失败次数达到5次时，该账户就被系统锁定。"（第16章 16.2）
> "审核通过后的信息，如果被用户重新编辑了，不会再次进行审核，也会直接发送到电视新闻的滚动条中"（第16章 16.2）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

业务逻辑漏洞（越权、流程绕过、状态不一致）与注入类不同：没有 payload 特征、扫描器看不见、与业务耦合极紧，"花样百出难以归纳"。但把它拆开看，绝大多数落在四个固定问题的答案里：

1. **能否替他人触发？** 列出所有状态变更的触发条件，问"攻击者能否代替受害者触发它"。惩罚性控制（锁定、限速、风控处置）尤其危险——它们本身是"对账户施加负面影响"的接口，被第三方滥用就是对任意用户的拒绝服务/业务打击。
2. **变更是否覆盖全部关联体系？** 一个用户身份往往对应多个凭据/账户体系（主站、IM、绑定三方、多端）。改密、冻结、踢下线若只作用于其一，处置形同虚设。
3. **校验挂在所有状态边上了吗？** 把业务画成状态机，审核/校验若只挂在首次提交那条边上，编辑、回退、复制、退款等旁路就能带着未检内容进入受信状态。
4. **敏感步骤重新认证了吗？** 改密、改绑、提现等操作不能只凭既有登录态——否则被盗会话一步洗白。

四问的用法：先画状态机与关联体系清单，逐问过，每问直接产出测试用例。

## A1 — 书中的应用 (Past Application)

### 案例 1: 恶意锁定竞拍对手（第16章 16.2.2）
- **问题**: "失败 5 次锁账户 1 小时"的抗爆破控制，反而成了攻击武器。
- **方法论的使用**: 第一问展开：锁定是"任何人都能对任意账户触发"的状态变更——黑客对出价更高的对手恶意试错 5 次触发锁定，订单系统作废其出价，低价拍得。
- **结论**: 惩罚性控制必须审查"能否被第三方对受害者主动触发"；修复是锁"来自该 IP 的请求"而非锁账户，并对已认定恶意的 IP 追加处罚。
- **结果**: 若页面暴露用户 ID，脚本可遍历锁定全站用户——该案同时揭示控制被反制为 DoS 的放大路径。

### 案例 2: 双账户体系改密不同步（第16章 16.2.1）
- **问题**: 网站账户与 IM 账户绑定，客服改密、改密保、踢下线后，攻击者仍凭旧 IM 账户登录，与客服反复互踢。
- **方法论的使用**: 第二问展开：画出"一个用户身份涉及的全部凭据体系"清单，逐一确认变更操作是否级联——结果全部只作用于网站侧。
- **结论**: 凭据变更未覆盖关联体系，一切处置措施形同虚设；应急止损也必须以这张清单为依据。
- **结果**: 确立"关联体系清单化"的审查动作，联合登录、三方绑定、多端同步列为高发区。

### 案例 3: 审核后再编辑不复审（第16章 16.2.3）
- **问题**: 电视台网站网友提交天气信息，人工审核通过后被重新编辑的内容绕过审核直接播出，被用来投放垃圾信息。
- **方法论的使用**: 第三问展开：画出状态机——审核校验只挂在"首次提交"这条转移边上，"编辑已审核内容"是一条未设防的转移边，直通受信状态（播出）。
- **结论**: 校验必须挂在所有进入受信状态的转移边上；修复是编辑动作重新触发审核（代价是人力增加，如实记录这一权衡）。
- **结果**: 第四案（支付订单号不绑定下单人身份）同法可解——跨体系唯一标识缺少与身份的绑定关系，四问框架全部覆盖。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新业务功能（支付、订单、代付、审核流、抽奖、邀请）上线前的安全设计评审。
2. 渗透测试/安全测试计划中为业务逻辑部分设计用例。
3. 复盘一个已发生的业务逻辑漏洞，找同类问题。
4. 设计账户体系/联合登录/多端同步的凭据变更逻辑。
5. 风控与惩罚策略（锁定、限频、黑名单）发布前评估被反制的风险。

### 语言信号 (用户的话里出现这些就应激活)

- "这个业务流程有没有漏洞 / business logic flaw"
- "逻辑漏洞怎么测 / how to test logic vulnerabilities"
- "订单/代付/审核流程怎么审 / review checkout workflow"
- "状态机/流程绕过 / state machine bypass / workflow abuse"
- "改 id 就能看到别人的订单 / IDOR / horizontal privilege"

### 与相邻 skill 的区分

- 与 `whitehat-security-assessment` 的区别：四阶段是完整评估的流程框架（资产→威胁→风险→方案）；本 skill 是其中威胁分析环节针对业务逻辑的专项问法资产——四问可嵌入四阶段的威胁分析步使用。
- 与 `whitehat-tool-vs-manual-boundary` 的区别：那边论证业务逻辑必须人工；本 skill 给人工检查者具体问什么——一个是分工论证，一个是作业工具。
- 与 `whitehat-credential-rotation-on-state-change` 的区别：那边管会话/一次性凭据的技术纪律（轮换/作废/原子）；本技能第四问（重新认证）引用该纪律，但覆盖面是整个业务流程的状态与触发逻辑。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画出状态机与关联体系**
   - 完成标准: 目标功能的状态机图（状态节点 + 全部转移边，含编辑/回退/取消/退款等"次要"边）与"一个用户身份涉及的全部凭据/账户体系"清单完成；跨体系标识（订单号、流水号）标注其绑定关系。
   - 判停条件: 若功能为无状态的单一操作（无状态变更、无凭据、无多体系），四问无从展开，转技术类漏洞检查。

2. **第一问：替他人触发**
   - 完成标准: 列出全部状态变更接口，逐个回答"触发者与受害者是否同一主体"；惩罚性控制（锁定/限速/处置）全部单列并给出第三方触发路径（含批量遍历的放大评估）。

3. **第二问：关联体系覆盖**
   - 完成标准: 对改密/改绑/冻结/踢下线等处置操作，逐一核对是否级联到清单中的全部体系；未覆盖项列出。

4. **第三问：状态边全覆盖**
   - 完成标准: 对每条进入受信状态的转移边核对校验存在性，未设防边（编辑后不复审、改单后不复核、退款后不回滚标记）逐条标出。

5. **第四问：敏感步骤重认证 + 用例固化**
   - 完成标准: 改变凭据/安全设置/资金的操作确认前置二次认证且因子未被污染；四问的全部发现转化为具体测试用例（每问至少覆盖每条可疑边），修复项各归入对应修复模式。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 注入/XSS/上传等技术类漏洞——有明确成因模型与专项方法，四问不覆盖它们。
- 权限模型的整体设计（RBAC 角色体系、ACL 建模）——四问里只处理"水平越权"的检查面，建模另有方法。
- 与用户/资金无关的纯内部算法问题（性能、正确性）——非安全审计对象。

### 作者在书中警告的失败模式

- 惩罚性控制无差别对账户生效——被第三方反制为打击工具（锁定对手、遍历锁全站）。
- 凭据变更只改一处——关联体系留旧凭据，处置与客服流程全部空转。
- 校验只挂首次提交——旁路编辑直通受信状态；"审核过"是内容状态不是永久豁免。
- 跨平台唯一标识不绑定身份——银行只知订单已付不知谁付，钓鱼站借真实支付表单收网。

### 作者的盲点 / 时代局限

- 四问从电商/社区业务提炼；资金类强对抗场景（营销补贴、虚拟货币、直播打赏）与复杂多方协议（分账、担保交易）需要在此基础上扩展问法（如"同一标识能否跨主体复用""回滚是否对称"）。
- 书中断言业务逻辑漏洞"难以归纳、只能靠经验"——四问本身已是反例，但自动化（基于状态机的模糊测试、业务不变量断言）在书中缺席，今日可作为用例固化的工程增强。
- 未覆盖并发触发的竞态问题（同一边同时转移），可作为第三问的补充维度。

### 容易混淆的邻近方法论

- 安全评估四阶段（流程框架 vs 业务逻辑专项问法）。
- 凭证状态跃迁纪律（第四问的会话层展开 vs 全流程四问）。
- 需求分解法（把口号变具体威胁 vs 对具体威胁的固定审查——先后衔接）。
