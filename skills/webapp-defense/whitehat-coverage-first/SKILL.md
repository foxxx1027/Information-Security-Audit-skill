# 白帽求全：覆盖率优先的失败模型

## R — 原文 (Reading)

> "对于黑帽子来说，只要能够找到系统的一个弱点，就可以达到入侵系统的目的；而对于白帽子来说，必须找到系统的所有弱点，不能有遗漏。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.2 黑帽子，白帽子

---

## I — 方法论骨架 (Interpretation)

攻防双方的胜负条件不对称：攻击者命中一个弱点就赢，防守者漏掉一个就输。这个结构差异决定了两边的思维方式和作业排序都不能照搬：

- 攻击方工作是有选择、微观的——挑最软的点打。
- 防守方工作必须全面、宏观——失败模式是"漏"而不是"不够深"。

由此推出一条反直觉的排序：**覆盖率优先于深度**。先保证对象清单（资产、项目、攻击面、数据流）被完整覆盖，再对高风险点深挖。三件事随之改变：

1. **评估产出必须双栏**："发现的问题"与"没看到的范围"并列呈现。一份只写"未发现问题"的报告隐瞒了覆盖面信息——未发现可能是没找。
2. **流程靠制度求全而非自觉**：SDL 绑定立项环节，让边角小项目无法绕过——出事的常是没人知道的小项目，不是防护最弱的大项目。
3. **扫描盲区要申报**：编译产物、新存储介质、第三方组件等工具看不到的范围，主动列为"未覆盖"而不是默认安全。

这也是 STRIDE/DREAD 等"求全工具"存在的动机：模型的价值不在聪明，而在可核对的完整性。

## A1 — 书中的应用 (Past Application)

### 案例 1: SDL 准则二——立项制度保证全覆盖（第 17 章）
- **问题**: 公司变大后多部门多项目并行，安全团队甚至不知道某些小项目已上线。
- **方法论的使用**: 按"漏即败"排序——最糟糕的不是流程不严，而是"边边角角的小项目发布后安全团队都不知道，最后导致安全事件"。
- **结论**: 把 SDL 绑定到集中管理的立项环节，让"立项必经安全"成为制度而非自愿申请；立项期介入还留出更多反应时间。
- **结果**: 覆盖率指标（多少项目走完流程、多少资产在扫描范围）成为安全成熟度的第一度量，先于技术深度指标。

### 案例 2: 智取华山——威胁分析"只有一条路"的代价（第 1 章 1.6.2）
- **问题**: 国民党守华山把重兵布在"自古华山一条道"的正路，为何全部部署作废。
- **方法论的使用**: 用战例说明"漏"的结构性代价：守方相信其他路不存在（攻击面假设不完整），侦察小队从悬崖爬上来，所有针对正路的防御瞬间失效。
- **结论**: 威胁分析必须头脑风暴各种可能攻击面求全，遗漏一条即整体失守——这正是 STRIDE 兜底的价值。
- **结果**: 该案例成为全书威胁建模求全原则的开篇论据，随后用 DREAD 对已列全的路径排序。

### 案例 3: 编译产物是扫描盲区（第 3 章）
- **问题**: 源码扫描看着干净，为何上线后仍出 XSS。
- **方法论的使用**: 把"swf 等编译后文件不在源码扫描可见范围"显式列为资产覆盖盲区——工具结论只对它看过的范围负责。
- **结论**: 覆盖面外的东西要么换工具（反编译）、要么人工补，要么在报告中申报为未覆盖。
- **结果**: "扫描绿灯≠安全"成为评估结论的固定校验项。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到渗透测试/红队报告写着"未发现高危问题"，要判断可信度并决定是否追加投入。
2. 制定安全团队的工作计划，纠结"深挖一个系统"还是"先铺开覆盖全部资产"。
3. 推动安全流程（SDL、评审、扫描）落地，担心有项目/团队绕过。
4. 盘点资产/数据流/攻击面，为评估或采购安全产品做准备。
5. 向管理层汇报安全状况，需要诚实的"已知/未覆盖"结构。

### 语言信号 (用户的话里出现这些就应激活)

- "渗透测试做完了，没发现问题，可以上线吗？"
- "先集中火力深挖核心系统，其他以后再说？"
- "怎么知道我们还有多少资产没纳入扫描？"
- "安全团队连这个项目上线都不知道。"
- "pentest came back clean / does zero findings mean we're secure / how to prove coverage"

### 与相邻 skill 的区分

- 与 `whitehat-security-assessment` 的区别: 四阶段评估是"怎么评"的流程骨架；本 skill 是其上游动机与排序纪律——为什么威胁分析必须求全、为什么先铺覆盖再深挖。评估流程里的资产清点阶段直接消费本 skill 的产出。
- 与 `whitehat-tool-vs-manual-boundary` 的区别: 那个裁决"工具与人怎么分工"；本 skill 裁决"结论如何随覆盖面表述"——扫描器绿灯在分工上没问题，但按本 skill 必须附未覆盖面申报。
- 与 `whitehat-resource-quota-audit` 的区别: 那个是对单类问题（资源滥用）的穷举式审计动作；本 skill 是一切求全式工作的总排序原则。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **建对象清单**：列出评估范围内的全部对象——项目、资产（域名/服务/存储/密钥）、数据流、第三方依赖、账号体系。
   - 完成标准: 清单有明确来源（立项记录、CMDB、网络扫描、访谈），且每项有 owner；能回答"怎么证明没漏"。
2. **标注覆盖状态**：对每个对象标注已覆盖（做过什么检查）/未覆盖/部分覆盖，以及工具可见性（源码/二进制/配置/运行时）。
   - 完成标准: 三态标注完整，未覆盖项写明原因与工具盲区类型。
   - 判停条件: 若清单本身无法闭合（不知道有哪些资产），先执行资产发现（扫描+立项核对+访谈），拿不到清单前不接受"未发现问题"类结论。
3. **双栏呈现结论**：报告/汇报把"发现的问题（按风险排序）"与"未覆盖面（含理由）"并列，未覆盖部分不因无发现而隐去。
   - 完成标准: 读者能直接看到"结论的边界在哪里"。
4. **按覆盖率排投入**：优先补覆盖缺口（把未覆盖对象纳入流程/扫描），再对已覆盖对象做深度。
   - 完成标准: 排期表先列覆盖动作后列深挖动作，附理由（漏即败）。
5. **制度化防绕过**：把覆盖动作绑定到不可绕过的流程节点（立项、发布、开仓），设置覆盖率指标并周期复核。
   - 完成标准: 有可度量指标（如"新项目 100% 过安全评审"）与复核周期；边角对象的绕过路径被堵住。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已锁定单个对象/单条漏洞的深度分析——进入深挖阶段后，本 skill 的排序纪律不再指导具体动作。
- 攻击方视角的工作（红队路径规划）——黑帽"有一即胜"，选择性思维反而是优势，套用求全会拖慢打击。
- 无限求全：覆盖以对象清单闭合为目标，不追求对所有威胁无限枚举——"彗星撞机房"式超低概率场景按成本排除。

### 作者在书中警告的失败模式

- "未发现问题"被当成"没有问题"：红队是黑帽思维，找不到≠不存在；结论必须绑定覆盖证据。
- 流程只覆盖大项目：小项目私上线击穿流程（第 18 章），安全事件复盘常发现原因并不复杂，只是发生在被忽视的角落。
- 扫描工具的可见范围被高估：编译产物、框架内部、业务逻辑都在可见范围外——"模型是死人是活的"，覆盖的最后一公里靠人。

### 作者的盲点 / 时代局限

- 大厂语境（集中立项、专职安全团队）浓厚，对无立项流程的小团队/开源项目，"绑定立项"需要替换为 CI 门禁、开仓钩子等自动触发点。
- 未讨论云原生/影子 IT 时代的资产发现难度（API、Serverless、SaaS 集成使清单闭合远比 2014 年难），资产清单的方法需现代化。

### 容易混淆的邻近方法论

- 风险排序（DREAD）：求全解决"列没列全"，打分解决"先修哪个"——顺序不能倒：对不完整的清单打分是把资源精确地花在错误的问题上。
- 深度防御：那是"单点失守后还有多层"的结构补救；本 skill 是"别漏掉对象"的清单纪律——两者互补，纵深不能成为漏盘资产的理由。
