# 凭证状态跃迁纪律：质变即轮换，一次性即作废

## R — 原文 (Reading)

> "解决Session Fixation的正确做法是，在登录完成后，重写SessionID。"（第9章 9.5）
> "因为验证码消耗掉后SessionID未更新，导致使用原有的SessionID可以一直重复提交同一个验证码。"（第13章 13.3）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

凭证的效力依附于它签发时刻的安全状态。状态一变，旧凭证就成了"过期产权"：它可能被攻击者提前拿到（预置给受害者），也可能被重复出示（重放）。两个不同漏洞族指向同一条纪律：

1. **质变即轮换**：会话的安全等级发生跃迁时——匿名变登录、普通变管理员、旧密变新密——必须换发新的会话/凭证标识。否则攻击者事先植入的旧标识随受害者一起"升级"，等于替攻击者登录。判断"卖车不换锁"：车换了主人，锁必须换。
2. **一次性即作废，且原子**：验证码、授权码、nonce、重置链接这类"只能用一次"的凭据，成功消费后必须立即失效；失效动作与业务状态更新必须是同一个原子操作，否则"消费了但没作废"的窗口就是重放通道。

审计不问"有没有验证码/token"，而是列出系统里全部状态跃迁点和全部一次性凭据，逐项核对轮换与作废是否存在、是否原子。

## A1 — 书中的应用 (Past Application)

### 案例 1: discuz 7.2 WAP 版 Session Fixation（第9章 9.5）
- **问题**: WAP 版把 sid 放在 URL 中传递，且用户登录完成后 sid 不变。
- **方法论的使用**: 识别状态跃迁点（匿名→已登录）未轮换凭证：攻击者先构造含自己 sid 的链接，诱使受害者点击并登录。
- **结论**: 登录前后 SessionID 不变使预置的标识自动升级为已认证会话——"卖车不换锁"。
- **结果**: 确立"登录完成后必须重写 SessionID"的修复规则；书中同时指出 sid 进 URL 还会随 Referer 外泄，双重违反凭证纪律。

### 案例 2: 验证码消费后不作废，无限重放（第13章 13.3）
- **问题**: 防爆破验证码校验成功后，Session 中保存的验证码明文不清空、SessionID 也不更新。
- **方法论的使用**: 审计一次性凭据的作废机制：同一 Session 可无限重复提交同一个验证码，防自动化效果归零。
- **结论**: "消费即失效"是所有防重放设计的最小要求；修补只需一句 captcha_stored=""，并同时更新 session_id。
- **结果**: 漏洞与修复伪代码都固化进书，成为"一次性凭据审计三点"（只验一次/失败也作废/有期限与次数上限）的样板。

### 案例 3: 改密不验当前密码，被盗会话完成洗白（第16章 16.2.4）
- **问题**: 修改密码的功能不要求提供当前密码，仅凭登录态即可改密。
- **方法论的使用**: 识别"凭证变更"这一敏感跃迁：会话被盗后，攻击者借该功能改密把受害者永久锁在门外——旧信任（登录态）不应有权制造新信任（新密码）。
- **结论**: 凡改变凭证/安全设置的操作必须在既有信任之上重新认证，且认证因子须是攻击者尚未掌握的。
- **结果**: 与前两案共同构成"状态质变时刻的凭证纪律"：登录轮换、消费作废、变更重认证三条互相补位。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计登录/注册/找回密码流程：登录成功后要做什么、重置链接如何生效与失效。
2. 接入或评审 OAuth/OpenID 授权码流程：code 换 token 环节的作废与绑定。
3. 验证码、短信码、一次性密码（OTP）的实现与测试。
4. 审计既有系统会话管理：检查登录、提权、改密、改绑代码路径里有没有轮换调用。
5. API 设计时决定 token 有效期、刷新机制与重放防护。

### 语言信号 (用户的话里出现这些就应激活)

- "登录成功后 session 要重新生成吗 / session regenerate after login"
- "验证码为什么可以重复用 / captcha reuse replay"
- "code 换 token 之后 code 还能用吗 / OAuth code one-time"
- "改密码要不要输入当前密码 / re-authentication for password change"
- "一次性链接/nonce 怎么防重放 / one-time token replay protection"

### 与相邻 skill 的区分

- 与 `whitehat-business-logic-four-questions` 的区别：四问里"敏感步骤是否重新认证"只是本 skill 纪律之一；本 skill 提供完整的跃迁点/一次性凭据清单化审计流程，覆盖轮换、作废、原子性三个维度。
- 与 `whitehat-signal-reliability` 的区别：那边裁决"客户端可控的信号能否作为安全边界"；本 skill 管的是凭证本身的生命周期纪律（何时签发、何时作废），两者在"会话寿命由服务端裁决"处衔接。
- 与 `whitehat-crypto-misuse-audit` 的区别：那边审 token 的加密与签名构造是否安全；本 skill 审 token 的状态语义（一次性是否真的只有一次）——构造再安全，重放纪律缺失照样失守。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列出状态跃迁点清单**
   - 完成标准: 覆盖匿名→登录、登录→提权/切换角色、改密、改绑手机/邮箱、合并账户、找回密码重置——每个跃迁点对应代码路径可定位。

2. **列出一次性凭据清单**
   - 完成标准: 验证码、短信码、OAuth code、重置链接 token、nonce、防重放序列号等逐项列出，标注其存储位置与生效方式。

3. **逐项核对三条纪律**
   - 完成标准: 每个跃迁点回答"会话/凭证标识是否轮换"；每个一次性凭据回答"成功消费后是否立即作废"、"作废与状态更新是否原子（同事务/同请求内）"、"失败消费是否也作废或计数"。
   - 判停条件: 若系统为无状态凭证（如 JWT 无法服务端作废），停止逐项核对，转入步骤 4 的补偿设计评估——原纪律无法直接套用。

4. **对无状态/外部凭证设计补偿**
   - 完成标准: 短寿命 + 刷新令牌轮换 + 服务端吊销名单/版本号等补偿机制明确落地；敏感跃迁点改为换发新令牌而非沿用旧令牌。

5. **重放测试收尾**
   - 完成标准: 对每个一次性凭据实测二次提交被拒；对登录/改密路径确认旧凭证（旧 sid、旧 token、重放 code）在新状态下全部失效。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 凭证的生成随机性是否足够（能否被预测）——属密码学误用与不可预测性问题；本 skill 假设凭证本身随机，只管其状态纪律。
- 长期凭证（API key）的保管与轮换周期策略——那是密钥管理问题，不是"状态跃迁触发轮换"。
- 会话超时/绝对寿命策略设计——属"会话寿命裁决权在服务端"的信号可靠性问题。

### 作者在书中警告的失败模式

- 登录后不重写 SessionID——Session Fixation 成立，攻击者预置的标识随认证升级。
- 验证码消费后不作废——同 Session 无限重放，防自动化归零。
- 改密不验当前密码——被盗会话一步完成"洗白"，处置措施（踢下线、改密）全部失效。

### 作者的盲点 / 时代局限

- 成书于 OAuth 2.0/JWT 普及之前：授权码、刷新令牌、无状态 JWT 的跃迁与作废纪律书中未覆盖（verified 阶段已按 V2 外推：code 一次性作废且绑定客户端、换取成功换发新会话、code 不进 URL/日志）。
- 书中会话以 Cookie/URL 传 sid 为主，未讨论分布式会话与令牌版本号等现代实现；"轮换"在现代框架（session_regenerate_id、refresh token rotation）有现成原语，应优先使用而非自造。

### 容易混淆的邻近方法论

- 不可预测性原则（凭证猜不猜得到 vs 凭证还能不能用）。
- 密码学误用审计（构造安全 vs 状态语义安全）。
- 业务逻辑四问（重新认证是四问之一，本 skill 是其会话层的完整展开）。
