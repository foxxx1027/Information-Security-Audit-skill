# 跨域/跨上下文通道的枚举审计：SOP 之外逐条设防

## R — 原文 (Reading)

> "浏览器中的拖拽对象可以是一个链接，也可以是一段文字，还可以从一个窗口拖拽到另外一个窗口，因此拖拽是不受同源策略限制的。"（第5章 5.4）
> "（1）在必要时，可以在接收窗口验证Domain，甚至验证URL，以防止来自非法页面的消息。这实际上是在代码中实现一次同源策略的验证过程。"（第6章 6.2.2）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

同源策略只是浏览器隔离模型的一条主坝，不是全部。数据与消息还能从许多"侧门"跨过源边界：拖拽、跨窗口消息、跨源授权头、可加载不可读的标签通道、各类策略文件。每条侧门有自己的校验规则，且大多把安全责任交给接收端——门开不开由你决定，SOP 不替你把关。

审计方法因此不是"检查同源策略是否生效"，而是：

1. **枚举通道**：把目标运行时里所有能跨越信任边界传递数据/消息的机制列成清单，一条不漏。
2. **逐条验证接收端**：每条通道问三个问题——谁有权发（发送端如何限定）？接收端验了什么（来源校验强度）？内容去了哪（是否进 innerHTML/脚本/存储等危险去处）？
3. **新通道即新边界**：平台每加一种跨上下文机制，就要重新走一遍枚举。

漏掉一条通道，就等于在未设防的方向上假设了 SOP 保护——假设不存在的保护比没有保护更糟。

## A1 — 书中的应用 (Past Application)

### 案例 1: 拖拽劫持窃取 Gmail 邮件（第5章 5.4）
- **问题**: 点击劫持只能骗点击，能不能骗出数据？
- **方法论的使用**: 枚举 SOP 之外的通道，发现拖拽不受同源策略限制——诱使用户从隐藏 iframe 中把邮件内容拖进攻击者页面的隐藏 textarea。
- **结论**: 拖拽是一条独立的跨域数据通道，视觉欺骗从"诱导点击"升级为"诱导取数"。
- **结果**: 该 POC 使"跨域通道枚举"成为浏览器威胁建模的固定动作，拖拽与 postMessage、CORS 并列审计。

### 案例 2: postMessage 不验来源 + 信任消息内容（第6章 6.2.2）
- **问题**: postMessage 允许任意窗口发消息且不受 SOP 限制，开发者常直接消费消息。
- **方法论的使用**: 逐条验证接收端——不验证 origin 等于任何页面都能投递；消息内容写入 innerHTML 直接造成 DOM based XSS。
- **结论**: 通道的安全责任整体转移给接收方，接收端必须自行补一次同源校验（验 Domain/URL），内容按不可信输入处理（写 textContent 而非 innerHTML）。
- **结果**: 形成两条纪律并给出审计动作：搜 addEventListener('message') 处理函数，逐个核对 origin 校验与输出编码。

### 案例 3: 用 postMessage 突破 JS sandbox（第6章 6.2.2）
- **问题**: 研究者构造的 JS sandbox iframe 沙箱被认为可隔离不可信代码。
- **方法论的使用**: 枚举沙箱内可触达的跨窗口通道——被隔离代码仍可向父窗口 postMessage。
- **结论**: 跨窗口通道是沙箱逃逸面：只要沙箱内代码能触达一条未设防的跨上下文通道，隔离假设即被打破。
- **结果**: "新通道=新信任边界"得到反向验证：评估任何隔离机制都要枚举其内部可用的跨上下文通道。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 前端嵌入第三方内容/iframe（广告、小组件、支付页）或微前端架构下的跨应用通信设计。
2. 浏览器扩展、Electron/WebView 混合应用的安全模型评审。
3. 审查已有代码里的 window.postMessage / message 事件处理。
4. CORS/跨源策略配置评审之外的"还有没有别的通道"式追问。
5. 新平台/新运行时（小程序、Worker、沙箱环境）的隔离假设检验。

### 语言信号 (用户的话里出现这些就应激活)

- "postMessage 怎么用才安全 / postMessage security"
- "iframe 之间怎么传数据 / cross-frame communication"
- "同源策略管不管 X / does SOP cover X"
- "微前端消息传递安全吗 / micro-frontend messaging"
- "浏览器扩展的攻击面在哪 / browser extension attack surface"

### 与相邻 skill 的区分

- 与 `whitehat-trust-boundary` 的区别：那边画信任域、定检查位置（通用框架）；本 skill 提供浏览器/运行时场景的**通道清单**这一具体资产——先枚举侧门，再用信任边界方法逐门设防。
- 与 `whitehat-whitelist-first` 的区别：白名单管"允许什么值进来"；本 skill 先回答"一共有几扇门"——门没枚举全，白名单配得再严也会被侧门绕过。
- 与 `whitehat-parser-consistency-audit` 的区别：那边审"两端对同一数据的理解差异"；本 skill 审"数据走的通道本身是否在设防范围内"。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **枚举通道清单**
   - 完成标准: 针对目标平台列出全部跨域/跨上下文机制（Web：postMessage、拖拽、CORS、src 标签加载、storage 事件、WebSocket 跨源、导航/窗口引用；扩展：content script 注入、message passing、native messaging 等），每条标注数据流向与默认校验强度。
   - 判停条件: 若评估对象是纯服务端系统、无任何浏览器/运行时跨上下文交互，则本 skill 不适用，终止并说明。

2. **逐条三问验证**
   - 完成标准: 每条在用通道回答：①发送端是否被限定（origin 白名单是否精确、可否任意页面触发）②接收端验了什么（是否校验来源、缺失来源时行为）③内容流向哪里（是否进 innerHTML/eval/特权 API/存储）。

3. **对弱通道补防线**
   - 完成标准: 接收端补来源校验（精确到 origin/URL）、内容按不可信处理（结构化解析+安全写入）、特权操作对消息来源再授权；无法补强的通道关闭或降权。

4. **隔离假设复核**
   - 完成标准: 对沙箱/iframe/Worker 等隔离机制，枚举其内部代码可触达的跨上下文通道并逐条确认设防；确认"隔离"承诺不依赖未验证的 SOP 假设。

5. **文档化并定义重盘触发器**
   - 完成标准: 通道清单与各通道防线落入设计文档；平台新增跨上下文机制时触发重新枚举。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一应用内部组件间通信（无跨信任域）——普通的数据流设计问题。
- 纯服务端 API 的授权与访问控制——用访问控制与信任边界方法。
- 通道协议本身的加密强度（端到端加密选型）——属密码学问题；本 skill 假设传输机密性已解决，专审"谁在门里验票"。

### 作者在书中警告的失败模式

- "同源策略会保护我们"——拖拽、postMessage 等通道根本不在 SOP 管辖内。
- postMessage 接收端不验来源、消息内容直接进 DOM——等于主动放弃同源策略。
- 检测规则/模型下发到客户端被逆向——通道方向反过来的同族问题：跨上下文暴露的不仅是数据，还有防御逻辑本身。

### 作者的盲点 / 时代局限

- 书中通道清单停留在 2014 年浏览器（Flash 相关通道已随 EOL 失效）；今日清单需扩展：Service Worker/SharedWorker、WebRTC data channel、BroadcastChannel、Storage 事件、MSE/OffscreenCanvas、小程序与原生 bridge、Shadow DOM 穿透。
- 未讨论跨上下文消息的协议设计（消息版本化、能力票据 capability token）——接收端校验之外，现代做法还包括最小化消息能力面。

### 容易混淆的邻近方法论

- 信任边界建模（通用画界 vs 浏览器通道清单）。
- 白名单优先（值的准入 vs 门的枚举）。
- 攻击面收敛（功能存废 vs 通道设防——通道砍不掉时只能设防，本 skill 处理"必须存在的通道"）。
