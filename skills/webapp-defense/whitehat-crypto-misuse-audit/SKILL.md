# 密码学误用审计：乘法模型与独立失败点清单

## R — 原文 (Reading)

> "ECB模式的缺陷，并非某个加密算法的问题，因此即使强壮如AES-256等算法，只要使用了ECB模式，也无法避免此问题。"（第11章 11.4）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

开发者的直觉是"选对了算法就安全了"。真实的依赖关系是乘法：算法强度 × 使用方式（模式、IV、认证、随机源、密钥管理），任何一项为零，整体为零——AES-256 配 ECB 照样泄露明文结构。

因此审计的正确姿势不是评价算法，而是把方案拆成相互独立的失败点逐项打分：

1. **模式**：ECB 泄露结构、分组可替换；CBC 无认证可被位翻转。
2. **IV/nonce**：价值全在"随机且不重复"——空间小或可预测（时间戳派生、计数器）等于没有；WEP 与 authcode 的实测（16 秒碰撞）证明这层归零是可量化的。
3. **认证**：只加密不认证=密文可篡改；先认证后解密。
4. **随机源**：时间、自增计数器、弱种子都不是随机数——预测随机数即预测全部下游凭证。
5. **密钥管理**：硬编码即随代码分发；密钥与被保护数据同库同机=一同失陷。
6. **自研**：包装不增加强度（authcode 被 XOR 拆穿），结构定强度；安全原语一律用专家实现。

评估输出应是"哪个失败点为零"的判定清单，而不是"算法是否先进"。

## A1 — 书中的应用 (Past Application)

### 案例 1: ECB 替换攻击——1 元买走万元单（第11章 11.4）
- **问题**: 支付报文按字段分组加密，如何篡改金额？
- **方法论的使用**: 查模式失败点：ECB 下相同明文组密文相同，攻击者先买 1 元商品获得 "1.00" 的合法密文，替换进自己的支付请求。
- **结论**: 缺陷与算法强度无关——分组边界可控 + 可获得替代密文 = 替换攻击；多于一个分组就不该用 ECB。
- **结果**: 确立"定位加密调用后先看 mode 参数再谈密钥长度"的审计次序。

### 案例 2: Discuz authcode()——弱 IV 让复杂包装归零（第11章 11.2.3）
- **问题**: authcode() 有 MD5、密钥簿打乱、base64 等层层包装，被广泛复用，安全吗？
- **方法论的使用**: 逐失败点审查：其 IV 仅 4 字节且由 microtime 派生——实测约 16 秒、遍历 19295 个 XOR KEY 即碰撞到相同 IV，Reused Key Attack 直接还原明文。
- **结论**: 包装不增加强度，结构定强度；IV 空间与生成方式是独立失败点，"有 IV"不等于安全。WEP 的 24bit IV 数小时耗尽是同一失败模式的协议级后果。
- **结果**: "算法×使用方式任一为零整体为零"的乘法模型有了可量化的实证标本。

### 案例 3: Flickr/AWS 裸 MD5 拼接签名被长度扩展伪造（第11章 附录）
- **问题**: API 签名用 MD5(secret||参数)，secret 未泄露为何还能伪造？
- **方法论的使用**: 查认证构造失败点：Merkle-Damgård 结构允许在不知道 secret 的情况下追加数据算出新签名；拼接无分隔符（a=1&b=2 拼成 a1b2）使攻击者可构造恰好可扩展的形态。
- **结论**: 裸哈希拼接不能做签名——改用 HMAC，或把 secret 放参数末尾；自研签名方案要在哈希构造与拼接格式两个维度同时审。
- **结果**: "搜签名函数里的 md5($secret.$data)"成为标准审计信号，写入误用清单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审包含加密/签名/摘要/随机数的方案设计（加密 cookie、API 签名、令牌生成、密码存储）。
2. 代码审计中定位到加密调用点（crypto API、hash 函数、random 函数）后的深入检查。
3. 接手遗留系统：发现自研加密函数、无名算法、硬编码密钥字符串。
4. 评估"我们用了 AES/HTTPS/ bcrypt，够安全吗"式的结论请求。
5. 密钥的存放与轮换方式设计（配置、环境变量、KMS）。

### 语言信号 (用户的话里出现这些就应激活)

- "用了 AES 加密，还安全吗 / is AES enough"
- "自己实现一个加密/签名 / homemade crypto / roll my own"
- "md5/sha 拼接 secret 做签名 / hash concatenation signature"
- "随机数用时间戳/随机一下 / random token from timestamp"
- "密钥写在代码里/环境变量 / hardcode key / secret in env"
- "IV 是什么，要随机吗 / IV nonce reuse"

### 与相邻 skill 的区分

- 与 `whitehat-framework-authority-audit` 的区别：那边审"依赖的组件/文档是否可信"；本 skill 审密码学方案本身的构造。两者在"不自研、用专家库"处衔接——本 skill 说"用库"，那边说"用了库也要验证"。
- 与 `whitehat-credential-rotation-on-state-change` 的区别：那边管 token 的一次性/轮换语义；本 skill 管 token 的构造（随机性、签名）是否可伪造可预测。
- 与 `whitehat-unpredictability` 的区别：那边是设计原则（让关键值不可猜）；本 skill 是落地审计清单（随机性从哪来、如何不被误用拖垮）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **定位全部密码学调用点**
   - 完成标准: 加密、解密、哈希、签名、随机数生成、密钥读取的调用位置全量列出（含依赖库内部的直接调用），每处标注用途与数据对象。
   - 判停条件: 若系统完全不使用密码学原语（无加密/签名/随机数/凭据生成），终止并说明不适用。

2. **按独立失败点清单逐项审**
   - 完成标准: 对每个调用点回答六项：模式（是否 ECB/无认证）？IV/nonce（空间与生成源，是否存在重用路径如多实例共享计数器）？认证（密文是否带 MAC/AEAD，先认证后解密？）？随机源（CSPRNG 还是 time/rand/自增）？密钥（来源、存放、轮换、是否硬编码）？自研痕迹（无名算法、自造拼接协议）？每项给出"为零/存疑/通过"判定。

3. **对"为零"项验证可利用性**
   - 完成标准: 每个判"为零"的失败点给出具体攻击推导（如 IV 重用→两密文异或消去密钥；无认证→位翻转改权限字段），不停留在"不合规"。

4. **替换为成熟方案**
   - 完成标准: 失败点对应替换落地——认证加密（AEAD）、HMAC 系签名、CSPRNG、密钥管理服务/KMS + 轮换；自研算法/协议全部替换为久经审计的库。

5. **复核与回归**
   - 完成标准: 替换后重走清单全项通过；随机性/密钥不随日志、错误信息、版本库泄露；兼容旧数据的迁移路径明确（重加密或强制重置）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 密码学理论研究、算法对比选型论证（性能、专利、标准采纳度）——本 skill 只审"使用方式"，默认采用现成安全原语。
- 合规密码测评（等保密评、FIPS 认证流程）——那是程序性问题。
- 传输层安全（TLS 配置与证书链）已由平台保证时的应用层设计——不重复审计底层。

### 作者在书中警告的失败模式

- "用了 AES 就安全"——ECB 照样泄露结构，模式是独立失败点。
- 只加密不认证——密文可被位翻转定向篡改（提权 Cookie、改金额）。
- 时间当随机数、弱种子—— microtime 派生口令被预测，Debian OpenSSL 事件中全部密钥可穷举。
- 硬编码密钥随代码分发；自研协议与算法"没人审计你的实现"，缺陷在被攻击时才暴露。

### 作者的盲点 / 时代局限（本条目经 verified.md 标注需按现代标准替换）

- 书为 2014 年文本，**具体推荐条目已过时**：书中推荐 HMAC-SHA1、AES-CBC+HMAC 组合、"随机数做 MD5 再拼再 MD5"、重要系统读 /dev/random——按现代标准应替换为：**AEAD 认证加密（AES-GCM / ChaCha20-Poly1305）**取代 CBC+HMAC 手工组合、**SHA-2/SHA-3** 取代 SHA-1/MD5 系、**Argon2id/bcrypt/scrypt** 做口令存储（书中加盐 MD5/SHA 已不满足慢哈希要求）、**/dev/urandom 即足够**（/dev/random 的"更安全"说法已被主流密码学界否定）。
- 乘法模型与失败点清单骨架不变：IV/nonce 重用（GCM 下 nonce 重用灾难性）、只加密不认证（AEAD 缺失）、弱随机、密钥管理、自研——五类误用在现代栈上依旧成立，审计动作照旧。
- 书中"HMAC 目前未发现安全漏洞"式绝对化表述应谨慎；未覆盖现代主题：AEAD nonce 管理策略、KMS/信封加密、后量子迁移、JWT 签名算法选择（alg=none 攻击属此类框架的外推应用）。

### 容易混淆的邻近方法论

- 不可预测性原则（设计目标 vs 实现审计）。
- 框架与权威双面审计（组件可信度 vs 方案构造正确性）。
- 信任假设检验（普适的机制前提审查 vs 密码学专属失败点清单——后者更具体，可独立执行）。
