# 数据定级与安全方案模块化

## R — 原文 (Reading)

> "一个最佳实践是给公司拥有的数据定级，对不同级别的数据定义不同的保护方式，将安全方案模块化。这样在review项目的需求和设计时，根据项目涉及的数据敏感程度，可以套用不同的等级化保护标准。"
>
> — 原作者，原始方法论来源第17章 17.4

---

## I — 方法论骨架 (Interpretation)

这套方法把"安全评审"从逐案发明变成查表选配，分三步且顺序不可颠倒：

1. **定级**：互联网公司的核心资产是数据，所以"资产等级划分"实质就是数据分级。定级的输入不是安全团队拍脑袋，而是逐一访谈业务负责人——了解公司最重要的资产、他们最看重什么数据。访谈同时让安全部门熟悉业务。
2. **按级定义保护**：每个级别对应一套明确的保护方式（加密、访问控制、脱敏、日志等）。没有统一分级就没有统一保护标准。
3. **模块化复用**：把各级保护方式做成可复用的模块/清单/组件库。新项目评审时只需回答"涉及哪级数据"，直接套用对应保护标准。

两个动态纪律：每引入一种新存储介质（客户端存储、缓存、新数据库）等于新增资产与攻击面，须重做盘点；字段的敏感性随攻击能力变化——今天无害的标识字段，明天可能变成撞库凭据，定级要周期性重估。

## A1 — 书中的应用 (Past Application)

### 案例 1: SDL 需求/设计评审的等级化保护
- **问题**: 每个项目评审时安全方案都要重新设计一遍，质量参差、效率低下。
- **方法论的使用**: 给公司数据定级→对不同级别定义保护方式→将安全方案模块化。
- **结论**: 评审从"每次重新发明方案"变成"查项目涉及哪级数据，套用对应保护标准"。
- **结果**: 兼顾一致性与效率，安全评审成为可规模化的流水线动作。

### 案例 2: 资产等级划分靠访谈业务（第1章 1.6.1）
- **问题**: 安全评估从哪里入手？保护对象如何确定？
- **方法论的使用**: 与各业务部门负责人逐一访谈，了解最重要的资产与他们最看重的数据——资产等级划分实质是数据分级。
- **结论**: 先确定保护目标和数据重要性，后续的威胁分析、风险分析才有对象。
- **结果**: 成为"资产分级→威胁→风险→方案"四阶段评估的第一块基石。

### 案例 3: loginID 敏感性的动态重估（第1章 附录）
- **问题**: 登录ID原本只是普通标识字段，为什么后来要保护？
- **方法论的使用**: 按攻击能力重估字段敏感性——loginID 泄露后可被暴力破解、可用于撞库第三方站点、有用户拿它当密码的一部分。
- **结论**: 数据的敏感性由其在业务中的可利用价值决定，不是固定属性；分级要随攻击能力演进重估。
- **结果**: 业务安全设计良好的网站把登录ID与昵称分离：昵称公开、不可用于登录。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 多项目/多业务线要统一安全标准，不想每个项目重新设计保护方案（SaaS 多租户平台、中台架构、集团多子公司）。
2. 评审新项目需求/设计时，需要快速判断该套什么等级的保护。
3. 引入新技术（新数据库、客户端存储、第三方 SDK）后，不确定是否要重新做数据资产盘点。
4. 某个字段以前不敏感、现在敏感了（手机号变成撞库凭据、行为数据变成画像原料），需要重估定级。
5. 数据治理/合规分级（等保、个保法）需要落地成工程上可执行的保护措施。

### 语言信号 (用户的话里出现这些就应激活)

- "数据要怎么分级/定级 data classification"
- "这么多项目，安全方案怎么统一/标准化 standardized security controls"
- "敏感数据到底怎么保护才合适"
- "新上了一种存储/技术，要不要重新盘点数据资产"
- "这个字段现在算敏感信息吗 / 这个字段泄露了有什么风险"

### 与相邻 skill 的区分

- 与 `whitehat-data-minimization` 的区别：那边裁决"要不要持有这份数据"（不持有即零泄露面）；本 skill 裁决"已持有的数据如何分级并配套可复用保护"。
- 与 `whitehat-security-assessment` 的区别：那边是"资产分级→威胁→风险→方案"完整评估流程；本 skill 是其中资产/数据分级环节的工程化与模块化复用。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点数据清单并访谈业务**
   - 完成标准: 产出全量数据类别清单，标注来源系统与业务负责人；最重要数据有业务方确认记录（不是安全团队单方认定）。

2. **给每类数据定级**
   - 完成标准: 每类数据有级别标签 + 一句话定级理由（业务价值/泄露后果/可利用性）。
   - 判停条件: 若业务方说不清某数据的用途与价值 → 停在访谈环节补齐信息，未定级数据不得进入下一步。

3. **按级定义保护方式**
   - 完成标准: 每个级别对应明确的控制集（加密、访问控制、脱敏、日志、留存期限），级别间差异可描述。

4. **模块化封装**
   - 完成标准: 各级保护方式落成可复用形态（组件/清单/代码库/配置模板）；新项目评审只需识别"涉及哪级数据"即可选配，不需要重新设计。

5. **定义重估触发器**
   - 完成标准: 列出触发重新定级的事件（新增存储介质、字段用途变化、攻击能力变化、合规变化）并指派重估责任人；loginID 式"标识变凭据"作为示例写入触发器说明。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一系统、数据类型少且稳定的一次性安全设计——建级制是过度工程，直接按最小集合设计保护即可。
- "要不要收集/保留这份数据"的裁决——那是数据最小化的领地；本 skill 只处理已决定持有的数据。
- 纯基础设施层加固（网络、操作系统）不涉及业务数据分级的场合。

### 作者在书中警告的失败模式

- 定级脱离业务：资产等级划分必须靠与业务负责人逐一访谈，安全部门闭门造车会保护错对象。
- 定级一劳永逸：新存储介质引入、攻击能力演进后不重估，分级表腐烂失效。

### 作者的盲点 / 时代局限

- 书中分级语境是 2014 年电商/大厂（PCI、隐私保护），未覆盖 GDPR/《个保法》的法定分级维度、跨境传输要求与"按敏感个人信息专门规则"——现代落地需叠加合规定级轴。
- "按级选配模块"在大厂语境（安全团队建制完整）下描述，中小团队需大幅裁剪，书中对中小团队路径着墨少。
- 书中未涉及机器学习训练数据、向量库等新型数据的定级。

### 容易混淆的邻近方法论

- 数据最小化（先减量再谈保护）。
- 安全评估四阶段（本 skill 是其第一阶段的制度化延伸）。
- 攻击面收敛（减少可被打的机会；本 skill 是给保留的数据配保护，方向相反）。
