# 数据与代码分离：注入类漏洞的统一成因模型

## R — 原文 (Reading)

> "此类问题均可以根据'数据与代码分离原则'设计出真正安全的解决方案，因为这个原则抓住了漏洞形成的本质原因。"
> "注入攻击是应用违背了'数据与代码分离原则'导致的结果。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.7.3；第 7 章《注入攻击》小结

---

## I — 方法论骨架 (Interpretation)

表面五花八门的注入漏洞，成因只有一个：程序把用户数据送进了某个解释器，而解释器无法区分"这是我写死的结构"和"这是外部塞进来的内容"。数据一旦能改变代码的语义，攻击者就获得了改写程序行为的能力。

这个模型的价值在于**归因先于防御**：

1. 找到解释器——SQL 引擎、HTML 解析器、shell、正则引擎、XML 解析器、日志系统，甚至 CPU 的取指逻辑（缓冲区溢出=数据进入本应只放代码的执行路径）。
2. 确认数据可控——用户输入是否到达该解释器。
3. 防御 = 恢复分离——不是"过滤坏字符"，而是让结构不可变：参数化绑定让输入只能填值位置；保留字符转义让数据无法伪装成结构（HTML 的 `<>&'"`、日志的 `\r\n`、shell 的引号）。
4. 若业务确实要执行用户提供的逻辑（富文本、可配置查询），就重写代码结构：把可变部分限制在受控的语法槽位里，而不是拼接后整体解释。

推论：编码/转义发生的位置 = 解释发生的位置。在别处做的转义，到解释器眼里可能什么都不是。

## A1 — 书中的应用 (Past Application)

### 案例 1: SQL 注入章的统一收束（第 7 章）
- **问题**: SQL 注入的绕过手法层出不穷（注释替代空格、十六进制免引号、宽字节吃转义），逐个封堵为何永远失败。
- **方法论的使用**: 章末把整族问题归因为"违背数据与代码分离"，防御不再跟 payload 走，而是让 SQL 结构先编译、数据后绑定。
- **结论**: 预编译语句下"变量用 ? 表示，攻击者无法改变 SQL 的结构"——语义不可变，注入面整体消失。
- **结果**: 确立防御阶梯"预编译 → 安全存储过程 → 类型检查/安全函数兜底"，escape 与关键字黑名单被三组反证否定。

### 案例 2: XML 注入换解释器不换骨架（第 7 章 7.4.1）
- **问题**: 用户在 email 字段提交 `a@b.com</email></USER><USER role="admin_role">...`，把一条记录变成两条并自我提权。
- **方法论的使用**: 按统一模型归因：XML 解析器是新解释器，`< > & ' "` 是它的结构保留字符，闭合标签即"数据伪装成结构"。
- **结论**: 修补方案与 HTML 注入同构——转义语言自身的保留字符，而非针对"USER 标签"打补丁。
- **结果**: "两条件核对 + 保留字符处理"的方法被平移到任何结构化数据解释器上。

### 案例 3: CRLF 注入——两个字符撑起的结构边界（第 7 章 7.4.3）
- **问题**: 登录失败用户名直接写日志，输入 `guest\nUser login succeeded for: admin` 后日志多出一条伪造的 admin 登录成功记录；校内网案例中 `%0d%0a%0d%0a<script>` 经 Set-Cookie 进响应头，两次换行提前结束头部、脚本落入响应体执行。
- **方法论的使用**: 归因到"以换行为分隔符的系统里，`\r\n` 是保留字符"——数据携带它就等于携带了结构控制权。
- **结论**: 防御收敛到极简：写日志/写响应头前剥离或编码这两个字符，无需理解每种攻击变体。
- **结果**: "管住少数保留字符即管住整个注入面"成为可迁移规则，适用于一切以分隔符组织结构的输出点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 遇到书里/经验里没有的注入类型（NoSQL 操作符注入、GraphQL、SSTI 模板注入、日志注入），不知道从哪下手防。
2. 已做了 escape/过滤但 payload 仍绕过，需要判断防御为什么无效。
3. code review 发现字符串拼接进 SQL/命令/HTML/正则，或 ORM 的动态变量（iBatis `$value$`）被用户控制。
4. 设计富文本、可配置报表、动态排序字段等"业务需要执行用户逻辑"的功能。
5. 评估"过滤了危险字符/关键字"类方案是否可靠。

### 语言信号 (用户的话里出现这些就应激活)

- "这个 XX 注入没见过，怎么防？"
- "明明转义了为什么还是被注入？"
- "过滤掉危险关键字够不够？"
- "用户要自己传查询条件/排序字段，怎么设计？"
- "how to prevent XX injection / escaped but still injected / is keyword filtering enough"

### 与相邻 skill 的区分

- 与 `whitehat-source-sink-audit` 的区别: 本 skill 回答"成因是什么、防御往哪个方向走"（世界观层）；那个回答"这个代码库里漏洞面具体在哪"（枚举 source 与 sink 的审计操作）。先归因用本 skill，找面用那个。
- 与 `whitehat-defense-at-interpretation` 的区别: 那个裁决"防线放在哪一环"（输入侧还是输出侧、语境何时可确定）；本 skill 不裁位置，只给成因模型与分离方向。
- 与 `whitehat-whitelist-first` 的区别: 白名单/黑名单是"检查规则怎么写"的形态选择；本 skill 说的是更根本的一层——结构槽位与数据填充分离，参数化后甚至不需要黑名单。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **确认解释器**：列出数据从进入到落地的全部环节，标出每个环节的解释器（SQL 引擎、HTML 解析器、shell、正则、XML/JSON 解析器、日志/协议格式化器）。
   - 完成标准: 一张"环节 → 解释器 → 保留字符/结构语法"清单。
   - 判停条件: 若数据全程不被任何东西"解释执行"（纯存储、纯传输），此问题不是注入，跳出本 skill。
2. **核对两个条件**：对每个解释器问——用户能否控制到达它的数据？数据是否被拼接进结构位置？
   - 完成标准: 每个解释器有"可控/不可控、拼接/绑定"的明确判定。
3. **选分离手段**：优先参数化/结构化绑定；无绑定原语时转义该解释器的保留字符（照抄标准转义表，不自造子集）；业务确需执行用户逻辑时重写为受控语法槽位（白名单标签/白名单操作符/沙箱）。
   - 完成标准: 每个注入点对应一种分离手段，且手段作用于解释发生处。
4. **验证语义不可变**：构造"结构注入"输入（闭合符、保留字符、同义编码变体）验证它只能成为字面值。
   - 完成标准: 攻击输入进入后解释器看到的结构与设计者写的一致；转义表覆盖标准全集。
5. **横向扫同族**：同一解释器的其他入口、同构的其他解释器（换存储、换模板、换协议）逐个复查。
   - 完成标准: 同族清单上的每个入口都有了第 3 步的处置结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 业务逻辑漏洞（改 id 越权、审核旁路）——没有"数据被当代码"的环节，分离模型用不上。
- 配置错误、默认口令、权限过宽——成因在策略不在解释器。
- 纯传输/存储场景（加密、编码转换）——数据不被解释执行时，套注入模型会把问题带偏。

### 作者在书中警告的失败模式

- 用 escape 当万能药：`mysql_real_escape_string` 只转义少数字符，不含这些字符的 payload 照样注入——转义必须针对具体解释器的保留字符。
- 关键字黑名单误杀正常数据：HAVING、ORDER BY 是常用词，硬过滤破坏业务——过滤不是分离。
- 存储过程/ORM 的虚假安全：过程内部拼接动态 SQL、iBatis `$value$` 动态变量，都把绑定重新退化回拼接——"用了 X 所以安全"的标签式记忆是危险的。

### 作者的盲点 / 时代局限

- 成书 2014 年，案例集中在 SQL/HTML/XML/CRLF 与 PHP 危险函数，未覆盖 NoSQL、SSTI、原型污染、GraphQL——模型本身可外推，但具体保留字符表需按现代解释器补齐。
- 缓冲区溢出只作类比带过（第 1 章一句），内存安全语言普及后该分支的实际权重已下降。

### 容易混淆的邻近方法论

- "输入检查"：过滤输入是改变数据内容，不改变结构可变性；本书用"过滤 1<2 误杀"证明输入侧路线两头失败，正解是消费点分离（见 `whitehat-defense-at-interpretation`）。
- "纵深防御"：分离是消除成因，HttpOnly/WAF 是减损层——两者层级不同，不能因加了减损层就跳过分离（见 `whitehat-mitigation-vs-fix`）。
