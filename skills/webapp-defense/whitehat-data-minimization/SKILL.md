# 数据最小化：不存在的数据最安全

## R — 原文 (Reading)

> "PCI认为现有的安全技术是复杂的，要想完美地保护好用户个人信息比较困难，最好的做法是限制数据的使用——'不存在的数据是最安全的'。"
> "个人数据应该只能由算法或者程序来计算，工作人员不应该有直接查看的权限。"
>
> — 方法论出处，第 16 章《互联网业务安全》16.6.1 / 16.4

---

## I — 方法论骨架 (Interpretation)

收到"保护 X 数据"的需求时，直觉是给 X 加锁（加密、权限、审计）。但还有一问排在其前：**X 需要被持有吗？** 保护是有失败概率的，不持有是零风险的——这就是"不存在的数据最安全"：它把裁决从"怎么保护"上移到"要不要持有"，绕开了"完美保护在技术上困难"这个现实约束。

操作上是一条链上的同把标尺：

- **采集**：能不采的不采，能少采的少采（每个字段都要回答"哪个功能在什么时候用它"）。
- **存储**：必须存的先定级（决定保护强度），能脱敏/聚合的就不存原文。
- **使用**：个人数据默认对内部员工不可见，只由程序计算消费（Gmail 广告模式）；人工查看走授权与审计——最小权限原则用在人身上。
- **留存**：限期 + 到期即删，"永久保存以备后用"默认不成立。
- **对外**：第三方集成要最小授权令牌（范围受限、可撤销），绝不索取/存放对方站点的密码——那等于替用户把攻击面扩大到第三方。

每引入一份数据就是新增一份必须永久防守的资产；反过来，每减掉一份，泄露面、合规义务、内部滥用风险同步消失。

## A1 — 书中的应用 (Past Application)

### 案例 1: PCI 的减量立场（第 16 章 16.6.1）
- **问题**: 支付行业持有海量卡号与个人信息，"把保护做到完美"为什么不是答案。
- **方法论的使用**: 引 PCI 的结论——安全技术复杂、完美保护困难，最优做法是限制数据使用；按采集、存储、展示、留存每一环逐个复核"这份数据是否必须存在"。
- **结论**: 减量先于加固：能不存的不存、必须存的分级定周期、到期即删，剩下的才谈加密与权限。
- **结果**: 隐私保护方案从"加锁"反转为"减量"，成为数据分级方案的逻辑起点。

### 案例 2: 员工默认不可见——最小权限用在人身上（第 16 章 16.4）
- **问题**: 内部人员查看用户隐私的滥用风险怎么控。
- **方法论的使用**: 把"个人数据只能由算法或程序来计算"立为规则——Gmail 广告由算法生成、人看不到邮件正文；需要人工介入时走授权与审计。
- **结论**: 隐私保护要落到"人对数据的可见性"上，而非只防外贼。
- **结果**: 内部滥用与越权查看获得结构性控制，与"最大漏洞是人"的判断呼应。

### 案例 3: 交出密码 vs 最小授权令牌（第 10 章 10.4）
- **问题**: 为实现"绑定 MSN 同步好友"，让用户把第三方站点的账号密码交给本站，为什么书中定性为"扩大攻击面"。
- **方法论的使用**: 按持有必要性裁决——本站需要的是"读好友列表"这个能力，不是密码这个最高级凭据；持有密码后本站一次泄露即波及用户在第三方的账户，且密码复用会扩散到更多站点，"承诺安全"不改变风险归属。
- **结论**: 第三方集成只拿范围受限、时效受限、可撤销的令牌（Access Token），这正是 OAuth 的设计动机。
- **结果**: "永远不要交出主密码"成为集成类功能的红线；同原则推广到一切开放平台授权场景。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新功能要采集/存储用户数据（含"接更多数据提升效果"类需求），评估要不要接、怎么接。
2. 制定留存与删除策略（日志、行为数据、聊天记录存多久）。
3. 第三方集成/开放平台授权设计：对方该拿到什么（密码 vs 令牌 vs 只读范围）。
4. 隐私合规设计（个保法/GDPR 下的最小必要原则落地）。
5. 数据泄露复盘后收缩持有面，或评估已有库表的攻击面。

### 语言信号 (用户的话里出现这些就应激活)

- "这些数据先存下来，以后说不定有用？"
- "要不要接用户聊天记录/通讯录来提升效果？"
- "日志里把请求全量记下来，有问题吗？"
- "第三方要读我们的数据，直接给他们一套账号密码？"
- "do we need to store this / data retention policy / should we collect user X"

### 与相邻 skill 的区分

- 与 `whitehat-data-classification-modules` 的区别: 那个管"已确定持有的数据怎么分级选保护模块"；本 skill 管更上游的"要不要持有"。顺序：先过本 skill 减量，剩下的再定级。
- 与 `whitehat-attack-surface-reduction` 的区别: 那个收敛功能与服务的暴露面（攻击者能打到什么）；本 skill 收敛数据持有面（泄露后有什么可漏）。每多存一份数据=多一个必须防守的资产，与"每多一个组件=多一分攻击面"同构但对象不同。
- 与 `whitehat-trust-boundary` 的区别: 那个决定数据流过哪条边界要检查；本 skill 决定这条数据流根本要不要存在——少一条流，就少一条要设防的边界。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **盘点数据流全链**：列出该功能涉及的每类数据（字段级），标注采集点、存储位置、消费方（程序/人/第三方）、留存时长。
   - 完成标准: 每类数据能回答"谁在什么场景用它"；无人消费的字段已标红。
2. **逐项问持有必要性**：对每类数据问——去掉它功能损失多少？能否用脱敏/聚合/即时计算/抽样替代持有？展示环节能否默认不回显原文？
   - 完成标准: 每类数据有"不持有 / 降级持有（脱敏聚合）/ 原文持有（附理由）"三选一结论。
   - 判停条件: 若数据为法定必须留存（合规留痕），跳过删除讨论，直接进入第 3 步做访问与可见性最小化。
3. **最小化消费与可见性**：对保留的数据限制消费方式——程序计算优先、员工默认不可见（需人工时走授权+审计）、对第三方的输出按最小范围令牌化。
   - 完成标准: 人工可见清单为空或有逐项授权记录；对外授权均为范围/时效受限的令牌，无密码类交接。
4. **定留存与删除**：为每类保留数据定留存期限与到期动作（删除/匿名化），"无限期"需要单独论证。
   - 完成标准: 留存表含期限、删除触发条件、执行负责人；有到期自动执行或定期清理机制。
5. **复核与回访**：上线后按同一标尺周期复核（新功能加字段、日志悄悄扩容、第三方要扩权都要重过第 2 步）；泄露事件后重估持有面。
   - 完成标准: 复核有周期与 owner；持有面只减不增（增量须过必要性裁决）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已确定必须持有的数据如何保护（加密选型、密钥管理）——那是密码学误用审计与数据分级的领域；最小化只裁决持有与否。
- 法定/合规强制留存的数据（审计留痕、交易记录）——删除讨论无意义，重心转为可见性与期限管理。
- 安全运行自身必需的数据（检测日志的最小集合）——减到无法检测响应，属过度最小化；权衡点是响应能力下限。

### 作者在书中警告的失败模式

- "先存下来以后有用"：没有消费方的数据是最典型的多余持有——泄露时它照样在库里。
- 替用户交出第三方密码：一次泄露波及多个站点，"承诺安全"不是控制措施，风险归属不会因承诺改变。
- 只防外贼不防内部：员工可直接查看敏感数据，等于把最小权限漏掉一半——数据可见性也是攻击面。

### 作者的盲点 / 时代局限

- 成书早于 GDPR/《个保法》，"最小化"当时是工程智慧，如今是法定义务（最小必要原则、目的限制、删除权）——引用时把"最佳实践"口径升级为"合规底线"口径。
- 未覆盖现代数据场景的边界：AI 训练集的二次用途、数据出域与跨境、"匿名化后重新识别"风险——标尺不变，环节清单需扩展。

### 容易混淆的邻近方法论

- 数据分级保护：分级是"持有后按级配置"，最小化是"持有前的裁决"——顺序颠倒会把资源精确花在不该持有的数据上。
- 最小权限原则：作用于"主体能做什么"；本 skill 作用于"系统持有什么"——两者在"员工默认不可见"处交汇但轴不同。
