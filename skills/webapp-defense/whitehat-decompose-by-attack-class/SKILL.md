# 分解问题、按攻击类别设防

## R — 原文 (Reading)

> "白帽子必然是在不断地分解问题，再对分解后的问题逐个予以解决。"
> "白帽子选择的方法，是克服某种攻击方法，而并非抵御单次的攻击。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.2 黑帽子，白帽子

---

## I — 方法论骨架 (Interpretation)

攻击者的一次入侵是多种弱点的**组合**；防守者如果盯着组合后的效果（某次事件、某条告警）去响应，永远在追赶。反过来做的路径是两步：

1. **分解**：把涌来的问题拆回原子层面——每条告警、每个风险都归因到"哪一类攻击方法、它的成立条件是什么"。组合会无限变体，但原子类别是有限的（注入、凭证泄露、资源滥用、逻辑缺陷……）。
2. **类别级设防**：对每个原子类设计一个在特定环境下解决"所有已知和未知该类问题"的方案，并作为工作单元排期。判别标准是可验收的目标（"3 个月内消除全部 SQL 注入弱点"），而不是"加强防护"这类口号。

两类工作的本质差异：按事件救火，做完事情回到原点（同类攻击换个入口再来）；按类别做完，该类对抗中防守方转主动（攻击者失去这一整类武器）。全书的技术体系就是这个方法的展开：注入族归到"数据与代码分离"、DoS 五形态归到"资源滥用配额"、权限问题归到"主体-客体-操作"。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: "3 个月内消除全部 SQL 注入弱点"（第 1 章 1.2）
- **问题**: SQL 注入个案不断冒出，逐个修补的团队永远在救火。
- **方法论的使用**: 把工作单元从"修这个洞"改为"克服这一类攻击方法"：目标是消除环境内全部 SQL 注入弱点（已知与未知），手段是类别级方案（预编译+类型检查全面推行）。
- **结论**: 执行完后，无论攻击者用什么新 payload，该类攻击在本环境整体失效——对抗主动权易手。
- **结果**: 该目标成为作者给出的类别级排期范式，是"化被动为主动"的字面演示。

### 案例 2: DoS 五形态归一到资源滥用（第 13 章）
- **问题**: CC、Slowloris、POST DOS、Server Limit DOS、ReDOS 各有形态，逐个防不胜防。
- **方法论的使用**: 分解到底层共性——全部是"对有限资源的无限制滥用"；类别级方案是给一切有限资源配额（连接数、CPU、正则回溯、请求头大小）。
- **结论**: 不需要为每种攻击名单独产品，按资源类别设防即可覆盖未来变体。
- **结果**: 第 13 章从"五种攻击"收敛为"一张资源清单逐项问配额"的审计法。

### 案例 3: "提高密码复杂度"分解为可判定威胁（第 16 章 16.1.2）
- **问题**: 业务方提出口号式安全需求，直接实现必然做偏。
- **方法论的使用**: 分解动作前置于需求：口号拆成"对抗暴力破解"与"防密码包含个人信息"两条可判定威胁，再逐条设计机制（限速/锁定；注册资料比对拒绝）。
- **结论**: 需求分解是"分解问题"在需求侧的镜像——把模糊目标变成可验收的类别级目标。
- **结果**: 方案能与业务方对齐验收标准，上线后说得清"防住了什么"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 安全团队被钓鱼、撞库、蠕虫、告警多线轰炸，要决定人力怎么组织。
2. 制定季度/年度安全目标，要把"提升安全水平"翻译成可排期、可验收的工作单元。
3. 复盘一起事件后，决定修复范围只堵这一个洞还是消一类问题。
4. 向上汇报"治本方案"时，需要说明与逐洞修补的差别。
5. 面对一种新攻击手法，判断是否已有类别级方案覆盖它。

### 语言信号 (用户的话里出现这些就应激活)

- "告警太多了，每天都在救火。"
- "这个洞修了，但感觉同类问题到处都是。"
- "怎么定今年的安全目标？"
- "治本和治标到底差在哪？"
- "we keep patching the same class of bugs / how to stop firefighting / category-level fix"

### 与相邻 skill 的区分

- 与 `whitehat-requirement-decomposition` 的区别: 那个分解的是"需求"（口号→具体威胁，需求期用）；本 skill 分解的是"工作与攻击面"（告警/风险→攻击类别，运营与规划期用）。同一思维的两个阶段。
- 与 `whitehat-coverage-first` 的区别: 那个管"对象清单闭合"（别漏资产/项目）；本 skill 管"问题归类"（别按事件组织工作）。组合顺序：先覆盖全部对象，再把发现的问题归到类别。
- 与 `whitehat-fix-at-highest-leverage` 的区别: 那个裁决"同一问题在多层中选哪层修"（杠杆）；本 skill 裁决"工作按什么单元组织排期"（类别）。类别方案落地时选层用那个。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **收集问题全集**：把时间窗内的告警、事件、漏洞、扫描结果汇成一张表，逐条列出，不预合并。
   - 完成标准: 表中每条有入口、对象、后果三要素。
2. **归因到攻击类别**：对每条问"它属于哪类攻击方法、成立条件是什么"（注入类=可控输入×解释器；凭证类=泄露/复用；资源类=无限制消耗有限资源；逻辑类=状态转移旁路……）。
   - 完成标准: 每条问题挂到一个类别，类别清单有限（≤10 个）；无法归类的新类别显式立户。
   - 判停条件: 若某问题经查是孤例且无变体可能（配置笔误一次性修复），不建类别，直接关闭。
3. **评估各类对抗态势**：对每类问——是否有类别级方案？方案覆盖率多少？当前是被动（逐案响应）还是主动（方案生效）？
   - 完成标准: 每类标注"被动/半主动/主动"与证据。
4. **制定类别级方案并排期**：每类一个方案（作用于一类全部实例），目标可验收（"消除/阻断该类全部已知与未知利用"），按业务风险排序铺开。
   - 完成标准: 排期表以类别为行，每行有验收判据；没有"加强安全意识"式的不可验收项。
5. **验收与转主动**：方案落地后回归测试——同类新变体（换入口、换编码、换载体）是否被方案拦住；拦住即宣告该类对抗转主动，转入监控维护。
   - 完成标准: 每类有"变体验证通过"记录；人力从该类救火中释放的证据（告警量下降或自动处置率）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 正在进行的入侵/大故障应急——先止损、保全现场，归类与治本在事后复盘做。
- 一次性配置错误、人为失误类问题——无"攻击类别"可言，修复即关闭。
- 极小团队的单点问题——为一次性问题建类别方案是过度工程。

### 作者在书中警告的失败模式

- 盯组合不盯原子：黑帽靠组合取胜，防守方若模仿攻击视角追着组合现象跑，问题只会越处理越多。
- 类别目标不可验收："提高安全性""加强防护"无法完成也无法证伪——必须写成可判定的消除/阻断目标。
- 修完一类就一劳永逸：攻击方法本身会演化（如注入从 SQL 扩展到 NoSQL），类别方案的覆盖范围要随技术栈变化重估——"安全是持续的过程"。

### 作者的盲点 / 时代局限

- "3 个月消除一类弱点"隐含大厂式的集中执行能力（能推行全局预编译改造）；中小团队需改为渐进式目标（先覆盖新代码、存量按风险分批）。
- 类别体系以 2014 年 Web 攻击面为背景，未覆盖供应链投毒、勒索运营、云配置错误等新类别——归因框架可迁移，类别清单需自行扩展。

### 容易混淆的邻近方法论

- 风险排序（DREAD）：给已分解的类别排优先级，是本 skill 第 4 步的输入，不替代分解本身。
- "治本"口号：本书的贡献正是把治本操作化——判据是"完成后该类对抗主动化"，没有这个判据的治本只是修辞。
