# 防线放在解释发生处：输入检查 vs 输出编码的裁决

## R — 原文 (Reading)

> "XSS的本质还是一种'HTML注入'，用户的数据被当成了HTML代码一部分来执行，从而混淆了原本的语义，产生了新的语义。"
> "但此时用户数据并没有结合渲染页面的HTML代码，因此XSS Filter对语境的理解并不完整。"
>
> — 方法论出处，第 3 章《跨站脚本攻击 XSS》3.3.4 / 3.3.2

---

## I — 方法论骨架 (Interpretation)

"在入口统一过滤"和"在出口按需编码"是长期争论。裁决判据只有一条：**语境在哪个环节才可确定，防线就必须放在哪个环节**。

- 入口处，数据还没有目的地：同一条输入之后可能进 HTML 正文、进属性、进 script、进 SQL、进日志——入口的过滤器不知道该按哪种规则处理，于是漏报（`<script src="$var">` 里用户只提交一个 URL，过滤器看是合法数据，放行即注入）与误杀（`1<2` 的尖括号被吞，用户语义被改）两头失败。这不是过滤器写得不好，是**位置**决定了它不可能知道答案。
- 消费点处，语境完全确定：这条数据将进入哪个解释器、占据结构中哪个位置一目了然，正确的编码/绑定动作可以精确执行。

所以正确分工是：**存储原始数据，每个消费点按目标语境各自处理**（store raw, encode per sink）。入口不是没事干——它的职责是格式白名单校验（长度、类型、字符集），服务于业务约束，不承担编码。

例外判据同样清晰：如果语境在提交时就已经确定（富文本本身就是完整 HTML、输出位置固定在正文），入口过滤就合法——但前提是用解析器按白名单清洗，而非关键词替换。

## A1 — 书中的应用 (Past Application)

### 案例 1: 输入侧过滤的两头失败（第 3 章 3.3.2）
- **问题**: 全站统一在提交时过滤 XSS，为何既漏攻击又伤用户。
- **方法论的使用**: 用两个实例证明位置错误——漏报：页面模板是 `<script src="$var">`，用户提交一个 URL 字符串，Filter 判为合法数据放行，输出后构成 XSS；误杀：`1+1<3` 被过滤成 `1 13` 类乱码，昵称里的引号被转义后显示异常。
- **结论**: "此时用户数据并没有结合渲染页面的 HTML 代码，Filter 对语境的理解并不完整"——输入侧不是坏一点，是结构上不可能正确。
- **结果**: 全章防御体系从输入检查转向"输出点按语境编码"，并确立输入端职责=格式白名单。

### 案例 2: magic_quotes_gpc——层级错配的历史标本（第 12 章 12.1 / 第 14 章）
- **问题**: PHP 全局自动转义输入（addslashes 级），为何被官方弃用。
- **方法论的使用**: 定位它作用的层（入口/GPC 输入层）与问题所在的层（Model/数据访问层）——SQL 注入要在消费点（SQL 构造处）解决，入口层的全局转义被 GBK 宽字节（0xbf5c 吃掉反斜杠）、无引号注入绕过，还衍生双重转义破坏数据。
- **结论**: "Model 层的事情搞到 View 层去解决，效果只会适得其反"——全局开关式防护制造虚假安全感。
- **结果**: 防御正位：SQL 在参数化绑定处、XSS 在输出编码处、命令注入在禁用危险函数处。

### 案例 3: 富文本的例外判据（第 3 章 3.3.5）
- **问题**: 富文本就是 HTML，输出编码会把它变成可见源码，怎么处理。
- **方法论的使用**: 按判据检验——富文本的语义在提交时已知（完整 HTML）、输出位置固定（正文、不进属性），语境在入口可确定，因此入口过滤合法；但必须用 HTML Parser 解析后按标签/属性/事件三层白名单清洗。
- **结论**: 例外不是偏好，是判据推导的结果；Samy Worm 证明黑名单式入口过滤（漏了 style 属性）依然全盘失效。
- **结果**: "入口过滤 vs 输出编码"之争被收敛为一个可判定问题：看语境何时可确定。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计表单/API 的校验方案，纠结在入口统一过滤还是在渲染/查询时处理。
2. 团队推行"全局过滤器/中间件统一转义"，需要评估其有效性与副作用。
3. code review 发现入口转义了特殊字符，但输出点仍是裸拼接。
4. 数据多处消费（存库、进日志、进 HTML、进 URL、进 React/模板渲染），要定处理职责分工。
5. 富文本/Markdown 类"内容本身是代码"的功能要设计过滤方案。

### 语言信号 (用户的话里出现这些就应激活)

- "输入过滤和输出编码到底用哪个？"
- "我们做个全局过滤器把特殊字符都转义掉？"
- "入库前都 escape 一遍是不是就安全了？"
- "用户输入 1<2 被过滤坏了，怎么办？"
- "input validation vs output encoding / sanitize on ingress or encode at sink / global escape middleware"

### 与相邻 skill 的区分

- 与 `whitehat-context-encoding` 的区别: 本 skill 裁决"防线放哪一环"（位置问题）；那个给出"到了输出点之后按语境选哪种编码"（选择问题）。先用本 skill 定位，再用那个选函数。
- 与 `whitehat-trust-boundary` 的区别: 那个按信任等级决定检查摆在哪条数据流上（跨域视角）；本 skill 按解释器与语境决定防线在哪一跳（消费点视角）。跨边界后仍要在消费点编码，两者叠加。
- 与 `whitehat-data-code-separation` 的区别: 那个是成因模型（数据被当代码）；本 skill 是由模型推出的位置裁决。成因解释"为什么要分离"，本 skill 回答"分离动作放哪做"。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **画数据流**：从入口到全部消费点列出数据的完整旅程（存储、缓存、渲染、查询、日志、第三方转发），每个消费点标注目标解释器。
   - 完成标准: 每个消费点有"解释器类型 + 结构位置（正文/属性/SQL 值/URL…）"标注。
2. **判定语境可确定的最早环节**：对每个消费点问——它的语境在入口时已知吗？
   - 完成标准: 每条数据流标注"语境出口才可知 / 入口即可知（富文本类）"。
   - 判停条件: 若某数据流语境入口即知且输出位置唯一固定（富文本），走第 4 步的入口白名单分支；其余一律走第 3 步。
3. **执行 store raw, encode per sink**：存储/传递保持原始数据；每个消费点在"数据变成代码"的那一刻按目标语境处理（参数化/按语境编码/保留字符转义）；入口只保留格式白名单校验。
   - 完成标准: 每个消费点有明确的处理动作；入口处不再承担编码职责；没有全局转义开关残留。
4. **处理例外分支**（富文本类）：入口用标准解析器解析后按白名单清洗（标签、属性、事件三层，事件一律禁、CSS 尽量禁），使用成熟库而非自研关键词替换。
   - 完成标准: 白名单清单显式列出允许的标签/属性；过滤后输出可二次校验无事件属性。
5. **复查与回归**：对两头失败模式各做一次验证——漏报侧：`src="$var"` 类消费点喂 URL 看是否放行后注入；误杀侧：`1<2`、含引号昵称入库再展示，语义不变。
   - 完成标准: 两类测试均按预期（消费点拦住攻击、入口不破坏语义）。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 跨信任域的检查摆位（外网数据进内网）——那是信任边界的职责，本 skill 只管解释器维度的消费点定位；两者叠加而非替代。
- 非注入类的输出处理（日志脱敏、隐私字段屏蔽）——目标是不泄露而非不被解释，按数据最小化处理。
- 已按消费点编码的存量系统再做合规检查——直接核对编码选型即可，不必重推位置。

### 作者在书中警告的失败模式

- 全局开关式防护：magic_quotes 类"看似内置的防护"造成虚假安全感，已知多种绕过且破坏数据——审计时把"依赖某个全局开关即安全"的假设逐条推翻。
- 输入侧过滤改挂数据语义：编码属于输出行为，不属于存储行为——入库前转义会让同一数据在不同语境展示错乱。
- 富文本例外被滥用：例外的前提（语境提交时已知+输出位置固定+解析后白名单）缺一条就退回黑名单老路（Samy Worm 的 style 属性漏网）。

### 作者的盲点 / 时代局限

- 案例基于 2014 年服务端渲染架构（MVC/模板引擎）；前后端分离下"输出点"移到浏览器端，但判据不变（React 默认转义也只覆盖 JSX 文本语境，进属性/URL 仍需各自处理）。
- 未讨论 API 网关/服务网格层的统一处理位（现代"框架层统一实施"的延伸），引用时需映射到当前架构的等效消费点。

### 容易混淆的邻近方法论

- 纵深防御第二层含义："在正确的地方做正确的事情"是总纲，本 skill 是它在注入类问题上的具体裁决——总纲覆盖网络/主机所有层，本 skill 只裁语境与消费点。
- 输入校验（格式白名单）：不是被否定，而是被重新定位——入口负责业务格式约束，不负责编码；两者职责互补。
