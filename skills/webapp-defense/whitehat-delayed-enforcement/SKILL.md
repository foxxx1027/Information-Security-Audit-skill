# 对抗性规则的"见光死"：延迟与分批处置

## R — 原文 (Reading)

> "当使用规则识别出垃圾账户后，过一段时间再做处理，这样恶意用户就摸不准到底触犯了哪条规则。同时还可以'打压'大部分账户，放过一小批账户。"
> "这些模型显然是不适合放在客户端的，因为这会让攻击者得以分析、研究并绕过这些规则。"
>
> — 方法论出处，第 16 章 16.4.2；第 2 章 2.3

---

## I — 方法论骨架 (Interpretation)

检测系统与普通系统的最大差别：它的对象会读它的输出并适应。如果"命中规则"与"受到处置"之间零延迟、全量执行，规则本身就变成了一个**探测器**——攻击者拿小批量样本试探，观察哪些被处置、哪些没被，几个来回就能二分出规则边界，然后绕开。规则一"见光"就死。

处置纪律因此有三条：

1. **延迟处置**：识别与处置之间拉开时间差，让"做了什么动作"与"什么时候被封"解耦——攻击者无法把处置时刻归因到具体行为。
2. **分批打压 + 放过小批**：命中名单打掉大部分、刻意放一小批不动。全量处置等于确认边界（触线的全被抓=没被抓的都在线外）；留一批"活口"使对手无法定位阈值，被控风险留在明处。
3. **检测逻辑保密（在服务端）**：模型与规则不下发到客户端——下发了就是发给对手抄作业（可逐条逆向绕过）；客户端只拿黑名单结果做匹配。

本质是不可预测性原则在运营侧的应用：让防御的反馈本身不可预测。适用前提是存在对抗回路——对手能观察到处置结果并调整；没有这个回路（纯内部审计）就不需要付延迟与漏网的代价。

## A1 — 书中的应用 (Past Application)

### 案例 1: 垃圾账户的延迟 + 分批处置（第 16 章 16.4.2）
- **问题**: 反垃圾规则命中即封，为何几天后规则集体失效。
- **方法论的使用**: 分析对抗回路——封禁动作即时且全量，恶意用户用小号试探即可摸清"到底触犯了哪条规则"，针对性绕开。
- **结论**: 识别后过一段时间再处理；同时打压大部分、放过一小批，让攻击者摸不准触发条件。
- **结果**: 风险控制住大部分的同时保住了规则的不透明性，"掌握主动权"而非陷入规则军备竞速。

### 案例 2: 恶意网址识别模型必须放服务端（第 2 章 2.3）
- **问题**: 浏览器拦截恶意网址，识别模型能不能放在客户端本地跑。
- **方法论的使用**: 检验逻辑保密性——模型下发客户端即可被逆向分析、逐条绕过（且本地采集访问历史有隐私与数据量问题）；厂商因此把模型留在服务端，浏览器端只拉取黑名单匹配。
- **结论**: 检测逻辑放在攻击者可控的一侧，其机密性无法保证——对抗性规则必须假设会被完整看到。
- **结果**: "云端模型+端侧黑名单"成为安全产品标配结构；IE8 XSS Filter 规则被逆向还原（成套正则被研究员提取）反向印证了端侧规则泄露是常态。

### 案例 3: 反垃圾规则保密（第 16 章 16.4.2 配套）
- **问题**: 规则即使不被逆向，被"试出来"怎么办。
- **方法论的使用**: 双管齐下——规则内容保密（服务端持有）+ 处置反馈不可预测（延迟/分批），两者共同切断"试探→归因"的学习回路。
- **结论**: 保密性属于不可预测性在运营侧的应用：对手既看不到规则（静态），也摸不到边界（动态反馈）。
- **结果**: 与三维特征体系配合，反垃圾系统形成"识别在云端、处置带延迟、边界不可测"的完整对抗结构。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计风控/反爬/反欺诈的处置策略：命中规则后是实时拦截、延迟封禁还是观察。
2. 规则上线后很快被绕过，怀疑触发条件被摸清，复盘处置策略。
3. 决定检测模型/规则的部署位置（客户端 SDK 还是服务端）。
4. 电商/支付风控处置恶意订单（自动拒绝还是延迟处理）。
5. 制定封禁的灰度策略（一次全封还是分批执行）。

### 语言信号 (用户的话里出现这些就应激活)

- "识别到恶意行为，要实时拦截吗？"
- "规则又被绕过了，他们好像知道我们怎么判的。"
- "风控模型要不要下发给 App 本地跑？"
- "抓到的垃圾账号直接全封了，有问题吗？"
- "should I block in real-time / rules getting probed / client-side risk SDK"

### 与相邻 skill 的区分

- 与 `whitehat-abuse-feature-model` 的区别: 那个管"怎么识别"（三维特征架构）；本 skill 管"识别之后怎么处置"。两者必须解耦——识别体系再好，处置泄漏边界照样被绕。
- 与 `whitehat-unpredictability` 的区别: 那个是总原则（关键值不可预测）；本 skill 是它在对抗运营的落地：让"处置反馈"这个值不可预测，并管规则保密与部署位置。
- 与 `whitehat-mitigation-vs-fix` 的区别: 那个对措施定级（治根因还是后果）；本 skill 优化处置时序——风控措施本身多是减损控件，但"怎么执行"决定它衰减多快。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **画出对抗回路**：确认对手能否观察到处置结果（被封/被拦/订单失败）并据此调整策略；列出可观察通道（错误提示、行为成功与否、时间戳）。
   - 完成标准: 回路图明确"对手看到什么信号"；确认无对抗回路则本 skill 不适用，直接即时处置。
2. **切断即时归因**：为处置设计时间差（识别后 T+n 执行）与批量策略（命中集分批执行、刻意留一小批观察不动）；阻断时刻与触发行为在对手视角不可关联。
   - 完成标准: 处置时延与批量参数有依据（风险暴露窗口 × 归因难度权衡）；"放过批"有留存理由（对照样本/边界模糊）。
   - 判停条件: 若单条风险敞口大于延迟窗口可承受损失（如正在进行的资金盗转），该项转即时止损通道，不套用延迟。
3. **审计反馈信号**：检查处置动作是否向对手泄露维度——错误文案是否区分"内容命中/行为命中"、拦截是否即时同步给客户端、封禁是否有固定阈值表现。
   - 完成标准: 对手可见通道里的信号不携带命中维度信息；文案、时延、成功率均做了模糊化。
4. **校验部署位置**：确认检测模型/规则全量在服务端；客户端只收结果（黑名单/分数），无本地可逆向的判定逻辑。
   - 完成标准: 客户端产物清单中无规则/权重/阈值明文。
5. **监控规则衰减并回流**：跟踪绕过率突变（对手摸到边界的信号）；被绕过样本回流特征体系；周期性重估延迟与批量参数。
   - 完成标准: 有绕过率监控指标与回流管道；参数复审有周期与 owner。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 进行中的破坏性攻击（在盗转资金、在拖库）——止损优先，延迟处置此时是为保规则而放任损失，本末倒置。
- 无自适应对手的场景（内部合规审计、一次性作弊）——没有学习回路，延迟与漏网是纯损失。
- 低价值高频规则的微调——延迟分批有运营成本，先确认该规则值得保护。

### 作者在书中警告的失败模式

- 识别即处置：把处置当确认信号送给对手——"抓到就处理"直觉在对抗场景直接反噬。
- 规则/模型下发客户端：可被逆向分析逐条绕过，"检测逻辑放在攻击者可控的一侧，其机密性无法保证"。
- 全量处置：无差别执行等于公开阈值（触线全被抓），给对手画出精确边界。

### 作者的盲点 / 时代局限

- 2014 年语境假设攻击者是"恶意用户+脚本"；现代黑产工具（群控、指纹浏览器、AI 试探）使探测效率更高，延迟窗口与放水比例需更保守，方法仍成立。
- 未讨论用户体验与法务约束（延迟封禁期间用户的损失责任、误放批次的下游影响），落地需补治理条款。

### 容易混淆的邻近方法论

- "放水养鱼"式钓鱼执法：本 skill 的放过小批是为保护规则边界，不是取证诱导；目的不同，红线也不同（不得主动诱导犯罪）。
- 灰度发布/金丝雀：那是发布工程的稳定性手段（控制爆炸半径）；本 skill 是对抗工程的保密手段（控制信息泄漏）——同形的"分批"，不同目标。
