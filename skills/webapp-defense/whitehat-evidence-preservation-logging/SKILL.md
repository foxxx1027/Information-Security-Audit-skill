# 证据保全：日志实时外送与现场保护优先

## R — 原文 (Reading)

> "攻击者入侵成功后，要做的第一件事情就是清除入侵痕迹，修改、删除日志文件，因此access log应当妥善保管，比如实时地发送到远程的syslog服务器上。"（第15章 15.2）
> "比较合理的做法是先将被入侵的机器下线，在线下进行分析。"（第18章 18.2）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

日志通常被当作调试工具设计（存本地、按空间轮转、够排查就行）。取证视角的评判标准完全不同：**证据的价值取决于攻击者够不够得着**。入侵者清痕的第一步就是改删本地日志——与被攻对象同机同生命周期的控制，注定与被攻对象同归于尽。

三条纪律：

1. **隔离生命周期**：日志实时流式外送到被攻系统权限之外（远程 syslog/独立日志集群），本地只做缓冲；外送侧只追加、时间同步。攻击者拿到应用或主机权限也删不到证据。
2. **响应先保全再处置**：事发时"保留证据（下线镜像、留现场）"与"最快止损（断网、封口令、补洞）"是一对矛盾——顺序与分工必须预先写进预案，临场抉择必然顾此失彼。
3. **双重工程约束**：日志属机密（含敏感信息，按机密保管），且写日志是 IO（高频触发的日志会拖垮应用，性能预算先评估）。

设计问句从"出了问题怎么查"换成"攻击者拿到最高权限后，哪些证据还活着"——日志架构由取证需求驱动，而不是调试需求驱动。

## A1 — 书中的应用 (Past Application)

### 案例 1: access log 实时外送远程 syslog（第15章 15.2）
- **问题**: 入侵者成功后第一件事是清除痕迹，本地日志还能作为证据吗？
- **方法论的使用**: 用"攻击者够不着"标准审查日志架构：本地日志在攻击者权限范围内必然不完整；改为实时发送远程 syslog 集中保存，本地仅缓冲。
- **结论**: 事后可追溯性是设计出来的——毁尸灭迹无法完成，取证链才存在。
- **结果**: 配套最小权限限制 Web 进程对自身日志的写权限；该要求在应用层复述为"安全日志属机密信息，应实时保存到远程服务器"（第18章）。

### 案例 2: 响应纪律——先下线保全，再线下分析（第18章 18.2）
- **问题**: 发现被入侵，立即在原机杀毒查马的处置对吗？
- **方法论的使用**: 编排证据与止损的矛盾：先弄清入侵者全部行为、评估损失，把被入侵机器下线在线下分析——既切断继续失血，又保全现场（内存、进程、临时文件等易失证据）。
- **结论**: 现场保护与最快处置是一对矛盾，预案必须预先写明两者的执行顺序与分工，而不是事发时临场抉择。
- **结果**: "保护现场 + 最快处置"成为应急响应的双原则，证据与止损的矛盾被制度化编排。

### 案例 3: 日志的性能预算（第18章 18.1）
- **问题**: 什么日志都记、高频记，安全吗？
- **方法论的使用**: 承认工程约束：写日志是 IO 操作，误报式高频触发的日志会拖垮应用——设计时评估写入频率，不适合启用的就不启用。
- **结论**: 日志方案要在取证价值、机密性、性能三者间做显式权衡；无预算的全面记录反而制造新的可用性问题。
- **结果**: 形成日志设计三问：记什么（取证价值）、谁能看（机密）、代价多少（性能）——与外送保真共同构成完整日志纪律。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新系统/新平台的日志架构设计（存哪、送哪、留多久、谁能删）。
2. 容器化/Serverless/易失基础设施迁移时的取证能力评估。
3. 编写或评审应急响应预案（IR plan）中的证据与止损编排。
4. 合规审计要求提供不可抵赖的操作留痕。
5. 事后溯源失败复盘："为什么被入侵了却查不出过程"。

### 语言信号 (用户的话里出现这些就应激活)

- "日志应该存哪里 / where to store logs"
- "容器销毁后日志还有吗 / ephemeral container logs"
- "被入侵后第一步做什么 / first step after breach"
- "取证怎么准备 / forensic readiness"
- "日志外送到哪里 / remote syslog / log shipping"

### 与相邻 skill 的区分

- 与 `whitehat-continuous-security-verification` 的区别：那边验证"制度/资产是否仍被覆盖"（Find-Fix 循环）；本 skill 解决"事件发生时证据链是否还存在"——一个是日常验证，一个是取证准备，同属运营但问题不同。
- 与 `whitehat-attack-chain-pruning` 的区别：那边限制攻击者拿到权限后的破坏路径；本 skill 承认权限可能失守，保证失守后证据仍在——攻击链裁剪会砍掉"攻击者删日志"的能力，本技能假设那跳砍不断时仍要留证。
- 与一般"安全监控"方法的区别（本书未单列 skill）：监控用日志做检测（实时告警）；本 skill 保证日志本身可信、可作证据——检测消费日志，本技能生产可信日志，先此后彼。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点取证所需证据源**
   - 完成标准: 列出事件重建所需记录：访问日志、认证记录、特权操作、应用错误、网络流、变更记录；每项标注当前存储位置与保留周期。
   - 判停条件: 若系统为纯外部托管且完全无日志掌控权（日志能力由平台决定），转为向平台提出取证需求清单并评估替代证据源。

2. **逐项检验"攻击者够不着"**
   - 完成标准: 对每个证据源回答：拿到主机/应用最高权限的攻击者能否删除或篡改它？答案为"能"的项（本地存储、同集群存储、可写 API）全部标红。

3. **设计隔离生命周期**
   - 完成标准: 实时流式外送到被攻权限之外（集群外/独立账号/只追加存储）；本地仅缓冲；时间同步（NTP）就位；外送通道自身有认证与加密；敏感字段按机密等级处理；写入频率过性能预算。

4. **编排响应预案**
   - 完成标准: 预案写明：谁下线保全、谁止损处置、执行顺序（先下线保全再分析）、易失证据（内存/进程）的采集动作、决策人——不留"临场决定"的空白。

5. **演练与复核**
   - 完成标准: 至少一次桌面演练验证预案可执行；抽查一次"删除本地日志"模拟攻击，确认远端证据完整；保留周期满足溯源与合规双重需求。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 业务日志的字段设计与分析（漏斗、调试）——那是可观测性工程；本技能只裁决证据链，但可要求"调试日志不得污染取证日志的预算"。
- 检测规则与告警内容运营（SIEM 用例）——消费侧问题。
- 日志留存期限的法规解释（各合规框架条目）——查对应法规，本技能只提供"够取证"的下限思考。

### 作者在书中警告的失败模式

- 日志只存本机——入侵者第一步删日志，事后无据可依。
- 事发时临场抉择"先查还是先断"——证据与止损的矛盾没有预案，必然顾此失彼。
- 无节制记录——高频 IO 拖垮应用；日志含敏感信息却按普通数据保管。

### 作者的盲点 / 时代局限

- 书中方案停留在"远程 syslog"形态；云原生下的对应物（集群外日志服务、对象存储锁定 WORM/Object Lock、审计日志独立账号）书中未覆盖——verified V2 已按容器场景外推：容器易失=本地日志必然随尸灭迹，实时流式外送+只追加+时间同步是最低配置。
- 未讨论证据的法律效力链（哈希固化、时间戳签名）与隐私约束（日志中的个人信息脱敏）——今日取证设计需补充。
- 未覆盖攻击者驻留外送通道篡改（agent 失陷后伪造日志）的场景，需要外部基准比对补偿。

### 容易混淆的邻近方法论

- 持续安全验证（日常验证 vs 取证准备）。
- 攻击链裁剪（限制失守后果 vs 假设失守仍留证）。
- 纵深防御（整体分层 vs 证据链这一条专项——本技能可视为纵深思想在"可追溯性"层的落实）。
