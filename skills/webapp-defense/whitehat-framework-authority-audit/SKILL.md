# 框架与权威的双面审计：权威不构成安全证据

## R — 原文 (Reading)

> "Web框架的开发者在设计安全方案时，有时会缺乏来自安全专家的建议。所以开发者在使用框架时，应该慎重对待安全问题，不可盲从官方指导文档。"（第12章 12.2）
> "很多Web框架提供的安全解决方案有时并不可靠，我们仍然需要自己实现一个更好的方案。同时Web框架自身的安全性也不可忽视"（第12章 12.8）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

"我们用了 X（知名框架/官方推荐/市场第一），所以安全"——这是标签式记忆，不是安全论证。权威与流行度证明的是生态成熟，不是无漏洞。

审计一个依赖要同时查两条线，缺一不可：

1. **它提供的安全**：文档承诺的防护是否真的覆盖全部场景？默认配置是否默认安全？正确做法是对安全特性做一次对抗性验证——写个绕过 PoC 试试，绕不过去再依赖；官方文档可能推荐不完整方案（转义字符集不全、教用户关掉 auto-escape）。
2. **它自身的安全**：框架也是代码，也会出 RCE（Struts2/Spring/Django 都出过）；更糟的是它属于基础设施——业务不愿频繁升级，漏洞修补滞后而影响面是所有基于它的站点。

由此推出三个动作：依赖清单与版本台账、安全特性独立验证（PoC）、组件 CVE 史与升级节奏评估。框架能降低风险，但"降低"与"消除"之间正是评审要量化的一段。

## A1 — 书中的应用 (Past Application)

### 案例 1: jQuery html()——框架不解决逻辑问题（第3章 3.2.9）
- **问题**: "我们用 jQuery/成熟 JS 框架，XSS 应该没问题吧？"
- **方法论的使用**: 对框架提供的安全做验证：html() 带参数即写 innerHTML，用户可控参数传入必然 XSS；Dojo/YUI 的示例页与组件自身也各有 DOM XSS。
- **结论**: 框架只是语言封装，不解决代码逻辑上的安全问题；sink 的语义掌握在开发者手里，"选型成熟"不等于"输出安全"。
- **结果**: 确立 grep innerHTML/document.write/html() 等 sink 并查参数来源的审计动作，安全不能外包给框架选型。

### 案例 2: Struts2/Spring MVC/Django 框架自身 RCE（第12章 12.7-12.8）
- **问题**: 框架是业界主流，能默认信任吗？
- **方法论的使用**: 查框架自身安全线：Struts2 OGNL 参数映射 + \u0023 绕过 # 过滤直达命令执行；Spring MVC 数据绑定暴露 class.classLoader 即 RCE；Django .po 文件处理命令注入——均为当年主流框架。
- **结论**: 流行度与安全无因果关系；数据绑定/表达式引擎把内部对象图暴露给请求参数，等价于内置远程执行入口。
- **结果**: 确立"框架自身也要审"的第二条线：版本台账 + 安全公告跟踪 + 升级流程，作为组件治理的常规项。

### 案例 3: 存储过程防注入——"用了 X 所以安全"的标签式记忆（第7章 7.3.2）
- **问题**: 团队认为"SQL 都走存储过程，注入不存在"。
- **方法论的使用**: 对其提供的安全做验证：存储过程内部若拼接动态 SQL（外部参数直入），注入点只是从应用层移进数据库；内置过程（xp_cmdshell 等）反而可能成为武器库。
- **结论**: 机制的有效性取决于实现细节（是否真参数化），标签式记忆"用了 X 所以安全"掩盖了需要逐处确认的事实。
- **结果**: 注入审计范围扩展到数据库内部代码（存储过程、触发器、定时任务），与框架两面审计同一逻辑。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 技术选型/安全组件采购评审：面对"大厂出品/榜单第一/事实标准"的论证。
2. 按官方文档实现了安全功能，准备宣布"已覆盖 XSS/CSRF/注入"。
3. 建立依赖治理：版本台账、升级策略、组件 CVE 跟踪。
4. 团队争论"要不要信任框架默认值"（auto-escape、内置 CSRF、参数绑定）。
5. 供应链事件（流行包爆洞）后的应急评估：我们暴露面多大。

### 语言信号 (用户的话里出现这些就应激活)

- "官方文档就是这么写的 / follow the official docs"
- "大厂/主流框架应该没问题 / trust the framework"
- "用了 Django/Rails/Spring 还会有漏洞吗 / framework protects us right"
- "选哪家安全产品 / security vendor selection"
- "框架要不要升级，业务不敢动 / dependency upgrade risk"

### 与相邻 skill 的区分

- 与 `whitehat-crypto-misuse-audit` 的区别：那边说"不要自研、用专家实现"；本条补充另一半纪律——用了专家实现也要独立验证其安全特性。两条合起来才是完整的"外购安全"态度。
- 与 `whitehat-attack-surface-reduction` 的区别：那边做功能存废（删不删）；本条对保留下来的依赖做两面验证（可不可信）。
- 与 `whitehat-root-cause-patch-discipline` 的区别：那边管补丁质量；本条管依赖引入前的信任评估——一个在修复端，一个在引入端。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **建依赖清单与版本台账**
   - 完成标准: 直接依赖与关键传递依赖列出，含版本、用途、暴露面（是否处理用户输入/是否面向公网）、维护状态。
   - 判停条件: 若评审对象是纯自研代码且无任何第三方安全依赖，则只剩"官方文档式"内部规范审查，缩小范围后继续。

2. **第一面：验证它提供的安全**
   - 完成标准: 对每个被依赖的安全特性列出其承诺覆盖的场景，对每条承诺构造绕过样本实测（转义是否覆盖全部输出语境、CSRF 是否覆盖全部写入口、参数绑定是否可触达元对象）；绕过成功项标记为"不可依赖，需自补方案"。

3. **第二面：验证它自身的安全**
   - 完成标准: 每个依赖查 CVE 历史（数量、严重度、修复时长）、当前版本是否落后、升级路径与破坏性变更；结果写成风险台账而非"通过/不通过"。

4. **输出选型/裁决结论**
   - 完成标准: 结论基于两面证据（PoC 结果 + CVE 台账），显式区分"证据支持""待验证假设""标签式断言"；对不可依赖项给出自补方案（安全函数、中间件、配置收紧）。

5. **常态化**
   - 完成标准: 版本台账接入安全公告订阅与升级流程；对安全特性的 PoC 验证纳入框架大版本升级的回归项。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 组件的功能/性能/成本选型——非安全问题，本 skill 不给意见。
- "自研还是外购"的通用工程决策——本 skill 只裁决"依赖的安全可信度"，且默认倾向使用成熟实现（不迷信≠不用）。
- 一次性 demo/原型中的依赖——生命周期太短，评审成本大于收益，标注"不得进入生产"即可。

### 作者在书中警告的失败模式

- 盲从官方文档——文档推荐的转义方案可能不完整，甚至教用户关闭默认防护。
- 把安全外包给框架选型——html() 即 innerHTML，sink 语义在开发者手里。
- 只看它提供的安全、不看它自身的安全——主流框架同样出 RCE，且基础设施升级滞后会放大后果。
- 标签式记忆（"用了存储过程/预编译所以安全"）——机制有效性取决于实现细节，须逐处确认。

### 作者的盲点 / 时代局限

- 书中案例（Struts2 OGNL、Spring classLoader、Django .po）是 2010-2013 代框架；今日同类风险平移到新载体：依赖链投毒（typosquatting）、CI/CD 集成凭证、容器基础镜像、npm/PyPI 供应链——"两面审计 + 版本台账"方法直接迁移。
- 未提出 SBOM、锁文件审计、自动依赖更新等现代治理工具，可作为步骤 1/5 的增强。
- 对"对抗性验证"只给了思想（写绕过 PoC），未给用例来源——今日可用 OWASP 测试用例库补齐。

### 容易混淆的邻近方法论

- 密码学误用审计（不自研 vs 不迷信——一枚硬币的两面，对象不同：前者审方案构造，本条审组件信任）。
- 攻击面收敛（依赖删减 vs 依赖验证）。
- 持续安全验证（对制度的周期复验 vs 对组件的一次性双面评估——台账建立后两者衔接）。
