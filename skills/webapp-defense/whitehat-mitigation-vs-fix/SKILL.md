# 减损控件 ≠ 修复控件：缓解措施的分级评估

## R — 原文 (Reading)

> "严格地说，HttpOnly并非为了对抗XSS——HttpOnly解决的是XSS后的Cookie劫持攻击。"
> "添加了HttpOnly，不等于解决了XSS问题。"
>
> — 方法论出处，第 3 章《跨站脚本攻击 XSS》3.3.1

---

## I — 方法论骨架 (Interpretation)

安全措施不都在同一个层级起作用，验收前必须先问三个问题：

1. **治根因还是治后果？** 根因修复消除漏洞存在本身（输出编码消除 XSS）；减损控件（mitigation）只切断漏洞被利用后的某条损失路径（HttpOnly 切断"凭证被偷读"这一条，XSS 本身还在，还能代办业务操作）。把减损当修复结案是最常见的验收错误。
2. **触达哪类损失？** 一个漏洞的后果往往有多类（XSS：凭证外泄、行为代办、钓鱼），单一减损控件只覆盖其中一类——HttpOnly 管不了"以用户身份发请求"，验证码挡不住已驻留页面的 XSS 后台代答。残余风险=后果全集减去已覆盖部分。
3. **覆盖率要求是什么？** 有些减损控件是全有或全无：HttpOnly 必须在所有 Set-Cookie 处生效，漏一处即整体失效；这类措施的部署核对比单点加固更关键。

分级之后对待方式不同：减损控件可以叠加、要写清"减损后残余风险"的验收口径，但不能替代根因修复；报告措辞从"已防住"改为"已抬高成本/已切断损失路径 X"。

## A1 — 书中的应用 (Past Application)

### 案例 1: HttpOnly 的精确定位（第 3 章 3.3.1）
- **问题**: 给 Cookie 全加了 HttpOnly，能否宣布 XSS 问题解决。
- **方法论的使用**: 按"治根因还是后果"分级——HttpOnly 切断的是 XSS 后的 Cookie 劫持这一条损失路径；再按"触达哪类损失"检查——XSS 还能模拟 GET/POST 代办业务操作、读取页面数据（pr114 两类后果）。
- **结论**: HttpOnly 是减损控件且要求全覆盖（"漏掉了一个地方，都可能使得这个方案失效"），"添加了 HttpOnly 不等于解决了 XSS 问题"。
- **结果**: 部署方案定为：会话中间件统一下发、禁手写 Set-Cookie、响应头扫描核对覆盖率；XSS 本身的修复仍走输出编码。

### 案例 2: 关闭错误回显——抬高侦察成本而非堵注入（第 7 章）
- **问题**: 生产环境关掉数据库错误回显，注入风险是否解除。
- **方法论的使用**: 分级判定——错误回显给攻击者提供"注入调试器"（库类型、查询伪代码、行号）；关掉它抬高侦察成本，但注入本身还在：攻击演化出盲注（真假条件对比）与 Timing Attack。
- **结论**: 属信息泄露面收敛的减损措施，不可作为注入的修复结案；参数化才是根因路径。
- **结果**: 防御清单上两项并存且标注层级：关回显（减损）+ 预编译（根因）。

### 案例 3: 验证码是辅助手段而非主防线（第 4 章 4.3.1）
- **问题**: 全站加验证码是否就是 CSRF 的主防线。
- **方法论的使用**: 分级评估——验证码把"静默自动请求"变为"必须人工交互"，原理上打断 CSRF；但体验约束使它无法覆盖所有操作，且强度随攻击者自动化能力衰减（Canvas 像素级识别案例）。
- **结论**: 定位为"辅助手段而非主要方案"，与 Token 分层使用：高敏感低频操作用验证码，全量写操作用 Token。
- **结果**: 防御方案的主/辅层级显式化，避免用辅助手段替代主方案。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 验收整改：开发说"已加 HttpOnly/已上 WAF/已加验证码"，判断能不能关闭漏洞工单。
2. 设计缓解方案（根因短期修不掉），需要定义"减损后残余风险"的验收口径。
3. 核验渗透测试报告中的修复结论，防止"缓解当修复"过关——只审结论的定级，不指导报告本身的结构与写法。
4. 写安全方案/汇报，需要准确表述措施的作用层级。
5. 决定多个减损控件的叠加组合（HttpOnly+WAF+限速各覆盖什么损失）。

### 语言信号 (用户的话里出现这些就应激活)

- "加了 HttpOnly，这个 XSS 是不是可以关了？"
- "登录接口加了验证码，能防撞库吗？"
- "上了 WAF 应该就没事了吧？"
- "这个问题修不动，先缓解一下怎么算达标？"
- "is HttpOnly enough to close XSS / does captcha stop credential stuffing / mitigation vs fix"
- 排除信号（出现这些**不激活**）："渗透测试报告的目录结构怎么组织""报告章节怎么排比较专业"——纯文书结构/排版咨询，与任何具体措施的定级验收无关，不调用本书技能。

### 与相邻 skill 的区分

- 与 `whitehat-defense-in-depth` 的区别: 那个设计多层结构并划定每层守护边界（体系视角）；本 skill 对**单个措施**做分级验收（控件视角）——纵深体系里的每个控件拿出来，都要过本 skill 的三问。
- 与 `whitehat-unpredictability` 的区别: "让攻击方法失效"（ASLR/DEP 类）在本书中被承认是正统防御的一种；本 skill 负责在对外承诺时给它准确定级（抬高利用成本，非消除缺陷）。
- 与 `whitehat-continuous-security-verification` 的区别: 那个管"措施部署后是否持续有效"（运营验证）；本 skill 管"措施在验收时算哪一级"（定级结案）。先定级，再纳入持续验证。
- 与 `whitehat-security-assessment` 的区别: 那个管"资产→威胁→风险→方案"的评估四阶段流程；本 skill 只在整改验收环节给措施定级。"渗透测试报告怎么组织/怎么写"属纯文书问题，两边都不归。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **描述措施与目标威胁**：写清措施针对的漏洞/攻击，及其作用点（入口、执行点、后果环节）。
   - 完成标准: 能一句话回答"它切断的是链条的哪一环"。
2. **分级判定**：问三个问题——治根因还是治后果？触达后果全集中的哪几类？该措施是否全有或全无（覆盖率要求）？
   - 完成标准: 结论为"根因修复 / 减损控件（覆盖损失 X、Y）"之一；全有或全无型措施标注覆盖率要求。
   - 判停条件: 若措施就是根因修复（如输出编码之于 XSS、参数化之于注入），按修复验收直接关闭，跳到第 5 步记录。
3. **计算残余风险**：列出该漏洞全部后果类型，减去措施已覆盖部分，明确写出"减损后仍存在的损失"。
   - 完成标准: 残余风险清单可被业务方确认接受；对冲成本（打码平台、代理池对抗限速）写进评估。
4. **叠加与覆盖率核对**：为残余风险补充其他层控件；对全有或全无型措施做覆盖核对（扫描响应头/全量配置核查）。
   - 完成标准: 每类残余损失至少有对应层或显式风险接受；覆盖率核对有工具证据。
5. **按准确口径结案**：工单/报告措辞分级——"已消除成因"或"已切断损失路径 X（残余风险 Y 已由 Z 缓解/接受）"。
   - 完成标准: 没有任何减损控件被表述为"已修复漏洞"；验收人与业务方对残余风险签字。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 设计多层防御体系（选哪些层、各层职责划分）——用纵深防御；本 skill 只对单措施定级。
- 根因修复本身的实现选型——分级确认是修复后，具体怎么修走对应技术方法（编码矩阵、参数化等）。
- 供应链/第三方组件的风险接受决策——那是"修在最高杠杆层"与业务决策的组合问题。

### 作者在书中警告的失败模式

- "已加 HttpOnly 即已解决 XSS"：书中点名的高频错误——凭证路径被切断，行为代办路径仍开放。
- 缓解措施的覆盖率被忽视：Set-Cookie 散落各模块，漏一处整套失效；TRACE 回显类老特性还会架空安全标记（XST）。
- 辅助手段替代主防线：验证码体验上不能全量部署、强度随自动化能力衰减，当主方案用必被对冲。

### 作者的盲点 / 时代局限

- 2014 年语境下 WAF/风控的对抗演化（规则被调优绕过、机器学习绕过）着墨少；现代验收需补"减损控件自身的对抗衰减"评估维度。
- 未给出"风险接受"的正式流程（谁有权接受残余风险、接受后多久复审），引用时按组织治理补齐。

### 容易混淆的邻近方法论

- 纵深防御：多层配合是结构，控件分级是验收——没有分级的"多层"可能全是减损层而无根因层，看似纵深实则零修复。
- "让攻击方法失效"（不可预测性的反向应用）：同为抬高成本的路线，区别在于它主动破坏利用条件（可设计、可验证），而许多减损控件只遮蔽后果——定级时前者可承诺更高。
