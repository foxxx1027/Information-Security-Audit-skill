# 解析与口径一致性审计：校验与使用必须同解释器、同数据形态

## R — 原文 (Reading)

> "这往往是因为应用的开发者没有深入理解Web Server的细节所导致的。"（第8章 8.2）
> "要解决这种问题，需要统一数据库、操作系统、Web应用所使用的字符集，以避免各层对字符的理解存在差异。"（第7章 7.2.4）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

一份数据从进入到生效，往往要穿过好几个"解释器"：前端正则、WAF、路由、Web 服务器、脚本引擎、数据库。每个解释器都按自己的规则回答"这串字节是什么意思"——按什么字符集切分、取哪段当后缀、截断到多长、怎么规范化 URL。

漏洞出现在口径差上：校验组件认为无害的输入，执行组件可能解释成武器。单看每一层都没错，组合起来就是漏洞。

由此推出三条纪律：

1. **同解释器**：校验必须发生在与最终消费数据相同的解析口径下（最好同进程、消费点之前），跨层校验一律存疑。
2. **同数据形态**：校验时的值必须与落库/落盘/执行的值同形（截断前后、解码前后、规范化前后）。
3. **同时点**：数据被修改的每一步（重定向、二次解码、存储后再读出）之后，校验要重新成立。

审计动作不是试 payload，而是先画解释链：列出同一输入经过的所有解释环节，逐对找口径差。

## A1 — 书中的应用 (Past Application)

### 案例 1: Apache 多后缀解析 vs 应用层后缀校验（第8章）
- **问题**: 应用只校验"上传文件末尾是 .rar"即放行，攻击者上传 a.php.jpg。
- **方法论的使用**: 找出校验器（应用按末尾后缀判断）与解析器（Apache 不认识 .rar 时从后往前找，解析成 .php）的口径差。
- **结论**: 校验规则与服务器真实解析规则不一致，等于没有检查；同族还有 IIS 分号截断、fastcgi 路径回溯。
- **结果**: 确立"校验以容器实际解析口径为准"的规则，多后缀/截断类绕过全部归入同一漏洞族。

### 案例 2: GBK 宽字节——三层字符集理解不一致（第7章 7.2.4）
- **问题**: PHP addslashes() 在 0xbf27 前插入反斜杠得到 0xbf5c27，本应转义单引号。
- **方法论的使用**: 画出字节流经过的三个解释环节：应用按字节转义，数据库按 GBK 双字节切分——0xbf5c 被合成一个字符，反斜杠被"吃掉"，单引号逃逸。
- **结论**: 转义有效的前提是编码一致；解法是数据库、OS、应用三层统一 UTF-8。
- **结果**: 宽字节注入（SQL 与 XSS 两个场景）都归因到"跨层编码口径不一致"，统一字符集成为标准修复。

### 案例 3: SQL Column Truncation——校验值与落库值不同形（第7章 7.2.5）
- **问题**: MySQL 非 strict 模式下超长值被静默截断；攻击者注册 "admin+55空格+x"。
- **方法论的使用**: 对比"校验时的值"（提交原文，唯一性检查通过）与"落库后的值"（截断成第二个 admin）——同解释器但不同数据形态、不同时点。
- **结论**: 安全关键的唯一性/等值判断必须对齐存储层真实截断行为；WordPress 2.6.1 即真实受害案例。
- **结果**: "校验与使用同形态"成为独立审计项，与 URL 解析差异、后缀校验差异同族处理。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计"前端/网关做一层校验、后端另一层执行"的方案：URL 白名单防 SSRF、前端文件名校验、网关参数过滤。
2. 文件上传/路径处理功能评审：后缀校验、MIME 判断、文件头嗅探与服务器解析行为的对齐。
3. 系统字符集/编码混杂（历史 GBK 系统、多语言存储）时的注入面评估。
4. WAF/过滤规则与真实浏览器、真实后端框架解析行为的差异验证。
5. 数据入库后再次读出使用（唯一性判断、审批标记）的流程设计。

### 语言信号 (用户的话里出现这些就应激活)

- "前端做了校验，后端还需要吗 / client-side validation enough"
- "为什么转义了还是被注入 / escaped but still injected"
- "URL 白名单防 SSRF / SSRF whitelist bypass"
- "文件后缀校验被绕过 / extension check bypass"
- "双次 URL 解码 / double decoding / normalization bypass"

### 与相邻 skill 的区分

- 与 `whitehat-trust-boundary` 的区别：那边回答"检查点应该摆在哪条边界上"（位置问题）；本 skill 回答"边界两端的两个组件对同一数据的理解是否一致"（口径问题）——检查点摆对了位置，口径不一致照样被绕。
- 与 `whitehat-whitelist-first` 的区别：白名单是校验内容的选型策略；本 skill 审计的是校验所依据的解析口径本身与消费端是否同轨。
- 与 `whitehat-defense-at-interpretation` 的区别：那边裁决"输入检查 vs 输出编码"；本 skill 覆盖更广的双解释器场景（服务器解析、字符集、截断），两者经常组合使用。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **画出解释链**
   - 完成标准: 对目标数据流列出全部解释环节（校验器、规范化器、路由、容器、引擎、存储），每个环节标注其解析口径：字符集、后缀规则、长度/截断语义、URL 规范化行为、解码次数。

2. **逐对找口径差**
   - 完成标准: 对"校验环节 → 最终执行环节"的每一对，明确回答：校验时数据的形态与执行时是否同形？校验所用的解析规则与执行组件是否一致（含版本差异）？重定向/二次解码/截断之后校验是否仍成立？
   - 判停条件: 若校验与消费在同一进程、同一库、同一数据形态下完成，且中间无修改步骤，则该数据流通过，跳到下一条数据流。

3. **构造双口径差异样本验证**
   - 完成标准: 对每个疑似口径差，构造一个"校验端判合法、执行端变武器"的具体样本（多后缀、宽字节序列、超长截断值、畸形 URL），并实测或给出可复现推导。

4. **按口径统一修复**
   - 完成标准: 修复落在消除口径差上——校验移到消费点同进程执行；或统一各层字符集/严格模式；或规范化后校验且重定向每跳重校验；禁止"在校验端追加黑名单条目"式修补。

5. **复核**
   - 完成标准: 差异样本复测全部失败（校验端或执行端任一处被拦截），且正常业务输入不被误杀。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单一解释器内部怎么写好一条校验逻辑（转义表、白名单条目）——那是编码函数与白名单的选型问题。
- 纯客户端 UX 层校验（防误操作）——它本来就不承担安全职责，无需做口径审计，直接标记"服务端必须独立校验"即可。
- 协议层的语义歧义（同一字段不同实现本来就该不同理解）——超出 Web 数据流审计范围。

### 作者在书中警告的失败模式

- 开发者不理解 Web Server 细节就写校验——应用层认为安全，容器按另一套规则解析执行（多后缀、分号截断、cgi.fix_pathinfo 路径回溯）。
- "转义了就安全"——escape 的有效性以编码一致为前提，GBK 下反斜杠被双字节吃掉。
- 校验时的值 ≠ 落库后的值——静默截断让唯一性检查形同虚设。

### 作者的盲点 / 时代局限

- 书中案例绑定 2014 技术（IIS 6、cgi.fix_pathinfo、老版浏览器容错解析），具体漏洞多已修复，但"双解释器口径差"的漏洞族在 SSRF、JSON 解析差异、路径规范化（..;/）、Unicode 归一化（同形字符）中持续重现。
- 未系统化提出"解析差异测试"方法（对畸形输入分别喂给校验端与执行端对比结果），今日已成标准做法，可作为本 skill 步骤 3 的强化。

### 容易混淆的邻近方法论

- 信任边界建模（检查位置 vs 解析口径）。
- 白名单优先（校验内容选型 vs 校验口径对齐）。
- 数据与代码分离（注入成因模型 vs 双解释器一致性——前者解释漏洞为何存在，本条解释防御为何失效）。
