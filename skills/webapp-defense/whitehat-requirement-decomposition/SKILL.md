# 把模糊安全需求分解为具体威胁

## R — 原文 (Reading)

> "'提高密码复杂度'这个安全需求，其本质其实可以分解为：（1）如何对抗暴力破解；（2）如何防止密码中包含个人信息。"
>
> — 方法论出处，第 16 章《互联网业务安全》16.1.2 什么是好的安全方案

---

## I — 方法论骨架 (Interpretation)

产品方给安全需求时几乎总是给口号："让转账更安全""提高密码复杂度""防止账号被盗"。口号直接实现必然做偏——因为没人说得清它防什么、防到什么程度算完成。

分解动作把口号翻译成威胁清单：

1. **展开"更 X"背后的攻击场景**：把抽象目标还原为"谁、用什么手段、达成什么后果"的若干条具体威胁。密码复杂度 → 对抗暴力破解（在线/离线）、防止密码包含个人信息（可猜测）——每条都是可独立判定成败的命题。
2. **逐条设计机制**：每条威胁对应一个或一组机制（抗暴力破解 → 限速/锁定；防个人信息 → 与注册资料比对拒绝），机制之间不混算。
3. **对齐验收标准**：从"提高了安全性"（不可验收）换成"防住了威胁清单上的每一条"（可逐条测试）。上线后说得清防住了什么、没防什么。

这个动作的前置性很重要：它发生在威胁建模与方案设计之前，决定后面所有工作的靶子。需求访谈（问业务方"要保护什么"）是它的输入端；数据定级是它在资产维度的制度化形态。

## A1 — 书中的应用 (Past Application)

### 案例 1: "提高密码复杂度"的两条分解（第 16 章 16.1.2）
- **问题**: 产品要求提高密码复杂度，直接照做（加长度/字符集要求）会有什么问题。
- **方法论的使用**: 分解为两条可判定威胁——(1) 对抗暴力破解；(2) 防止密码中包含个人信息。两条的目标函数不同：前者要熵，后者要"与个人资料无关"（纯长度要求防不住生日密码）。
- **结论**: 每条独立设计机制：抗破解 → 登录限速/锁定；防个人信息 → 注册资料比对、生日/手机号出现在密码中即拒绝。
- **结果**: 需求从口号变成两条可验收的技术目标，上线后可逐条证明防住了什么。

### 案例 2: 资产划分靠访谈——"要安全"翻译为"保护什么"（第 1 章 1.6）
- **问题**: 安全评估第一阶段就要定资产等级，但业务方只会说"我们要安全"。
- **方法论的使用**: 用访谈把口号还原为对象清单：与业务负责人逐一确认最重要的数据是什么、放在哪、谁可访问——资产等级划分由此产生，而非安全团队臆断。
- **结论**: 需求分解在评估流程的最前端：先有"保护什么"，才有后面的威胁分析与方案。
- **结果**: 资产划分/数据定级成为后续一切评审（按数据级别选保护模块）的依据。

### 案例 3: SDL 需求阶段的 checklist 化（第 17 章 17.4）
- **问题**: 项目立项时安全需求如何落地成可核对条目，而不是再次变成口号。
- **方法论的使用**: 需求阶段引入四类安全 checklist + 数据定级——把"本项目要安全"拆解为逐项可判定的需求条目，设计阶段照条目选配保护模块。
- **结论**: 分解动作制度化后，评审从"重新发明方案"变为"按级选配、按单核对"。
- **结果**: 需求分解的产出（威胁条目+定级）成为整个 SDL 流程的锚点。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 产品经理/业务方提了一句模糊安全需求（"让 X 更安全""防止账号被盗"），要接需求、出方案、报工期。
2. 写安全需求文档/评审 checklist，需要可判定条目而非形容词。
3. 与业务方对齐验收标准，避免上线后"说不清防住了什么"。
4. SDL/需求评审阶段，把安全目标转成设计输入。
5. 复盘"做了很多安全工作但没效果"的项目，检查当初需求是否可验收。

### 语言信号 (用户的话里出现这些就应激活)

- "产品说要让转账/账号更安全，怎么接这个需求？"
- "安全需求怎么写才不空？"
- "这个安全项目怎么验收？"
- "怎么防止用户账号被盗？"（作为需求而非事件提出时）
- "vague security requirement / how to make X more secure / acceptance criteria for security work"

### 与相邻 skill 的区分

- 与 `whitehat-security-assessment` 的区别: 四阶段评估面向"已有系统"（资产→威胁→风险→方案）；本 skill 面向"一句话需求"（口号→威胁→机制→验收），多用于需求/设计期。两者的威胁枚举动作相通，输入不同。
- 与 `whitehat-decompose-by-attack-class` 的区别: 那个把涌来的**问题**归因到攻击类别（运营视角）；本 skill 把提出的**需求**分解为威胁条目（需求视角）。前者治乱，后者立靶。
- 与 `whitehat-solution-acceptance-checklist` 的区别: 那个评审"方案本身好不好"（有效/体验/性能/低耦合/易扩展五条）；本 skill 在更上游，先定义"要防住什么"，产出方案后再过那个清单。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **复述并追问目标对象**：把口号原话记下，追问要保护的对象与场景（谁的什么资产、在什么操作里、担心谁攻击）。
   - 完成标准: 得到"保护对象 × 操作场景"的初步范围；无法回答时列出待访谈问题而不是自行假设。
2. **分解为威胁条目**：把目标展开为 3–7 条"攻击者用手段 X 达成后果 Y"的具体威胁，覆盖不同攻击者角色（外部攻击者、被骗的用户、被盗会话的持有者、内部人员）。
   - 完成标准: 每条是可判定命题；无"提高/加强/优化"类形容词残留。
   - 判停条件: 若需求方追问后发现对象范围过大（整站安全），退回资产分级/评估四阶段先收敛范围，本 skill 等范围明确后继续。
3. **逐条设计机制**：每条威胁绑定至少一个机制，注明机制的作用层（认证/风控/流程/监控）与依赖前提。
   - 完成标准: 威胁→机制映射表完成；机制冲突（如安全与体验）显式标注留给权衡。
4. **对齐验收标准**：为每条威胁写"防住"的可测试判据（构造该攻击场景应被阻断/检出/限额），与需求方确认范围外的残余风险。
   - 完成标准: 每条威胁有验收用例草案；需求方确认"这 N 条之外不在本期范围"。
5. **锁定并回溯**：把威胁清单作为后续设计/测试/上线的对照基线；方案变动时回查是否仍覆盖全部条目。
   - 完成标准: 清单进入需求文档与测试计划；有变更回溯机制。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 已有明确威胁清单或合规条目（等保/PCI 对表）——直接进入机制设计或对表执行，重复分解徒增成本。
- 正在发生的安全事件响应——先止损后复盘，需求分解不参与救火。
- 纯技术选型问题（用哪种哈希、哪个 WAF）——那是分解之后的机制层决策。

### 作者在书中警告的失败模式

- 直接实现口号：做偏的典型是"提高复杂度=加长度要求"，防不住包含生日的密码——两条威胁的目标函数不同，混为一条必漏。
- 验收标准缺位：上线后说不清防住了什么，安全投入无法度量也无法辩护。
- 需求与资产脱节：不经访谈臆断保护对象，资产划分失真，后续威胁分析整体偏向。

### 作者的盲点 / 时代局限

- 分解示范（密码复杂度）来自 2014 年电商语境；现代需求（隐私合规、AI 数据使用）分解时需引入"数据主体权利"类非攻击者威胁维度，框架可容纳但条目需扩展。
- 未讨论需求方与安全团队对"残余风险接受"的治理流程（谁签字、何时复审），落地时补。

### 容易混淆的邻近方法论

- 威胁建模（STRIDE）：枚举威胁的系统化模型，可作为本 skill 第 2 步的展开工具；本 skill 管的是"从口号到威胁清单"的翻译纪律与验收对齐。
- 用户故事拆解（敏捷）：按价值拆任务；本 skill 按"攻击成立条件"拆需求——拆分轴不同，不可互替。
