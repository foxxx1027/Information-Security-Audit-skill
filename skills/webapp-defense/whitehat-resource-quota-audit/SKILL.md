# 拒绝服务的本质与资源配额审计

## R — 原文 (Reading)

> "此类拒绝服务攻击的本质，实际上是对有限资源的无限制滥用。"
> "由此看来，应用层DDOS攻击与正常业务的界线比较模糊。"
>
> — 方法论出处，第 13 章《应用层拒绝服务攻击》13.5.1 / 13.2.1

---

## I — 方法论骨架 (Interpretation)

DoS 的形态多得记不完（CC、慢连接、超大 POST、超长请求头、灾难正则），但拆开看只有一句话：**找到一样有限的东西，让一个便宜的动作无限制地消耗它**。攻击者选的永远是"成本不对称最大"的资源——一个几乎不花带宽的慢连接占住一个线程，一段恶意输入让正则回溯指数爆炸。

这给出两边的操作化：

- **审计侧**：列资源清单，逐项问配额。系统的有限资源是可枚举的（连接数、线程、CPU、内存、DB 连接与行锁、消息队列长度、正则回溯栈、请求头大小、查询深度与复杂度），对每项问"一个匿名/低权限用户能否无限制触发对它的消耗"。能，就是 DoS 面，与攻击叫什么名字无关。
- **防御侧**：三层递进且每层承认可被绕过——性能层（缓存、削减单次成本，抬高单位攻击代价）、架构层（冗余分流、把压力从最脆弱组件移开、隐藏高成本接口）、限频层（按客户端维度截断触发次数）。任何单层都不是"专门防御"，组合才成立。

识别的关键约束：应用层攻击由**完全正常的请求**构成，"请求是否合法"这个维度失效，只能看**资源消耗画像与行为模式**——且不能简单封 IP（误伤正常用户与爬虫，IP 也换得了）。

## A1 — 书中的应用 (Past Application)

### 案例 1: 五形态归一到资源滥用（第 13 章）
- **问题**: CC、Slowloris、POST DOS、Server Limit DOS、ReDOS 五种攻击形态各异，防御要不要逐个买设备。
- **方法论的使用**: 对每种攻击问"它滥用的是哪样有限资源"——CC 打 DB/磁盘 IO、Slowloris 占连接与线程、POST DOS 打带宽与解析、Server Limit DOS 打请求头上限（Apache 8192 字节）、ReDOS 打正则回溯 CPU。
- **结论**: 全部是"有限资源的无限制滥用"，防御收敛为资源清单+配额，而非攻击名单。
- **结果**: "列资源清单逐项问配额"成为抗 DoS 评估的标准动作，覆盖未来新变体。

### 案例 2: ReDOS——代码缺陷型资源滥用（第 13 章 13.6）
- **问题**: 正则也能造成拒绝服务？扫描配置为什么查不出来。
- **方法论的使用**: 分析资源消耗机理——NFA 引擎逐个尝试"下一个状态"，缺陷正则（^(a+)+$ 类嵌套量词）遇不匹配输入时路径指数增长（18 个 a 达 65536，此后每字符翻倍），单个请求打满 CPU。
- **结论**: 它是代码实现缺陷而非配置问题；"用户输入直接进正则"列为必查项。
- **结果**: 缺陷正则模式清单与测试用例被直接固化进安全评估流程——"一定不能忽略 ReDOS 可能造成的影响"。

### 案例 3: CC 攻击与正常业务界线模糊（第 13 章 13.2.1）
- **问题**: 攻击全是正常 HTTP 请求、IP 真实，商业抗 D 设备为何缺乏手段。
- **方法论的使用**: 按识别维度分析——连接层握手完成、请求合法，"合法性"维度彻底失效；深分页查询（limit 起始位置暴涨）等高资源页面与正常用户访问无法按内容区分，爬虫爬死小站与此雷同。
- **结论**: 不能简单封 IP/封请求（误伤正常用户与搜索引擎）；识别必须换维度——资源消耗画像、按客户端维度限频、JS 人机识别。
- **结果**: 三层防御（性能 memcache/架构分流隐藏/限频+人机识别）成为应用层标准结构，且明示每层可被绕过（缓存未命中回源、IP+Cookie 双变化）须叠加。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评估一个系统/接口的抗 DoS 能力（新上线服务、开放 API、查询接口）。
2. 面对新型高资源接口（GraphQL 深嵌套、批量端点、文件上传解析、报表导出）做容量与滥用设计。
3. 限频/限流方案评审：维度选 IP+Cookie 对不对、阈值怎么定、会不会误伤。
4. 疑似 CC/资源耗尽故障复盘：流量看着正常但服务被打挂。
5. 代码审计中排查 ReDOS（用户输入进正则）与无界循环/无界查询。

### 语言信号 (用户的话里出现这些就应激活)

- "这个接口会不会被刷挂？"
- "怎么设计限流/限频？按 IP 限吗？"
- "流量不高但 CPU/数据库被打爆了。"
- "正则会有安全问题吗？"
- "how to protect against DoS / rate limit design / is this endpoint abusable / ReDOS check"

### 与相邻 skill 的区分

- 与 `whitehat-decompose-by-attack-class` 的区别: 那个是把 DoS 当作一个攻击类别去规划消除；本 skill 是该类别内部的审计动作与三层防御结构——类别方案的具体内容在这里。
- 与 `whitehat-signal-reliability` 的区别: 限频与封禁要选客户端标识，那些标识（IP/Cookie）可不可靠由那个 skill 裁决；本 skill 决定"要不要限、限什么资源、限多少"。
- 与 `whitehat-mitigation-vs-fix` 的区别: 性能优化对 DoS 是缓解非专门防御——本 skill 内嵌该分级（三层都标注可绕过），对外承诺时按减损口径。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **列资源清单**：枚举系统全部有限资源——连接/线程、CPU、内存、磁盘 IO、DB 连接与行锁、缓存容量、消息队列长度、正则回溯、请求头/请求体大小、查询深度/返回行数、第三方调用配额。
   - 完成标准: 每项标注"上限值（配置/默认）与耗尽后果"。
2. **逐项问配额**：对每项资源问——最低权限用户（匿名/免费层）能否无限制触发对它的消耗？触发一次的成本（请求字节/次数）与消耗量之比是多少？
   - 完成标准: 每项有"可无限制触发（DoS 面）/已有配额（配额值）"结论；成本不对称最大的前 3 项标红。
   - 判停条件: 若某资源已有多维配额（并发+速率+总量）且验证无法绕过，该项关闭，继续下一项。
3. **设计配额与三层防御**：为每个 DoS 面定配额（深度/复杂度/速率/大小上限）；再按三层排布——性能（降单次成本）、架构（分流、隐藏高成本接口、异步化）、限频（按客户端维度，配合人机识别）。
   - 完成标准: 每个红项至少落在两层；配额有明确的拒绝行为（429/截断/降级），而非静默堆积。
4. **维度校验识别策略**：检查识别逻辑是否押在"请求合法性"或单一可变标识上；改为资源消耗画像+多维标识+行为特征；确认误伤边界（搜索引擎、正常高峰）。
   - 完成标准: 有模拟正常流量不触发拦截、模拟滥用被截断的对照测试。
5. **对抗回归**：用已知形态逐层测绕过——直连高成本页绕缓存、换 IP 清 Cookie 绕限频、嵌套量词正则打 CPU、超长头打服务器限制；每绕过一层确认下一层接住。
   - 完成标准: 每种绕过路径的最终拦截层有记录；残余暴露面写入运营监控告警。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 无对抗视角的纯性能优化（慢查询日常调优）——那是性能工程；本 skill 在"有人刻意放大消耗"的假设下工作。
- 机密性/完整性问题——资源滥用只打击可用性，别的问题走各自方法。
- 已由基础设施层（云厂商抗 D、LB）覆盖的网络层洪水——本 skill 管应用层与代码层资源；但"防护已在哪层"本身值得用资源清单核对一遍。

### 作者在书中警告的失败模式

- 简单封 IP/封请求：与正常业务界线模糊，误伤用户与搜索引擎；IP+Cookie 双变化即绕过。
- 把性能优化当专门防御：缓存未命中仍回源，攻击者专挑未命中页；除"读"外还能触发"写"。
- 忽略 ReDOS 类代码缺陷：扫描配置查不到，缺陷正则模式与测试用例必须进评估流程。
- 押注单一限频标识：代理可换 IP、浏览器可清 Cookie——对抗性输入不能当安全边界。

### 作者的盲点 / 时代局限

- 案例与数字基于 2014 年（Apache 8190 字节头限制、Yahoo 频率专利）；现代栈的资源清单需扩展（容器配额、Serverless 并发与费用、CDN 回源、队列积压、LLM token 成本），方法不变。
- 对自动扩容架构下的"费用型 DoS"（横向扩容把资源耗尽转为账单爆炸）未有概念，引用时补充经济维度。

### 容易混淆的邻近方法论

- 攻击面收敛（删除高成本接口）与配额（限制保留接口）常组合：先用前者砍面，再用本 skill 给保留项配额。
- 限频实现细节（令牌桶/滑动窗口）是工程选型，本 skill 只约束"限什么维度、漏配额的后果是什么"。
