# 根因修复纪律：按成因修，补丁本身也要被审

## R — 原文 (Reading)

> "通常造成此问题的原因是，补丁的实现方案与代码未经安全部门检查，有时候也有可能是处理问题的安全工程师未能理解漏洞的本质，因此导致修补方案存在缺陷。"（第18章 18.2）
> "于是有人发现，如果构造<<script>>，经过一次处理后会变为<script>。"（第12章 12.7.2）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

同一份渗透报告，两种修法：

- **按 POC 修**：对着报告里的 payload 封堵特征——替换 script 字符串、过滤某个关键字、禁用一个字符。修的是"这个样本"，漏洞成立条件原封不动，攻击者换一个同族变体（剥壳、加空格、换编码、换原语）就绕回来。
- **按成因修**：先说清楚漏洞为什么成立（数据被当代码？校验与使用不同形？凭证可预置？），再消除成立条件本身——结构改造、正确编码、参数化、轮换。变体再多也依赖同一个成因，成因没了变体全体失效。

判定一个修复属于哪类，看它改变的是"漏洞成立条件"还是"已知样本的可达性"。

第二条纪律：补丁本身也是代码变更，会引入新面、会修错地方、会留下语义边界盲区——因此补丁必须经与开发同等的安全审查（安全工程师做漏洞分析→与开发共定方案→review 补丁代码→才可发布），"紧急"不等于"免检"。

验收"修完了"看修复方式与复测结果，不看速度与承诺。

## A1 — 书中的应用 (Past Application)

### 案例 1: Struts2 补丁连环绕过（第12章 12.7.2）
- **问题**: 报告 POC 是 `<script>alert(1)</script>`，官方补丁用"替换掉 script 标签"的黑名单。
- **方法论的使用**: 判定修复类型：按 POC 修。同族变体逐个击穿——`<<script>>` 剥壳绕过第一版；官方把 if 改 while 递归处理；`<script test=hello>` 标签后加属性再绕过。
- **结论**: 字面替换针对样本不针对成因（输出语境未编码）；补丁提交者"对安全的理解非常粗浅"。
- **结果**: 确立"黑名单字符串替换不是 XSS 正解，按上下文输出编码才是"的对照样本，成为补丁审查的教科书反例。

### 案例 2: 禁 %00 后的目录长度截断（第14章 14.2.1）
- **问题**: 文件包含的 %00 截断被禁用，漏洞算关闭了吗？
- **方法论的使用**: 分析成因：漏洞成立条件是"动态可控的文件路径 + 路径解析可被截断"，%00 只是截断原语之一。换成目录长度上限原语（Windows 256 字节/Linux 4096 字节后丢弃），用 ./ 重复拼接同样达到截断。
- **结论**: 封堵单一绕过特征不等于修复——攻击者会换同族原语；按根因治理是消除"用户可控路径拼接"。
- **结果**: 与 Struts2 案例共同证明"逐个堵特征永远堵不完"，特征封堵必须升级为结构修复。

### 案例 3: unset 清理补丁被 $GLOBALS 注入绕过（第14章 14.2.1）
- **问题**: 为禁用 register_globals 污染，打了 `foreach($_REQUEST as $k=>$v) unset(${$k})` 的补丁，为何无效？
- **方法论的使用**: 补丁代码审查暴露语义边界盲区：unset 默认只销毁局部变量，攻击者提交 GLOBALS[a]=1 仍覆盖全局变量——补丁本身留有可绕过的实现缺陷。
- **结论**: 补丁代码也是代码，会犯与业务代码同类的错误；评审补丁的提问模板——攻击者还能从哪些语义边界进入？覆盖的是症状还是成因？
- **结果**: 支撑第18章流程：补丁必须经安全工程师 review 才能发布，补丁质量从运气问题变成流程问题。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 渗透测试/扫描报告返回后，验收开发团队的修复。
2. 作为开发，设计一个漏洞的修复方案（避免做出会被绕过的补丁）。
3. Code review 补丁/热修复 PR，判断能否合并。
4. 评估"上了 WAF 规则/过滤了关键字"能否作为修复结案。
5. 制定组织的漏洞修补流程与复测标准。

### 语言信号 (用户的话里出现这些就应激活)

- "开发说一天就修完了 / fixed all findings overnight"
- "加了 WAF 规则挡住了，算修复吗 / virtual patch enough"
- "过滤了 <script> 为什么还能绕 / bypass after patch"
- "补丁还需要安全评审吗 / patch review"
- "复测没复现就能关闭吗 / retest before closing"

### 与相邻 skill 的区分

- 与 `whitehat-fix-at-highest-leverage` 的区别：那边决定**在哪一层修**（上游 vs 本地）；本 skill 裁决**修的方式**（成因 vs 样本）与**补丁自身的质量**——一个定位置，一个定质量，两维正交。
- 与 `whitehat-whitelist-first` 的区别：白名单是一种根因修复的形态（消除"枚举坏值"这个错误结构）；本技能是验收纪律，判定给定的修复是否真具备这种结构。
- 与 `whitehat-attack-chain-pruning` 的区别：那边接受漏洞存在、限制后果（降损）；本 skill 要求最终消除漏洞成立条件——缓解与修复可以并存，但不能互相冒充。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **要求逐条提交成因说明**
   - 完成标准: 对每个修复项，开发能回答"漏洞为什么成立"（数据被当代码/校验与使用不同形/凭证可预置……）与"修复消除了哪个成立条件"；说不出成因的项目标记待澄清。
   - 判停条件: 若为应急响应阶段（漏洞正在被利用），先放行临时缓解，但必须登记"临时"标签与根因修复排期，随后仍回到本流程。

2. **分类：根因消除 vs 特征封堵**
   - 完成标准: 每项修复归入两类之一——根因消除（结构/编码/参数化/轮换等条件级改造）或特征封堵（规则、过滤、关键字、单点禁用）；仅存在特征封堵类的高危项不得关闭。

3. **对特征封堵项构造同族变体复测**
   - 完成标准: 每个特征封堵项推导并实测至少一个同族变体（换编码、换原语、剥壳、语义边界），预期被绕过的项退回重修；WAF/过滤类虚拟补丁一律按此复测。

4. **审查补丁本身**
   - 完成标准: 补丁 diff 经过与开发同等的安全 review：是否引入新攻击面、是否遗漏同类调用点、是否留下语言/框架语义边界盲区（如 unset 之于超全局）、配置改动是否影响他处。

5. **复测通过才关闭并归档**
   - 完成标准: 原始 POC 与全部变体复测失败；修复方式（根因/缓解）、复测证据、补丁 review 记录归档入漏洞台账，供后续统计。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 修复优先级与排期决策（先修哪个）——属风险排序问题，本 skill 只管"修的方式对不对"。
- 临时缓解的存在性判断——应急场景允许先缓解，本 skill 的要求是缓解必须显式标注临时并排期根因，而非禁止缓解。
- 设计阶段的前瞻性安全设计（尚无漏洞可修）——用对应的设计类技能。

### 作者在书中警告的失败模式

- 按 POC 字面替换打补丁——Struts2 三连绕过；"补丁提交者对安全的理解非常粗浅"。
- 封堵单一绕过特征当修复——禁 %00 后目录长度截断接力，同族原语换不停。
- 补丁绕过安全检查直接上线，或安全工程师未理解漏洞本质——修补方案从根上就错。

### 作者的盲点 / 时代局限

- 书中案例集中于 PHP/Java 黑名单补丁；今日同型失败换载体：WAF 规则当永久修复、只修扫描器报告的路径（变体路径未扫到）、依赖组件升级但未验证补丁是否真正覆盖成因、AI 生成补丁的"看起来对"——纪律不变。
- 未讨论回归测试自动化（修复引入新洞的检测）与补丁的灰度/回滚策略；今日应把"补丁 review + 变体复测"接入 CI 流水线。
- 对"复测证据"的形态（截图/脚本/回归用例固化）未细化，建议将变体固化为回归用例。

### 容易混淆的邻近方法论

- 杠杆最大层修复（在哪修 vs 修得对不对）。
- 白名单优先（根因修复的一种形态 vs 验收全部修复的纪律）。
- 攻击链裁剪（限制后果的降损 vs 消除条件的修复——并存但不可互替）。
