# 把"是否安全"转化为"是否合规/可判定"

## R — 原文 (Reading)

> "其核心思想是，并非直接检查代码是否安全，而是检查开发者是否遵守了开发规范。"（第17章）
> "对于程序员们来说，记住代码规范中的要求，远比记住复杂的安全原理要容易得多。"（第17章）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

"这段代码安全吗"是开放问题：无边界、依赖专家判断、每次答案可能不同，无法规模化。但"这段代码是否调用了参数化查询函数"是封闭问题：可判定、可扫描、机器可答。

方法论就是做这层转换，三步：

1. **规范条目化**：把安全要求固化成开发规范——每条形如"做 X 时必须用 Y"（输出必须走安全函数、路径必须白名单、查询必须参数化）。专家的知识沉淀在条目里，开发者只需记住规范，不必人人成为密码学/注入专家。
2. **条目信号化**：每条规范映射到可机械检查的信号——函数名（未用安全函数即不合规）、AST 模式、配置项。由此可定制白盒扫描，逐行检查、开发者可自检。
3. **度量与归档**：对发现的漏洞归档统计（数量/类型/成因），从全局看系统性短板，为下一轮规范修订与投入决策提供依据。

转换后得到的三个能力：判断稳定（同一代码总得同一结论）、检查可自动化（CI 门禁）、组织可学习（统计短板）。这是安全从艺术走向工程的路径——但前提是规范本身正确且完整，条目错了就会错得规模化。

## A1 — 书中的应用 (Past Application)

### 案例 1: 安全函数/安全宏 + 白盒扫描（第17章）
- **问题**: 如何让大量程序员的日常代码可被安全审计？
- **方法论的使用**: 把各类上下文的正确写法封装成安全函数/安全宏，规定输出必须走它们；代码审核阶段用白盒扫描检查"变量输出是否使用了安全函数"，未使用即判不合规。
- **结论**: 开放式"代码是否安全"的审计被压缩成函数名级别的机械检查，开发者可自检，扫描可规模化。
- **结果**: 安全宏配套自动测试防止其自身实现被改坏——条目本身的质量也被纳入管理。

### 案例 2: "记住规范比记住安全原理容易"（第17章 准则四）
- **问题**: 安全培训讲原理，开发者转头就忘，代码质量不见提升。
- **方法论的使用**: 把安全方案写进工作手册：开发者只需记住"如何使用安全功能"，不必深究背后原理；遵守规范=写出安全代码。
- **结论**: 安全能力从个别专家的脑内知识沉淀为组织资产（规范+函数库），这是 SDL 准则四的落地形态。
- **结果**: 规范成为培训、评审、扫描三者的共同基准，安全知识可复制。

### 案例 3: 漏洞归档统计找全局短板（第18章 18.1）
- **问题**: 单个漏洞修完就丢，组织学不到东西。
- **方法论的使用**: 对历史漏洞按数量、类型、成因归档统计——某类漏洞高发指向对应规范/培训/组件缺失，而非个别程序员的失误。
- **结论**: 统计结果为下一周期的 SDL 重点、培训内容、投入方向提供决策依据；度量让"安全能力"可谈论。
- **结果**: 阿里实践给出量化样板（覆盖率/时延/准确率衡量安全能力），规范—扫描—统计形成闭环。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 起草安全编码规范/工作手册，希望它能被真正执行和检查。
2. 为 CI/代码评审设计可自动化的安全门禁与检查项。
3. 让 LLM/代码审查工具稳定输出安全结论（不被开放问题的不稳定输出困扰）。
4. 制定安全度量体系，向管理层证明投入与短板。
5. 团队安全能力标准化：新人按规范即可写出合格代码。

### 语言信号 (用户的话里出现这些就应激活)

- "安全规范怎么落地 / enforce coding standards"
- "定制白盒扫描/检查规则 / custom lint / static analysis rules"
- "CI 安全门禁怎么设计 / security gate in CI"
- "LLM 审代码安全结论不稳定 / inconsistent security review"
- "安全能力怎么度量 / security metrics"

### 与相邻 skill 的区分

- 与 `whitehat-tool-vs-manual-boundary` 的区别：那边裁决"哪类漏洞交给工具、哪类必须人工"；本 skill 提供"让更多内容变得可交给工具"的转换技术——转换后边界外移，两个 skill 先后使用。
- 与 `whitehat-whitelist-first` 的区别：白名单是单条规则的设计思想；本 skill 是把一批规则工程化（条目化+信号化+度量）的组织技术。
- 与 `whitehat-business-logic-four-questions` 的区别：四问处理规范覆盖不到的业务逻辑（须人工经验）；本 skill 处理可模式化的技术性要求——两者互补，勿用合规检查冒充逻辑审查。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **圈定转换范围**
   - 完成标准: 列出目标安全要求清单，逐条标注"可判定（有明确允许/禁止行为）"或"开放（依赖逻辑与上下文判断）"；开放的条目移出本流程，标注交给人工/专项方法。
   - 判停条件: 若全部要求都是开放型（纯业务逻辑约束），本 skill 不适用，转人工审查方法。

2. **条目化改写**
   - 完成标准: 每条规范改写为可断言形式：动词 + 对象 + 允许集合/必须使用的安全 API（"所有数据库查询必须使用 X 参数化函数；例外须登记"）；无"注意安全""谨慎处理"式的不可判定表述。

3. **映射检查信号**
   - 完成标准: 每条条目指明其机械检查方式（函数名/AST 模式/依赖声明/配置项），并评估误报率；无信号可映射的条目降级为"评审要点"并显式标注。

4. **接入执行链**
   - 完成标准: 检查接入 CI/IDE 自检/评审清单三者中至少一处，阻断或告警策略明确；安全函数库/宏有自动测试防退化。

5. **归档统计闭环**
   - 完成标准: 漏洞与违规按数量/类型/成因归档，定期输出短板报告并驱动规范修订——规范有版本、有 owner、有修订记录。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 业务逻辑漏洞（越权、流程旁路、状态机缺陷）——不可模式化，合规条目覆盖不到，须用业务逻辑专项审查；用合规检查冒充逻辑审查会产生虚假覆盖。
- 规范条目本身的安全正确性论证——条目由专家沉淀并验证，本 skill 假设条目正确；条目错了会被规模化复制错误。
- 一次性/探索性代码——转换成本大于收益。

### 作者在书中警告的失败模式

- checklist 非万能——清单保证覆盖面与下限，判断仍依赖安全工程师经验；把清单当全部能力是误用。
- 扫描绿灯≠安全——误报漏报之外还有可见范围之外的盲区（编译产物、边角项目）。
- 规范不被强制执行即失效——"有规范"与"规范被执行"之间需要门禁与度量桥接。

### 作者的盲点 / 时代局限

- 书中实践绑定 PHP 时代的安全函数与自研扫描；今日落地形态换为 Semgrep/CodeQL 自定义规则、SBOM/依赖策略、策略即代码（OPA）——"条目化+信号化+度量"骨架不变。
- 未讨论规则的误报治理（规则启用初期的告警洪水会瓦解门禁公信力）与豁免流程的设计——今日需补充。
- "把开放问题转封闭"用于 LLM 辅助审查时（verified V2 外推）：LLM 按清单核对+CI 强制的组合，结论才可复核——书中无此场景，属骨架迁移。

### 容易混淆的邻近方法论

- 工具与人工分工（可检出的交给工具 vs 让更多内容变得可检出）。
- 白名单优先（单条规则思想 vs 规则体系工程化）。
- 持续安全验证（验证制度执行率 vs 把安全要求变可判定——一个验流程，一个造流程内容）。
