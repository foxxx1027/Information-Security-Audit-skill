# 安全是产品特性：保护"要什么"，优化"怎么给"

## R — 原文 (Reading)

> "没有不安全的业务，只有不安全的实现方式。"（第1章 1.6.4）
> "将安全视为产品特性，往往也就解决了业务与安全之间的矛盾。"（第16章 16.1）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

这套方法用来裁决"安全 vs 业务"的冲突，核心是一次问题重构：

**冲突通常不在"业务目标"与"安全"之间，而在"安全"与"当前实现方式"之间。**

- 杯子的比喻：除了能装水，还要问材质是否有毒、高温会不会熔化——安全是产品的固有属性，从未考虑安全的产品是不完整的产品。
- 因此裁决动作是拆开两列：业务要达成什么（保护目标），现在打算怎么实现（可改造对象）。安全要求落在实现层，就不必砍业务。
- 为每个高危点寻找**等价安全实现**：加风控、降级、灰度、限额、白名单——功能继续上线，风险被控制。只有穷举后确实不可替代时才谈功能裁剪，且要拿出"实现不可替代"的证据。
- 制度化落点：安全像功能一样进需求评审、排期、验收；需求层少改业务（安全为业务服务），实现层必须安全（"安全的功能"——权限校验、编码、参数化内建在代码里，而不是事后附加检查）。
- 长期论据：成熟到有利可图的领域，安全本身成为产品竞争力（搜索结果安全、邮箱反垃圾）——安全不只是成本。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 杯子与产品属性（第1章 1.6.4）
- **问题**: 安全和业务谁该让步？
- **方法论的使用**: 把安全定义为产品属性而非外挂检查——设计之初就考虑，方案尽可能不改变商业需求的初衷。
- **结论**: 保护"要什么"，优化"怎么给"；没有不安全的业务，只有不安全的实现。
- **结果**: 安全方案设计有了明确的裁决顺序：先守住业务目标，再改造实现方式。

### 案例 2: 视为产品特性化解矛盾（第16章 16.1）
- **问题**: 安全团队与业务团队长期对立，工作难推进。
- **方法论的使用**: 把安全当产品特性来需求评审、排期、验收，而非上线后的追加检查。
- **结论**: 对立感源于安全被放在业务流程之外；嵌入产品定义后矛盾自然消解。
- **结果**: 该立场成为全书从世界观落到业务开发的纲领性要求。

### 案例 3: 安全即竞争力的产业证据（第16/18章）
- **问题**: 安全投入凭什么值得？
- **方法论的使用**: 用搜索引擎过滤恶意站点（每千个结果约 1 个导向恶意网站）、邮箱反垃圾等案例论证：安全能力直接体现产品实力。
- **结论**: 成熟领域必然出现安全性竞争；安全做得差（垃圾泛滥、骗子满地）会毁掉产品，做得好则成为卖点。
- **结果**: 反向实证"安全是产品特性"——甚至能塑造用户习惯、创造需求（薯条蘸番茄酱的类比）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 安全团队要求下线/冻结一个高转化但高危的功能，业务强烈反对——需要裁决框架。
2. 新产品设计阶段，安全怎么介入需求评审而不被当成"泼冷水的"。
3. "安全需求跟业务需求冲突了"的日常拉扯，需要谈判话术与方案结构。
4. 向管理层论证安全投入的商业价值（ROI、竞争力）。

### 语言信号 (用户的话里出现这些就应激活)

- "安全和业务冲突了 / security vs business trade-off"
- "这个功能有风险，要不要直接下线 / kill the feature"
- "业务方不接受安全方案，怎么说服他们"
- "安全的价值怎么证明 / security ROI"
- "有没有既保住功能又降低风险的做法"

### 与相邻 skill 的区分

- 与 `whitehat-solution-acceptance-checklist` 的区别：那是单个安全方案的五维评审标准（本 skill 裁决之后的方案细化工具）；本 skill 是"业务与安全谁让步"的立场与重构框架。
- 与 `whitehat-requirement-decomposition` 的区别：那边把"让转账更安全"这类口号拆成可判定威胁清单；本 skill 回答"拆出威胁后与业务冲突怎么办"。

---

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **把冲突写成两列**
   - 完成标准: 左列业务目标（要达成什么、衡量指标），右列当前实现方式；冲突点被精确定位在右列的某个实现上，而不是笼统的"这个功能"。

2. **逐高危点寻找等价安全实现**
   - 完成标准: 每个安全风险点至少列出一个不砍功能的替代实现（限额/风控/降级/灰度/白名单/分步放开），附代价说明。
   - 判停条件: 穷举后确无等价实现 → 才进入功能裁剪谈判，且记录"实现不可替代"的证据与业务方确认，避免把"方案没想够"当成"天然对立"。

3. **把安全作为特性纳入产品流程**
   - 完成标准: 安全条目出现在需求文档、排期表、验收标准中（像功能点一样有 owner 和 deadline）。

4. **定义可验收的安全目标**
   - 完成标准: 与业务方确认"防住什么"的具体条款——"更安全"不可验收，"防住这三类攻击场景"可以。

5. **需要时引用竞争力论证**
   - 完成标准: 向决策层陈述时含同领域"安全成为竞争力/不安全毁掉产品"的对比例证。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 业务本身违法违规（欺诈、无证金融）——不存在"等价安全实现"，那是合规底线问题，不要用本框架为违法实现找补。
- 具体漏洞的修复技术选型——那是修复纪律的领地。
- 用户拿它当"安全给业务让路"的借口——方向恰好相反：守住业务目标的同时改造实现，不是放松安全要求。

### 作者在书中警告的失败模式

- 等价实现若体验差、性能差，仍会被业务推翻、被用户关掉——方案要过体验与性能两条硬门槛。
- 不能把安全判断推给用户（弹窗让用户选）——那不是"融入产品"，是转嫁责任。
- 上线后再补安全（产品已定型）成本最高——特性必须在设计之初进入。

### 作者的盲点 / 时代局限

- 立论的产业证据来自 2014 年的搜索安全/邮箱反垃圾（电商大厂语境）；对初创"先上线后安全"的生存压力、增长黑客文化下的安全债务问题，书中没有给出可操作路径（对个人开发者与中小团队着墨少）。
- "安全成为竞争力"在今日安全左移/信任牌（trust badge）营销中更明显，但书中未预见了"以安全为卖点的付费分层"等商业模式。
- 案例背景是中国互联网 2011–2014 语境，个别论断（如杀毒厂商创造需求）有时代痕迹。

### 容易混淆的邻近方法论

- 好方案验收清单（有效/体验/性能/低耦合/易扩展——本 skill 裁决后的验收工具）。
- 模糊安全需求分解（把口号变成具体威胁——上游工具）。
- 安全面交互设计（实现层"不把判断推给用户"的专项纪律）。
