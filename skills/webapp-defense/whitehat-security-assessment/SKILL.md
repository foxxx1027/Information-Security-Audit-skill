# 安全评估四阶段：资产分级 → 威胁分析 → 风险分析 → 确认解决方案

## R — 原文 (Reading)

> "一个安全评估的过程，可以简单地分为4个阶段：资产等级划分、威胁分析、风险分析、确认解决方案。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.6 如何实施安全评估

---

## I — 方法论骨架 (Interpretation)

评估一个系统的安全，不能上来就扫漏洞，要按固定的四步走，且每一步的产出是下一步的输入：

1. **资产等级划分**——先回答"保护什么"。互联网公司的核心资产是数据，靠与各业务负责人逐一访谈找出最重要的数据在哪。没做过评估的系统必须从这里起步。
2. **威胁分析**——回答"危险从哪来"。先头脑风暴把攻击面想全，再用 STRIDE 之类的模型清单兜底，防遗漏。
3. **风险分析**——回答"先防哪个"。风险 = 发生概率 × 损失大小，用 DREAD 之类的方法给每条威胁打分排序，避免低概率高损失的威胁被低估。
4. **确认解决方案**——回答"怎么办"。按排序逐条设计机制，此时方案自然对齐了保护目标。

关键约束：阶段顺序不可颠倒。跳过资产分级直接做威胁分析，会得到一份与业务价值脱节的漏洞清单；跳过风险分析直接出方案，会把资源平均撒到所有威胁上。上一阶段产出决定下一阶段的目标和深度；长期维护、已评估过的系统，前两段可以复用既有结论只做增量。

## A1 — 书中的应用 (Past Application)

### 案例 1: 智取华山——威胁分析不求全，全部部署"化作浮云"
- **问题**: 威胁分析阶段如何保证不遗漏？遗漏一条攻击路径的代价是什么。
- **方法论的使用**: 作者用《智取华山》战例做阶段二的反例推演：守方把"自古华山一条道"当作唯一攻击面并在正路布重兵；随后用 DREAD 给"正门强攻"打 15 分（高危，须重兵）、"后山小路"打 9 分（中危，也不能忽视）。
- **结论**: 威胁枚举靠个人灵感必然有漏，要头脑风暴求全 + 模型清单兜底；且打分排序能防止只盯显性高危路径。
- **结果**: 侦察小队从悬崖（事先没想到的路径）突破，正路全部部署失效——印证"攻击面假设不完整则方案整体失效"。

### 案例 2: 账户被盗业务的完整四阶段复用（第 16 章）
- **问题**: 网站账户被盗频发，安全投入该投向哪里。
- **方法论的使用**: 先穷举被盗途径（暴力破解、找回流程逻辑漏洞、盗号木马、撞库），再逐条 DREAD 打分。
- **结论**: 暴力破解 15 分居首、找回流程逻辑洞 14 分紧随，修复投入按分数排序先封高分路径。
- **结果**: 四阶段流程从第 1 章的理论完整落到真实互联网业务，产出可执行的加固次序。

### 案例 3: XSS 修补优先级——风险分析阶段在漏洞运营里的应用（第 3 章 3.3.7）
- **问题**: XSS 漏洞数量多到修不过来时如何排序。
- **方法论的使用**: 把"技术可利用性"换成"业务后果"排序：存储型 > 反射型（可绕过基于 URL 的过滤器）、用户互动页面可升级为 Worm 再加一档、按 PageView 估影响面。
- **结论**: 排序准则是 Damage 维度（后果量级），与 DREAD 的损失项同构。
- **结果**: 有限的修补资源集中到首页、互动页的存储型 XSS 上，排序从感觉变成三准则。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接手一个新系统/新业务线，被要求"做一下安全"，不知道从哪里入手。
2. 渗透测试或风险评估报告要交付，需要一份结构化的评估框架而不是漏洞流水账。
3. 扫描器扫出上百个告警，团队争论先修哪些，需要一个排优先级的依据。
4. 有人质疑"这个系统不出公网/只有内部员工用，还要做安全评估吗"，需要论证评估的入手点。
5. 做威胁建模（threat modeling）工作坊，需要按阶段组织产出物。

### 语言信号 (用户的话里出现这些就应激活)

- "要对这个系统做个安全评估/安全审计，怎么开展？"
- "先做威胁建模还是先跑扫描？资产梳理怎么做？"
- "漏洞太多了修不过来，优先级怎么排？"
- "内网系统还要做威胁分析吗？"
- "help me threat model this system / how to prioritize security findings"

### 与相邻 skill 的区分

- 与 `whitehat-trust-assumption-audit` 的区别: 本 skill 是评估流程的骨架（四阶段推进与排序）；那个是对单个机制的前提假设做逐条检验，是第二/四阶段里可复用的一个具体动作。
- 与 `whitehat-coverage-first` 的区别: 本 skill 定义"怎么评估"；那个定义白帽的失败模式是"漏"，强调覆盖率优先于深度的作业排序，是四阶段中威胁分析求全的动机说明。
- 与 `whitehat-requirement-decomposition` 的区别: 本 skill 面向"评估已有系统"；那个面向"把一句模糊安全需求拆成可验收的具体威胁"，多用于需求/设计期。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **判定起点**：确认被评估系统是否做过安全评估。
   - 完成标准: 明确写出"从第 N 阶段起步"及理由（未评估过→从资产分级起步；已有资产清单→从威胁分析增量做起）。
2. **资产分级**：访谈业务负责人/列数据清单，按重要性给数据分级，标出最高价值资产所在 subsystem。
   - 完成标准: 产出一张资产清单表（数据类型 × 位置 × 等级 × 业务负责人），最高级资产被显式标注。
   - 判停条件: 若用户无法提供任何业务信息且无文档，停止并输出访谈问题清单，不要凭空猜资产。
3. **威胁分析**：对每个高价值资产先头脑风暴攻击面，再用 STRIDE 六类逐项对照补漏。
   - 完成标准: 每个高价值资产至少对应一组威胁列表，且能指出哪几条来自模型兜底（防止把头脑风暴当求全）。
4. **风险分析**：按"概率 × 损失"给每条威胁打分排序（可用 DREAD 三档制，也可自定义但须写明标尺）。
   - 完成标准: 输出带分数的排序表；低概率高损失条目被显式抬升讨论而非默认排后。
5. **确认解决方案**：仅对排前列的威胁设计机制，每条方案标注它对应哪条威胁、哪个资产。
   - 完成标准: 方案与威胁一一挂钩，无"通用加固套餐"式的无对应项。
6. **声明未覆盖面**：列出本轮没评估到的资产/威胁与原因。
   - 完成标准: 报告含"未覆盖面"小节——这是求全纪律的落点，缺了它结论就是虚假安全。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 单个漏洞已定位、只需要修复方案选型时——直接进入编码/参数化类技能，重跑四阶段是浪费。
- 纯工具配置问题（"Nessus 怎么扫这个网段"）——那是运维操作，不是评估流程。
- 事件响应中的紧急止血（正在被入侵）——先响应止损，评估是事后动作。

### 作者在书中警告的失败模式

- 威胁分析靠个人灵感、没求全：智取华山式的"只想到一条路"，方案实施完攻击者却用了事先完全没想到的漏洞。
- 只看损失或只看概率：都会误判，"一旦突破损失太大"的场景要被模型调高风险值。
- 把模型当机器打表："模型是死的，人是活的"——STRIDE/DREAD 保证覆盖下限，确定攻击面与判断风险仍靠经验。

### 作者的盲点 / 时代局限

- STRIDE/DREAD 是微软模型的转述（成书 2014），微软自身后来已弃用 DREAD 打分；打分数字应视为讨论脚手架而非客观度量。
- 案例语境是 2011–2014 的中国互联网（阿里电商、门户 CMS），资产分级访谈法在微服务/数据中台下需改造为数据流与 API 盘点。
- 未覆盖云原生、供应链、隐私合规（GDPR/个保法）等新时代的资产形态——访谈对象清单要自行扩充。

### 容易混淆的邻近方法论

- "纵深防御"（`whitehat-defense-in-depth`）是第四阶段设计方案时的原则，不是评估流程本身。
- "攻击面收敛"（v27，阶段 2 另建）回答"怎么减少可被打的机会"，与威胁分析互补但动作不同。
