# 安全交互设计：不把判断推给用户

## R — 原文 (Reading)

> "如果用户能够分辨什么样的行为是安全的，那么还要安全软件做什么？"（第1章 1.6.4）
> "过多的警告信息只会使用户丧失警惕性。"（第16章 16.5.3.3）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

一个安全提示要想有效，得满足一个常被忽略的前提：读到提示的人有能力做出正确判断。而安全产品的用户大多不具备这个能力——如果用户能分辨哪个程序是恶意的，安全软件就没有存在的必要。把裁决推给用户，本质是把安全责任转嫁给最没有信息的一方。

更糟的是提示有衰减效应：告警越多、越含糊，用户越快学会无脑点"允许"。泛滥的提示不仅失效，还会变成社工素材——骗子可以指着弹窗说"你看，最新版什么都报，正常现象，点吧"。

设计纪律由此推出：

1. **默认不问**：能由服务端/策略引擎裁决的（黑名单、默认安全、自动拦截），不做成问题抛给用户。
2. **只在两个条件同时满足时提示**：用户此刻能采取行动（拒绝/中止/换路径），且风险具体可核对（是什么、怎么验证）。
3. **分级呈现**：静默拦截→一次性告知→强阻断，危害与打扰程度对齐；宁缺毋滥。
4. **文案可解释**：让用户/客服有可核对的事实依据，不给攻击者留下"什么都报"式的通用话术空间。

一句话：提示是稀缺资源，花掉一次就贬值一分。

## A1 — 书中的应用 (Past Application)

### 案例 1: Vista UAC 弹窗（第1章 1.6.4）
- **问题**: UAC 动辄弹窗"是否允许此程序对计算机进行更改"，为何成为 Vista 被诟病最多的设计？
- **方法论的使用**: 检验前提：普通用户根本无法分辨弹窗里的行为是否安全——把判断推给用户等于转嫁责任；用户被骚扰到习惯性点"允许"，恶意请求反而更容易被放行。
- **结论**: 好的安全方案应对用户透明、不改变使用习惯（验收五条中"用户体验好"的具体化）；主动防御类软件的同款交互被作者评为"非常荒谬"。
- **结果**: 该反例成为"安全裁决放在有信息优势一侧"的固定论据，写入方案设计原则。

### 案例 2: IM 的 .exe 警告被话术消解（第16章 16.5.3.3）
- **问题**: IM 检测传输文件含 .exe 即弹警告提示可能有病毒，为何没防住骗子？
- **方法论的使用**: 分析提示的对抗面：泛滥且不可解释的告警（什么都报）给了骗子反向话术——"您用的是最新版本吧？是就对了，这个版本什么都报是木马，没事的，您点吧"。
- **结论**: 过多的警告使用户丧失警惕性；防御方的告警反而替社工铺路；用户教育是必要一环但不能单靠它，技术控制优先。
- **结果**: 确立"提示必须克制、精准、可解释"的三性要求，与验证码"只在检测到爆破才出"同属一条节制原则。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计安全产品的提示/弹窗/拦截页（杀软、风控、浏览器警告、企业 DLP）。
2. 产品流程里要不要加"我已知晓风险"式确认的决策。
3. 诊断"用户总是忽略我们的安全提示"的现状。
4. 防钓鱼/防诈骗的产品化方案（提示文案、拦截策略）。
5. 安全方案的体验评审（验收五条中"用户体验好"的落地）。

### 语言信号 (用户的话里出现这些就应激活)

- "要不要加个确认弹窗 / add a confirmation dialog"
- "怎么提示用户有风险 / security warning design"
- "用户都无脑点允许 / users ignore warnings / click-through"
- "告警太多了用户麻木 / alert fatigue"
- "防钓鱼怎么提醒用户 / anti-phishing user prompt"

### 与相邻 skill 的区分

- 与 `whitehat-solution-acceptance-checklist` 的区别：验收清单评整个方案（有效/体验/性能/低耦合/易扩展五条）；本 skill 是其中"用户体验好"一条在交互层的具体纪律——何时提示、提示什么、文案怎么写。
- 与 `whitehat-abuse-feature-model` 的区别：那边解决"如何识别恶意"；本 skill 解决"识别之后的处置如何呈现给用户"——识别与处置呈现是两段，本 skill 管后段。
- 与 `whitehat-delayed-enforcement` 的区别：那边防的是攻击者探测规则边界（对敌策略）；本 skill 防的是己方提示把用户训练成攻击者的突破口（对友呈现）。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **盘点全部面向用户的安全决策点**
   - 完成标准: 弹窗、警告条、确认页、拦截提示、通知全量列出，每处标注触发频率与当前用户可选动作。
   - 判停条件: 若产品无任何面向用户的安全交互（全自动处置），本 skill 不适用，转后端告警运营方法。

2. **逐点检验"用户凭什么做对"**
   - 完成标准: 对每个决策点回答：用户有判断此风险所需的信息吗？做错的代价由谁承担？该决策能否改为服务端裁决或默认安全？——回答不了前两问的标记为"推责设计"。

3. **回收推责决策**
   - 完成标准: 能服务端裁决的改为自动处置；确需用户参与的（真实知情选择，如授权范围确认）保留，并压缩到最小集合。

4. **分级与文案重设计**
   - 完成标准: 保留的提示按"静默拦截/一次性告知/强阻断"三级对齐危害；每条文案含具体风险事实与可核对项（指纹、来源、金额），不含无法验证的泛化恐吓；模拟"骗子如何利用这条提示"逐一过。

5. **度量与收敛**
   - 完成标准: 提示曝光量与用户放行率可度量；放行率高的提示回炉（要么给信息要么改自动）；提示总量随版本迭代只减不增成为设计约束。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- SOC/运维侧告警策略（面向专业分析员的告警调优）——受众有判断能力，问题域不同。
- 合规强制的知情同意（隐私授权、条款确认）——存在性由法规决定，本 skill 仍可用于改进其文案与频率，但不能裁撤。
- 纯技术防护的取舍（该不该拦）——本 skill 管呈现方式，不管检测能力本身。

### 作者在书中警告的失败模式

- UAC 式"把判断推给用户"——双重失败：用户被骚扰 + 恶意请求被习惯性放行。
- 告警泛滥——"过多的警告信息只会使用户丧失警惕性"，提示贬值并成为社工素材。
- 指望用户教育单扛防线——用户教育必要但边际失效，技术控制与自动化识别优先。

### 作者的盲点 / 时代局限

- 书中无量化人因研究支撑（如 Google 对浏览器恶意警告的点击率研究、warning science），"克制/精准/可解释"三性今日有实证数据可校准文案与分级。
- 未讨论现代交互形态（推送通知疲劳、移动端权限对话、密码管理器提示、支付人脸确认）与对抗演化（深度伪造客服话术）——纪律可迁移，形态需重审。
- "好方案对用户透明"与"用户知情权/可控感"之间的张力（过度静默会让用户失去信任）书中未展开。

### 容易混淆的邻近方法论

- 安全方案验收清单（整体验收 vs 交互层纪律）。
- 反滥用识别三维建模（识别端 vs 呈现端）。
- 数据最小化（少收集 vs 少打扰——同属"少即是多"，作用面不同）。
