# 安全机制必须适配交付节奏与可运维性

## R — 原文 (Reading)

> "这要求在实施SDL时需要在每个阶段更新威胁模型和隐私策略，在必要的环节迭代模糊测试、代码安全分析等工作。"（第17章 17.2）
> "这样做有利于产品的快速发布，但是对于安全来说，往往是一场灾难。"（第17章 17.2 敏捷SDL）
>
> — 原作者，原始方法论来源

---

## I — 方法论骨架 (Interpretation)

一条安全流程被绕过，通常不是因为它设计得不好，而是因为它和团队的交付节奏、运维成本不兼容。错配的流程很少被正式否决——它被无声地绕过：评审会跳过、检查事后补、记录造假。从外面看流程"存在"，实际防护为零。

判断一个机制能不能活，看三件事：

1. **节奏兼容**：安全活动的粒度要等于或小于交付节奏。双周迭代的团队，每月一次的集中评审必然漏掉一半变更——安全要切片嵌入迭代，随版本滚动更新威胁模型与检查，而不是指望一次性评审。
2. **运维成本可承受**：再好的机制，若配置和维护的人力超过团队能持续支付的量，就会被放弃（CSP 理念出色却因逐页配置成本未推广）。评估机制时把维护工时量化出来，与收益一起过评审。
3. **度量执行率而非存在性**：有制度≠被执行。健康检查要看覆盖率、执行率、绕过次数，"我们有流程"本身不是证据。

推论：优先选择"默认生效、不依赖持续人力"的控制，少依赖"必须有人一直做对"的控制。

## A1 — 书中的应用 (Past Application)

### 案例 1: 敏捷"小步快跑"硬套瀑布 SDL（第17章 17.2）
- **问题**: 微软式厚重 SDL 遇上文档少、需求不断变的敏捷开发，安全设计无法在前期固定。
- **方法论的使用**: 诊断错配根源：评审节点与迭代节奏不匹配——要么流程被跳过，要么拖垮迭代，两种结果都使安全落空。
- **结论**: 不是删掉安全活动，而是承认变化：威胁模型/隐私策略每个阶段更新，模糊测试与代码分析随迭代滚动。
- **结果**: 形成敏捷 SDL——安全工作从"一次性阶段评审"改为"随版本演进的常设活动"。

### 案例 2: CSP 理念出色却推广失败（第2章 2.4）
- **问题**: CSP 白名单式限定资源加载，能根治一类 XSS，为何没有普及？
- **方法论的使用**: 从可运维性归因：规则配置复杂、页面多时无法逐页配置、后期维护成本巨大——机制落不了地，实际防护为零。
- **结果**: 成为"方案验收五条标准"（体验/性能/低耦合/易扩展）在真实世界的反向实证；推论是优先选默认生效、不依赖持续人力维护的控制。

### 案例 3: 安全运营持续循环兜底一次性建设（第18章 18.1）
- **问题**: 一次性安全建设完成后，如何防止随时间衰减？
- **方法论的使用**: 承认任何一次性机制都会漂移（配置被改、新资产未纳入），用 Find（周期检查）+ Fix（例行修补与紧急响应）的持续循环兜底。
- **结论**: 机制的存续需要运营节奏托底；"上线即完事"的流程必然过期。
- **结果**: 与敏捷 SDL 共同构成"机制必须活在交付与运营节奏里"的完整论证。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 为团队制定安全评审/SDL/规范，决定安全活动的频率与粒度。
2. 诊断"制度明明有，为什么没人执行/总是被绕过"——设计端归因；若问的是已运行制度"还在被执行吗/有没有走过场"，转 `whitehat-continuous-security-verification`。
3. 推广一项安全机制（安全头、CSP、代码检查、签名流程）时评估落地成本。
4. 快速迭代团队（双周/持续部署）被要求套用重型安全流程。
5. 向管理层解释"安全流程要怎么改才能被执行"。

### 语言信号 (用户的话里出现这些就应激活)

- "安全流程总是被绕过 / process bypassed / skipped"
- "开发说安全评审太慢了 / security review slows us down"
- "评审定成每月一次集中做行吗 / review cadence"
- "规范写了没人遵守 / policy not followed"
- "这个机制维护成本太高 / too complex to maintain / operational cost"
- 排除信号（出现这些**不激活**）："制度跑了一年，怎么确认还在被有效执行、有没有变成走过场"——问的是已上线机制的运营核验（执行率检查、健康巡检），用 `whitehat-continuous-security-verification`；本 skill 只回答"为什么被绕过、节奏怎么重排"。

### 与相邻 skill 的区分

- 与 `whitehat-continuous-security-verification` 的区别：那边假设制度/设备会失效，用周期检查+监控兜底（运营视角）；本 skill 在设计端就把"能否被执行"作为约束条件，防止造出注定被绕过的流程。两者是设计与运营的两端。判据：问"为什么被绕过/节奏怎么重排"（事前设计）归本 skill；问"跑了段时间还在生效吗/是不是走过场"（事后验证）归那个——对已运行制度做执行率检查与健康巡检不归本 skill。
- 与 `whitehat-solution-acceptance-checklist` 的区别：五条验收里"低耦合/易扩展"与本 skill 的可运维性重叠，但验收清单评单个方案；本 skill 评流程与整个交付体系的匹配。
- 与 `whitehat-tool-vs-manual-boundary` 的区别：那边分派"哪些交给自动化"；本 skill 决定"活动放在节奏的哪个位置"——粒度与排期问题。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **测量真实交付节奏**
   - 完成标准: 拿到事实数据：迭代长度、发布频率、每次变更规模、安全相关变更占比；标注当前安全活动实际发生的位置与频率。

2. **对照找出错配点**
   - 完成标准: 对每个安全活动回答：粒度是否大于交付节奏（集中评审 vs 双周迭代）？执行它需要谁花多少时间，该时间是否可持续？跳过它会发生什么、会被发现吗？列出全部错配项。
   - 判停条件: 若安全活动粒度已小于交付节奏且执行率数据健康（抽查无绕过），则流程设计无错配，转入步骤 4 只做度量固化。

3. **重排：切片嵌入 + 里程碑保留重型活动**
   - 完成标准: 轻量可自动化项（增量威胁建模 diff、依赖与配置检查、安全函数扫描）进入每次迭代的定义完成项；重型项（渗透测试、全量审计）绑定里程碑/大版本；无一项安全活动的等待周期超过一个迭代。

4. **降低持续人力依赖**
   - 完成标准: 清点每个机制的人工维护点，可自动化/默认生效的改造完成；不可自动化的显式标注所需工时并获资源确认。

5. **以执行率度量**
   - 完成标准: 建立执行率指标（覆盖率、按期完成率、绕过发现数）并定期公布；"流程存在"不再单独作为合规证据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 用"适配节奏"为借口砍掉必要的安全活动——本 skill 重排活动的位置与粒度，不豁免活动本身；砍不砍是风险接受决策，须走显式审批。
- 单个漏洞的修复方案设计、单项安全技术的实现——与流程节奏无关。
- 一次性项目/原型（生命周期短于一个迭代）——无需流程适配分析。

### 作者在书中警告的失败模式

- 敏捷团队直接套瀑布 SDL——"对安全来说往往是一场灾难"，流程被跳过或拖垮节奏。
- 只验证有效性、不评估配置与维护成本——CSP 式好理念死在落地成本上。
- 把"我们有制度/审批"当控制措施——缺少对执行情况的验证手段，制度沦为纸面。

### 作者的盲点 / 时代局限

- 书中给出的是原则与 SDL 语境，未涉及现代 DevSecOps 工具链（CI 内嵌扫描、策略即代码、安全门禁自动化），今日"切片嵌入"大部分可由工具自动完成，人力成本论证需按此重算。
- 未讨论跨团队节奏差异（平台团队 vs 业务团队 vs 数据团队）与流程本地化；也未涉及远程/开源协作模式下的流程执行。

### 容易混淆的邻近方法论

- 持续安全验证（运营端兜底 vs 设计端适配）。
- 安全方案验收清单（单方案评审 vs 流程体系适配）。
- 安全合规化（把问题变可判定条目 vs 把活动排进节奏——前者造内容，本条定排期，组合使用）。
