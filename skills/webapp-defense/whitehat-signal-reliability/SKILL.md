# 信号可靠性判据：可用 ≠ 可依赖

## R — 原文 (Reading)

> "即使我们能够通过检查Referer是否合法来判断用户是否被CSRF攻击，也仅仅是满足了防御的充分条件。Referer Check的缺陷在于，服务器并非什么时候都能取到Referer。"
> "因为HTTP头中的User-Agent是可以被客户端篡改的，所以不能信任。"
>
> — 方法论出处，第 4 章 4.3.2；第 13 章 13.4

---

## I — 方法论骨架 (Interpretation)

风控、识别、封禁都依赖"信号"：UA、Referer、IP、Cookie、自定义头。评估一个信号能不能用在**安全决策**上，看两个独立维度：

1. **可伪造成本**：这个值由谁产生？客户端随手可改的（UA、客户端 Cookie 属性、可注入的声明头如 XFF），攻击成本趋近于零；需要付出真实计算或行为代价的（JS 挑战计算、行为序列、功能差异指纹），才谈得上对抗性。
2. **可缺失性**：合法流量里它会不会天然缺席？Referer 会被隐私设置、HTTPS→HTTP 跳转剥掉——缺失时"放行还是拒绝"没有好答案：放行即绕过口，拒绝即误杀。

由此得到使用纪律：

- **分级使用**：弱信号（可改可缺）只进监控与画像，不做阻断判据；强信号才做主判据。
- **同问题选最强信号**：同样是来源标记，Origin 比 Referer 难伪造、不易缺失，应作主判据。
- **裁决权留在服务端**：会话寿命、权限判定不能委托给客户端可控的属性（Cookie Expire 由客户端改写即失效）。
- **识别看行为不看自述**：人机识别用"执行能力/行为序列/功能差异"，而不是客户端自报的字段。

## A1 — 书中的应用 (Past Application)

### 案例 1: Referer Check 只宜监控不宜阻断（第 4 章 4.3.2）
- **问题**: 用校验 Referer 防 CSRF，为何书中定位为"只适合监控"。
- **方法论的使用**: 按两维评估——可伪造（旧插件可自定义）、可缺失（隐私设置、HTTPS 跳转不发 Referer）；缺失放行则成为绕过口，缺失拒绝则误杀正常用户，两难无解。
- **结论**: Referer 正确时只构成充分条件而非充要条件——"可用"但不"可依赖"。
- **结果**: CSRF 主防线转为 Token；来源类信号升级为 Origin（更强信号原则）；Referer 降级为监控用途。

### 案例 2: P3P 一条配置瓦解"浏览器拦第三方 Cookie"（第 4 章 4.2.2）
- **问题**: 指望浏览器默认拦截第三方 Cookie，算不算 CSRF 的一道防线。
- **方法论的使用**: 检验信号来源的控制权——该"屏障"由浏览器默认行为提供，但网站为广告业务设置 P3P 头后 IE 即放行，且影响整个域的所有页面。
- **结论**: 客户端策略是可被无关配置瓦解的偶然屏障，不构成安全边界；且 P3P 的放行按域扩散，违反最小权限。
- **结果**: 结论固化为"CSRF 防御必须落在服务端，客户端策略只能当补充"；分诊经验：iframe 反常带 Cookie 先查 P3P 头。

### 案例 3: 会话寿命裁决权与限频标识的失效（第 9/13 章）
- **问题**: 用 Cookie Expire 控制会话失效、用 IP+Cookie 定位客户端做限频，为何都不可靠。
- **方法论的使用**: 统一按可篡改性判定——Cookie Expire 完全由客户端控制，改成 2038 年即"永久会话"且服务端无法察觉；IP 可换（代理池）、Cookie 可清，两者同时变化即绕过封禁（"代理猎手"/AccessDiver 实证）。
- **结论**: 会话寿命裁决权必须在服务端（绝对超时+单会话策略）；限频不能押单一可变标识，要多维信号叠加（IP+Cookie+行为+JS 人机识别）。
- **结果**: 浏览器识别改用功能差异与行为特征（ActiveXObject 探测、一行式指纹），而非 UA 自述——"识别看行为不看自述"成为规则。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计风控/反爬/人机识别方案，决定采信哪些字段（UA、头、IP、Cookie、设备参数）。
2. 封禁/限流策略被绕过（换 IP、清 Cookie、改 UA），复盘信号选型哪里错了。
3. 代理/CDN/网关后面取"真实客户端 IP"（XFF 可信吗、在哪一跳取）。
4. 评审"客户端校验/客户端签名"类方案（前端算的签名可不可信）。
5. 同一判断有多个候选信号（Referer vs Origin、IP vs 设备指纹），要选主判据。

### 语言信号 (用户的话里出现这些就应激活)

- "User-Agent / Referer / X-Forwarded-For 能不能信？"
- "从 XFF 里取真实 IP 做封禁行不行？"
- "前端做个校验/签名，是不是就防住了？"
- "限频用 IP+Cookie，为什么还是被刷？"
- "can I trust XFF for bans / is client-side validation enough / spoofable headers"

### 与相邻 skill 的区分

- 与 `whitehat-trust-assumption-audit` 的区别: 那个检验机制的全部前提（含环境与上游）；本 skill 专门给"信号"按可伪造/可缺失分级并定主判据，是前者在信号类前提上的深化执行。
- 与 `whitehat-abuse-feature-model` 的区别: 那个设计识别系统的特征架构（内容/行为/主体三维）；本 skill 评估单个特征能否承担安全决策——它是三维建模里"每个特征可信度"的判定器。
- 与 `whitehat-csrf-intent-token` 的区别: 那个是意图凭证的完整工程；本 skill 提供其中的选型判据（为何 Origin 强于 Referer、为何 token 优于来源校验）。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **盘点决策所依赖的信号**：列出当前方案中参与判定/封禁/放行的每个输入，标注其来源（客户端自报/客户端计算/网络层/服务端自产）。
   - 完成标准: 信号清单每项有来源标注。
2. **两维分级**：对每个信号评"可伪造成本"（谁改得了、改起来多贵）与"可缺失性"（合法流缺失场景）；归为强（可作主判据）/中（辅助）/弱（仅监控）。
   - 完成标准: 每个信号有分级结论与理由；弱信号清单显式化。
   - 判停条件: 若方案的关键决策全部押在弱信号上（如封禁只看 XFF），直接判方案不可行，输出重构建议而非继续微调。
3. **重排主判据**：同一判断存在多候选时选最强信号作主判据，其余降为辅助画像；缺失时的行为显式定义（默认拒绝/转人工，不做静默放行）。
   - 完成标准: 每个决策点"主判据+辅助集+缺失策略"三要素齐全。
4. **收回服务端裁决权**：检查是否有安全决策委托给客户端可控项（Cookie 属性、前端校验、本地时间）；改为服务端记录与校验。
   - 完成标准: 裁决逻辑全部在服务端；客户端只承担挑战计算（可验证的工作量）而非自证。
5. **对抗验证**：按"最便宜的伪造方式"实测——改 UA/清 Cookie/换代理/注入 XFF 重放，确认弱信号只影响画像不影响放行。
   - 完成标准: 每个伪造测试都不导致未授权放行；误杀率统计进入辅助信号调参依据。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 服务端自产数据（自身日志、连接层四元组在可信入口的观测）的完整性——那是日志与取证纪律问题，不是信号可靠性。
- 隐私合规字段采集的合法性评估——本 skill 管"可信度"，不管"可不可以采"（数据最小化的领域）。
- 纯提升用户体验的客户端预校验——不承担安全决策的校验不受此判据约束。

### 作者在书中警告的失败模式

- 把"能取到"当"可依赖"：Referer 案例的四重失败（可缺失、可伪造、缺失放行成绕过口、缺失拒绝误杀）。
- 押注客户端默认行为：P3P/浏览器策略是"偶然屏障"，一条配置即瓦解且影响全域。
- 单一可变标识扛封禁：IP+Cookie 双变化即绕过——对抗性系统"不要把安全性押在攻击者可以自由修改的输入上"。

### 作者的盲点 / 时代局限

- 2014 年的"强信号"清单已老化：JS 挑战被无头浏览器普遍破解、XFF 在多云链路下更复杂、TLS/HTTP 指纹是新的信号层——分级方法不变，但"当前可伪造成本"需按现代攻防重估。
- 未讨论信号收集本身的隐私代价（客户端行为采集 vs 合规），现代设计需与数据最小化联合权衡。

### 容易混淆的邻近方法论

- 数据与代码分离：管"数据进解释器"；本 skill 管"数据当证据"——同为"输入不可信"原则，作用面不同。
- 不可预测性：token 的随机性解决"猜得到吗"；本 skill 解决"这个值谁说了算"——token 同时过两关才有效。
