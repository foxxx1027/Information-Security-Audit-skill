# 好安全方案的验收清单

## R — 原文 (Reading)

> "能够有效解决问题；用户体验好；高性能；低耦合；易于扩展与升级。"
>
> — 原作者，原始方法论来源第1章 1.6.4

---

## I — 方法论骨架 (Interpretation)

行业默认只验一条"能不能防住"，这套清单把安全方案当**产品**来评审，共五条：

1. **有效解决问题**——底线：针对的威胁有真实阻断/缓解效果，这是入场券。
2. **用户体验好**——对用户透明、不改变使用习惯。用户被打扰到一定程度会自己绕过或关掉方案。
3. **高性能**——不拖业务后腿。安全机制引入的时延/吞吐代价要量化并让业务接受。
4. **低耦合**——高聚合、不侵入业务代码；安全逻辑和业务逻辑纠缠的方案难以维护。
5. **易于扩展升级**——能随威胁演进扩展（如可插拔规则、可自行添加插件）。

关键判断：**第 2、3 条是一票否决项**。一个"有效"但体验差或性能差的方案不会"带病存活"，而是会死——被业务方否决、被运维关掉、被用户绕过，届时实际防护为零。所以评审的正确产出不是"通过/不通过"，而是五维逐项结论 + 具体改进项清单；后四条失守的方案要回炉，而不是硬推上线。

## A1 — 书中的应用 (Past Application)

### 案例 1: UAC 弹窗（第1章 1.6.4，反例）
- **问题**: Vista 的 UAC 想解决权限滥用问题，为何成为最大败笔？
- **方法论的使用**: 用五条验收衡量——有效性没问题，但体验维度崩塌：动辄弹窗、把判断推给用户。
- **结论**: 有效但体验差的方案必然被诟病甚至被关闭；好方案应对用户透明。
- **结果**: "用户体验好"进入方案验收标准，与有效性并列。

### 案例 2: CSP 理念出色却败在配置与维护成本（第2章 2.4）
- **问题**: CSP（内容安全策略）能根治一类 XSS 加载，为何当年未能推广？
- **方法论的使用**: 事后五维复盘——有效性与性能尚可，但规则配置复杂（页面多时无法逐页配置）、后期维护成本巨大：低耦合与易扩展两条失守。
- **结论**: 再好的机制落不了地，实际防护就是零；可运维性与安全性同等重要。
- **结果**: 成为五条标准的反向实证；教训固化为"预估规模化部署与日常运营代价"。

### 案例 3: 两硬条件来自业务一线（第16章 16.1）
- **问题**: 为什么产品方对安全方案的最大挑战总在体验和性能上？
- **方法论的使用**: 作者从业务安全实践中提炼：有效性之外，良好体验与优秀性能是被业务接受的两个前提。
- **结论**: 设计时就主动验证这两条，而不是上线后被业务推翻。
- **结果**: 五条验收与"好方案尽量不改变用户习惯"一起构成方案评审固定维度。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审一个新安全方案/控制措施（WAF 规则集、风控策略、加密改造、登录升级）。
2. 方案被业务方抱怨"太重/太慢/太麻烦"，需要诊断问题出在哪一维。
3. 设计安全功能时预防"上线即被关掉"的命运。
4. 比较多个候选安全方案的优劣。

### 语言信号 (用户的话里出现这些就应激活)

- "这个安全方案好不好，怎么评价 / evaluate security solution"
- "方案被业务拒绝了 / solution rejected by product team"
- "安全措施拖慢了业务 / 影响体验 / performance impact"
- "用户把安全功能关掉了 / users disable security features"
- "有没有更轻的做法，这个方案太重了"

### 与相邻 skill 的区分

- 与 `whitehat-security-as-product-feature` 的区别：那是裁决"业务与安全谁让步"的立场框架；本 skill 是立场落地后对单个方案的验收工具。
- 与 `whitehat-security-process-fit-delivery-cadence` 的区别：那边管流程/机制与交付节奏、运维成本的组织级适配；本 skill 管单个方案本身的五维质量。
- 与 `whitehat-security-interaction-design` 的区别：那边是"不把判断推给用户"的交互专项深度；本 skill 的体验维度只是其一。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **有效性验证**
   - 完成标准: 方案声称防御的每个威胁场景有测试证据（攻击场景被阻断/缓解的演示或数据）；说不清防什么的方案直接退回。

2. **体验评估**
   - 完成标准: 列出方案对终端用户和内部开发/运维的全部打扰点；正常使用路径零打扰或有豁免机制。
   - 判停条件: 若方案需要用户做安全判断（"是否允许该行为"式弹窗）→ 转安全交互设计重做该部分，体验维度判不过。

3. **性能评估**
   - 完成标准: 关键路径时延/吞吐影响量化成数字，并与业务方确认可接受阈值；高频场景有实测。

4. **耦合与扩展评估**
   - 完成标准: 说明方案的接入方式与对业务代码的侵入面（改多少处、是否可独立升级）；未来扩展点（新规则/新场景）列举成文。

5. **产出评审结论**
   - 完成标准: 五维逐项给出 结论+证据；不通过项标"一票否决"（体验/性能）或"需改进"（耦合/扩展），附具体改进项；明确"回炉"或"带条件通过"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 商业安全产品的采购选型（价格、支持、生态是采购维度，本清单只可作技术评审子集）。
- 一次性临时脚本/实验环境的安全措施——五维全过是浪费。
- 漏洞修复方案的验证（那是修复纪律的核验动作，重点在是否按根因修）。

### 作者在书中警告的失败模式

- 只验有效性：行业默认错误；后四条失守的方案"上线即死亡"。
- UAC 式设计：把安全判断推给用户，体验维度必然崩塌。
- 低估规模化成本：单页/单实例测试通过 ≠ 全站部署可行（CSP 教训：页面一多配置就不可维护）。

### 作者的盲点 / 时代局限

- 五条标准成文于 2014 年 Web 应用层方案语境，无量化方法（今日会配 SLO、性能预算、可用性测试）；"低耦合"在微服务/插件化时代的含义比书中更丰富。
- CSP 反例已部分过时：CSP nonce/hash 方案（2015 后）与其报告模式大幅缓解了当年"逐页配置"的维护痛点，引用该案例需注明时代前提。
- 五条未含"可观测性"维度（方案自身运行状况可见），现代评审通常要补。

### 容易混淆的邻近方法论

- 安全是产品特性（立场层，本清单是其验收执行层）。
- 安全机制适配交付节奏（组织级落地适配）。
- 安全交互设计（体验维度的专项深化）。
