# 漏洞最小条件判定与 source→sink 数据流审计

## R — 原文 (Reading)

> "注入攻击的本质，是把用户输入的数据当做代码执行。这里有两个关键条件，第一个是用户能够控制输入；第二个是原本程序要执行的代码，拼接了用户输入的数据。"
> "找到所有可能的用户输入入口，然后跟踪变量的传递情况，看变量最后是否会走到危险函数（如 eval()）。"
>
> — 方法论出处，第 7 章《注入攻击》章首；第 17 章《SDL》17.5.2

---

## I — 方法论骨架 (Interpretation)

找漏洞不必碰运气地试 payload。每类可注入漏洞的成立条件都可以压缩成一个**最小条件集**——通常只有两条：

- **source 可控**：存在用户能控制的输入入口（请求参数、header、cookie、上传文件、数据库里存的旧数据）。
- **sink 危险**：存在会把数据当代码/结构解释的执行点（eval、system、SQL 拼接、include、模板渲染、正则）。

两条同时成立，漏洞面就存在；审计因此变成两件可穷举的事：列全 source 清单，列全 sink 清单，然后对每条 source→sink 路径做数据流追踪（污点传播：变量被赋值、拼接、函数包裹后污点是否保留）。追踪可以正向（从入口跟到末端）也可以反向（从危险函数回溯调用者），两个方向交叉验证可减少遗漏。

这个判定式同时给出防御映射：破坏条件一（入口约束）或破坏条件二（消灭危险函数、参数化），任一条成立漏洞即不成立。扩面时记住 sink 清单比表面更宽：数据库内部的动态 SQL、回调函数名、`preg_replace /e`、反序列化，都是"近似后门"的执行面。

## A1 — 书中的应用 (Past Application)

### 案例 1: 注入/代码执行/文件包含三族共用一个判定式（第 7、14 章）
- **问题**: SQL 注入、PHP 代码执行、文件包含各有一堆变体，逐个学习成本高且总漏。
- **方法论的使用**: 作者对三族分别提炼两条件——注入：可控输入+拼接进执行的代码；代码执行：可控的函数输入+危险函数；文件包含：动态变量的包含+该变量可控。审计动作统一为"找 include/require/eval 的动态变量，追来源是否用户可控"。
- **结论**: 同构判定式成立，"找漏洞"从经验直觉变成逐项核对。
- **结果**: 第 14 章进一步给出 PHP 七类代码执行途径清单（代码注入/危险函数参数/preg_replace /e/动态函数/回调覆盖/反序列化等），作为 sink 清单直接用于审核。

### 案例 2: webshell 三条件与逐条破坏（第 8 章）
- **问题**: 上传漏洞何时才算真正成立，业界常争论"传上去了但解析不了算不算"。
- **方法论的使用**: 把攻击成立拆成三条件——能被容器解析执行、能被 Web 访问到、内容未被检查/改写。防御即逐条破坏：目录禁执行、放 Web 根外/独立域名、内容重写（图片压缩）。
- **结论**: 用最小条件集消解判定争议，评估任何上传点时按三条核对。
- **结果**: 安全上传四要点（类型白名单、随机改名、独立域名、去执行权限）全部可映射回"破坏某一条"。

### 案例 3: ORM 动态变量的收敛审计（第 12 章 12.5）
- **问题**: ORM 框架看似天然免疫注入，iBatis 的 `$value$` 动态变量却仍可注入。
- **方法论的使用**: 把"运行期把变量拼进 SQL 文本"的位置视为 sink，规则是把动态 SQL 变量集中到少数配置里，grep 即可全覆盖，再逐个确认是否用户可控。
- **结论**: 注入面可以被收敛到可穷举的位置，审计成本从"读全部代码"降到"审配置清单"。
- **结果**: source→sink 追踪从手工方法升级为可工程化的审计线索。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 接手一个陌生代码库/开源项目，要系统摸清注入与代码执行面（而非验证某个已知 payload）。
2. 评审 SAST/扫描器结果：0 告警能不能信、误报如何复核、覆盖面盲区在哪。
3. 框架迁移/重构后，确认 ORM、模板、文件操作没引入新的动态执行点。
4. 设计安全编码规范或 CI 检查，要把"危险函数 + 可控输入"固化成可扫描规则。
5. 审计存储型/二阶注入：source 不是本次请求而是数据库里的旧数据。

### 语言信号 (用户的话里出现这些就应激活)

- "帮我审计一下这个项目有没有注入/命令执行。"
- "扫描器没报问题，是不是就安全了？"
- "这个框架会不会有 SSTI/模板注入？"
- "哪些函数是危险的，怎么排查？"
- "audit this codebase for injection / is SAST clean result enough / how to find RCE surface"

### 与相邻 skill 的区分

- 与 `whitehat-data-code-separation` 的区别: 那个给成因模型与防御方向（为什么、往哪修）；本 skill 给审计操作（在代码库里怎么找：列清单、追数据流）。防御选型归它，找漏洞面归本 skill。
- 与 `whitehat-tool-vs-manual-boundary` 的区别: 那个裁决"哪些漏洞交给工具、哪些必须人工"；本 skill 是人工/白盒审计的具体动作，恰好是工具覆盖不到的业务逻辑区之外的系统化方法。
- 与 `whitehat-context-encoding` 的区别: 本 skill 找到注入面即止；那个处理"输出点找到之后按什么语境编码"，是修复阶段的选择。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **列 source 清单**：枚举全部用户可控入口——请求参数、header、cookie、上传文件名与内容、URL path、数据库/缓存中的历史数据、第三方回调。
   - 完成标准: 清单覆盖"进入进程的全部外部数据"，每项标注入口函数/变量名。
2. **列 sink 清单**：按目标语言的危险原语枚举执行点——SQL 拼接、命令执行（eval/system/exec）、文件包含/路径拼接、模板渲染、动态函数/回调、正则（回溯与 /e）、反序列化、响应头/日志写入。
   - 完成标准: 每类 sink 有具体函数/调用形态清单，含 ORM 动态变量、存储过程内动态 SQL 等"藏在配置或数据库里"的执行面。
   - 判停条件: 若项目无任何第 2 步清单内的执行原语（纯静态服务），注入面判定为空，报告结论并结束。
3. **数据流追踪**：对每个 sink 反向回溯（谁调它、参数从哪来），或对每个 source 正向跟踪（流向了哪里）；污点经赋值、拼接、函数包裹后标记是否保留。
   - 完成标准: 每条 source→sink 路径有"连通/不连通"结论；两个方向的结果交叉比对，不一致的路径列为待人工确认。
4. **判定与取证**：对连通路径给出两条件判定（可控证据 + sink 证据），标注为漏洞面并定级（代码注入按后门级处置）。
   - 完成标准: 每个漏洞面有最小复现路径（source 入口到 sink 的调用链），而非"可能存在"的猜测。
5. **映射防御与复核覆盖面**：每个漏洞面指定破坏哪一条条件（入口约束/消灭 sink）；最后核对 source 与 sink 清单本身的覆盖率（语言、框架、编译产物是否都在可见范围）。
   - 完成标准: 输出"漏洞面清单 + 修复映射 + 未覆盖面申报"三部分，未覆盖面显式列出而非默认安全。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 黑盒渗透（拿不到代码）——source/sink 无法枚举，应走威胁建模与模糊测试。
- 业务逻辑漏洞（越权、审核旁路、薅羊毛）——没有固定 sink，两条件判定式失效，用业务逻辑审查问法。
- 运维/配置类风险（默认口令、目录权限）——不涉及数据流。

### 作者在书中警告的失败模式

- 扫描器在复杂项目上失灵：跨文件调用使"从危险函数回溯"极难、复杂框架产生大量误报漏报——工具输出是线索不是结论，必须人工处理。
- 忽略存储型注入：source 不一定是本次请求，MyBB 模板 eval 案例中危险函数的输入来自数据库里的模板数据（管理员编辑写入），逐请求审计看不到。
- 漏掉"近似后门"的执行面：可变函数 `$dyn_func($_GET['x'])`、回调参数、preg_replace /e 拼接——sink 清单必须包含语言的全部动态执行原语。
- 编译产物在扫描可见范围之外：swf 等二进制是盲区，覆盖面要申报。

### 作者的盲点 / 时代局限

- sink 清单以 PHP/Java 2014 年生态为准（register_globals、magic_quotes 时代），用于现代栈需替换（JS 的 eval/Function、反序列化 gadget 链、模板引擎清单），但"可控输入 × 危险原语"的判定式不变。
- 未讨论自动化污点分析的工程实现（现代 SAST 即其产品化），书中的手工追踪法在大型代码库需与工具配合。

### 容易混淆的邻近方法论

- Fuzz/渗透测试：从外部试探行为，覆盖黑盒但无覆盖面保证；本方法从代码内部穷举路径，结论可声明覆盖范围——两者互补。
- 危险函数禁用（php.ini disable_functions）：只是破坏 sink 条件的一种手段，不替代追踪——入口约束与结构化绑定同样是合法破坏点。
