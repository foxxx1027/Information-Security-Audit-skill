# 工具与人工的分工边界

## R — 原文 (Reading)

> "而对于'CSRF'、'越权访问'、'文件上传'等漏洞，却难以达到自动化检测的效果。这是因为这些漏洞涉及系统逻辑或业务逻辑，有时候还需要人机交互参与页面流程。因此这类漏洞的检测更多的需要依靠手动测试完成。"
>
> — 原作者，原始方法论来源第17章 17.6

---

## I — 方法论骨架 (Interpretation)

这条方法回答"安全测试的活怎么分给机器和人"，判据只有一条：**漏洞是否可模式化**。

- 可模式化的漏洞（SQL 注入、XSS、信息泄露等有明确特征模式的输入类问题）交给扫描器大面积跑；
- 依赖系统逻辑、业务逻辑或人机交互流程的漏洞（CSRF、越权访问、文件上传、业务流程类）机器测不了，必须人工设计用例测试。

三条配套纪律：

1. **工具输出=待验证线索，不是结论**。扫描器有误报（浪费修补资源）和漏报（制造虚假安全感），报告必须经安全工程师逐条确认，再结合手动测试结果，才构成安全测试报告。未经确认的扫描结果不得作为发布依据。
2. **模型与工具保证下限，人做取舍**。checklist/扫描器/威胁模型是放大器不是替代品——覆盖面靠工具，判断质量靠经验。
3. **审计工具的可见范围**。"扫过了"不等于"都扫到了"：编译产物（书中是 swf，今天是 wasm/混淆包/预编译库）、边角小项目、复杂框架内部都在扫描器视野之外。0 告警可能是盲区而非安全，报告应显式声明未覆盖面。

## A1 — 书中的应用 (Past Application)

### 案例 1: SDL 测试阶段的分工规则
- **问题**: 测试资源有限，扫描器与人工测试各管什么？
- **方法论的使用**: 按"是否依赖业务逻辑/人机交互"划界——注入类交扫描器，CSRF/越权/文件上传必须手动测试。
- **结论**: 自动化做广度、人工做深度与逻辑；扫描报告须人工确认才是安全测试报告。
- **结果**: 形成可执行的测试资源分配规则，避免用扫描报告冒充安全测试、也避免人力浪费在机械项上。

### 案例 2: 代码审计工具的两大失灵场景（17.5.2）
- **问题**: 自动化代码审计工具能否替代人工审计？
- **方法论的使用**: 考察工具实际能力——找到 eval() 等敏感函数后，跨文件回溯调用路径极难；复杂框架缺支持导致大量误报漏报。
- **结论**: 没有完美的自动化审计工具；安全测试与代码审计是两个互补环节（静态看"写得对不对"、运行看"跑起来会怎样"），不可互替。
- **结果**: 确立"工具产出=待验证线索"的纪律，人工确认成为必要预算项而非可选项。

### 案例 3: Flash XSS 的扫描盲区（第3章 3.2.8）
- **问题**: 注入 Flash 变量的 XSS 为什么长期漏网？
- **方法论的使用**: 检查工具可见范围——问题藏在编译后的 swf 里，一般扫描与代码审计工具都读不到。
- **结论**: 工具可见范围之外就是盲区；安全左移必须覆盖构建产物，或把检查前移到源码侧。
- **结果**: "扫描覆盖率是虚假的"成为显性风险，报告需声明盲区。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. CI 里集成了 SAST/DAST，跑完 0 告警，要判断能否据此通过安全评审。
2. 制定渗透测试/安全测试计划，决定人天怎么分配、哪些项交给工具。
3. 拿到扫描器报告要转给开发修复，需要先处理误报。
4. 团队想让某类漏洞（越权、逻辑类）也能自动化检测，需要判断可行性。
5. 安全评审中要评估"扫描绿灯"的含金量。

### 语言信号 (用户的话里出现这些就应激活)

- "扫描器没扫出问题，是不是就安全了 / SAST 0 告警"
- "误报太多了 / false positives 处理不过来"
- "这个漏洞能不能自动化检测 automate detection"
- "渗透测试要多少人天 / 测试计划怎么排"
- "CI 安全门禁 security gate 绿了能发布吗"

### 与相邻 skill 的区分

- 与 `whitehat-continuous-security-verification` 的区别：那边处理"制度/设备已存在"的假设不可靠，要周期性验证；本 skill 处理一次测试内部工具与人的分工判据。
- 与 `whitehat-security-as-compliance-checks` 的区别：那边是把开放性安全问题转成可判定条目（让更多内容变得可机器查）；本 skill 先划界——哪些本来就该机器、哪些本来就必须人。

## E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

1. **列出目标漏洞类别并逐条标注**
   - 完成标准: 每类漏洞标注"可模式化 / 依赖业务逻辑"及一句理由（如：SQL 注入—特征模式明确；水平越权—需理解数据归属逻辑）。

2. **可模式化项配置工具覆盖**
   - 完成标准: 扫描器/SAST 规则已覆盖对应资产并在近期跑过，原始报告产出。

3. **审计工具覆盖面**
   - 完成标准: 列出工具可见范围之外的资产/形态（编译产物、第三方预编译库、边角项目、框架内部），逐项说明如何补检（专门工具/源码侧检查/人工）。
   - 判停条件: 若关键资产大半在工具盲区内 → 结论只能写"未覆盖"，不得给出"通过"或"未发现问题"。

4. **业务逻辑项排人工用例**
   - 完成标准: CSRF/越权/文件上传/流程类每项有具体人工测试用例、执行人、排期；不允许"由扫描器代查"。

5. **人工确认并合成报告**
   - 完成标准: 每条扫描告警标记"确认真实/误报"；最终安全测试报告 = 确认后的扫描结果 + 手动测试结果，并附"未覆盖面"声明。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 具体扫描器产品的采购选型对比（性能/误报率横向评测是采购流程，本 skill 只提供分工判据）。
- 单个漏洞怎么修的方案设计（那是修复纪律的领地）。
- 一人小团队的一次性全包测试——判据仍可用，但不必机械走五步。

### 作者在书中警告的失败模式

- 把扫描器原始报告当安全测试结论交付或直接转开发修复（误报浪费资源、漏报制造虚假安全感）。
- "扫描绿灯 = 安全"——书用编译产物盲区直接否定该误区。
- IDS/告警规则装完就用：规则须按本环境长期调优，未经实践检验不联动处置（工具在运营侧同理）。

### 作者的盲点 / 时代局限

- 成书于 2014：无现代 SAST 的半自动数据流分析、无 LLM 辅助审计的语境；"CSRF 难自动化"在今日因框架内置 Token 与扫描器进步已部分改善——但"业务逻辑类必须人"的判据依然成立，只是边界线在移动，需按当前工具能力重画。
- 盲区例子是 Flash swf（已 EOL），同类盲区应替换为 wasm、混淆压缩包、预编译第三方库、生成的代码。
- 书中工具语境是甲方自研扫描器（大厂资源），中小团队用开源/商用组合时判据不变、覆盖面审计更重要。

### 容易混淆的邻近方法论

- 安全合规化（把判断变成可扫描条目——本 skill 的配套手段，不是同一件事）。
- 持续验证运营观（部署之后的周期性验证纪律）。
