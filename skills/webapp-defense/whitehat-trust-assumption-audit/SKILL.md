# 信任假设检验法：列出机制信任什么，逐条攻击

## R — 原文 (Reading)

> "笔者认为，安全问题的本质是信任的问题。"
> "这个跨域访问方案的安全基础就是信任'JavaScript无法控制该HTTP头'，如果此信任基础被打破，则此方案也将不再安全。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.3；第 2 章《浏览器安全》2.1

---

## I — 方法论骨架 (Interpretation)

没有机制是凭空安全的，每个机制都在"赌"一些前提成立。CORS 赌"JS 控制不了 HTTP 头"，CSRF Token 赌"参数不可预测"且"XSS 已解决"，白名单赌"名单条目不失陷"，密钥管理赌"还没被入侵"。评审的核心动作因此不是给印象分，而是把赌注翻出来看：

1. **枚举前提**：这个机制正常工作，需要哪些条件一直为真？——写下来，越显式越好（客户端可控的、环境依赖的、上游依赖的、时间敏感的，分四类找）。
2. **逐条攻击**：对每条前提问"谁能让它变假？"——不是问"一般会不会"，而是找具体场景（新 API、插件、配置项、内部攻击者、被入侵后的状态）。
3. **分级定论**：某条前提在真实环境已被打破 → 机制在该场景整体失效，结论是"先修前提，再谈实现细节"；多条前提同时脆弱 → 方案从根上重选。
4. **双向使用**：防守侧用来评审方案；攻击侧同法——对"利用链必然成立"的假设列出失效条件（Cookie 绑定 IP 则劫持失效），评估报告写前提不写断言。

这套动作把"感觉还行"变成可执行的清单，也解释了为何安全方案难做：不是机制不够聪明，而是赌注容易被忽视。

## A1 — 书中的应用 (Past Application)

### 案例 1: CORS/CSP 的共同前提——"XSS 无法控制 HTTP 头"（第 2 章）
- **问题**: W3C 跨域方案与 CSP 看似完全不同，凭什么都可信。
- **方法论的使用**: 显式写出两者的同一信任前提——脚本无法注入/控制 HTTP 头；再检验该前提：普通 XSS 确实改不了头，但插件（如 Flash 曾可自定义 Expect 头）能打破它。
- **结论**: 前提被打破的范围内方案整体失效——凡以"不可控头"为根基的机制，都要随浏览器/插件能力演进重验。
- **结果**: "评估机制先列信任前提"成为全书反复复用的评审动作，CORS、CSP、crossdomain.xml 三例同一骨架。

### 案例 2: CSRF Token 依赖"XSS 已解决"（第 4 章 4.3.3.2）
- **问题**: 上了 Anti-CSRF Token，为何仍可能被伪造请求击穿。
- **方法论的使用**: 列出 Token 的前提链——token 不可预测（安全随机数）、不外泄（不进 URL）、以及最关键的：页面里没有 XSS 能直接读取 token。
- **结论**: 存在 XSS 时攻击者读到 token 再构造合法请求（XSRF），Token 形同虚设——"先解决 XSS，CSRF Token 才有意义，否则是空中楼阁"。
- **结果**: 防御体系存在依赖顺序，评审时必须查"它依赖的前提是否被别的漏洞破坏"。

### 案例 3: 密钥管理对"入侵后"场景失效（第 11 章 11.6）
- **问题**: 集中管理的密钥系统是否就是最后防线。
- **方法论的使用**: 检验前提"取密钥的请求来自正常业务"——攻击者拿到 webshell 后恰恰以应用身份调取钥逻辑，前提无法区分攻击者与业务。
- **结论**: 密钥管理防的是非正常渠道泄露（内控、误配、传播），不是入侵后的最后一道防线；每道防线有明确作用域。
- **结果**: 评审结论从"有密钥管理即安全"改为"认清该防线管什么、不管什么，入侵后场景另行设防"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 评审一份安全方案（认证设计、JWT/OAuth 集成、加密方案、风控规则），要给出结构化意见。
2. 方案里某组件"默认应该安全"（框架、云服务、浏览器行为），需要验证默认假设。
3. 写渗透/风险评估报告，需要说明利用链成立的前提条件而非只给结论。
4. 事故复盘时定位"我们当初信任了什么、它为什么变假"。
5. 引入新技术（新协议、新中间件）时评估既有机制的前提是否被新能力打破。
6. 把云厂商/SaaS/第三方的承诺当安全依据（"厂商负责底层安全"），需要检验责任共担边界与我方剩余责任。

### 语言信号 (用户的话里出现这些就应激活)

- "这个方案安全吗？帮我评审一下。"
- "JWT 的密钥放环境变量、算法头客户端指定，有问题吗？"
- "我们用了 X 框架/云托管，应该就没事了吧？/ 厂商说底层安全他们负责（把第三方承诺当默认前提）"
- "为什么上了 Token/防火墙还是被打？"
- "review this auth design / what could break this scheme / trust assumptions"

### 与相邻 skill 的区分

- 与 `whitehat-trust-boundary` 的区别: 那个建模"域与边界"决定检查摆在哪（空间/结构视角）；本 skill 检验"某机制隐含信任什么前提"（逻辑/时间视角）。画图用那个，挑假设用本 skill。
- 与 `whitehat-security-assessment` 的区别: 四阶段评估是流程骨架；本 skill 是其中方案确认与机制评审阶段反复调用的原子动作。
- 与 `whitehat-signal-reliability` 的区别: 那个专门给"信号"分级（可伪造成本）；本 skill 覆盖一切前提（含非信号类：环境、上游、时间、内部人员）。
- 与 `whitehat-continuous-security-verification` 的区别: 那个持续验证已部署机制是否仍有效（运营巡检）；本 skill 把"厂商负责底层安全/设备已部署/半年零事故"当作待列出、待攻击的信任前提来检验——检验前提本身用本 skill，部署后的周期核验用那个。
- 与 `whitehat-defense-in-depth` 的区别: "上了 Token 又配了防火墙还是被打"若问层间怎么配合、还该加哪层（结构设计）→ 那个；若问既有机制为何没守住——哪条隐含前提被打破（Token 赌"无 XSS 能读到它"、防火墙赌"流量可见"）→ 本 skill。先查前提，再谈补层。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **描述机制**：一句话写清机制的工作方式与保护目标（输入什么、判定什么、失效时发生什么）。
   - 完成标准: 能指出"这个机制在防线中挡的是哪一步"。
2. **枚举信任前提**：按四类列——①客户端可控项（头、Cookie 属性、JS 环境）；②环境默认（浏览器行为、框架版本、基础设施）；③上游依赖（其他漏洞是否已解决、第三方是否可信）；④时间/状态（前提现在成立，重放/升级/被入侵后是否仍成立）。
   - 完成标准: 每条前提写成可证伪的陈述句（"X 无法被 Y 控制"），而非形容词。
   - 判停条件: 若机制完全不存在（用户还在开放式威胁建模阶段），转 `whitehat-security-assessment` 流程，本 skill 等有方案雏形再用。
3. **逐条攻击前提**：对每条找具体打破场景——新技术、配置项、内部人、组合漏洞、被入侵后的状态；标注"已可打破/理论可打破/暂无打破路径"。
   - 完成标准: 每条前提有打破场景或明确论证"当前无已知路径"；已打破的给出复现思路。
4. **定论与排序**：按打破的难易排序；任一核心前提已破 → 结论为"方案在该场景整体失效，先修前提"；前提都成立 → 明确写出机制的适用边界。
   - 完成标准: 评审意见形如"前提①③已破（场景 X/Y）→ 先修前提；前提②成立但依赖版本 Z，纳入升级监控"。
5. **写入依赖与复核**：把幸存的前提转为监控项/依赖声明（版本锁定、周期重验、上游漏洞联动），前提被新能力打破时触发重评。
   - 完成标准: 每条前提有"谁来复核、多久复核、什么事件触发重验"。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没有机制可评的开放式威胁建模——先走评估四阶段产出方案，再回来验前提。
- 纯合规对表检查（等保/PCI 条目核对）——对表动作不需要重推信任链，照标准执行即可。
- 用它替代测试：前提"暂无打破路径"不等于安全证明，渗透验证仍是独立环节。

### 作者在书中警告的失败模式

- 赌注叠加不自知：CSRF Token 之上再叠 Referer 校验，两层机制共享同一前提（头不可伪造/不可缺失）——前提一破两层同倒，不是纵深。
- 依赖外部默认不重验：浏览器行为、插件能力随版本演进（P3P 一条配置瓦解第三方 Cookie 拦截），"当前成立"需要周期复核。
- 内部人员与被入侵态缺位：锁匠可能私藏钥匙——前提清单必须包含"我们自己人"与"已被入侵后"两类场景。

### 作者的盲点 / 时代局限

- 2014 年案例绑定当时的浏览器/插件格局（Flash、P3P、IE8），具体打破场景已过时，但"列前提—攻击前提"的骨架不随技术过期。
- 未系统引入威胁建模工具化的前提管理（如 STRIDE 中每威胁对应的前提矩阵），评审输出与现代 ATT&CK 场景映射需自行补充。

### 容易混淆的邻近方法论

- 威胁建模（STRIDE）：枚举"谁会怎么打"；本 skill 枚举"我们的机制赌什么"——一个向外看攻击者，一个向内看自身赌注，评审时双向并用。
- 信任边界划分：那是结构性布局（域怎么划、检查放哪）；本 skill 是逻辑性检验（布局里的每个组件信任什么），边界画完仍需逐组件验前提。
