# 信任域与信任边界的单向检查规则

## R — 原文 (Reading)

> "数据从高等级的信任域流向低等级的信任域，是不需要经过安全检查的；数据从低等级的信任域流向高等级的信任域，则需要经过信任边界的安全检查。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.3 返璞归真，揭秘安全的本质

---

## I — 方法论骨架 (Interpretation)

把系统切成若干信任域（可信程度不同的区域），域与域之间是信任边界。核心是一条**单向规则**：检查只看数据流向，不看区域本身——

- 数据从低信任域流向高信任域（如公网请求进应用、外部输入进数据库），必须过边界检查；
- 数据从高信任域流向低信任域（如服务端配置下发到前端），不需要检查。

作者用机场安检类比：安检后的旅客去别处免检，从外面回来要再检——检查跟着流向走，不是对候机厅一刀切。最简实现是按网络圈划分（Internet → Web 圈 → 数据库圈），但**网络位置不等于信任等级**：同集群的两个服务、浏览器里的两个"源"，都可以是不同信任域。

这条规则的两个直接用途：
1. **摆位判定**——过滤器/校验器应放在"不可信→可信"的抬升方向上，放错方向等于没放。
2. **越界识别**——凡是让凭证、数据或权限跨出其所属信任域的设计（把密码交给第三方、会话标识进 URL），都是在强行合并信任域，攻击面随之扩大。

## A1 — 书中的应用 (Past Application)

### 案例 1: 同源策略——浏览器里的信任域划分（第 2 章）
- **问题**: 浏览器如何决定一段脚本能不能读另一份文档的数据。
- **方法论的使用**: 把"源"（协议/域/端口）视为浏览器层面的信任域，边界画在"读取"而非"加载"上：script/img 的 src 可以跨域加载资源，但 JS 不能读写返回内容；XMLHttpRequest 只能访问同源。
- **结论**: "能加载"不等于"能读取"——加载是让数据流进低信任的展示层，读取才是跨边界进高信任的执行环境。
- **结果**: 精确解释了哪些标签是安全边界内的通道、哪些是跨域通道，成为后续 CORS/postMessage 讨论的基础。

### 案例 2: 为集成交出第三方密码——信任域被强行扩大（第 10 章）
- **问题**: 人人网做"绑定 MSN 好友"功能，直接索要用户的 MSN 账号密码。
- **方法论的使用**: 用信任域视角审视：A 站持有 B 站主凭据 = 把 A 站数据库划进了 B 站的信任域；A 站一旦被拖库，攻击者同时拿到用户在 B 站的身份。
- **结论**: "承诺安全"不改变风险归属，攻击面已被扩大；应改用范围受限、可撤销的令牌（OAuth 的动机）。
- **结果**: 书中以此引出最小授权票据的正确方向，这一反例成为"不要交出主凭据"的标准论据。

### 案例 3: sid 放进 URL——会话凭证漂移出受控边界（第 9 章）
- **问题**: 手机浏览器不支持 Cookie 时，QQ WAP 邮箱把会话标识 sid 放进 URL 传递。
- **方法论的使用**: 追踪 sid 的数据流向：URL → Referer → 第三方服务器日志，凭证一路流出应用控制的信任边界；Cookie 路径有同源策略与 HttpOnly 保护，URL 路径什么都没有。
- **结论**: 凭证进 URL = 凭证进入不可控信任域，Referer/历史/日志都会外泄。
- **结果**: 攻击者在 sid 生命周期内拿这个值即可登录邮箱——等同于账户失窃。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 架构评审：新系统的服务拓扑图摆在面前，需要决定在哪里放认证、校验、过滤逻辑。
2. 有人主张"内网互信"——同 VPC/同 K8s 集群的服务之间免认证，需要论证是否成立。
3. 第三方集成方案评审：对方要求拿到用户凭据/长期 token，评估攻击面变化。
4. 凭证或敏感数据的存储位置与传递路径设计（放 URL、放日志、放消息队列是否越界）。
5. 审计一组校验规则时发现"处处都在校验但仍被绕过"，需要重新定位校验层。

### 语言信号 (用户的话里出现这些就应激活)

- "内网的服务互相调用还要认证吗？都是可信的嘛"
- "这个校验放在网关还是放在服务里做？"
- "把密码给第三方/第三方要拿我们的 token，有什么风险？"
- "为什么不能把 sid/token 放在 URL 里传？"
- "should services inside the same cluster trust each other / where should validation live"

### 与相邻 skill 的区分

- 与 `whitehat-trust-assumption-audit` 的区别: 本 skill 建模"域与边界"并决定检查摆在哪，是空间/结构视角；那个检验"某个机制隐含信任了什么前提"，是时间/逻辑视角（前提被打破则机制失效）。画图用本 skill，挑假设用那个。
- 与 `whitehat-whitelist-first` 的区别: 本 skill 决定"在哪检查"，那个决定"检查规则写成白名单还是黑名单"，两者常组合使用但回答不同问题。
- 与 `whitehat-defense-at-interpretation` 的区别: 本 skill 是信任等级维度的摆位（跨域数据流）；那个是解释器维度的摆位（数据变成代码的那一刻），两者可叠加：跨边界后还要在消费点按语境编码。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **画信任域图**：把系统组件按可信程度分域（如：公网用户、浏览器页面、API 网关、业务服务、数据服务、第三方系统），标注每个域持有的凭据与数据。
   - 完成标准: 一张分域清单/图，每域一行（组件、信任等级、持有物），等级至少三档且排序有理由。
2. **标数据流向**：对图上每条数据/请求通道标注方向（谁调用谁、数据从哪流到哪），区分"上行"（进入更高信任域）与"下行"。
   - 完成标准: 每条通道有方向箭头与载荷说明，无未标注的通道。
3. **核对上行通道的边界检查**：逐条检查每个低→高数据流上是否存在检查，检查强度是否与目标域等级匹配。
   - 完成标准: 输出"通道 × 检查现状 × 缺口"三列表；任何无检查的上行通道被列为缺口。
4. **找越界凭证**：检查是否有凭据/敏感数据离开其所属域（URL 携带、日志落盘、交第三方、跨服务明文传递）。
   - 完成标准: 每个凭证一条流向记录；越界项标注风险与替代方案（最小授权令牌、一次性转发）。
   - 判停条件: 若第 3 步发现所有上行通道全部无检查（完全裸奔），先输出最高优先级的 1–3 条补防建议即可结束，不必继续细查——此时的答案已确定。
5. **输出摆位结论**：明确写出每类检查应放的层次（如"服务间认证放 B 服务入口而非依赖网络策略"），并说明为何该方向是抬升方向。
   - 完成标准: 结论能与第 1 步的域图一一对应，避免与网络拓扑混谈。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 讨论单个字段的具体校验正则/编码函数——那是编码细节，画信任域图是过度准备。
- 评估某机制的前提假设是否可靠（"CSP 为什么可行"）——用信任假设检验，不是画边界。
- 纯网络分区/防火墙策略配置——网络圈只是信任域的最简实现之一，两者不能画等号。

### 作者在书中警告的失败模式

- 把网络位置当信任等级：交出第三方密码的反例证明"承诺安全"不能合并信任域；攻击面扩大是结构事实。
- 检查按区域一刀切而非按流向：机场安检类比里，对候机厅内部反复检查（高→低方向）是浪费，而回流未检（低→高漏检）才是漏洞。
- 凭证随 URL 漂移出受控边界：sid 经 Referer 泄露一案说明边界外的通道（日志、历史、外链）不受应用控制。

### 作者的盲点 / 时代局限

- 书中"按网络圈划分"的最简实现停留在 2014 年的自建机房拓扑；云原生下的信任域应是服务/身份/密钥维度（服务账户、IAM 角色），同集群 ≠ 同域——书中无 K8s/mTLS/服务网格素材，需按"网络位置≠信任等级"的规则自行外推。
- 浏览器侧讨论大量绑定 Flash/P3P 等已消亡技术，"源四要素"部分仍然成立，插件部分仅作历史参考。

### 容易混淆的邻近方法论

- "输入检查 vs 输出编码"（`whitehat-defense-at-interpretation`）同为摆位问题，但裁决判据不同：本 skill 看信任抬升方向，那个看语境在哪一环可确定。
- "数据最小化"（`whitehat-data-minimization`）与越界凭证检查相邻，但它的裁决问题是"要不要持有"，不是"流经哪里"。
