# 不可预测性原则：让关键值不可猜

## R — 原文 (Reading)

> "不可预测性（Unpredictable），能有效地对抗基于篡改、伪造的攻击。"
> "即使无法修复 code，但是如果能够使得攻击的方法无效，那么也可以算是成功的防御。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.7.4 不可预测性原则

---

## I — 方法论骨架 (Interpretation)

很多攻击的前提不是"攻破了什么"，而是"猜得到"。攻击者能按规律推算出关键值——自增的记录 id、可枚举的用户名、可预知的放号时间——就能用一个循环批量遍历，或在攻击前离线构造好全部请求。防御思路因此可以反过来做：**不堵漏洞，堵预测**。

三个操作要点：

1. **识别可预测资产**：凡是"知道值≈获得能力"的东西（资源 id、会话凭证、找回链接、放号凭证、回调参数）都不能有规律。
2. **用强随机替换规律**：值必须来自安全随机数，攻击成本从"遍历序号"变成"先爬取全站才能拿到全集"或"必须在受害者会话里实时读取"。
3. **反向应用——让攻击方法失效**：当缺陷本身修不掉（不可能要求所有软件无漏洞），可以让利用它所需的确定性条件消失。ASLR 让栈地址不可猜、DEP 让数据页不可执行：漏洞还在，利用链断了。这为"补不胜补"的场景提供了正统出路——抬高利用成本也是防御。

它对抗的是篡改/伪造类攻击；对"值本来就该保密"的场景（密钥），随机只是底线，仍需密钥管理。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: CMS 文章 id 随机化（第 1 章 1.7.4）
- **问题**: 内容管理系统用自增 id 标记文章，攻击者想批量删除/抓取时成本极低。
- **方法论的使用**: 按"堵预测"重构标识：id 随机化后，攻击者必须先爬取全部页面拿到完整 id 集合才能继续。
- **结论**: 攻击成本从"一个循环"涨到"全站爬取"，批量攻击的经济性被破坏。
- **结果**: 该例子成为全书随机化设计的第一样板，与水平越权防护中的"不可猜测间接引用"同源。

### 案例 2: ASLR/DEP——修不了缺陷就废掉攻击方法（第 1 章 1.7.4）
- **问题**: 微软无法要求所有第三方软件没有内存破坏漏洞，逐个修补不可行。
- **方法论的使用**: 反向应用原则：攻击利用依赖可预测的内存地址与可执行的栈，DEP 让堆栈不可执行、ASLR 让基址随机——确定性条件被移除。
- **结论**: "使攻击的方法无效"与修复缺陷并列为正统防御，实践证明有效。
- **结果**: "补不胜补"的场景获得结构性出路：把修补问题转化为抬高利用成本问题。

### 案例 3: Anti-CSRF Token 与 SessionID 的随机性（第 4、9 章）
- **问题**: CSRF 防御与 会话安全为什么都把"足够随机"列为第一工程要求。
- **方法论的使用**: 归因同一条原则——CSRF 成立的根基是"重要操作参数全部可猜测"（token 引入不可预测参数即破坏）；SessionID 若可预测则可伪造会话。
- **结论**: token 必须用安全随机数生成器；验证码用随机文件名防彩虹表预计算、反垃圾规则保密，都是同一原则在不同层的落地。
- **结果**: 随机性成为凭证类设计的验收项：安全随机数生成、不进 URL、消耗后更新。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计资源标识/订单号/分享链接，纠结自增 id 会不会被遍历（水平越权批量试探）。
2. 高并发稀缺资源发放（挂号、抢票、秒杀）被脚本预构造请求打穿，需要让"预测+预构造"失效。
3. 设计 token/会话/找回链接/回调参数，确定随机性与传递方式。
4. 存在修不掉/短期修不掉的缺陷，考虑"让利用条件失效"的缓解路径（配置随机化、地址随机化）。
5. 评估爬虫/批量注册/薅羊毛的攻击成本结构。

### 语言信号 (用户的话里出现这些就应激活)

- "自增 id 会不会被遍历/批量爬？"
- "号一放出来就被脚本抢光了，怎么设计？"
- "这个 token 要多随机？能不能用时间戳/哈希？"
- "这个洞修不动，有没有别的办法？"
- "enumerable IDs being scraped / predictable tokens / how to stop bulk enumeration"

### 与相邻 skill 的区分

- 与 `whitehat-whitelist-first` 的区别: 白名单裁决"允许什么"（规则形态）；本 skill 处理"关键值能不能被猜"（值的生成方式）。随机 id 常与授权白名单配合，但回答的是枚举成本问题，不是准入问题。
- 与 `whitehat-csrf-intent-token` 的区别: 那个是本原则在 CSRF 场景的完整工程化（token 的生成/绑定/校验/依赖顺序）；本 skill 是一般原则，覆盖 id、凭证、缓解设计等更广对象。
- 与 `whitehat-mitigation-vs-fix` 的区别: ASLR/DEP 这类"让攻击失效"的手段在本书中被当作成功防御而非二等缓解；但对外承诺时仍应按减损口径验收——两个视角并存，裁决归那个 skill。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **盘点可预测资产**：列出全部"知道值即获得某种能力"的值——资源 id、用户名、凭证、token、分享链接、放号/开奖时序、回调参数。
   - 完成标准: 清单中每项标注当前生成方式（自增/时间戳/弱哈希/安全随机）与"猜到一个值能干什么"。
   - 判停条件: 若某值猜到后无任何能力增益（纯展示型数据），从清单移除，不为它付随机化成本。
2. **推演批量攻击成本**：对每项问——攻击者拿到规律后能否一个循环遍历？能否离线预构造全部请求？
   - 完成标准: 每项写出现行成本曲线（遍历 N 次请求 vs 先爬全站）。
3. **替换为强随机**：对可预测且有能力增益的项改用安全随机数（CSPRNG），检查长度与熵是否支撑"猜中概率可忽略"。
   - 完成标准: 生成代码不再含时间戳/自增/低熵输入；随机值不进 URL/日志（会随 Referer 泄露）。
4. **评估反向应用**（若缺陷不可修）：列出利用链依赖的确定性条件（固定地址、固定文件名、固定时序、固定响应），逐个设计随机化/失效手段。
   - 完成标准: 每个确定性条件有对应失效措施，并明确标注这是"让攻击失效"的缓解而非根因修复。
5. **验证与配套**：实测枚举（顺序请求相邻值应不可达）；确认服务端授权校验仍在——随机化只抬高成本，不替代访问控制。
   - 完成标准: 枚举测试失败证据 + "不可预测≠授权"的说明写入方案。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 机密数据的保密——不可预测不等于保密：一个不可猜但未加密的接口，拿到链接的人仍可使用；密钥管理走密码学纪律。
- 替代访问控制——随机 id 只是抬高枚举成本，服务端必须仍做归属校验，否则是 security by obscurity。
- 对内部系统/低价值枚举对象滥用随机化——破坏可读性、可调试性与统计（书中也指出参数哈希"伤 URL 可读性与统计"，才演进为 token 方案）。

### 作者在书中警告的失败模式

- 时间戳/伪随机当随机数：弱随机三案例（Debian 弱随机、种子猜解、跨应用攻击）说明可预测的"随机"比不随机更危险——制造了安全假象。
- 随机值进 URL：会随 Referer 外泄（QQ 邮箱 sid 案例），不可预测性被传递渠道瓦解。
- 规则/模型下发到客户端被逆向：反垃圾特征放客户端即"见光死"——保密性同样属于不可预测性的配套要求。

### 作者的盲点 / 时代局限

- 成书于 2014 年，未覆盖现代侧信道与机器学习对"不可预测"的侵蚀（行为指纹、批量打码平台使某些随机化收益下降）；ASLR/DEP 案例之后也出现了绕过技术（info leak 类利用），引用时按"抬高成本"而非"绝对防御"口径。
- 对分布式 id 生成的工程权衡（分库分表需要有序性 vs 安全需要无序）未展开，现代方案（雪花 id+间接引用层）需自行补。

### 容易混淆的邻近方法论

- 最小权限：限制"能做什么"；本原则限制"能猜到什么"——水平越权防护中两者叠加（随机间接引用 + 归属校验）。
- 混淆（obfuscation）：作者明确把"依赖攻击者不知道算法"归为混淆而非安全（Kerckhoffs），不可预测性针对的是每个实例的值，不是算法保密。
