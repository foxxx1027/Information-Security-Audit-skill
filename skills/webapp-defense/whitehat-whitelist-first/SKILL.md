# 白名单优先（Secure By Default）及其信任边界

## R — 原文 (Reading)

> "'Secure by Default'原则，也可以归纳为白名单、黑名单的思想。如果更多地使用白名单，那么系统就会变得更安全。"
>
> — 方法论出处，第 1 章《我的安全世界观》1.7.1 Secure By Default 原则

---

## I — 方法论骨架 (Interpretation)

面对"禁止什么"与"允许什么"两种写规则的方式，默认选白名单。理由不是审美，而是**失败模式的不对称**：

- 黑名单枚举"坏的东西"，而坏集合随技术演进无限增长（新后缀、新标签、新编码），永远枚举不全；漏掉一项即放行攻击——**失败开放**。
- 白名单枚举"允许的东西"，允许集合可枚举、可审计；漏配的后果是新功能不可用（被发现、被补上），而不是被攻击——**失败关闭**。

配套含义还有两层：授权配置用"默认拒绝 + 逐项显式允许"；最小权限是它在主体维度上的同胞原则（只授予必要的）。

但白名单不是终点：**白名单本身是一个信任假设**。名单条目失陷、被通配符（*、0.0.0.0/0、allow all）放全、被错误维护得过宽，白名单立刻退化为全开，甚至比不配更糟——它制造了"已有防护"的假象。所以审计白名单要看两点：条目粒度是否精确到具体值，以及名单的变更是否受控。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: FCKEditor 上传黑名单——未列出的后缀直传（第 8 章）
- **问题**: 富文本编辑器用黑名单限制上传后缀（禁 php/php3/asp/jsp 等），为何仍被拿 webshell。
- **方法论的使用**: 按"黑名单失败开放"分析：坏后缀集合随解析器与版本增长，php2、php4、inc、asa、cer 等未列后缀直接上传并在部分环境被解析。
- **结论**: 文件类型检查必须白名单（只允许 jpg/png 等已知安全类型），黑名单"已经无数次被证明是不可靠的"（书中 8.3 节原话）。
- **结果**: 配合"目录禁执行、随机改名、独立域名"多层设计，安全上传方案成立；黑名单路线被全书否定。

### 案例 2: SQL 注入防御中 escape 与关键字黑名单的三组反证（第 7 章）
- **问题**: 开发者常用"转义特殊字符 + 过滤关键字"当防注入，为何不可靠。
- **方法论的使用**: 作者逐组推演黑名单的漏：注释可替代空格（/**/）、十六进制可免引号、免括号写法绕过括号过滤；而 HAVING、ORDER BY 是自然语言常用词，硬过滤又误杀正常数据。
- **结论**: 黑名单"或多或少存在问题"，唯一可靠路线是参数化（SQL 结构与数据分离）+ 白名单式类型约束。
- **结果**: 防御阶梯收敛为：预编译 → 安全存储过程 → 类型检查/安全函数兜底。

### 案例 3: crossdomain.xml 与 CORS 通配符——白名单自身的信任边界（第 1/6 章）
- **问题**: Flash crossdomain.xml 和 CORS 都是白名单机制，为何书中仍标为高危点。
- **方法论的使用**: 对白名单本身做信任假设检验：策略写成 allow-access-from domain="*" 时，任意域都能访问，白名单退化为全开；CORS 的 Access-Control-Allow-Origin: * 同理，"等于没有做任何安全限制"。
- **结论**: 白名单解决的是可枚举性，没解决名单条目的可信度——通配符与过宽条目要把白名单判为失效。
- **结果**: 审计动作定为：全站搜授权配置里的通配符与反射任意 Origin 的实现，正确写法精确到具体源。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 设计文件上传/导入功能的类型检查规则，纠结"禁哪些后缀"还是"允许哪些后缀"。
2. API 网关/路由/权限系统要挡未上线或高危路径，考虑加黑名单规则。
3. 评审 CORS、crossdomain.xml、安全组、防火墙等授权配置，发现通配符。
4. 富文本/UGC 内容过滤：过滤危险标签（黑名单）还是只允许安全标签（白名单）。
5. 给新模块设计默认访问策略（默认允许还是默认拒绝）。

### 语言信号 (用户的话里出现这些就应激活)

- "我们加一条黑名单把恶意路径/危险后缀封掉？"
- "CORS 配成 * 图省事，有什么问题吗？"
- "过滤掉 script 标签和 on 事件是不是就安全了？"
- "权限先都放开，出问题再收？"
- "why is my blacklist filter bypassed / is CORS wildcard * okay"

### 与相邻 skill 的区分

- 与 `whitehat-context-encoding` 的区别: 本 skill 裁决"规则写成允许集还是禁止集"（结构选择）；那个裁决"输出到某语境时用哪种编码"（消费点动作）。富文本过滤两者都涉及：标签集合用白名单选，非富文本输出用语境编码。
- 与 `whitehat-trust-boundary` 的区别: 本 skill 是检查规则本身的形态；那个是检查该摆在哪条数据流上。
- 与 `whitehat-attack-surface-reduction` 的区别: 那个的次序是"删除>禁用>加固"，处理的是功能面存废；本 skill 处理保留功能的规则写法。

## E — 可执行步骤 (Execution)

当 skill 被激活后， agent 应按以下步骤执行：

1. **定位规则形态**：找出当前方案里所有"禁止 X"型规则（黑名单/负向匹配/通配符放行）。
   - 完成标准: 一张清单，每条规则标注形态（黑/白/通配）与保护对象。
2. **对每条黑名单做失败模式推演**：问"漏掉哪个值会怎样？新增值何时会被发现？"
   - 完成标准: 每条黑名单写出至少一个绕过变体（变体路径：编码、同义后缀、新标准标签、大小写/截断），证明其失败开放。
   - 判停条件: 若某场景的合法值域确实无法枚举（如自由文本正文），停止转白名单讨论，跳到第 4 步按"消费点编码/净化"处理。
3. **改写为白名单**：把规则翻转为"显式枚举允许值 + 默认拒绝"，允许集逐条有 owner。
   - 完成标准: 新规则可回答"新增一个值需要谁审批"；默认行为是拒绝而非放行。
4. **审计白名单自身**：搜通配符（*、ANY、0.0.0.0/0、allow all）与反射型放行（回显用户输入的 Origin/Host）；核对每个条目是否精确到具体值。
   - 完成标准: 通配符清单为空或每项有书面豁免理由；条目粒度到"具体源/具体类型/具体路由"。
5. **验证失败方向**：故意提交一个未登记的新值（新后缀、新路由、新标签），确认系统行为是拒绝。
   - 完成标准: 有可复现的失败关闭证据（请求被拒/功能不可用），而非静默放行。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 值域天然开放的自由文本（正文、评论内容）——标签白名单只适用于富文本结构，正文内容应走输出编码/净化，硬上字符白名单会重演"1<2 被过滤成 1 2"的误杀。
- 讨论某白名单该包含哪些业务条目（允许 jpg 还是 png）——那是业务决策，本 skill 只裁决形态。
- 一次性排查已知恶意样本（IOC 列表）——黑名单作为检测线索仍有价值，只是不能当唯一边界。

### 作者在书中警告的失败模式

- 黑名单被未来演进绕过：HTML5 新标签（video + onloadedmetadata）绕过百度空间 XSS Filter——词表更新永远落后于标准演进。
- 白名单写成通配符即全开：crossdomain.xml 的 `*`、CORS 的 `*`，"等于没有做任何安全限制"，且制造有防护的假象。
- 只做局部转义当白名单：escape 只覆盖少数字符，不含这些字符的 payload 照样注入——转义表必须完整照抄标准。

### 作者的盲点 / 时代局限

- 案例绑定 2014 年技术栈（Flash crossdomain.xml、IE8 XSS Filter、PHP 后缀变体），具体词表已过时，但"失败开放 vs 失败关闭"的机制判断不随技术过期。
- 未讨论现代豁免场景：灰度发布、特性开关（feature flag）需要临时放行时的白名单治理流程（TTL、审批、自动回收），引用时需补。

### 容易混淆的邻近方法论

- "不可预测性"（`whitehat-unpredictability`）：随机 id 常被误当成"更细的黑名单预防"，实际它是抬高枚举成本，与白名单互补而非替代。
- "数据最小化"（`whitehat-data-minimization`）：授权最小化（要什么凭据）与规则白名单（允许什么行为）同源但作用对象不同。
